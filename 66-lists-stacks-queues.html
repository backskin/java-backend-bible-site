66. Связные списки, стеки, очереди и деки

13 165 слов≈ 1 ч 15 мин чтения
Зачем это знать

В бэкенде LinkedList и queue почти никогда не выглядят как «чистая структура данных» в вакууме. Они показывают себя в реестрах событий, планировщиках задач, кэше LRU, потоках данных и обработке HTTP-очередей. Стеки и очереди — это не просто абстракции из учебника: они появляются в коде, где важна временная локальность, ограничение на память, контроль очередности и потоковая обработка. На собеседовании именно эти структуры чаще всего проверяют, умеет ли кандидат отличить «внешнее API» от «внутренней механики» и не перепутать хранимое состояние с логикой доступа.

Связные списки, стеки, очереди и деки — это базовый слой для всех алгоритмов, где важен порядок и последовательность операций, а не произвольный доступ по индексу. В массиве чтение по i почти всегда быстро, но вставка и удаление в середине дорого, потому что сдвигаются соседние элементы. В связном списке всё наоборот: вставка и удаление по указателю дешевы, а доступ по индексу — линейный. Стек и очередь — частные случаи этого принципа: они определяют правила, по которым элементы добавляются и извлекаются, а не способ хранения. Именно поэтому главный вопрос в этой главе не «что такое list», а «какая операция у вас доминирует: произвольный доступ, вставка в голову, извлечение по приоритету, управление окном или моментальная проверка хвоста».

1. Список и массив

1.1 Массивы, списки и модель доступа

Массив — это блок памяти с последовательными ячейками. По индексу можно получить элемент за O(1), но вставка в середину требует смещения хвоста и даёт O(n). В системах, где важен быстрый проход по данным, хороший локальный массив часто выигрывает по кэшу и скорости. В Java это int[], long[], Object[] и ArrayList: массив хранит элементы последовательно, а ArrayList лишь управляет ёмкостью и ростом.

Связный список строится иначе. У него есть узлы: каждый узел хранит value и ссылку на следующий элемент. Если это двусвязный список, у узла есть ещё и ссылка на предыдущий. Это даёт O(1) на вставку/удаление после найденной точки, но O(n) на поиск по индексу, потому что придётся пройти цепочку. Для бэкенда это означает: связный список полезен там, где есть потоковая обработка, много вставок и удаления по предсказуемым точкам, а не там, где нужно быстро обратиться к середине по индексу.

🔧 Под капотом. В Java LinkedList реализован как двусвязный список, а не как список на массиве. Это даёт O(1) для addFirst, addLast, removeFirst, removeLast, но не для get(i): для этого придётся идти по ссылкам. Поэтому ArrayDeque обычно быстрее для стека/очереди, чем LinkedList, а LinkedList остаётся полезным там, где нужен именно список узлов со ссылками и предсказуемый порядок модификаций.

В практическом коде список не выбирают «по красоте». Его выбирают по операции: если вы постоянно добавляете в голову, удаляете в хвосте и не нужны случайные индексы, связный список может быть естественным решением. Но в банке и микросервисах это чаще всего не то, что вы реально хотите: там намного чаще подходят ArrayDeque, ArrayList, HashMap и PriorityQueue. Связный список переоценивают в интервью и недооценивают в production, хотя в некоторых местах он всё ещё вполне уместен: кэш LRU, алгоритмы планирования, объединение цепочек событий, трекеры случайно связанных объектов.

1.2 Односвязный список: минимум механики

Односвязный список выглядит как набор узлов:

Java
class Node {
    int value;
    Node next;
}

Вставка в голову выглядит так:

Java
static Node pushFront(Node head, int x) {
    Node node = new Node();
    node.value = x;
    node.next = head;
    return node;
}

Удаление головы:

Java
static Node popFront(Node head) {
    if (head == null) return null;
    return head.next;
}

Это наивный пример, но он показывает саму идею: у нас нет «массива» с перераспределением памяти; мы лишь перетаскиваем ссылки. В задачах на собеседовании часто просят развернуть список, обнаружить цикл, найти средний элемент, слить два отсортированных списка или найти пересечение. Везде ключевая идея — не ломать ссылочную цепь и держать корректный инвариант: от текущего узла можно добраться до следующего, а затем до конца.

1.3 Двусвязный список: зачем нужен prev

У двусвязного списка у каждого узла есть prev и next.

Java
class DoublyNode {
    int value;
    DoublyNode prev;
    DoublyNode next;
}

С ним проще удалять текущий узел без ссылки на голову:

Java
static void deleteNode(DoublyNode node) {
    if (node == null) return;
    if (node.prev != null) node.prev.next = node.next;
    if (node.next != null) node.next.prev = node.prev;
}

Такой список удобен для LRU-кэша, буфера с быстрым удалением по ключу и двусторонних очередей. В Java LinkedHashMap внутри держит двусвязный список для порядка доступа, а ArrayDeque — кольцевой буфер, который сильно быстрее на обычной очереди, но не умеет гарантировать бесконечное расширение без копирования массива.

⚠️ Осторожно. Список почти всегда ломают не из-за самой структуры, а из-за забытых ссылок. Если вы удаляете узел и не обновили prev.next или next.prev, в цепочке остаются висячие звенья. Если вы вставляете в середину, надо соблюдать порядок:

  1. присоединить новый узел к prev и next;
  2. обновить соседей;
  3. только потом продолжить обход.

Иначе можно потерять часть списка или получить цикл.

2. Задачи на связные списки: механика и типовые шаблоны

2.1 Задача: разворот списка

Уровень: средний. Встречается как: Reverse Linked List.

Условие. Развернуть односвязный список 1 -> 2 -> 3 -> 4 -> null в 4 -> 3 -> 2 -> 1 -> null.

Ход решения. Нужно не просто «поменять местами соседние элементы», а перетаскивать ссылки. На каждом шаге запоминаем next = head.next, затем меняем head.next = prev, затем сдвигаем prev = head, head = next. Это стандартный «один указатель на previoius, один на current».

Решение на Java.

Java
static Node reverse(Node head) {
    Node prev = null;
    Node cur = head;
    while (cur != null) {
        Node next = cur.next;
        cur.next = prev;
        prev = cur;
        cur = next;
    }
    return prev;
}

Решение на Kotlin.

Kotlin
fun reverse(head: Node?): Node? {
    var prev: Node? = null
    var cur = head
    while (cur != null) {
        val next = cur.next
        cur.next = prev
        prev = cur
        cur = next
    }
    return prev
}

Сложность. O(n) времени, O(1) памяти.

Крайние случаи и ловушки. Пустой список и список из одного элемента. Не забывайте сохранять next до того, как перезаписать cur.next. Если это сделать после, вы потеряете весь хвост и получите разрушение списка. На собеседовании это очень частая ошибка.

Дополнительные вопросы. «А как развернуть за k элементов?» — добавляем счётчик и небольшую логику. «А как развернуть рекурсивно?» — это возможность показать понимание рекурсии и стека вызовов.

2.2 Задача: обнаружение цикла в списке

Уровень: средний. Встречается как: Linked List Cycle.

Условие. Дан список, возможно, с циклом. Нужно определить, есть ли цикл, и, если да, найти начало цикла.

Ход решения. Алгоритм Флойда: slow шагает на 1, fast — на 2. Если они когда-нибудь встретятся, цикл есть. Для определения начала цикла снова двигаем slow с головы и fast с места встречи: в момент совпадения они будут в точке входа в цикл. Это одна из самых красивых задач на связные списки, потому что она показывает идею сокращения пространства до O(1), а не до O(n).

Решение на Java.

Java
static boolean hasCycle(Node head) {
    Node slow = head, fast = head;
    while (fast != null && fast.next != null) {
        slow = slow.next;
        fast = fast.next.next;
        if (slow == fast) return true;
    }
    return false;
}

Решение на Kotlin.

Kotlin
fun hasCycle(head: Node?): Boolean {
    var slow = head
    var fast = head
    while (fast != null && fast.next != null) {
        slow = slow!!.next
        fast = fast.next!!.next
        if (slow === fast) return true
    }
    return false
}

Сложность. O(n) времени, O(1) памяти.

Крайние случаи и ловушки. Если список пустой, head == null, всё корректно. Если цикл очень короткий, fast и slow встречаются быстро; важно не забыть проверку fast.next. Если список не цикличен, алгоритм заканчивается и возвращает false. Чтобы найти начало цикла, используем второй проход.

Дополнительные вопросы. «А если нужно найти длину цикла?» — после встречи надо посчитать шаги до следующего совпадения. «А если список большой и нужно распознать несколько циклов?» — уже другая архитектура: это не обычный список, а граф с повторяющимися ссылками.

2.3 Задача: соединение двух отсортированных списков

Уровень: средний. Встречается как: Merge Two Sorted Lists.

Условие. Есть два отсортированных односвязных списка. Объединить их в один отсортированный список.

Ход решения. Два указателя: a и b. В каждом шаге выбираем меньший текущий узел и встраиваем его в результирующий список в порядке сортировки. Это тот же merge sort, но применённый к спискам. Здесь ключевая мысль — не возвращать всё заново в массив и не копировать данные; мы переставляем ссылки.

Решение на Java.

Java
static Node mergeSorted(Node a, Node b) {
    Node dummy = new Node();
    Node tail = dummy;
    while (a != null && b != null) {
        if (a.value <= b.value) {
            tail.next = a;
            a = a.next;
        } else {
            tail.next = b;
            b = b.next;
        }
        tail = tail.next;
    }
    tail.next = (a != null) ? a : b;
    return dummy.next;
}

Решение на Kotlin.

Kotlin
fun mergeSorted(a: Node?, b: Node?): Node? {
    val dummy = Node(0)
    var tail: Node? = dummy
    var left = a
    var right = b
    while (left != null && right != null) {
        if (left.value <= right.value) {
            tail?.next = left
            left = left.next
        } else {
            tail?.next = right
            right = right.next
        }
        tail = tail?.next
    }
    tail?.next = left ?: right
    return dummy.next
}

Сложность. O(n + m) времени, O(1) дополнительной памяти.

Крайние случаи и ловушки. Если один список пустой, возвращаем второй. Если оба пустые, возвращаем null. Обязательно конструировать dummy, иначе придётся отдельно обрабатывать голову. Если не обновить tail = tail.next после вставки, всё будет собираться в один узел и список перестанет двигаться.

2.4 Задача: пересечение двух списков

Уровень: средний. Встречается как: Intersection of Two Linked Lists.

Условие. Даны два списка с общей хвостовой частью. Найти точку пересечения без O(n + m) памяти.

Ход решения. Два указателя идут по разным спискам с одинаковой длиной «путешествия» по сумме длин, но с учётом разницы в стартовых позициях. Сначала вычисляем длины, затем выравниваем хвосты и идём параллельно. Если в какой-то момент указатели совпадают, это точка пересечения. Это ещё один хороший пример, где структура данных управляет поведением: хвосты списков совпадают, так что разукладка по длинам даёт корректный ответ.

Решение на Java.

Java
static int length(Node head) {
    int len = 0;
    while (head != null) {
        len++;
        head = head.next;
    }
    return len;
}

static Node intersect(Node a, Node b) {
    int lenA = length(a), lenB = length(b);
    while (lenA > lenB) {
        a = a.next;
        lenA--;
    }
    while (lenB > lenA) {
        b = b.next;
        lenB--;
    }
    while (a != null && b != null) {
        if (a == b) return a;
        a = a.next;
        b = b.next;
    }
    return null;
}

Сложность. O(n + m) времени, O(1) памяти.

Крайние случаи и ловушки. Если списки не пересекаются, оба указателя дойдут до null. Если начать сравнение до выравнивания, можно получить ложный «пересечение» в самом начале. Это достаточно простой алгоритм, но на собеседовании он часто проверяет внимательность к структуре инварианта.

3. Стек: LIFO и его инженерный смысл

Стек — это «последний вошёл, первый вышел» (Last In, First Out). В порядке выполнения кода он обычно моделирует вызовы функций, вложенные блоки, поворот выполнения и обработку временных структур. На собеседовании стек чаще всего встречается в задачах про скобочные последовательности, обратную польскую запись, минимальные элементы и вычисление выражений. В производстве стек возникает в виде списка задач, развёрнутых сессий, рекурсии, буфера для обработки событий и in-memory pipeline.

3.1 Устройство и применение стека

Стек может быть реализован на массиве или на связном списке. На массиве это обычно ArrayDeque<Integer> в Java и ArrayDeque/MutableList в Kotlin. На связном списке — это push/pull из головы. Операции push, pop, peak стоят O(1) при корректной реализации. Под капотом у стека нет магии: любая операция — это изменение указателя на вершину или выделение/освобождение элемента.

В JVM стек вызовов у каждого потока уже есть, поэтому в чистом виде программный стек и стек вызовов — разные вещи. Но идея одна: порядок возврата должен быть «последний вошёл — первый вышёл». Это как трассировка сообщений, а также важный инвариант для рекурсии, операторов и анализаторов выражений.

3.2 Задача: проверка корректности скобочной последовательности

Уровень: разминка. Встречается как: Valid Parentheses.

Условие. Проверить, что строка с ()[]{} закрывается корректно, то есть каждая открывающая скобка закрывается соответствующей закрывающей.

Ход решения. Идём по строке слева направо. Если видим открывающую скобку — кладём её в стек. Если видим закрывающую — проверяем, совпадает ли она с вершиной стека. Если совпадает, выталкиваем; если нет — строка некорректна. По завершении проверяем, пуст ли стек.

Решение на Java.

Java
static boolean validParentheses(String s) {
    Deque<Character> stack = new ArrayDeque<>();
    for (char ch : s.toCharArray()) {
        if (ch == '(' || ch == '[' || ch == '{') stack.push(ch);
        else {
            if (stack.isEmpty()) return false;
            char top = stack.pop();
            if ((ch == ')' && top != '(') ||
                (ch == ']' && top != '[') ||
                (ch == '}' && top != '{')) {
                return false;
            }
        }
    }
    return stack.isEmpty();
}

Решение на Kotlin.

Kotlin
fun validParentheses(s: String): Boolean {
    val stack = ArrayDeque<Char>()

        else {

            val top = stack.removeFirst()
            if ((ch == ')' && top != '(') ||
                (ch == ']' && top != '[') ||
                (ch == '}' && top != '{')) {
                return false
            }
        }
    }
    return stack.isEmpty()
}

Сложность. O(n) времени, O(n) памяти.

Крайние случаи и ловушки. Пустая строка допустима и должна возвращать true. Если строка заканчивается открывающей скобкой без закрытия, стек не пустой и мы возвращаем false. Часто кандидат путает открывающие и закрывающие скобки или проверяет только тип закрывающей, но не сравнивает с вершиной.

Дополнительные вопросы. «А если скобки могут быть более сложными: много типов или вложение с приоритетом?» — тогда стек всё равно работает, но логика сравнения может быть сложнее. «А если это не просто скобки, а выражение с операторами?» — уже задача на обратную польскую запись или стек с приоритетами.

3.3 Задача: минимальный элемент в стеке

Уровень: средний. Встречается как: Min Stack.

Условие. Поддерживать стек и быстро отвечать на запрос «какой минимальный элемент сейчас в стеке?» без O(n).

Ход решения. У обычного стека нет операции min(). Если хранить отдельно минимумы в дополнительном стеке, то при push мы кладём элемент только если он меньше или равен текущему минимуму. При pop удаляем вершину из обоих стеков, если она равна минимуму. Это даёт O(1) для push, pop, min и легко объясняется на интервью.

Решение на Java.

Java
static class MinStack {
    Deque<Integer> values = new ArrayDeque<>();
    Deque<Integer> mins = new ArrayDeque<>();

    void push(int x) {
        values.push(x);
        if (mins.isEmpty() || x <= mins.peek()) mins.push(x);
    }

    void pop() {
        if (values.isEmpty()) return;
        int x = values.pop();
        if (!mins.isEmpty() && x == mins.peek()) mins.pop();
    }

    int min() {
        return mins.peek();
    }
}

Решение на Kotlin.

Kotlin
class MinStack {
    private val values = ArrayDeque<Int>()
    private val mins = ArrayDeque<Int>()

    fun push(x: Int) {
        values.addFirst(x)
        if (mins.isEmpty() || x <= mins.first()) mins.addFirst(x)
    }

    fun pop() {
        if (values.isEmpty()) return
        val x = values.removeFirst()
        if (mins.isNotEmpty() && x == mins.first()) mins.removeFirst()
    }

    fun min(): Int = mins.first()
}

Сложность. O(1) на каждую операцию, O(n) памяти.

Крайние случаи и ловушки. Если значения повторяются, условие должно быть <=, чтобы избежать потери минимума при повторяющемся значении. Нужно снимать минимум из второго стека только тогда, когда удаляется текущий минимум, иначе min() будет некорректным. Иногда спрашивают и top(); это просто values.peek().

3.4 Монотонный стек

Монотонный стек — это стек, в котором элементы отсортированы по определённому правилу, например по возрастанию или убыванию. Он используется в задачах про следующий больший элемент, уличный дождь, высоту барьеров, гистограммы и профиль нагрузки. Идея проста: когда новый элемент больше/меньше вершины, они бывают связаны; если нет — стек очищается до подходящего условия. Это классический шаблон на интервью, потому что он решает задачи с локальными сравнениями на O(n).

Пример: для массива [2, 1, 2, 4] нужно найти следующий больший элемент для каждого индекса. Поддерживаем стек индексов, уменьшающихся по значению. Когда новая величина больше вершины, она «поднимает» предыдущее значение и позволяет вычислить следующий больший элемент.

Решение на Java.

Java
static int[] nextGreater(int[] a) {
    int[] out = new int[a.length];
    Deque<Integer> stack = new ArrayDeque<>();
    for (int i = a.length - 1; i >= 0; i--) {
        while (!stack.isEmpty() && a[stack.peek()] <= a[i]) {
            stack.pop();
        }
        out[i] = stack.isEmpty() ? -1 : a[stack.peek()];
        stack.push(i);
    }
    return out;
}

Сложность. O(n) времени, O(n) памяти.

Крайние случаи и ловушки. Для равных значений важно выбрать строгое сравнение. Если вы допускаете <=, равные элементы будут удаляться из стека, а это влияет на корректность и иногда даже на логическую интерпретацию задачи. В задачах про гистограмму и воду нужно не только проверять высоту, но и сохранять текущие индексы и понимать, что область начинает формироваться только тогда, когда стек не пуст.

4. Очередь: FIFO и её важность в системах обработки

Очередь — это «первый вошёл, первый вышёл» (First In, First Out). В системах она встречается везде: очереди сообщений, буфер обмена, пул задач, обработка пакетов, HTTP-соединения, backlog процессов, брокеры сообщений и API-вызовы. Структура важна не сама по себе, а тем, что она описывает порядок: один и тот же запрос должен быть обработан в порядке поступления, если не предусмотрена специальная логика приоритета.

Словарь: FIFO

4.1 Очередь на массиве и на связном списке

В Java наиболее практичная очередь — ArrayDeque. Её используют и как очередь, и как стек. Она работает как кольцевой буфер, что особенно удобно для сильно нагруженных потоков и обработки событий. LinkedList тоже реализует Deque, но для обычной очереди он обычно проигрывает в памяти и производительности за счёт объектов и ссылок.

Java
Deque<Integer> queue = new ArrayDeque<>();
queue.offer(1);
queue.offer(2);
int x = queue.poll();

Если данные идут потоком и финальный порядок важен, очередь как раз и помогает отложить обработку. В больших системах это видно в Kafka, очередях задач и планировщиках процессов: можно складывать данные в буфер, а затем обрабатывать их по порядку, с ограничением по скорости и возможностью сглаживания всплесков.

4.2 Задача: очередь на двух стеках

Уровень: средний. Встречается как: Implement Queue using Stacks.

Условие. Реализовать очередь с операциями enqueue и dequeue, используя только два стека.

Ход решения. Идея в том, что один стек хранит входящие элементы, второй — выходящие. Если второй стек пуст, перекидываем все элементы из первого во второй. Тогда старый элемент оказывается на вершине стека, и dequeue получает порядок FIFO. Это типичная interview-идея: сочетание двух LIFO-структур даёт один FIFO-интерфейс.

Решение на Java.

Java
static class MyQueue {
    Deque<Integer> in = new ArrayDeque<>();
    Deque<Integer> out = new ArrayDeque<>();

    void enqueue(int x) { in.push(x); }

    int dequeue() {
        if (out.isEmpty()) {
            while (!in.isEmpty()) out.push(in.pop());
        }
        return out.pop();
    }
}

Решение на Kotlin.

Kotlin
class MyQueue {
    private val input = ArrayDeque<Int>()
    private val output = ArrayDeque<Int>()

    fun enqueue(x: Int) = input.addFirst(x)

    fun dequeue(): Int {
        if (output.isEmpty()) {
            while (input.isNotEmpty()) output.addFirst(input.removeFirst())
        }
        return output.removeFirst()
    }
}

Сложность. O(1) амортизированно на dequeue, O(n) в худшем случае, когда приходится перекидывать стек. Память O(n).

Крайние случаи и ловушки. Если вы выполняете dequeue и out не пуст, берите из него, не трогая in. Если in и out оба пусты, это корректная ошибка: очередь пуста. Тонкая ловушка — использовать peek и pop в одном и том же порядке; легко потерять элемент или нарушить состояние двух стеков.

4.3 Монотонная очередь

Монотонная очередь — это очередь, в которой элементы хранятся в отсортированном порядке относительно ключа. Обычно она используется для задач про окно: максимум/минимум в скользящем окне, обработку потока событий и планирование в реальном времени. Идея следующая: пока хвостовой элемент меньше нового, удаляем хвост; вставляем новый, а в окно сдвигаем границы и фиксируем максимум.

Решение на Java.

Java
static int[] slidingMax(int[] a, int k) {
    Deque<Integer> dq = new ArrayDeque<>();
    int[] out = new int[a.length - k + 1];
    for (int i = 0; i < a.length; i++) {
        while (!dq.isEmpty() && dq.peekFirst() <= i - k) dq.pollFirst();
        while (!dq.isEmpty() && a[dq.peekLast()] <= a[i]) dq.pollLast();
        dq.offerLast(i);
        if (i >= k - 1) out[i - k + 1] = a[dq.peekFirst()];
    }
    return out;
}

Сложность. O(n) времени, O(k) памяти.

Крайние случаи и ловушки. Если окно k == 0 или k > a.length, нужно определить поведение явно. Важно, что в монотонной очереди значения хранятся отсортированно по индексу и по величине одновременно. Если перепутать очередной порядок и удаление по условию, вы получите максимумы неправильных окон.

5. Дек: очередь с двумя концами

Дек (deque, double-ended queue) позволяет добавлять и удалять элементы с обеих сторон: offerFirst, offerLast, pollFirst, pollLast. Для бэкенда это полезная структура при реализации протоколов, очередей задач и алгоритмов с двумя направлениями: накапливать вход, быстро бросать на аутсайдер, быстро извлекать и из начала, и из конца.

В Java чаще всего используют ArrayDeque для Deque и ArrayBlockingQueue/LinkedBlockingDeque для многопоточных сценариев. В Java LinkedList тоже реализует Deque, но он не лучший выбор для высокой нагрузки и частых сетевых/потоковых операций, потому что работает через объекты и ссылки, а не через массив. В Kotlin ArrayDeque — стандартный инструмент для стеков и деки.

5.1 Удобство и неудобство дека

Дек удобен, когда нужно:

  • иметь оба конца приоритетными;
  • быстро добавлять слева и справа;
  • реализовать алгоритмы типа мониторов температуры, кредитных лимитов, логики обратной последовательности и сценариев с частым вращением окон.

Дек не всегда удобен, когда:

  • нужен по-настоящему большой объём и много операций с индексацией;
  • нужен порядок доступа по get(i) на каждом шаге;
  • нужна строгая совместимость со списком как последовательностью, а не двусторонней очередь.

5.2 Задача: палиндром с помощью дека

Уровень: разминка. Встречается как: Palindrome Check.

Условие. Проверить, является ли строка палиндромом, используя двустороннюю очередь.

Ход решения. Добавляем символы в дек с обоих концов или просто в хвост и проверяем пары. Если на внешних позициях символы не совпадают, строка не палиндром. Это хороший демонстрационный пример: дек позволяет сравнивать символы с начала и конца без полного массива или сложности с индексами.

Решение на Java.

Java
static boolean isPalindrome(String s) {
    Deque<Character> dq = new ArrayDeque<>();
    for (char ch : s.toCharArray()) dq.offerLast(ch);
    while (dq.size() > 1) {
        if (dq.pollFirst() != dq.pollLast()) return false;
    }
    return true;
}

Сложность. O(n) времени, O(n) памяти.

Крайние случаи и ловушки. Здесь иногда забывают учитывать регистр, пунктуацию и пробелы. В реальных задачах по строкам это не просто «проверка палиндрома», а «нормализовать строку», убрать символы и сравнить только буквенно-цифровые фрагменты. Вынос нормализации в отдельный метод — типичный инженерный шаг.

6. LRU-кэш: связный список и словарь в одном месте

LRU (Least Recently Used) — это не просто «кэш с TTL», а способ отслеживать актуальность данных по времени использования. Он очень часто реализуется с помощью комбинации HashMap и двусвязного списка. HashMap даёт O(1) для поиска по ключу, а двусвязный список — O(1) для удаления и вставки в начало/конец. Это один из лучших примеров, где две структуры данных работают вместе и каждая несёт свою половину логики.

Классический вариант:

  • HashMap<Key, Node> даёт доступ к узлу по ключу;
  • двусвязный список хранит порядок использования; самый старый элемент — хвост, самый свежий — голова;
  • при get(key) перемещаем узел в голову;
  • при put(key, value) либо обновляем существующий узел, либо вставляем новый в голову;
  • если размер превышает capacity, удаляем хвост.

Решение на Java.

Java
static class LRUCache {
    static class Node {
        int key, value;
        Node prev, next;
    }

    final int capacity;
    final Map<Integer, Node> map = new HashMap<>();
    Node head = new Node();
    Node tail = new Node();

    LRUCache(int capacity) {
        this.capacity = capacity;
        head.next = tail;
        tail.prev = head;
    }

    int get(int key) {
        Node node = map.get(key);
        if (node == null) return -1;
        moveToHead(node);
        return node.value;
    }

    void put(int key, int value) {
        Node node = map.get(key);
        if (node != null) {
            node.value = value;
            moveToHead(node);
            return;
        }
        if (map.size() == capacity) {
            Node oldest = tail.prev;
            remove(oldest);
            map.remove(oldest.key);
        }
        Node fresh = new Node();
        fresh.key = key;
        fresh.value = value;
        addToHead(fresh);
        map.put(key, fresh);
    }

    void addToHead(Node node) {
        node.prev = head;
        node.next = head.next;
        head.next.prev = node;
        head.next = node;
    }

    void remove(Node node) {
        node.prev.next = node.next;
        node.next.prev = node.prev;
    }

    void moveToHead(Node node) {
        remove(node);
        addToHead(node);
    }
}

Сложность. O(1) на get и put при корректной реализации, O(capacity) памяти.

Крайние случаи и ловушки. Здесь обычно ломают порядок ссылок: если удаляете узел и потом вставляете в голову, важно, чтобы head.next и tail.prev были актуальны. В реальных сервисах LRU часто оказывается плохим решением, когда один элемент очень популярен и почти всё время переходит в голову: справедливее или эффективнее работают LFU, Window-TinyLFU и стратифицированный кэш, особенно в JVM-кэше и прокси-кэше. Но для учебных задач LRU остаётся эталонной структурой.

💡 На интервью. LRU показывает, что вы понимаете связь между схемой хранения и операционным интерфейсом. Внутри он не «магия» — это HashMap + двусвязный список, где HashMap даёт быстрый доступ, а список удерживает порядок «самые старые и самые новые».

6.1 Задача: удалить средний узел без доступа к head

Уровень: средний. Встречается как: Delete Node in a Linked List.

Условие. Дан узел в середине списка, не заголовок; нужно удалить его, не меняя ссылку на голову. Важно, что в реальном списке такого узла может не быть, а сам контекст обычно предполагает, что мы знаем только выделенный объект.

Ход решения. Если у узла есть next, то можно скопировать значение следующего узла в текущий, а затем переподключить ссылку на следующий после следующего. Это работает, потому что на уровне данных узел не обязан хранить собственную адресацию в списке; он должен быть частью цепи. Мы удаляем логически следующий элемент, а физически заменяем содержимое текущего на next.value и переподключаем ссылку.

Решение на Java.

Java
static void deleteNode(Node node) {
    if (node == null || node.next == null) return;
    node.value = node.next.value;
    node.next = node.next.next;
}

Решение на Kotlin.

Kotlin
fun deleteNode(node: Node?) {
    if (node == null || node.next == null) return
    node.value = node.next.value
    node.next = node.next.next
}

Сложность. O(1) времени и O(1) памяти.

Крайние случаи и ловушки. Невозможно удалить хвостовой узел, потому что у него нет следующего. Это важно в условии и должно быть явно зафиксировано. Частая ошибка — думать, что можно просто «сдвинуть ссылку назад» без копирования данных. Вспомните, что у вас есть только указатель на текущий узел, а не на предыдущий, поэтому единственный безопасный путь — переписать значение и сместить цепочку.

6.2 Задача: определить начало цикла и длину цикла

Уровень: сложный. Встречается как: Find Cycle Start and Length.

Условие. В списке может быть цикл. Найдите длину цикла и точку, с которой он начинается.

Ход решения. Сначала находим встречу slow и fast с помощью алгоритма Флойда. Затем вычисляем длину цикла: двигаем один указатель до совпадения и считаем шаги. После этого запускаем slow от головы и второй указатель от start через length шагов; в момент совпадения они встречаются в начале цикла. Чтобы не путаться, меняйте только одно состояние за раз и помните: meet и start — это разные моменты в одном и том же цикле.

Решение на Java.

Java
static Node findCycleStart(Node head) {
    Node slow = head, fast = head;
    while (fast != null && fast.next != null) {
        slow = slow.next;
        fast = fast.next.next;
        if (slow == fast) break;
    }
    if (fast == null || fast.next == null) return null;

    slow = head;
    while (slow != fast) {
        slow = slow.next;
        fast = fast.next;
    }
    return slow;
}

Сложность. O(n) времени, O(1) памяти.

Крайние случаев и ловушки. Если список без цикла, fast доходит до null и функция возвращает null. Если в цикле есть только один элемент, он тоже работает; slow и fast встретятся на этом одном узле. Это хороший пример, когда одна и та же структура вызывает вопрос: «сначала надо найти факт, потом — начало и длину», а не «сразу решить всё одним проходом».

6.3 Очередь и буфер в системах: ring buffer и producer-consumer

В продакшене очередь редко выглядит как LinkedList. Чаще это кольцевой буфер (ring buffer), потому что массив фиксированного размера и два индекса — head и tail — дают очень предсказуемую и быструю модель. Producer пишет в хвост, consumer читает из головы. Когда tail догоняет head, буфер заполнен, и нужно решать, что делать: блокировать, отбрасывать, применять backpressure или буферизировать на другом уровне.

Это ключевой механизм для сетевых стеков, логгеров, очередей событий и блокировочных систем с ограниченной памятью. В Java ArrayBlockingQueue, LinkedBlockingQueue и ArrayDeque отдают нам примерно эту же модель, но на уровни выше. В APM и брокерах это всё визуально выглядит как «буфер в памяти», а в реальности там часто вовлечены Semaphore, Condition, ReentrantLock и понятие backpressure.

Решение на Java.

Java
static class RingBuffer {
    private final int[] buf;
    private int head = 0, tail = 0, size = 0;

    RingBuffer(int capacity) { this.buf = new int[capacity]; }

    boolean offer(int value) {
        if (size == buf.length) return false;
        buf[tail] = value;
        tail = (tail + 1) % buf.length;
        size++;
        return true;
    }

    Integer poll() {
        if (size == 0) return null;
        int v = buf[head];
        head = (head + 1) % buf.length;
        size--;
        return v;
    }
}

Сложность. O(1) на offer и poll, O(n) памяти на буфер.

Крайние случаи и ловушки. Пустой буфер и полный буфер — это разные состояния и разные политики. В сетевом коде полное состояние часто означает, что надо снижать throughput или отбрасывать сообщения, а не замолкать. Допущение «сначала пишем, потом читаем» может ломать модель, если вы забыли учитывать size и индексы head/tail.

6.4 Задача: обратная польская запись (RPN)

Уровень: средний. Встречается как: Evaluate Reverse Polish Notation.

Условие. Дана строка с выражением в обратной польской записи, например "2 3 + 4 *", вычислить результат.

Ход решения. Когда встречаем число, кладём его в стек; когда встречаем оператор, берём два последних значения, вычисляем результат и кладём обратно. Это классический пример, где стек не просто удобен, а прямо отражает модель вычисления: каждая операция работает над последними двумя аргументами.

Решение на Java.

Java
static int evalRPN(String[] tokens) {
    Deque<Integer> stack = new ArrayDeque<>();
    for (String token : tokens) {
        switch (token) {
            case "+" -> stack.push(stack.pop() + stack.pop());
            case "-" -> {
                int b = stack.pop();
                int a = stack.pop();
                stack.push(a - b);
            }
            case "*" -> stack.push(stack.pop() * stack.pop());
            case "/" -> {
                int b = stack.pop();
                int a = stack.pop();
                stack.push(a / b);
            }
            default -> stack.push(Integer.parseInt(token));
        }
    }
    return stack.pop();
}

Решение на Kotlin.

Kotlin
fun evalRPN(tokens: Array<String>): Int {
    val stack = ArrayDeque<Int>()
    for (token in tokens) {
        when (token) {
            "+" -> stack.addFirst(stack.removeFirst() + stack.removeFirst())
            "-" -> {
                val b = stack.removeFirst()
                val a = stack.removeFirst()
                stack.addFirst(a - b)
            }
            "*" -> stack.addFirst(stack.removeFirst() * stack.removeFirst())
            "/" -> {
                val b = stack.removeFirst()
                val a = stack.removeFirst()
                stack.addFirst(a / b)
            }
            else -> stack.addFirst(token.toInt())
        }
    }
    return stack.removeFirst()
}

Сложность. O(n) времени, O(n) памяти.

Крайние случаи и ловушки. В Java stack.pop() два раза внутри выражения может дать неверный порядок, потому что первое извлечение снимает верхний элемент; это означает, что выражение нужно аккуратно парсить с сохранением локальных переменных. a / b и a - b должны вычисляться в корректном порядке. Это простая версия задачи, но она очень хорошо показывает, как стек на самом деле моделирует вычислительный процесс.

6.5 Очереди в бэкенде: backlog, rate limiter и планирование задач

В продакшене очередь редко используется просто как структура; чаще это элемент управления потоком. В API-гейтвеях, service mesh и бэкенд-скарпинге очередь встречается как место, где временно задерживаются входящие запросы и истощается нагрузка. В планировщиках задач очередь отвечает за порядок выполнения, а при наличии приоритетов используется PriorityQueue или перевод на mutation/ordering.

Структура в реальном сервисе может выглядеть так:

  • запрос приходит в обработку;
  • он кладётся в очередь задач;
  • worker-поток извлекает его и делает вычисления;
  • в случае ошибок/таймаутов задача уходит в retry queue или DLQ;
  • при устойчивой перегрузке может быть включён rate limiter и backpressure.

Вот где и видно, что стек/очередь — это не «учебные контейнеры», а механизм управления потоками и очередностью. На практике они почти всегда находятся под другими слоями: ExecutorService, BlockingQueue, DelayQueue, Spring-TaskExecutor, Kafka topics, RabbitMQ queues. Алгоритмическая форма обслуживания остаётся той же, просто уровень абстракции выше.

6.6 Задача: max/min в окне за O(n)

Уровень: сложный. Встречается как: Sliding Window Maximum.

Условие. Для массива и окна длины k найти максимум в каждом окне.

Ход решения. Используем монотонную очередь: в ней индексы хранятся в порядке убывания значений. При добавлении нового элемента удаляем мелкие значения с конца, потому что они уже не будут максимумом в текущем окне. При сдвиге окна удаляем индексы, которые выпали за границы окна. Это один из самых стандартизованных шаблонов в алгоритмах с очередями.

Решение на Java.

Java
static int[] maxSlidingWindow(int[] nums, int k) {
    if (nums.length == 0) return new int[0];
    Deque<Integer> dq = new ArrayDeque<>();
    int[] out = new int[nums.length - k + 1];

    for (int i = 0; i < nums.length; i++) {
        while (!dq.isEmpty() && dq.peekFirst() <= i - k) {
            dq.pollFirst();
        }
        while (!dq.isEmpty() && nums[dq.peekLast()] <= nums[i]) {
            dq.pollLast();
        }
        dq.offerLast(i);
        if (i >= k - 1) {
            out[i - k + 1] = nums[dq.peekFirst()];
        }
    }
    return out;
}

Сложность. O(n) времени, O(k) памяти.

Крайние случаи и ловушки. На самом деле это не просто про максимум: похожий шаблон используется и для минимума, и для окна с условием «данных упало» или «данных выросло». Во многих задачах всплывает понятие активного окна, и алгоритм накапливает только те элементы, которые все ещё представляют интерес для будущего.

6.7 Куча и приоритетная очередь как части очереди

У PriorityQueue другой логический смысл: это не про порядок поступления, а про приоритет. Если обычная очередь обрабатывает первые пришедшие, то PriorityQueue выбрасывает те, у которых приоритет выше. Поэтому её часто используют в планировщиках задач, топ-K выборках и событиях, где new task должно идти в соответствии с приоритетом, а не с временем прихода.

Решение на Java.

Java
static int[] topK(int[] a, int k) {
    PriorityQueue<Integer> pq = new PriorityQueue<>();
    for (int x : a) {
        if (pq.size() < k) pq.offer(x);
        else if (x > pq.peek()) {
            pq.poll();
            pq.offer(x);
        }
    }
    int[] out = new int[pq.size()];
    int i = out.length - 1;
    while (!pq.isEmpty()) out[i--] = pq.poll();
    return out;
}

Сложность. O(n log k) времени, O(k) памяти.

Крайние случаи и ловушки. В обратной логике приоритетная очередь может возвращать не самый ранний элемент, а самый высокий приоритет. Если бизнес-логика требует сначала рано пришедшие, а потом приоритетные, нужно отдельно моделировать очередь с приоритетом и timestamp. Это отличная демонстрация, что на практике очередь — это не только структура, но и контекст: приоритет, тайминг, дедлайны и стратегия вытеснения.

6.8 Задача: следующий меньший элемент

Уровень: средний. Встречается как: Next Smaller Element.

Условие. Для массива чисел найти индекс/значение следующего меньшего элемента слева или справа от каждого элемента.

Ход решения. Этот шаблон — почти брат-близнец к next greater, но логика там обычно чуть тоньше. В стеке храним индексы элементов в порядке возрастания или убывания, а затем проверяем новый элемент относительно вершины. Для задачи «следующий меньший» стек поддерживает строго возрастающую последовательность и выталкивает элементы, пока новый элемент меньше вершины. Это очень частый шаблон в алгоритмах обработки графиков, высоты и визуальных метрик.

Решение на Java.

Java
static int[] nextSmallerLeft(int[] a) {
    int[] out = new int[a.length];
    Deque<Integer> stack = new ArrayDeque<>();
    for (int i = 0; i < a.length; i++) {
        while (!stack.isEmpty() && a[stack.peek()] >= a[i]) {
            stack.pop();
        }
        out[i] = stack.isEmpty() ? -1 : a[stack.peek()];
        stack.push(i);
    }
    return out;
}

Сложность. O(n) времени, O(n) памяти.

Крайние случаи и ловушки. Если нужно именно «следующий меньший справа», проход идёт справа налево. Важна разница между строгим и нестрогим сравнением: если вы проверяете >=, то равные значения будут выталкиваться и больше не будут участвовать в следующем дополнении. В задачах про гистограммы и воду это сомнительно, потому что равная высота может менять форму левой/правой границы и даже давать разные площади.

6.9 Задача: merge k отсортированных списков через heap

Уровень: средний. Встречается как: Merge k Sorted Lists.

Условие. Есть k отсортированных связанных списков и нужно получить один отсортированный список.

Ход решения. В куче держим по одному самому маленькому элементу из каждого списка. Затем мы извлекаем минимум, добавляем его в результат, и сдвигаем указатель в том списке, откуда он пришёл. Это тот же k-way merge, только применённый к списку, а не к массивам. В продакшене это похоже на слияние нескольких потоков данных: от разных источников приходит часть данных, а затем вы ставите их в общий порядок.

Решение на Java.

Java
static Node mergeK(List<Node> lists) {
    PriorityQueue<Node> heap = new PriorityQueue<>(Comparator.comparingInt(n -> n.value));
    Node dummy = new Node();
    Node tail = dummy;
    for (Node head : lists) {
        if (head != null) heap.offer(head);
    }
    while (!heap.isEmpty()) {
        Node cur = heap.poll();
        tail.next = cur;
        tail = cur;
        if (cur.next != null) heap.offer(cur.next);
    }
    tail.next = null;
    return dummy.next;
}

Сложность. O(n log k) времени, O(k) памяти.

Крайние случаи и ловушки. Если список пустой, его просто пропускают. Важно не потерять хвост основного списка и не оставить tail.next на старом объекте. Для продакшена это обычно выглядит как «сначала пишем в буфер, потом сливаем по chunks»; память ограничена, а не всё место лежит в RAM.

6.10 Работа с очередью и backpressure в реальном сервисе

Немало проблем в бэкенде связано не с тем, «что такое очередь», а с тем, как она ведёт себя при перегрузке. Если worker-потоки одновременно читает поток задач, а producer продолжает писать, то рано или поздно очередь переполняется. Это не просто ошибка логики; это фактический signal о том, что обработка срывается. Обычно выбирают одну из стратегий:

  • блокировать producer до тех пор, пока место освободится;
  • ограничивать вход потоками и отбрасывать часть задач;
  • использовать приоритетную обработку для важных событий;
  • отдавать запрос в retry queue или DLQ;
  • нагружать только выделенный пул, а остальной трафик отправлять в планировщика.

Эта проблема выглядит абстрактно, но по сути она про то, что буфер должен подчиняться лимитам. В финансовой системе одно переполнение очереди может замедлить обработку статуса or create backlog, а в случае платёжных операций это уже вопрос SLA и корректности. Поэтому на собеседованиях иногда спрашивают не только «что такое queue», но и «что делать, если она последние 30 минут переполнена?» — это уже вопрос про backpressure, SLO и архитектурный контроль.

6.11 Задача: стек как механизм вычисления выражения со скобками и приоритетами

Уровень: средний. Встречается как: Basic Calculator/Expression Evaluation.

Условие. Дано выражение вроде "2 + 3 * 4" или "(2 + 3) * 4". Нужно вычислить результат, учитывая приоритеты и скобки.

Ход решения. Здесь используется стек двух видов: один хранит значения, второй — операторы. При чтении символов мы проверяем приоритеты и выталкиваем более приоритетные операторы перед добавлением текущего. Скобки сбрасывают приоритет до закрытия. Похожий шаблон применяют в парсерах и калькуляторах, и именно поэтому стек часто называют «семантическим механизмом вычисления».

Решение на Java.

Java
static int calculate(String s) {
    Deque<Integer> vals = new ArrayDeque<>();
    Deque<Character> ops = new ArrayDeque<>();
    int num = 0;
    for (int i = 0; i < s.length(); i++) {
        char ch = s.charAt(i);
        if (Character.isDigit(ch)) {
            num = num * 10 + (ch - '0');
        } else if (ch == ' ') {
            if (i > 0 && Character.isDigit(s.charAt(i - 1))) {
                vals.push(num);
                num = 0;
            }
        } else {
            if (Character.isDigit(s.charAt(i - 1))) {
                vals.push(num);
                num = 0;
            }
            while (!ops.isEmpty() && precedence(ops.peek()) >= precedence(ch)) {
                apply(vals, ops.pop());
            }
            if (ch != ')') ops.push(ch);
            else {
                while (!ops.isEmpty() && ops.peek() != '(') apply(vals, ops.pop());
                ops.pop();
            }
        }
    }
    if (num != 0) vals.push(num);
    while (!ops.isEmpty()) apply(vals, ops.pop());
    return vals.pop();
}

static int precedence(char op) {
    if (op == '+' || op == '-') return 1;
    if (op == '*' || op == '/') return 2;
    return 0;
}

static void apply(Deque<Integer> vals, char op) {
    int b = vals.pop();
    int a = vals.pop();
    switch (op) {
        case '+' -> vals.push(a + b);
        case '-' -> vals.push(a - b);
        case '*' -> vals.push(a * b);
        case '/' -> vals.push(a / b);
    }
}

Сложность. O(n) времени, O(n) памяти.

Крайние случаи и ловушки. Слишком легко забыть, что числа могут быть многозначными и между ними есть пробелы. В выражениях это особенно важно: перед +/-/*// вы должны «подхватить» накопленное число в стек, иначе операция работает над куском числа или пустым стеком. Схема precedence и apply — это именно тот случай, когда алгоритмический принцип оказывается на практике в калькуляторах и парсерах.

7. Ошибки и антипаттерны

  1. Использование LinkedList как «псевдо-ArrayList». Если основной операция — чтение по индексу, LinkedList почти всегда хуже ArrayList. На больших данных эта разница становится огромной: get(i) на связанном списке — O(n), а в ArrayList — O(1).
  2. Потерянные ссылки в цикле. Для вставки и удаления в связных списках часто забывают обновить prev.next, next.prev или сохранить next до перезаписи. Итог — потерянный хвост или цикл.
  3. Бесконечный цикл из-за неправильного fast/slow. В задачах на цикл очень легко пропустить проверку fast != null && fast.next != null; иначе NullPointerException или неверный результат.
  4. Неправильный выбор <= vs < в монотонной структуре. В стековых задачах, где нужны «следующий больший» или «предыдущий меньший» элементы, знак сравнения определяет, будут ли равные элементы удаляться или останутся, и это меняет результат.
  5. Смешение Stack и Queue. В Java Stack — deprecated, и его не стоит использовать в новой кодовой базе. Легче и безопаснее работать через ArrayDeque и правильный Deque-интерфейс.
  6. Использование рекурсии в структуре без контроля глубины. На больших списках рекурсивное разворачивание или обход может привести к StackOverflowError. Для глубоких структур обычно нужна итеративная версия или -Xss в JVM.
  7. Путаница между стеком вызовов и программным стеком данных. В Java стек вызовов и Deque-структура похожи по идее, но их не стоит смешивать. Один — про управление потоком выполнения, второй — про модель данных.
  8. Невнимание к головному/хвостовому элементу. В queue и deque очень часто ломаются крайние случаи: пустая структура, один элемент, операция с пустым списком. Их нужно тестировать отдельно.
  9. Использование ArrayDeque без контроля переполнения. В деках и очередях накопитель может расти, но если в коде вы явно работаете с фиксированным буфером, надо следить за переполнением и порядком операций на границах.
  10. Ошибки в LRU из-за неактуальной map и list после удаления. Словарь и список всегда должны быть синхронизированы. Если элемент удалён из списка, но остался в HashMap, кэш начинает возвращать устаревшие данные.

8. Диагностика

Для структур данных диагностика обычно сводится к четырём вещам: проверка состояния границ, проверка инвариантов, проверка на повторный проход и проверка на память/объекты.

8.1 Симптомы

  • NullPointerException после нескольких простых операций с head/tail.
  • Постоянно растущая потребность в памяти, хотя логически список должен быть ограничен.
  • Queue «теряет» элемент, потому что offer и poll вызваны в неправильной последовательности.
  • В LRU «старые» элементы не удаляются, хотя capacity исчерпан.
  • В монотонных стек/queue алгоритмах появляются неправильные минимум/максимум в окне, потому что элементы удаляются не в правильной очередности.

8.3 Инварианты для проверки вручную

Для связного списка важны три вещи:

  • отсутствие циклов в обычной ветке;
  • корректный head и tail;
  • все ссылки у соседей совпадают по направлению.

Для стека важно: после каждого push/pop вершина соответствует последнему добавленному элементу; для min() — вершина дополнительного стека хранит актуальный минимум.

Для очереди важно: все элементы идут в порядке поступления, и peek возвращает самый старый доступный элемент. Для ArrayDeque и кольцевого буфера это проверяется через границы индексов и длину.

9. Вопросы на интервью

  1. В чём разница между массивом и списком с точки зрения вставки и удаления? Ответ: в массиве вставка/удаление в середине — O(n), потому что сдвигаются элементы; в связанном списке — O(1) после точки входа, но поиск по индексу — O(n).
  2. Почему ArrayDeque часто лучше LinkedList для очереди и стека? Ответ: ArrayDeque хранит элементы в массиве, имеет хорошие кэши, не создаёт лишние объекты и обычно быстрее для высокой интенсивности операций.
  3. Что такое monotonic stack и где он применяется? Ответ: стек, поддерживающий упорядоченность элементов, часто используется для следующего большего/меньшего элемента, гистограммы и задач со скользящими окнами.
  4. Что такое monotonic queue и чем он отличается от обычной очереди? Ответ: это очередь, где элементы хранятся в сортированном или ограниченном порядке, обычно по значению; её используют для максимумов/минимумов в скользящем окне.
  5. Как проверить, есть ли цикл в связном списке без дополнительной памяти? Ответ: алгоритм Флойда с двумя указателями: slow и fast движутся с разной скоростью; если встречаются, есть цикл.
  6. Почему LRU обычно строят как HashMap + двусвязный список? Ответ: HashMap даёт O(1) для доступа по ключу, а двусвязный список даёт O(1) для удаления и перемещения в начало.
  7. Почему Stack в Java считается устаревшим? Ответ: Stack расширяет Vector и синхронизируется, но это не лучший инструмент для современного кода; обычно используют ArrayDeque с нужным интерфейсом.
  8. В чем разница между queue и deque? Ответ: queue работает только с двух концов в одной логике FIFO, а deque позволяет операции на обоих концах и поэтому пригоден и для стека, и для очереди.
  9. Какой подход лучше для выражений: стек или рекурсия? Ответ: стек, потому что выражения и скобочные последовательности естественно решаются через LIFO-порядок.
  10. Почему peek и poll в ArrayDeque фактически быстрее LinkedList? Ответ: массивная структура лучше использует кэши, требует меньше выделений памяти и меньше ссылок.
  11. Какой смысл у dummy-узла в задачах на списки? Ответ: он упрощает обработку головы и помогает вставлять/удалять элементы без ветвлений на начало списка.
  12. Когда связный список лучше массива? Ответ: когда важны частые вставки/удаления в середине по указателю, а не случайный доступ. Например, списки задач, буферы событий, простые очереди с разворотами и цепочки операций.
  13. Как отличить queue по приоритету от обычной очереди? Ответ: обычная очередь сохраняет порядок вставки, а приоритетная — извлекает элемент с наибольшим/наименьшим приоритетом. Для этого обычно используют PriorityQueue.
  14. Что происходит, если в монотонном стеке сравнение выполняется <=, а не <? Ответ: равные значения могут выталкиваться и это меняет форму окна/гистограммы, теряя часть информации о повторяющихся элементах.
  15. Почему LinkedHashMap — это вроде бы и отображение, и список? Ответ: он хранит хеш-таблицу для доступа по ключу и двусвязный список для логического порядка вставки или доступа.

11.1 Разворот списка по блокам по k

Когда список нужно разворачивать не целиком, а кусками, часто приходит вариант с k-группами. Например, 1 -> 2 -> 3 -> 4 -> 5, k = 2 даёт 2 -> 1 -> 4 -> 3 -> 5. В этой задаче важен не сам разворот, а правильное управление хвостами и границами. Самый частый способ — принимать next у текущего узла, переворачивать k элементов, а затем соединять хвост предыдущей группы с новой группой.

Решение на Java.

Java
static class Node {
    int value;
    Node next;
}

static Node reverseKGroup(Node head, int k) {
    if (head == null || k <= 1) return head;

    Node dummy = new Node();
    dummy.next = head;
    Node prev = dummy;

    while (head != null) {
        Node tail = prev;
        for (int i = 0; i < k; i++) {
            tail = tail.next;
            if (tail == null) return dummy.next;
        }

        Node nextGroup = tail.next;
        Node[] reversed = reverse(head, tail);
        head = reversed[0];
        tail = reversed[1];

        prev.next = head;
        tail.next = nextGroup;
        prev = tail;
        head = nextGroup;
    }
    return dummy.next;
}

static Node[] reverse(Node head, Node tail) {
    Node prev = null;
    Node cur = head;
    while (cur != tail) {
        Node next = cur.next;
        cur.next = prev;
        prev = cur;
        cur = next;
    }
    Node next = cur.next;
    cur.next = prev;
    return new Node[]{cur, head};
}

Решение на Kotlin.

Kotlin
class Node(var value: Int, var next: Node? = null)

fun reverseKGroup(head: Node?, k: Int): Node? {
    if (head == null || k <= 1) return head

    val dummy = Node(0, head)
    var prev = dummy
    var current = head

    while (current != null) {
        var tail = prev
        repeat(k - 1) {
            tail = tail.next ?: return dummy.next
        }

        val nextGroup = tail.next
        val reversed = reverseGroup(current, tail)
        prev.next = reversed.first
        reversed.second?.next = nextGroup
        prev = reversed.second
        current = nextGroup
    }
    return dummy.next
}

fun reverseGroup(head: Node?, tail: Node?): Pair<Node?, Node?> {
    var prev: Node? = null
    var cur = head
    while (cur !== tail) {
        val next = cur?.next
        cur?.next = prev
        prev = cur
        cur = next
    }
    val next = cur?.next
    cur?.next = prev
    return cur to head
}

Сложность. O(n) по времени и O(1) по дополнительной памяти, если считать только несколько указателей. Это хороший пример, где prev/tail и next служат буквально механизмом удержания связи между блоками.

Критическая ловушка. Очень легко потерять хвост предыдущей группы, когда вы меняете prev.next и tail.next, не сохранив nextGroup заранее. Если сделать это в неправильном порядке, часть списка теряется навсегда. Именно поэтому в таких задачах всегда важна временная переменная "сохрани ссылку на следующий блок".

11.2 Слияние пересекающихся списков

Иногда в интервью спрашивают: «Есть два списка, они пересекаются в какой-то точке; как найти точку схождения, не строя структуру данных?» Ответ обычно такой: посчитать длины, сдвинуть более длинный список на разницу, затем идти параллельно. Это очень чистая работа со ссылками и счетчиком, без лишних структур.

Решение на Java.

Java
static int length(Node head) {
    int len = 0;
    while (head != null) {
        len++;
        head = head.next;
    }
    return len;
}

static Node findIntersection(Node a, Node b) {
    int lenA = length(a);
    int lenB = length(b);

    while (lenA > lenB) {
        a = a.next;
        lenA--;
    }
    while (lenB > lenA) {
        b = b.next;
        lenB--;
    }

    while (a != null && b != null) {
        if (a == b) return a;
        a = a.next;
        b = b.next;
    }
    return null;
}

Обоснование. После выравнивания длин два указателя проходят одинаковое число шагов и встречаются в точке пересечения. Это по сути та же идея, что и с двумя поездками на одной линии: сначала выравниваем стартовую позицию, потом идём синхронно.

Интервью-ошибка. Считать, что пересечение списка — это всегда один и тот же объект. В реальности это может быть «один и тот же узел памяти», а может быть и логически равный объект с одинаковыми значениями. В Java для сравнения ссылок нужно пользоваться ==, а не equals, потому что equals может быть перегружен и скрывать факт реального объединения цепочки.

11.3 Копия списка со случайными ссылками

Задача про копию списка со случайным указателем тоже очень показательна. Это один из тех случаев, когда стандартная техника «создать новую копию и просто присвоить значения» ломает связи, потому что для каждого узла нужен отдельный объект, а любая ссылка должна указывать на его копию, а не на оригинал.

Решение на Java.

Java
static class RandomNode {
    int value;
    RandomNode next;
    RandomNode random;
}

static RandomNode copyRandomList(RandomNode head) {
    if (head == null) return null;

    RandomNode cur = head;
    while (cur != null) {
        RandomNode copy = new RandomNode();
        copy.value = cur.value;
        copy.next = cur.next;
        cur.next = copy;
        cur = copy.next;
    }

    cur = head;
    while (cur != null) {
        if (cur.random != null) {
            cur.next.random = cur.random.next;
        }
        cur = cur.next.next;
    }

    RandomNode oldHead = head;
    RandomNode newHead = head.next;
    cur = newHead;
    while (oldHead != null) {
        oldHead.next = oldHead.next.next;
        if (cur.next != null) {
            cur.next = cur.next.next;
        }
        oldHead = oldHead.next;
        cur = cur.next;
    }
    return newHead;
}

Главное. Этот подход известен как "in-place interleaving": сначала вставляем копию после каждого оригинального узла, затем корректируем random, затем разъединяем две цепочки. Это очень хороший пример того, как указатели и временные ссылки используются не для «красоты», а для сохранения полной модели данных без дополнительной памяти.

Место в реальном сервисе. Подобные структуры выглядят как "утилиты для графов и ссылочных объектов". На бэкенде их меньше, чем в алгоритмических задачах, но это же и хороший показатель: если вы понимаете, как сохранять корректную ссылочную топологию, вы уже мыслите про ограничение на память и про состояние объектов, а не только про типы данных.

11.4 Палиндром и очередь как логическая структура

Палиндром и Deque часто идут вместе, потому что Deque позволяет сравнивать символы с обоих концов. Это выглядит просто, но очень полезно: задача редко про саму строку, а про то, как вы понимаете LIFO/FIFO и границы. Например, проверка, что строка читается одинаково с двух концов, может быть решена через ArrayDeque и offerFirst/offerLast.

Решение на Java.

Java
static boolean isPalindrome(String s) {
    Deque<Character> deque = new ArrayDeque<>();
    for (char ch : s.toCharArray()) {
        if (Character.isLetterOrDigit(ch)) {
            deque.offerLast(Character.toLowerCase(ch));
        }
    }

    while (deque.size() > 1) {
        if (deque.pollFirst() != deque.pollLast()) {
            return false;
        }
    }
    return true;
}

Значение шаблона. В бизнес-сценариях похожая логика возникает, когда нужно сравнивать хвост и голову потока: например, проверить, что входящая запись имеет симметрию в метаданных, или что в буфере нет странной последовательности событий. Это не «чисто академическая задача», а пример того, как два конца структуры становятся важным источником контекста.

11.5 Очередь на двух стеках и стек с минимумом

Эти задачи стали классикой не потому, что они «жесткие», а потому что они проверяют способность видеть композицию структур. Очередь на двух стеках — очень простой и типичный механизм: один стек принимает элементы, второй отдаёт. Стек с минимумом — показатель, что вы понимаете, что поддержка дополнительного инварианта часто означает дополнительный вспомогательный стек.

Решение на Java: очередь на двух стеках.

Java
static class MyQueue {
    private final Deque<Integer> in = new ArrayDeque<>();
    private final Deque<Integer> out = new ArrayDeque<>();

    void enqueue(int x) {
        in.push(x);
    }

    int dequeue() {
        if (out.isEmpty()) {
            while (!in.isEmpty()) {
                out.push(in.pop());
            }
        }
        return out.pop();
    }
}

Решение на Java: стек с минимумом.

Java
static class MinStack {
    private final Deque<Integer> values = new ArrayDeque<>();
    private final Deque<Integer> mins = new ArrayDeque<>();

    void push(int x) {
        values.push(x);
        if (mins.isEmpty() || x <= mins.peek()) {
            mins.push(x);
        }
    }

    int pop() {
        int x = values.pop();
        if (x == mins.peek()) {
            mins.pop();
        }
        return x;
    }

    int min() {
        return mins.peek();
    }
}

Итог. В обоих случаях нет магии: задача состоит в поддержании корректного инварианта. Для очереди — самый старый элемент должен быть в "выходном" стеке. Для MinStack — текущий минимум должен всегда быть верхом вспомогательного стека. Если вы меняете одну из этих вещей в грубом цикле, структура ломается, и это сразу видно на тестах.

11.6 LinkedList в production

Даже если связный список — чистая и полезная структура, в бэкенде её редко используют как первичную модель хранения. Обычно причина не в том, что список «плохой», а в том, что реальные данные и трафик имеют другую локальность. ArrayList, ArrayDeque, HashMap, PriorityQueue и ConcurrentLinkedQueue более предсказуемы по памяти, кешу, паттернам доступа и количеству выделений памяти. LinkedList часто всплывает в учебных задачах и в логике, где порядок и ссылки важнее индексации.

На практике это выглядит так:

  • HTTP-запросы идут в ArrayDeque или LinkedBlockingQueue;
  • очереди задач — в BlockingQueue и PriorityBlockingQueue;
  • LRU — в LinkedHashMap или HashMap + двусвязный список;
  • таймеры и дедлайны — в PriorityQueue или DelayQueue;
  • сетевые буферы — в кольцевых массивах, а не в цепочке узлов.

Это важно понимать на собеседовании: если кандидат говорит «я выберу LinkedList, потому что проще», это обычно признак, что он не думал про реальные операции и про память. В системе, которая держит миллионы событий, ссылка на следующий элемент уже не выглядит как 'удобный трюк', а означает лишние выделения памяти и плохую локальность.

11.7 Списки на собеседовании

Хороший кандидат обычно объясняет не «что такое связный список», а «какая операция контролирует его форму». Вопросы не о том, может ли структура хранить данные, а о следующем:

  • где важен порядок;
  • где нужно удаление без поиска;
  • где нужна быстрая вставка в голову/хвост;
  • где важен доступ по индексу и где нет;
  • где нужна отслеживаемая история доступа;
  • где элементы действительно имеют логическую привязку к соседям.

Если в ответе есть хотя бы четыре из этих пунктов, кандидат уже перестаёт говорить «это просто список» и начинает говорить «это модель данных и её инварианты». Именно так в продакшене и выглядит зрелое понимание: не «я знаю контейнер», а «я знаю, какой контракт этот контейнер несёт и какие постусловия у него должны соблюдаться».

12. Выбор структуры по операции: в чем смысл сравнения

Частая ошибка в интервью — рассматривать LinkedList, ArrayDeque, PriorityQueue, HashMap и Stack как набор красивых коробок, не замечая, что они отличаются не только API, но и тем, какие операции у них дешёвые и какие вообще не стоит делать. Правильный вопрос выглядит не «какая из них более популярная?», а «какую операцию вы будете делать чаще всего и какой инвариант должен быть гарантирован для всех переходов состояния». Чаще всего репутация структуры определяется не её названием, а тем, кто и как её использует.

12.1 Предмет измерения: не только O(n) и O(1)

В учебниках обычно пишут: ArrayList.get(i) — O(1), LinkedList.get(i) — O(n), ArrayDeque.offer — O(1), PriorityQueue.add — O(log n). Это верно, но недостаточно. В продакшене важны ещё три вещи: локальность памяти, число выделений памяти и степень устойчивости к коллизиям доступа.

ArrayList и ArrayDeque хранят данные в массиве, а значит, элементы физически рядом. Это помогает процессору, потому что он может читать их небольшими блоками, а не прыгать по указателям. LinkedList живёт за счёт больших затрат на указатели: у каждого узла две ссылки и объект-обёртка, поэтому даже простая итерация по списку становится заметно дороже, чем по массиву. В Java это особенно заметно, когда размер набора растёт до миллионов элементов.

Для бэкенда проблема всегда выглядит так: работать с массивом внутри контейнера нормально, если вы в основном делаете проход, addLast, pollFirst, peek, и не нужно вставлять в середину. Если стек/очередь работает как очередь задач или конвейер, ArrayDeque почти всегда лучше LinkedList. Если же логика требует удаления из любой точки списка и постоянной пересборки ссылок, тогда связный список уже становится не «просто удобной структурой», а важной частью самого алгоритма.

12.2 Преимущества ArrayList перед LinkedList

ArrayList лучше везде, где есть хороший случайный доступ: чтение по индексу, проход по коллекции, заполнение пакетом, фильтрация, сериализация и агрегация. В бэкенде это типично для:

  • кэша метаданных и конфигураций;
  • временных списков из результатов запросов;
  • буферов, которые читаются большими фрагментами;
  • валидации списков параметров, а не их динамической перестройки.

Формально ArrayList действительно имеет O(n) на вставку в середину, но если по факту вы делаете append и потом итерируетесь, массив почти всегда выигрывает. Он дешевле для CPU и предсказуемее для памяти. Это одна из частых причин, почему в production подход не «связный список, потому что удобнее», а «список как массив, потому что там во главу угла ставится обход и локальность».

Пример. Если вы читаете 100 тысяч записей из файлов и фильтруете их, то ArrayList даст более предсказуемую нагрузку на GC и лучшие шансы на кэширование. Если же вы постоянно вставляете в голову новые события и удаляете хвост, это уже не ArrayList, а Deque/Queue.

12.3 Оправданный LinkedList

Связный список не «плохой» сам по себе. Он полезен там, где важны ссылки и последовательность узлов, а не локальность массива. Яркие случаи:

  • задача про разворот списка и циклы;
  • алгоритмы, где нужно переставлять хвосты, разворачивать блоки и сохранять инвариант ссылок;
  • буфера с логической, а не физической непрерывностью;
  • модели, где нет случайного доступа, но есть постоянное удаление/добавление по фактической точке.

Именно поэтому на собеседовании связный список много лет остаётся темой: он показывает, умеет ли кандидат думать о ссылках и инвариантах, а не просто про List как интерфейс. Пример со списком с циклом, с удалением среднего узла, с лентой задач и с разворотом блоков — это то, что отлично проверяет мышление про состояние.

12.4 Deque и обычная очередь

Принципиальное отличие между Queue и Deque — не в том, что один «лучше», а в том, что один ограничен моделью FIFO, а второй позволяет работать с обоими концами. В коде это меняет архитектуру:

  • Queue: «первый пришёл — первый ушёл»;
  • Deque: «один и тот же объект может нулевой и верхний элемент на обоих концах»;
  • PriorityQueue: «выбираем по приоритету, а не по времени входа».

В бэкенде это оборачивается так:

  • HTTP-queue как FIFO — предпочтительная модель для событий и входящего трафика;
  • Deque — естественная модель для обработки конвейеров и двусторонних буферов;
  • PriorityQueue — для таймеров, дедлайнов, пересылки срочных задач и событий, где важно не «когда пришло», а «какой приоритет».

Разница очень важна, потому что у каждой структуры есть свой подход к ошибкам. Очереди про порядок и перегрузку, Deque — про локальность и управление двумя границами, а PriorityQueue — про приоритет и типичный сценарий «сначала самые важные события, потом всё остальное».

12.5 Преимущество ArrayDeque перед LinkedList в Java

Если не вдаваться в теорию, а смотреть на рабочий код, то в Java ArrayDeque почти всегда хорошее решение для стеков и очередей. Он:

  • хранит элементы в массиве;
  • почти не создаёт лишних объектов;
  • имеет низкую выделение памяти и предсказуемую память;
  • дает O(1) для addLast, pollFirst, pollLast, peekFirst, peekLast;
  • подходит и как стек, и как очередь, и как двусторонний буфер.

LinkedList выигрывает только в сценариях, где вам нужен именно список, а не просто очередь/стек. В продуктовой кодовой базе этот нюанс зачастую очень важен, потому что вы платите не только за алгоритмическую сложность, но и за стоимость каждого объекта, каждого next и каждой референсной связи. Для высоконагруженного server-side кода это часто определяет, не будет ли приложение врет под нагрузкой, даже если теоретически всё «работает».

12.6 Операции, которые ломают структуру

Для связных списков и очередей критичны не только алгоритмы, но и порядок операций. Самые частые ошибки:

  • забыли сохранить ссылку на next до того, как переписали её;
  • удалили узел из списка, но не обновили соседей;
  • у PriorityQueue не учли политику сравнения и получили не тот порядок;
  • в Deque и ArrayDeque работали с хвостом и головой в противоположной логике и сломали инвариант;
  • в LRU удалили узел из списка, но забыли обновить HashMap.

Это именно тот тип ошибок, который на интервью обычно не решается «потому что не хватает кода», а решается через формулировку инвариантов. Вместо «я вставил элемент в список» разработчик должен говорить: «я обновил prev у следующего элемента, next у предыдущего, а затем синхронизировал карту с состоянием буфера. В результате список остаётся связанным и не теряет хвост.»

12.7 Короткий ответ на собеседовании

Хороший ответ звучит так:

Я выбираю структуру не по красивой идее, а по той операции, которая доминирует в рабочем цикле. Если нужен произвольный доступ и проход по массиву — ArrayList. Если нужна вставка/удаление в середине по конкретной точке и нет большого случайного доступа — список. Если нужны FIFO/LIFO и высокая скорость на границах — ArrayDeque. Если нужен приоритет — PriorityQueue. Внутри каждого варианта я смотрю на инварианты, границы и проверяю, не ломается ли состояние при пустом/одиночном/полном случае.

Это уже не «знаю названия контейнеров», а «знаю контракт и границы применения». Именно такой уровень понимания и нужен в финтехе, биллинге, планировщиках, очередях задач и системах интеграции. Там нет академической чистоты — есть работающий инвариант и зафиксированный контракт на ресурсы.

12.8 Промышленные сценарии: где тянут именно эти структуры

На практике связные списки и очереди не абстрактны. Они проявляются в работе систем так:

  • очередь сообщений в Java может быть ArrayDeque на уровне буфера, а BlockingQueue — на уровне producer/consumer;
  • планировщик задач может использовать PriorityQueue для дедлайнов и приоритетов;
  • HTTP-конвейер может собирать запросы в Deque, чтобы быстро добавлять и дедублировать их в окне времени;
  • LRU-кэш — почти всегда HashMap + двусвязный список;
  • в алгоритмах анализа данных стек и очередь появляются в алгоритмах скользящего окна и в потоковой обработке.

Именно поэтому задачи на списки и очереди важны — они отражают саму модель работы кода, а не только академический список типов. Если человек может связать структуру с реальной системой, он уже двигается от «я знаю типы» к «я понимаю, как работает штука под нагрузкой».

13. Практические чек-листы перед финальным решением

Когда вы уже видите задачу про стек, очередь, список или дек, полезно пройти короткий чек-лист:

  1. Что должен делать интерфейс: push/pop, offer/poll, peek, addLast, removeFirst, contains?
  2. Есть ли у структуры инвариант по границам: пустой, один элемент, полный буфер, цикл?
  3. Нужно ли хранить порядок вставки или порядок приоритета?
  4. Где именно у вас происходит обновление ссылок: выделение next, prev, head, tail?
  5. Что происходит с памятью и выделениями памяти: массивы, ссылки, новых узлы?
  6. Можно ли решить задачу за O(1), O(log n) или только O(n)?
  7. Есть ли риск переполнения, deadlock, race condition или потерянной ссылки?
  8. Равны ли все операции одному и тому же контракту при boundary-case проверках?

Если ответа нет хотя бы на половину из этого списка, обычно решение ещё слишком расплывчатое. Хорошая структура данных — это не набор методов на бумаге, а набор гарантированных состояний, которые сохраняются при каждом переходе.

14. Сценарии из продакшена: как списки и очереди живут в системах

В учебнике типичная проблема выглядит аккуратно: стек, очередь, дек, LRU и PriorityQueue — это контейнеры, а решение — это набор алгоритмов. В реальном сервисе же всё оказывается более скучно и более важно. Очередь может быть не самой структурой, а политикой обработки сообщений; стек может быть не контейнером, а частью механизма вычисления запроса; LinkedList может быть не инструментом, а символом неверной архитектуры. Чтобы понять, как работает бэкенд, нужно смотреть не на отдельное API, а на то, что именно происходит с потоком данных.

14.1 Очередь задач и worker pool: где очередь реально нужна

Представьте, что у вас есть HTTP-сервис и он должен отправлять события в другое место. На входе приходит поток запросов. Не все из них равны: часть ресивит, часть занимает время на асинхронный вызов, а часть просто должен жить в очереди до освобождения worker-а. В этом сценарии очередь — не «алгоритм ради алгоритма», а механизм сглаживания всплесков. Сам по себе ArrayDeque не решает проблему, а только держит порядок. Реальное решение — это соединение:

  • входной буфер;
  • ограничение по токенам или планировщику;
  • worker pool;
  • retry policy;
  • DLQ или dead-letter queue;
  • ограничение по времени и давлению.

Если бы у вас был высокий трафик, а LinkedList для хранения задач на уровне сервиса, вы бы быстро столкнулись с тем, что объекты создаются слишком часто, а общая скорость падает. Тогда логичным вариантом становится ArrayBlockingQueue, LinkedBlockingQueue или PriorityBlockingQueue с правильным ограничением и стратегией отказа. В этом и есть смысл сравнения структур: ту же идею можно выразить разными контейнерами, но их разная стоимость влияет на дистрибуцию нагрузки по CPU и на время реакции.

Интервью-ответ. В продакшене очередь — это инструмент контроля потока, а не просто список. Важно задать себе вопросы: кто пишет, кто читает, что делать при переполнении, нельзя ли отправить в retry, чем быстрее сработает backpressure, и какой контракт гарантируется при падении/ударе по p99.

14.2 Rate limiter и token bucket: стек и очередь в политике доступа

Фильтрация входящего потока — ещё одна точка, где данные и структуры связаны самым прямым образом. Если ваше API должно ограничивать число запросов в секунду, то логика почти всегда строится на модели token bucket или leaky bucket:

  • токены генерируются с постоянной скоростью;
  • запрос занимает токен;
  • при нехватке токенов запрос либо задерживается, либо отбрасывается;
  • queue/stack в этом случае служит не хранилищем данных, а моделью тайминга и перераспределения доступа.

В учебник это иногда превращают в простую очередь, но в production вы быстро понимаете: вокруг неё есть не только Deque, но и часы, планировщик, таймеры и политикa TTL. Тут уже нельзя говорить «я выберу ArrayDeque, потому что это очередь» — нужно говорить «я выберу алгоритм ограничителя с буфером событий и строгим контролем времени, чтобы не ломать SLOS».

14.3 LRU и история доступа: HashMap + список — не «магия», а контракт

LRU — этот символ хорошо показывает, что слово «структура данных» в реальном сервисе почти всегда означает набор контрактов. У HashMap и двусвязного списка не совпадают цели, но их комбинация очень сильна:

  • HashMap даёт случайный доступ по ключу;
  • список хранит историю реального использования;
  • добавление/снятие происходит по границе — в голову или с хвоста;
  • старый элемент уходит, когда размер превышает лимит.

Почему это важно в бэкенде? Потому что LRU часто используется в кэше данных, а не в учебной задаче по алгоритмам. В кэше важны не самые красивые методы, а честная модель вытеснения и отслеживание реального доступа. Если вы делаете кэш и используете HashMap без списка или список без HashMap, вы быстро получите либо постоянное вытеснение, либо практически неуправляемое поведение. Эта комбинация и есть тот слой, который делает операции O(1) и не ломает логической моделью.

14.4 LinkedList под нагрузкой

Если вы проводите нагрузочное интервью, вас почти всегда проверяют на понимание разницы между «теорией контейнера» и «формой доступа в продакшене». LinkedList может показаться удобным, потому что создаётся из узлов и next/prev, но в продакшене он часто проигрывает даже там, где по формуле вроде бы должен быть лучше. Причины:

  • у всех узлов свои объекты и ссылки;
  • больше выделений памяти и больше давления на GC;
  • хуже локальность памяти;
  • обращение к по индексу случается далеко не так часто, как в учебной задаче;
  • на реальной нагрузке у вас обычно есть поток записи и поток чтения, а не простой линейный проход.

В результате LinkedList может быть не более чем удобным объектом для демонстрации алгоритма. Это важный момент, который часто формулируют так: «ссылки и порядок — важны, но не всегда это самый эффективный вариант в runtime». Поэтому хороший разработчик умеет отличать теоретическую корректность от практической пригодности.

14.5 Сцена с дедлайнами и PriorityQueue

Когда задача зависит не от времени прихода, а от дедлайна или бизнес-значимости, обычная очередь уже не подходит. Тогда в игру вступает PriorityQueue. Пример: система обработки заявок. Не все заявки одинаково важны. Некоторые идут на обработку сразу, а часть — по приоритету: например, спорные операции, аварийные сценарии, служебные события или операции с высоким уровнем риска. Приоритетная очередь даёт не порядок «первый пришёл — первый обслужен», а порядок «сначала важное».

Это очень важная разница, потому что в реальных системах фраза «очередь» часто скрывает вовсе не FIFO, а вполне конкретную операционную политику. Если вы этого не видите, вы не понимаете, где хранится контекст приоритета. Структура подменяет бизнес-смысл: вопросы вида «что делать с заявками в 2:00?» или «как разбить обработку для пользователей VIP?» уже не про контейнер, а про стратегию упорядочивания и приоритетов.

14.6 Ситуация с windowing и sliding maximum

Задачи про скользящее окно — это один из главных примеров, где стек/очередь становятся не академической шуткой, а инструментом вычисления. В логистике, трейдинге, мониторинге и бэкенд-скоринге это может быть окно последних 5 минут, окно запросов по группам или окно фильтрации переходных данных. Всё выглядит как расчёт максимума/минимума по окну, но на деле за этим стоит очень простой принцип:

  • окно сдвигается по одному событию;
  • старые индексы выкидываются;
  • актуальные остаются в порядке, который помогает быстро вернуть максимум или минимум;
  • вся логика живёт в поддержании корректного состояния, а не в сложности вычислений.

Что делает эту тему важной, так это то, что здесь видно разницу между «подобрал правильную структуру» и «собрал правильный инвариант». Буфер, в котором вы просто храните значения, не поможет; нужен порядок, который сохраняется при каждом сдвиге окна.

14.7 Вопросы сильного и слабого интервью

Сильный интервьюер обычно не спрашивает «что такое стек?». Он спрашивает:

  • какой инвариант вы поддерживаете;
  • какой элемент вы удаляете и почему;
  • почему массив/связный список/очередь выбираются именно здесь;
  • какую сложность вы получаете в реальном сценарии и сколько будет выделений памяти;
  • что происходит, когда окно заполнено, очередь переполнена, или элемент бросается в конец;
  • как вы проверяете, что аргумент о O(1) действительно применим к конкретной задаче.

Это и есть разница между поверхностным знанием и рабочим пониманием. Один человек может назвать ArrayDeque и PriorityQueue, но не понять, что у приоритетной очереди есть своя логика отказа при переполнении. Другой может объяснить, почему ArrayDeque лучше LinkedList под нагрузкой и почему приоритетную очередь не надо использовать там, где важен порядок по времени. Это уже уровень инженера, а не школьника в качестве решения задачи.

15. Таблица выбора и короткие формулировки для собеседования

В конце этого раздела полезно зафиксировать модель принятия решения: какие структуры выбирать, когда и почему. Если кандидат умеет объяснить не «класс структуры», а «сценарий и инвариант», он уже говорит на языке production-архитектуры, а не на языке примитивной академической теории.

15.1 Матрица выбора по операциям

Сценарий Лучше всего Объяснение
Частое чтение по индексу ArrayList Массив = хорошая локальность и предсказуемые кэши
Много вставок/удалений в середине связный список Нет сдвигов, только изменение ссылок
Стек / LIFO ArrayDeque O(1), минимум выделений памяти, естественная модель
FIFO с высокой интенсивностью ArrayDeque или BlockingQueue Порядок прост и стабилен
Очередь с дедлайнами/приоритетами PriorityQueue Извлекается не «первый пришёл», а «самый важный»
Cкользящее окно и максимум/минимум Deque + индекс Фиксируется нужный временной контекст
LRU и история доступа HashMap + двусвязный список O(1) на get и на вытеснение
Пакетный поток задач BlockingQueue/DelayQueue Призвана сглаживать нагрузку и контролировать backpressure

Главный принцип здесь прост: ArrayList и ArrayDeque — это не конкуренты в идеальном смысле, а решения для разного контракта. Одни выигрывают по локальности и доступу, другие — по работе с концами и управлению потоками.

15.2 Выбор контейнера как ошибка архитектуры

Самая типичная ошибка — брать LinkedList «потому что на собеседовании часто спрашивают связный список», а потом использовать его в реальном сервисе для огромного потока данных. Это не значит, что связный список автоматически плох, а значит, что логика применения должна быть конкретной:

  • если важно хранить порядок и возможность вставки в середину без сдвига;
  • если без ссылки на prev/next решение распадается;
  • если вы проектируете алгоритм, а не буфер практической обработки.

Только после этого LinkedList работает как инструмент. В противном случае вы получаете не структуру данных, а набор дополнительных объектов и сложностей с GC.

15.3 Короткие ответы для собеседования: как говорить без лишних слов

Ниже — варианты формулировок, которые можно произнести вслух в 3–5 предложениях и не потерять смысл.

Вопрос. Почему ArrayDeque обычно лучше LinkedList для стека и очереди?

Ответ. Потому что ArrayDeque хранит элементы в массиве, а не в узлах со ссылками. У него меньше выделений памяти, лучше локальность памяти, и операции на концах остаются O(1). LinkedList полезен, когда нужна именно логика связного списка, а не просто стек/очередь.

Вопрос. Когда выбирают PriorityQueue вместо обычной очереди?

Ответ. Когда важен приоритет, а не порядок вставки. Если в системе есть дедлайны, критические события, VIP-операции или срочные задачи, обычная FIFO-очередь будет неверна по смыслу. PriorityQueue решает именно эту задачу, но требует ясной политики приоритетов.

Вопрос. Почему LRU строят как HashMap + двусвязный список?

Ответ. Потому что HashMap даёт O(1) доступ по ключу, а список держит реальный порядок использования. Тогда get и put могут быть O(1), а старые элементы удалить можно без полного перебора структуры.

Вопрос. В чём разница между стеком и очередью?

Ответ. Стек работает по принципу LIFO: последняя добавленная сущность уходит первой. Очередь — по принципу FIFO: первый пришёл, первый ушёл. Решение зависит не от «есть ли у структуры методы», а от контракта, который вы должны поддерживать.

Вопрос. Почему на собеседовании часто проверяют fast/slow?

Ответ. Потому что это один из самых простых и сильных способов показать, что вы понимаете инвариант, а не только названия структур. Алгоритм с двумя указателями выигрывает по памяти и позволяет находить цикл, начало цикла и длину без дополнительных структур.

15.4 Тесты, которые реально показывают, что вы держите контракт

Нужно не просто написать код, а проверить четыре состояния:

  1. пустой контейнер;
  2. контейнер из одного элемента;
  3. контейнер с повторными значениями;
  4. полная/переполненная структура.

Например, для MinStack это означает:

  • push 5, push 3, push 3, pop — минимальный элемент после pop должен быть 3;
  • при повторных значениях <= критично, иначе один из минимумов будет потерян;
  • при пустом стеке min() и pop() должны вести себя явно и безопасно.

Для Queue на двух стеках:

  • enqueue(1), enqueue(2), enqueue(3), dequeue() должен вернуть 1;
  • при нескольких dequeue подряд выходной стек должен не забывать разыгрывать новую порцию элементов;
  • после полного опустошения очереди не должно оставаться «висячих» элементов.

Для связного списка:

  • после reverse список должен быть симметрично перевёрнут;
  • после merge не должно теряться начало или хвост;
  • при detect cycle важно не забыть fast != null && fast.next != null.

15.5 Значение для финтеха

В платёжных системах, системах лимитов, брокерах событий и реестрах очереди не являются «произволом» или «абстракцией для задач». Они несут реальную ответственность за порядок обработки и за сохранение согласованности. Если вы перепутаете queue и priority queue, то в одной системе вы можете поставить первый пришедший запрос выше более важного, и это уже не академическая ошибка. Она может означать, что клиенты с высоким риском обрабатываются позже, чем мелкие операции, или что критический реестр ложится у хвоста потока.

То же касается LRU, списков и Deque: если вы сэкономили на структуре в пользу «удобства», вы можете получить не только дополнительные выделения памяти, но и временную задержку, рост heap, а иногда и странную деградацию при пиках нагрузки. Поиск и исправление этого в проде никогда не выглядит как «почему ArrayDeque нельзя использовать?», а как реальный инцидент: «очередь была переполнена в 2:20 и обработка замедлилась по всем транзакциям, потому что в рабочем пуле стояла неверная структура».

Это и даёт смысл главе: она не про красивую теорию, а про инварианты состояния, управление порядком и честный ответ на вопрос «что именно происходит, когда поток данных начинает ломаться».
