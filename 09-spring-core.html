Зачем это знать

Почти весь серверный код на Java работает внутри контекста приложения Spring, и многие ошибки, которые выглядят необъяснимыми, оказываются следствием того, как контейнер собирает объекты и где подставляет вместо них прокси. @Transactional не сработал, @Async выполнился в том же потоке, бин остался без обработки, приложение не стартует с BeanCurrentlyInCreationException, тесты идут двадцать минут, потому что поднимают десять разных контекстов, — всё это объясняется механикой, которую разбирает глава. На собеседованиях Spring Core входит в обязательную программу: о жизненном цикле бина, постпроцессорах, циклических зависимостях и вызове метода через this спрашивают почти всегда, и ценят умение объяснить, что происходит внутри refresh(), а не перечень аннотаций. Глава написана по Spring Framework 7.0 и Spring Boot 4.1, а там, где поведение менялось между версиями, это показано запуском на нескольких версиях.

Spring Core — ядро Spring Framework, и его центральная часть — контейнер инверсии управления (IoC container). С контейнерами Docker и Kubernetes из глав 46–48 у него общее только слово: те изолируют процессы операционной системы, а контейнер Spring — обычный объект внутри JVM, который собирает остальные объекты приложения. Поэтому в этой главе «контейнер» без уточнения всегда означает контейнер Spring. Контейнер по описаниям создаёт объекты приложения, передаёт им зависимости, вызывает их методы инициализации и остановки и при необходимости подменяет их прокси — обёртками, которые добавляют к вызову метода транзакцию, кэш или асинхронность. Объект, которым управляет контейнер, называют бином (bean): платёжный сервис, репозиторий, пул соединений, клиент антифрода. Если вы собирали сервис вручную в main, создавая пул, репозиторий и сервис в правильном порядке, то контейнер делает ту же работу, только автоматически и по правилам, которые нужно знать, чтобы понимать его поведение.

Контейнер устроен слоями. Внизу лежат описания бинов (BeanDefinition), над ними фабрика, которая по описаниям создаёт объекты, а сверху контекст приложения (ApplicationContext), который добавляет события, окружение с настройками и расширения. Расширения называют постпроцессорами: это бины, которые контейнер вызывает на определённых этапах, чтобы изменить описания других бинов или сами созданные объекты. Почти всё, что в Spring выглядит как действие аннотации, выполняют постпроцессоры и прокси.

Глава идёт от принципа к механике и затем к практике. Разделы 1–4 определяют инверсию управления и внедрение зависимостей, показывают устройство контейнера, двенадцать шагов refresh() и жизненный цикл бина. Разделы 5–7 разбирают способы внедрения, области видимости, циклические зависимости и подкласс CGLIB у @Configuration. Центральная часть, разделы 8 и 9, посвящена прокси и аспектам: как Spring обёртывает бины, почему вызов через this обходит обёртку и в каком порядке срабатывают транзакции, кэш, повторные попытки и проверка прав. Разделы 10–15 описывают события, настройки и условия, фоновую работу, расширение контейнера, тестирование контекста и обработку AOT. Завершают главу разобранные инциденты, типичные ошибки, приёмы диагностики, вопросы с собеседований и упражнения. 1. Инверсия управления и внедрение зависимостей

Почти каждому классу для работы нужны другие объекты: сервису платежей — репозиторий, конвертеру валют — источник курсов, проверке лимитов — справочник лимитов. Вопрос в том, кто эти объекты создаёт и передаёт. Если класс создаёт их сам, он намертво привязан к одной реализации, и подменить её ни в тесте, ни в другой среде нельзя. Если же объекты создаёт кто-то снаружи и передаёт классу готовыми, класс становится гибким и проверяемым, а вся сборка приложения оказывается в одном месте. Этот переход и называют инверсией управления, а передачу зависимостей снаружи — внедрением зависимостей. Раздел показывает на примере, чем плох класс, который сам добывает зависимость, как отделить сборку приложения от его работы и что добавляет к этой идее контейнер Spring.

1.1 Класс, который сам добывает зависимость

Возьмём конвертер валют, которому нужен источник курсов. Самое частое решение — статический служебный класс с курсами внутри:

// Плохо: одна зашитая таблица курсов на все случаи
public final class StaticConverter {
    private static final Map<String, BigDecimal> RATES = Map.of("USD", new BigDecimal("81.20"));
    private StaticConverter() { }

    public static BigDecimal toRub(BigDecimal amount, String currency) {
        return amount.multiply(RATES.get(currency)).setScale(2, RoundingMode.HALF_EVEN);
    }
}

Листинг 9.1. Статический конвертер с зашитой таблицей курсов.

Такой класс исходит из того, что источник курсов один и годится для всего. На деле курсы ЦБ нужны для отчётности, курсы банка для операций клиента, а в тесте нужны фиксированные курсы, иначе результат будет меняться каждый день. Синглтон с полем private final RateSource rates, которое он заполняет сам, страдает тем же самым. Можно сделать поле изменяемым и добавить метод замены источника, но это решение неуклюжее: о замене легко забыть, а в многопоточном коде один поток подменит курсы под другим. Статический класс и синглтон не годятся для классов, поведение которых зависит от ресурса.

Другая частая форма той же ошибки — отложенная инициализация, при которой класс создаёт зависимость при первом обращении:

public class PaymentOrderService {
    private PaymentOrderRepository repository;

    private PaymentOrderRepository repository() {
        if (repository == null) {
            repository = new PostgresOrderRepository(dataSource);   // реализация выбрана здесь, раз и навсегда
        }
        return repository;
    }
}

Листинг 9.2. Отложенная инициализация: класс сам выбирает реализацию репозитория.

У приёма есть достоинства: объект не создаётся, пока не понадобится, и метод никогда не вернёт null. Недостатков больше, и их три. Класс жёстко зависит от PostgresOrderRepository и от всего, что нужно его конструктору, и без этих классов не скомпилируется, даже если репозиторий в данном запуске ни разу не понадобится. Его трудно тестировать: перед вызовом приходится подкладывать в поле тестовый дублёр, а поскольку метод одновременно создаёт зависимость и работает с ней, проверять надо и ветку с null. Это две обязанности в одном методе. Главный же недостаток в том, что сервис вынужден знать глобальный контекст: он сам решает, что PostgresOrderRepository подходит во всех случаях. Одна такая инициализация ничего не ломает, но в приложении их десятки, и правило сборки размазывается по всему коду.

1.2 Сборка отдельно от работы

Все три примера лечатся одним приёмом: создание объектов и связывание их друг с другом выносят из классов, которые этими объектами пользуются. Конвертер перестаёт выбирать источник курсов и получает его в конструкторе:

public final class CurrencyConverter {
    private final RateSource rates;

    public CurrencyConverter(RateSource rates) {
        this.rates = Objects.requireNonNull(rates);
    }

    public BigDecimal toRub(BigDecimal amount, String currency) {
        return amount.multiply(rates.rubPer(currency)).setScale(2, RoundingMode.HALF_EVEN);
    }
}

Листинг 9.3. Конвертер получает источник курсов через конструктор.

Кто и с каким источником его создаёт, решает теперь одно место программы, чаще всего метод main или модуль, который он вызывает. Остальной код пишется в предположении, что все объекты уже созданы и правильно связаны. Стрелки зависимостей при этом ведут только от main к приложению: приложение ничего не знает о том, как его собирали.

RateSource cbr = ccy -> switch (ccy) {
    case "USD" -> new BigDecimal("81.20");
    case "EUR" -> new BigDecimal("94.10");
    default -> throw new IllegalArgumentException(ccy);
};
CurrencyConverter prod = new CurrencyConverter(cbr);                    // рабочая сборка
CurrencyConverter test = new CurrencyConverter(ccy -> BigDecimal.ONE);  // тестовая сборка

Листинг 9.5. Опыт 1.2: один конвертер с двумя источниками курсов.

Один и тот же класс без единого изменения работает с курсами ЦБ и с заглушкой. Класс к тому же можно сделать неизменяемым: поле final, источник задан при создании, и несколько потоков безопасно пользуются одним конвертером.

Бывает, что моментом создания объекта должно распоряжаться само приложение: отчёт за день создаёт конвертер на свою дату, заказ создаёт свои позиции. Тогда приложению передают не объект, а фабрику, и подробности сборки остаются на стороне main. Для фабрики подходит Supplier, причём параметр типа лучше ограничить, Supplier<? extends CurrencyConverter>, чтобы клиент мог передать фабрику любого подтипа:

static final class DailyReport {
    private final Supplier<? extends CurrencyConverter> converterFactory;

    DailyReport(Supplier<? extends CurrencyConverter> converterFactory) { this.converterFactory = converterFactory; }

    BigDecimal totalRub(Map<String, BigDecimal> balances) {
        CurrencyConverter c = converterFactory.get();                  // создать, когда нужно отчёту
        return balances.entrySet().stream()
                .map(e -> c.toRub(e.getValue(), e.getKey()))
                .reduce(BigDecimal.ZERO, BigDecimal::add);
    }
}

DailyReport report = new DailyReport(() -> new CurrencyConverter(cbr));   // как создать — решает main

1.3 Внедрение зависимостей и инверсия управления

Приём из предыдущего подраздела называют внедрением зависимостей (dependency injection, DI): зависимость передаётся объекту снаружи, через конструктор, фабричный метод, сеттер или поле, и объект не участвует в её поиске. Внедрение — частный случай более общей идеи, инверсии управления (inversion of control, IoC). Обычно класс сам создаёт то, что ему нужно, и сам решает, когда и как. При инверсии эта вторичная обязанность переходит к другому объекту, созданному специально для неё, — к main, к конструирующему модулю или к контейнеру, а класс занимается только своей работой.

Не всякий отказ от new — уже внедрение. Если класс сам запрашивает зависимость по имени у каталога, например jndiContext.lookup("rateSource"), он не выбирает реализацию, но разрешает зависимость активно и знает, у кого и что спросить. Это лишь частичная инверсия. При настоящем внедрении класс пассивен: он объявляет конструктор или сеттеры, а создают объекты и связывают их другие.

Внедрение зависимостей не требует фреймворка. Код из подраздела 1.2 не содержит ни одной аннотации, его проверяет компилятор, в нём нет скрытого поведения, и стартует он мгновенно. Неудобство ручной сборки проявляется в большом проекте: когда объектов сотни, main разрастается в длинный список конструкторов, и его приходится править при каждом изменении зависимостей. Эту работу берут на себя каркасы внедрения зависимостей: Spring, Guice, Dagger. Классы, написанные под ручное внедрение, переходят на любой из них почти без изменений, поэтому проектировать их стоит именно так: зависимости в конструкторе, без поиска по имени и без статического доступа.

1.4 Что добавляет контейнер Spring и чем он неудобен

Контейнер Spring берёт на себя то, что в подразделе 1.2 делал main: создаёт объекты, связывает их и хранит до остановки приложения. Устройство контейнера разобрано в разделе 2, а здесь — зачем он нужен, если сборка руками работает. Оправдывают его три возможности, которые руками писать долго:

  1. Сборка по типам. Контейнер сам находит, какой объект подходит под параметр конструктора, по его типу, и при четырёхстах объектах не нужен файл на две тысячи строк с конструкторами.
  2. Жизненный цикл. Контейнер создаёт объекты в порядке зависимостей и закрывает их в обратном порядке: вызывает close() у пулов соединений, клиентов брокера и пулов потоков.
  3. Сквозная функциональность. Транзакции, кэш, метрики, проверку прав и повторные попытки нужно добавить ко многим классам сразу, хотя ни к чьей бизнес-логике они не относятся. Контейнер подставляет вместо бина обёртку (прокси), которая выполняет эту работу вокруг вызова метода (раздел 8). Без контейнера пришлось бы вручную вкладывать декораторы друг в друга.

У каждой из этих возможностей есть обратная сторона, и на собеседовании её стоит назвать прямо:

  • Ошибки при старте, а не при компиляции. Отсутствующая зависимость или неоднозначный выбор между двумя бинами обнаруживаются только при запуске, как NoSuchBeanDefinitionException или NoUniqueBeanDefinitionException. У ленивого бина (lazy), который создаётся при первом обращении, ошибка проявится ещё позже, на первом запросе к нему. Контекст Spring по умолчанию создаёт все синглтоны при старте, а ленивым бин становится только по явной просьбе: аннотацией @Lazy на бине или свойством spring.main.lazy-initialization=true для всего приложения. Получить зависимость отложенно, не делая бин ленивым, позволяет ObjectProvider (раздел 5.3).
  • Время старта. Контейнер сканирует пакеты, разбирает метаданные классов, создаёт прокси и сотни бинов, и приложение среднего размера стартует секунды, большую часть которых занимает refresh() (раздел 3). Тесты, которые поднимают полный контекст, по той же причине идут медленнее срезов вроде @WebMvcTest (раздел 14).
  • Длинные трассировки стека. Между контроллером и сервисом в трассировке оказывается несколько кадров прокси и перехватчиков, например CglibAopProxy$DynamicAdvisedInterceptor.intercept и ReflectiveMethodInvocation.proceed.
  • Поведение в прокси, а не в коде. Транзакция и кэш работают, только когда вызов проходит через прокси, а вызов this.method() изнутри бина идёт мимо него (раздел 8.3). Разработчик, который не знает об аспекте на классе, долго ищет, почему метод вернул значение из кэша вместо того, чтобы выполниться.
  • Рефлексия и классы, созданные на лету. Контейнер создаёт объекты и классы прокси во время работы, а сборка в нативный образ GraalVM требует знать всё это заранее. Отсюда появилась AOT-обработка Spring (раздел 15).

❓ Спрашивают на интервью. Что такое IoC и DI, и нужен ли для DI Spring? Инверсия управления передаёт создание и связывание объектов от самих объектов внешнему коду, а внедрение зависимостей — способ её реализовать: зависимости приходят в конструктор или сеттер готовыми, и класс их не ищет. Spring для этого не нужен: граф можно собрать в main, и такой код проще и быстрее. Контейнер оправдан в большом приложении, где он собирает граф по типам, управляет жизненным циклом и добавляет транзакции и кэш через прокси. Взамен ошибки конфигурации видны только при старте, старт занимает секунды, а часть поведения живёт в прокси.

2. Как устроен контейнер Spring

Контейнер Spring — это объект, который создаёт компоненты приложения, связывает их друг с другом и управляет ими до остановки приложения. В Spring его называют контекстом приложения (application context), а компоненты, которыми он управляет, — бинами (beans). Связывание держится на внедрении зависимостей (dependency injection): компонент сам не создаёт объекты, от которых зависит, и получает их готовыми от контейнера, чаще всего через аргументы конструктора. Это частный случай инверсии управления (inversion of control): созданием объектов и их назначением распоряжается фреймворк, поэтому реализацию можно заменить, не трогая код, который ею пользуется. Раздел начинается с примера, ипотечного калькулятора, описанного тремя способами. Затем на том же примере разобрано, что контейнер делает с конфигурацией до того, как создаст первый объект, и чем фабрика бинов отличается от контекста.

2.1 Один калькулятор, три способа его описать

Возьмём сервис, который считает ежемесячный платёж по ипотеке, и класс App, которому этот сервис нужен. Сервис объявлен интерфейсом с одной реализацией: потребитель зависит от интерфейса, а какую реализацию ему дать, решает конфигурация.

public interface MortgageCalculatorService {
    double payment(double principal, double annualInterestRate, int years);
}

@Service
public class MortgageCalculatorServiceImpl implements MortgageCalculatorService {
    @Override
    public double payment(double principal, double annualInterestRate, int termInYears) {
        double monthlyInterestRate = annualInterestRate / 12 / 100;
        int numberOfPayments = termInYears * 12;
        // Ипотечная формула: P * R * [(1+R)^N] / [(1+R)^N - 1]
        return principal * (monthlyInterestRate * Math.pow(1 + monthlyInterestRate, numberOfPayments))
                / (Math.pow(1 + monthlyInterestRate, numberOfPayments) - 1);
    }
}

@Component
public class App {
    final MortgageCalculatorService calculatorService;

    public App(MortgageCalculatorService calculatorService) {   // зависимость приходит снаружи
        this.calculatorService = calculatorService;
    }
}

App нигде не пишет new MortgageCalculatorServiceImpl(): он получает сервис через конструктор и не знает, какая реализация ему досталась. Кто её выберет и создаст, описывает конфигурация, и у Spring есть три способа её записать. Первый, исторический, — XML-файл, который по традиции называется applicationContext.xml. В нём перечислены бины: у каждого есть идентификатор и класс, а constructor-arg ref говорит, какой бин передать в конструктор.

<bean id="app" class="dev.team.mortgage.App">
    <constructor-arg ref="mortgageCalculatorService"/>
</bean>

Второй способ — класс конфигурации. Это обычный класс с аннотацией @Configuration, в котором каждый метод с @Bean возвращает бин; имя бина совпадает с именем метода, а тип — с типом результата. Зависимость App объявлена параметром метода, и контейнер сам передаст туда бин подходящего типа.

@Configuration
public class AppConfig {
    @Bean
    MortgageCalculatorService mortgageCalculatorService() {
        return new MortgageCalculatorServiceImpl();
    }

    @Bean
    App app(MortgageCalculatorService mortgageCalculatorService) {
        return new App(mortgageCalculatorService);
    }
}

Листинг 9.10. Класс конфигурации с @Bean-методами.

Третий способ — сканирование компонентов. Классы помечают аннотациями @Service, @Component, @Repository или @Controller, а конфигурация только называет пакет, в котором их искать. Для контейнера @Service и @Component равнозначны, но @Service яснее говорит читателю о роли класса. В нашем проекте AppConfig лежит в том же пакете, поэтому его приходится исключить фильтром, иначе его @Bean-методы зарегистрировали бы те же бины второй раз.

@Configuration
@ComponentScan(basePackages = "dev.team.mortgage",
        excludeFilters = @ComponentScan.Filter(type = FilterType.ANNOTATION, classes = Configuration.class))
public class ScanConfig { }

Каждую конфигурацию запускает свой класс контекста: XML читает ClassPathXmlApplicationContext, а класс конфигурации или пакет для сканирования принимает AnnotationConfigApplicationContext. Дальше бин получают по имени или по типу, и результат во всех трёх случаях одинаков. Запуск на Spring Framework 7.0.9 считает платёж по кредиту в 250 000 долларов под 6,5 % годовых на 30 лет:

try (var ctx = new AnnotationConfigApplicationContext(AppConfig.class)) {
    App app = ctx.getBean(App.class);
    System.out.printf(Locale.US, "Monthly Payment: $%,.2f%n", app.calculatorService.payment(250_000, 6.5, 30));
}

2.2 Сначала описание, потом объект

Прочитав конфигурацию, контейнер не создаёт объекты сразу. Сначала он превращает каждую запись о бине в описание, объект BeanDefinition, и складывает описания в реестр. Описание хранит всё, что понадобится потом: класс (или его имя строкой, если класс ещё не загружен), область видимости (scope, подробно в 5.2), признаки lazy, primary и autowire-candidate, аргументы конструктора и значения свойств, методы инициализации и уничтожения, список depends-on, а для бина из @Bean-метода — имя фабричного бина и фабричного метода. Сколько описаний получилось, видно сразу после старта контекста:

@Configuration: определений бинов: 8 [...internalConfigurationAnnotationProcessor,
                ...internalAutowiredAnnotationProcessor, ...internalCommonAnnotationProcessor,

                appConfig, mortgageCalculatorService, app]

У XML-контекста два описания, ровно по числу тегов <bean>. У контекста на аннотациях их восемь: кроме самой конфигурации и двух бинов, AnnotationConfigApplicationContext зарегистрировал пять служебных. Это постпроцессоры, которые и придают смысл аннотациям: один разбирает классы @Configuration и @Bean-методы, другой обрабатывает @Autowired, третий — @PostConstruct и @PreDestroy, остальные два — @EventListener. Без них аннотации остались бы просто метаданными в байткоде.

Описания разных источников представлены разными классами. Запуск показывает это для бина app: в конфигурации AppConfig его описание — ConfigurationClassBeanDefinition, а найденное сканированием — ScannedGenericBeanDefinition. Всего классов пять:

Строка о ScannedGenericBeanDefinition объясняет, почему сканирование безопасно для пакетов, где лежат не только компоненты. Сканер не загружает классы в JVM, а читает .class-файлы как байты библиотекой ASM (класс SimpleMetadataReader) и отбирает кандидатов по аннотациям. Загрузка класса выполнила бы его статическую инициализацию, а при сканировании этого не происходит. В пакет примера положен класс NotABean без аннотаций, со статическим блоком, который печатает сообщение. Сканирование всего пакета dev.team.mortgage прошло, а сообщения в выводе нет: класс не был загружен.

Разделение на описание и объект нужно не ради порядка в коде. Пока объектов нет, описание ещё можно изменить, и этим пользуется BeanFactoryPostProcessor — постпроцессор, который работает с реестром описаний до создания бинов (подробно в 4.2). Перед созданием объекта фабрика сливает описание с родительским, заданным через parentName, в одно RootBeanDefinition (метод getMergedLocalBeanDefinition), и после этого менять описание поздно. Опыт показывает, как постпроцессор вмешивается вовремя: он меняет у mortgageCalculatorService область видимости на prototype, пока не создан ни один объект.

ctx.register(AppConfig.class);
ctx.addBeanFactoryPostProcessor(bf ->
        bf.getBeanDefinition("mortgageCalculatorService").setScope(BeanDefinition.SCOPE_PROTOTYPE));
ctx.refresh();
Object a = ctx.getBean("mortgageCalculatorService"), b = ctx.getBean("mortgageCalculatorService");

2.3 Фабрика бинов и контекст приложения

Описания хранит реестр (BeanDefinitionRegistry, методы registerBeanDefinition, removeBeanDefinition, getBeanDefinition), а объекты по ним создаёт фабрика бинов (BeanFactory). На практике обе роли выполняет один класс, DefaultListableBeanFactory. Он же служит SingletonBeanRegistry, хранилищем созданных синглтонов. Над ним выстроена лестница интерфейсов, и у всей лестницы одна полноценная реализация:

BeanFactory                 getBean(...), containsBean, isSingleton
  ↳ ListableBeanFactory     getBeanNamesForType, getBeansWithAnnotation — обход всех определений
  ↳ HierarchicalBeanFactory getParentBeanFactory — иерархия контекстов
  ↳ AutowireCapableBeanFactory  autowireBean, initializeBean, createBean для внешних объектов
     ↳ ConfigurableListableBeanFactory  всё вместе + preInstantiateSingletons
        ↳ DefaultListableBeanFactory    единственная полноценная реализация

Так было не всегда. Во времена Spring 2.5 контейнер обычно создавали одной строкой new XmlBeanFactory(new ClassPathResource("app.xml", getClass())), и этот класс сам читал XML и сам создавал бины. В Spring 3.1 XmlBeanFactory объявили устаревшим в пользу связки DefaultListableBeanFactory и XmlBeanDefinitionReader, а в javadoc Spring Framework 6.0 его уже нет.3 С тех пор чтение описаний отделено от создания объектов: читатели XML, классы конфигурации и сканер только наполняют реестр, а фабрика одна.

Фабрику можно использовать и без контекста, и опыт показывает, чего ей тогда не хватает. В голый DefaultListableBeanFactory зарегистрировано описание бина RateSource, у которого есть метод с @PostConstruct:

По той же причине в голой фабрике не работают @Autowired и @Transactional. Тот же бин в контексте ведёт себя иначе:

Контекст приложения, ApplicationContext, расширяет BeanFactory и отличается от фабрики двумя вещами, обе видны в выводе. Он сам находит и подключает все постпроцессоры, поэтому @PostConstruct сработал. И он создаёт синглтоны на старте, в методе preInstantiateSingletons внутри refresh(), а не по первому запросу. Раннее создание выгодно: ошибка конфигурации, например неверный пароль к базе, проявится при запуске, а не на первом платеже. Помимо бинов контекст хранит служебные сведения, например активный профиль. В приложении на Spring Boot контекст руками не создают: его создаёт SpringApplication.run(), а класс контекста выбирается по тому, что лежит в classpath. С веб-стартером Spring MVC это AnnotationConfigServletWebServerApplicationContext со встроенным сервером (подкласс GenericWebApplicationContext), с WebFlux — AnnotationConfigReactiveWebServerApplicationContext, без веба — AnnotationConfigApplicationContext. Их общий предок GenericApplicationContext удобен в тестах: бины в нём регистрируют вызовом registerBean, без сканирования.

Функция-поставщик (instance supplier) создаёт объект без рефлексии, но AOT-обработка, подготовка контекста при сборке (раздел 15), её не поддерживает: код лямбды нельзя перенести в сгенерированные классы (Spring Reference: AOT).

Последний интерфейс лестницы, который нужен на практике, — AutowireCapableBeanFactory. Через него проводят сквозь контейнер объект, созданный не контейнером: восстановленный из JSON или созданный планировщиком Quartz. autowireBean внедряет такому объекту зависимости, а initializeBean проводит его через обратные вызовы Aware (вроде setApplicationContext), BeanPostProcessor'ы и методы инициализации.

@Component
class ExternalObjectEnricher {
    private final AutowireCapableBeanFactory factory;

    ExternalObjectEnricher(AutowireCapableBeanFactory factory) { this.factory = factory; }

    <T> T enrich(T external) {
        factory.autowireBean(external);
        return (T) factory.initializeBean(external, external.getClass().getName());
    }
}

❓ Спрашивают на интервью. Чем BeanFactory отличается от ApplicationContext? В приложениях работают с контекстом, а голая фабрика осталась внутренней деталью.

3. Как стартует контекст: метод refresh()

Контекст приложения оживает в одном методе, refresh() класса AbstractApplicationContext. До его вызова в контексте есть только зарегистрированные классы конфигурации, а после возврата все синглтоны созданы, связаны, обёрнуты в прокси и запущены. Внутри метода проходит двенадцать шагов, и их порядок важен на практике: от того, на каком шаге создан бин, зависит, достанутся ли ему внедрение зависимостей, @PostConstruct, транзакции и кэш. Раздел начинается с опыта, в котором каждая точка расширения контейнера печатает строку в момент срабатывания. Затем те же шаги разобраны по порядку, а в конце показано, что теряет бин, созданный раньше своего шага, и почему это не всегда видно в журнале.

3.4 Что Spring Boot делает до refresh()

В приложении на Spring Boot refresh() вызывает SpringApplication.run(), и до этого вызова проходит собственная подготовка Boot. Он создаёт BootstrapContext и публикует ApplicationStartingEvent, затем готовит Environment, публикует ApplicationEnvironmentPreparedEvent, и в этот момент ConfigDataEnvironmentPostProcessor читает application.yml, профили и файлы из spring.config.import. После этого печатается баннер, создаётся контекст нужного типа, применяются все ApplicationContextInitializer (событие ApplicationContextInitializedEvent), загружаются источники конфигурации (ApplicationPreparedEvent), и только потом вызывается refresh(). Подробно эта подготовка разобрана в главе 10.

Граница между подготовкой Boot и шагами контейнера объясняет известную ловушку. Свойства из @PropertySource на классе @Configuration попадают в Environment только на шаге 5, когда разбирается конфигурация. Настройки, которые Boot читает раньше, например logging.* и spring.main.*, к этому моменту уже применены, и файл, подключённый через @PropertySource, на них не влияет. Такие настройки задают в application.yml, в переменных окружения или аргументах командной строки.

❓ Спрашивают на интервью. Почему @Transactional не работает на бине, который нужен моему BeanPostProcessor? Постпроцессоры бинов создаются на шаге 6 refresh(), раньше обычных бинов, и всё, от чего они зависят, тоже создаётся рано, пока зарегистрированы не все постпроцессоры. Создатель прокси AOP к этому моменту может быть ещё не зарегистрирован, и бин остаётся без прокси, а значит без транзакций и кэша; Spring пишет об этом предупреждение is not eligible for getting processed by all BeanPostProcessors. Если же бин понадобился постпроцессору фабрики на шаге 5, он теряет обработку молча. Лечат это static-методами без параметров для постпроцессоров и ленивым получением зависимостей через ObjectProvider.

4. Жизненный цикл бина

Каждый бин проходит через одни и те же этапы: контейнер создаёт объект, внедряет зависимости, вызывает методы инициализации, при необходимости подменяет объект прокси, а при закрытии контекста вызывает методы уничтожения. Порядок этих этапов определяет, что бину уже доступно в каждый момент. В @PostConstruct зависимости уже внедрены, но транзакций ещё нет, потому что прокси появляется позже. В методе уничтожения бин ещё может закрыть свои ресурсы, а вот события публиковать уже поздно. Раздел начинается с опыта, в котором сервис лимитов печатает каждый вызов от конструктора до закрытия. Затем на том же сервисе показано, как постпроцессор подменяет бин прокси, и разобрано, куда ставить код, который должен выполниться при старте приложения.

4.1 От конструктора до закрытия

Сервис лимитов в опыте реализует все обратные вызовы, какие бывают у бина: сеттер с @Autowired, интерфейс BeanNameAware, через который бин узнаёт своё имя, @PostConstruct, InitializingBean, метод инициализации из @Bean(initMethod = ...), а для закрытия — @PreDestroy, DisposableBean и метод уничтожения из @Bean(destroyMethod = ...). Рядом стоит постпроцессор бинов, который печатает свои вызовы до и после инициализации.

public static class LimitService implements LimitChecker, BeanNameAware, InitializingBean, DisposableBean {
    public LimitService() { System.out.println(" 1. конструктор"); }
    @Autowired void setDirectory(LimitsDirectory d) { System.out.println(" 2. внедрение через @Autowired-сеттер"); }
    @Override public void setBeanName(String n) { System.out.println(" 3. BeanNameAware: " + n); }
    @PostConstruct void post() { System.out.println(" 5. @PostConstruct, this — " + getClass().getSimpleName()); }
    @Override public void afterPropertiesSet() { System.out.println(" 6. afterPropertiesSet"); }
    void customInit() { System.out.println(" 7. initMethod"); }
    @Override public boolean allowed(long amountKop) { return amountKop <= 15_000_000; }
    @PreDestroy void pre() { System.out.println(" 9. @PreDestroy"); }
    @Override public void destroy() { System.out.println("10. DisposableBean.destroy"); }
    void customDestroy() { System.out.println("11. destroyMethod"); }
}

Для @Bean контейнер к тому же сам находит у объекта публичный метод close или shutdown и вызывает его при закрытии, поэтому пул соединений, объявленный @Bean-методом, закрывается без всяких настроек: в том же опыте класс RatesPool без единой аннотации получил вызов своего close() при закрытии контекста. Отключает такой поиск destroyMethod = "".6

Третье наблюдение объясняет строку 4, которая стоит раньше @PostConstruct. Аннотации @PostConstruct и @Autowired сами ничего не делают: их обрабатывают обычные постпроцессоры: CommonAnnotationBeanPostProcessor (он же отвечает за @PreDestroy и @Resource) и AutowiredAnnotationBeanPostProcessor. 4.2 Постпроцессор подменяет бин прокси

Строка 8 опыта — главная для всего, что дальше в главе связано с прокси. Метод postProcessAfterInitialization вправе вернуть не тот объект, который получил, и контейнер положит в реестр то, что вернул постпроцессор. Постпроцессор в опыте возвращает вместо сервиса лимитов динамический прокси JDK, который печатает каждый вызов и передаёт его настоящему объекту:

@Bean static BeanPostProcessor auditProxy() {
    return new BeanPostProcessor() {
        @Override public Object postProcessAfterInitialization(Object bean, String name) {
            if (!(bean instanceof LimitChecker target)) return bean;
            return Proxy.newProxyInstance(LimitChecker.class.getClassLoader(), new Class<?>[]{LimitChecker.class},
                    (proxy, method, args) -> {
                        System.out.println("    [аудит] " + method.getName() + "(" + args[0] + ")");
                        return method.invoke(target, args);
                    });
        }
    };
}

4.3 Код, который выполняется при старте

Сервису курсов нужно при старте загрузить курсы на текущую дату, потребителю очереди — начать читать сообщения, отчёту — проверить, что справочники заполнены. Мест, куда можно поставить такой код, несколько, и они срабатывают в разное время. Опыт на Spring Boot 4.1.1 печатает их по порядку:

public static class RatesLoader implements SmartInitializingSingleton, SmartLifecycle {
    @PostConstruct void post() { System.out.println("1. @PostConstruct — бин создан, другие бины могут быть ещё не созданы"); }
    @Override public void afterSingletonsInstantiated() { System.out.println("2. SmartInitializingSingleton — созданы все синглтоны"); }
    @Override public void start() { running = true; System.out.println("3. SmartLifecycle.start — запуск компонентов"); }
    // stop() и isRunning() опущены
}

@EventListener void refreshed(ContextRefreshedEvent e) { System.out.println("4. ContextRefreshedEvent — refresh() завершён"); }
@EventListener void started(ApplicationStartedEvent e) { System.out.println("5. ApplicationStartedEvent — контекст поднят, раннеры ещё не вызваны"); }
@Bean ApplicationRunner appRunner() { return a -> System.out.println("6. ApplicationRunner.run — аргументы: " + a.getOptionNames()); }
@Bean CommandLineRunner cliRunner() { return a -> System.out.println("7. CommandLineRunner.run — аргументы: " + String.join(" ", a)); }
@EventListener void ready(ApplicationReadyEvent e) { System.out.println("8. ApplicationReadyEvent — приложение готово принимать работу"); }

Первые четыре точки принадлежат контейнеру Spring и срабатывают внутри refresh(), остальные добавляет Spring Boot уже после него. От выбора зависит, что будет готово к моменту вызова:

  • @PostConstruct подходит для проверки и подготовки самого бина: убедиться, что настройки заданы, заполнить внутренний кэш из уже внедрённых зависимостей. Прокси у бина ещё нет, и транзакционные методы других бинов вызывать отсюда рискованно: созданы ещё не все бины.
  • SmartInitializingSingleton.afterSingletonsInstantiated вызывается, когда созданы все синглтоны и прокси. Здесь уже можно обращаться к другим бинам через их прокси.
  • SmartLifecycle.start — место для компонентов с собственным циклом «запуск — остановка»: потребителей очередей, планировщиков, серверов. Контейнер вызывает start() после создания всех бинов, а stop() — первым делом при закрытии, до уничтожения бинов, поэтому потребитель успевает прекратить приём сообщений, пока его зависимости ещё живы (раздел 12.4). В опыте при закрытии строка SmartLifecycle.stop напечаталась раньше @PreDestroy того же бина.
  • ApplicationRunner и CommandLineRunner вызываются, когда контекст полностью поднят, и получают аргументы командной строки: CommandLineRunner — как массив строк, ApplicationRunner — разобранными (getOptionNames() вернул [date]). Сюда удобно ставить разовую работу при старте, например загрузку демонстрационных данных. Порядок между ApplicationRunner и CommandLineRunner без @Order гарантировать нельзя: в опыте CommandLineRunner выполнился раньше ApplicationRunner, хотя объявлен позже. Если порядок важен, его задают аннотацией @Order или интерфейсом Ordered.
  • ApplicationReadyEvent публикуется последним, когда отработали все ApplicationRunner и CommandLineRunner. Это сигнал «приложение готово»: на него удобно повесить регистрацию в балансировщике или первое оповещение мониторинга.

❓ Спрашивают на интервью. Почему @Transactional-метод, вызванный из @PostConstruct, работает без транзакции? @PostConstruct вызывается внутри postProcessBeforeInitialization, на исходном объекте, а прокси, который открывает транзакцию, создаётся позже, в postProcessAfterInitialization. Вызов this.method() к тому же никогда не проходит через прокси. Работу, которой нужна транзакция, при старте переносят в SmartInitializingSingleton, ApplicationRunner или слушатель ApplicationReadyEvent, а метод вызывают через другой бин, у которого прокси уже есть.

5. Способы внедрения и области видимости

У каждой зависимости есть два независимых свойства. Первое — путь, которым контейнер передаёт её в объект: через конструктор, через сеттер или прямо в поле. Второе — сколько живёт сам бин и сколько его экземпляров создаёт контейнер; это свойство называют областью видимости (scope). От первого зависит, можно ли создать объект без контейнера и будет ли он неизменяемым, от второго — что получит синглтон, если внедрить в него короткоживущий бин. Раздел разбирает оба свойства на опытах: сначала способы внедрения и выбор конструктора, затем области видимости, прототип внутри синглтона и уничтожение прототипов.

5.1 Конструктор, сеттер или поле

Возьмём сервис антифрода, которому нужен набор правил проверки. Зависимость можно передать тремя путями:

// 1. Через конструктор
@Component
public class AntiFraud {
    private final List<FraudRule> rules;
    public AntiFraud(List<FraudRule> rules) { this.rules = rules; }
}

// 2. Через сеттер
@Component
public class AntiFraudReport {
    private List<FraudRule> rules;
    @Autowired public void setRules(List<FraudRule> rules) { this.rules = rules; }
}

// 3. Прямо в поле
@Component
public class LegacyAntiFraud {
    @Autowired private List<FraudRule> rules;
}

Листинг 9.34. Три способа внедрить зависимость: конструктор, сеттер, поле.

Для контейнера все три пути равноценны, разница проявляется вне его. Объект с внедрением в поле нельзя правильно создать без Spring: в опыте new для такого класса дал объект с пустым полем, и первый же вызов метода закончился NullPointerException. Чтобы протестировать такой класс, приходится либо поднимать контекст, либо записывать поле через рефлексию, например ReflectionTestUtils.setField. Объект с внедрением через конструктор создаётся в тесте обычным new AntiFraud(List.of(rule)), и состояния «создан, но зависимости ещё не внедрены» у него не бывает. Поле к тому же можно объявить final, объект становится неизменяемым, а final-поля по модели памяти Java видны другим потокам заполненными без дополнительной синхронизации (глава 08). Конструктор с семью параметрами ещё и честно показывает, что класс делает слишком много; семь полей с @Autowired глаз легко пропускает. Сеттер оставляют для необязательных зависимостей, которые можно поменять после создания; если бина может не оказаться вовсе, сеттер помечают @Autowired(required = false), и контейнер его просто не вызовет.

Аннотацию @Autowired на конструкторе писать не обязательно: если конструктор у класса один, Spring внедряет зависимости через его параметры сам. Правило перестаёт работать, когда конструкторов несколько, и тут опыт показывает две ловушки:

@Component
public static class TwoCtors {
    final String how;
    public TwoCtors() { how = "конструктор без параметров"; }
    public TwoCtors(List<FraudRule> rules) { how = "конструктор с правилами (" + rules.size() + ")"; }
}

public static class TwoArgCtors {                       // конструктора без параметров нет
    public TwoArgCtors(List<FraudRule> r) { }
    public TwoArgCtors(Map<String, FraudRule> m) { }
}

5.2 Синглтон и прототип

Область видимости определяет, сколько экземпляров бина создаёт контейнер. По умолчанию бин — синглтон (singleton): один объект на контекст, и все получают ссылку на него. Прототип (prototype) — новый объект на каждый запрос к контейнеру, будь то getBean или внедрение. В веб-приложении к ним добавляются request (объект на HTTP-запрос), session (на HTTP-сессию), application (на ServletContext) и websocket. Область задаёт аннотация @Scope:

@Bean @Scope("prototype")
PaymentDraft paymentDraft() { return new PaymentDraft(); }   // черновик поручения: у каждой операции свой

Объекты с областями request и session Spring привязывает к текущему запросу через RequestContextHolder, а тот хранит атрибуты запроса в переменной потока. Поэтому из другого потока, например из метода с @Async, бин области request недоступен, если не включено наследование атрибутов запроса дочерними потоками (FrameworkServlet.setThreadContextInheritable), и для пула потоков такое наследование работает так же ненадёжно, как наследование контекста безопасности в главе 13.8

5.3 Прототип внутри синглтона

Самая частая ошибка с областями видимости — внедрить прототип в синглтон и ждать нового объекта при каждом обращении. Внедрение выполняется один раз, при создании синглтона, и синглтон навсегда сохраняет тот прототип, который получил:

public static class StuckService {
    final PaymentDraft draft;
    public StuckService(PaymentDraft draft) { this.draft = draft; }
    int draftNo() { return draft.no(); }
}

У ObjectProvider есть и другие методы: getIfAvailable() вернёт null, если бина нет, getIfUnique() — если кандидатов несколько, а stream() и orderedStream() обойдут всех кандидатов. Поэтому он годится и для необязательных зависимостей.

Второй способ — @Lookup на абстрактном методе: Spring сам реализует метод в подклассе CGLIB так, чтобы тот возвращал бин из контейнера. Опыт показывает его ограничение, о котором легко не знать:

@Component
public static abstract class LookupService {
    @Lookup protected abstract PaymentDraft draft();
    int draftNo() { return draft().no(); }
}

Третий способ — прокси области видимости (scoped proxy): в синглтон внедряется прокси, который при каждом вызове метода берёт объект текущей области. Для request и session это правильный и обычный путь, а для прототипа он даёт ловушку:

5.4 Прототип и @PreDestroy

Контейнер проводит прототип через весь путь создания: внедрение, Aware, постпроцессоры, @PostConstruct. А после выдачи забывает о нём, и методы уничтожения у прототипа не вызывает. Опыт считает это:

Поэтому прототип не должен владеть ресурсом: соединения берут из пула, который живёт в синглтоне, а объект с ресурсом реализует AutoCloseable и используется в try-с-ресурсами: try (var session = sessions.getObject()) { session.upload(file); }.

6. Циклические зависимости

Циклическая зависимость (circular dependency) возникает, когда бину A для создания нужен бин B, а бину B нужен A. В платёжном сервисе так бывает почти незаметно: сервис платежей проверяет перевод через сервис лимитов, а сервис лимитов, пересчитывая остаток лимита, запрашивает у сервиса платежей сумму операций за день. Контейнер может разрешить такой цикл, а может отказаться, и зависит это от способа внедрения, от версии Spring и от того, получают ли бины прокси. Раздел начинается с опыта, в котором один и тот же цикл собран разными способами, затем объясняет, как контейнер разрешает цикл через сеттеры, и показывает, как с этим изменилось поведение в Spring 6.2 и где цикл приводит к тихой ошибке.

6.1 Один цикл, пять исходов

В опыте два сервиса, платежей и лимитов, ссылаются друг на друга, и цикл собран пятью способами: через конструкторы, через сеттеры, через сеттеры при бине с @Async, через конструкторы с @Lazy на одном параметре и через сеттеры в приложении на Spring Boot.

@Component public static class PaymentsCtor { public PaymentsCtor(LimitsCtor l) { } }
@Component public static class LimitsCtor { public LimitsCtor(PaymentsCtor p) { } }

@Component public static class PaymentsSetter { @Autowired void setLimits(LimitsSetter l) { ... } }
@Component public static class LimitsSetter { @Autowired void setPayments(PaymentsSetter p) { ... } }

@Component public static class PaymentsLazy { public PaymentsLazy(@Lazy LimitsLazy l) { ... } }
@Component public static class LimitsLazy { public LimitsLazy(PaymentsLazy p) { ... } }

6.2 Как контейнер разрешает цикл через сеттеры

Цикл через сеттеры разрешается благодаря тому, что контейнер умеет выдать ссылку на бин, который ещё создаётся. Для этого в DefaultSingletonBeanRegistry есть три словаря, их часто называют трёхуровневым кэшем синглтонов:

  1. singletonObjects хранит полностью готовые бины; отсюда getBean берёт результат почти всегда.
  2. singletonFactories хранит фабрики ранних ссылок: сразу после вызова конструктора бин кладут сюда в виде функции, которая умеет выдать ссылку на ещё не достроенный объект.
  3. earlySingletonObjects запоминает уже выданную раннюю ссылку, чтобы все, кто попросит недостроенный бин, получили один и тот же объект.

Цикл платежей и лимитов проходит так. Контейнер вызывает конструктор Payments и кладёт в singletonFactories фабрику его ранней ссылки. Затем он внедряет зависимости Payments и обнаруживает, что нужен Limits. Создавая Limits, контейнер доходит до сеттера setPayments, ищет Payments в первом словаре, не находит, ищет во втором, не находит, берёт фабрику из третьего и получает раннюю ссылку на недостроенный Payments. Limits достраивается целиком и попадает в singletonObjects, после чего достраивается и Payments.

Фабрика ранней ссылки — не просто () -> bean. Она вызывает у постпроцессоров getEarlyBeanReference, и постпроцессор, который создаёт прокси, вроде механизма AOP Spring, здесь же возвращает прокси вместо объекта. Так в опыте с @Async соседу внедрён тот же прокси, что лежит в контексте. Трудность возникает с постпроцессором, который умеет подменять бин прокси только после инициализации, в postProcessAfterInitialization. К этому моменту сосед уже получил раннюю ссылку на исходный объект, а в контексте окажется прокси, то есть в приложении будут два разных «одних и тех же» бина. Опыт проверяет три варианта такого постпроцессора на четырёх версиях Spring:

public static class LateProxyBpp implements BeanPostProcessor {                  // прокси только после инициализации
    @Override public Object postProcessAfterInitialization(Object bean, String name) {
        return bean instanceof Payments ? proxyOf(bean) : bean;
    }
}

public static class EarlyProxyBpp implements SmartInstantiationAwareBeanPostProcessor {   // умеет отдать прокси раньше
    @Override public Object getEarlyBeanReference(Object bean, String name) { ... return proxyOf(bean); }
    @Override public Object postProcessAfterInitialization(Object bean, String name) { ... }
}

public static class LateProxyBothBpp implements BeanPostProcessor {              // прокси обоим бинам, только после инициализации
    @Override public Object postProcessAfterInitialization(Object bean, String name) {
        return (bean instanceof Payments || bean instanceof Limits) ? proxyOf(bean) : bean;
    }
}

6.3 Цикл как проблема проекта

Все способы, которыми Spring разрешает цикл, лечат симптом. Сам цикл между сервисами означает, что у них нет чёткой границы ответственности: сервис платежей зависит от лимитов, а лимиты от платежей, и изменить один, не задев другой, нельзя. Поэтому запрет циклов в Spring Boot по умолчанию разумен, а включать spring.main.allow-circular-references=true стоит только как временную меру при обновлении старого приложения.

Разрывают цикл перестройкой зависимостей. Чаще всего общую часть выносят в третий бин: сумму операций за день знает не сервис платежей, а отдельный журнал операций, от которого зависят оба сервиса. Если направление вызова обратное и редкое, сервис лимитов может не вызывать платежи, а публиковать событие, на которое платежи подписаны (раздел 10). @Lazy на параметре конструктора поднимет контекст, но оставит цикл в коде и спрячет его за прокси, поэтому его применяют, когда перестройку отложили сознательно. Чтобы новый цикл не появился незаметно, его ловят тестом архитектуры ещё до запуска: правилом ArchUnit slices().should().beFreeOfCycles() для пакетов или, в модульном монолите на Spring Modulith, вызовом ApplicationModules.verify() (глава 32).

❓ Спрашивают на интервью. Как Spring разрешает циклические зависимости и почему не может при внедрении через конструктор? При внедрении через сеттеры или поля контейнер создаёт объект конструктором, кладёт фабрику его ранней ссылки в singletonFactories и, когда сосед просит этот бин, отдаёт недостроенный объект или, если бин получает прокси AOP, прокси через getEarlyBeanReference. При внедрении через конструктор объект нельзя создать, не имея готового соседа, поэтому цикл заканчивается BeanCurrentlyInCreationException. Spring Boot с версии 2.6 запрещает циклы и через сеттеры. Хороший ответ добавляет, что цикл — признак плохих границ между сервисами, и лечат его выносом общей части в третий бин или событием, а @Lazy лишь прячет цикл за прокси.

7. @Configuration и подкласс CGLIB

Класс с @Configuration объявляет бины своими @Bean-методами, но кроме этого Spring по умолчанию подменяет его подклассом, созданным библиотекой генерации байткода CGLIB. Подкласс перехватывает вызов одного @Bean-метода из другого и вместо нового объекта возвращает бин из контейнера. От этого зависит, сколько пулов соединений или клиентов окажется в приложении, поэтому разницу между полным режимом с подклассом и облегчённым режимом без него нужно знать. Раздел показывает её на опыте и перечисляет ограничения полного режима.

7.1 Вызов @Bean-метода из другого

В классе конфигурации один @Bean-метод часто вызывает другой, чтобы передать готовую зависимость, и от режима конфигурации зависит, что вернёт такой вызов: бин из контейнера или новый объект. Классический пример Java-конфигурации: сервис товаров зависит от сервиса остатков, и метод productService() сам вызывает соседний метод inventoryService().

@Configuration
public static class FullConfig {
    @Bean public InventoryService inventoryService() { return new InventoryService(); }
    @Bean public ProductService productService() { return new ProductService(inventoryService()); }
}

В полном режиме бин конфигурации — подкласс FullConfig$$SpringCGLIB$$0. Он переопределяет inventoryService(): при вызове проверяет, есть ли такой бин в контейнере, и возвращает его, поэтому объект создан один раз. В облегчённом режиме, @Configuration(proxyBeanMethods = false), подкласса нет, вызов inventoryService() — обычный вызов Java, и сервис товаров получает второй объект, о котором контейнер не знает. Если на месте сервиса остатков стоит HikariDataSource, это второй пул соединений к той же базе со своим лимитом. Тот же облегчённый режим получается у @Bean-методов внутри класса с @Component, даже если об этом не задумываться.

Правильный способ для облегчённого режима — передавать зависимость параметром метода: productService(InventoryService inventory). Тогда контейнер сам подставит готовый бин, и третья строка опыта показывает один объект без всякого подкласса. Облегчённый режим не создаёт классов на лету, поэтому стартует быстрее и лучше подходит для нативной сборки; так написана вся автоконфигурация Spring Boot. Полный режим нужен только конфигурациям, где уже есть прямые вызовы между @Bean-методами, и переводить такую конфигурацию на proxyBeanMethods = false, не заменив вызовы параметрами, нельзя: появятся дубликаты, а компилятор ничего не скажет.10

7.2 Ограничения полного режима

Полный режим держится на подклассе, который Spring создаёт для класса конфигурации, а подкласс может переопределить только то, что Java разрешает переопределять: ни класс конфигурации, ни его @Bean-методы не могут быть final, и методы к тому же не могут быть private. Spring проверяет это при разборе конфигурации, и опыт с обоими нарушениями показывает сообщения:

FinalConfig: BeanDefinitionParsingException: Configuration problem: @Configuration class 'FinalConfigLab.FinalConfig' may not be final. Remove the final modifier to continue.
PrivateBeanMethod: BeanDefinitionParsingException: Configuration problem: @Bean method 'rates' must not be private or final; change the method's modifiers to continue.

Листинг 9.56. Опыт 7.2: final-класс конфигурации и private @Bean-метод.

Класс конфигурации в полном режиме не может быть final, а @Bean-методы — private или final; контекст с такой конфигурацией не поднимается. В Kotlin классы и методы по умолчанию final, поэтому конфигурации либо открывают плагином компилятора kotlin-spring (all-open), либо объявляют с proxyBeanMethods = false; в практикуме главы 81, где плагина нет, класс приложения так и помечен. Третий вариант — статический @Bean-метод: он вызывается без экземпляра конфигурации, и только так правильно объявлять постпроцессоры (раздел 3.3).

❓ Спрашивают на интервью. Зачем @Configuration нужен CGLIB и что даёт proxyBeanMethods = false? По умолчанию Spring подменяет класс конфигурации подклассом, который перехватывает вызовы @Bean-методов и возвращает бин из контейнера, поэтому new ProductService(inventoryService()) получает тот же синглтон, а не новый объект. С proxyBeanMethods = false подкласса нет, вызов метода создаёт новый объект, и зависимости надо передавать параметрами @Bean-методов; взамен старт быстрее и нет ограничений на final. Полный режим запрещает final-класс конфигурации и private или final @Bean-методы.

8. Прокси

Прокси (proxy), или посредник, — это объект, который контейнер подставляет вместо бина, чтобы выполнять код до и после вызова его методов. Так в Spring устроены транзакции, кэш, проверка прав, асинхронные методы и аспекты: клиент держит ссылку на прокси, прокси открывает транзакцию или проверяет права и передаёт вызов настоящему объекту, который называют целевым (target). Создают прокси двумя способами, через динамический прокси JDK и через подкласс, сгенерированный библиотекой CGLIB, и от способа зависит, что прокси умеет перехватить. Раздел начинается с прокси JDK, написанного вручную, затем показывает, как Spring выбирает способ и как выглядит сгенерированный класс, и заканчивается тремя вопросами, на которых чаще всего ошибаются: вызов через this, методы, которые прокси перехватить не может, и проверка типа бина.

8.1 Прокси JDK

Платёжный шлюз описан интерфейсом PaymentGateway, и нужно, ничего не меняя в его реализации, замерять время каждого вызова. Стандартная библиотека Java позволяет создать во время работы программы класс, который реализует заданные интерфейсы и передаёт любой вызов их методов одному обработчику:

public interface PaymentGateway { String pay(String account, long kopecks); }

static class TimingHandler implements InvocationHandler {
    private final Object target;
    TimingHandler(Object target) { this.target = target; }
    @Override public Object invoke(Object proxy, Method method, Object[] args) throws Throwable {
        long start = System.nanoTime();
        Object result = method.invoke(target, args);
        System.out.printf("   [обработчик] %s, %d мкс%n", method.getName(), (System.nanoTime() - start) / 1000);
        return result;
    }
}

PaymentGateway gw = (PaymentGateway) Proxy.newProxyInstance(PaymentGateway.class.getClassLoader(),
        new Class<?>[] {PaymentGateway.class}, new TimingHandler(new BankGateway()));

Сгенерированный класс $Proxy0 объявлен public final и наследует java.lang.reflect.Proxy, а для одного загрузчика и одного набора интерфейсов JVM создаёт его один раз: второй прокси получил тот же класс. Даже в этом примере видно, во что обходится ручной посредник. Нужны интерфейс, реализация и обработчик, который разбирает вызовы рефлексией, а для класса без интерфейса стандартный механизм не годится вовсе: подкласс приходится строить библиотеками генерации байткода вроде CGLIB, ASM или Javassist. Такой код объёмен и сложен, и прикладной программист его почти не пишет.4 Spring берёт эту работу на себя: обработчиком вызовов у него служит класс JdkDynamicAopProxy, который передаёт вызов цепочке перехватчиков, а для классов без интерфейса Spring генерирует подкласс собственной копией CGLIB, встроенной в spring-core.

8.3 Вызов через this

Сервис платёжных поручений проводит пачку поручений методом transferAll, который для каждого вызывает transfer, помеченный @Transactional. Опыт с менеджером транзакций, который печатает начало и фиксацию, показывает, что при вызове снаружи транзакция открывается, а при вызове из соседнего метода того же бина её нет:

public:
   begin TransferService.transfer
   transfer: транзакция есть
   commit
public без @Transactional, внутри this.transfer():
   transferAll: транзакция нет
   transfer: транзакция нет

Листинг 9.63. Опыт 8.3: транзакция при вызове снаружи и через this.

Причина следует из устройства прокси. Клиент вызывает transferAll у прокси, прокси не находит на этом методе советов и передаёт вызов целевому объекту. Внутри целевого объекта this указывает на него самого, поэтому transfer() становится обычным вызовом Java, и прокси о нём не узнаёт. Такую ситуацию называют вызовом самого себя (self-invocation), и она одинаково отключает всё, что Spring делает через прокси: @Transactional, @Cacheable, @Async, @Retryable, @PreAuthorize. В платёжном сервисе это выглядит так: поручения проводятся без транзакции, и при ошибке на пятом из них первые четыре остаются записанными.

Опыт с аспектом аудита сравнивает три способа вызвать метод process того же бина:

2) через внедрённый self:
   [аудит] process(п/п 17)
   проведено п/п 17
3) через AopContext.currentProxy():
   [аудит] process(п/п 17)
   проведено п/п 17
без exposeProxy:
3) через AopContext.currentProxy():

Листинг 9.64. Опыт 8.3: три способа вызвать метод того же бина.

Второй способ — внедрение бина в самого себя (self-injection): поле @Autowired @Lazy PaymentOrderService self получает прокси, и вызов self.process() проходит через него. @Lazy здесь нужен, чтобы бин не попал в цикл с самим собой: в поле кладётся ленивый прокси-заместитель, который найдёт готовый бин при первом вызове (раздел 6.1). Третий способ — статический метод AopContext.currentProxy(), который возвращает прокси текущего вызова. Работает он, только если включить @EnableAspectJAutoProxy(exposeProxy = true): тогда прокси на каждом вызове кладёт себя в ThreadLocal, причём делает это на всех бинах контекста, а без настройки метод бросает исключение из последней строки опыта. В другом потоке, например внутри @Async-метода, ThreadLocal пуст, и исключение будет то же.

Все три способа сохраняют сам вызов через this, а лучшие решения устроены иначе. Если методу нужна своя транзакция, значит, он образует отдельную операцию, и его выносят в отдельный бин, например PaymentOrderProcessor, который сервис внедряет и вызывает через прокси. Когда отдельная транзакция нужна на каждый элемент пачки, проще открыть её кодом через TransactionTemplate: orders.forEach(o -> tx.executeWithoutResult(s -> process(o))). Внедрение самого себя оставляют для старого кода, который пока нельзя перестроить, а AopContext.currentProxy() документация Spring прямо не рекомендует, потому что он намертво привязывает код к Spring AOP (Understanding AOP Proxies). Есть и способ, который устраняет проблему целиком: AspectJ вплетает код аспекта в байткод самого класса при компиляции или загрузке, и перехватывается даже вызов через this (раздел 9.6).11

❓ Спрашивают на интервью. Почему @Transactional не срабатывает при вызове метода из того же класса? Транзакцию открывает прокси, который перехватывает вызовы, пришедшие снаружи бина. Внутри целевого объекта this указывает на сам объект, поэтому вызов соседнего метода идёт мимо прокси. Правильное исправление — вынести метод в отдельный бин или открыть транзакцию через TransactionTemplate; внедрение себя через @Lazy и AopContext.currentProxy() с exposeProxy = true работают, но первое запутывает зависимости, а второе привязывает код к Spring AOP и не работает в другом потоке. AspectJ-вплетение перехватывает и вызовы через this. Тот же эффект у @Cacheable, @Async, @Retryable и @PreAuthorize.

8.4 Что прокси перехватить не может

Подкласс перехватывает только те методы, которые язык позволяет переопределить, и нарушение этого правила обычно не даёт никакой ошибки. Опыт вызывает через CGLIB-прокси сервиса лимитов методы разной видимости и записывает, какие из них дошли до перехватчика:

   dev.team.proxy.SpringProxyLab$DailyLimitService.limitFinal()] cannot get proxied via CGLIB, ...
вызваны remaining, prot, pkg, limitFinal, stat, priv; перехвачены: [remaining, prot, pkg]

Листинг 9.65. Опыт 8.4: какие методы перехватывает прокси CGLIB.

Методы public, protected и package-private из того же пакета прокси перехватил, а final, static и private прошли мимо. Хуже всего с final-методом: Spring только пишет предупреждение при создании прокси, и то лишь для публичного метода (о protected final в том же опыте он промолчал), а сам метод выполняется на экземпляре прокси, у которого поля не инициализированы, поэтому limitFinal() вернул null вместо лимита. Такая ошибка выглядит как загадочное пустое значение, а не как пропущенная транзакция. final-класс, наоборот, отвергается громко: контекст не поднимется с AopConfigException. У прокси JDK ограничение другое и проще: он перехватывает только методы интерфейса.

Видимость имеет значение и для самой аннотации @Transactional. Тот же сервис переводов с @Transactional на protected-методе refund и package-private методе hold собран на трёх версиях Spring:

До Spring 6.0 @Transactional действовал только на публичных методах, а с 6.0 прокси-подкласс применяет его к любому методу, который может переопределить. Поэтому правило «@Transactional только на public» в современной версии строже необходимого, и проверять стоит то, что прокси действительно не перехватит.         .should().notBePrivate()
        .andShould().notBeFinal()
        .andShould().notBeStatic()
        .because("прокси Spring не перехватывает private, final и static методы");

❓ Спрашивают на интервью. Какие методы прокси Spring не перехватывает? CGLIB-подкласс переопределяет только то, что разрешает язык, поэтому private, static и final методы идут мимо прокси без ошибки, а final-метод к тому же выполняется на пустом экземпляре прокси с непроинициализированными полями. final-класс отвергается при создании прокси. Прокси JDK перехватывает только методы интерфейса. protected и package-private методы с @Transactional работают с Spring 6.0, а в 5.3 аннотация на них молча игнорировалась. В Kotlin всё final по умолчанию, и нужен плагин kotlin-spring.

Проверка типа бина — getClass(), поиск аннотации на классе, сравнение классов — на прокси даёт не тот ответ, который ожидает автор кода. Опыт задаёт эти вопросы CGLIB-прокси сервиса лимитов, у которого класс и метод remaining помечены аннотацией @Audited:

Аннотации класса подкласс не наследует, если они не помечены @Inherited, а у переопределённого метода их нет совсем, поэтому код вида bean.getClass().isAnnotationPresent(Audited.class) на прокси всегда даёт false. 9. AOP: аспекты и порядок перехватчиков

Аспектно-ориентированное программирование (aspect-oriented programming, AOP) — это способ вынести сквозную функциональность, то есть код, который нужен во многих методах сразу, вроде аудита, замера времени, транзакций и кэша, в отдельный модуль, аспект, и подключать его к методам правилом, а не вызовом в каждом из них. Spring подключает аспекты через прокси из раздела 8, и на этом же механизме работают @Transactional, @Cacheable, @Async, @Retryable и @PreAuthorize. Поэтому, разобравшись в AOP один раз, можно объяснить поведение любой из этих аннотаций, а главное — порядок, в котором они срабатывают на одном методе. Раздел начинается с первого аспекта и словаря AOP, затем разбирает выражения, которые выбирают методы, виды советов и цепочку вызовов, а заканчивается порядком перехватчиков и сравнением прокси с вплетением AspectJ.

9.1 Первый аспект

Банк хочет записывать в журнал аудита каждый перевод: аргументы до проведения, результат после и ошибку, если перевод не прошёл. Вставлять эти строки в каждый метод сервиса переводов значит размножить один и тот же код и смешать его с бизнес-логикой. Аспект собирает его в одном классе:

@Aspect
public static class AuditAspect {
    @Pointcut("execution(* dev.team.aop.AdviceLab.TransferService.transfer(..))")
    void transfer() { }

    @Before("transfer()")
    public void before(JoinPoint jp) { System.out.println("   @Before " + jp.getSignature().getName()); }

    @AfterReturning(pointcut = "transfer()", returning = "receipt")
    public void afterReturning(Receipt receipt) { ... }

    @AfterThrowing(pointcut = "transfer()", throwing = "error")
    public void afterThrowing(Exception error) { System.out.println("   @AfterThrowing: " + error.getMessage()); }
}

@Configuration
@EnableAspectJAutoProxy
static class Cfg {
    @Bean TransferService transferService() { return new TransferService(); }
    @Bean AuditAspect auditAspect() { return new AuditAspect(); }
}

Листинг 9.70. Аспект аудита переводов.

На этом примере видны все понятия AOP, и их русские названия полезно знать, потому что в литературе встречаются оба варианта. Точка соединения (join point) — место в программе, где можно вставить код; в Spring это всегда выполнение метода бина. Срез (pointcut) — выражение, которое выбирает точки соединения; здесь execution(* ...TransferService.transfer(..)), а метод transfer() с аннотацией @Pointcut даёт срезу имя, чтобы не повторять выражение в каждом совете. Совет (advice) — код, который выполняется в выбранной точке: методы before, afterReturning, afterThrowing. Аспект (aspect) — класс, который объединяет срезы и советы, а в Spring внутри контейнера каждую пару «срез и совет» представляет объект Advisor. Наконец, связывание аспекта с кодом называют вплетением (weaving); Spring вплетает аспекты во время работы, создавая прокси.15

Из того, что аспекты работают через прокси, следует главное ограничение Spring AOP: перехватываются только вызовы методов бинов, которые контейнер создал сам. Аспект должен быть бином, иначе контейнер его не найдёт, и бином должен быть объект, чьи методы перехватывают. Последняя строка опыта вызывает тот же метод у объекта, созданного через new, и аспект его не замечает:

== объект, созданный через new, а не контейнером
      transfer 40817-001 -> 40817-003, 100 коп.

Листинг 9.71. Опыт 9.1: объект, созданный через new, аспект не перехватывает.

Перехватить вызов у такого объекта, обращение к полю или конструктор может только AspectJ с вплетением в байткод, о котором пойдёт речь в подразделе 9.6.14

9.2 Срезы

Срез решает, к каким методам применится совет, и ошибка в нём даёт либо аспект, который молча ничего не делает, либо аспект, который перехватывает лишнее. Опыт подключает к двум бинам, сервису платежей с интерфейсом Payments и репозиторию счетов с @Repository, по совету на каждый вид выражения и записывает, какие методы попали в каждый срез. Сервис платежей реализует интерфейс, поэтому в «голом» Spring получил прокси JDK:

@annotation(Audited)                         [pay]
@within(Repository)                          [save, lock]

Листинг 9.72. Опыт 9.2: какие методы попали в каждый вид среза.

execution выбирает методы по сигнатуре: модификатору, типу результата, классу, имени и параметрам, где * означает любое имя или тип, а (..) — любое число параметров. within выбирает все методы классов из заданного типа или пакета, @annotation — методы с аннотацией, @within — методы классов с аннотацией, bean — методы бина по имени, причём маска *Repository относится к имени бина, а не класса. args проверяет типы аргументов в момент вызова, поэтому под args(String, long) попали и pay, и lock, хотя это методы разных классов. Выражения объединяют операторами &&, || и !: последний срез выбирает методы двух классов, кроме помеченных @Audited.

Тонкость, которую любят на собеседованиях, видна в строках this и target. target проверяет тип целевого объекта, а this — тип самого прокси. Прокси JDK класс PaymentService не наследует, поэтому this(PaymentService) не выбрал ни одного вызова, а this(Payments) с интерфейсом сработал. У CGLIB-прокси, который в Spring Boot выбирается по умолчанию (раздел 8.2), оба выражения совпали бы, и разница проявится, только когда кто-то выключит proxyTargetClass.14

🎲 Неочевидно. Слишком широкий срез захватывает класс конфигурации. В первой версии опыта последний срез был записан как execution(* dev.team.aop.PointcutLab.*.*(..)), то есть «любой метод любого вложенного класса». Под него попал и класс конфигурации PointcutLab$Cfg: его CGLIB-подкласс (раздел 7) тоже стал целью аспекта, и вызов @Bean-метода, создающего сам аспект, потребовал экземпляр аспекта. Контекст не поднялся с BeanCurrentlyInCreationException: Error creating bean with name 'probe': Requested bean is currently in creation, и по сообщению причину не узнать: оно говорит о цикле, а не о срезе. Срезы по пакету в реальном проекте нужно ограничивать слоем, например within(com.bank.payments.service..*), а не всем приложением.14

Листинг 9.73. Опыт 9.3: советы пяти видов при успешном и неудачном переводе.

@Before выполняется до метода и видит аргументы. @AfterReturning выполняется только после успешного возврата и получает результат через параметр, имя которого указано в returning, а @AfterThrowing выполняется только при исключении и получает его через throwing. @After выполняется в любом случае, как блок finally, и не видит ни результата, ни исключения, поэтому годится для освобождения ресурсов и метрик. @Around оборачивает вызов целиком: он получает ProceedingJoinPoint, сам вызывает proceed() и сам решает, что вернуть. Внутри одного аспекта Spring с версии 5.2.7 упорядочивает советы по виду, и @After при этом срабатывает после @AfterReturning и @AfterThrowing, как и положено блоку finally (Advice Ordering).

Различие в возможностях советов важнее порядка. @AfterReturning в опыте изменил статус квитанции, и вызывающий получил изменённый объект, но второй совет того же вида, который попытался вернуть вместо квитанции новый объект, ничего не добился:

   @AfterReturning пытается вернуть другой объект
   ...
вызывающий получил Receipt(ПРОВЕДЁН (проверен аудитом))

Листинг 9.74. Опыт 9.3: @AfterReturning не подменяет результат.

Значение, которое возвращает метод @AfterReturning, Spring отбрасывает, поэтому такой совет может менять состояние результата, но не может подменить сам результат. Подменить результат, перехватить исключение и вернуть значение по умолчанию, не вызвать метод вовсе или вызвать его повторно может только @Around. Если @Around оборачивает метод void, proceed() возвращает null, и совет возвращает его же:

      notifyClient 40817-001
   @Around для void: proceed() вернул null

Листинг 9.75. Опыт 9.3: @Around для метода void.

Документация Spring советует выбирать самый слабый вид совета, которого хватает для задачи. Совет @Before не может забыть вызвать proceed() и тем самым тихо отключить метод, а @Around может, и такая ошибка выглядит как метод, который «иногда ничего не делает». Изменять результат даже там, где это возможно, стоит осторожно: разработчик, который не знает про аспект, будет долго искать, почему у квитанции другой статус и почему не срабатывает точка останова в методе.1514

9.5 Порядок перехватчиков

Если на одном методе стоят транзакция и кэш или транзакция и повторная попытка, от их взаимного порядка зависит, открывается ли транзакция при попадании в кэш и получает ли каждая попытка новую транзакцию. Правило порядка простое: перехватчик с меньшим значением @Order стоит снаружи, то есть первым входит и последним выходит. Опыт подключает к методу close два аспекта с @Order(1) и @Order(2), а сам метод помечен @Transactional:

close через два аспекта:
   Outer(@Order 1) вход
    Inner(@Order 2) вход
      begin
         close 40817-001
      commit
    Inner(@Order 2) выход
   Outer(@Order 1) выход

Листинг 9.79. Опыт 9.5: два аспекта с @Order вокруг транзакции.

Аспекты вкладываются друг в друга, а транзакция оказалась внутри обоих, потому что у транзакций по умолчанию самый низкий приоритет, Ordered.LOWEST_PRECEDENCE. Отсюда важное следствие для своих аспектов журнала и метрик: аспект с любым явным @Order стоит снаружи транзакции, и его код «после» выполняется уже после фиксации. Значит, такой аспект видит настоящий исход, в том числе ошибку фиксации на ограничении целостности, а аспект, поставленный внутрь транзакции, сообщает об «успехе» раньше, чем база согласилась его зафиксировать. Порядок аспектов без @Order между собой не определён, и полагаться на него нельзя.

Порядок встроенных перехватчиков опыт печатает прямо из прокси сервиса лимитов, у которого есть методы с @Transactional, @Cacheable и @Retryable:

10. События

Событие приложения (application event) — это объект, которым один бин сообщает о случившемся, не зная, кто на это отреагирует: публикатор вызывает publishEvent, а контейнер находит слушателей по типу события и вызывает их. Так сервис платёжных поручений может сообщить «поручение принято», а СМС плательщику, аудит и антифрод подпишутся на это сами, и сервису не придётся знать о каждом из них. Выглядит это как шина сообщений, но по умолчанию работает как вызов метода: в том же потоке и в той же транзакции. Из этого и вырастают все сюрпризы темы: упавший слушатель откатывает поручение, письмо уходит до фиксации, а запись в базу из слушателя после фиксации в одних случаях сохраняется, а в других молча пропадает. Раздел разбирает событие и слушатель, синхронность и ошибки, слушатели, привязанные к транзакции, асинхронные слушатели и границу между событиями Spring и брокером сообщений.

10.1 Событие и слушатель

Сервис принимает платёжное поручение, сохраняет его и сообщает об этом событием. Событие удобно описывать записью: с Spring 4.2 событию не нужно наследовать ApplicationEvent, контейнер сам обернёт любой объект в PayloadApplicationEvent.

public record OrderAccepted(long orderId, String payer, BigDecimal amount) {}

@Transactional
public void accept(long id, String payer, String amount) {
    jdbc.update("insert into payment_order(id, payer, amount) values (?, ?, ?)", id, payer, new BigDecimal(amount));
    events.publishEvent(new OrderAccepted(id, payer, new BigDecimal(amount)));
}

Все слушатели выполнились в потоке main, а publishEvent вернул управление только через 232 мс, когда отработал последний из них. Так ведёт себя мультикастер по умолчанию, SimpleApplicationEventMulticaster: он вызывает слушателей по очереди в потоке публикатора, и время публикации складывается из времени всех слушателей, которых не видно в коде сервиса. Порядок задаёт @Order. Слушатель может вернуть объект, и контейнер опубликует его следующим событием: так поручение на 750 000,00 породило FraudCheckRequested, а коллекцию контейнер публикует поэлементно. Цепочка выполняется синхронно и рекурсивно, поэтому две-три ступени читаются нормально, а длинная цепочка — это скрытый оркестратор, которому место в явном коде.16

Имя параметра (#event) работает, только если оно есть в байткоде, а начиная с Spring 6 имена берутся только из флага -parameters. Проекты на родительском POM spring-boot-starter-parent получают этот флаг из его настройки maven-compiler-plugin (<parameters>true</parameters>), а модуль, собранный без этого родителя, падает на первом же событии, и сообщение cannot be found on null ничего не говорит о причине. Хорошее событие устроено по правилам, которые пришли из предметно-ориентированного проектирования. Событие предметной области (domain event) — это факт, который важен для экспертов этой области, поэтому его имя стоит в прошедшем времени и выводится из команды, которая его вызвала: команда «принять поручение» порождает OrderAccepted. Событие неизменяемо, и конструктор заполняет все его поля сразу. А несёт оно то, что нужно подписчикам, чтобы не возвращаться к источнику с запросом: идентификаторы затронутых объектов, сумму, момент события. Поэтому в OrderAccepted лежат номер поручения, плательщик и сумма, а не ссылка на сущность JPA, которую слушатель стал бы перечитывать.18

10.2 Синхронность и ошибки

Из того, что слушатели выполняются в потоке и транзакции публикатора, следует главное свойство событий Spring: ошибка слушателя — это ошибка публикатора. Опыт принимает поручение плательщика, для которого слушатель СМС бросает исключение:

== 3. слушатель СМС бросает исключение
   сервис: поручение 3 сохранено, публикую событие, поток main
   слушатель audit, поток main
   слушатель notifyPayer: СМС плательщику сбой СМС (200 мс)
   вызывающий получил: СМС-шлюз недоступен
   поручение 3 в базе: 0

Листинг 9.89. Опыт 10.2: исключение слушателя откатывает публикатора.

Исключение прошло через publishEvent в метод accept, транзакция откатилась, и поручения в базе нет: сбой СМС-шлюза отменил платёж. Мультикастер прерывает обход на первом исключении, поэтому слушатели, стоящие дальше по порядку, не вызываются вовсе. В том числе не вызвался и слушатель отката AFTER_ROLLBACK из подраздела 10.3: он регистрируется в транзакции только тогда, когда до него доходит очередь, а до него очередь не дошла.

С обработчиком TaskUtils.LOG_AND_SUPPRESS_ERROR_HANDLER остальные слушатели отработали и поручение зафиксировалось, но СМС так и не ушла, а единственный след — строка журнала о «запланированной задаче», которой в приложении нет. Поэтому выбор обработчика ошибок — бизнес-решение. Если СМС не обязательна для платежа, ошибку стоит подавить, но своим обработчиком, который пишет понятное сообщение и увеличивает счётчик метрик, чтобы потеря была видна. Если без побочного действия операция не имеет смысла, ему не место в событии: его вызывают явно в коде сервиса.16

Синхронный слушатель, который правит в той же транзакции другой объект, нарушает ещё одно правило предметно-ориентированного проектирования: в одной транзакции меняется один агрегат, а остальные изменения, вызванные событием, выполняются в своих транзакциях и приходят к согласованности позже. Слушатель, который при приёме поручения уменьшает остаток лимита клиента в той же транзакции, связывает судьбу двух объектов, и сбой одного откатывает оба.18

10.3 Слушатель, привязанный к транзакции

Сервис принимает поручение и по событию отправляет его в Kafka. Обычный слушатель отправит сообщение внутри транзакции, и если она потом откатится, смежные системы узнают о поручении, которого нет в базе. @TransactionalEventListener откладывает вызов слушателя до заданной фазы транзакции публикатора, по умолчанию до успешной фиксации. В опыте с настоящим DataSourceTransactionManager на событие подписаны слушатели всех фаз:

@TransactionalEventListener(phase = TransactionPhase.BEFORE_COMMIT)
public void beforeCommit(OrderAccepted e) { ... }

@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
public void afterCommit(OrderAccepted e) { ... }

@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT, fallbackExecution = true)
public void fallback(OrderAccepted e) { ... }

Фаза AFTER_COMMIT не гарантирует доставку. Между фиксацией в базе и отправкой в брокер процесс может упасть, и поручение будет создано, а сообщение не уйдёт, о чём не узнает ни один механизм. Где доставка обязательна, нужен transactional outbox из подраздела 10.6.

10.4 Запись в базу после фиксации

Слушатель AFTER_COMMIT из подраздела 10.3 не только печатает строку, но и пишет запись аудита в базу через JdbcTemplate, без новой транзакции. Рядом в опыте стоит тот же слушатель с @Transactional(propagation = REQUIRES_NEW). После всех сценариев опыт печатает таблицу аудита:

== аудит в базе:
   1 AFTER_COMMIT
   1 REQUIRES_NEW
   2 AFTER_COMMIT
   2 REQUIRES_NEW

Листинг 9.93. Опыт 10.4: таблица аудита после всех сценариев.

Через JDBC запись сохранилась и без новой транзакции. Причина в том, как менеджер транзакций закрывает соединение. В фазе AFTER_COMMIT фиксация уже выполнена, но соединение ещё привязано к потоку, поэтому JdbcTemplate выполняет вставку на нём, внутри новой неявной транзакции. Затем менеджер возвращает соединению режим автоматической фиксации, а по спецификации JDBC вызов setAutoCommit(true) посреди транзакции фиксирует её. Сохранение получилось случайным: оно держится на очистке соединения, а не на явной транзакции.

С JPA тот же слушатель ведёт себя иначе. Опыт повторяет его на Hibernate 7.4.5 и JpaTransactionManager:

   AFTER_COMMIT: persist выполнен, id=1, транзакция активна: true
поручений в базе: 1
аудит в базе: REQUIRES_NEW

Листинг 9.94. Опыт 10.4: слушатель AFTER_COMMIT на JPA.

persist выдал записи идентификатор, TransactionSynchronizationManager отвечает, что транзакция активна, но в базу запись не попала: сущность легла в контекст персистентности, а сбрасывать его в базу больше некому, потому что фиксация уже прошла. Ошибки нет ни в журнале, ни в коде. Поэтому правило для обоих случаев одно: слушатель AFTER_COMMIT, который пишет в базу, помечают @Transactional(propagation = REQUIRES_NEW). Такая запись открывает вторую транзакцию и берёт второе соединение из пула, и она уже не атомарна с основной: поручение может сохраниться, а аудит упасть. Если запись обязана быть согласованной с поручением, её делают в том же методе сервиса или в фазе BEFORE_COMMIT.16

10.5 Асинхронные слушатели

Чтобы медленный слушатель не задерживал приём поручения, его помечают @Async, и он выполняется в пуле потоков. Вместе с потоком меняется многое, и опыт показывает что, подготовив в потоке публикатора идентификатор запроса в MDC (Mapped Diagnostic Context, поля, которые библиотека журналирования добавляет к каждой строке текущего потока) и «текущего клиента» в собственном ThreadLocal:

== @Async без переноса контекста
   @Async слушатель: поток events-1, MDC requestId=null, клиент=null
   publishEvent(1) вернул управление, поток main
   publishEvent(2) вернул управление, поток main
   @Async слушатель: поток events-1, MDC requestId=null, клиент=null
ERROR org.springframework.aop.interceptor.SimpleAsyncUncaughtExceptionHandler -- Unexpected exception occurred invoking async method: ...sendSms(...)
java.lang.IllegalStateException: СМС-шлюз недоступен

Листинг 9.95. Опыт 10.5: @Async-слушатель без переноса контекста.

Публикатор больше не ждёт слушателя, но и не узнаёт о его ошибке: исключение попало только в журнал через SimpleAsyncUncaughtExceptionHandler. Всё, что было привязано к потоку публикатора, в потоке пула пусто: MDC, свой ThreadLocal, а в настоящем приложении ещё и SecurityContextHolder с текущим пользователем, контекст трассировки и транзакция. Переносят контекст декоратором задач TaskDecorator, который пул применяет к каждой задаче:

static class ContextCopyingDecorator implements TaskDecorator {
    @Override public Runnable decorate(Runnable task) {
        Map<String, String> mdc = MDC.getCopyOfContextMap();
        String client = currentClient.get();
        return () -> {
            try { if (mdc != null) MDC.setContextMap(mdc); currentClient.set(client); task.run(); }
            finally { MDC.clear(); currentClient.remove(); }
        };
    }
}

Листинг 9.96. Декоратор задач, переносящий MDC и ThreadLocal.

== @Async с TaskDecorator
   @Async слушатель: поток events-1, MDC requestId=req-7f3a, клиент=dev.team

Листинг 9.97. Опыт 10.5: @Async-слушатель с TaskDecorator.

Декоратор снимает копию контекста в потоке публикатора, ставит её в потоке пула и обязательно очищает в finally. Очистка нужна не для красоты: пул повторно использует поток, и без неё следующая задача выполнится с чужим пользователем, а это уже утечка данных между клиентами. Для контекста безопасности есть готовый DelegatingSecurityContextAsyncTaskExecutor (глава 13), для трассировки — ContextPropagatingTaskDecorator из Micrometer.

Асинхронному слушателю нельзя возвращать следующее событие. Документация называет это неподдерживаемым, а на деле в Spring 7.0.9 такой слушатель не вызывается вовсе, и публикатор синхронно получает ошибку:

== @Async-слушатель возвращает событие
   публикатор получил IllegalArgumentException: Invalid return type for async method (only Future and void supported): class ReceiptRequested

Листинг 9.98. Опыт 10.5: @Async-слушатель, возвращающий событие.

Есть и второй способ сделать события асинхронными: задать пул самому мультикастеру через setTaskExecutor. Но тогда асинхронными становятся все события приложения, включая системные, поэтому помечать @Async нужные слушатели почти всегда лучше. Сочетание @TransactionalEventListener и @Async ставит слушателя в очередь после фиксации, и его ошибка никак не связана с транзакцией и не видна вызывающему, поэтому для критичной работы такой слушатель должен хотя бы записывать в журнал постановку и результат.16

10.6 События Spring и брокер сообщений

Брокер сообщений — отдельный сервер, например Kafka или RabbitMQ, который принимает сообщения от одних процессов, хранит их и доставляет другим. Событие Spring и сообщение брокера решают похожие задачи, но гарантии у них разные, и таблица ниже показывает, где кончается область каждого.

Событие Spring Kafka, RabbitMQ
Границы один процесс, один контекст между процессами и сервисами
Доставка в памяти, пока процесс жив хотя бы один раз, с хранением и повторами
Переживает перезапуск нет да
Наблюдаемость события видны только в стеке вызовов отставание потребителя, смещения, очередь недоставленных
Изменение контракта рефакторинг в одном модуле схемы, совместимость версий

Таблица 9.13. События Spring и брокер сообщений.

Поэтому событие Spring развязывает модули внутри одного приложения, а интегрировать через него сервисы нельзя. Как только реакция должна пережить перезапуск, попасть в другой сервис или повториться при сбое, это сообщение брокера. И между транзакцией базы и отправкой должен стоять transactional outbox: сообщение записывают в таблицу outbox той же локальной транзакцией, что и поручение, а отдельный компонент читает таблицу и отправляет сообщения в брокер.17 Та же идея известна в предметно-ориентированном проектировании как хранилище событий в базе модели с отдельным компонентом пересылки. Брокер при этом может доставить сообщение повторно, например если отправитель упал до подтверждения, поэтому у события должен быть уникальный идентификатор, по которому подписчик отбрасывает дубликаты, если его операция не идемпотентна.18 Подробно outbox разобран в главе 31 (31-integration-patterns-consistency.md), механика Kafka — в главе 29 (29-kafka-internals.md).

Промежуточный вариант для событий внутри одного приложения предлагает Spring Modulith: реестр публикаций сохраняет факт публикации в таблицу той же транзакцией, что и бизнес-изменение, и повторяет незавершённые публикации при старте, то есть даёт слушателю гарантию «хотя бы один раз» без брокера. ⚠️ Запуском этот механизм не проверялся.

❓ Спрашивают на интервью. Чем @TransactionalEventListener отличается от @EventListener, и где события теряются? Обычный слушатель выполняется сразу при публикации, в потоке и транзакции публикатора: его исключение откатывает публикатора и прерывает остальных слушателей, а отправка наружу может уйти до отката. @TransactionalEventListener откладывает вызов до фазы транзакции, по умолчанию AFTER_COMMIT, и без транзакции не вызывается вовсе, если не задан fallbackExecution. Запись в базу из AFTER_COMMIT через JPA молча теряется, а через JDBC сохраняется случайно, поэтому слушателю нужен REQUIRES_NEW. AFTER_COMMIT не гарантирует доставку, для неё нужен transactional outbox. Асинхронный слушатель теряет контекст потока и прячет исключения в журнал.

11. Настройки: Environment, профили, условия, SpEL и преобразование типов

Настройка приложения — это всё, что меняется от среды к среде без пересборки кода: процент комиссии, адрес шлюза, таймаут расчётов, режим отправки уведомлений. Spring собирает такие значения в объект окружения Environment, а дальше несколько механизмов решают, что из них следует: профили и условия включают и выключают целые конфигурации, язык выражений SpEL вычисляет значения в аннотациях, а преобразование типов превращает строку из файла в Duration или номер счёта. У каждого механизма есть поведение, которое в «голом» Spring и в Spring Boot различается, и опыты этого раздела показывают такие различия на настройках тарифа. Раздел разбирает источники свойств, профили, условия, SpEL, преобразование типов и ресурсы.

11.1 Источники свойств

Тариф сервиса расчётов лежит в файле fee.properties: комиссия 1,5 % и минимум 30 рублей. Для промышленной среды комиссия другая, 0,9 %, и её кладут в отдельный файл fee-prod.properties. В «голом» Spring оба файла подключают аннотацией @PropertySource, а имя второго можно составить из активного профиля:

@Configuration
@PropertySource("classpath:env/fee.properties")
@PropertySource("classpath:env/fee-${spring.profiles.active}.properties")
static class ProfileFiles { }

static class Tariff {
    @Value("${fee.percent}") String percent;
    @Value("${fee.min}") String min;
    @Value("${fee.max:не задан}") String max;
}

Окружение хранит свойства в упорядоченном списке источников PropertySource, и поиск идёт сверху вниз: выигрывает первый источник, в котором свойство нашлось. В «голом» Spring первыми стоят системные свойства JVM и переменные окружения, а под ними файлы из @PropertySource, причём позже объявленный файл встаёт выше раннего. Поэтому комиссия из fee-prod.properties перекрыла общий файл, минимум взялся из общего, а -Dfee.percent=2.0 перекрыл оба. Значение по умолчанию после двоеточия, ${fee.max:не задан}, сработало, потому что свойства нет ни в одном источнике. Если же профиль не задан, подстановка в имени файла падает на старте, так что такой приём годится, только когда профиль задан всегда.2122

Свойство без значения по умолчанию ведёт себя в «голом» Spring неожиданно:

== свойство fee.max без значения по умолчанию
   Strict.max = "${fee.max}"
== то же с PropertySourcesPlaceholderConfigurer
   PlaceholderResolutionException: Could not resolve placeholder 'fee.max' in value "${fee.max}"

Листинг 9.101. Опыт 11.1: свойство без значения по умолчанию.

Без бина PropertySourcesPlaceholderConfigurer контейнер разрешает заполнители нестрого, и в поле молча попадает сама строка ${fee.max}. Объявленный статическим @Bean-методом, этот бин делает разрешение строгим, и контекст падает на старте с понятным сообщением. Spring Boot регистрирует его автоматически, поэтому в Boot-приложении отсутствующее свойство без значения по умолчанию всегда даёт Could not resolve placeholder.1922

В Spring Boot источников больше полутора десятков, и порядок их старшинства надо знать хотя бы в главном. Выше всего стоят тестовые свойства, затем аргументы командной строки, SPRING_APPLICATION_JSON, системные свойства JVM, переменные окружения, а под ними файлы application-{профиль} и application, сначала внешние, потом упакованные в jar, и в самом низу @PropertySource и значения по умолчанию из SpringApplication.19 Опыт на Boot 4.1.1 проверяет главные следствия:

== spring.config.activate.on-profile, профиль не задан: app.fee-percent=1.5
== spring.config.activate.on-profile, профиль prod: app.fee-percent=0.9
== профиль prod и аргумент --app.fee-percent=2.5: app.fee-percent=2.5
--- с APP_FEE_PERCENT=3.1
== spring.config.activate.on-profile, профиль prod: app.fee-percent=3.1
== профиль prod и аргумент --app.fee-percent=2.5: app.fee-percent=2.5

Листинг 9.102. Опыт 11.1: порядок источников свойств в Spring Boot.

Переменная окружения APP_FEE_PERCENT перекрыла файл, хотя называется иначе: точки и дефисы в именах переменных операционная система не разрешает, и Boot сам сопоставляет APP_FEE_PERCENT со свойством app.fee-percent. Аргумент командной строки перекрыл и файл, и переменную, поэтому срочно поменять настройку в работающей среде можно при перезапуске, не пересобирая артефакт.20

Профильные настройки в Boot кладут либо в файл application-prod.yml, либо в отдельный документ того же YAML, отделённый строкой ---. Признак профиля у такого документа с Boot 2.4 записывается ключом spring.config.activate.on-profile, а старый ключ spring.profiles, который до сих пор встречается в книгах и статьях, Boot 4.1.1 отвергает:

InvalidConfigDataPropertyException: Property 'spring.profiles' imported from location 'class path resource [bootcfg/old-syntax.yml]' is invalid and should be replaced with 'spring.config.activate.on-profile' [origin: class path resource [bootcfg/old-syntax.yml] - 5:13]

Активный профиль лучше задавать переменной SPRING_PROFILES_ACTIVE или аргументом --spring.profiles.active при запуске: профиль, записанный в сам application.yml, становится профилем по умолчанию для всех сред, и смысл профилей пропадает.2022 Источник с высшим приоритетом можно добавить и программно, в ApplicationContextInitializer или EnvironmentPostProcessor, вызвав getPropertySources().addFirst(...): так подключают, например, секреты из хранилища Vault.

11.2 Профили и условия

Профиль — именованная среда, для которой включают свои бины и настройки, а @Profile — аннотация, которая регистрирует бин или конфигурацию, только если активен подходящий профиль. Загрузчик тестовых тарифов нужен везде, кроме промышленной среды и стенда приёмочных испытаний, и для этого есть две записи, которые выглядят одинаково, но работают по-разному. Опыт регистрирует конфигурации с обеими записями при разных наборах активных профилей:

активны        {"!prod", "!qa"}       "!prod & !qa"          {"dev", "qa"}
[]             создан                 создан                 —
[dev]          создан                 создан                 создан
[prod]         создан                 —                      —
[qa]           создан                 —                      создан
[prod, qa]     —                      —                      создан

Листинг 9.104. Опыт 11.2: две записи отрицания профилей.

Элементы массива в @Profile объединяются через «или»: конфигурация регистрируется, если подходит хотя бы один элемент. Поэтому {"!prod", "!qa"} означает «не активен prod или не активен qa», и загрузчик тестовых тарифов создался даже в промышленной среде, а пропал, только когда активны оба профиля сразу. Нужное условие записывается выражением профилей, которое Spring понимает с версии 5.1: "!prod & !qa". Ошибиться здесь легко, и ошибка встречается даже в учебной литературе.202322

@Profile — частный случай общего механизма условий. Аннотация @Conditional регистрирует бин, только если условие, реализованное интерфейсом Condition с методом matches(ConditionContext, AnnotatedTypeMetadata), вернёт true. Условие ниже включает отправку уведомлений в Kafka, только если в настройках выбран режим kafka и клиент Kafka действительно лежит в classpath:

static class OnKafkaMode implements Condition {
    @Override public boolean matches(ConditionContext ctx, AnnotatedTypeMetadata md) {
        boolean mode = "kafka".equals(ctx.getEnvironment().getProperty("app.notify.mode"));
        boolean client = ClassUtils.isPresent("org.apache.kafka.clients.producer.KafkaProducer", ctx.getClassLoader());
        return mode && client;
    }
}

Листинг 9.106. Опыт 11.2: условие OnKafkaMode.

Через ConditionContext условию доступны окружение, загрузчик классов и реестр описаний бинов. Вычисляется условие при разборе конфигурации, до создания бинов, поэтому трогать бины в matches нельзя: getBean создал бы бин раньше постпроцессоров (раздел 3.3). Опыт показывает и вторую особенность: при подходящих значениях контейнер вызвал matches трижды, на разных этапах разбора. Условие должно быть дешёвым и без побочных эффектов.22

На том же интерфейсе построены условия Spring Boot: @ConditionalOnClass, @ConditionalOnProperty, @ConditionalOnMissingBean. Последнее смотрит на реестр в момент вычисления, а не на итоговый, и в пользовательских конфигурациях от этого зависит результат:

   порядок [DefaultFeeConfig, CustomFeeConfig]: бины [defaultFee, corporateFee]
   порядок [CustomFeeConfig, DefaultFeeConfig]: бины [corporateFee]

Листинг 9.107. Опыт 11.2: @ConditionalOnMissingBean зависит от порядка конфигураций.

Когда конфигурация с запасным тарифом под @ConditionalOnMissingBean(FeeCalculator.class) разобрана первой, корпоративного тарифа в реестре ещё нет, и в контексте оказываются оба бина, а внедрение FeeCalculator упадёт на неоднозначности. Поэтому автоконфигурации Boot разбираются после всех пользовательских конфигураций (раздел 3.2, шаг 5), а в своих конфигурациях @ConditionalOnMissingBean лучше не использовать: запасную реализацию проще пометить @Fallback (раздел 5.1).22 Как Boot сообщает, какие условия сработали, разобрано в главе 10.

11.3 SpEL в @Value

У @Value два синтаксиса, которые часто путают. ${...} — заполнитель свойства из окружения, а #{...} — выражение на языке выражений Spring (Spring Expression Language, SpEL), который умеет вызывать методы, обращаться к бинам по имени и вычислять. Опыт собрал основные варианты:

@Value("${fee.percent}") BigDecimal percent;                                  // заполнитель свойства
@Value("#{T(java.time.Duration).ofSeconds(30)}") Duration timeout;          // статический метод
@Value("#{limits.daily() * 2}") BigDecimal weekly;                          // ссылка на бин
@Value("#{'${fee.min}' + ' руб.'}") String minText;                          // заполнитель внутри выражения
@Value("#{systemEnvironment['NO_SUCH_VAR'] ?: 'по умолчанию'}") String env;  // оператор Элвиса

Листинг 9.108. Варианты @Value: заполнитель и выражения SpEL.

percent=1.5, timeout=PT30S, weekly=1000000.00, minText=30 руб., env=по умолчанию

Листинг 9.109. Опыт 11.3: значения @Value.

Заполнитель разрешается первым, поэтому '${fee.min}' внутри выражения превратился в строку '30', а оператор Элвиса ?: подставил запасное значение вместо отсутствующей переменной окружения. @Value вычисляется один раз при создании бина, а выражения в @Cacheable(key = ...), @PreAuthorize и @EventListener(condition = ...) — на каждом вызове, поэтому там сложную логику лучше выносить в метод бина: @PreAuthorize("@accessChecker.canRead(#id, authentication)") и выполняется быстрее, и проверяется обычным модульным тестом.

Главный риск SpEL — выражение из недоверенного источника. Если оператор мониторинга задаёт фильтр платежей текстом, а сервис вычисляет его в стандартном контексте, оператор получает возможность выполнить на сервере любой код. Опыт вычисляет два фильтра в двух контекстах, и второй фильтр вместо опасного вызова делает безобидный, но такой же по устройству:

== фильтр оператора: amount > 600000
   StandardEvaluationContext: true
   SimpleEvaluationContext:   true
== фильтр оператора: T(java.lang.Runtime).getRuntime().availableProcessors() > 0
   StandardEvaluationContext: true
   SimpleEvaluationContext:   EL1005E: Type cannot be found 'java.lang.Runtime'

Листинг 9.110. Опыт 11.3: фильтр оператора в двух контекстах вычисления.

StandardEvaluationContext выполнил обращение к java.lang.Runtime, а значит, выполнил бы и exec(...). SimpleEvaluationContext не знает ссылок на типы, конструкторов и бинов, поэтому для выражений, пришедших извне, годится только он, а собирать выражение склейкой строк с пользовательским вводом нельзя ни в каком контексте. Риск не теоретический: в 2022 году уязвимость CVE-2022-22963 в Spring Cloud Function позволяла передать выражение SpEL в заголовке маршрутизации и выполнить код на сервере (spring.io/security/cve-2022-22963). Вышедший тогда же Spring4Shell, CVE-2022-22965, к SpEL отношения не имеет: это выполнение кода через привязку параметров запроса к объектам (spring.io/security/cve-2022-22965).22

11.4 Преобразование типов

Любое значение в файле настроек — строка, и превращать её в Duration, номер счёта или перечисление должен отдельный механизм, а не код каждого бина. В Spring таким механизмом служит ConversionService с конвертерами Converter<S, T>, а старые редакторы свойств PropertyEditor из JavaBeans остались для совместимости. Опыт читает настройки расчётов, settle.timeout=30s, settle.iso-timeout=PT45S, settle.account=4070 2810 9000 0000 0001 и settle.mode=real-time, в трёх окружениях:

== «голый» Spring без ConversionService
   IsoTimeout: IllegalStateException: Cannot convert value of type 'java.lang.String' to required type 'java.time.Duration': no matching editors or conversion strategy found
   SettlementAccount: IllegalStateException: Cannot convert value of type 'java.lang.String' to required type '...AccountNumber': no matching editors or conversion strategy found
   SettlementMode: IllegalStateException: Cannot convert value of type 'java.lang.String' to required type '...SettleMode': no matching editors or conversion strategy found
== «голый» Spring с бином conversionService
   IsoTimeout: PT45S -> PT45S
   ShortTimeout: DateTimeParseException: Text cannot be parsed to a Duration
   SettlementAccount: account=AccountNumber[digits=40702810900000000001]
   SettlementMode: IllegalArgumentException: No enum constant ...SettleMode.real-time
== Boot, @ConfigurationProperties, конвертер с @ConfigurationPropertiesBinding: SettleProps[timeout=PT30S, account=AccountNumber[digits=40702810900000000001], mode=REAL_TIME]

Листинг 9.111. Опыт 11.4: преобразование настроек расчётов в трёх окружениях.

Без ConversionService «голый» Spring не превращает строку ни в Duration, ни в запись с конструктором от строки. ConversionService контейнер берёт из бина с именем conversionService, и с DefaultFormattingConversionService и своим конвертером номера счёта прошли ISO-запись PT45S и номер счёта, а короткая запись 30s и значение real-time не прошли. Spring Boot добавляет к стандартным преобразованиям свои: Duration из 30s, размер данных из 10MB, перечисления без учёта регистра и дефисов, — и всё это работает при привязке @ConfigurationProperties (глава 10).22

У конвертера в Boot есть ловушка, на которую уходит полчаса отладки:

== Boot, @ConfigurationProperties, конвертер без @ConfigurationPropertiesBinding: IllegalArgumentException: номер счёта: '4070 2810 9000 0000 0001'

Листинг 9.112. Опыт 11.4: конвертер без @ConfigurationPropertiesBinding.

Конвертер, объявленный обычным бином, Boot применяет к @Value и к параметрам веб-запросов, но не к привязке @ConfigurationProperties. Без пометки @ConfigurationPropertiesBinding привязка его не видит и вызывает конструктор записи с сырой строкой, в которой остались пробелы, и проверка номера счёта падает.

11.5 Ресурсы

Resource — абстракция над тем, что можно прочитать: файлом в classpath, на диске или по URL, а ResourceLoader выбирает реализацию по префиксу пути: classpath:, file:, https:. Два свойства ресурсов важны на практике, и опыт показывает оба:

classpath:META-INF/spring.factories  — найдено: 1
classpath*:META-INF/spring.factories — найдено: 3
--- ресурс в каталоге классов
ресурс env/fee.properties: ClassPathResource, URL file:…
   getInputStream(): fee.percent=1.5
   getFile(): fee.properties
--- ресурс внутри jar
ресурс env/settle.properties: ClassPathResource, URL jar:…
   getInputStream(): settle.timeout=30s
   getFile(): FileNotFoundException: class path resource [env/settle.properties] cannot be resolved to absolute file path because it does not reside in the file system: jar:file:/…/tariffs.jar!/env/settle.properties

Листинг 9.113. Опыт 11.5: classpath и classpath*, ресурс в каталоге и в jar.

Префикс classpath: возвращает первый найденный ресурс, а classpath*: — все совпадения во всех jar classpath. На втором построена загрузка файлов META-INF/spring.factories и META-INF/spring/*.imports: каждая библиотека кладёт свой файл, и Boot собирает их все. Метод getFile() работает, только пока ресурс лежит отдельным файлом, то есть при запуске из IDE. В собранном jar ресурс становится записью архива, и getFile() падает, поэтому читать ресурсы нужно через getInputStream(): такой код работает и в IDE, и в jar, и в нативном образе.22

❓ Спрашивают на интервью. Что перекрывает что в настройках Spring Boot, и чем ${...} отличается от #{...}? Окружение — упорядоченный список источников, и выигрывает первый, где свойство нашлось: аргументы командной строки выше системных свойств, те выше переменных окружения, а переменные окружения выше файлов application-{профиль} и application. Переменная APP_FEE_PERCENT сопоставляется со свойством app.fee-percent. ${...} — заполнитель свойства, #{...} — выражение SpEL, которое может вызывать методы и обращаться к бинам; выражения из недоверенных источников вычисляют только в SimpleEvaluationContext. Профильный документ YAML с Boot 2.4 помечают spring.config.activate.on-profile, а @Profile({"!prod", "!qa"}) означает «или», и для «ни то, ни другое» нужно выражение "!prod & !qa".

12. Фоновая работа: @Async, @Scheduled, SmartLifecycle

Фоновая работа — всё, что сервис делает вне обработки входящего запроса: отправляет чек в ОФД после оплаты, раз в сутки сверяет остатки с банком, читает сообщения из очереди. Spring даёт для неё три механизма: @Async выполняет метод в пуле потоков, @Scheduled запускает метод по расписанию, а SmartLifecycle позволяет компоненту стартовать после подъёма контекста и остановиться в нужном порядке. Все три держатся на пулах потоков, и значения этих пулов по умолчанию для платёжного сервиса не годятся: исполнитель без ограничения очереди, планировщик на один поток, остановка, которая бросает задачи. Раздел начинается с того, как устроен пул потоков, затем разбирает @Async, @Scheduled и порядок остановки приложения.

12.1 Пул потоков

Сервис отправляет фискальные чеки в ОФД, и после распродажи за секунду приходит 50 оплат, а отправка одного чека занимает 100 мс. Пул для такой работы — объект ThreadPoolExecutor, и его поведение задают ядерный размер (core pool size, число потоков, которые пул держит всегда), максимальный размер, очередь и политика насыщения. Опыт отправляет 50 задач в пул с ядром 2 и максимумом 8 при разных очередях:

== core=2, max=8, 50 задач по 100 мс
очередь 500:                       потоков максимум 2, принято 50, отклонено 0, в очереди 48
очередь 10:                        потоков максимум 8, принято 18, отклонено 32, в очереди 10
SynchronousQueue (ёмкость 0):      потоков максимум 8, принято 8, отклонено 42, в очереди 0

Листинг 9.114. Опыт 12.1: пул с ядром 2 и максимумом 8 при разных очередях.

С очередью на 500 мест пул так и остался из двух потоков, а 48 задач ждали в очереди. Пул создаёт потоки сверх ядра только тогда, когда очередь заполнена, поэтому при большой очереди максимальный размер не достигается вовсе, и на этом попадаются почти все, кто впервые настраивает пул. С очередью на 10 мест пул вырос до восьми потоков, а 32 задачи отверг. SynchronousQueue задачи не хранит, а передаёт сразу свободному потоку, поэтому пул рос до максимума с первой задачи сверх ядра. Очередь сглаживает короткие всплески, но если задачи приходят быстрее, чем выполняются, неограниченная очередь растёт в памяти, и вместо понятного исключения отказ придёт исчерпанием памяти, когда задержка уже станет заметна всем.24

Когда очередь полна и все потоки заняты, пул применяет политику насыщения (saturation policy):

Политика Что делает Когда уместна
AbortPolicy (по умолчанию) бросает RejectedExecutionException вызывающему отказ нужно увидеть: ответить 503, положить задачу в очередь недоставленных
CallerRunsPolicy выполняет задачу в вызывающем потоке естественное торможение источника: поток запроса занят и не принимает новое
DiscardPolicy молча выбрасывает задачу только для необязательной работы, например прогрева кэша
DiscardOldestPolicy выбрасывает самую старую задачу из очереди метрики и журналы, где свежее ценнее старого

Таблица 9.14. Политики насыщения пула.

== CallerRunsPolicy при насыщении
   задачи выполнялись в потоках: [main, pool-4-thread-1]

Листинг 9.115. Опыт 12.1: CallerRunsPolicy.

При CallerRunsPolicy часть задач выполнил поток main, который их и отправлял, и пока он был занят, новых задач он не ставил. Так перегрузка доходит до источника, а не копится в памяти. Опасна эта политика там, где вызывающий поток — единственный, например поток цикла событий или потребитель очереди: он встанет на чужой работе.24

Фабрики Executors прячут эти параметры, и знать их значения стоит:

== фабрики Executors
   core=0, max=Integer.MAX_VALUE, keepAlive=60 с, очередь SynchronousQueue      ← newCachedThreadPool()
   core=4, max=4, keepAlive=0 с, очередь LinkedBlockingQueue                   ← newFixedThreadPool(4)
== core=0 и очередь на 100 мест
   одна задача выполнена: true, через 0 мс, потоков в пуле 1

Листинг 9.116. Опыт 12.1: параметры фабрик Executors и пул с нулевым ядром.

newCachedThreadPool растёт без ограничения, а newFixedThreadPool держит постоянное число потоков, но с неограниченной очередью. Последняя строка опыта опровергает старое предостережение о пуле с нулевым ядром и ограниченной очередью: будто задачи в нём не выполнятся, пока очередь не заполнится. Начиная с Java 6 пул в этом случае создаёт один поток, и задача выполнилась сразу.2426

Сколько потоков нужно пулу, зависит от того, во что он упирается. Для вычислений больше потоков, чем ядер процессора, ничего не даёт, а для задач, которые ждут внешнюю систему, потоков нужно больше, но добавлять их имеет смысл только до тех пор, пока узким местом не станет сама эта система: лишние потоки, которые ждут перегруженную базу или ОФД, только увеличивают задержку каждого запроса.25 Поэтому пул заводят на каждый класс работы отдельно, чтобы медленная отправка чеков не заняла потоки, нужные для обратных вызовов платёжного шлюза. Этот приём называют переборками (bulkhead), подробно он разобран в главе 35 (35-resilience.md).

12.2 @Async

@Async — аннотация, которая выполняет метод бина в пуле потоков: вызывающий получает управление сразу, а метод работает в другом потоке. Включает её @EnableAsync, а работает она через прокси (раздел 8), поэтому не срабатывает при вызове через this. Всё поведение @Async определяется исполнителем, который за ней стоит, и опыт отправляет 20 чеков в трёх окружениях:

== «голый» Spring, своего исполнителя нет
   20 вызовов sendReceipt выполнены в потоках (20): [SimpleAsyncTaskExecutor-1, SimpleAsyncTaskExecutor-2, SimpleAsyncTaskExecutor-3] …
== Spring Boot 4.1.1
   applicationTaskExecutor: ThreadPoolTaskExecutor, core=8, max=Integer.MAX_VALUE, очередь Integer.MAX_VALUE
   20 вызовов sendReceipt выполнены в потоках (8): [task-1, task-2, task-3] …
== Spring Boot 4.1.1 --spring.threads.virtual.enabled=true
   applicationTaskExecutor: SimpleAsyncTaskExecutor
   20 вызовов sendReceipt выполнены в потоках (20): [VirtualThread task-1, VirtualThread task-2, VirtualThread task-3] …

Листинг 9.117. Опыт 12.2: исполнитель @Async в трёх окружениях.

«Голый» Spring без своего исполнителя отдаёт @Async в SimpleAsyncTaskExecutor, который пула не держит и создаёт новый поток на каждый вызов, и под нагрузкой это кончается ошибкой unable to create native thread. Spring Boot создаёт ThreadPoolTaskExecutor из восьми потоков, но с неограниченными максимумом и очередью, то есть с той самой бесконечной очередью из подраздела 12.1, а с виртуальными потоками — исполнитель без ограничения параллелизма вовсе, где каждый вызов получает свой виртуальный поток. Ни один из вариантов не защищает внешнюю систему от перегрузки, поэтому для платёжного сервиса пул объявляют явно, на каждый класс работы:

@Bean("fiscalExecutor")
ThreadPoolTaskExecutor fiscalExecutor() {
    var ex = new ThreadPoolTaskExecutor();
    ex.setCorePoolSize(8);
    ex.setMaxPoolSize(8);
    ex.setQueueCapacity(200);                                         // конечная очередь
    ex.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());
    ex.setThreadNamePrefix("fiscal-");
    ex.setTaskDecorator(new ContextCopyingDecorator());               // MDC и пользователь, раздел 10.5
    ex.setWaitForTasksToCompleteOnShutdown(true);
    ex.setAwaitTerminationSeconds(20);
    return ex;
}

@Async("fiscalExecutor")
public CompletableFuture<String> fiscalize(long orderId) { ... }

Листинг 9.118. Отдельный пул для отправки чеков.

Как только в контексте появляется свой бин-исполнитель, Boot свой не создаёт: в опыте с бином fiscalExecutor бина applicationTaskExecutor не оказалось, и @Async без имени ушёл в fiscal-1. Когда пулов станет два, @Async без имени будет искать бин по умолчанию и может достаться не тому пулу, поэтому имя в @Async("fiscalExecutor") лучше указывать всегда.26

Судьба исключения зависит от того, что возвращает метод:

ERROR ... SimpleAsyncUncaughtExceptionHandler -- Unexpected exception occurred invoking async method: public void ...ReceiptService.failVoid(long)
   CompletableFuture получил ошибку: ОФД недоступен, чек 2

Листинг 9.119. Опыт 12.2: исключение в методе void и в CompletableFuture.

Исключение из метода void вызывающему передать некуда, и Spring отдаёт его обработчику AsyncUncaughtExceptionHandler, который по умолчанию только пишет строку в журнал. Метод, который возвращает CompletableFuture, передаёт исключение через результат, и вызывающий может его обработать. Поэтому @Async void годится только для необязательной работы, а всё, что важно, возвращает CompletableFuture<T>, и для void-методов задают свой обработчик через AsyncConfigurer.getAsyncUncaughtExceptionHandler(), который не только пишет в журнал, но и увеличивает счётчик метрик. Метод, который возвращает другой тип, например String, в Spring 7 не выполнится вовсе: вызывающий получит IllegalArgumentException: Invalid return type for async method (раздел 10.5).

Ещё два ограничения следуют из того, что @Async работает через прокси:

   @PostConstruct @Async warmUp: поток main

Листинг 9.120. Опыт 12.2: @Async на @PostConstruct.

@Async на методе @PostConstruct не работает: контейнер вызывает этот метод у целевого объекта до того, как прокси создан, и прогрев выполнился синхронно в потоке main. А @Async вместе с @Transactional на одном методе открывает транзакцию уже в потоке пула, поэтому асинхронная работа не видит незафиксированных изменений вызывающего, а откат вызывающего её не отменяет.26

12.3 @Scheduled

@Scheduled — аннотация, которая запускает метод бина по расписанию: с фиксированной задержкой после окончания предыдущего запуска (fixedDelay), с фиксированной частотой от начала предыдущего (fixedRate) или по выражению cron. Включает её @EnableScheduling. Опыт в Spring Boot 4.1.1 держит в одном бине четыре задачи: сверку, которая занимает 1,5 с, проверку связи со шлюзом раз в 100 мс, выгрузку, которая первые три раза падает, и задачу на 500 мс с fixedRate = 200:

== по умолчанию
   потоки: [ping:scheduling-1, reconciliation:scheduling-1]
   ping за 3 с: 1 раз; failingExport вызван 1 раз (первые 3 упали)
   fixedRate=200 мс при задаче 500 мс: запусков 3, интервалы между началами, мс: [2036, 500]
== --spring.task.scheduling.pool.size=4
   ping за 3 с: 28 раз; failingExport вызван 15 раз (первые 3 упали)

@Scheduled выполняется в каждом экземпляре приложения: три пода в Kubernetes дают три ночные сверки и тройные письма клиентам. ShedLock при занятой блокировке пропускает запуск, а не откладывает его, и считает, что часы на узлах синхронизированы, поэтому срок блокировки lockAtMostFor ставят с большим запасом относительно самого долгого запуска (ShedLock). Сравнение планировщиков разобрано в главе 24 (24-batch-and-scheduling.md).

12.4 Порядок запуска и остановки

SmartLifecycle — интерфейс для компонентов, которые должны запуститься после подъёма контекста и остановиться в заданном порядке: потребителей очередей, пулов соединений с внешними системами. Метод getPhase() задаёт фазу, и опыт запускает и останавливает три компонента с разными фазами:

== фазы SmartLifecycle
   start пул соединений со шлюзом (фаза -100)
   start прогрев справочников (фаза 0)
   start потребитель Kafka (фаза 2147483547)
   закрываю контекст
   stop  потребитель Kafka (фаза 2147483547)
   stop  прогрев справочников (фаза 0)
   stop  пул соединений со шлюзом (фаза -100)

Листинг 9.124. Опыт 12.4: запуск и остановка по фазам SmartLifecycle.

Компоненты стартуют от меньшей фазы к большей, а останавливаются в обратном порядке. Отсюда правило выбора фаз: потребитель сообщений получает большую фазу, чтобы стартовать последним, когда всё, что ему нужно, уже готово, и останавливаться первым, переставая брать новую работу, а инфраструктура вроде пула соединений — маленькую, чтобы работать до конца. Встроенный веб-сервер в Boot 4.1.1 останавливается в фазе Integer.MAX_VALUE - 2048, а корректную остановку, при которой сервер перестаёт принимать запросы и дожидается текущих, выполняет компонент в фазе Integer.MAX_VALUE - 1024, то есть раньше. Ожидание каждой фазы ограничено свойством spring.lifecycle.timeout-per-shutdown-phase, по умолчанию 30 с.26 Для работы «после полного старта, с симметричной остановкой» SmartLifecycle подходит лучше, чем @PostConstruct, который срабатывает до создания прокси, и лучше, чем ApplicationRunner, у которого нет остановки.

Пулы @Async и @Scheduled останавливаются вместе с контекстом, и что станет с задачами, зависит от одной настройки. Опыт ставит четыре проводки по 500 мс в пул из двух потоков и сразу закрывает пул:

== пул без ожидания задач, 4 проводки по 500 мс, 2 потока
   shutdown() вернул управление через 0 мс
   проводка 2 прервана
   проводка 1 прервана
== waitForTasksToCompleteOnShutdown(true), awaitTermination 5 с
   проводка 1 завершена
   проводка 2 завершена
   проводка 4 завершена
   проводка 3 завершена
   shutdown() вернул управление через 920 мс

Листинг 9.125. Опыт 12.4: остановка пула с ожиданием задач и без.

Без ожидания пул прервал две выполнявшиеся проводки, а две проводки из очереди не выполнились вовсе: это внезапная остановка, при которой пул отменяет выполняемые задачи и выбрасывает незапущенные. С setWaitForTasksToCompleteOnShutdown(true) пул остановился плавно: дождался и выполняемых задач, и очереди. В Boot для автоматических пулов то же включают свойства spring.task.execution.shutdown.await-termination и spring.task.scheduling.shutdown.await-termination с периодом ожидания.2426

Настраивать ожидание нужно согласованно с тем, сколько времени процессу даёт среда. Kubernetes между сигналами SIGTERM и SIGKILL ждёт terminationGracePeriodSeconds, по умолчанию 30 с, и если приложение собирается ждать задачи 60 секунд, на 30-й его убьют, и задачи потеряются так же, как без ожидания. Ожидание распространяется на всю очередь, поэтому очередь на 500 задач по 2 секунды не опустеет за разумное время, и такую очередь надёжнее хранить вне памяти. А долгая задача, например сверка на 40 минут, корректной остановки не дождётся ни при каких настройках: её делают возобновляемой, с контрольной точкой в базе, и это уже область Spring Batch (глава 24).

❓ Спрашивают на интервью. Какой пул получает @Async по умолчанию и почему его нельзя оставлять в платёжном сервисе? «Голый» Spring отдаёт @Async в SimpleAsyncTaskExecutor, который создаёт поток на каждый вызов. Spring Boot создаёт ThreadPoolTaskExecutor из восьми потоков с неограниченной очередью, поэтому максимальный размер не достигается, а очередь растёт в памяти; с виртуальными потоками параллелизм не ограничен вовсе. Пул создаёт потоки сверх ядра, только когда очередь заполнена. Поэтому пул объявляют явно, на каждый класс работы, с конечной очередью, осознанной политикой насыщения и ожиданием задач при остановке. Исключение из @Async void попадает только в журнал, а @Scheduled по умолчанию делит один поток на все задачи.

13. Расширение контейнера

Точки расширения контейнера позволяют коду подключать конфигурации по условию, регистрировать бины, для которых нет класса в исходниках, управлять сканированием и вмешиваться в контекст до его запуска. На них построены Spring Boot, Spring Data, клиенты OpenFeign и почти любая библиотека, которая подключает свою конфигурацию одной зависимостью в сборке. Знать их нужно не только авторам библиотек: тот, кто разбирается, откуда в контексте взялся бин и почему его нет в исходниках, ищет ответ именно здесь. Раздел разбирает три уровня @Import, сканирование и его стоимость и самую раннюю точку расширения, ApplicationContextInitializer.

13.1 @Import, ImportSelector, ImportBeanDefinitionRegistrar

Платёжная библиотека умеет проводить расчёты двумя способами: мгновенно через СБП или пакетом раз в час, и приложение выбирает способ одной аннотацией, @EnableSettlement(mode = "sbp"). Так устроены все аннотации @Enable… в Spring: сама аннотация помечена @Import, а @Import указывает на класс, который решает, какую конфигурацию подключить:

@Target(ElementType.TYPE) @Retention(RetentionPolicy.RUNTIME)
@Import(SettlementModeSelector.class)
@interface EnableSettlement { String mode() default "batch"; }

static class SettlementModeSelector implements ImportSelector {
    @Override public String[] selectImports(AnnotationMetadata md) {
        String mode = md.getAnnotations().get(EnableSettlement.class).getString("mode");
        return new String[] {(mode.equals("sbp") ? SbpSettlementConfig.class : BatchSettlementConfig.class).getName()};
    }
}

Листинг 9.126. Аннотация @EnableSettlement и ImportSelector.

== @EnableSettlement(mode = "sbp")
   SettlementModeSelector: mode=sbp, аннотация стоит на SbpApp
   Settlement: СБП, мгновенные переводы
== @EnableSettlement без атрибута
   SettlementModeSelector: mode=batch, аннотация стоит на DefaultApp
   Settlement: пакетный клиринг раз в час

Листинг 9.127. Опыт 13.1: выбор способа расчётов через @EnableSettlement.

@Import бывает трёх уровней гибкости. Простейший, @Import(SomeConfig.class), подключает конкретный класс конфигурации. ImportSelector возвращает имена классов, вычисленные при старте, и через AnnotationMetadata видит атрибуты аннотации на классе, где стоит @Import. Его подвид DeferredImportSelector откладывает выбор, пока не разобраны все остальные конфигурации: так подключается автоконфигурация Spring Boot, и поэтому её условия вроде @ConditionalOnMissingBean видят бины приложения (раздел 11.2). Все три уровня обрабатывает постпроцессор конфигурационных классов на пятом шаге refresh() (раздел 3.2).

Третий уровень, ImportBeanDefinitionRegistrar, регистрирует описания бинов напрямую, без классов конфигурации. Он нужен, когда число бинов заранее неизвестно, например когда бины порождаются из интерфейсов. Клиенты к банку-эквайреру и антифроду в опыте описаны только интерфейсами с аннотацией @BankClient, а регистратор находит такие интерфейсы и для каждого регистрирует фабрику:

static class BankClientsRegistrar implements ImportBeanDefinitionRegistrar {
    @Override public void registerBeanDefinitions(AnnotationMetadata md, BeanDefinitionRegistry registry) {
        var scanner = new ClassPathScanningCandidateComponentProvider(false) {
            @Override protected boolean isCandidateComponent(AnnotatedBeanDefinition bd) { return bd.getMetadata().isInterface(); }
        };
        scanner.addIncludeFilter(new AnnotationTypeFilter(BankClient.class));
        for (var candidate : scanner.findCandidateComponents("dev.team.ext")) {
            var bd = BeanDefinitionBuilder.genericBeanDefinition(BankClientFactoryBean.class)
                    .addPropertyValue("clientInterface", candidate.getBeanClassName()).getBeanDefinition();
            registry.registerBeanDefinition(..., bd);
        }
    }
}

Листинг 9.128. Регистратор клиентов банков из интерфейсов.

   регистратор: AcquirerAClient -> BankClientFactoryBean
   регистратор: AntifraudClient -> BankClientFactoryBean
   POST https://acquirer-a.example/api/authorize [2200700000000001, 150000]
   POST https://fraud.example/api/score [2200700000000001, 150000]
   getBean("AcquirerAClient"): $Proxy14, getBean("&AcquirerAClient"): BankClientFactoryBean

Листинг 9.129. Опыт 13.1: клиенты, зарегистрированные регистратором.

Фабрика BankClientFactoryBean реализует интерфейс FactoryBean<T>: контейнер отдаёт не её саму, а объект, который она производит, — прокси JDK, который превращает вызов метода интерфейса в запрос к банку (раздел 8.1). Саму фабрику можно получить по имени с префиксом &. Ровно так работают репозитории Spring Data, клиенты OpenFeign и интерфейсы Mapper в MyBatis: интерфейс превращается в фабрику, а фабрика — в прокси, который этот интерфейс реализует. У FactoryBean есть ловушка: чтобы узнать тип продукта, контейнер вызывает getObjectType() рано, ещё при поиске бинов по типу, поэтому фабрика может создаться раньше постпроцессоров и не пройти через часть из них, как любой бин, созданный раньше своего шага (раздел 3.3).27

Классы автоконфигурации Spring Boot перечисляет в файле META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports, по строке на класс, и с Boot 3 только там. Старый файл META-INF/spring.factories при этом не исчез, как иногда утверждают: в jar spring-boot 4.1.1 через него по-прежнему регистрируются ApplicationContextInitializer, ApplicationListener, EnvironmentPostProcessor (с Boot 4 он лежит в пакете org.springframework.boot), анализаторы ошибок старта и загрузчики конфигурации.2827

13.2 Сканирование и его стоимость

@ComponentScan находит в указанных пакетах классы с @Component и его производными и регистрирует их бинами. Это самый привычный способ наполнить контекст и самый дорогой, потому что сканер читает каждый файл класса в пакете, хотя и без загрузки класса в JVM (раздел 2.2). Опыт сканирует пакеты разного размера с фильтрами по умолчанию:

== сканирование с фильтрами по умолчанию
   dev.team.mortgage      кандидатов    4,    1 мс
   dev.team               кандидатов   85,    9 мс
   org.springframework    кандидатов   29,   52 мс

Листинг 9.130. Опыт 13.2: время сканирования пакетов разного размера.

В пакете org.springframework около 3500 файлов классов, и сканер прочитал их все ради 29 кандидатов. Так выглядит сканирование от корня, которое случается, если главный класс приложения лежит слишком высоко в дереве пакетов: в сканирование попадают классы библиотек, а вместе с ними и чужие компоненты. Spring Boot сканирует пакет главного класса и всё ниже, поэтому главный класс держат в корне пакетов самого приложения. Отбор кандидатов уточняют фильтрами includeFilters и excludeFilters пяти типов: по аннотации, по типу, по выражению AspectJ, по регулярному выражению и собственный TypeFilter.27

При сканировании контейнер сразу вычисляет и условия @Conditional на найденных классах: в выводе опыта две лишние строки OnKafkaMode появились потому, что под сканирование dev.team попал класс из раздела 11.2, и его условие вычислилось ещё до регистрации. Это ещё одна причина держать условия дешёвыми.

Сканирование можно заменить индексом кандидатов: обработчик аннотаций spring-context-indexer при компиляции записывает список компонентов в файл META-INF/spring.components, и контекст читает его вместо обхода классов. В Spring 7.0.9 класс CandidateComponentsIndexLoader, который читает индекс, на месте и устаревшим не помечен, но из справочника раздел об индексе убран. Индекс работает, только если проиндексированы все участники сканирования, а частичный индекс хуже никакого: компоненты из неиндексированного jar просто не найдутся, и для такого случая есть свойство spring.index.ignore=true. Ту же задачу радикальнее решает обработка AOT, которая фиксирует весь набор бинов при сборке (раздел 15), а библиотеки и приложения, где важен старт, вообще отказываются от сканирования и перечисляют конфигурации через @Import.

13.3 ApplicationContextInitializer

ApplicationContextInitializer — самая ранняя точка, в которой приложение может изменить контекст: инициализатор вызывается после создания контекста, но до refresh(), когда ни одна конфигурация ещё не разобрана. Опыт добавляет через него вычисляемое свойство с идентификатором экземпляра сервиса расчётов:

static class InstanceIdInitializer implements ApplicationContextInitializer<ConfigurableApplicationContext> {
    @Override public void initialize(ConfigurableApplicationContext ctx) {
        ctx.getEnvironment().getPropertySources().addFirst(new MapPropertySource("computed", Map.of("app.instance-id", "settle-7")));
    }
}

Листинг 9.131. Инициализатор с вычисляемым свойством.

   после refresh: app.instance-id=settle-7, описаний бинов 6

Листинг 9.132. Опыт 13.3: инициализатор до refresh().

В момент вызова контекст ещё неактивен, а в реестре лежат только шесть служебных описаний, поэтому инициализатор подходит для правки окружения и для регистрации того, что должно появиться раньше всех конфигураций, например постпроцессора, который обязан увидеть все бины. В Spring Boot инициализатор подключают тремя способами: методом SpringApplication.addInitializers(...), свойством context.initializer.classes или строкой в META-INF/spring.factories под ключом org.springframework.context.ApplicationContextInitializer. Для правки одного только окружения в Boot удобнее EnvironmentPostProcessor, который срабатывает ещё раньше, до создания контекста (раздел 3.4).27

❓ Спрашивают на интервью. Как работают аннотации @Enable… и откуда в контексте берутся бины Spring Data, у которых нет классов? Аннотация @Enable… помечена @Import, который ведёт к конфигурации, к ImportSelector, выбирающему конфигурации по атрибутам аннотации, или к ImportBeanDefinitionRegistrar, регистрирующему описания бинов напрямую. Spring Data и OpenFeign используют регистратор: он находит интерфейсы и для каждого регистрирует FactoryBean, который производит прокси, реализующий интерфейс; саму фабрику можно получить по имени с &. Автоконфигурацию Boot подключает DeferredImportSelector, который срабатывает после конфигураций приложения и читает список классов из AutoConfiguration.imports.

14. Тестирование контекста

Интеграционный тест в Spring — тест, который поднимает контекст приложения с настоящими бинами, и обычно именно старт контекста, а не сами проверки, определяет, сколько идёт весь прогон тестов. Подсистема тестирования Spring (TestContext Framework) умеет повторно использовать поднятый контекст в следующих тестовых классах, но только если их конфигурация совпадает целиком, и одна лишняя аннотация в тесте незаметно добавляет ещё один старт. Раздел разбирает, сколько контекста поднимать, как устроен кэш контекстов и что его ломает, @DirtiesContext и аннотации подмены бинов @MockitoBean, @MockitoSpyBean и @TestBean.

14.1 Сколько контекста поднимать

Сколько контекста поднимает тест, определяет его уровень: чем больше бинов участвует в проверке, тем дороже старт и тем медленнее весь прогон. Отправная точка у всех одна: каждый проект, созданный в Spring Initializr, начинается с теста, в котором нет ни одной проверки:

@SpringBootTest
class SettleAppTests {
    @Test void contextLoads() { }
}

Листинг 9.133. Тест contextLoads из Spring Initializr.

Пустой метод заставляет @SpringBootTest поднять контекст целиком, и если очередное изменение помешает контексту подняться, тест упадёт. Это самая дешёвая страховка от ошибок конфигурации, но поднимать полный контекст для каждой проверки — самая частая причина медленных тестов. @SpringBootTest нужен для интеграционных тестов, которые проверяют совместную работу многих компонентов, а для всего, что можно проверить ниже, есть более лёгкие уровни: условие в сервисе проверяется модульным тестом без Spring, веб-слой и его защита — срезом @WebMvcTest, репозитории — срезом @DataJpaTest.2931

Сам @SpringBootTest поднимает контекст в одном из четырёх режимов веб-среды, webEnvironment. Режим MOCK, по умолчанию, поднимает веб-контекст с имитацией веб-среды без настоящего сервера, а если веба в classpath нет, — обычный контекст. RANDOM_PORT запускает встроенный сервер на свободном порту, DEFINED_PORT — на порту из настроек, а NONE поднимает контекст без веб-среды вовсе. Мок на уровне Mockito, @Mock, нужен модульному тесту без контекста, а подмена бина внутри контекста делается аннотацией подмены, и путать эти два случая в одном тесте нельзя.3231

14.2 Кэш контекстов

Кэш контекстов (context cache) хранит поднятые контексты, и подсистема тестирования отдаёт готовый контекст следующему тестовому классу, если у того совпадает ключ кэша. Ключ складывается из всего, что определяет конфигурацию: классов и файлов конфигурации, инициализаторов, активных профилей, тестовых свойств, подмен бинов, настроек тестовых срезов Boot и иерархии контекстов. Опыт на Spring Boot 4.1.1 прогоняет десять тестовых классов сервиса расчётов, которые различаются ровно одним признаком, и каждый новый контекст печатает свой номер:

--- A_PlainTest                      @SpringBootTest
>>> поднят тестовый контекст №1
--- B_PlainAgainTest                 @SpringBootTest
--- C_ProfileTest                    @ActiveProfiles("test")
>>> поднят тестовый контекст №2
--- D_MockGatewayTest                @MockitoBean PaymentGateway
>>> поднят тестовый контекст №3
--- E_MockGatewayAgainTest           @MockitoBean PaymentGateway
--- F_MockNotifierTest               @MockitoBean Notifier
>>> поднят тестовый контекст №4
--- G_PropertyTest                   @SpringBootTest(properties = "settle.batch-size=500")
>>> поднят тестовый контекст №5
--- H_DirtiesTest                    @DirtiesContext(AFTER_EACH_TEST_METHOD), три метода
>>> поднят тестовый контекст №6
>>> поднят тестовый контекст №7
--- I_PlainAfterDirtiesTest          @SpringBootTest
>>> поднят тестовый контекст №8
--- J_TestBeanTest                   @TestBean PaymentGateway
>>> поднят тестовый контекст №9

Листинг 9.134. Опыт 14.2: какие тестовые классы поднимают новый контекст.

Класс B получил контекст класса A, потому что конфигурации совпали. Всё остальное дало новые контексты: профиль, свойство, подмена PaymentGateway, подмена Notifier. Классы D и E с одинаковым @MockitoBean PaymentGateway поделили один контекст, а мок при этом пересоздаётся для каждого теста, поэтому состояние заглушки между классами не переходит. Из десяти классов получилось девять контекстов, и если контекст стартует 6 секунд, вариации стоят почти минуту на каждом прогоне. Статистику кэша, строку cache statistics, печатает журнал org.springframework.test.context.cache на уровне DEBUG, и по ней видно, сколько контекстов поднял прогон.30

Отсюда стратегия: свести число вариаций к минимуму. Интеграционные тесты наследуют общий базовый класс или общую мета-аннотацию поверх @SpringBootTest с одинаковым набором профилей, свойств и подмен, а контейнеры Testcontainers с базой и брокером поднимаются один раз на прогон и подключаются через @ServiceConnection (глава 43, 43-testing.md). На одном проекте такое выравнивание конфигураций дорогих интеграционных тестов сократило сборку с 25 до 9 минут.31

14.3 @DirtiesContext

@DirtiesContext помечает контекст как испорченный тестом: подсистема тестирования закрывает его, удаляет из кэша и пересоздаёт для следующего теста. Класс H из опыта помечен @DirtiesContext(classMode = AFTER_EACH_TEST_METHOD) и содержит три метода, а по конфигурации совпадает с A. Первый метод получил из кэша контекст №1 и испортил его, второй и третий подняли контексты №6 и №7, а класс I, которому хватило бы общего контекста, поднял №8. Одна аннотация на классе из трёх методов дала три лишних старта и выбросила из кэша контекст, нужный всем остальным тестам.

Поэтому @DirtiesContext ставят, только когда тест действительно меняет то, что нельзя вернуть, например перерегистрирует бины. Состояние базы надёжнее откатывать транзакцией теста или очищать скриптом @Sql, состояние заглушек сбрасывает сама подсистема подмен, а кэши приложения очищают явно через CacheManager.30

14.4 Подмена бинов в тесте

@MockitoBean подменяет бин в тестовом контексте моком Mockito, а @MockitoSpyBean оборачивает настоящий бин шпионом, который вызывает настоящие методы и записывает вызовы. Обе аннотации живут в самом Spring Framework, начиная с версии 6.2, в пакете org.springframework.test.context.bean.override.mockito, и пришли на смену аннотациям Spring Boot @MockBean и @SpyBean. Те в Boot 3.4 объявили устаревшими, а в Boot 4 удалили: в jar spring-boot-test версий 4.0.2 и 4.1.1 этих классов нет, и при обновлении старые тесты перестают компилироваться.30

@SpringBootTest
class D_MockGatewayTest {
    @MockitoBean PaymentGateway gateway;
    @Autowired SettlementService service;

    @Test void declined() {
        given(gateway.charge("40702810900000000004", 1_000)).willReturn("DECLINED");
        assertThat(service.settle("40702810900000000004", 1_000)).startsWith("DECLINED");
    }
}

Листинг 9.135. Тест с @MockitoBean вместо платёжного шлюза.

Подменить бин можно и настоящей тестовой реализацией вместо мока. @TestBean берёт её из статического метода тестового класса с тем же именем, что и поле, и это часто честнее заглушки, потому что такая реализация ведёт себя как банк, а не как набор заранее заданных ответов:

@TestBean PaymentGateway gateway;
static PaymentGateway gateway() { return (account, kopecks) -> "STUB-BANK " + account; }

Листинг 9.136. Подмена бина через @TestBean.

Любая подмена входит в ключ кэша, поэтому класс J с @TestBean поднял свой контекст №9: подмены выгодно собирать в общий базовый класс, а не объявлять по-разному в каждом тесте.30

❓ Спрашивают на интервью. Почему интеграционные тесты Spring Boot идут долго и как это исправить? Подсистема тестирования кэширует контексты, но повторно использует контекст, только если конфигурация тестового класса совпадает целиком: профили, свойства, набор @MockitoBean и @TestBean, срезы. Каждое отличие поднимает новый контекст, а @DirtiesContext выбрасывает контекст из кэша и заставляет поднимать его заново. Исправляют это общим базовым классом с одинаковой конфигурацией, контейнерами, поднятыми один раз на прогон, отказом от @DirtiesContext в пользу отката транзакции и проверками на более низких уровнях: модульными тестами и срезами @WebMvcTest, @DataJpaTest. Число поднятых контекстов показывает журнал org.springframework.test.context.cache на уровне DEBUG.

15. Spring AOT и нативный образ

Обработка AOT (ahead-of-time, «заранее») переносит часть работы контейнера со старта приложения на этап сборки: разбор конфигураций, вычисление условий и подготовку описаний бинов. Нужна она прежде всего для нативного образа GraalVM (native image) — исполняемого файла, в который приложение скомпилировано в машинный код заранее и который стартует без JVM за доли секунды. В таком образе рефлексия, динамические прокси и загрузка классов во время работы недоступны без предварительного описания, поэтому контейнер не может разбирать аннотации так, как описано в разделах 2–7. Обработку AOT можно включить и на обычной JVM, где она просто ускоряет старт, но в обоих случаях часть решений, которые раньше принимались при запуске, принимается при сборке и потом уже не меняется. Раздел показывает, что генерирует обработка AOT, что она фиксирует, как описывают подсказки для GraalVM и когда всё это нужно.

15.1 Что генерирует обработка AOT

Опыт запускает обработку AOT для сервиса расчётов из раздела 14 командой mvn spring-boot:process-aot. Плагин поднимает контекст в «сухом» режиме: разбирает конфигурации, вычисляет условия, но не создаёт бинов, — и пишет в target/spring-aot три класса и файл подсказок:

SettleApp__ApplicationContextInitializer.java
SettleApp__BeanDefinitions.java
SettleApp__BeanFactoryRegistrations.java
META-INF/native-image/dev.team/context-tests/reachability-metadata.json

Листинг 9.137. Опыт 15.1: что пишет process-aot в target/spring-aot.

Для каждого бина генерируется метод, который возвращает готовое описание бина вместе с кодом создания экземпляра. Для сервиса расчётов он выглядит так:

private static BeanInstanceSupplier<SettleApp.SettlementService> getSetTlementServiceInstanceSupplier() {
  return BeanInstanceSupplier.<SettleApp.SettlementService>forConstructor(SettleApp.PaymentGateway.class, SettleApp.Notifier.class)
          .withGenerator((registeredBean, args) -> new SettleApp.SettlementService(args.get(0), args.get(1)));
}

public static BeanDefinition getSetTlementServiceBeanDefinition() {
  RootBeanDefinition beanDefinition = new RootBeanDefinition(SettleApp.SettlementService.class);
  ...
}

Листинг 9.138. Сгенерированный код создания бина SettlementService.

Рефлексии в этом коде нет: конструктор вызывается напрямую, а зависимости приходят по типам параметров. Сгенерированный ApplicationContextInitializer регистрирует все описания в порядке, зафиксированном при сборке (в опыте их 51), и при запуске с -Dspring.aot.enabled=true контекст пропускает разбор конфигурационных классов, сканирование и условия, то есть весь пятый шаг refresh() (раздел 3.2). Файл reachability-metadata.json — подсказки для GraalVM: какие классы нужны рефлексии, какие ресурсы включить в образ, какие прокси создать. Без них GraalVM включает в образ только то, до чего дотягивается статический анализ кода, и всё, к чему обращаются рефлексией, из образа пропадает.33

15.2 Что фиксируется при сборке

Бины, которые зависят от профиля или от свойства, контейнер выбирает при разборе конфигурации, а при обработке AOT разбор происходит на сборке. В сервис расчётов добавлены канал СБП под @Profile("sbp") и антифрод под @ConditionalOnProperty("settle.fraud.enabled"), обработка AOT выполнена без профиля и без свойства, а приложение запущено с обоими, --spring.profiles.active=sbp --settle.fraud.enabled=true --settle.batch-size=500:

--- обычная JVM
>>> режим AOT: false, профили: [sbp], SbpChannel: true, FraudFilter: true, settle.batch-size=500
--- -Dspring.aot.enabled=true
>>> режим AOT: true, профили: [sbp], SbpChannel: false, FraudFilter: false, settle.batch-size=500

Листинг 9.139. Опыт 15.2: профиль и условие в режиме AOT.

На обычной JVM оба бина создались. В режиме AOT профиль sbp в окружении активен и свойство задано, но ни канала СБП, ни антифрода в контексте нет: решение о них принято при сборке, где не было ни профиля, ни свойства. Обычное свойство settle.batch-size при этом работает, потому что значения свойств читаются при запуске, а фиксируется только набор бинов. Отсюда главное следствие для эксплуатации: схема «один артефакт на все среды, профиль выбирается флагом запуска» для бинов, зависящих от профиля, при AOT не работает, и профиль нужно задавать при сборке.33

Документация Spring перечисляет и другие ограничения той же природы: classpath фиксируется при сборке, набор бинов во время работы не меняется, а бины, зарегистрированные через функцию-поставщик (context.registerBean(Foo.class, Foo::new)) или через registerSingleton, обработка AOT преобразовать не может. Тип бина при этом берётся из сигнатуры @Bean-метода, потому что экземпляров при сборке нет, поэтому метод должен возвращать возможно более точный тип: если он объявлен как возвращающий интерфейс, контейнер не узнает, что бин реализует, например, SmartLifecycle (Ahead of Time Optimizations).

15.3 Подсказки для нативного образа

Если код обращается к чему-то рефлексией или читает ресурс по имени, которое не видно анализу, нужна своя подсказка. Сервис отчётов по расчётам читает шаблон из ресурсов, а библиотека шаблонов обращается к строке отчёта рефлексией, поэтому сервис объявляет подсказки через RuntimeHintsRegistrar и подключает их аннотацией @ImportRuntimeHints:

@Service
@ImportRuntimeHints(ReportService.Hints.class)
public class ReportService {
    public record ReportRow(String account, long kopecks) {}

    static class Hints implements RuntimeHintsRegistrar {
        @Override public void registerHints(RuntimeHints hints, ClassLoader cl) {
            hints.resources().registerPattern("templates/settlement-report.ftl");
            hints.reflection().registerType(ReportRow.class, MemberCategory.INVOKE_PUBLIC_METHODS);
        }
    }
}

Листинг 9.140. Свои подсказки через RuntimeHintsRegistrar.

После обработки AOT подсказки оказались в reachability-metadata.json: {"glob": "templates/settlement-report.ftl"} в разделе ресурсов и {"type": "dev.team.settle.ReportService$ReportRow", "allPublicMethods": true} в разделе рефлексии. Проверять подсказки удобнее модульным тестом, потому что сборка нативного образа занимает минуты:

assertThat(RuntimeHintsPredicates.reflection().onType(ReportService.ReportRow.class)
        .withMemberCategory(MemberCategory.INVOKE_PUBLIC_METHODS)).accepts(hints);
assertThat(RuntimeHintsPredicates.resource().forResource("templates/settlement-report.ftl")).accepts(hints);
assertThat(RuntimeHintsPredicates.resource().forResource("templates/other.ftl")).rejects(hints);

Листинг 9.141. Проверка подсказок через RuntimeHintsPredicates.

Этот механизм появился в Spring Framework 6 и заменил экспериментальный проект Spring Native, в котором подсказки описывали аннотациями @NativeHints и @TypedHint; в книгах и статьях до 2023 года встречаются именно они.3433

15.4 Когда это нужно

Нативный образ стартует за доли секунды и занимает меньше памяти, поэтому он выигрывает там, где экземпляр поднимается часто и живёт недолго: в бессерверных функциях, при масштабировании от нуля, в утилитах командной строки. Взамен сборка занимает минуты и требует много памяти, отладка и профилирование ограничены, агенты JVM и вплетение AspectJ при загрузке (раздел 9.6) не работают, а прогретая JVM с оптимизирующим компилятором обычно обгоняет образ по пиковой производительности. Для долгоживущего сервиса с постоянной нагрузкой, который перезапускается раз в неделю, время старта почти ничего не решает.34

Обработка AOT на обычной JVM даёт часть выигрыша без смены среды выполнения. Сервис расчётов из опыта, по шесть запусков в каждом режиме, стартовал так:

jvm: 0.701 0.675 0.719 0.682 0.694 0.694
aot: 0.588 0.585 0.582 0.595 0.583 0.595

Листинг 9.142. Опыт 15.4: время старта на JVM и с AOT, шесть запусков.

Приложение маленькое, и выигрыш около 0,1 с, примерно седьмая часть старта. В большом приложении доля разбора конфигураций больше, но и время, которое уходит на подключение к базе, миграции и прогрев пулов, AOT не сокращает, поэтому выигрыш нужно мерить на своём приложении: чужие цифры к нему не переносятся. Отдельный механизм JDK, кэш AOT (JEP 483), сохраняет загруженные и связанные классы между запусками, и в описании JEP приведён замер на Spring PetClinic: старт сократился с 4,486 до 2,604 с (JEP 483). Если нативный образ всё же выбран, его сборку и тесты (native:compile, native:test) включают в CI с первого дня: поломки, характерные для образа, вроде недостающей подсказки для Jackson или прокси Hibernate, дешевле ловить по одной, чем разом в конце проекта. Сборка образа в контейнере разобрана в главе 46 (46-docker-jvm.md).33

❓ Спрашивают на интервью. Что меняет Spring AOT и почему профиль в нативном образе нельзя выбрать флагом запуска? Обработка AOT при сборке разбирает конфигурации и условия и генерирует код регистрации бинов без рефлексии, а также подсказки для GraalVM. При запуске контекст пропускает разбор конфигураций, поэтому бины, зависящие от @Profile и от @ConditionalOnProperty, остаются такими, какими были при сборке: профиль, активированный при запуске, их уже не добавит, а значения свойств при этом читаются как обычно. Классы, к которым обращаются рефлексией, и ресурсы описывают через RuntimeHintsRegistrar и @ImportRuntimeHints и проверяют тестом с RuntimeHintsPredicates. Нативный образ выгоден для коротко живущих экземпляров, а для долгоживущего сервиса чаще хватает AOT на обычной JVM.

16. Разобранные инциденты

Разобранный инцидент — история сбоя, пройденная от первого симптома до мер, которые не дают ему повториться. Шесть историй ниже построены на механизмах этой главы, и каждая опирается на опыт, который воспроизводит ту же поломку на стенде, поэтому выводы в них проверены запуском. Разобраны они по одной схеме: симптом, как искали, причина, исправление и как не допустить. Читать их полезно ради хода поиска: почти везде ключом оказываются два вопроса — есть ли на бине прокси и в каком порядке стоят его перехватчики.

16.1 Аудит лимитов пропал после нового постпроцессора

Симптом. После релиза перестали писаться записи аудита при смене лимитов клиента. Метод LimitService.updateLimit() помечен @Transactional и собственной аннотацией аудита, лимиты меняются, ошибок в журнале нет.

Как искали. Аннотации на месте, метод публичный, вызов приходит снаружи. Тогда проверили сам бин: AopUtils.isAopProxy(limitService) вернул false, а getClass() показал класс без суффикса $$SpringCGLIB$$, то есть прокси не было вовсе. Строки not eligible for getting processed by all BeanPostProcessors в журнале старта не нашлось, и это сбило поиск на день.

Причина. В релиз добавили постпроцессор фабрики, объявленный статическим @Bean-методом с параметром LimitService: из сервиса он брал лимиты по умолчанию для новых тарифов. Чтобы вызвать постпроцессор фабрики на пятом шаге refresh(), контейнер создал сервис раньше, чем зарегистрировал постпроцессоры бинов, и LimitService остался без прокси. В этом случае контейнер ничего не пишет в журнал: предупреждение not eligible появляется, только когда бин понадобился постпроцессору бинов, а не постпроцессору фабрики (раздел 3.3).

Исправление. Параметр у @Bean-метода убрали, нужное значение постпроцессор читает из Environment через EnvironmentAware.

Как не допустить. Методы @Bean, которые возвращают постпроцессоры, объявляют static и без параметров, и это пункт проверки на ревью. Дымовой тест после старта проверяет AopUtils.isAopProxy у бинов с транзакциями и аудитом: он ловит этот класс ошибок независимо от того, что пишет журнал.

16.2 Реестр платежей сохранился частично

Симптом. В отчётности стали попадаться реестры платежей, в которых часть строк есть, а части нет, хотя импорт реестра должен быть атомарным.

Как искали. На одном экземпляре включили журнал org.springframework.transaction.interceptor на уровне TRACE. Для метода импорта реестра строки Getting transaction for [...] и Completing transaction for [...] были, а для метода сохранения строк, который раньше открывал собственную транзакцию, их не было (раздел 18). История изменений показала, что метод две недели назад перенесли в тот же класс, что и импорт, «чтобы не плодить классы».

Причина. После переноса метод стал вызываться через this, мимо прокси, и транзакционный перехватчик о нём больше не знал (раздел 8.3). Импорт ловил исключение проверки строки и продолжал работу, а пометить транзакцию к откату стало некому, поэтому записанные до ошибки строки зафиксировались.

Исправление. Метод вернули в отдельный бин, а перехват исключения в импорте убрали: реестр, в котором хотя бы одна строка не прошла проверку, откатывается целиком.

Как не допустить. Интеграционный тест на каждую транзакционную границу проверяет откат, а не успешный сценарий: исключение в середине — и в базе ничего. При переносе метода между классами на ревью проверяют, не стал ли вызов внутренним.

16.3 Пул соединений кончился на кэшируемом справочнике

Симптом. Под пиковой нагрузкой сервис тарифов начал отвечать с задержкой в секунды, а в журнале появились ошибки ожидания соединения из пула, хотя справочник тарифов почти целиком лежит в кэше.

Как искали. Метрики показали, что почти все запросы попадают в кэш, но число активных соединений с базой при этом растёт вместе с нагрузкой. Распечатка советов прокси сервиса тарифов показала, что CacheInterceptor стоит после TransactionInterceptor.

Причина. У транзакций и кэша по умолчанию одинаковое значение порядка, Ordered.LOWEST_PRECEDENCE, и кэш оказался внутри транзакции: каждое попадание в кэш всё равно открывало и фиксировало транзакцию, а с ней брало соединение из пула (раздел 9.5).

Исправление. Кэш вынесли наружу явным порядком, @EnableCaching(order = 100), и попадание в кэш перестало трогать базу.

Как не допустить. Порядок механизмов с одинаковым значением по умолчанию задают явно, а тест проверяет его как контракт: индекс CacheInterceptor в ((Advised) bean).getAdvisors() меньше индекса TransactionInterceptor.

16.4 Аудит после фиксации пропал при переходе на Spring Data

Симптом. После того как модуль платёжных поручений перевели с JdbcTemplate на репозитории Spring Data JPA, из таблицы аудита исчезли записи о принятых поручениях. Слушатель аудита не менялся, ошибок нет, save() возвращает сущность с идентификатором.

Как искали. Слушатель помечен @TransactionalEventListener с фазой по умолчанию AFTER_COMMIT и пишет без новой транзакции. Тот же слушатель на JdbcTemplate в старой версии записи сохранял.

Причина. В фазе AFTER_COMMIT фиксация уже выполнена, но соединение ещё привязано к потоку. Через JDBC вставка выполнялась на этом соединении, и её случайно фиксировал вызов setAutoCommit(true) при очистке соединения. Через JPA сущность ложилась в контекст персистентности, а сбрасывать его в базу было уже некому, и запись молча пропадала (раздел 10.4).

Исправление. Слушатель пометили @Transactional(propagation = REQUIRES_NEW).

Как не допустить. Любой слушатель AFTER_COMMIT, который пишет в базу, помечают REQUIRES_NEW независимо от способа доступа к данным, а тест проверяет запись в таблице, а не возвращённый объект.

16.5 Шлюз ночью счёл сервис мёртвым

Симптом. Каждую ночь около 02:00 платёжный шлюз на 40 минут выводил сервис расчётов из балансировки: проверка связи, которую сервис отправляет раз в 30 секунд, переставала приходить. В журнале сервиса ошибок не было.

Как искали. Провал по времени совпадал с ночной сверкой. Снимок потоков jcmd <pid> Thread.print показал единственный поток планировщика scheduling-1 внутри метода сверки.

Причина. Планировщик Spring Boot по умолчанию держит один поток, и все задачи @Scheduled делят его: пока шла 40-минутная сверка, проверка связи не выполнилась ни разу (раздел 12.3).

Исправление. Сверку вынесли в отдельный планировщик атрибутом @Scheduled(scheduler = "heavyScheduler"), а пул основного планировщика увеличили свойством spring.task.scheduling.pool.size.

Как не допустить. Долгие задачи никогда не делят планировщик с короткими, а метрика времени с последнего запуска каждой периодической задачи с оповещением на превышение показывает такой провал за минуты, а не по жалобе смежной команды.

16.6 После обновления Spring приложение перестало падать, а транзакции пропали

Симптом. Сервисы платежей и лимитов ссылались друг на друга через сеттеры, и вдобавок оба получали прокси от самописного постпроцессора замеров. На Spring 6.1 приложение с такой конфигурацией не стартовало, и команда держала обходное решение: @Lazy на одной из точек внедрения. После обновления до Spring 6.2 приложение стартовало без ошибок, обходное решение убрали, а через неделю обнаружилось, что при вызовах из сервиса платежей у сервиса лимитов не работают транзакции.

Как искали. Отладчик показал, что поле limits в целевом объекте сервиса платежей указывает на объект Limits без прокси, тогда как в контексте лежит прокси.

Причина. Постпроцессор замеров подменял бины прокси только в postProcessAfterInitialization и не умел отдавать прокси по ранней ссылке. До 6.2 контейнер отказывался запускаться, обнаружив, что сосед получил «сырой» объект. С 6.2 он пересоздаёт бины в другом порядке, но когда прокси после инициализации получают оба бина цикла, одному из них всё равно достаётся ранняя ссылка без прокси, и контейнер поднимается молча (раздел 6.2).

Исправление. Цикл разорвали: общую часть, сумму операций за день, вынесли в отдельный журнал операций, от которого зависят оба сервиса. Постпроцессор замеров переписали на SmartInstantiationAwareBeanPostProcessor с getEarlyBeanReference.

Как не допустить. Циклы запрещены, spring.main.allow-circular-references не встречается ни в одном профиле, а архитектурный тест проверяет отсутствие циклов между пакетами. Обновление минорной версии Spring проверяют тестами, а не только тем, что приложение стартует.

17. Ошибки и антипаттерны

Здесь собраны типовые ошибки, которые повторяются из проекта в проект. Каждая ниже записана по одной схеме — симптом, причина, лечение — со ссылкой на раздел, где механизм проверен запуском, поэтому искать по списку удобно от симптома: нашли похожее поведение в своём сервисе, прочитали причину и проверили её.

  1. Аннотация не работает при вызове из того же класса. Симптом: нет транзакции, кэша или асинхронности, ошибок нет. Причина: вызов через this идёт мимо прокси (8.3). Лечение: вынести метод в отдельный бин или открыть транзакцию через TransactionTemplate.

  2. final, private или static метод с @Transactional. Симптом: аннотация молча не работает, а final-метод вдобавок возвращает null вместо значения поля. Причина: подкласс CGLIB не может переопределить такой метод, а final-метод выполняется на экземпляре прокси с пустыми полями (8.4). Лечение: убрать модификатор, в Kotlin подключить kotlin-spring, проверять правилом ArchUnit.

  3. Бин нельзя внедрить по классу реализации. Симптом: BeanNotOfRequiredTypeException: ... but was actually of type 'jdk.proxy2.$Proxy42'. Причина: в приложении выключен spring.aop.proxy-target-class, и бин с интерфейсом получил прокси JDK (8.2). Лечение: внедрять по интерфейсу или вернуть значение по умолчанию.

  4. Бин потерял прокси, а в журнале тишина. Симптом: транзакции и аудит перестали работать на одном бине. Причина: бин создан раньше постпроцессоров, например как зависимость @Bean-метода постпроцессора фабрики с параметром; предупреждение not eligible в этом случае не пишется (3.3). Лечение: static-методы постпроцессоров без параметров, дымовой тест на AopUtils.isAopProxy.

  5. Прототип внутри синглтона создаётся один раз. Симптом: «новый» объект хранит состояние предыдущего запроса. Причина: зависимость внедряется один раз, при создании синглтона (5.3). Лечение: ObjectProvider<T>.getObject(); @Lookup не работает у бинов из @Bean-методов, а прокси области видимости (scoped proxy) создаёт новый объект на каждый вызов метода.

  6. Ресурс прототипа не освобождается. Симптом: растёт число открытых соединений или файлов. Причина: у прототипов контейнер не вызывает @PreDestroy (5.4). Лечение: прототип не владеет ресурсом, ресурс живёт в синглтоне-пуле.

  7. Два пула соединений после перехода на proxyBeanMethods = false. Причина: прямой вызов @Bean-метода в облегчённом режиме создаёт новый объект (7.1). Лечение: передавать зависимости параметрами @Bean-методов.

  8. Конфигурация не поднимается в Kotlin. Симптом: @Configuration class ... may not be final. Причина: полный режим требует открытого класса (7.2). Лечение: плагин kotlin-spring или proxyBeanMethods = false.

  9. Кэш открывает транзакцию на каждое попадание. Причина: у кэша и транзакций одинаковый порядок по умолчанию, и кэш оказался внутри (9.5). Лечение: @EnableCaching(order = 100).

  10. Слишком широкий срез роняет контекст. Симптом: BeanCurrentlyInCreationException на бине аспекта. Причина: срез захватил класс конфигурации, и аспект понадобился при создании самого себя (9.2). Лечение: ограничивать срезы слоем приложения.

  11. Исключение слушателя откатывает поручение. Причина: синхронный слушатель выполняется в транзакции публикатора и прерывает остальных слушателей (10.2). Лечение: побочные действия, без которых операция имеет смысл, выносить в @TransactionalEventListener или в асинхронный слушатель.

  12. Условие слушателя падает с cannot be found on null. Причина: модуль собран без -parameters, и имя параметра неизвестно; #root.event для записи — обёртка PayloadApplicationEvent (10.1). Лечение: обращаться к событию через #a0.

  13. Запись в базу из AFTER_COMMIT пропала. Причина: через JPA изменение остаётся в контексте персистентности, который никто не сбросит (10.4). Лечение: REQUIRES_NEW на слушателе.

  14. В поле попала строка ${...}. Причина: «голый» Spring без PropertySourcesPlaceholderConfigurer разрешает заполнители нестрого (11.1). Лечение: объявить этот бин статическим @Bean-методом; в Boot он есть всегда.

  15. Конфигурация есть во всех средах, хотя должна быть только вне промышленной. Причина: @Profile({"!prod", "!qa"}) — это «или» (11.2). Лечение: @Profile("!prod & !qa").

  16. Свой конвертер не работает в @ConfigurationProperties. Причина: привязка видит только конвертеры с @ConfigurationPropertiesBinding (11.4). Лечение: добавить аннотацию.

  17. getFile() падает в собранном jar. Причина: ресурс внутри jar — запись архива, а не файл (11.5). Лечение: читать через getInputStream().

  18. Пул не растёт до максимума, а очередь растёт. Причина: потоки сверх ядра появляются, только когда очередь заполнена; у пула Boot очередь не ограничена (12.1, 12.2). Лечение: свой пул с конечной очередью и политикой насыщения.

  19. Исключение из @Async void никто не видит. Причина: оно уходит в SimpleAsyncUncaughtExceptionHandler, который пишет в журнал фреймворка (12.2). Лечение: CompletableFuture<T> для важной работы и свой обработчик со счётчиком метрик.

  20. Короткие периодические задачи не выполняются, пока идёт долгая. Причина: планировщик Boot по умолчанию однопоточный (12.3). Лечение: отдельный планировщик для долгих задач.

  21. Задача по cron в 02:30 пропустила день или выполнилась дважды. Причина: переход на летнее время в поясе с переводом часов (12.3). Лечение: не ставить задачи на часы перевода, задавать zone.

  22. Тесты поднимают десятки контекстов. Причина: каждое отличие профилей, свойств и подмен бинов даёт новый ключ кэша, а @DirtiesContext выбрасывает контекст (14.2, 14.3). Лечение: общий базовый класс, отказ от @DirtiesContext.

  23. После обновления до Boot 4 не компилируются тесты. Причина: @MockBean и @SpyBean удалены (14.4). Лечение: @MockitoBean, @MockitoSpyBean из Spring Framework.

  24. В нативном образе или в режиме AOT пропал бин под профилем. Причина: бины под @Profile и @ConditionalOnProperty выбираются при сборке (15.2). Лечение: задавать профиль при сборке образа.

18. Диагностика

Диагностика контейнера — способы заглянуть в живой контекст: есть ли на бине прокси, какие перехватчики в каком порядке на нём стоят, открываются ли транзакции, почему бин создан или не создан. Большинство проблем этой главы видны снаружи лишь косвенно — аннотация «не работает», старт долгий, задача не выполнилась, — поэтому инструменты ниже собраны по вопросу, на который они отвечают. В конце раздела три чеклиста для самых частых симптомов.

Есть ли прокси и какие перехватчики на нём. AopUtils.isAopProxy(bean) отвечает, прокси ли это, AopProxyUtils.ultimateTargetClass(bean) возвращает настоящий класс, а массив ((Advised) bean).getAdvisors() — советы в порядке выполнения, где индекс 0 стоит снаружи (разделы 8.5 и 9.5). Короче всего проверить суффикс класса: $$SpringCGLIB$$ у подкласса или jdk.proxy у прокси JDK.

Открываются ли транзакции. Журнал org.springframework.transaction.interceptor на уровне TRACE печатает по паре строк на каждый вызов через прокси:

TransactionInterceptor Getting transaction for [dev.team.proxy.TxVisibilityLab$TransferService.transfer]
TransactionInterceptor Completing transaction for [dev.team.proxy.TxVisibilityLab$TransferService.transfer]

Листинг 9.143. Журнал TransactionInterceptor на уровне TRACE.

Если для метода этих строк нет, вызов прошёл мимо прокси, и для метода, вызванного через this, их действительно нет.

Почему бин создан или не создан. Запуск Spring Boot с аргументом --debug печатает отчёт CONDITIONS EVALUATION REPORT с секциями Positive matches, Negative matches, Exclusions и Unconditional classes: какие условия автоконфигурации сработали, какие нет и почему. Тот же отчёт отдаёт Actuator по адресу /actuator/conditions, а /actuator/beans — список бинов с типом, источником описания и зависимостями (Actuator Endpoints).

Откуда взялось значение свойства. ((ConfigurableEnvironment) env).getPropertySources() перечисляет источники в порядке приоритета (раздел 11.1), а Actuator по адресу /actuator/env/имя.свойства показывает, какой источник выиграл.

Как выглядит сгенерированный прокси. Свойство -Dcglib.debugLocation=каталог сохраняет сгенерированные подклассы на диск, а javap -p показывает их структуру (раздел 8.2).

Сколько контекстов поднимают тесты. Журнал org.springframework.test.context.cache на уровне DEBUG печатает статистику кэша size, hitCount, missCount (раздел 14.2).

Чем заняты потоки планировщика и пулов. jcmd <pid> Thread.print показывает стек каждого потока, и по именам scheduling-1, task-N или своему префиксу видно, где застряла задача (раздел 12.3).

Что зафиксировала обработка AOT. Каталог target/spring-aot/main/sources после mvn spring-boot:process-aot содержит сгенерированные описания бинов, и по ним видно, какие бины попали в сборку (раздел 15.1).

18.1 Чеклист: «аннотация не работает»

Проверки идут от самой дешёвой к самой трудоёмкой, и каждая занимает секунды:

  1. Включён ли механизм: @EnableTransactionManagement, @EnableCaching, @EnableAsync, @EnableMethodSecurity, @EnableResilientMethods; в Spring Boot часть из них включает автоконфигурация.
  2. Прокси ли это: AopUtils.isAopProxy(bean). Если нет — пункт 3, если да — пункт 5.
  3. Не создан ли бин раньше постпроцессоров: найти @Bean-методы постпроцессоров с параметрами или нестатические, поискать в журнале not eligible (раздел 3.3).
  4. Не final ли класс, подключён ли в Kotlin kotlin-spring.
  5. Не private, final или static ли метод; для прокси JDK — объявлен ли метод в интерфейсе.
  6. Не вызывается ли метод через this: журнал перехватчика на уровне TRACE покажет, доходит ли вызов до прокси.
  7. Есть ли нужный совет в getAdvisors() и правильный ли у советов порядок.

18.2 Чеклист: «приложение долго стартует»

Причины медленного старта проверяют в таком порядке: сначала то, что видно из отчёта --debug и структуры пакетов, потом обращения к внешним системам при старте, и в конце замер с обработкой AOT:

  1. --debug покажет, сколько автоконфигураций применилось; лишние выключают свойством spring.autoconfigure.exclude.
  2. Не сканируется ли лишнее: главный класс лежит в корне пакетов приложения, а не выше (раздел 13.2).
  3. Не ходит ли что-то в сеть при старте: @PostConstruct с вызовом внешней системы, миграции к недоступной базе, обращение к хранилищу секретов.
  4. Не слишком ли широки срезы аспектов: выражение вроде execution(* *.*(..)) проверяется на каждом методе каждого бина.
  5. Сравнить старт с -Dspring.aot.enabled=true (раздел 15.4).

18.3 Чеклист: «фоновая задача не выполнилась»

Задача @Async или @Scheduled может не выполниться, не оставив в журнале ни одной строки с ошибкой (разделы 12.2 и 12.3), поэтому причины проверяют по очереди:

  1. Не занят ли единственный поток планировщика: jcmd <pid> Thread.print, поток scheduling-1.
  2. Не упала ли задача молча: для @Async void — журнал SimpleAsyncUncaughtExceptionHandler или свой обработчик, для @Scheduled — журнал ошибок планировщика.
  3. Не отвергнута ли задача пулом: счётчик отказов пула, исключение RejectedExecutionException.
  4. Не выполнилась ли задача в другом экземпляре сервиса: без распределённой блокировки она выполняется во всех, а с ней — в одном.
  5. Не потерялась ли задача при остановке: сравнить время последнего запуска со временем выката и настройку ожидания задач (раздел 12.4).

19. Вопросы на интервью

Ниже вопросы, которые по Spring Core задают на собеседованиях уровня senior, с ответами, которые укладываются примерно в минуту. Ответы построены одинаково: механизм, следствие для практики и граница применимости, которой удобно закончить, а в скобках указан раздел, где механизм проверен запуском.

  1. Чем BeanFactory отличается от ApplicationContext? Контекст надстроен над фабрикой: он сам находит и регистрирует постпроцессоры, без которых не работают @Autowired, @PostConstruct и прокси, публикует события, даёт окружение и ресурсы и по умолчанию создаёт синглтоны при старте. «Голая» фабрика создаёт бины лениво и аннотаций не обрабатывает (2.3).

  2. Что происходит в refresh()? Двенадцать шагов, из которых главные три: на пятом постпроцессоры фабрики разбирают конфигурации и условия, на шестом регистрируются постпроцессоры бинов, на одиннадцатом создаются синглтоны, а на двенадцатом стартуют компоненты SmartLifecycle и публикуется ContextRefreshedEvent (3.2).

  3. Опишите жизненный цикл бина. Конструктор, внедрение через сеттеры и поля, интерфейсы Aware, postProcessBeforeInitialization с @PostConstruct, afterPropertiesSet, метод инициализации, postProcessAfterInitialization, где появляется прокси. При закрытии — @PreDestroy, destroy, метод уничтожения, причём SmartLifecycle.stop вызывается раньше @PreDestroy. @PostConstruct выполняется до появления прокси, поэтому транзакции и @Async в нём не работают (4.1, 12.2).

  4. Чем постпроцессор фабрики отличается от постпроцессора бинов? Первый меняет описания бинов, пока объектов ещё нет; второй обрабатывает созданные объекты и может подменить их прокси. Объявлять оба нужно статическими @Bean-методами без параметров, иначе их зависимости создадутся раньше времени и останутся без обработки (3.3).

  5. Как Spring разрешает циклические зависимости? Через три словаря DefaultSingletonBeanRegistry: при внедрении через сеттеры сосед получает раннюю ссылку на недостроенный объект или прокси через getEarlyBeanReference. Цикл через конструкторы разорвать нельзя, а Spring Boot с 2.6 запрещает и циклы через сеттеры. С 6.2 контейнер при цикле с поздними прокси пересоздаёт бины, и если прокси получают оба бина, один из них молча получает объект без прокси (6.1, 6.2).

  6. Зачем @Configuration подкласс CGLIB? Чтобы вызов одного @Bean-метода из другого возвращал бин из контейнера. С proxyBeanMethods = false подкласса нет, прямой вызов создаёт второй объект, а зависимости передают параметрами (7.1).

  7. Когда Spring создаёт прокси JDK, а когда CGLIB? JDK — когда у класса есть интерфейс и proxyTargetClass не включён, CGLIB — иначе. Spring Boot включает proxyTargetClass по умолчанию, поэтому в Boot прокси почти всегда подкласс. Экземпляр подкласса создаётся без конструктора, поэтому его поля пусты (8.2).

  8. Почему @Transactional не работает при вызове из того же класса? Вызов через this идёт мимо прокси. Лечат выносом метода в отдельный бин или TransactionTemplate. С Spring 6.0 @Transactional работает и на protected, и на package-private методах подкласса, а в 5.3 молча игнорировался на них (8.3, 8.4).

  9. Как устроена цепочка советов? Прокси создаёт ReflectiveMethodInvocation со списком перехватчиков, и каждый вызывает proceed(), передавая вызов следующему. Перехватчик, который не вызвал proceed(), обрывает цепочку, как кэш при попадании, а @Around может вызвать proceed() повторно, на чём держатся повторные попытки (9.4).

  10. В каком порядке срабатывают @Transactional, @Cacheable, @Retryable, @Async, @PreAuthorize? Меньший @Order стоит снаружи. Проверки прав Spring Security имеют порядок 100–600 (PRE_AUTHORIZE — 200), у транзакций и кэша одинаковый LOWEST_PRECEDENCE, и кэш по умолчанию оказывается внутри транзакции. @Retryable из Spring 7 и @Async вставляются в начало цепочки (9.5).

  11. Что делает @AfterReturning и может ли он подменить результат? Выполняется после успешного возврата и получает результат; менять его состояние может, а подменить сам результат — нет, это умеет только @Around (9.3).

  12. Чем @TransactionalEventListener отличается от @EventListener? Обычный слушатель выполняется сразу, в транзакции публикатора, и его исключение откатывает публикатора. Транзакционный выполняется в заданной фазе, по умолчанию после фиксации, и без транзакции не вызывается вовсе. Запись в базу из AFTER_COMMIT через JPA пропадает без REQUIRES_NEW, а доставку наружу эта фаза не гарантирует (10.3, 10.4).

  13. Что теряется в @Async? Всё, что живёт в ThreadLocal: пользователь, MDC, трассировка, транзакция. Переносят их TaskDecorator, обязательно очищая в finally. Исключение из void-метода попадает только в журнал (10.5, 12.2).

  14. Какой пул получает @Async по умолчанию? «Голый» Spring — SimpleAsyncTaskExecutor с потоком на вызов, Spring Boot — ThreadPoolTaskExecutor из восьми потоков с неограниченной очередью, с виртуальными потоками — исполнитель без ограничения параллелизма. Поэтому пул объявляют явно с конечной очередью (12.2).

  15. Чем ${...} отличается от #{...}? Первое — заполнитель свойства, второе — выражение SpEL, которое может вызывать методы и обращаться к бинам. Выражения из недоверенных источников вычисляют только в SimpleEvaluationContext (11.3).

  16. Как ускорить интеграционные тесты? Свести число вариаций конфигурации, потому что каждое отличие профилей, свойств и подмен бинов поднимает новый контекст, и убрать @DirtiesContext. Проверять как можно больше на уровне модульных тестов и срезов (14.2).

  17. Что делает Spring AOT? При сборке разбирает конфигурации и генерирует код регистрации бинов без рефлексии и подсказки для GraalVM. Бины под @Profile и @ConditionalOnProperty фиксируются при сборке, поэтому профиль, заданный при запуске, их не добавит (15.1, 15.2).

  18. Поведенческий. Расскажите об инциденте из-за механики Spring. Хороший ответ построен по схеме «ситуация — задача — действия — результат» и показывает ход поиска: что проверили первым, какой инструмент дал ключ и какую проверку завели, чтобы класс ошибок больше не повторился. Подходящие истории — в разделе 16.
