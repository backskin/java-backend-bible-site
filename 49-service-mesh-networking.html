49. Service mesh и сетевое взаимодействие

21 936 слов≈ 2 ч 00 мин чтения
Зачем это знать

Между вашим RestClient.get() и чужим контроллером в Kubernetes лежит десяток слоёв: conntrack и iptables на узле, CoreDNS с его ndots:5, EndpointSlice, два Envoy-прокси, mTLS-сессия и пара таймаутов, о которых вы не писали ни строчки. Когда в проде «то ли сеть, то ли сервис» отдаёт 503 UC upstream_connect_error, разбираться придётся именно в этих слоях, и разработчик, который умеет только смотреть логи приложения, встаёт в тупик. На интервью Istio спрашивают не потому, что ждут от вас работы SRE, а потому что он меняет контракт: часть отказоустойчивости, безопасности и наблюдаемости уезжает из вашего кода в инфраструктуру, и вы обязаны знать, где проходит граница. Эта глава закрывает сеть Kubernetes до уровня «я понимаю, куда делся пакет», mesh до уровня «я могу написать VirtualService и прочитать proxy-config», и честно отвечает, когда mesh не нужен вовсе.

1. Сетевая модель Kubernetes

1.1 Четыре правила сетевой модели

Kubernetes не реализует сеть — он объявляет требования к ней и делегирует реализацию плагину. Требования следующие (kubernetes.io, Cluster Networking):

  1. Каждый под получает собственный IP-адрес из плоского адресного пространства кластера.
  2. Поды могут общаться друг с другом без NAT — под A видит под B по его настоящему IP, и под B видит источник как настоящий IP пода A.
  3. Агенты на узле (kubelet, системные демоны) могут достучаться до любого пода на этом узле.
  4. Поды в host network видят другие поды без NAT.

Из этих правил вытекает больше, чем кажется. Во-первых, порт-конфликтов между подами не бывает: два Spring Boot-приложения на одном узле спокойно слушают 8080, потому что это 8080 в разных сетевых namespace. Прощай, Docker-эра с -p 18080:8080 и таблицей занятых портов в вики. Во-вторых, IP пода — эфемерный: пересоздали под — получили новый адрес. Всё, что пытается кешировать IP надолго (привет, networkaddress.cache.ttl=-1 в JVM — см. § 3.4), ломается. В-третьих, поскольку NAT между подами нет, логи и аудит видят настоящий источник, и NetworkPolicy может опираться на IP.

Внутри пода все контейнеры делят один сетевой namespace: один IP, одна таблица маршрутизации, один набор портов, общий localhost. Это база для sidecar-паттерна (§ 7): прокси в соседнем контейнере может перехватывать трафик приложения через iptables-правила, потому что iptables у них — общие. Технически namespace создаётся не контейнером приложения, а инфраструктурным «pause»-контейнером, который живёт весь срок жизни пода и держит namespace, даже когда прикладные контейнеры перезапускаются.

Node 10.0.1.5
┌──────────────────────────────────────────────────────┐
│  Pod A 10.244.1.7        Pod B 10.244.1.8            │
│  ┌───────────────┐       ┌───────────────┐           │
│  │ pause  app    │       │ pause  app    │           │
│  │  (net ns #1)  │       │  (net ns #2)  │           │
│  └──────┬────────┘       └──────┬────────┘           │
│      veth1                   veth2                   │
│         └──────── cni0 / bridge ───────┘             │
│                       │                              │
│                    eth0 10.0.1.5  ── к другим нодам  │
└──────────────────────────────────────────────────────┘

Пара veth — виртуальный «патч-корд»: один конец внутри namespace пода как eth0, второй — в host namespace, включён в бридж или напрямую в таблицу маршрутизации хоста.

1.2 Функции CNI-плагина

CNI (Container Network Interface) — это до неприличия простая спецификация: бинарник, которому kubelet (точнее, CRI-среда выполнения) передаёт JSON на stdin и переменные окружения, а тот выполняет команду ADD / DEL / CHECK и печатает результат. На ADD плагин обязан: выделить IP из выделенного узлу диапазона (IPAM), создать veth-пару, перенести её конец в namespace пода, настроить адрес и маршрут по умолчанию, вернуть результат. Всё остальное — маршрутизация между узлами, политики, шифрование — уже надстройка конкретной реализации.

Принципиальная развилка — как пакет попадает с узла на узел.

Overlay (инкапсуляция). Пакет пода целиком заворачивается в UDP-датаграмму (VXLAN, порт 8472) или в IP-in-IP и отправляется на IP узла-получателя. Подсети подов физической сети неизвестны — ей видны только адреса узлов. Плюс: работает в любой сети, включая облачные VPC с anti-spoofing-фильтрами и сети, где вы не управляете маршрутизатором. Минус: накладные расходы. VXLAN добавляет 50 байт заголовка (14 внешний Ethernet + 20 IP + 8 UDP + 8 VXLAN), поэтому при физическом MTU 1500 внутренний MTU пода становится 1450. Если вы этого не учли (или учли, а облачный провайдер втихую поставил MTU 1450 на VPC — как AWS для некоторых сценариев), получаете классику: TCP-рукопожатие проходит, мелкие запросы летают, а большой POST зависает до таймаута, потому что пакеты полного размера без уведомления отбрасываются и Path MTU Discovery не работает из-за фильтрации ICMP. Плюс к байтам — CPU на инкапсуляцию/декапсуляцию, хотя современные NIC умеют offload для VXLAN.

Routed (без инкапсуляции). Каждый узел анонсирует «подсеть 10.244.1.0/24 — за мной» по BGP, физическая сеть маршрутизирует нативные пакеты подов. Плюс: нет накладных расходов, полный MTU, пакет пода виден в сети как есть — легче отлаживать tcpdump-ом на аплинке. Минус: нужна кооперация с сетевой инфраструктурой (BGP-пиринг с ToR-коммутаторами) либо чтобы все узлы были в одном L2-домене.

Плагин Режим по умолчанию Datapath NetworkPolicy Отличительное
Flannel VXLAN overlay ядро (bridge + vxlan) нет (нужен отдельный контроллер) минимализм; только связность
Calico routed (BGP), опционально IPIP/VXLAN iptables/nftables или eBPF да, плюс расширенные GlobalNetworkPolicy зрелый BGP, хорош в bare-metal

🔧 Под капотом. Разница между Calico в режиме iptables и Cilium в режиме eBPF — не «быстрее/медленнее» на 10 %, а разные точки в стеке. iptables работает в netfilter-хуках и обрабатывает правила линейно; eBPF-программа цепляется к tc-хуку сетевого драйвера или к XDP и выполняет хеш-лукап в eBPF map. Для сотни правил разницы почти нет, для десяти тысяч — на порядок.

⚠️ Осторожно. kubectl apply -f networkpolicy.yaml с Flannel проходит успешно, объект появляется в API, kubectl get netpol его показывает — и ничего не блокирует. Kubernetes прямо документирует: без сетевого плагина, реализующего NetworkPolicy, создание объекта не имеет эффекта (kubernetes.io, Network Policies). Это самый коварный вид «безопасности»: аудит зелёный, защиты нет. Проверять надо тестом — подняли под, попробовали curl туда, куда нельзя.

1.3 MTU и оверлей: симптомы в Java-сервисе

MTU и оверлей — не абстракция. Три симптома, которые стоит уметь связать с сетью:

  • Большие ответы (>1 КБ) зависают, маленькие работают. MTU/фрагментация. Проверка: ping -M do -s 1400 <pod-ip> — если проходит, а -s 1472 нет, эффективный MTU меньше 1500.
  • SocketTimeoutException строго на 60–75 секундах при работающем соединении — это не приложение, это conntrack на узле выкинул запись об idle-соединении (nf_conntrack_tcp_timeout_established по умолчанию 5 суток, но для NAT-шлюзов облака часто 350 с) и обратные пакеты пошли в никуда. Лечение — TCP keep-alive короче таймаута NAT (см. главу 50).
  • Соединения к внешнему API рвутся при скейле кластера — исчерпание портов SNAT на egress-шлюзе.

2. Service, kube-proxy и EndpointSlice

Словарь: Service

2.1 ClusterIP

ClusterIP — не адрес чего-либо. Это виртуальный адрес из service-cluster-ip-range, на который никто не отвечает ARP-ом и который не принадлежит ни одному интерфейсу. Он существует только как ключ в правилах на каждом узле: «пакет на 10.96.0.42:80 → подменить адрес назначения на один из живых подов».

Кто наполняет эти правила: контроллер эндпоинтов следит за подами, попадающими под селектор Service и прошедшими readiness, и пишет их в объекты EndpointSlice. kube-proxy на каждом узле подписан на Service и EndpointSlice и перекладывает их в datapath.

Замена Endpoints на EndpointSlice. Старый объект Endpoints хранил все адреса сервиса в одном ресурсе. Сервис на 5000 подов — это объект в несколько мегабайт, и любое изменение (один под перезапустился) отправляло весь объект всем watch-подписчикам: каждому kube-proxy на каждом узле, каждому ingress-контроллеру. При скейле это превращалось в шторм на apiserver и etcd. EndpointSlice режет список на куски (по умолчанию до 100 эндпоинтов на срез), и обновляется только затронутый срез. Заодно в срезе появились поля, которых не было в Endpoints: conditions.ready / serving / terminating, zone и nodeName для topology-aware routing, hints.

🔧 Под капотом. Поле serving отделили от ready именно ради graceful shutdown: под, получивший SIGTERM, становится ready=false, но остаётся serving=true и terminating=true, пока дорабатывает текущие запросы. Это позволяет прокси не рвать существующие соединения. Подробности жизненного цикла пода — глава 47.

2.2 Режимы kube-proxy

iptables-режим (значение по умолчанию). На каждую пару (сервис, порт) создаётся цепочка KUBE-SVC-XXX, в ней — по правилу на каждый эндпоинт с модулем statistic --mode random --probability, ведущее в KUBE-SEP-YYY, где происходит DNAT. Балансировка — равновероятная случайная, не round-robin и не настраивается.

Проблема — линейность. Netfilter проходит правила цепочки последовательно. Формально лукап O(n) по числу эндпоинтов внутри сервиса, но настоящая боль в другом: правила обновляются целиком. kube-proxy при изменении делает iptables-restore всей таблицы, а не точечную правку. При 5000 сервисов таблица — это сотни тысяч правил, генерация и применение занимают секунды, и во время iptables-restore ядро держит глобальную блокировку xtables. Известные цифры сообщества: при ~10 000 сервисов задержка применения изменений измеряется десятками секунд. Практическое следствие для разработчика: после деплоя нового пода трафик может пойти на него не мгновенно, а через заметную паузу, и наоборот — удалённый под ещё несколько секунд получает запросы.

IPVS-режим. Использует подсистему ядра для балансировки (тот же механизм, что в LVS): хеш-таблица вместо линейного списка, лукап O(1), обновление — точечное добавление/удаление real server. Плюс — настоящие алгоритмы балансировки: rr, lc (least connection), dh, sh (source hashing), sed, nq. Включается --proxy-mode=ipvs --ipvs-scheduler=lc. Минус: iptables всё равно нужен для части сценариев (маскарадинг, NodePort, фильтрация), поэтому «избавиться от iptables» не получается; и часть сетевых политик CNI всё равно живёт в iptables.

nftables-режим. Появился как альтернатива iptables-режиму: тот же подход, но на nftables с его словарями (vmap), что даёт лукап по хешу вместо линейного обхода и намного более дешёвые инкрементальные обновления. Это штатный путь миграции для больших кластеров, не требующий IPVS.

eBPF (Cilium без kube-proxy). Cilium умеет полностью заменить kube-proxy: «use Cilium to fully replace it» для сервисов типов ClusterIP, NodePort, LoadBalancer и с externalIPs (docs.cilium.io). Ключевой приём — socket-level load balancing: вместо того чтобы транслировать адрес на каждом пакете, Cilium цепляется к системным вызовам и подменяет адрес назначения один раз, при connect(): «upon connect (TCP, connected UDP), sendmsg (UDP), or recvmsg (UDP) system calls, the destination IP is checked for an existing service IP and one of the service backends is selected». Приложение в поде думает, что соединяется с ClusterIP, а сокет ядра уже открыт напрямую к IP пода — DNAT на пути пакетов не нужен вовсе, conntrack-запись для сервиса не создаётся. Документация подтверждает, что при этом «no iptables rule for the service is present». Для входящего трафика возможно ускорение на XDP — «directly in the networking driver instead of a higher layer».

2.3 Headless-сервис

clusterIP: None — это Service без виртуального адреса. DNS-запрос к такому имени возвращает не один адрес, а список IP всех готовых подов (kubernetes.io, DNS for Services and Pods). Никакого kube-proxy, никакого DNAT — клиент сам решает, к кому идти.

Это основа для:

  • StatefulSet — стабильные DNS-имена подов pod-0.svc.ns.svc.cluster.local (нужно Kafka, PostgreSQL-кластерам, Cassandra);
  • клиентской балансировки — gRPC-клиент с dns:///my-svc.ns.svc.cluster.local разрешает headless-имя, получает N адресов и держит по соединению к каждому (см. § 5);
  • SRV-записей — _grpc._tcp.my-svc.my-ns.svc.cluster.local отдаёт порты и хосты.

Обратная сторона: headless + mesh — источник классических проблем (см. ошибку № 14): у Envoy нет одного VIP, на который вешать listener, и конфигурация строится иначе.

3. DNS в кластере: CoreDNS и ndots:5

Словарь: DNS

3.1 Устройство DNS-имён в кластере

Kubelet записывает в /etc/resolv.conf каждого пода (kubernetes.io, DNS for Services and Pods):

nameserver 10.96.0.10
search <namespace>.svc.cluster.local svc.cluster.local cluster.local
options ndots:5

Полное имя сервиса — my-svc.my-namespace.svc.cluster-domain.example, где cluster-domain.example почти всегда cluster.local. Обычный сервис разрешается в свой ClusterIP, headless — в набор IP подов. Для именованных портов существуют SRV-записи вида _port-name._port-protocol.my-svc.my-namespace.svc.cluster.local.

За разрешение имён отвечает CoreDNS — плагинный DNS-сервер на Go. Его конфигурация — Corefile:

.:53 {
    errors
    health { lameduck 5s }
    ready
    kubernetes cluster.local in-addr.arpa ip6.arpa {
        pods insecure
        fallthrough in-addr.arpa ip6.arpa
        ttl 30
    }
    prometheus :9153
    forward . /etc/resolv.conf { max_concurrent 1000 }
    cache 30
    loop
    reload
    loadbalance
}

Плагин kubernetes отвечает на *.cluster.local из своего watch-кеша объектов Service/EndpointSlice — то есть в API-сервер на каждый запрос он не ходит. Всё остальное уходит в forward на вышестоящие распознаватели узла. cache 30 кеширует положительные ответы, ttl 30 — TTL в ответах.

3.2 Опция ndots:5 и разрешение внешних имён

Опция ndots:N в распознавателе glibc означает: если в имени меньше N точек, сначала пробовать его с каждым search-доменом по очереди, и только потом — как абсолютное. Kubernetes ставит ndots:5, чтобы работали короткие имена внутри кластера: payments → payments.<ns>.svc.cluster.local, payments.billing → payments.billing.svc.cluster.local.

Теперь посчитайте для api.partner-bank.com — в нём две точки, то есть меньше пяти:

  1. api.partner-bank.com.myns.svc.cluster.local → NXDOMAIN
  2. api.partner-bank.com.svc.cluster.local → NXDOMAIN
  3. api.partner-bank.com.cluster.local → NXDOMAIN
  4. api.partner-bank.com → наконец-то ответ

Четыре запроса вместо одного. А если приложение разрешает и A, и AAAA (glibc делает оба параллельно), то восемь DNS-пакетов на одно разрешение имени. При этом три из четырёх — гарантированные промахи: CoreDNS их обрабатывает, форвардит наружу (если не настроен template-плагин для отсечки), а отрицательные ответы кешируются хуже положительных.

📊 Цифры. Каждый лишний round-trip к CoreDNS — это, в лучшем случае, доли миллисекунды; под нагрузкой при перегруженном CoreDNS или потерях UDP-пакетов — единицы и десятки миллисекунд, а при срабатывании timeout 5 в распознавателе glibc — пять секунд на попытку. Классический инцидент: «раз в несколько минут запрос к внешнему API занимает ровно 5 секунд» — это потерянный UDP-пакет DNS и повтор распознавателя, усиленный в 4 раза из-за ndots.

Три способа лечения.

  1. FQDN с точкой на конце. api.partner-bank.com. — завершающая точка делает имя абсолютным, search-домены не применяются. Проблема: не все библиотеки и не все места конфигурации это переживают корректно (некоторые валидаторы URL ругаются), плюс это надо сделать во всех конфигах.

  2. dnsConfig на поде — снизить ndots:

YAML
apiVersion: v1
kind: Pod
metadata:
  name: payments
spec:
  dnsPolicy: ClusterFirst
  dnsConfig:
    options:
      - name: ndots
        value: "2"
      - name: single-request-reopen   # A и AAAA в разных сокетах, лечит баг с потерей ответа
      - name: timeout
        value: "1"
      - name: attempts
        value: "3"

С ndots:2 имя api.partner-bank.com (2 точки — не меньше 2) идёт сразу абсолютным запросом, а короткое payments внутри namespace продолжает работать. Ломается только двухсегментная форма payments.billing — её придётся писать как payments.billing.svc.cluster.local. Это осознанный компромисс, и для сервисов, много ходящих наружу, он почти всегда оправдан.

  1. NodeLocal DNSCache — DaemonSet с кеширующим распознавателем на каждом узле, слушающим на link-local адресе. Пода общаются с локальным кешем по TCP-соединению к CoreDNS вместо UDP, что убирает и потери пакетов, и conntrack-записи для UDP-DNS.

3.3 Кеширование DNS в JVM

JVM кеширует результаты разрешения имён в самой JVM, поверх ОС-распознавателя, и параметры этого кеша исторически отличаются от ожиданий:

  • networkaddress.cache.negative.ttl по умолчанию 10 секунд;
  • networkaddress.cache.ttl — implementation-specific; значение -1 означает «кешировать вечно», и именно оно включается при установленном SecurityManager (которого с JDK 24 уже нет, но старые конфигурации живут);
  • с JDK 21 есть networkaddress.cache.stale.ttl — отдавать протухшую запись, пока идёт фоновое обновление.

Подробности проверены и зафиксированы в главе 27; механика ОС-распознавателя и search-доменов — в главе 50 (50-linux-and-networking.md). Для mesh это важно потому, что при включённом sidecar приложение почти никогда не разрешает само — Envoy перехватывает соединение на уровне IP:порт и сам решает, куда его отправить, опираясь на конфигурацию от istiod, а не на DNS. Но разрешение имени всё равно происходит: приложение должно получить какой-то IP, чтобы вызвать connect(). Именно поэтому у Istio есть режим DNS-прокси (ISTIO_META_DNS_CAPTURE), которая перехватывает и DNS-запросы тоже — тогда разрешение имени обслуживает локальный агент из конфигурации mesh, без похода в CoreDNS вообще. Это одновременно и лечение ndots-проблемы, и способ заставить работать имена из ServiceEntry, которых в кластерном DNS нет.

4. NetworkPolicy, ingress и egress

Словарь: NetworkPolicy

4.1 Модель NetworkPolicy: аддитивный список разрешений

Три правила, которые нужно понимать буквально (kubernetes.io, Network Policies):

  1. Пока под не выбран ни одной политикой — он не изолирован, весь трафик разрешён. Как только его выбирает хотя бы одна политика с Ingress в policyTypes — входящий трафик запрещён весь, кроме явно разрешённого. То же отдельно для Egress.
  2. Изоляция ingress и egress независимы. Политика без указанного policyTypes по умолчанию считается только Ingress.
  3. Политики аддитивны: если применимы несколько, разрешено объединение. Запретить что-то «поверх» разрешающей политики штатным NetworkPolicy нельзя — в списке ограничений прямо сказано: нет «deny all except», нет L7-фильтрации, нет выбора контейнеров по имени, протоколы только TCP/UDP/SCTP. Трафик от/к узлу, на котором работает под, разрешён всегда, независимо от IP.

Важное следствие: для соединения A → B должны сойтись обе стороны — egress-политика A должна разрешать выход к B, и ingress-политика B должна разрешать вход от A.

Базовый набор для сервиса. Начинаем с default deny в namespace:

YAML
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-all
  namespace: payments
spec:
  podSelector: {}          # все поды namespace
  policyTypes: [Ingress, Egress]
  # ни ingress, ни egress не перечислены => запрещено всё

Дальше — точечные разрешения. Первое, о чём забывают: DNS. Если запретили egress, поды перестают разрешать имена, и симптом выглядит как «приложение не видит базу», хотя дело в CoreDNS:

YAML
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-dns
  namespace: payments
spec:
  podSelector: {}
  policyTypes: [Egress]
  egress:
    - to:
        - namespaceSelector:
            matchLabels: { kubernetes.io/metadata.name: kube-system }
          podSelector:
            matchLabels: { k8s-app: kube-dns }
      ports:
        - { protocol: UDP, port: 53 }
        - { protocol: TCP, port: 53 }

Обратите внимание на структуру: namespaceSelector и podSelector внутри одного элемента списка to (без дефиса перед podSelector) означают AND — «под с меткой k8s-app: kube-dns в namespace kube-system». Если поставить дефис и сделать их двумя элементами, получится OR — «любой под в kube-system ИЛИ под с меткой kube-dns где угодно». Это ошибка № 1 в NetworkPolicy, и YAML о ней не предупредит.

Типовой полный набор для Spring Boot-сервиса:

YAML
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: payments-ingress, namespace: payments }
spec:
  podSelector:
    matchLabels: { app: payments }
  policyTypes: [Ingress]
  ingress:
    # трафик от ingress-контроллера
    - from:
        - namespaceSelector:
            matchLabels: { kubernetes.io/metadata.name: ingress-nginx }
      ports: [{ protocol: TCP, port: 8080 }]
    # трафик от сервиса заказов
    - from:
        - namespaceSelector:
            matchLabels: { kubernetes.io/metadata.name: orders }
          podSelector:
            matchLabels: { app: orders }
      ports: [{ protocol: TCP, port: 8080 }]
    # Prometheus скребёт actuator
    - from:
        - namespaceSelector:
            matchLabels: { kubernetes.io/metadata.name: monitoring }
      ports: [{ protocol: TCP, port: 8081 }]
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: payments-egress, namespace: payments }
spec:
  podSelector:
    matchLabels: { app: payments }
  policyTypes: [Egress]
  egress:
    - to:
        - namespaceSelector:
            matchLabels: { kubernetes.io/metadata.name: kube-system }
          podSelector:
            matchLabels: { k8s-app: kube-dns }
      ports: [{ protocol: UDP, port: 53 }, { protocol: TCP, port: 53 }]
    # PostgreSQL вне кластера
    - to: [{ ipBlock: { cidr: 10.20.30.0/24 } }]
      ports: [{ protocol: TCP, port: 5432 }]
    # Kafka
    - to:
        - namespaceSelector:
            matchLabels: { kubernetes.io/metadata.name: kafka }
      ports: [{ protocol: TCP, port: 9092 }]
    # выход наружу через egress-gateway
    - to:
        - namespaceSelector:
            matchLabels: { kubernetes.io/metadata.name: istio-system }
          podSelector:
            matchLabels: { istio: egressgateway }
      ports: [{ protocol: TCP, port: 443 }]

⚠️ Осторожно. NetworkPolicy — L3/L4 и работает по IP. Она не знает про DNS-имена. Правило «разрешить egress на api.partner-bank.com» штатно невозможно: партнёр меняет IP — вы теряете связь; вы прописали /16 — открыли пол-облака. Решения: (а) egress-gateway с фиксированным набором адресов, (б) CNI с DNS-aware политиками (Calico GlobalNetworkPolicy с доменами, Cilium toFQDNs), (в) ServiceEntry + egress-gateway в Istio (§ 9.6).

4.2 Ingress-контроллеры и Gateway API

Ingress — старый API, чей spec умеет только host/path-маршрутизацию и TLS-терминацию; всё остальное (таймауты, повторы, канареечные веса, rewrite, аутентификация, rate limiting) живёт в аннотациях конкретного контроллера. Аннотации nginx-ingress несовместимы с аннотациями Traefik, а те — с HAProxy. Это не стандарт, это конвенция.

Gateway API — замена, вынесенная в отдельную группу gateway.networking.k8s.io. Четыре вида ресурсов достигли v1: GatewayClass, Gateway, HTTPRoute, GRPCRoute; они покрывают матчинг по заголовкам и веса трафика, которые в Ingress были возможны только через аннотации. Ingress при этом не объявлен устаревшим, и в документации есть отдельный раздел про миграцию (kubernetes.io, Gateway API).

Ключевая идея Gateway API — разделение ролей. Инфраструктурная команда владеет GatewayClass и Gateway (кто и как терминирует TLS, какие адреса, какие порты), команда сервиса владеет HTTPRoute (куда идут её пути) и не может случайно поменять TLS-конфигурацию всего кластера. В Ingress всё это было в одном объекте.

YAML
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: public
  namespace: infra
spec:
  gatewayClassName: istio
  listeners:
    - name: https
      protocol: HTTPS
      port: 443
      hostname: "*.bank.example"
      tls:
        mode: Terminate
        certificateRefs: [{ name: wildcard-bank-tls }]
      allowedRoutes:
        namespaces: { from: Selector, selector: { matchLabels: { exposed: "true" } } }
---
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: payments
  namespace: payments
spec:
  parentRefs: [{ name: public, namespace: infra }]
  hostnames: ["api.bank.example"]
  rules:
    - matches: [{ path: { type: PathPrefix, value: /v1/payments } }]
      backendRefs:
        - { name: payments, port: 8080, weight: 90 }
        - { name: payments-canary, port: 8080, weight: 10 }
      timeouts: { request: 3s }

Istio реализует Gateway API наравне со своими CRD, и для north-south трафика это сейчас предпочтительный путь: те же веса, что в VirtualService, но в стандартном API.

4.3 Исходящий трафик (egress)

По умолчанию под выходит в интернет через SNAT на IP узла: исходящий пакет с 10.244.1.7 маскарадится в адрес узла. Проблемы начинаются, когда партнёр требует белый список IP.

Варианты:

  • NAT-шлюз облака со статическим IP — весь egress кластера через один или несколько адресов. Просто, но исчерпание SNAT-портов (≈64 000 на пару «адрес, протокол», а по факту меньше) при большом числе соединений к одному адресату превращается в загадочные connection timed out.
  • Выделенный пул узлов с публичными IP + nodeSelector для «исходящих» подов.
  • Egress-gateway — специальный под(ы), через который принудительно идёт весь внешний трафик; статический IP даётся только им, а NetworkPolicy запрещает остальным подам прямой выход. В Istio это штатный паттерн (§ 9.6): ServiceEntry описывает внешний хост, VirtualService заворачивает трафик к нему на istio-egressgateway, а тот терминирует/оригинирует TLS и выходит со своего адреса. Дополнительный бонус — точка наблюдения: весь внешний трафик виден в метриках и логах одного компонента.

5. Балансировка на уровнях L4 и L7

Словарь: L4, L7

5.1 Механизм балансировки L4 и L7

L4-балансировщик работает с TCP-соединением: смотрит на IP и порт, выбирает бэкенд один раз при установлении соединения и дальше просто перекладывает байты. Он не разбирает содержимое, не знает про HTTP-запросы, не может маршрутизировать по заголовку. Именно так работает kube-proxy: DNAT при первом SYN, дальше conntrack.

L7-балансировщик терминирует соединение, разбирает протокол и принимает решение на каждый запрос: смотрит путь, метод, заголовки, может переписать URI, добавить заголовок, повторить запрос на другом бэкенде, посчитать метрику по коду ответа.

5.2 Балансировка L4 для gRPC и HTTP/2

HTTP/1.1 без keep-alive был идеален для L4: соединение на запрос, значит балансировка на соединение = балансировка на запрос. С keep-alive уже не так, но соединения всё же повторно используются ограниченно и закрываются.

HTTP/2 и gRPC устроены наоборот: одно долгоживущее TCP-соединение, в нём мультиплексируются тысячи стримов (см. главу 28). Клиент установил соединение, L4-балансировщик выбрал под #3 — и все последующие запросы, часами, идут в под #3. Вы отскейлили сервис с 3 до 30 подов — трафик остался на трёх.

Наблюдаемый симптом: добавили реплик, нагрузка на них нулевая, на старых подах — 100 %. В метриках RPS распределён как угодно, только не равномерно; kubectl top pods показывает три горячих пода и двадцать семь спящих.

Три способа лечить:

  1. L7-прокси в пути — Envoy/sidecar/ingress-контроллер терминирует HTTP/2 и балансирует по стримам. Это ровно то, что даёт mesh «бесплатно», и это одна из самых частых настоящих причин его внедрения.
  2. Клиентская балансировка — gRPC-клиент разрешает headless-сервис, получает список IP подов, держит подсоединение к каждому и сам применяет round_robin:
Java
ManagedChannel channel = Grpc.newChannelBuilder(
            "dns:///payments-headless.payments.svc.cluster.local:9090",
            InsecureChannelCredentials.create())
        .defaultLoadBalancingPolicy("round_robin")
        .idleTimeout(30, TimeUnit.SECONDS)
        .build();

Схема dns:/// включает DNS-распознаватель grpc-java; для headless-сервиса он получает все адреса подов. Минус: клиент не узнаёт о новых подах до следующего разрешения имени (grpc-java разрешает имя заново при разрыве соединения или по своему расписанию), а при 100 клиентах × 50 подов получаем 5000 соединений.

  1. Ограничить время жизни соединения на сервере — maxConnectionAge в gRPC-сервере или maxRequestsPerConnection в Istio DestinationRule. Соединение периодически закрывается (с GOAWAY), клиент переподключается, L4 заново распределяет. Грубо, но работает даже с тупым L4.
Java
Server server = NettyServerBuilder.forPort(9090)
        .maxConnectionAge(30, TimeUnit.MINUTES)
        .maxConnectionAgeGrace(30, TimeUnit.SECONDS)  // время на добивку текущих стримов
        .addService(new PaymentsService())
        .build();

💡 На интервью. «Почему L4-балансировщик ломает gRPC?» — «Потому что gRPC — это HTTP/2: одно долгоживущее TCP-соединение, в котором мультиплексируются все запросы. L4 балансирует на уровне соединений, значит выбор бэкенда делается один раз и навсегда. После скейлинга новые поды не получат трафика. Лечится L7-прокси, который балансирует по стримам, клиентской балансировкой через headless-сервис, либо принудительным закрытием соединений по maxConnectionAge.»

Sidecar в mesh — это client-side балансировка, вынесенная из процесса: решение принимается рядом с клиентом (на его localhost), но конфигурируется централизованно и не зависит от языка. В этом и состоит основной технический смысл mesh — получить преимущества client-side без обязательства писать библиотеку на каждом языке.

6. Назначение service mesh

6.1 Задача service mesh

Возьмите список того, что должен уметь любой сервис в распределённой системе:

  • таймауты на исходящие вызовы;
  • повторы с ограничением и джиттером;
  • circuit breaker и отсечение больных экземпляров;
  • балансировка с учётом здоровья бэкендов;
  • взаимная аутентификация (mTLS) и шифрование трафика между сервисами;
  • авторизация «кто с кем может говорить»;
  • метрики RED (rate/errors/duration) по каждому вызову;
  • проброс контекста трассировки;
  • канареечная маршрутизация при выкатке.

Этот список одинаков для всех сервисов и никак не зависит от бизнес-логики. Классический ответ — библиотека: Netflix OSS (Ribbon + Hystrix + Eureka), потом Spring Cloud, потом Resilience4j. Работает, пока верны два условия: все сервисы на одном языке и вы можете заставить их вовремя обновляться.

В реальном банке ни одно из условий не выполняется. Есть Java 8-монолит, Java 21-микросервисы, Kotlin, Python для ML, Go для инфраструктурных демонов, пара Node.js-BFF и подсистема на C#. Ribbon под Python нет. А главное — обновление политики требует релиза приложения: чтобы поменять таймаут с 30 с на 3 с в сорока сервисах, нужно сорок PR, сорок сборок, сорок деплоев и сорок команд, у каждой свой спринт. В инциденте, когда таймаут надо срезать прямо сейчас, это неприемлемо.

Идея mesh: вынести весь этот слой из процесса приложения в сеть, где он станет одинаковым для всех языков и управляемым централизованно, без релиза приложения.

6.2 Data plane и control plane

Data plane — это прокси, через которые реально идут байты. В Istio это Envoy: по одному рядом с каждым подом (sidecar) либо по одному на узел (ztunnel в ambient) плюс общие waypoint/gateway. Прокси перехватывает весь входящий и исходящий трафик пода, применяет политики и собирает телеметрию.

Control plane — компонент, который знает состояние кластера (сервисы, поды, эндпоинты) и конфигурацию (ваши CRD), компилирует их в конфигурацию прокси и рассылает. В Istio это istiod — один бинарник, в котором объединены исторические компоненты:

  • Pilot — трансляция Service/EndpointSlice/VirtualService/DestinationRule в xDS-конфигурацию Envoy и её раздача;
  • Citadel — встроенный CA: приём CSR от агентов, выпуск и ротация сертификатов рабочих нагрузок;
  • Galley — валидация и агрегация конфигурации (сейчас — validating webhook и конвертация).

До Istio 1.5 это были три (плюс sidecar-injector и mixer) отдельных Deployment; их слияние в istiod — главное упрощение эксплуатации за всю историю проекта. Заодно выкинули Mixer — компонент, через который раньше шли все проверки политик и телеметрия: каждый запрос порождал вызов к Mixer, что давало ощутимую латентность и делало Mixer узким местом. Сейчас телеметрия и политики считаются внутри Envoy.

Важнейшее свойство архитектуры: падение control plane не роняет трафик. Envoy продолжает работать с последней полученной конфигурацией. Что перестаёт работать: применение новых политик, обновление списков эндпоинтов (новые поды не получат трафика, удалённые продолжат его получать) и — через несколько часов — ротация сертификатов. То есть istiod down — это не авария, а «часы до аварии».

6.3 Встроенные возможности mesh

  • mTLS между всеми сервисами без единой строчки в приложении и без ручной работы с keystore. Сертификаты выпускаются автоматически, живут часами и ротируются сами.
  • Политики доступа уровня «сервис A может вызывать POST /v1/payments у сервиса B» — декларативно, на основе криптографической идентичности, а не IP.
  • Retry / timeout / outlier detection / circuit breaking — одинаково для Java, Python и Go.
  • Traffic shifting — веса между версиями, маршрутизация по заголовкам, зеркалирование.
  • Телеметрия без инструментирования — стандартные RED-метрики по каждой паре «источник → назначение» и access-логи в едином формате.
  • Fault injection — искусственные задержки и ошибки для проверки устойчивости, без тестового кода в приложении.

6.4 Ограничения mesh

Это самая ценная часть темы на интервью, потому что её обычно не проговаривают.

Mesh не знает семантику запроса. Прокси видит POST /v1/transfers и код ответа. Он не знает:

  • идемпотентен ли запрос. Настроив retryOn: 5xx на маршруте создания платежа, вы получите дубли платежей — прокси не в курсе, что повтор опасен. Идемпотентность — свойство вашего API (ключ идемпотентности, см. главу 27), и решение «можно ли повторять» принимает тот, кто знает контракт;
  • что считать ошибкой. Ваш сервис отдаёт 200 OK с телом {"status":"DECLINED"} — для mesh это успех, для бизнеса отказ. И наоборот: 404 при проверке существования клиента — нормальный ответ, а не ошибка, но outlier detection может посчитать иначе (правда, он смотрит только 5xx — см. § 8.5);
  • что делать вместо. Fallback «если скоринг недоступен — считаем клиента среднерисковым и продолжаем» — это бизнес-решение. Прокси умеет только вернуть 503.

Mesh не заменяет авторизацию в приложении. AuthorizationPolicy отвечает на вопрос «какой сервис имеет право дёргать этот эндпоинт». Он не отвечает на вопрос «имеет ли этот пользователь право видеть этот счёт». Row-level и object-level авторизация — всегда в приложении (см. главу 13, 13-spring-security.md). Broken Access Control — это A01 в OWASP Top 10:2025, и mesh закрывает из него ровно ноль на уровне объектов.

Mesh не проверяет данные. Схема запроса, бизнес-инварианты, ограничения БД — вне его компетенции.

Mesh не создаёт трассировку. Он может сгенерировать корневой span и добавить заголовки на входе, но связать входящий запрос с исходящим внутри вашего процесса он не в состоянии — это требует проброса заголовков в коде. Подробно в § 11.3; это самое частое заблуждение про mesh.

Mesh не чинит плохую архитектуру. Если цепочка вызовов на 8 сервисов в глубину, mesh добавит к ней 16 хопов через прокси и покажет вам красивую картинку того, насколько всё плохо.

💡 На интервью. «Что service mesh может, а что нет?» — «Может всё, что определяется на уровне соединения и HTTP-метаданных: mTLS, идентичность и политики доступа между сервисами, таймауты, повторы, outlier detection, веса маршрутов, RED-метрики и access-логи — причём одинаково для всех языков и без релиза приложения. Не может ничего, что требует семантики: он не знает, идемпотентен ли запрос, что в вашем домене считать ошибкой, какой нужен fallback, и не делает объектную авторизацию. И он не создаёт трассировку сам — приложение обязано пробрасывать заголовки контекста.»

7. Sidecar и его альтернативы

7.1 Перехват трафика sidecar-прокси

Sidecar — это контейнер с Envoy в том же поде, а значит, в том же сетевом namespace. У них общий localhost, общие порты и, главное, общие iptables-правила. Дальше — фокус: приложение ничего не знает о прокси, а весь его трафик заворачивается.

Классический механизм Istio — init-контейнер istio-init, который запускает скрипт istio-iptables до старта прикладных контейнеров и настраивает правила в namespace пода:

  • исходящий трафик от любого процесса в поде, кроме UID/GID прокси (по умолчанию 1337), перенаправляется правилом REDIRECT в цепочке OUTPUT/ISTIO_OUTPUT на порт 15001;
  • входящий трафик из PREROUTING/ISTIO_INBOUND — на порт 15006;
  • исключения: localhost-трафик внутри пода, порты самого Envoy (15000 admin, 15020 telemetry/health, 15021 healthz, 15090 prometheus), а также настраиваемые списки CIDR и портов, которые надо пропустить мимо прокси.

Ключевая деталь — исключение по UID: если бы его не было, трафик, который Envoy отправляет наружу, тут же снова попадал бы в Envoy, и получилась бы петля. Поэтому прокси работает под отдельным пользователем 1337, и правило -m owner --uid-owner 1337 -j RETURN выпускает его напрямую.

Порты, которые полезно помнить:

Порт Назначение
15000 admin-интерфейс Envoy (/config_dump, /clusters, /stats) — главный инструмент отладки
15001 outbound capture (куда REDIRECT-ится исходящий трафик)
15006 inbound capture
15008 HBONE (ambient, туннель между ztunnel)
15020 istio-agent: агрегированные метрики, /healthz/ready, /quitquitquit
15021 health check для kubelet (/healthz/ready)
15090 Prometheus-эндпоинт Envoy
15012 istiod: xDS + CA (mTLS)

istio-init требует NET_ADMIN и NET_RAW — на кластерах с жёсткими Pod Security Standards или в OpenShift с restricted-v2 SCC (см. главу 47) это проблема. Поэтому есть альтернатива: Istio CNI plugin — DaemonSet, который выполняет ту же настройку iptables из привилегированного агента на узле в момент создания пода. Тогда сам под не требует повышенных привилегий и init-контейнера. Цена — CNI-плагин становится частью критического пути создания пода: если он не успел отработать, под может стартовать без перехвата (за это отвечает отдельный istio-validation init-контейнер, который проверяет, что правила на месте, и валится, если нет).

В ambient-режиме перехват делается без iptables в поде вообще — через eBPF или через правила в namespace узла, направляющие трафик пода в ztunnel.

7.2 Нативные sidecar-контейнеры

До Kubernetes 1.29 контейнеры в поде стартовали параллельно и останавливались параллельно. Для sidecar-прокси это порождало две тяжёлые проблемы.

Проблема старта. Приложение стартует раньше Envoy, при инициализации лезет в БД или дёргает другой сервис — а iptables уже перенаправляет трафик на порт 15001, где никто не слушает. Результат: Connection refused на старте, Spring-контекст падает, под уходит в CrashLoopBackOff, kubectl logs показывает загадочное «не смог подключиться к Kafka», хотя Kafka жива. Особенно больно для Job и CronJob.

Проблема остановки. При завершении пода Envoy получал SIGTERM одновременно с приложением и часто умирал первым. Приложение, дорабатывающее запросы в graceful shutdown, внезапно теряло сеть. Для Job было ещё хуже: приложение завершалось, Envoy продолжал работать, под никогда не переходил в Completed, Job висел вечно.

Обходные пути эпохи до 1.29:

  • holdApplicationUntilProxyStarts: true в конфигурации инжекции — Istio вставляет в Envoy postStart-хук, который блокирует запуск остальных контейнеров, пока прокси не готов;
  • EXIT_ON_ZERO_ACTIVE_CONNECTIONS=true — Envoy завершается, когда закрылись все активные соединения, а не сразу по SIGTERM;
  • для Job — curl -X POST localhost:15020/quitquitquit в конце скрипта.

Native sidecars = initContainers с restartPolicy: Always. Доступны по умолчанию с Kubernetes 1.29, GA (feature gate залочен) с 1.33 (kubernetes.io, Sidecar Containers). Семантика ровно та, что нужна:

  • стартуют до основных контейнеров, причём следующий init-контейнер ждёт прохождения startupProbe sidecar;
  • останавливаются после основных контейнеров, в обратном порядке объявления;
  • поддерживают readinessProbe и startupProbe (обычный init-контейнер не поддерживает ничего);
  • перезапускаются независимо, не считаются при определении завершённости Job.
YAML
apiVersion: apps/v1
kind: Deployment
metadata: { name: payments }
spec:
  template:
    spec:
      initContainers:
        - name: istio-proxy
          image: docker.io/istio/proxyv2:1.31.0
          restartPolicy: Always          # <- превращает init-контейнер в native sidecar
          startupProbe:
            httpGet: { path: /healthz/ready, port: 15021 }
            periodSeconds: 1
            failureThreshold: 30
      containers:
        - name: app
          image: registry.bank.example/payments:1.4.2

Istio внедряет прокси как native sidecar при включённой опции ENABLE_NATIVE_SIDECARS (в современных версиях — поведение по умолчанию на кластерах с поддержкой). Проверить, какой у вас режим, можно так:

Bash
kubectl get pod -l app=payments -o jsonpath='{.items[0].spec.initContainers[*].name}'
# если среди init-контейнеров есть istio-proxy — это native sidecar

⚠️ Осторожно. Даже с native sidecar остаётся окно на завершении: под уже исключён из EndpointSlice, но kube-proxy на других узлах ещё не обновил правила, и запросы продолжают приходить. Это не проблема mesh, это свойство Kubernetes (удаление из эндпоинтов и SIGTERM идут параллельно и без синхронизации — см. главу 47). Лечится preStop: sleep 5–15s на прикладном контейнере.

7.3 Накладные расходы sidecar

Честный подсчёт, который стоит держать в голове при разговоре о внедрении.

Память и CPU. Envoy — процесс на C++ с собственной конфигурацией. Запросы ресурсов по умолчанию у Istio для sidecar исторически 100m CPU / 128Mi memory с лимитами 2000m / 1024Mi. Реальное потребление сильно зависит от объёма конфигурации: прокси, который знает обо всех сервисах кластера, держит в памяти все listeners, clusters и endpoints. В кластере с 2000 сервисов это легко 300–500 МБ на каждый под. Вот арифметика, от которой становится неуютно: 1000 подов × 200 МБ = 200 ГБ RAM, потраченных на прокси. Это главный драйвер ambient-режима и главный аргумент за Sidecar-ресурс (§ 9.7), ограничивающий видимость.

Латентность. Каждый запрос между сервисами проходит два дополнительных прокси: исходящий sidecar клиента и входящий sidecar сервера. Порядок величин, который обычно называют, — единицы миллисекунд суммарно на p50 и заметно больше на хвостах p99. Для сервиса, чей собственный p50 — 200 мс, это шум; для сервиса с p50 в 2 мс (кеш, простой lookup) — удвоение латентности. ⚠️ Конкретные цифры сильно зависят от версии Istio, включённых фильтров, размера тела и CPU-квоты; публикуемые бенчмарки Istio по первичному источнику в рамках этой главы я не проверял, поэтому конкретные миллисекунды не привожу.

CPU throttling — недооценённая проблема. Если контейнеру прокси выставлен limits.cpu, cgroups применяет жёсткий throttling (см. главу 47), и под нагрузкой Envoy начинает «залипать» на границах периода CFS. Симптом: ровные ступеньки на графике p99, синхронные с всплесками container_cpu_cfs_throttled_seconds_total у контейнера istio-proxy, при том что средняя утилизация CPU — 20 %.

Сложность отладки. Трассировка стека приложения больше не покрывает весь путь запроса. «503» может прийти от sidecar клиента, sidecar сервера, самого сервера или ingress-gateway, и отличить их можно только по response flags (§ 15.2).

Операционная нагрузка. Обновление Istio — это перезапуск всех подов кластера (sidecar встроен в pod spec). Нужен процесс canary-апгрейда, ревизии, тестовые namespace. Нужен человек, который это умеет.

7.4 Режим ambient в Istio

Ambient — «sidecar-less» реализация Istio, построенная на разделении L4 и L7 (istio.io, Ambient Mode):

  • ztunnel — per-node прокси на Rust, «intentionally scoped to handle L3 and L4 functions such as mTLS, authentication, L4 authorization and telemetry». Он не разбирает HTTP-заголовки вообще. Трафик между ztunnel идёт по HBONE — туннелю на базе HTTP CONNECT поверх mTLS (порт 15008), внутри которого передаётся исходное TCP-соединение вместе с идентичностью источника.
  • waypoint proxy — обычный Envoy, развёрнутый как отдельный Deployment на namespace или на сервис, вне пода приложения. Включается только там, где нужны L7-функции: маршрутизация по заголовкам, веса, повторы, L7-авторизация.

Что это даёт:

Критерий Sidecar Ambient
Прокси на под 1 (Envoy, 100–500 МБ) 0
Прокси на узел — 1 ztunnel (Rust, существенно легче)
L7-функции всегда есть, всегда платите опционально, через waypoint
Включение mesh требует перезапуска пода метка на namespace, без рестарта
Обновление прокси перезапуск всех подов обновление DaemonSet
Изоляция сбоя прокси падает — падает один под ztunnel падает — страдает весь узел
Хопы L4-only 2 Envoy 2 ztunnel (легче)
Хопы с L7 2 Envoy 2 ztunnel + 1–2 waypoint

Главные выигрыши — память (прокси на узел вместо прокси на под) и отсутствие перезапуска при включении/обновлении mesh. Главный проигрыш — при полном L7-наборе путь запроса становится длиннее, и сбой ztunnel затрагивает весь узел.

Статус на сентябрь 2026. Ambient — полноценная часть текущей ветки 1.31 со своими руководствами по установке и апгрейду; ядро функциональности подаётся как готовое к продуктиву. Отдельные возможности всё ещё помечены Alpha: маршрутизация по claim'ам JWT, WebAssembly-расширения для waypoint, Lua-расширения (istio.io, Ambient Mode Overview, проверено 2026-09-21). Практический вывод: для L4 (mTLS + идентичность + базовая телеметрия) ambient — разумный выбор уже сейчас; если вам нужен весь L7-арсенал везде, вы всё равно развернёте waypoint, и преимущество по ресурсам частично съедается.

7.5 Другие варианты mesh без sidecar

gRPC proxyless. Клиент gRPC умеет сам быть xDS-клиентом: подключается к control plane, получает те же LDS/RDS/CDS/EDS и применяет маршрутизацию, балансировку и политики внутри процесса, без прокси. Нулевая латентность добавочного хопа, нулевая память сверх приложения. Ограничения серьёзные: только gRPC (HTTP/1.1 мимо), поддержка зависит от языка и версии grpc-библиотеки, набор поддерживаемых xDS-возможностей меньше, чем у Envoy, mTLS работает через отдельный механизм, и вы снова получаете «обновление политики = обновление библиотеки» для той части, которая не покрыта xDS. Это возврат к библиотечной модели с центральной конфигурацией.

Cilium Service Mesh. eBPF-программы в ядре берут на себя L4-часть (идентичность, политики, балансировка, шифрование через WireGuard или IPsec), а для L7 поднимается Envoy на узел, а не на под. Идея та же, что в ambient, но реализована на уровне CNI, что убирает один слой абстракции. Минус — Istio-совместимого набора CRD там нет (используется Gateway API и собственные ресурсы), и экосистема (Kiali, готовые дашборды, Flagger-интеграции) слабее.

8. Прокси Envoy

Словарь: Envoy

8.1 Envoy как стандарт data plane

Envoy — прокси от Lyft, ставший де-факто стандартом data plane. Причины: он написан под динамическую конфигурацию (не reload-конфига, а поток обновлений по gRPC), понимает HTTP/1.1, HTTP/2, HTTP/3 и gRPC нативно, имеет расширяемую цепочку фильтров и подробнейшую статистику. Istio, Consul Connect, Gloo, Contour, Ambassador, AWS App Mesh, Kuma — все используют Envoy как data plane; различаются они control plane.

8.2 Протоколы xDS

xDS — семейство API, по которым control plane отдаёт конфигурацию прокси. Основные:

API Раздаёт Аналогия
LDS (Listener Discovery) listeners — на каких адресах/портах слушать и какие цепочки фильтров применять «какие сокеты открыть»
RDS (Route Discovery) таблицы маршрутов HTTP: какой путь/заголовок → в какой cluster «роутинг»
CDS (Cluster Discovery) clusters — логические группы вышестоящих сервисов (upstream), политики LB, connection pool, outlier detection «куда можно ходить»
EDS (Endpoint Discovery) endpoints — конкретные IP:порт внутри cluster с весами и состоянием здоровья «живые адреса»
SDS (Secret Discovery) сертификаты и ключи «крипто»
ADS (Aggregated) всё перечисленное одним gRPC-стримом с гарантией порядка —

ADS важен не формально: без него можно получить рассинхрон — Envoy применил новый route, ссылающийся на cluster, который ещё не пришёл, и запросы падают с NC no_cluster_found. ADS гарантирует согласованный порядок обновлений в одном потоке.

Обновление без рестарта. Envoy применяет новые listeners и routes на лету: существующие соединения дорабатывают на старой конфигурации (draining), новые идут по новой. Это принципиальное отличие от nginx с его reload и от HAProxy старых версий.

8.3 Цепочка обработки запроса в Envoy

Эту цепочку надо уметь проговорить — на ней строится вся отладка mesh.

входящий пакет
   ↓
Listener            (адрес:порт; выбирается по destination IP:port)
   ↓  filter chain match (SNI, ALPN, source/destination CIDR, transport protocol)
Filter chain        (network filters: tls_inspector → http_connection_manager)
   ↓
HTTP Connection Manager (парсит HTTP, ведёт stream'ы, генерирует access-log)
   ↓  HTTP filter chain: jwt_authn → rbac → fault → router
Route configuration (virtual_hosts по :authority → routes по :path/headers)
   ↓
Cluster             (политики: LB, connection pool, circuit breaker, outlier detection, TLS)
   ↓
Endpoint            (конкретный IP:порт)

Что из этого следует практически:

  • Если запрос не доходит — отказ произошёл на одном из этих уровней, и у каждого свой диагностический признак. Нет listener → соединение вообще не принято. Нет маршрута в route config → 404 с флагом NR. Нет cluster → 503 NC. Cluster есть, эндпоинтов нет → 503 UH no_healthy_upstream. Эндпоинты есть, соединиться не смог → 503 UF/UC.
  • Порядок HTTP-фильтров имеет значение: jwt_authn до rbac, иначе RBAC не увидит claims; fault до router, иначе внедрять сбой некуда.
  • Istio-CRD — это генератор этой конфигурации: VirtualService → RDS, DestinationRule → CDS, Gateway → LDS, ServiceEntry → CDS+EDS, AuthorizationPolicy → HTTP-фильтр rbac, PeerAuthentication → transport socket и listener filter chain match.

8.4 Admin-интерфейс Envoy

Envoy слушает admin на localhost:15000 внутри пода. Это единственный источник истины о том, что прокси реально знает, в отличие от того, что вы ему написали в YAML.

Bash
POD=$(kubectl get pod -l app=orders -o jsonpath='{.items[0].metadata.name}')

# полный дамп конфигурации (десятки тысяч строк — грепайте)
kubectl exec $POD -c istio-proxy -- curl -s localhost:15000/config_dump > dump.json

# только clusters и состояние их эндпоинтов (health, outlier ejection)
kubectl exec $POD -c istio-proxy -- curl -s localhost:15000/clusters | grep payments

# статистика: ретраи, таймауты, circuit breaking, коды ответов
kubectl exec $POD -c istio-proxy -- curl -s localhost:15000/stats | grep -E 'payments.*(upstream_rq_retry|pending_overflow|timeout|5xx)'

# какие сертификаты загружены и когда истекают
kubectl exec $POD -c istio-proxy -- curl -s localhost:15000/certs

# поднять уровень логирования конкретных подсистем на лету
kubectl exec $POD -c istio-proxy -- curl -s -X POST \
  'localhost:15000/logging?router=debug&connection=debug&upstream=debug'

# сбросить статистику перед экспериментом
kubectl exec $POD -c istio-proxy -- curl -s -X POST localhost:15000/reset_counters

Счётчик Значение

upstream_rq_retry_limit_exceeded исчерпан лимит попыток
upstream_rq_retry_overflow повтор не сделан из-за retry budget / circuit breaker
upstream_rq_pending_overflow сработал circuit breaker по http1MaxPendingRequests
upstream_cx_overflow сработал circuit breaker по maxConnections
upstream_rq_timeout таймаут запроса

8.5 Outlier detection и circuit breaker

Это любимый вопрос-ловушка, потому что термины перепутаны в индустрии.

Outlier detection у Envoy — это пассивный health checking. Прокси не шлёт специальных проб; он смотрит на реальный трафик и, если конкретный эндпоинт начинает вести себя хуже остальных, временно исключает его из пула балансировки. Типы детекции (envoyproxy.io, Outlier detection):

  1. Consecutive 5xx — N подряд идущих 5xx или локальных сбоев;
  2. Consecutive gateway failure — только 502/503/504;
  3. Consecutive local origin failure — таймауты и TCP-reset, отдельно от ответов сервера (при split_external_local_origin_errors);
  4. Success rate — статистика: хост, чей success rate заметно ниже среднего по кластеру;
  5. Failure percentage — доля отказов выше абсолютного порога, без сравнения со средним;
  6. Degraded — хост, вернувший заголовок x-envoy-degraded, деприоритизируется (не исключается).

Время исключения растёт: «base_ejection_time multiplied by the number of times the host has been ejected in a row», с потолком max_ejection_time. То есть флапающий под наказывается всё сильнее.

Значения по умолчанию в терминах Istio DestinationRule (istio.io, DestinationRule): consecutive5xxErrors: 5, interval: 10s, baseEjectionTime: 30s, maxEjectionPercent: 50%, minHealthPercent: 50%.

Circuit breaker в Envoy — это другое. Это лимиты ресурсов на кластер: максимум соединений (maxConnections), максимум ожидающих запросов (http1MaxPendingRequests), максимум параллельных запросов (http2MaxRequests), максимум параллельных повторов. При превышении запрос немедленно отбивается с 503 и флагом UO upstream_overflow — без попытки соединиться. Это load shedding, а не «состояния OPEN/HALF_OPEN/CLOSED».

Сравнение с Resilience4j (подробно — глава 35):

Критерий Envoy outlier detection Envoy circuit breaker Resilience4j CircuitBreaker
Гранулярность эндпоинт (под) cluster (сервис) вызов метода / экземпляр клиента
Что измеряет коды ответов и локальные сбои по хосту занятость ресурсов сейчас скользящее окно вызовов
Реакция исключить под из LB на время отбить запрос сразу (UO) открыть цепь, вызвать fallback
Состояния ejected / not ejected, время растёт нет состояний, порог CLOSED / OPEN / HALF_OPEN
Знает про fallback нет нет да
Знает про исключения Java нет нет да (recordExceptions)

Ключевое: outlier detection умеет то, чего Resilience4j не умеет в принципе — отличить один больной под от здорового сервиса. Resilience4j в вашем приложении видит «сервис payments отвечает ошибками 30 % времени» и открывает цепь на весь сервис; Envoy видит «под payments-7f9d-x отвечает ошибками, остальные четыре в порядке» и просто перестаёт в него ходить. При этом Resilience4j умеет то, чего не умеет Envoy: вызвать ваш fallback и отличить PaymentDeclinedException от SocketTimeoutException.

💡 На интервью. «Что такое outlier detection?» — «Пассивный health checking в Envoy: прокси не шлёт отдельных проб, а анализирует реальные ответы и временно выкидывает из балансировки конкретный эндпоинт, который отвечает 5xx подряд или хуже среднего по кластеру. В Istio значения по умолчанию — 5 последовательных 5xx, интервал сканирования 10 секунд, базовое исключение 30 секунд и не более половины эндпоинтов. От circuit breaker он отличается гранулярностью: outlier работает на уровне пода, а circuit breaker в Envoy — это лимиты соединений и запросов на весь кластер, при превышении которых запрос отбивается флагом UO.»

8.6 Повторные попытки в Envoy

Политика повторов настраивается на маршруте: число попыток, таймаут одной попытки, условия повтора (retryOn), а также retry budget — ограничение доли параллельных повторов от общего числа активных запросов. Последнее критично: без бюджета повторы в момент деградации умножают нагрузку и добивают сервис (retry storm — см. главу 35).

Условия retryOn в терминах Istio: 5xx, gateway-error (502/503/504), connect-failure, refused-stream, retriable-4xx (по умолчанию только 409), reset (разрыв без ответа), retriable-status-codes, retriable-headers, а для gRPC — cancelled, deadline-exceeded, internal, resource-exhausted, unavailable.

Значение по умолчанию Istio, о котором надо знать: если политика повторов не задана явно, действует cluster-wide default — attempts: 2, retryOn: connect-failure,refused-stream,unavailable,cancelled (istio.io, VirtualService). То есть повторы в вашем mesh уже включены, даже если вы их не настраивали. Именно отсюда берутся двойные повторы (§ 12.2).

Обратите внимание на выбранный набор условий: он консервативный и в основном покрывает случаи, когда запрос гарантированно не дошёл до приложения (connect-failure, refused-stream). Это единственные безопасные для неидемпотентных операций повторы. Добавляя 5xx или gateway-error, вы берёте на себя риск повторить уже обработанный запрос.

8.7 Локальное и глобальное ограничение частоты

Local rate limit — токен-бакет внутри каждого экземпляра Envoy. Дёшево, без внешних зависимостей, но лимит фактически умножается на число подов: «100 rps» при 10 репликах превращается в 1000 rps на сервис.

Global rate limit — Envoy на каждый запрос дёргает внешний сервис (RLS) по gRPC, тот держит счётчики в Redis и отвечает OVER_LIMIT/OK. Точный общий лимит ценой сетевого вызова на каждый запрос и нового SPOF (обычно настраивается failure_mode_deny: false, чтобы недоступность RLS не роняла трафик).

Отказ по локальному лимиту виден в логах как флаг RL, по глобальному при ошибке RLS — RLSE.

8.8 Алгоритмы балансировки в Envoy

Алгоритм Механизм Применение
ROUND_ROBIN по кругу значение по умолчанию; документация Istio отмечает, что «generally unsafe» без health checking
LEAST_REQUEST из двух случайных выбрать менее загруженный (power of two choices) разброс времени обработки; почти всегда лучше RR
RANDOM случайный здоровый когда нет health checking и нужен простой равномерный разброс
ringHash consistent hashing по ключу; minimumRingSize по умолчанию 1024 липкость сессии/кеша к поду; при изменении пула переезжает минимум ключей
maglev таблица Google Maglev, размер по умолчанию 65537 то же, что ringHash, но быстрее лукап и лучше равномерность
PASSTHROUGH без балансировки, на исходный IP headless/специальные случаи

LEAST_REQUEST в Envoy — не «пройти весь список и выбрать минимум», а P2C: взять два случайных эндпоинта и отдать запрос тому, у кого меньше активных запросов. Это O(1) и при этом даёт распределение, близкое к оптимальному, — классический результат теории «power of two random choices».

Zone-aware routing (topology-aware) — предпочитать эндпоинты в той же зоне доступности, что и клиент, пока их достаточно здоровых. Экономит cross-AZ трафик (в облаке это деньги) и десятки миллисекунд латентности. Envoy автоматически переливает часть трафика в другие зоны, если локальных эндпоинтов не хватает, чтобы не перегрузить их.

Mirroring (shadowing) — копия трафика отправляется на второй кластер, ответ игнорируется и не влияет на клиента. Envoy добавляет к Host/:authority суффикс -shadow, чтобы зеркальный сервис мог отличить теневой запрос. Применение: проверить новую версию на реальном трафике без риска. Смертельная ловушка: если зеркальный сервис пишет в ту же базу, вы получите двойные записи. Зеркалировать можно только то, что не имеет побочных эффектов, либо с отдельной БД.

9.2 Sidecar injection

Инжекция делается mutating admission webhook'ом istiod при создании пода. Включается меткой на namespace:

Bash
kubectl label namespace payments istio-injection=enabled

Важно: метка влияет только на вновь создаваемые поды. Существующие надо перезапустить (kubectl rollout restart deployment -n payments). Это отдельная строка в плане внедрения — «перезапустить всё».

Точечное управление аннотациями на поде:

YAML
spec:
  template:
    metadata:
      labels:
        sidecar.istio.io/inject: "false"        # не инжектировать этот под
      annotations:
        sidecar.istio.io/proxyCPU: "50m"
        sidecar.istio.io/proxyMemory: "192Mi"
        proxy.istio.io/config: |
          holdApplicationUntilProxyStarts: true
          terminationDrainDuration: 30s
        traffic.sidecar.istio.io/excludeOutboundPorts: "5432"   # PostgreSQL мимо прокси
        traffic.sidecar.istio.io/excludeOutboundIPRanges: "10.20.30.0/24"

Кандидаты на исключение из mesh: соединения к БД (JDBC — не HTTP, mesh даёт мало, а риск сломать TLS высок), высокочастотные бинарные протоколы, поды с host network.

Revision-based upgrade и canary-апгрейд самого Istio. Обновление control plane — рискованная операция, потому что затрагивает весь трафик. Ревизии позволяют держать две версии istiod одновременно:

Bash
# ставим новую ревизию рядом со старой
istioctl install --set revision=1-31-0 --set profile=default -y

# переводим один namespace на новую ревизию
kubectl label ns payments istio.io/rev=1-31-0 --overwrite
kubectl label ns payments istio-injection-              # снимаем старую метку
kubectl rollout restart deployment -n payments

# убедились, что всё хорошо — переводим остальные, затем удаляем старую ревизию
istioctl uninstall --revision 1-30-2 -y

Дополнительно есть revision tags — именованный псевдоним (prod-stable), на который указывают namespace; переключение тега на новую ревизию меняет целевую версию без правки меток на всех namespace.

⚠️ Осторожно. Забытая метка istio-injection=enabled на старом namespace плюс переход на ревизии = в поды продолжает внедряться прокси старой ревизии, которую вы уже удалили → при следующем рестарте пода webhook не отвечает, и под не создаётся вовсе (если failurePolicy: Fail). Проверяйте kubectl get ns -L istio-injection -L istio.io/rev перед удалением ревизии.

9.3 Gateway: входной шлюз mesh

Gateway описывает L4/L6-часть: на каком порту слушать, какой протокол, какой хост, какой сертификат. Он не задаёт маршрутизацию — это делает привязанный VirtualService.

YAML
apiVersion: networking.istio.io/v1
kind: Gateway
metadata:
  name: bank-gateway
  namespace: istio-system
spec:
  selector:
    istio: ingressgateway          # какие поды gateway реализуют этот объект
  servers:
    - port: { number: 443, name: https, protocol: HTTPS }
      hosts: ["api.bank.example"]
      tls:
        mode: SIMPLE
        credentialName: bank-tls   # Secret типа kubernetes.io/tls в namespace gateway
    - port: { number: 80, name: http, protocol: HTTP }
      hosts: ["api.bank.example"]
      tls:
        httpsRedirect: true        # 301 на HTTPS

credentialName ссылается на Secret в namespace самого gateway-пода (обычно istio-system), а не там, где лежит Gateway-объект, — типовая причина «сертификат не подхватился». Режимы TLS: SIMPLE (обычный TLS), MUTUAL (требовать клиентский сертификат), PASSTHROUGH (не терминировать, маршрутизировать по SNI), ISTIO_MUTUAL (внутренний mTLS mesh).

9.4 Маршрутизация через VirtualService

VirtualService — главный объект маршрутизации в Istio: он описывает, на какие версии сервиса и по каким правилам уходят запросы к хосту, и именно в нём задают повторы, таймауты, разбиение трафика и внедрение сбоев. Ниже ключевые свойства объекта в том виде, как их фиксирует справочник Istio (reference):

  • gateways по умолчанию = mesh — то есть правило применяется ко всем sidecar. Если нужен и внешний трафик, и внутренний, перечисляйте оба: gateways: [bank-gateway, mesh];
  • правила http упорядочены, применяется первое совпавшее — порядок критичен;
  • внутри одного блока match условия комбинируются по AND, разные блоки match — OR;
  • timeout по умолчанию выключен;
  • fault при включении отключает таймауты и повторы на этом маршруте.

Маршрутизация по заголовку (dark launch для внутренних тестировщиков) плюс веса:

YAML
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: payments
  namespace: payments
spec:
  hosts: ["payments.payments.svc.cluster.local", "api.bank.example"]
  gateways: ["istio-system/bank-gateway", "mesh"]
  http:
    # 1. внутренние тестировщики принудительно на v2
    - match:
        - headers:
            x-canary-user: { exact: "true" }
      route:
        - destination: { host: payments, subset: v2 }
      timeout: 5s

    # 2. административный путь — только на стабильную версию, с длинным таймаутом
    - match:
        - uri: { prefix: /v1/payments/reconciliation }
      route:
        - destination: { host: payments, subset: v1 }
      timeout: 120s
      retries: { attempts: 0 }          # длинный отчёт не повторяем

    # 3. остальное — 95/5
    - route:
        - destination: { host: payments, subset: v1 }
          weight: 95
        - destination: { host: payments, subset: v2 }
          weight: 5
      timeout: 3s
      retries:
        attempts: 2
        perTryTimeout: 1s
        retryOn: connect-failure,refused-stream,gateway-error
        retryRemoteLocalities: false

Заметьте арифметику таймаутов: timeout: 3s — это общий бюджет на все попытки, а perTryTimeout: 1s × attempts: 2 плюс исходная попытка даёт максимум 3 с. Если поставить perTryTimeout: 2s при attempts: 3, общий таймаут 3 с обрежет процесс на середине второй попытки — и вы получите не то поведение, которое ожидали. Правило: timeout ≥ perTryTimeout × (attempts + 1) плюс запас на backoff.

Fault injection — искусственные отказы для проверки устойчивости без изменения кода:

YAML
    - match:
        - headers:
            x-chaos: { exact: "delay" }
      fault:
        delay:
          percentage: { value: 100 }
          fixedDelay: 7s
      route:
        - destination: { host: payments, subset: v1 }
---
# или процент ошибок для всего трафика в тестовом контуре
      fault:
        abort:
          percentage: { value: 10 }
          httpStatus: 503

Комбинация delay с заголовком-переключателем — самый дешёвый способ проверить, что ваши Resilience4j-таймауты и fallback реально работают: включили задержку, увидели, что клиент отвалился по своему таймауту и отдал деградированный ответ, выключили. Для gRPC вместо httpStatus используется grpcStatus.

Mirroring:

YAML
    - route:
        - destination: { host: payments, subset: v1 }
      mirror: { host: payments, subset: v2 }
      mirrorPercentage: { value: 5 }     # по умолчанию 100 %

9.5 DestinationRule: политики для получателя

VirtualService решает «куда», DestinationRule — «как туда ходить». Он же объявляет subsets — именованные группы подов по меткам, на которые ссылается VirtualService.

YAML
apiVersion: networking.istio.io/v1
kind: DestinationRule
metadata:
  name: payments
  namespace: payments
spec:
  host: payments.payments.svc.cluster.local
  trafficPolicy:
    tls: { mode: ISTIO_MUTUAL }
    loadBalancer:
      simple: LEAST_REQUEST
    connectionPool:
      tcp:
        maxConnections: 200              # дефолт 2^32-1, то есть без лимита
        connectTimeout: 2s               # минимум 10s по дефолту документации
        tcpKeepalive: { time: 60s, interval: 10s, probes: 3 }
      http:
        http1MaxPendingRequests: 100     # дефолт 2^32-1
        http2MaxRequests: 500            # дефолт 2^32-1
        maxRequestsPerConnection: 0      # 0 = без лимита (дефолт)
        idleTimeout: 60s                 # дефолт 1 час
        h2UpgradePolicy: UPGRADE
    outlierDetection:
      consecutive5xxErrors: 5            # дефолт 5
      interval: 10s                      # дефолт 10s
      baseEjectionTime: 30s              # дефолт 30s
      maxEjectionPercent: 50             # дефолт 50
      minHealthPercent: 50               # дефолт 50
  subsets:
    - name: v1
      labels: { version: v1 }
    - name: v2
      labels: { version: v2 }
      trafficPolicy:                     # переопределение только для v2
        connectionPool:
          http: { http2MaxRequests: 50 }

Значения по умолчанию соединений — «без лимита», и это осознанный выбор Istio: не ломать существующий трафик при включении mesh. Но это значит, что circuit breaking у вас выключен, пока вы его явно не настроите. Если хотите защиты от перегрузки — задавайте maxConnections и http2MaxRequests осмысленно (обычно на основе измеренной пропускной способности сервиса и числа реплик).

Липкая балансировка по пользователю (например, чтобы попадать в локальный кеш пода):

YAML
    loadBalancer:
      consistentHash:
        httpHeaderName: x-user-id
        # либо: httpCookie: { name: session, ttl: 3600s }
        # либо: useSourceIp: true
        # либо: maglev: { tableSize: 65537 }

ringHash по умолчанию строит кольцо минимум из 1024 виртуальных узлов; maglev — таблицу на 65537 записей и работает быстрее при большом числе эндпоинтов.

⚠️ Осторожно. DestinationRule с subsets есть, но VirtualService на него не ссылается — трафик идёт мимо subsets, на все поды сразу, и канарейка не работает, хотя объекты «применились». И наоборот: VirtualService ссылается на subset, которого нет в DestinationRule → 503 NC no_cluster_found. Проверка — istioctl analyze.

9.6 ServiceEntry: внешние сервисы

Всё, чего нет в реестре Kubernetes, для mesh не существует. По умолчанию Istio настроен разрешать исходящий трафик наружу (outboundTrafficPolicy.mode: ALLOW_ANY), но такой трафик идёт через passthrough-кластер: без телеметрии по хостам, без политик, без TLS-оригинации.

YAML
apiVersion: networking.istio.io/v1
kind: ServiceEntry
metadata:
  name: partner-bank-api
  namespace: payments
spec:
  hosts: ["api.partner-bank.com"]
  ports:
    - { number: 443, name: https, protocol: HTTPS }
  resolution: DNS
  location: MESH_EXTERNAL
---
apiVersion: networking.istio.io/v1
kind: DestinationRule
metadata: { name: partner-bank-api, namespace: payments }
spec:
  host: api.partner-bank.com
  trafficPolicy:
    connectionPool:
      tcp: { maxConnections: 50, connectTimeout: 3s }
    outlierDetection:
      consecutive5xxErrors: 3
      baseEjectionTime: 60s

После этого партнёрский API появляется в метриках и в Kiali как отдельный узел, к нему применяются таймауты и circuit breaking, а VirtualService может добавить повторы.

TLS origination — приложение ходит по HTTP на localhost-подобный внутренний адрес, а прокси сам устанавливает TLS наружу. Полезно, когда не хочется тащить truststore в приложение:

YAML
spec:
  host: api.partner-bank.com
  trafficPolicy:
    portLevelSettings:
      - port: { number: 80 }
        tls:
          mode: SIMPLE
          sni: api.partner-bank.com
          caCertificates: /etc/certs/partner-ca.pem

Для жёсткого контроля выхода ставят outboundTrafficPolicy.mode: REGISTRY_ONLY — всё, что не описано ServiceEntry, блокируется (502 с флагом, в логах Envoy — BlackHoleCluster). Это сильная мера безопасности (предотвращает exfiltration и SSRF в известные плохие адреса), но требует дисциплины: каждый новый внешний хост — новый объект.

Схема egress-gateway целиком:

YAML
apiVersion: networking.istio.io/v1
kind: Gateway
metadata: { name: egress, namespace: istio-system }
spec:
  selector: { istio: egressgateway }
  servers:
    - port: { number: 443, name: tls, protocol: TLS }
      hosts: ["api.partner-bank.com"]
      tls: { mode: PASSTHROUGH }
---
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata: { name: partner-via-egress, namespace: payments }
spec:
  hosts: ["api.partner-bank.com"]
  gateways: [mesh, istio-system/egress]
  tls:
    - match: [{ port: 443, sniHosts: ["api.partner-bank.com"], gateways: [mesh] }]
      route:
        - destination:
            host: istio-egressgateway.istio-system.svc.cluster.local
            port: { number: 443 }
    - match: [{ port: 443, sniHosts: ["api.partner-bank.com"], gateways: [istio-system/egress] }]
      route:
        - destination: { host: api.partner-bank.com, port: { number: 443 } }

Egress-gateway даёт партнёру предсказуемый IP (это IP подов gateway или их NAT), а вам — единую точку логирования и политик для внешнего трафика.

9.7 Ресурс Sidecar и ограничение видимости

По умолчанию istiod рассылает каждому прокси конфигурацию всех сервисов кластера. Прокси сервиса payments, который ходит в три места, знает о двух тысячах кластеров и десятках тысяч эндпоинтов. Это и есть та самая память по 300–500 МБ на под.

Ресурс Sidecar режет видимость:

YAML
apiVersion: networking.istio.io/v1
kind: Sidecar
metadata:
  name: default
  namespace: payments
spec:
  egress:
    - hosts:
        - "./*"                          # всё в своём namespace
        - "istio-system/*"               # gateway'и и control plane
        - "kafka/kafka-bootstrap.kafka.svc.cluster.local"
        - "accounts/accounts.accounts.svc.cluster.local"
  outboundTrafficPolicy:
    mode: REGISTRY_ONLY

Эффект на больших кластерах — кратное снижение памяти прокси и объёма xDS-трафика, плюс заметно более быстрая сходимость конфигурации. Есть и глобальный рычаг: PILOT_ENABLE_SIDECAR_SCOPING / discoverySelectors в MeshConfig, ограничивающие набор namespace, за которыми istiod вообще следит.

⚠️ Осторожно. Sidecar с REGISTRY_ONLY и забытым хостом — сервис внезапно перестаёт ходить туда, куда ходил. Симптом: 503 c флагом, в istioctl proxy-config clusters нужного кластера нет. Внедрять только после инвентаризации исходящих зависимостей (её удобно снять из метрик istio_requests_total по destination_service).

10. Istio: безопасность

10.1 Идентичность и mTLS

Каждой рабочей нагрузке mesh выдаёт криптографическую идентичность в формате SPIFFE — URI вида spiffe://<trust domain>/<workload identifier> (spiffe.io). В Istio это:

spiffe://cluster.local/ns/payments/sa/payments-sa

Идентичность привязана к ServiceAccount, а не к поду, namespace или IP. Это принципиально: политики пишутся в терминах «сервис-аккаунт orders-sa может звать», и это не ломается при пересоздании подов и не подделывается подменой IP.

Как выдаётся сертификат (istio.io, Security):

  1. istio-agent внутри пода генерирует приватный ключ и CSR;
  2. агент прикладывает к запросу токен ServiceAccount пода и шлёт в CA внутри istiod;
  3. CA проверяет учётные данные (проверяет токен через TokenReview API), извлекает идентичность и подписывает CSR;
  4. Envoy получает сертификат и ключ через SDS — по Unix-сокету от агента, не через диск и не через Kubernetes Secret;
  5. агент следит за истечением и повторяет цикл.

Последний пункт заслуживает внимания: приватный ключ рабочей нагрузки никогда не покидает под и не записывается на диск. Нет Secret, который можно прочитать через API, нет файла, который утечёт в бэкап. Сертификаты живут часами (по умолчанию порядка 24 часов, обновляются заметно раньше истечения) — украденный сертификат быстро протухает.

Корневой CA istiod по умолчанию self-signed. В банке это редко подходит: обычно подключают промежуточный CA от корпоративного PKI (Secret cacerts с ca-cert.pem, ca-key.pem, root-cert.pem, cert-chain.pem) или внешний SPIRE / Vault PKI. Детали X.509 и цепочек — глава 41.

Словарь: SPIFFE

10.2 PeerAuthentication и переход на режим STRICT

YAML
apiVersion: security.istio.io/v1
kind: PeerAuthentication
metadata:
  name: default
  namespace: istio-system     # в root namespace = на весь mesh
spec:
  mtls:
    mode: PERMISSIVE

Режимы: STRICT — только mTLS; PERMISSIVE — принимаются и mTLS, и plaintext; DISABLE — mTLS выключен.

PERMISSIVE — это механизм миграции, а не постоянное состояние. Он существует, потому что включить STRICT сразу на живом кластере — это гарантированная авария: любой под без sidecar (мониторинг, legacy, Job, под из другого namespace) мгновенно теряет доступ.

Порядок миграции, который работает:

  1. Включить PERMISSIVE глобально. Трафик не меняется.
  2. Внедрить sidecar во все namespace, перезапустить нагрузки.
  3. Измерить, сколько трафика идёт в plaintext. Метрика Istio различает это через метку connection_security_policy:
    PromQL
    sum by (destination_workload, destination_workload_namespace) (
  rate(istio_requests_total{connection_security_policy!="mutual_tls",
                            reporter="destination"}[5m])
)
    Пока эта сумма не нулевая — включать STRICT нельзя.
  4. Разобраться с остатками: обычно это Prometheus (скребёт /metrics напрямую), kubelet-пробы (идут с узла, не от пода — Istio их специально пропускает через перезапись проб), контроллеры без sidecar.
  5. Включить STRICT по namespace, начиная с наименее критичных:
    YAML
    apiVersion: security.istio.io/v1
kind: PeerAuthentication
metadata: { name: default, namespace: payments }
spec:
  mtls: { mode: STRICT }
  6. Только когда все namespace прошли — переключить корневую политику.

Гранулярность бывает нужна и на уровне порта:

YAML
spec:
  selector:
    matchLabels: { app: payments }
  mtls: { mode: STRICT }
  portLevelMtls:
    "8081": { mode: PERMISSIVE }   # actuator для Prometheus без sidecar

⚠️ Осторожно. Классическая ошибка — включить STRICT и забыть, что база данных или Kafka вне mesh. mTLS применяется только к входящему трафику меш-подов, так что исходящий к внешним системам не ломается; но если вы заодно включили ISTIO_MUTUAL в DestinationRule для хоста без sidecar — получите 503 UF upstream_connect_error со стороны клиента и ничего в логах сервера. Это симптом № 1 «mTLS mismatch».

10.3 AuthorizationPolicy

Правила «кто с кем может говорить». Порядок оценки строго определён: CUSTOM → DENY → ALLOW, и «deny policies take precedence over allow policies» (istio.io, Security). Плюс есть AUDIT — не блокирует, только помечает.

Ключевое поведение, которое путают: если на рабочую нагрузку есть хотя бы одна ALLOW-политика, всё, что не разрешено явно, запрещено. Если ALLOW-политик нет вовсе — разрешено всё (кроме явных DENY). Отсюда идиома default-deny:

YAML
apiVersion: security.istio.io/v1
kind: AuthorizationPolicy
metadata:
  name: deny-all
  namespace: payments
spec: {}          # пустой spec = ALLOW с пустыми rules = не разрешено ничего

Дальше — точечные разрешения по идентичности:

YAML
apiVersion: security.istio.io/v1
kind: AuthorizationPolicy
metadata:
  name: payments-access
  namespace: payments
spec:
  selector:
    matchLabels: { app: payments }
  action: ALLOW
  rules:
    # 1. сервис заказов может создавать и читать платежи
    - from:
        - source:
            principals: ["cluster.local/ns/orders/sa/orders-sa"]
      to:
        - operation:
            methods: ["POST", "GET"]
            paths: ["/v1/payments", "/v1/payments/*"]

    # 2. бэкофис может читать всё, но только из своего namespace
    - from:
        - source:
            namespaces: ["backoffice"]
      to:
        - operation:
            methods: ["GET"]

    # 3. ingress-gateway пускаем на публичные пути
    - from:
        - source:
            principals: ["cluster.local/ns/istio-system/sa/istio-ingressgateway-service-account"]
      to:
        - operation:
            paths: ["/v1/public/*"]

    # 4. health-эндпоинты без ограничений (иначе сломаются пробы)
    - to:
        - operation:
            paths: ["/actuator/health/*", "/healthz"]
---
# явный запрет: никто не ходит в админский путь снаружи
apiVersion: security.istio.io/v1
kind: AuthorizationPolicy
metadata: { name: deny-admin-external, namespace: payments }
spec:
  selector:
    matchLabels: { app: payments }
  action: DENY
  rules:
    - from:
        - source:
            notNamespaces: ["payments", "backoffice"]
      to:
        - operation:
            paths: ["/internal/*"]

Внутри одного rule условия from, to и when комбинируются по AND; элементы внутри списков — по OR; несколько rules — по OR.

Закрывается и не закрывается. AuthorizationPolicy закрывает вопрос «кто с кем может говорить» на уровне сервисов, HTTP-методов и путей — то есть латеральное перемещение внутри кластера. Скомпрометированный под сервиса отчётов не сможет дёрнуть POST /v1/payments, даже зная URL, потому что у него другая криптографическая идентичность. Это очень много.

Но он не отвечает на вопрос «имеет ли пользователь Иванов право видеть счёт № 40817...». Объектная и строковая авторизация остаётся в приложении: Spring Security с @PreAuthorize, проверки владения, row-level security (глава 13, 13-spring-security.md). Формулировка, которая хорошо звучит на интервью: mesh делает авторизацию между сервисами, приложение — авторизацию внутри домена данных.

Ещё одна причина не выбрасывать проверки из приложения — defence in depth. Sidecar можно случайно не заинжектить (namespace без метки, под с sidecar.istio.io/inject: "false"), и тогда AuthorizationPolicy просто не применяется: её обеспечивает прокси, а его нет. Никакого «fail closed» здесь не происходит.

10.4 RequestAuthentication: проверка JWT в mesh

YAML
apiVersion: security.istio.io/v1
kind: RequestAuthentication
metadata:
  name: jwt-keycloak
  namespace: payments
spec:
  selector:
    matchLabels: { app: payments }
  jwtRules:
    - issuer: "https://sso.bank.example/realms/retail"
      jwksUri: "https://sso.bank.example/realms/retail/protocol/openid-connect/certs"
      audiences: ["payments-api"]
      forwardOriginalToken: true          # пробросить токен приложению
      outputClaimToHeaders:
        - header: x-auth-subject
          claim: sub

Критически важная деталь: RequestAuthentication сам по себе ничего не требует. Он проверяет токен, если тот присутствует: некорректный токен → 401, отсутствующий токен → запрос проходит как анонимный. Чтобы потребовать токен, нужна отдельная AuthorizationPolicy:

YAML
apiVersion: security.istio.io/v1
kind: AuthorizationPolicy
metadata: { name: require-jwt, namespace: payments }
spec:
  selector:
    matchLabels: { app: payments }
  action: ALLOW
  rules:
    - from:
        - source:
            requestPrincipals: ["https://sso.bank.example/realms/retail/*"]
      to:
        - operation: { paths: ["/v1/*"] }
      when:
        - key: request.auth.claims[scope]
          values: ["payments:write"]

requestPrincipals: ["*"] означает «любой корректный JWT»; формат значения — <issuer>/<subject>.

Сочетание со Spring Security. Два жизнеспособных варианта.

Вариант A — mesh проверяет подпись, приложение доверяет. На границе (ingress-gateway) RequestAuthentication проверяет подпись, issuer, audience и срок; приложение получает токен и читает claims без повторной проверки подписи. Плюс: приложение не ходит за JWKS, меньше латентность и меньше кода. Минус: если sidecar не заинжектился или кто-то обратился к поду напрямую внутри кластера, проверки нет вообще. Применимо только вместе с жёсткой AuthorizationPolicy, гарантирующей, что в под приходит трафик только от gateway.

Вариант B — проверяют оба. Mesh отсекает мусор на границе (дешёвая защита от токен-флуда и гарантия, что до приложения не доедут заведомо битые токены), Spring Security Resource Server проверяет подпись ещё раз и выполняет @PreAuthorize по ролям и объектам. Это дороже на несколько сотен микросекунд и настоятельно предпочтительнее в финтехе. Настройка Spring — глава 13 и глава 42 (42-appsec-oauth-keycloak.md):

YAML
spring:
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: https://sso.bank.example/realms/retail
          audiences: payments-api

Рабочее правило: mesh — периметр и грубый фильтр, приложение — источник истины по правам. Проверка подписи в двух местах не является избыточной работой в смысле безопасности; это ровно defence in depth.

11. Istio: наблюдаемость и progressive delivery

11.1 Стандартные метрики Envoy

Как только под попал в mesh, Envoy начинает экспортировать стандартный набор метрик на :15090/stats/prometheus (агрегированно — на :15020/stats/prometheus). Основные:

Метрика Тип Польза
istio_requests_total counter RPS и коды ответов по паре «источник → назначение»
istio_request_duration_milliseconds histogram латентность, бакеты для квантилей
istio_request_bytes / istio_response_bytes histogram размеры
istio_tcp_sent_bytes_total / received counter не-HTTP трафик
istio_tcp_connections_opened_total / closed counter соединения

Ключевые метки: source_workload, source_workload_namespace, source_principal, destination_service, destination_workload, destination_version, request_protocol, response_code, response_flags, connection_security_policy, reporter.

Два метки заслуживают отдельного внимания:

  • reporter = source или destination. Одна и та же пара запросов учитывается дважды — прокси клиента и прокси сервера. При построении дашбордов это надо фильтровать, иначе RPS удваивается. Расхождение между ними само по себе диагностично: если reporter="source" показывает 5xx, а reporter="destination" их не видит, значит ошибку сгенерировал прокси клиента, до сервера запрос не дошёл.
  • response_flags — те самые флаги Envoy (§ 15.2), доступные прямо в Prometheus. Это делает возможным оповещение вида «растёт доля UO» (сработал circuit breaker) или «появились UH» (нет здоровых эндпоинтов) — на порядок точнее, чем просто «растут 503».

Пример полезных запросов:

PromQL
# error rate по сервису, глазами сервера
sum by (destination_workload) (
  rate(istio_requests_total{reporter="destination", response_code=~"5.."}[5m])
)
/
sum by (destination_workload) (rate(istio_requests_total{reporter="destination"}[5m]))

# p99 латентности вызова orders -> payments
histogram_quantile(0.99, sum by (le) (
  rate(istio_request_duration_milliseconds_bucket{
    reporter="source", source_workload="orders", destination_service=~"payments.*"}[5m])
))

# доля запросов, отбитых circuit breaker'ом
sum(rate(istio_requests_total{response_flags="UO"}[5m]))

⚠️ Осторожно: кардинальность. Стандартный набор меток Istio даёт source_workload × destination_service × response_code × response_flags × protocol × .... В кластере на 300 сервисов это легко сотни тысяч временных рядов только от mesh. Добавьте к этому гистограмму с двумя десятками бакетов — и Prometheus начинает есть десятки гигабайт. Симптом: после внедрения Istio Prometheus уходит в OOM. Лечение: (а) Telemetry API с tagOverrides для удаления ненужных измерений, (б) metricsRelabelings в ServiceMonitor, выбрасывающий source_version, destination_canonical_revision и подобное, (в) отключить сбор метрик с неинтересных namespace. Категорически нельзя добавлять в метки ничего запросозависимого (путь с ID, user id) — про кардинальность подробно в главе 51.

YAML
apiVersion: telemetry.istio.io/v1
kind: Telemetry
metadata: { name: reduce-cardinality, namespace: istio-system }
spec:
  metrics:
    - providers: [{ name: prometheus }]
      overrides:
        - match: { metric: ALL_METRICS }
          tagOverrides:
            source_canonical_revision: { operation: REMOVE }
            destination_canonical_revision: { operation: REMOVE }
            source_cluster: { operation: REMOVE }
            destination_cluster: { operation: REMOVE }

11.2 Access-логи Envoy

Формат по умолчанию (упрощённо, порядок полей):

[%START_TIME%] "%REQ(:METHOD)% %REQ(X-ENVOY-ORIGINAL-PATH?:PATH)% %PROTOCOL%"
%RESPONSE_CODE% %RESPONSE_FLAGS% %RESPONSE_CODE_DETAILS% %CONNECTION_TERMINATION_DETAILS%
"%UPSTREAM_TRANSPORT_FAILURE_REASON%" %BYTES_RECEIVED% %BYTES_SENT% %DURATION%
%RESP(X-ENVOY-UPSTREAM-SERVICE-TIME)% "%REQ(X-FORWARDED-FOR)%" "%REQ(USER-AGENT)%"
"%REQ(X-REQUEST-ID)%" "%REQ(:AUTHORITY)%" "%UPSTREAM_HOST%" %UPSTREAM_CLUSTER%
%UPSTREAM_LOCAL_ADDRESS% %DOWNSTREAM_LOCAL_ADDRESS% %DOWNSTREAM_REMOTE_ADDRESS%
%REQUESTED_SERVER_NAME% %ROUTE_NAME%

Читать надо в таком порядке: RESPONSE_CODE + RESPONSE_FLAGS (что произошло) → UPSTREAM_CLUSTER и UPSTREAM_HOST (куда пошёл запрос; пусто = никуда) → DURATION против X-ENVOY-UPSTREAM-SERVICE-TIME (сколько времени запрос провёл в вышестоящем сервисе, а сколько — в прокси и сети) → ROUTE_NAME (какое правило сработало).

Разница DURATION − UPSTREAM_SERVICE_TIME — прямой измеритель накладных расходов mesh и сети на этот конкретный запрос. Если она стабильно большая, ищите throttling прокси или проблему соединений, а не медленный бэкенд.

Включить логи в JSON и добавить трассировочные заголовки:

YAML
apiVersion: telemetry.istio.io/v1
kind: Telemetry
metadata: { name: access-logs, namespace: istio-system }
spec:
  accessLogging:
    - providers: [{ name: envoy }]
      filter:
        expression: "response.code >= 400 || has(request.headers['x-debug'])"

Фильтр по CEL-выражению — способ не утонуть: логировать только ошибки плюс помеченные запросы. При 10 000 rps полный access-log с двух прокси на запрос — это 20 000 строк в секунду, что сопоставимо с объёмом логов всего приложения.

11.3 Трассировка и распространение заголовков приложением

Самое частое заблуждение про mesh. Формулировка, которую надо запомнить дословно: service mesh не создаёт распределённую трассировку — он участвует в ней.

Механика. Sidecar видит два независимых события: (1) в под пришёл HTTP-запрос, (2) из пода ушёл HTTP-запрос. Он не может знать, что второй вызван первым. Между ними — ваш процесс: тредпул, CompletableFuture, очередь, кеш. Прокси не заглядывает внутрь JVM.

Единственный способ их связать — заголовки. Прокси на входе генерирует или пропускает traceparent / x-b3-traceid / x-request-id; если ваш код не скопирует их в исходящий запрос, прокси на выходе увидит запрос без контекста и начнёт новую трассу. Результат: в Jaeger вместо одной цепочки из восьми сервисов — восемь огрызков по два span'а, каждый начинающийся «из ниоткуда». Хуже: выглядит это как работающая трассировка, и проблему замечают месяцами позже, в инциденте.

Заголовки, которые надо пробрасывать: traceparent и tracestate (W3C Trace Context — см. главу 51), либо B3-набор (x-b3-traceid, x-b3-spanid, x-b3-parentspanid, x-b3-sampled, x-b3-flags), плюс x-request-id (Envoy) и, если используется, x-ot-span-context.

Хорошая новость для Java. Если у вас Spring Boot с Micrometer Tracing или OpenTelemetry Java agent, всё это делается автоматически — инструментированные RestClient/WebClient/RestTemplate/FeignClient подхватывают контекст из входящего запроса и кладут в исходящий. Проблема возникает, когда:

  • используется «голый» HttpClient или OkHttp, не обёрнутый инструментацией;
  • запрос уходит из другого потока, куда контекст не пробросился (см. главу 11 про Reactor Context и главу 8 про ThreadLocal);
  • в цепочке есть Kafka или другой брокер (заголовки сообщений — отдельная история, глава 31);
  • какой-то сервис в цепочке написан на языке без инструментации.

Минимальный ручной проброс, если инструментации нет:

Java
private static final List<String> TRACE_HEADERS = List.of(
        "x-request-id",
        "traceparent", "tracestate",
        "x-b3-traceid", "x-b3-spanid", "x-b3-parentspanid",
        "x-b3-sampled", "x-b3-flags",
        "x-ot-span-context");

@Bean
RestClientCustomizer tracePropagation() {
    return builder -> builder.requestInterceptor((request, body, execution) -> {
        HttpServletRequest inbound = ((ServletRequestAttributes)
                RequestContextHolder.currentRequestAttributes()).getRequest();
        for (String h : TRACE_HEADERS) {
            String v = inbound.getHeader(h);
            if (v != null) {
                request.getHeaders().set(h, v);
            }
        }
        return execution.execute(request, body);
    });
}

Это костыль (он ломается при асинхронности и не создаёт собственных span'ов), но он лучше, чем разорванная трасса. Правильный путь — OTel-агент или Micrometer Tracing; подробности в главе 51 (51-observability.md).

Проверить, работает ли проброс, можно за минуту:

Bash
kubectl exec deploy/orders -c istio-proxy -- \
  curl -s -H 'x-request-id: TESTME-12345' http://payments:8080/v1/payments/1 -o /dev/null
# смотрим, дошёл ли тот же id до payments
kubectl logs deploy/payments -c istio-proxy --tail=20 | grep TESTME-12345

Если x-request-id в логе прокси payments отличается — проброса нет.

💡 На интервью. «Почему трассировка требует участия приложения, если у меня есть mesh?» — «Sidecar видит входящий и исходящий запросы как два независимых события и не знает, что второй порождён первым: между ними ваш процесс, тредпулы и асинхронность, внутрь которых прокси не смотрит. Связать их можно только через заголовки контекста — traceparent или B3, — а скопировать их из входящего запроса в исходящий обязано приложение. Mesh даёт span'ы на границах и генерирует корневой контекст, но без проброса в коде трасса рассыпается на несвязанные куски.»

11.4 Kiali и карта сервисов

Kiali строит граф вызовов из метрик Prometheus: узлы — сервисы и рабочие нагрузки, рёбра — реальный трафик с RPS, долей ошибок и признаком mTLS (замочек). Полезен для трёх вещей: (1) увидеть фактические зависимости, которые обычно расходятся с архитектурной схемой, (2) найти сервис, от которого расходится волна ошибок, (3) проверять конфигурацию — Kiali подсвечивает VirtualService без DestinationRule, subsets без подов и подобные несогласованности.

Ограничение: Kiali показывает то, что было в метриках за окно. Редкий вызов раз в час на графе за 5 минут не виден, и «зависимости нет» — неверный вывод.

11.5 Canary и progressive delivery

Ручная канарейка — это VirtualService с весами, которые вы двигаете руками:

Bash
# 95/5 -> 80/20 -> 50/50 -> 0/100
kubectl patch virtualservice payments -n payments --type=merge -p '
spec:
  http:
  - route:
    - destination: {host: payments, subset: v1}
      weight: 80
    - destination: {host: payments, subset: v2}
      weight: 20'

Это работает, но требует человека, который смотрит на графики и решает. Автоматизация — Flagger или Argo Rollouts: контроллер сам двигает веса, на каждом шаге проверяет метрики (success rate, p99) и при нарушении порога откатывает.

YAML
apiVersion: flagger.app/v1beta1
kind: Canary
metadata: { name: payments, namespace: payments }
spec:
  provider: istio
  targetRef: { apiVersion: apps/v1, kind: Deployment, name: payments }
  service:
    port: 8080
    gateways: ["istio-system/bank-gateway"]
    hosts: ["api.bank.example"]
  analysis:
    interval: 1m
    threshold: 5           # столько неудачных проверок — откат
    maxWeight: 50
    stepWeight: 10
    metrics:
      - name: request-success-rate
        thresholdRange: { min: 99 }
        interval: 1m
      - name: request-duration
        thresholdRange: { max: 500 }   # ms, p99
        interval: 1m
    webhooks:
      - name: load-test
        url: http://flagger-loadtester.test/
        metadata: { cmd: "hey -z 1m -q 10 -c 2 http://payments.payments:8080/v1/payments/1" }

Flagger сам создаёт и обновляет VirtualService/DestinationRule — руками их трогать больше нельзя. Стратегии деплоя и GitOps подробно разобраны в главе 53 (53-cicd-process.md), объекты Kubernetes — в главе 47.

Важное ограничение канарейки по весам: она статистическая. При 5 % трафика на новую версию и базовом error rate 0,1 % нужно немало запросов, чтобы отличить 0,1 % от 0,3 %. Для низконагруженных сервисов канарейка по весам почти бесполезна — там лучше работает маршрутизация по заголовку (внутренние пользователи на v2) и мониторинг вручную.

12.2 Инцидент с повторами на двух уровнях

Симптом. Пятница, 19:40. Сервис scoring деградирует: p99 вырос с 300 мс до 4 с, но не падает. На графике scoring видно RPS в девять раз выше обычного, при этом orders — источник запросов — шлёт ровно столько же, сколько всегда. Подов scoring пять, все живы, CPU в потолке, orders отдаёт клиентам 504.

Диагностика.

  1. Сравнили istio_requests_total{reporter="source", source_workload="orders"} и {reporter="destination", destination_workload="scoring"} — на источнике 100 rps, на назначении 900 rps. Девятикратное расхождение — это не потеря, это размножение.
  2. Посмотрели счётчики Envoy у orders:
    Bash
    kubectl exec $ORDERS_POD -c istio-proxy -- curl -s localhost:15000/stats | grep scoring | grep retry
# upstream_rq_retry: 68400
    Прокси повторяет.
  3. Посмотрели VirtualService — политика повторов не задана. Значит работает значение по умолчанию Istio: attempts: 2 (istio.io, VirtualService). Итого 3 запроса от прокси на каждый запрос приложения.
  4. Посмотрели код orders:
    YAML
    resilience4j.retry:
  instances:
    scoring:
      maxAttempts: 3      # в Resilience4j это ВСЕГО попыток
      waitDuration: 200ms
    Три попытки приложения.

Причина. 3 (Resilience4j) × 3 (Envoy) = 9 запросов на один бизнес-вызов. Пока scoring здоров, это незаметно: повторов нет. Как только он начал отдавать первые 503, включились оба слоя, нагрузка выросла в 9 раз, и scoring уже не смог выбраться — классический retry storm (глава 35). Система сама себя добила.

Лечение немедленное. Отключили повторы в mesh для этого маршрута:

YAML
    - route:
        - destination: { host: scoring }
      retries: { attempts: 0 }
      timeout: 2s

RPS упал втрое, сервис поднялся за минуту.

Лечение системное — разделение ответственности.

Правило: повторять должен ровно один слой на каждом хопе. Мы выбрали такое разделение:

  • mesh повторяет только гарантированно недошедшие запросы: retryOn: connect-failure,refused-stream,reset. Это те случаи, когда приложение на той стороне запрос не видело, повтор безопасен даже для неидемпотентных операций.
  • приложение повторяет всё остальное — таймауты, 503, доменные коды — и только для тех операций, про которые знает, что они идемпотентны (есть Idempotency-Key, глава 27).
  • retry budget на уровне mesh на случай ошибки: доля повторов ограничена, чтобы даже неправильная конфигурация не дала девятикратного усиления.

Профилактика.

  • Проверка в CI: линтер на VirtualService, требующий явного блока retries (нельзя неявно получить значение по умолчанию).
  • Дашборд «усиление запросов»: отношение reporter="destination" к reporter="source" по каждой паре сервисов. Всё, что стабильно > 1.1, — повод разбираться.
  • Учение раз в квартал: fault injection с abort 50% / 503 на тестовом контуре и замер, во сколько раз вырастает нагрузка на бэкенд.

12.3 Разделение функций между кодом и mesh

В mesh:

  • mTLS и идентичность сервисов;
  • политики «кто с кем может говорить»;
  • L7-маршрутизация, веса, canary, зеркалирование;
  • базовые таймауты как страховочная сетка (глобальный потолок, чтобы ни один запрос не висел вечно);
  • outlier detection — mesh это делает лучше, потому что видит отдельные эндпоинты;
  • circuit breaking как load shedding (лимиты соединений и очередей);
  • RED-метрики и access-логи;
  • fault injection для учений.

В коде:

  • бизнес-fallback: отдать кешированное, деградированный ответ, значение по умолчанию;
  • идемпотентность: ключи, дедупликация, outbox;
  • доменные таймауты: «скоринг дольше 800 мс нам не нужен, дальше считаем клиента среднерисковым» — mesh не знает про 800 мс и не знает, что делать после;
  • классификация ошибок: что в вашем домене ошибка, а что нормальный отказ;
  • повторы с доменным знанием — только идемпотентное, с джиттером;
  • bulkhead по пулам внутри процесса (ограничить, сколько потоков занято вызовами к одному внешнему сервису);
  • объектная авторизация;
  • распространение контекста трассировки.

Хорошая эвристика: если для правильного решения нужно знать, что означает этот запрос, — это код. Если достаточно знать, что это HTTP-запрос из A в B, — это mesh.

12.4 Ненужный mesh

Честный список признаков, при которых внедрение принесёт больше боли, чем пользы:

  • Меньше 10–15 сервисов. Накладные расходы на эксплуатацию не окупаются: те же таймауты и метрики дешевле сделать библиотекой.
  • Один язык и одна платформа. Главное преимущество mesh — языковая независимость — не работает. Spring Boot + Resilience4j + Micrometer закроют 90 % потребностей.
  • Нет команды, которая будет это эксплуатировать. Mesh — это отдельный продукт со своим жизненным циклом, апгрейдами, инцидентами и экспертизой. Если некому дежурить, вы получите ещё один непонятный слой, который в аварии будут подозревать первым и снимать наугад.
  • Латентность критична, а запросы короткие. Для сервиса с p50 в 1–2 мс два дополнительных прокси — это удвоение.
  • Трафик в основном не HTTP. JDBC, бинарные протоколы, длинные TCP-стримы — mesh даёт им только mTLS и байтовые счётчики.
  • Регуляторные ограничения на криптографию. Если требуется ГОСТ (глава 41), Envoy вам его не даст.

Замена:

Потребность Замена без mesh
таймауты, повторы, circuit breaker Resilience4j / org.springframework.resilience (глава 35)
mTLS между сервисами SSL Bundles в Spring Boot + сертификаты из cert-manager (главы 40, 41)
маршрутизация, canary, TLS на входе ingress-контроллер / Gateway API
метрики и трассировка Micrometer + OTel-агент (глава 51)
политики «кто с кем» NetworkPolicy (L3/L4) + проверка identity в приложении
балансировка gRPC client-side через headless + round_robin

Эта связка закрывает большую часть задач и стоит примерно ноль в эксплуатации. Разумная стратегия для растущей системы: начать с неё, внедрять mesh, когда появится третий язык или сотый сервис — и начать с ambient-режима ради L4 (mTLS + идентичность + телеметрия), добавляя L7 точечно.

13. Другие mesh и смежные технологии

13.1 Linkerd

Второй по распространённости mesh, философски противоположный Istio: делать меньше, но проще. Заявленные возможности — автоматический mTLS между meshed-подами, retry и timeout для HTTP и gRPC, traffic split, балансировка для HTTP, HTTP/2 и gRPC (linkerd.io, Features). Актуальная версия — Linkerd 2.20.

Ключевое архитектурное отличие — собственный микропрокси вместо Envoy. Он специализирован под задачу sidecar (нет универсальной расширяемости Envoy, нет Wasm, нет произвольных фильтров), за счёт чего меньше по памяти и проще в эксплуатации. ⚠️ Язык реализации прокси (по сообществу — Rust) и конкретные цифры потребления ресурсов на странице возможностей не приведены; при разговоре об экономии ресурсов ссылайтесь на собственные измерения, а не на цифры из пересказов.

Что за это платят: меньше возможностей в traffic management (нет такого богатого матчинга, как в VirtualService), нет Wasm-расширений, меньше экосистема.

Кому подходит: командам, которым нужны mTLS, базовые метрики и простые повторы, и которые не хотят содержать Istio.

13.2 Consul Connect

Mesh от HashiCorp, выросший из service discovery. Отличия: работает не только в Kubernetes — Consul исторически умеет VM, bare-metal и смешанные среды, и это его главная ниша. Data plane — Envoy. Идентичность и политики («intentions») — в терминах сервисов Consul. Если у вас половина ландшафта на виртуалках (типично для банка с историей), Consul Connect может быть единственным вариантом, дающим единый mesh поверх k8s и не-k8s.

Цена: нужен и работающий кластер Consul (Raft, глава 34), и понимание его модели, которая не совпадает с моделью Kubernetes.

13.3 Cilium Service Mesh

Развитие CNI в сторону mesh. L4 (идентичность, политики, балансировка, шифрование) делается eBPF-программами в ядре, L7 — Envoy на узел, а не на под. Управление — через Gateway API и собственные CRD (CiliumNetworkPolicy с L7-правилами для HTTP, gRPC, Kafka, DNS).

Сильные стороны: нет sidecar вообще, один слой вместо двух (CNI и mesh — один продукт), Hubble даёт наблюдаемость сетевых потоков без инструментирования. Слабые: экосистема Istio (Kiali, готовые операторы, Flagger-интеграции, огромный корпус статей) не переносится, и набор traffic-management возможностей уже.

13.5 API Gateway и service mesh

Путаница возникает потому, что технически это часто один и тот же Envoy. Разница в задаче.

Критерий API Gateway (north-south) Service mesh (east-west)
Трафик извне внутрь между сервисами внутри
Клиент недоверенный (браузер, мобильное приложение, партнёр) доверенный сервис с идентичностью
Задачи аутентификация конечного пользователя, rate limiting по клиенту, монетизация и квоты, версионирование публичного API, трансформация, WAF, кеширование, developer portal mTLS, политики между сервисами, балансировка, повторы, телеметрия
Число экземпляров единицы сотни (по одному на под)
Владелец команда платформы / API-governance команда платформы + команды сервисов

Нужны оба. Типовая раскладка: Gateway API или Kong/Apigee на периметре делает OAuth2-интроспекцию, лимиты по клиентам и публичный контракт; Istio внутри делает mTLS, политики и наблюдаемость. Istio ingress-gateway при этом часто играет роль «внутреннего» входа в mesh, а полноценный API Gateway стоит перед ним.

Антипаттерн: пытаться сделать API Gateway из ingress-gateway Istio. AuthorizationPolicy и RequestAuthentication дают проверку JWT, но не дают квот по тарифным планам, аналитики по потребителям, портала разработчика и монетизации — а это то, ради чего API Gateway и покупают.

13.6 eBPF в сетевом стеке

eBPF — виртуальная машина в ядре Linux, позволяющая безопасно загружать и исполнять программы в точках-хуках: системные вызовы, сетевые хуки (XDP, tc), kprobes/uprobes, tracepoints. Программы проходят верификатор, который доказывает завершаемость и безопасность доступа к памяти, компилируются JIT в нативный код и работают со скоростью ядерного кода, без переключений контекста.

Для сети это значит три вещи:

  1. Обработка пакетов до всего остального. XDP-программа исполняется в драйвере NIC, ещё до выделения памяти sk_buff — там делают DDoS-фильтрацию и L4-балансировку на wire speed.
  2. Замена iptables. Вместо линейных цепочек — хеш-таблицы eBPF maps с O(1)-лукапом и инкрементальными обновлениями (§ 2.2).
  3. Наблюдаемость без инструментирования. Программа, подцепленная к нужным хукам, видит все соединения, все HTTP-запросы и все обращения к DNS, не требуя ни агента в поде, ни изменения кода.

Инструменты, которые стоит знать:

  • Hubble (часть Cilium) — поток сетевых событий: кто с кем соединялся, что разрешила или запретила политика, почему пакет был отброшен. hubble observe --from-pod payments/orders-xxx --verdict DROPPED в одну строку отвечает на вопрос «кто нас блокирует», на который NetworkPolicy сама по себе ответить не может.
  • Pixie — авто-инструментирование: перехватывает HTTP/gRPC/SQL/Redis-трафик через uprobes и eBPF, показывает запросы, тела и латентности без единой строчки кода в приложении. Для Java есть нюанс: TLS-трафик читается через uprobes на функциях библиотек шифрования, и для JVM это работает хуже, чем для Go или Python. ⚠️ Границы поддержки JVM в Pixie по первичному источнику не проверял.
  • bpftrace / BCC — однострочники для диагностики (tcpconnect, tcpretrans, execsnoop); подробнее в главе 50.

Ограничение, о котором стоит помнить: eBPF привязан к версии ядра. Часть возможностей требует 5.10+, часть — 6.x, и на RHEL с backport'ами матрица совместимости нетривиальна. В managed-кластерах вы не всегда управляете ядром.

14. Ошибки и антипаттерны

1. 503 сразу после деплоя, через 10–30 секунд всё нормализуется.

Симптом. Новый под поднялся, readiness прошла, трафик пошёл — и первые запросы отдают 503 NC no_cluster_found или 503 UH.

Причина. Прокси стартовал, но ещё не получил полную конфигурацию от istiod: listeners есть, clusters или endpoints — нет. Либо istiod перегружен и рассылка медленная.

Лечение. Проверить istioctl proxy-status — колонки должны быть SYNCED. Использовать native sidecar (k8s 1.29+) или holdApplicationUntilProxyStarts: true. Убедиться, что у istiod достаточно CPU: рассылка xDS — это CPU-bound сериализация protobuf.

Профилактика. Оповещение на pilot_proxy_convergence_time (время сходимости) и на число прокси в состоянии не-SYNCED.

2. upstream connect error or disconnect/reset before headers при включении STRICT mTLS.

Симптом. После применения PeerAuthentication: STRICT часть вызовов падает с 503 UF; в логах сервера — ничего.

Причина. Клиент без sidecar (или с DISABLE) шлёт plaintext туда, где требуется mTLS. Вариант: DestinationRule с ISTIO_MUTUAL на хост, у которого нет прокси.

Лечение. istioctl x describe pod <pod> показывает эффективный режим mTLS для нагрузки. Вернуть PERMISSIVE, найти источники plaintext через istio_requests_total{connection_security_policy!="mutual_tls"}, заинжектить sidecar, потом снова STRICT.

Профилактика. Миграция по шагам (§ 10.2), метрика plaintext-трафика на дашборде, запрет создавать namespace без метки инжекции политикой Kyverno/Gatekeeper.

3. Двойные повторы: приложение × mesh.

Разобрано в § 12.2. Коротко: значение по умолчанию Istio — attempts: 2, и он включён, даже если вы ничего не настраивали. Проверяйте усиление по отношению reporter="destination" / reporter="source".

4. mirror в продакшене и двойные записи в БД.

Симптом. После включения зеркалирования на v2 в базе появляются дубли транзакций.

Причина. Зеркальный сервис пишет в ту же БД. Envoy игнорирует ответ, а не побочные эффекты.

Лечение. Зеркалировать только read-only пути, либо давать зеркальной версии отдельную БД, либо научить её распознавать теневой трафик (Envoy добавляет к :authority суффикс -shadow).

5. Разорванная трассировка после внедрения mesh.

Симптом. В Jaeger вместо цепочки — множество двухспановых огрызков.

Причина. Приложение не пробрасывает traceparent/B3. Mesh этого сделать не может (§ 11.3).

Лечение. OTel-агент или Micrometer Tracing; для не инструментированных клиентов — ручной проброс.

Профилактика. Интеграционный тест, проверяющий, что x-request-id доезжает через всю цепочку.

6. Prometheus уходит в OOM после включения Istio.

Причина. Кардинальность стандартных метрик mesh: десятки меток × сотни сервисов × гистограммы.

Лечение. Telemetry API с tagOverrides: REMOVE, relabeling в ServiceMonitor, ограничение namespace.

Профилактика. Считать ожидаемое число временных рядов до включения; оповещение на prometheus_tsdb_head_series.

7. Память Envoy растёт линейно с числом сервисов в кластере.

Причина. Без ресурса Sidecar istiod рассылает каждому прокси конфигурацию всего кластера.

Лечение. Sidecar с явным списком egress.hosts (§ 9.7) и discoverySelectors в MeshConfig.

Профилактика. Ввести Sidecar по умолчанию в каждом namespace с первого дня, а не когда кластер вырастет.

8. Не-HTTP протокол опознан как HTTP (или наоборот).

Симптом. PostgreSQL/Redis/собственный бинарный протокол перестаёт работать после включения mesh; в логах прокси странные ошибки парсинга.

Причина. Istio определяет протокол по имени порта в Service (http, http2, grpc, tcp, tls, mongo, redis, mysql) или по полю appProtocol. Порт с именем postgres или без имени вообще обрабатывается эвристикой и может быть ошибочно принят за HTTP.

Лечение. Явно именовать порты: name: tcp-postgres или appProtocol: tcp.

YAML
spec:
  ports:
    - name: tcp-postgres      # префикс определяет протокол
      port: 5432
      appProtocol: tcp        # более явный способ

Профилактика. Правило в CI: каждый порт Service обязан иметь имя с корректным префиксом.

9. Headless-сервис не работает так, как ожидается.

Симптом. StatefulSet (Kafka, Cassandra) после включения mesh теряет связность между членами; или mTLS не применяется к обращениям по IP пода.

Причина. Для headless-сервиса нет ClusterIP, и Envoy строит конфигурацию на основе ORIGINAL_DST или отдельных listeners на IP подов. Маршрутизация по subsets и часть политик работают иначе.

Лечение. Для StatefulSet-кластеров с собственным TLS и протоколом проще исключить порты из перехвата (traffic.sidecar.istio.io/excludeInboundPorts) либо не включать mesh на них вовсе. Если mesh нужен — тщательно тестировать и явно указывать протокол порта.

10. Базы данных вне mesh.

Симптом. После включения mesh соединения к внешней PostgreSQL рвутся или тормозят.

Причины. (а) idleTimeout в connection pool Envoy (по умолчанию 1 час) закрывает соединение, которое HikariCP считает живым; (б) перехват ломает SSL-рукопожатие к БД; (в) Envoy добавляет накладные расходы на каждый пакет мелкого чата JDBC.

Лечение. Исключить порт БД: traffic.sidecar.istio.io/excludeOutboundPorts: "5432" — это почти всегда правильный ответ. Mesh для JDBC даёт очень мало (нет L7-семантики), а риск высок. Если оставляете — согласуйте idleTimeout Envoy с maxLifetime HikariCP (Hikari должен закрывать раньше).

11. NetworkPolicy применили — сломался DNS.

Симптом. После default-deny egress приложение не видит вообще ничего, включая свои же сервисы; в логах UnknownHostException.

Причина. Забыли разрешить UDP/TCP 53 к CoreDNS.

Лечение. Отдельная политика allow-dns (§ 4.1) в каждом namespace, где есть default-deny egress.

Профилактика. Шаблон namespace, в котором default-deny и allow-dns создаются вместе.

12. namespaceSelector + podSelector через дефис = OR вместо AND.

Разобрано в § 4.1. Симптом — политика «разрешить только kube-dns» на деле разрешает весь kube-system и все поды с такой меткой в кластере. YAML валиден, ошибки нет. Проверять тестом.

13. ndots:5 и пятисекундное разрешение внешних имён.

Разобрано в § 3.2. Симптом — периодические ровно-пятисекундные задержки на внешних вызовах. Лечение — dnsConfig с ndots: 2, FQDN с точкой, NodeLocal DNSCache, либо DNS-прокси Istio.

14. Потеря заголовков.

Симптом. Сервис B не видит заголовок, который A точно отправил.

Причины. (а) HTTP/2 требует lowercase-имён заголовков — библиотека, шлющая X-Custom-Header, может получить проблемы при конвертации; (б) headers.request.remove в VirtualService где-то в цепочке; (в) ingress-контроллер перед mesh чистит неизвестные заголовки; (г) подчёркивания в именах заголовков (x_custom) отбрасываются некоторыми прокси по умолчанию.

Лечение. Логировать нужные заголовки в access-log прокси на каждом хопе (%REQ(X-CUSTOM)%), найти, где исчезает. Не использовать подчёркивания в именах заголовков.

15. Рост латентности после внедрения mesh, который не объясняется «+2 хопа».

Симптом. p50 вырос на 2 мс (ожидаемо), но p99 — в пять раз.

Причина №1. CPU throttling контейнера istio-proxy: лимит стоит, под нагрузкой cgroups режет, Envoy залипает. Проверка: container_cpu_cfs_throttled_seconds_total{container="istio-proxy"}.

Причина №2. Connection pool: maxConnections или http1MaxPendingRequests выставлены слишком низко, запросы стоят в очереди. Проверка: upstream_rq_pending_overflow, upstream_cx_overflow в /stats.

Причина №3. Отсутствие keep-alive к вышестоящему сервису, соединение устанавливается на каждый запрос.

Лечение. Снять лимит CPU с прокси (оставить request) либо поднять его; настроить пул по измеренной нагрузке.

16. istiod OOM при большом числе прокси.

Причина. istiod держит в памяти модель кластера и генерирует конфигурацию для каждого прокси; при тысячах подов и тысячах сервисов это гигабайты.

Лечение. Горизонтальный скейл istiod (он stateless по отношению к трафику), discoverySelectors, Sidecar-ресурсы (снижают объём генерируемой конфигурации), PILOT_FILTER_GATEWAY_CLUSTER_CONFIG.

17. ztunnel OOM в ambient.

Причина. ztunnel обслуживает все поды узла; ошибка в лимитах или нагрузочный всплеск на плотном узле.

Последствие. Страдает весь узел, а не один под — это принципиальное отличие от sidecar-модели.

Лечение. Мониторить память ztunnel отдельно, не экономить на лимитах DaemonSet, ограничивать плотность подов на узел.

18. VirtualService применился, но трафик идёт мимо.

Причины. (а) в hosts указано короткое имя, а клиент ходит по FQDN из другого namespace — короткое имя разрешается относительно namespace самого VirtualService; (б) не указан gateways, а правило нужно для внешнего трафика (значение по умолчанию — только mesh); (в) правило стоит после более общего правила без match, которое перехватывает всё; (г) два VirtualService на один хост — поведение при конфликте недетерминировано, их надо объединять.

Лечение. istioctl proxy-config routes <pod> --name 8080 -o json показывает фактическую таблицу маршрутов прокси. istioctl analyze ловит большинство таких случаев.

19. Забыли, что fault отключает таймауты и повторы.

Симптом. Включили fault.delay: 10s для проверки таймаута — и таймаут не сработал.

Причина. Документация прямо говорит: при включённом fault таймауты и повторы на маршруте отключаются (istio.io, VirtualService).

Лечение. Внедрять задержку на маршруте к зависимости, а проверять таймаут — на клиенте, который к ней ходит. То есть fault ставится на vs сервиса B, а тестируется поведение сервиса A.

20. Пробы kubelet ломаются при STRICT mTLS.

Симптом. После включения STRICT поды начинают падать по liveness.

Причина. Пробы идут с узла, у kubelet нет сертификата mesh.

Лечение. Istio по умолчанию переписывает HTTP-пробы (sidecar.istio.io/rewriteAppHTTPProbers), направляя их через порт 15020, который освобождён от mTLS. Если пробы exec или переписывание отключено — настроить portLevelMtls: PERMISSIVE на порт actuator. Проверить, что аннотация присутствует в поде.

21. Внедрили mesh, но половина трафика идёт мимо него.

Симптом. Kiali показывает не всё; политики применяются выборочно.

Причины. Поды с hostNetwork: true (перехват невозможен), namespace без метки, sidecar.istio.io/inject: "false", обращения по IP пода в обход Service (ORIGINAL_DST обрабатывается иначе), Jobs и CronJobs, которые кто-то исключил из-за проблем с завершением.

Лечение. Инвентаризация: kubectl get pods -A -o json | jq -r '.items[] | select(.spec.containers | map(.name) | index("istio-proxy") | not) | "\(.metadata.namespace)/\(.metadata.name)"'.

22. REGISTRY_ONLY включили без инвентаризации исходящих зависимостей.

Симптом. Часть сервисов перестаёт ходить наружу; в логах 502 и BlackHoleCluster.

Лечение. Сначала собрать список внешних хостов из метрик (destination_service для PassthroughCluster и DNS-логов), завести ServiceEntry на каждый, и только потом включать.

23. Обновили Istio — половина подов осталась со старым прокси.

Причина. Версия прокси зафиксирована в pod spec при инжекции; обновление control plane не трогает работающие поды.

Симптом. istioctl proxy-status показывает разные версии; часть новых возможностей не работает.

Лечение. kubectl rollout restart по всем deployment'ам; в процессе апгрейда это отдельный запланированный шаг. Проверка совместимости: Istio поддерживает работу data plane на одну минорную версию младше control plane, не больше.

24. AuthorizationPolicy не применилась, потому что sidecar не заинжектился.

Причина. Политику обеспечивает прокси. Нет прокси — нет политики, и никакого fail-closed не происходит.

Следствие. Нельзя полагаться только на mesh в вопросах безопасности. Комбинируйте с NetworkPolicy (работает на уровне CNI, независимо от mesh) и проверками в приложении.

25. Таймаут в mesh короче таймаута приложения (или наоборот).

Симптом. Клиент получает 504 UT от прокси, а приложение в логах видит нормально завершившийся запрос — или наоборот, приложение таймаутит, а прокси всё ещё ждёт.

Причина. Два независимых таймаута, никто их не согласовывал.

Правило. Таймауты должны убывать вглубь: таймаут клиента > таймаут mesh > таймаут HTTP-клиента приложения > таймаут БД/запроса. И VirtualService.timeout ≥ perTryTimeout × (attempts + 1).

Сокращённая шпаргалка «503 + флаг»:

  • 503 UF → почти всегда mTLS или упавший вышестоящий сервис;
  • 503 UC → порт/сеть/политика: соединение не установилось;
  • 503 UH → нет готовых подов (или все выкинуты outlier detection);
  • 503 UO → вы сами настроили слишком узкий connection pool;
  • 503 NC / 404 NR → ошибка конфигурации маршрутизации, а не runtime;
  • 403 UAEX → AuthorizationPolicy.

15.3 Чеклист «запрос не доходит до сервиса»

  1. Есть ли вообще sidecar? kubectl get pod <pod> -o jsonpath='{.spec.containers[*].name}{"\n"}{.spec.initContainers[*].name}' — ищем istio-proxy.
  2. Синхронизирован ли прокси? istioctl proxy-status | grep <pod> — все колонки SYNCED.
  3. Что говорит анализатор? istioctl analyze -n <ns>.
  4. Видит ли прокси клиента нужный кластер? istioctl proxy-config clusters <client-pod> --fqdn <service-fqdn> — если пусто, виноват Sidecar-ресурс, REGISTRY_ONLY или отсутствие Service.
  5. Есть ли в кластере эндпоинты? istioctl proxy-config endpoints <client-pod> --cluster '<cluster-name>' — пусто значит нет готовых подов или селектор Service не совпадает с метками подов.
  6. Какой маршрут выбирается? istioctl proxy-config routes <client-pod> -o json.
  7. Что в access-log обоих прокси?
    Bash
    kubectl logs <client-pod>  -c istio-proxy --tail=50 | grep <path>
kubectl logs <server-pod>  -c istio-proxy --tail=50 | grep <path>
    Если запись есть только у клиента — запрос до сервера не дошёл (смотрим флаг). Если у обоих — проблема в приложении.
  8. Не блокирует ли авторизация? Флаг UAEX или 403; istioctl x describe pod <server-pod> покажет применимые политики.
  9. Не блокирует ли NetworkPolicy? Она работает ниже mesh и её mesh не видит. С Cilium — hubble observe --verdict DROPPED; иначе — временно снять политику в тестовом namespace.
  10. Обход mesh для проверки: запрос напрямую на IP пода из другого пода тем же curl — если проходит, проблема в mesh-слое.

15.4 Чеклист «503 в mesh»

  1. Посмотреть флаг, не только код (таблица § 15.2). Это сразу делит пространство поиска на порядок.
  2. Определить, кто сгенерировал 503: сравнить istio_requests_total{reporter="source"} и {reporter="destination"}. Если только source — виноват прокси клиента, сервер запроса не видел.
  3. Проверить mTLS-режим обеих сторон: istioctl x describe pod на клиенте и сервере.
  4. Проверить circuit breaker:
    Bash
    kubectl exec <client-pod> -c istio-proxy -- curl -s localhost:15000/stats \
  | grep -E 'pending_overflow|cx_overflow|rq_retry_overflow'
  5. Проверить outlier detection:
    Bash
    kubectl exec <client-pod> -c istio-proxy -- curl -s localhost:15000/clusters \
  | grep -E 'health_flags|ejected'
    /failed_outlier_check у эндпоинта означает, что он исключён.
  6. Проверить готовность подов сервера и совпадение меток Service с метками подов.
  7. Проверить, не истекли ли сертификаты: istioctl proxy-config secret <pod> — колонка с датой; и жив ли istiod (если он лежит сутки, ротация не произошла).
  8. Проверить таймауты: UT — чей таймаут сработал, mesh или приложения; сравнить DURATION и X-ENVOY-UPSTREAM-SERVICE-TIME в логе.

15.5 Чеклист «рост латентности после внедрения mesh»

  1. Разложить латентность. В access-log прокси клиента сравнить %DURATION% и %RESP(X-ENVOY-UPSTREAM-SERVICE-TIME)%. Разница — накладные расходы прокси и сети. Если разница мала, mesh ни при чём.
  2. CPU throttling прокси.
    PromQL
    rate(container_cpu_cfs_throttled_seconds_total{container="istio-proxy"}[5m]) > 0
    Один из самых частых виновников хвостовых задержек.
  3. Connection pool. upstream_rq_pending_overflow, upstream_cx_overflow, а также upstream_cx_total — если соединения создаются на каждый запрос, keep-alive не работает.
  4. Число кластеров у прокси. istioctl proxy-config clusters <pod> | wc -l — если тысячи, вводите Sidecar-ресурс: это влияет и на память, и на время применения конфигурации.
  5. Повторы. Отношение upstream_rq_retry к общему числу запросов; и усиление между reporter=source и reporter=destination.
  6. DNS. Если латентность скачет ступенями кратно 1 или 5 секундам — это распознаватель (§ 3.2), а не mesh.
  7. Выборка трассировки. Профиль demo даёт 100 %; на проде это ощутимая нагрузка. Проверить meshConfig.defaultConfig.tracing.sampling.
  8. Access-log на полном объёме. Два прокси × полный лог на каждый запрос — иногда это и есть источник нагрузки на диск и сеть; включить фильтр по CEL (§ 11.2).
  9. Сравнить с контролем. Поднять тот же сервис без sidecar в соседнем namespace и прогнать одинаковую нагрузку. Это единственный способ получить честную цифру «цены mesh» в вашей конфигурации.

16. Вопросы на интервью

1. Опишите сетевую модель Kubernetes.

Каждый под получает собственный IP из плоского адресного пространства кластера, и поды общаются друг с другом напрямую, без NAT: и адрес источника, и адрес назначения видны настоящими. Внутри пода все контейнеры делят один сетевой namespace, то есть один IP, общий localhost и общие iptables. Отсюда два следствия: конфликтов портов между подами не бывает, а IP пода эфемерен и его нельзя кешировать. Реализует это CNI-плагин; Kubernetes только задаёт требования.

2. Чем overlay-сеть отличается от routed и чем за это платят?

Overlay инкапсулирует пакет пода в UDP (VXLAN) или IP-in-IP и отправляет на IP узла, так что физическая сеть знает только адреса узлов. Routed анонсирует подсети подов по BGP, и пакеты идут нативно. Overlay работает в любой инфраструктуре, но добавляет около 50 байт заголовка — эффективный MTU падает с 1500 до 1450, — плюс CPU на инкапсуляцию. Классический симптом неправильного MTU: рукопожатие проходит, мелкие запросы работают, а большие тела просто зависают.

3. Что происходит при обращении к ClusterIP?

ClusterIP — виртуальный адрес, которому не отвечает ни один интерфейс. Контроллер эндпоинтов кладёт адреса готовых подов в EndpointSlice, kube-proxy на каждом узле превращает их в правила datapath, и первый SYN на ClusterIP подвергается DNAT на адрес конкретного пода; дальше соединение живёт через conntrack. Балансировка в iptables-режиме — равновероятная случайная и не настраивается.

4. Почему iptables-режим kube-proxy деградирует и что вместо него?

Правила в netfilter обходятся линейно, но главная проблема в другом: kube-proxy при любом изменении перегенерирует таблицу целиком через iptables-restore, и при тысячах сервисов это сотни тысяч правил и секунды на применение под глобальной блокировкой xtables. Практически это означает медленную сходимость после деплоя. Альтернативы: IPVS с хеш-таблицей и инкрементальными обновлениями, nftables-режим со словарями, либо Cilium, полностью заменяющий kube-proxy на eBPF с socket-level балансировкой — подмена адреса один раз при connect() вместо DNAT на каждом пакете.

5. Зачем EndpointSlice, если был Endpoints?

Endpoints хранил все адреса сервиса в одном объекте, поэтому изменение одного пода рассылало мегабайтный объект всем watch-подписчикам — каждому kube-proxy и каждому ingress-контроллеру. EndpointSlice режет список на срезы примерно по сотне эндпоинтов, обновляя только затронутый, и добавляет поля, которых не было: ready/serving/terminating для корректного graceful shutdown и zone для topology-aware маршрутизации.

6. Что такое ndots:5 и почему это классическая причина медленного разрешения имён?

Kubelet пишет в resolv.conf пода три search-домена и options ndots:5, чтобы работали короткие имена сервисов. Распознаватель glibc для имени с числом точек меньше пяти сначала пробует его со всеми search-доменами. Внешнее имя вроде api.partner-bank.com содержит две точки, значит уходит четыре запроса вместо одного, а с учётом параллельных A и AAAA — до восьми пакетов, три четверти которых заведомо NXDOMAIN. При потере UDP-пакета добавляется таймаут распознавателя в пять секунд. Лечится dnsConfig с ndots: 2, FQDN с завершающей точкой, NodeLocal DNSCache или DNS-прокси Istio.

7. Как работает NetworkPolicy и чего она не умеет?

Пока под не выбран ни одной политикой, он не изолирован. Как только политика с типом Ingress его выбирает, весь входящий трафик запрещается кроме явно разрешённого; egress изолируется независимо. Политики аддитивны — разрешено объединение, «запретить поверх разрешения» штатно нельзя. Она работает на L3/L4: нет фильтрации по HTTP, нет DNS-имён, нет выбора контейнеров, только TCP/UDP/SCTP. И главное — без CNI с поддержкой NetworkPolicy объект создаётся, но не делает ничего.

8. Почему L4-балансировщик ломает gRPC?

gRPC работает поверх HTTP/2: одно долгоживущее TCP-соединение, в котором мультиплексируются все запросы. L4 выбирает бэкенд один раз при установлении соединения, поэтому весь последующий поток запросов идёт в один под, и после скейлинга новые реплики не получают трафика. Лечения три: L7-прокси, который балансирует по стримам (это и даёт sidecar), клиентская балансировка через headless-сервис с политикой round_robin, либо принудительное закрытие соединений — maxConnectionAge на сервере или maxRequestsPerConnection в DestinationRule.

9. Зачем вообще появился service mesh?

Таймауты, повторы, mTLS, политики доступа, метрики и трассировка нужны каждому сервису, не зависят от бизнес-логики и при этом реализуются библиотекой, которая своя под каждый язык и обновляется только через релиз приложения. В разнородном ландшафте это не масштабируется: чтобы срезать таймаут в сорока сервисах, нужно сорок релизов. Mesh выносит этот слой в сеть — в прокси рядом с каждым подом, конфигурируемый централизованно, одинаковый для Java, Go и Python.

10. Что такое data plane и control plane в Istio?

Data plane — это прокси Envoy, через которые реально идут байты: sidecar рядом с каждым подом либо ztunnel на узле в ambient. Control plane — istiod, объединивший исторические Pilot, Citadel и Galley: он следит за Service, EndpointSlice и вашими CRD, компилирует их в xDS-конфигурацию и рассылает прокси, а также выступает CA. Важное свойство: падение istiod не роняет трафик — прокси работают на последней конфигурации; перестают обновляться эндпоинты, политики и, через часы, сертификаты.

11. Что такое sidecar и как трафик в него попадает?

Sidecar — контейнер с прокси в том же поде, а значит в том же сетевом namespace: общий IP, общий localhost, общие iptables. Init-контейнер istio-init запускает скрипт istio-iptables, который заворачивает весь исходящий трафик пода правилом REDIRECT на порт 15001 прокси, а входящий — на 15006. Чтобы не получилась петля, трафик самого прокси исключается по UID 1337. Альтернатива init-контейнеру — Istio CNI-плагин, который настраивает те же правила из DaemonSet, не требуя NET_ADMIN у пода; в ambient перехват делается вообще без iptables внутри пода.

12. Что починили native sidecars и почему это было нужно?

До Kubernetes 1.29 контейнеры пода стартовали и останавливались параллельно. Приложение могло стартовать раньше прокси и упасть на инициализации, потому что iptables уже заворачивали трафик туда, где никто не слушал; при завершении прокси часто умирал первым и приложение теряло сеть в середине graceful shutdown, а Job с sidecar вообще никогда не завершался. Native sidecar — это initContainer с restartPolicy: Always: он стартует до основных контейнеров, ждёт своей startupProbe и останавливается после них в обратном порядке. Доступно по умолчанию с 1.29, GA с 1.33. До этого обходились holdApplicationUntilProxyStarts, EXIT_ON_ZERO_ACTIVE_CONNECTIONS и вызовом /quitquitquit.

13. Сколько стоит sidecar?

Envoy — это память, пропорциональная объёму конфигурации: прокси, который знает обо всех сервисах кластера, легко занимает 300–500 МБ, и это умножается на число подов. Плюс два дополнительных сетевых хопа на каждый межсервисный вызов — единицы миллисекунд на p50 и заметно больше на хвостах, что критично для сервисов с собственной латентностью в пару миллисекунд. Плюс CPU throttling, если прокси выставлен лимит. Плюс усложнение отладки и обязательный перезапуск всех подов при обновлении Istio. Главное лечение по памяти — ресурс Sidecar, ограничивающий видимость сервисов.

14. Зачем придумали ambient mode?

Чтобы убрать прокси из каждого пода. В ambient на узле работает ztunnel — лёгкий L4-прокси, делающий mTLS, идентичность, L4-авторизацию и телеметрию, но не разбирающий HTTP; трафик между ztunnel идёт по HBONE поверх mTLS. L7-функции включаются точечно через waypoint-прокси на namespace или сервис, вне пода приложения. Выигрыш — память и отсутствие перезапуска подов при включении или обновлении mesh. Плата — при полном L7-наборе путь запроса длиннее, и отказ ztunnel затрагивает весь узел, а не один под. На сентябрь 2026 ядро ambient — часть текущей ветки 1.31; часть возможностей, вроде маршрутизации по JWT-claim и Wasm для waypoint, помечена Alpha.

15. Что такое xDS и зачем ADS?

xDS — семейство gRPC-API, по которым control plane раздаёт конфигурацию Envoy: LDS для listeners, RDS для маршрутов, CDS для кластеров, EDS для эндпоинтов, SDS для сертификатов. Конфигурация применяется без рестарта: старые соединения дорабатывают, новые идут по новой. ADS — агрегированный вариант, отдающий всё это одним потоком с гарантией порядка; без него возможен рассинхрон, когда маршрут ссылается на ещё не пришедший кластер, и запросы падают с флагом NC.

16. Опишите путь запроса внутри Envoy.

Listener выбирается по адресу и порту назначения, внутри него filter chain подбирается по SNI, ALPN и CIDR. Дальше network-фильтры, ключевой из которых http_connection_manager: он парсит HTTP, ведёт стримы и пишет access-log. Затем цепочка HTTP-фильтров — jwt_authn, rbac, fault, router. Router выбирает virtual host по :authority и маршрут по пути и заголовкам, маршрут указывает на cluster, cluster применяет политики балансировки, connection pool и outlier detection и выбирает конкретный endpoint. Каждый уровень даёт свой признак отказа: нет маршрута — NR, нет кластера — NC, нет здоровых эндпоинтов — UH.

17. Что такое outlier detection и чем он отличается от circuit breaker?

Outlier detection — пассивный health checking: Envoy не шлёт отдельных проб, а анализирует реальные ответы и временно исключает из балансировки конкретный эндпоинт, который отдаёт 5xx подряд или статистически хуже остальных. В Istio значения по умолчанию — пять последовательных 5xx, интервал 10 секунд, базовое исключение 30 секунд, не более половины эндпоинтов; время исключения растёт с каждым повторным срабатыванием. Circuit breaker в Envoy — это другое: лимиты соединений, ожидающих и параллельных запросов на кластер, при превышении которых запрос мгновенно отбивается флагом UO. Ключевое преимущество outlier detection перед Resilience4j — гранулярность: он отличает один больной под от больного сервиса.

18. Mesh или Resilience4j — что выбрать?

Не «или», а разделение по критерию семантики. Всё, для чего достаточно знать, что это HTTP-запрос из A в B, отдаём в mesh: mTLS, политики доступа, маршрутизацию, базовые таймауты, outlier detection, телеметрию. Всё, для чего нужно знать смысл запроса, оставляем в коде: идемпотентность, бизнес-fallback, доменные таймауты, классификацию ошибок. Резон в том, что прокси не знает, можно ли повторить платёж, и не умеет отдать кешированный ответ вместо ошибки. Если оставить повторы в обоих слоях, получите перемножение попыток.

19. Как работает mTLS в Istio?

Каждой нагрузке выдаётся идентичность в формате SPIFFE — spiffe://cluster.local/ns/<namespace>/sa/<serviceaccount>, то есть привязанная к ServiceAccount, а не к IP. Агент внутри пода генерирует ключ и CSR, подтверждает себя токеном ServiceAccount, CA внутри istiod проверяет его и подписывает, и Envoy получает сертификат через SDS по Unix-сокету. Приватный ключ никогда не пишется на диск и не хранится в Secret, сертификаты живут часами и ротируются автоматически. Режим включается PeerAuthentication: STRICT, PERMISSIVE или DISABLE.

20. Как перевести кластер на STRICT mTLS без простоя?

Включить PERMISSIVE глобально — он принимает и mTLS, и plaintext, поэтому ничего не ломает. Заинжектить sidecar везде и перезапустить нагрузки. Затем измерить остатки plaintext-трафика по метрике istio_requests_total с меткой connection_security_policy != mutual_tls и разобраться с источниками: обычно это Prometheus, пробы kubelet и контроллеры без sidecar. Только когда эта величина обнулилась, включать STRICT по одному namespace, начиная с некритичных, и в конце переключать корневую политику.

21. Заменяет ли AuthorizationPolicy авторизацию в приложении?

Нет. Она отвечает на вопрос «какой сервис имеет право вызвать этот метод на этом пути», опираясь на криптографическую идентичность, и это отлично закрывает латеральное перемещение внутри кластера. Но она ничего не знает о том, имеет ли конкретный пользователь право видеть конкретный счёт — объектная и строковая авторизация остаётся в приложении. Кроме того, политику обеспечивает прокси, поэтому под без заинжектированного sidecar просто не подпадает под неё, и никакого fail-closed не происходит. Поэтому mesh — это защита в глубину поверх проверок в коде, а не вместо них.

22. Почему трассировка требует участия приложения?

Sidecar видит два независимых события: входящий запрос и исходящий запрос. Он не может знать, что второй порождён первым, потому что между ними ваш процесс с тредпулами и асинхронностью, внутрь которого прокси не смотрит. Связать их можно только через заголовки — traceparent и tracestate или B3-набор, — и скопировать их обязано приложение. В Spring это делает Micrometer Tracing или OTel-агент автоматически для инструментированных клиентов; ломается на «голых» HTTP-клиентах, при переходе в другой поток и на брокерах сообщений. Симптом — вместо одной трассы множество двухспановых огрызков.

23. В чём разница между API Gateway и service mesh?

API Gateway обслуживает north-south трафик — извне от недоверенных клиентов, и решает задачи аутентификации конечного пользователя, квот по тарифам, версионирования публичного контракта, трансформаций и developer portal. Mesh обслуживает east-west — между доверенными сервисами с криптографической идентичностью, и решает mTLS, политики, балансировку и телеметрию. Технически это часто один и тот же Envoy, но задачи разные, и в зрелой системе нужны оба: gateway на периметре, mesh внутри.

24. Когда service mesh не нужен?

Когда сервисов меньше полутора десятков, язык один и нет отдельной команды, готовой эксплуатировать ещё один продукт с собственным жизненным циклом и инцидентами. Также когда трафик преимущественно не HTTP или когда собственная латентность сервисов измеряется единицами миллисекунд и два лишних прокси её удваивают. Замена: Resilience4j для устойчивости, cert-manager и SSL Bundles для mTLS, ingress-контроллер или Gateway API для входа, Micrometer с OTel-агентом для наблюдаемости, NetworkPolicy для базовой сегментации. Разумная стратегия — начать с этого и вводить mesh, когда появится третий язык, причём начинать с ambient ради L4.

25. Что произойдёт, если istiod упадёт на час?

Трафик продолжит идти: Envoy работает на последней полученной конфигурации, соединения и mTLS-сессии не рвутся. Перестанет работать обновление конфигурации — новые поды не попадут в списки эндпоинтов, а удалённые продолжат получать трафик, что даст ошибки при деплоях; новые поды с инжекцией вообще не создадутся, если webhook настроен с failurePolicy: Fail. Через несколько часов начнут истекать сертификаты рабочих нагрузок, и вот тогда начнётся настоящая авария. Поэтому istiod — не SPOF первого рода, но и терпеть его падение больше часа нельзя.

17. Попробовать руками

Все упражнения выполняются на локальном кластере kind (см. главу 47). Базовая подготовка:

Bash
kind create cluster --name mesh --config - <<'CFG'
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
nodes:
  - role: control-plane
  - role: worker
  - role: worker
CFG

istioctl install --set profile=demo -y
kubectl label namespace default istio-injection=enabled
kubectl apply -f https://raw.githubusercontent.com/istio/istio/master/samples/bookinfo/platform/kube/bookinfo.yaml
kubectl apply -f https://raw.githubusercontent.com/istio/istio/master/samples/bookinfo/networking/bookinfo-gateway.yaml
kubectl apply -f https://raw.githubusercontent.com/istio/istio/master/samples/bookinfo/networking/destination-rule-all.yaml

Упражнение 1. Увидеть sidecar и его правила.

Поднимите Bookinfo и выполните kubectl get pod -l app=reviews -o jsonpath='{.items[0].spec.containers[*].name}'.

Ожидаемо: в списке появится istio-proxy рядом с reviews. Затем kubectl exec <pod> -c istio-proxy -- iptables-save -t nat | head -40 покажет цепочки ISTIO_OUTPUT и ISTIO_INBOUND с REDIRECT на порты 15001 и 15006 и правилом RETURN для UID 1337.

Упражнение 2. Canary по весам.

Создайте VirtualService для reviews с весами 90/10 между subsets v1 и v3, затем прогоните сотню запросов:

Bash
for i in $(seq 100); do curl -s "http://$GATEWAY/productpage" | grep -o 'reviews-v[0-9]' | head -1; done | sort | uniq -c

Ожидаемо: соотношение примерно 90 к 10. Поменяйте веса на 50/50 без рестарта подов — распределение изменится в течение секунд.

Упражнение 3. STRICT mTLS и отвалившийся незамешанный клиент.

Создайте namespace outside без метки инжекции, запустите в нём curl-под и убедитесь, что он достучался до productpage.default. Затем примените PeerAuthentication: STRICT в default и повторите запрос.

Ожидаемо: до включения — 200; после — соединение обрывается, а в логе прокси productpage виден отказ. Меш-клиент из default продолжает работать. Верните PERMISSIVE — доступ восстановится.

Упражнение 4. Outlier detection в действии.

Отмасштабируйте ratings до трёх реплик, добавьте DestinationRule с outlierDetection: {consecutive5xxErrors: 3, interval: 5s, baseEjectionTime: 60s, maxEjectionPercent: 67}. Сломайте один под: kubectl exec <ratings-pod> -c ratings -- kill 1 либо переключите его в режим отдачи 500.

Ожидаемо: в kubectl exec <client-pod> -c istio-proxy -- curl -s localhost:15000/clusters | grep ratings у сломанного эндпоинта появится /failed_outlier_check, а счётчик outlier_detection.ejections_active станет больше нуля. Через 60 секунд Envoy вернёт под в пул и, если он всё ещё плох, выкинет снова — уже на большее время.

Упражнение 5. Fault injection и проверка таймаута.

Добавьте fault.delay: {percentage: {value: 100}, fixedDelay: 7s} на маршрут к ratings и timeout: 2s на клиентском маршруте к reviews.

Ожидаемо: запросы возвращаются примерно за 2 секунды с 504, в access-log прокси клиента флаг UT, а в логе прокси ratings — флаг DI. Проверьте на этом же примере ошибку № 19: если поставить delay и timeout на одном маршруте, таймаут не сработает.

Упражнение 6. Найти маршрут через proxy-config.

Bash
POD=$(kubectl get pod -l app=productpage -o jsonpath='{.items[0].metadata.name}')
istioctl proxy-config routes $POD --name 9080 -o json | jq '.[].virtualHosts[] | {name, domains}'
istioctl proxy-config clusters $POD --fqdn reviews.default.svc.cluster.local
istioctl proxy-config endpoints $POD --cluster "outbound|9080|v1|reviews.default.svc.cluster.local"

Ожидаемо: увидите virtual host reviews.default.svc.cluster.local:9080, три кластера по subsets и конкретные IP:порт подов. Теперь удалите subset v3 из DestinationRule, оставив ссылку на него в VirtualService, и повторите запрос — получите 503 с флагом NC, а istioctl analyze укажет на несогласованность.

Упражнение 7. Поймать двойной повтор.

На ratings включите fault.abort: {percentage: {value: 100}, httpStatus: 503}. В VirtualService для ratings задайте retries: {attempts: 3}. Обнулите счётчики и сделайте один запрос:

Bash
kubectl exec $POD -c istio-proxy -- curl -s -X POST localhost:15000/reset_counters
curl -s "http://$GATEWAY/productpage" > /dev/null
kubectl exec $POD -c istio-proxy -- curl -s localhost:15000/stats | grep ratings | grep -E 'retry|rq_total'

Ожидаемо: upstream_rq_retry равен 3, а общее число запросов к вышестоящему сервису — 4 на один клиентский. Добавьте повторы ещё и в клиентское приложение (или второй VirtualService на промежуточном хопе) — увидите перемножение.

Упражнение 8. Кардинальность метрик.

Посчитайте число временных рядов, которые даёт mesh:

Bash
kubectl exec $POD -c istio-proxy -- curl -s localhost:15090/stats/prometheus | grep -c '^istio_requests_total'

Ожидаемо: десятки строк даже на Bookinfo из шести сервисов. Примените Telemetry с tagOverrides: REMOVE для source_canonical_revision и destination_canonical_revision и повторите — число рядов заметно упадёт.

Упражнение 9. Разорвать и починить трассировку.

Прогоните запрос через Bookinfo и посмотрите трассу в Jaeger (istioctl dashboard jaeger). Bookinfo специально пробрасывает заголовки. Теперь разверните свой минимальный Spring Boot-сервис без Micrometer Tracing, поставьте его в середину цепочки и повторите.

Ожидаемо: трасса разорвётся на две несвязанные. Добавьте micrometer-tracing-bridge-otel и повторите — трасса снова целая. Быстрая проверка без Jaeger: послать -H 'x-request-id: TESTME' и грепнуть этот id в логах прокси следующего хопа.

Упражнение 10. Ограничить видимость через Sidecar.

Посмотрите, сколько кластеров знает прокси: istioctl proxy-config clusters $POD | wc -l. Примените Sidecar с egress.hosts: ["./*", "istio-system/*"] и повторите.

Ожидаемо: число кластеров упадёт; замерьте RSS контейнера istio-proxy до и после (kubectl top pod --containers). На маленьком кластере эффект скромный, на большом — кратный.

Упражнение 11. ndots своими глазами.

Bash
kubectl run -it --rm dnstest --image=nicolaka/netshoot --restart=Never -- \
  sh -c 'cat /etc/resolv.conf; time nslookup example.com; time nslookup example.com.'

Ожидаемо: в resolv.conf видны три search-домена и ndots:5; вариант с точкой на конце заметно быстрее. Затем создайте под с dnsConfig.options: [{name: ndots, value: "2"}] и сравните — разница исчезнет.

Упражнение 12. Сломать gRPC L4-балансировкой.

Разверните gRPC-сервис в трёх репликах за обычным ClusterIP и клиент, который держит один канал и шлёт 1000 запросов. Посчитайте распределение по подам (по логам или метрикам).

Ожидаемо: весь трафик уходит в один под. Теперь включите на клиенте sidecar (или перенастройте канал на dns:///<headless>:9090 с round_robin) и повторите — распределение станет равномерным. Третий вариант: оставить L4, но выставить maxConnectionAge: 30s на сервере — распределение выровняется постепенно, скачками при переподключениях.
