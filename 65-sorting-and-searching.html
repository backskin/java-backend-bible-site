65. Сортировка и поиск

17 488 слов≈ 1 ч 35 мин чтения
Зачем это знать

Сортировка и поиск — это не «отдельная тема на собеседовании», а базовый слой, на котором строятся индексы, пользовательские таблицы, маршрутизация запросов, обработка реестров и проверка лимитов. В бэкенде они встречаются везде: сортировка проводок по времени и статусу, поиск второго похожего счёта в реестре, разбиение диапазона на фрагменты, бинарный поиск по ответу в задачах про вместимость сервиса, распределение нагрузки, кэширование и планирование по таймингам. Если вы умеете узнавать по условию нужную технику, код на сортировку и поиск обычно пишется быстро и без переписывания после первого теста.

Сортировка (sorting) — это приведение набора элементов к строго определённому порядку; поиск (search) — это проверка, есть ли в отсортированном или структурированном наборе элемент с нужным свойством. В этой главе мы не будем превращать их в набор «шпаргалок по алгоритмам»; мы будем смотреть, какой вопрос в условии говорит о том, что подходит сортировка, а какой — что лучше делать поиск по массиву или по ответу. Сначала определим критерии эффективности: сравнение, устойчивость, асимптотики и верхнюю оценку n log n. Затем разберём сортировки на сравнении: вставки, слияние, быстрая сортировка, куча и их разные нюансы в Java/Kotlin. После этого перейдём к сортировкам без сравнений: подсчёт, поразрядная и блочная. Далее — выбор k-го элемента, quickselect и медиана, бинарный поиск и его вариации, а в конце — бинарный поиск по ответу, внешняя сортировка и типовые ошибки отладки.

Главная мысль всей главы простая: если условие говорит про порядок, диапазон значений или проверку свойства на полуинтервале, операция почти всегда сводится к сортировке или бинарному поиску. Но не всегда это самый быстрый путь: иногда промежуточный набор по диапазону выгоднее хранить в куче, а иногда лучше вообще не сортировать, а считать частоты или использовать TreeMap/TreeSet или индекс в БД. Там, где разница становится заметной, мы отметим её явно.

1. Сортировка как базовый инструмент

Сортировка — это не просто «расположить элементы по порядку». В инженерной практике она делает две вещи: приводит данные к форме, удобной для дальнейшего перебора, и даёт прямой способ сравнить разные подходы. Внутри один и тот же массив можно отсортировать разными алгоритмами, и их выбор зависит от того, что в условии важнее: устойчивость, память, доступность случайного доступа и значение n. В этом разделе мы закрепим базовые определения и рассмотрим сортировки, которые почти всегда видны на собеседованиях: вставки, слияние, быстрая и кучей.

1.1 Порядок и его значение

Порядок (order) — это отношение сравнения между элементами: a <= b, a < b, a == b. Если между элементами есть естественный или заданный компаратор, сортировка превращает набор данных в единую последовательность, и вскоре становится удобнее искать медиану, проверять дубликаты, считать диапазоны, строить инверсионный набор и объединять таблицы. Для платежей порядок обычно важен по времени, по идентификатору, по сумме, по статусу; для реестров — по дате и ключу. Когда порядок теряется, теряется и возможность быстро ответить на вопрос вроде «какой счёт в той же группе находится прямо рядом» или «какие проводки попали в интервал дат».

Устойчивость (stable sort) — это свойство, при котором если два элемента равны по ключу сортировки, их относительный порядок не меняется. Для проводок это важно, потому что равные по сумме проводки могут быть отсортированы по времени, а вы должны сохранить исходный порядок внутри одинаковых ключей. Если один и тот же алгоритм применяется дважды: сначала по одному ключу, потом по другому, устойчивость позволяет собирать сортировку по нескольким полям без потери порядка внутри группы.

Сравнительная сортировка (comparison sort) — это сортировка, которая решает задачу только с помощью сравнения элементов. Для n различных элементов любую такую сортировку нельзя сделать быстрее, чем Ω(n log n) сравнений в худшем случае: в двоичном дереве решений получается не меньше log₂(n!) узлов, а это эквивалентно n log n. Это нижняя граница, и она важна, потому что она объясняет, почему O(n²) сортировка в реальном проекте обычно не ожидается на больших наборов, даже если она выглядит короткой.

1.2 Сортировка вставками: когда она пригодится в продакшене

Сортировка вставками (insertion sort) работает по принципу «взять следующий элемент и вставить его в уже упорядоченную часть массива». На каждом шаге внутренний цикл ищет позицию и сдвигает элементы вправо, пока не найдет место для текущего. В худшем случае и среднем это O(n²), а в лучшем случае, когда массив почти отсортирован, оно может быть близко к O(n). Для небольших массивов, когда почти все элементы на месте, она часто быстрее более сложных алгоритмов именно за счёт очень маленькой константы.

В продакшене вставка полезна, если массив маленький: список из десятков или сотен элементов, часть данных уже отсортирована, или новая запись вставляется в набор, который всё ещё близок к упорядоченному. В JDK сортировка вставками используется внутри Arrays.sort для небольших кусков при реализации TimSort и dual-pivot quicksort. С точки зрения собеседования это хороший пример проблемы с инвариантом цикла: к моменту обработки a[i] левая часть массива уже отсортирована, а элемент a[i] должен быть вставлен на своё место.

1.3 Задача: сортировка вставками по сумме платежей

Уровень: разминка. Встречается как: Insertion Sort на массиве.

Условие. Дан массив сумм платежей amounts в копейках. Отсортируйте его по возрастанию без использования Arrays.sort, а затем верните отсортированный массив.

Пример. [6, 2, 9, 1, 5] → [1, 2, 5, 6, 9].

Ход решения. Сортировка вставками работает так: предположим, что первые i элементов уже отсортированы. Берём элемент x = amounts[i] и смотрим, куда он должен попасть в левую часть. Сдвигаем большие элементы вправо и вставляем x в освободившееся место. Инвариант цикла: в диапазоне [0, i] все элементы расположены в правильном порядке, и x вставлен в нужное место. Это типичный пример инварианта и снова показывает, почему решения ищут не «дешевую магию», а корректный сдвиг элементов.

Решение на Java.

Java
static int[] insertionSort(int[] amounts) {
    int[] a = amounts.clone();
    for (int i = 1; i < a.length; i++) {
        int x = a[i];
        int j = i - 1;
        while (j >= 0 && a[j] > x) {
            a[j + 1] = a[j];
            j--;
        }
        a[j + 1] = x;
    }
    return a;
}

Решение на Kotlin.

Kotlin
fun insertionSort(amounts: IntArray): IntArray {
    val a = amounts.copyOf()
    for (i in 1 until a.size) {
        val x = a[i]
        var j = i - 1
        while (j >= 0 && a[j] > x) {
            a[j + 1] = a[j]
            j--
        }
        a[j + 1] = x
    }
    return a
}

Сложность. O(n²) времени и O(1) дополнительной памяти. В лучшем случае, когда массив уже отсортирован, время становится O(n).

Крайние случаи и ловушки. Если amounts пустой или из одного элемента, цикл не выполняется. Ошибка — сдвигать элементы при a[j] >= x, тогда равные элементы поменяют местами и устойчивость нарушится. Если надо сохранить исходный порядок одинаковых значений, используйте > вместо >=.

Дополнительные вопросы. «А если значений миллионы и массив почти отсортирован?» — в JDK это уже не вставка, а TimSort/merge sort с бегущими отрезками. «А если нужна сортировка по нескольким полям?» — сравнивать сначала по одному ключу, потом по другому, а устойчивость в этом решении важна.

1.4 Сортировка слиянием: стабильность и рекурсивный разбор

Сортировка слиянием (merge sort) — один из самых понятных алгоритмов на интервью, потому что он работает ровно по той же схеме, что и рекурсия в теории: разбить массив на две части, отсортировать каждую, затем слить их в один. Это одна из немногих сортировок, которые гарантируют O(n log n) времени и стабильность, независимо от исходного порядка. Память в стандартной реализации — O(n) на вспомогательный массив: для каждого сливания нужно место под объединённый результат.

В Java/Kotlin это часто используется для сортировки больших массивов, где память ограничена, но количество данных огромно. Для избежания лишнего копирования иногда делают сортировку на int[] с буфером того же размера и сливают в него; в JDK TimSort и Arrays.parallelSort применяют более сложные схемы, но в учебном смысле merge sort — эталон для мысли «разделяй и властвуй».

1.5 Задача: сортировка слиянием списка платежей по времени

Уровень: средний. Встречается как: Merge Sort.

Условие. Дан массив timestamps с временем в миллисекундах. Отсортируйте его по возрастанию, а затем верните новый массив. Нельзя использовать стандартную сортировку в библиотеке.

Пример. [1700, 100, 900, 200, 1300] → [100, 200, 900, 1300, 1700].

Ход решения. Разложите задачу на три шага. Сначала разделите массив пополам. Затем рекурсивно отсортируйте левую и правую части. В конце вызовите слияние: два указателя проходят по двум половинам и копируют меньший элемент в буфер. Инвариант слияния: буфер всегда содержит первые элементы каждого отсортированного отрезка в правильном порядке, а оставшийся хвост не обработан. Эта постановка ключевая: рекурсия разбивает, а merge-часть объясняет, почему суммарно время O(n log n).

Решение на Java.

Java
static int[] mergeSort(int[] a) {
    if (a.length <= 1) return a.clone();
    int mid = a.length / 2;
    int[] left = mergeSort(Arrays.copyOfRange(a, 0, mid));
    int[] right = mergeSort(Arrays.copyOfRange(a, mid, a.length));
    int[] merged = new int[a.length];
    int i = 0, j = 0, k = 0;
    while (i < left.length && j < right.length) {
        if (left[i] <= right[j]) merged[k++] = left[i++];
        else merged[k++] = right[j++];
    }
    while (i < left.length) merged[k++] = left[i++];
    while (j < right.length) merged[k++] = right[j++];
    return merged;
}

Решение на Kotlin.

Kotlin
fun mergeSort(a: IntArray): IntArray {
    if (a.size <= 1) return a.copyOf()
    val mid = a.size / 2
    val left = mergeSort(a.copyOfRange(0, mid))
    val right = mergeSort(a.copyOfRange(mid, a.size))
    val merged = IntArray(a.size)
    var i = 0
    var j = 0
    var k = 0
    while (i < left.size && j < right.size) {
        if (left[i] <= right[j]) merged[k++] = left[i++]
        else merged[k++] = right[j++]
    }
    while (i < left.size) merged[k++] = left[i++]
    while (j < right.size) merged[k++] = right[j++]
    return merged
}

Сложность. O(n log n) времени и O(n) дополнительной памяти на буфер; глубина рекурсии O(log n).

Крайние случаи и ловушки. Пустой массив и массив из одного элемента чувствительны к тому, когда рекурсия заканчивается. Когда элементы равны, <= сохраняет их относительный порядок и делает сортировку устойчивой. Если писать left[i] < right[j], равные элементы потеряют порядок. Если в проекте нужна сортировка на месте без дополнительного массива, merge sort будет хуже по памяти и не всегда удобен.

Дополнительные вопросы. «Что делать, если массив на миллиарды элементов и память ограничена?» — внешняя сортировка и k-way merge (раздел 7). «Что делать, если сортировать надо не массив, а сущности с несколькими полями?» — применить компаратор и устойчивую сортировку по ключам.

1.6 Быстрая сортировка: идея опорного элемента и её границы

Быстрая сортировка (quicksort) обычно наиболее известна по асимптотике: O(n log n) в среднем, O(n²) в худшем случае на уже отсортированном массиве при плохом выборе опорного элемента. Главная идея — разнести элементы относительно опорного, так чтобы левый блок был меньше опорного, правый — больше, а затем рекурсивно отсортировать оба блока. Опорный элемент выбирается по-разному: середина, медиана трёх, случайный индекс, а в JDK для примитивов используется dual-pivot quicksort, где вместо одного элемента есть два опорных значения.

Ломается quicksort не потому, что он плохой в принципе; он ломается из-за неудачного выбора опорного элемента и отчасти из-за реализации на Java/Kotlin, где ArrayList и объекты в куче заставляют делать лишние обращения к памяти. В задачах на собеседовании этот алгоритм часто принимают и объясняют как «разделяй и властвуй с разбиением», а тесты на корректность строятся через инвариант: все элементы слева от опорного меньше или равны ему, справа — больше или равны ему.

1.7 Задача: быстрая сортировка массива лимитов счетов

Уровень: средний. Встречается как: Quicksort.

Условие. Дан массив лимитов счетов limits в рублях. Отсортируйте его по возрастанию в наивной реализации quicksort без использования библиотек.

Пример. [7, 3, 8, 2, 1, 9] → [1, 2, 3, 7, 8, 9].

Ход решения. Выбираем опорный элемент pivot = a[hi], затем делим массив на три части: left — элементы меньше pivot, equal — равные pivot, right — элементы больше pivot. Сначала идём по массиву, если элемент меньше pivot, меняем его с left, если больше — с right, а равные оставляем в центре. В готовой схеме часто делают partition «на месте» через два указателя i и j. Это ключевой инвариант: все элементы до i меньше pivot, все элементы после j больше pivot, а средняя зона обрабатывается. Затем рекурсивно сортируем левую и правую части. При случайном выборе pivot ожидаемая сложность O(n log n).

Решение на Java.

Java
static void quickSort(int[] a, int lo, int hi) {
    if (lo >= hi) return;
    int pivot = a[hi];
    int i = lo, j = hi;
    while (i < j) {
        while (i < hi && a[i] < pivot) i++;
        while (j > lo && a[j] >= pivot) j--;
        if (i < j) {
            int t = a[i]; a[i] = a[j]; a[j] = t;
            i++; j--;
        }
    }
    if (i < hi) quickSort(a, lo, i);
    if (j > lo) quickSort(a, j, hi);
}

Решение на Kotlin.

Kotlin
fun quickSort(a: IntArray, lo: Int, hi: Int) {
    if (lo >= hi) return

    var i = lo
    var j = hi

Сложность. O(n log n) времени в среднем, O(n²) в худшем случае при плохом выборе опорного элемента, O(log n) глубина рекурсии в среднем, O(n) — в худшем.

Крайние случаи и ловушки. Уже отсортированный массив со случайным pivot может приводить к O(n²), поэтому в продакшене выбирают середину, медиану трёх или случайный элемент. Распределение <= и < важно: если использовать <= в обоих циклах, можно получить зацикливание. Плохой partition часто выглядит корректным, но на повторяющихся значениях начинает зависать на одинаковых элементах.

Дополнительные вопросы. «Что будет при всех одинаковых элементах?» — все элементы попадут в одну сторону, и без выбора медианы quicksort деградирует. «Как сделать сортировку устойчивой?» — stable quicksort в обычной форме неустойчив, поэтому углубляться в TimSort и merge sort легко.

1.8 Сортировка кучей: если нужно top-K или очередность задач

Сортировка кучей (heap sort) реализуется через двоичную кучу: сначала строится max-heap за O(n), затем из корня последовательно извлекаются элементы и помещаются в конец массива. В результате получаем порядок от максимума к минимуму или наоборот, а сложность — O(n log n) времени и O(1) дополнительной памяти. В отличие от merge sort и quicksort она не требует дополнительного массива, но она не устойчива и в реальности обычно используется не как «основная» сортировка, а как инструмент для задач типа top-K, медианы потока и планировщиков.

Если задачу можно решить через PriorityQueue, она почти всегда проще и быстрее в коде, чем собственная heap sort. Но на собеседовании важна именно идея кучи: она хранит максимум в корне, а обновление элемента в куче и заплатка вверх/вниз занимают O(log n). Именно этот механизм объясняет, почему PriorityQueue удобно использовать в задачах про кэш, очереди по приоритету, и k наименьших элементов.

1.9 Задача: top-3 платежа по сумме без полного сортирования

Уровень: средний. Встречается как: Top K via min-heap.

Условие. Дан массив сумм платежей и число k = 3. Найдите три наибольшие суммы без полного сортирования массива.

Пример. [4, 1, 9, 8, 2, 7] → [9, 8, 7].

Ход решения. Если держать в куче только три наибольших элемента, то при прохождении массива новый элемент сравнивается с минимальным из текущих. Если он больше его, удаляем минимум и вставляем новый. В корне min-heap лежит минимальное из текущего «пула лучших». В итоге после обработки всего массива куча содержит ровно top-3. С точки зрения алгоритма это то же, что и задача выбора k-й статистики: число хранимых элементов не растёт, а стоимость вставки/удаления в куче — O(log k), поэтому общая сложность O(n log k).

Решение на Java.

Java
static int[] topK(int[] a, int k) {
    PriorityQueue<Integer> minHeap = new PriorityQueue<>();
    for (int x : a) {
        if (minHeap.size() < k) minHeap.offer(x);
        else if (x > minHeap.peek()) {
            minHeap.poll();
            minHeap.offer(x);
        }
    }
    int[] res = new int[minHeap.size()];
    int i = res.length - 1;
    while (!minHeap.isEmpty()) res[i--] = minHeap.poll();
    return res;
}

Решение на Kotlin.

Kotlin
fun topK(a: IntArray, k: Int): IntArray {
    val minHeap = PriorityQueue<Int>()
    for (x in a) {
        if (minHeap.size < k) minHeap.offer(x)
        else if (x > minHeap.peek()) {
            minHeap.poll()
            minHeap.offer(x)
        }
    }
    val res = IntArray(minHeap.size)
    var i = res.size - 1
    while (minHeap.isNotEmpty()) {
        res[i--] = minHeap.poll()
    }
    return res
}

Сложность. O(n log k) времени и O(k) памяти.

Крайние случаи и ловушки. Если k больше числа элементов, возвращаем весь массив или ещё один маркер. Важно не смешивать min-heap и max-heap: в top-K нужен minimum в вершине. Если значения дублируются, > и >= решают вопрос о том, надо ли выталкивать элемент, который уже равен текущему минимуму. Если ставить >=, возможны лишние обмены и менее стабильный порядок решений.

Дополнительные вопросы. «А если нужен top-K по нескольким полям?» — куча хранит кортеж score, id и сравнение ведётся по компаратору; это уже задача из главы 67 (67-heaps-intervals-greedy.md). «А если нужно не top-K, а k-й по порядку?» — quickselect и порядок статистики, раздел 4.

2. Устойчивость, компараторы и сортировка по нескольким полям

Слушая условие, можно легко пропустить один критерий, который потом ломает всю логику: надо не просто отсортировать элементы, а отсортировать их по нескольким ключам и сохранить внутренний порядок равных элементов. Здесь в игру вступают устойчивость и компараторы. Для финансовых записей это особенно важно: проводки могут иметь одинаковую сумму, но не одинаковый статус, клиент или время; промежуточная сортировка по одному ключу не должна менять другой.

2.1 Значение устойчивости

Устойчивость — это гарантия, что при сортировке по ключу K равные значения не меняют своего порядка относительно друг друга и относительно исходного массива. Если сначала отсортировать проводки по статусу, а потом по времени, без устойчивости вы потеряете естественный порядок внутри каждой группы. А если сортировать по нескольким полям в одном проходе через Comparator.comparing(), важно, какие поля имеют приоритет: сначала дата, затем сумма, затем ID, а внутри одинаковой даты — исходный порядок. Программно это делается через Comparator.comparingLong(...).thenComparingLong(...).thenComparing(...) или Kotlin sortedWith(compareBy<Payment> { it.date }.thenBy { it.amount }).

В теории сортировки устойчивость гарантирует, что часть равных элементов с идентичным ключом останется в том порядки, в котором они встречались. В повседневном бэкенде это полезно при сортировке по status, а потом по createdAt, где несколько транзакций могут иметь одинаковое время и одинаковый статус.

2.2 Задача: реестр проводок с сортировкой по нескольким полям

Уровень: средний. Встречается как: Stable sort with compound comparator.

Условие. Дана таблица проводок Payment { id, status, amount, createdAt }. Нужно отсортировать её по статусу, а внутри каждого статуса — по времени создания от раннего к позднему; при равном времени — сохранить исходный порядок. В массиве может быть до 10⁵ записей.

Пример. Проводки: [(p2, PENDING, 100, 10), (p1, OK, 50, 20), (p3, PENDING, 200, 5), (p4, OK, 100, 15)] → порядок статуса OK сначала, затем PENDING, а внутри одинакового статуса — по createdAt.

Ход решения. Правильный путь — использовать устойчивый алгоритм сортировки и компаратор по нескольким ключам. Сначала сравниваем статус: OK раньше PENDING или наоборот в зависимости от бизнес-логики. Затем сравниваем createdAt. Два объекта считаются равными по ключу, если их и статус, и время одинаковые; тогда устойчивость сохраняет исходный входной порядок. В Java это делается через Comparator и List.sort; в Kotlin — sortedWith(compareBy<Payment> { it.statusRank }.thenBy { it.createdAt }).

Решение на Java.

Java
record Payment(String id, String status, long amount, long createdAt) {}

static List<Payment> sortPayments(List<Payment> payments) {
    Comparator<Payment> cmp = Comparator
        .comparingInt((Payment p) -> switch (p.status()) {
            case "OK" -> 0;
            case "PENDING" -> 1;
            default -> 2;
        })
        .thenComparingLong(Payment::createdAt);
    return payments.stream().sorted(cmp).toList();
}

Решение на Kotlin.

Kotlin
data class Payment(val id: String, val status: String, val amount: Long, val createdAt: Long)

fun sortPayments(payments: List<Payment>): List<Payment> =
    payments.sortedWith(compareBy<Payment> { p ->
        when (p.status) {
            "OK" -> 0
            "PENDING" -> 1
            else -> 2
        }
    }.thenBy { it.createdAt })

Сложность. O(n log n) времени и O(n) памяти для List.sort с дополнительным массивом или O(log n) стека в TimSort, но в общем виде это сортировка по сравнению.

Крайние случаи и ловушки. Не используйте status.compareTo() без нормализации, иначе строки вроде OK, ok, Ok дадут кусочно разный порядок. Если несколько платежей имеют одинаковые status и createdAt, устойчивость должна сохранить исходный порядок. Если массив должен быть отсортирован по amount и только потом по createdAt, это другой ключевой порядок, не тот, что в условии.

Дополнительные вопросы. «А что если статусов больше десятка?» — используйте rank map и общий comparator. «А если нужно сохранять не только порядок, но и собирать стабильную сортировку через несколько проходов?» — применяйте устойчивую сортировку и thenComparing.

2.3 Задача: сортировка списка реестра по временной метке и идентификатору

Уровень: разминка. Встречается как: Sorting by several keys.

Условие. Дан список записей о реестре: (id, ts, amount). Отсортировать сначала по ts от раннего к позднему, затем по amount по убыванию, затем по id по возрастанию. Нельзя менять порядок при равенстве по всем трём полям.

Пример. [(b, 10, 100), (a, 10, 200), (c, 9, 50)] → [(c, 9, 50), (a, 10, 200), (b, 10, 100)].

Ход решения. Каждый следующий ключ — это падение приоритетов: сначала проверяем ts, затем amount, затем id. В Java Comparator раскрывает естественный метод дедукции «сначала один ключ, затем второй». В Kotlin compareBy на порядок ключей работает тем же способом. Если в равенстве по всем ключам вернуться 0, то общая стабильность сохраняется, а собственный обратный порядок для одинаковых ключей — нет.

Решение на Java.

Java
record Entry(String id, long ts, long amount) {}

static List<Entry> sortEntries(List<Entry> data) {
    Comparator<Entry> cmp = Comparator
        .comparingLong(Entry::ts)
        .thenComparingLong((Entry e) -> -e.amount())
        .thenComparing(Entry::id);
    return data.stream().sorted(cmp).toList();
}

Решение на Kotlin.

Kotlin
data class Entry(val id: String, val ts: Long, val amount: Long)

fun sortEntries(data: List<Entry>): List<Entry> =
    data.sortedWith(compareBy<Entry> { it.ts }
        .thenByDescending { it.amount }
        .thenBy { it.id })

Сложность. O(n log n) времени, O(n) памяти.

Крайние случаи и ловушки. Для thenComparingLong((e) -> -e.amount()) важно, что amount до 10¹² и -amount не переполнится в long, поэтому обычно либо Comparator.reverseOrder, либо thenComparingLong(e -> -e.amount()) в безопасных диапазонах. Если amount может быть максимально большим, лучше сравнивать через Long.compare и оборачивание Long.compare(amount, other.amount).

Дополнительные вопросы. «Как сделать сортировку одновременно по корректности и по дате?» — через comparator с rank map. «Как упростить код?» — вынести comparator в отдельную функцию.

2.4 Задача: компаратор для лимита и статуса клиента

Уровень: средний. Встречается как: Comparator-based sort.

Условие. У клиента есть status и limit в рублях. Сортируйте клиентов по приоритету: VIP > ACTIVE > NEW > BLOCKED, при равном статусе — по limit от большего к меньшему.

Пример. [NEW, 100], [VIP, 300], [ACTIVE, 200], [BLOCKED, 500] → [VIP, 300], [ACTIVE, 200], [NEW, 100], [BLOCKED, 500].

Ход решения. Используем rank map и Comparator.comparingInt, но в Kotlin можно сделать when для статуса. Важный момент — группировка по статусу задаёт порядок, а внутри группы — сортировка по числовому ключу. В этом случае statusRank — это просто функция преобразования String → число, а не магия.

Решение на Java.

Java
record Client(String name, String status, long limit) {}

static List<Client> sortClients(List<Client> clients) {
    Comparator<Client> cmp = Comparator
        .comparingInt((Client c) -> switch (c.status()) {
            case "VIP" -> 0;
            case "ACTIVE" -> 1;
            case "NEW" -> 2;
            case "BLOCKED" -> 3;
            default -> 4;
        })
        .thenComparingLong((Client c) -> -c.limit());
    return clients.stream().sorted(cmp).toList();
}

Решение на Kotlin.

Kotlin
data class Client(val name: String, val status: String, val limit: Long)

fun sortClients(clients: List<Client>): List<Client> =

        when (it.status) {
            "VIP" -> 0
            "ACTIVE" -> 1

Сложность. O(n log n) времени и O(n) памяти.

Крайние случаи и ловушки. Если статусов много, rank map лучше, чем switch в каждом сравнении. Если сравнение идёт по limit от большего к меньшему, не используйте thenBy { it.limit } без descending.

Дополнительные вопросы. «А если нужно сортировать в обратном направлении, но со стабильностью?» — используйте Comparator.reverseOrder на одном поле и сохраняйте порядок при равенстве через thenComparing. «А если статусы приходят в нижнем регистре?» — нормализуйте в нижний регистр до компаратора.

3. Сортировка без сравнений: подсчёт, поразрядная и блочная

Нижняя граница n log n относится только к сортировке через сравнение. Если значения принадлежат ограниченному диапазону или имеют известную структуру (например, цифры или байты), можно сортировать за O(n + k), O(n · d) и даже без отдельных сравнений. Такие подходы важны в бэкенде не потому, что они красивы, а потому что диапазон значений часто известен заранее: возраст клиента, номер карты, сервисный код, многие поля в реестрах и протоколах.

3.1 Подсчётная сортировка: когда диапазон мал

Подсчётная сортировка (counting sort) работает, если значения лежат в ограниченном диапазоне, например 0..k или 1..k, и нам нужно просто посчитать, сколько раз встретилось каждое значение. Затем из счётчиков строится результат. Время — O(n + k), память — O(k). Это идеально для букв, байт, возраста, статусов, служебных кодов. В Java это не «интерфейс стандартной библиотеки», а техника, и её стоит помнить как особый случай, когда простая таблица частот делает все сравнения лишними.

Проблема в том, что если диапазон огромен — например, все long от -9e18 до 9e18, — тогда k выходит за пределы разумного. В этом случае поразрядная сортировка (radix sort) или сортировка с компаратором лучше.

3.2 Задача: сортировка возрастов клиентов подсчётом

Уровень: разминка. Встречается как: Counting Sort.

Условие. У клиента возраст от 0 до 120. Отсортируйте массив возрастов подсчётом.

Пример. [24, 7, 42, 7, 81, 24] → [7, 7, 24, 24, 42, 81].

Ход решения. Создайте массив cnt[121]. Для каждого возраста увеличивайте соответствующий счётчик. Затем идите по диапазону 0..120 и выписывайте каждый возраст столько раз, сколько раз он встретился. Это не сортировка сравнением: мы не сравниваем элементы напрямую, а считаем их частоты. Преимущество в том, что для ограниченного диапазона она почти линейна.

Решение на Java.

Java
static int[] countingSort(int[] ages) {
    int[] cnt = new int[121];
    for (int age : ages) cnt[age]++;
    int[] out = new int[ages.length];
    int idx = 0;
    for (int age = 0; age <= 120; age++) {
        while (cnt[age]-- > 0) out[idx++] = age;
    }
    return out;
}

3.3 Поразрядная сортировка: цифры, IP-адреса и номера карт

Поразрядная сортировка (radix sort) работает по цифрам числа: сначала сортирует по младшему разряду, потом по следующему, и так до старшего. Для десятичного числа это 10 кучек, для 32-битного числа — 2 байта, 256 сегментов, и процесс повторяется по 4 байтам. На уровне асимптотики это O(d · (n + k)) для d разрядов и фиксированного основания, что хорошо для целых чисел и строк фиксированной длины.

В бэкенде radix sort реальный смысл в том, что числа часто укладываются в узкий диапазон байт и разрядов, а сравнение элементов как объектов дорого. Это актуально для идентификаторов, кодов статусов, IP-адресов, карт и шифрованных хэшей, где логика не требует сравнения как строк, а наоборот — надо явно сортировать по байтам. Подобное применяется и в системах пошивки/просмотра больших реестров.

3.4 Задача: поразрядная сортировка 32-битных идентификаторов

Уровень: средний. Встречается как: Radix sort.

Условие. Дан массив long-идентификаторов в диапазоне [0, 2^32); отсортировать их по возрастанию без Arrays.sort.

Пример. [123456, 999, 1000, 42] → [42, 999, 1000, 123456].

Ход решения. Сначала сортируем по младшим байтам, потом по следующим, и так далее, пока не пройдём все 4 байта. Для каждого прохода создаём count[256] и выполняем stable counting sort по одному байту. Ключевое наблюдение: значения в одном байте независимы и достаточно ограничены (0..255), поэтому можно использовать массив счётчиков. Техника называется LSD-версией radix sort: least significant digit first. Она стабильно сохраняет относительный порядок по предыдущее разряду.

Решение на Java.

Java
static int[] radixSort(int[] a) {
    int[] out = a.clone();
    int[] count = new int[256];
    for (int shift = 0; shift < 4; shift++) {
        Arrays.fill(count, 0);
        for (int x : out) {
            int b = (x >>> (shift * 8)) & 0xFF;
            count[b]++;
        }
        for (int i = 1; i < 256; i++) count[i] += count[i - 1];
        int[] tmp = new int[out.length];
        for (int i = out.length - 1; i >= 0; i--) {
            int x = out[i];
            int b = (x >>> (shift * 8)) & 0xFF;
            tmp[--count[b]] = x;
        }
        out = tmp;
    }
    return out;
}

Решение на Kotlin.

Kotlin
fun radixSort(a: IntArray): IntArray {
    var out = a.copyOf()
    val count = IntArray(256)
    repeat(4) { shift ->
        count.fill(0)
        for (x in out) {
            val b = (x.toUInt() shr (shift * 8)).toInt() and 0xFF
            count[b]++
        }
        for (i in 1 until 256) count[i] += count[i - 1]
        val tmp = IntArray(out.size)
        for (i in out.indices.reversed()) {
            val x = out[i]
            val b = (x.toUInt() shr (shift * 8)).toInt() and 0xFF

        }
        out = tmp
    }
    return out
}

Сложность. O(d · (n + k)) = O(4·(n + 256)) ≈ O(n), при условии фиксированного числа байт. Память O(n + k).

Крайние случаи и ловушки. Если данные знаковые, используйте >>> вместо >>, чтобы не распространять знаковый бит. Если значения отрицательные, сначала их нужно нормализовать или сортировать по абсолютному значению через два диапазона; на собеседовании осторожно отмечайте, что radix sort для знаковых int требует отдельной подготовки. В Kotlin UInt помогает явно нормализовать без знакового вставления.

Дополнительные вопросы. «А если строки фиксированной длины?» — то же самое, но по байтам строки. «А если длины переменные?» — выйти на trie / radix tree или сортировку по длине и затем по символам. «А если есть BigInteger?» — поразрядная сортировка по байтам служит только для фиксированных размеров.

3.5 Задача: сортировка словарных значений небольшим алфавитом

Уровень: разминка. Встречается как: Counting sort over alphabet.

Условие. Дан массив строк words длиной до 20, каждая строка состоит только из символов a–z. Отсортировать их лексикографически.

Пример. ["cab", "aaa", "ab"] → ["aaa", "ab", "cab"].

Ход решения. Если алфавит мал и длина строки ограничена, можно использовать сортировку по символам от конца к началу (LSD radix sort) или сортировку подсчётом по позициям. Это важное отличие от стандартной строки compareTo(): здесь сама структура символов и алфавита задокументирована и ограничена. При условии маленького алфавита мы легко можем сделать count[26] на позиции, а затем собрать результат.

Решение на Java.

Java
static String[] sortWords(String[] words) {
    String[] out = words.clone();
    int maxLen = 0;
    for (String w : out) maxLen = Math.max(maxLen, w.length());
    for (int pos = maxLen - 1; pos >= 0; pos--) {
        int[] count = new int[26];
        for (String w : out) {
            if (pos < w.length()) count[w.charAt(pos) - 'a']++;
        }
        for (int i = 1; i < 26; i++) count[i] += count[i - 1];
        String[] tmp = new String[out.length];
        for (int i = out.length - 1; i >= 0; i--) {
            String w = out[i];
            if (pos < w.length()) {
                int idx = w.charAt(pos) - 'a';
                tmp[--count[idx]] = w;
            }
        }
        out = tmp;
    }
    return out;
}

Решение на Kotlin.

Если алфавит включает заглавные буквы, диапазон уже 52 или 256, а нужно не забыть коды символов.

Дополнительные вопросы. «А если строки не в маленьком алфавите?» — лексикографическая сортировка через String.compareTo и TimSort или radix sort по UTF-16 кодам. «А если нужно искать по префиксу?» — trie или radix tree (глава 69 69-advanced-data-structures.md).

4. Выбор k-го элемента, quickselect и медиана

В реальном коде и на собеседовании часто требуется не полная сортировка, а поиск элемента, который стоит на k-ом месте: медиана, верхний квантиль, тридцатый процентиль, top-K и k наименьших. Полная сортировка здесь является перебором, а quickselect — естественная оптимизация, которая выбирает порядковую статистику за O(n) в среднем и O(n²) в худшем случае.

4.1 Quickselect и его инвариант

Quickselect (selection algorithm) — это quicksort, который сортирует только тот блок, который содержит искомый индекс k. Как и в quicksort, выбирается опорный элемент и делается partition: слева — меньше pivot, справа — больше pivot. Если индекс pivot равен k, задача решена; если индекс меньше k, ищем в правой части; если больше — в левой. Инвариант: между двумя указателями все элементы слева меньше pivot, справа больше pivot, а положение pivot известно. Из него следует, что всего мы обрабатываем один блок, а не итоговый массив полностью.

Quickselect — стандартный способ вычисления медианы в потоке или выборки без сортировки. Для k малых относительно n это очень эффективно; для устойчивого алгоритма по порядковой статистике в Java обычно используют Arrays.sort на отрезке и выбирают k, но если речь о миллионах элементов и частых запросах, quickselect лучше.

4.2 Задача: k-я наименьшая сумма в реестре

Уровень: средний. Встречается как: Kth smallest element.

Условие. Дан массив сумм проводок amounts длиной n. Найдите k-ю наименьшую сумму, если k отсчитывается от 1 (1-индексация), и 1 <= k <= n.

Пример. [7, 2, 5, 1, 9, 3], k = 3 → 3 (сортировка: [1, 2, 3, 5, 7, 9]).

Ход решения. Если сортировать весь массив, задача решается за O(n log n). Quickselect уменьшает эту цену до O(n) в среднем. Он отбрасывает одну сторону partition и ищет только блок, где лежит индекс k. После каждого partition выборка становится уже и решение корректно доводится до k-го элемента. Плюс — это стандартная техника для медианы потока без явной сортировки всего массива.

Решение на Java.

Java
static int kthSmallest(int[] a, int k) {
    int lo = 0, hi = a.length - 1;
    while (lo <= hi) {
        int pivot = a[(lo + hi) / 2];
        int left = lo, right = hi;
        while (left <= right) {
            while (a[left] < pivot) left++;
            while (a[right] > pivot) right--;
            if (left <= right) {
                int t = a[left]; a[left] = a[right]; a[right] = t;
                left++; right--;
            }
        }
        if (right >= k && right >= lo) hi = right;
        else if (left <= k && left <= hi) lo = left;
        else return pivot;
    }
    return a[k];
}

Решение на Kotlin.

Kotlin
fun kthSmallest(a: IntArray, k: Int): Int {
    var lo = 0
    var hi = a.size - 1
    while (lo <= hi) {

        var left = lo
        var right = hi

Сложность. O(n) времени в среднем, O(1) дополнительной памяти, но O(n²) в худшем случае при плохом pivot.

Крайние случаи и ловушки. k должен быть корректный. При k = 0 или k >= n нужно либо выбросить исключение, либо вернуть Integer.MIN_VALUE в соответствии с договором. В quicksort-подобном partition у равных значений важно избегать зацикливания и left/right пересечения.

Дополнительные вопросы. «А если нужно 3 наибольших элементов?» — heap или quickselect. «А если нужно медиана в потоке?» — две кучи (minHeap + maxHeap), см. главу 67 (67-heaps-intervals-greedy.md). «А если нужен порядковый элемент в отсортированном массиве?» — можно использовать бинарный поиск с ответом по индексу.

4.3 Задача: медиана массива без полной сортировки

Уровень: средний. Встречается как: Median selection.

Условие. Дана выборка баллов пользователей scores; найти медиану, то есть ((n+1)/2)-й элемент для нечетного n или среднее двух центральных элементов для чётного n.

Пример. [5, 15, 1, 3, 2] → 3.

Ход решения. Если задача «среднее двух центральных элементов» и массив не сортирован, можно сделать quickselect для n/2 и (n/2)-1, затем взять среднее. Это даёт O(n) в среднем и избегает полного Arrays.sort. Когда данные уже структурированы как массив без лишних операций, quickselect часто выглядит «локальной» и корректной техникой.

Решение на Java.

Java
static double median(int[] a) {
    int n = a.length;
    int[] b = a.clone();
    int left = n / 2;
    int right = (n - 1) / 2;
    if (n % 2 == 0) {
        int l = kthSmallest(b, right);
        int r = kthSmallest(b, left);
        return (l + r) / 2.0;
    }
    return kthSmallest(b, n / 2);
}

Решение на Kotlin.

Kotlin
fun median(a: IntArray): Double {
    val n = a.size
    val b = a.copyOf()
    return if (n % 2 == 0) {
        val left = kthSmallest(b, n / 2 - 1)
        val right = kthSmallest(b, n / 2)
        (left + right) / 2.0
    } else {
        kthSmallest(b, n / 2).toDouble()
    }
}

Сложность. O(n) в среднем, O(n²) в худшем случае.

Крайние случаи и ловушки. Для чётного массива медиана — среднее двух центральных значений; для нечётного — среднее значение на позиции n/2. Учитывайте целочисленное деление: ((left + right) / 2.0) необходимо для корректного double результата. Если данные могут быть длинными, используйте long.

Дополнительные вопросы. «А если массив очень большой и запросы являются частыми?» — две кучи или сбалансированная BST. «А если в потоке постоянно приходит новый элемент?» — медиана потока через две кучи.

4.4 Задача: top-K частот по сумме платежей

Уровень: средний. Встречается как: Top K by frequency.

Условие. Дан массив сумм платежей, нужно найти k наиболее частые суммы; если две суммы одинаково часты, порядок по сумме неважен.

Пример. [3, 1, 3, 4, 4, 4, 5], k = 2 → {4: 3, 3: 2} или {3: 2, 4: 3} в зависимости от критериев; обычно выбирают самые частые сначала.

Ход решения. Сначала считаем частоты: Map<Integer, Integer> freq. Затем превращаем их в список пар (freq, value) и сортируем по убыванию частоты, а при равенстве — по значению. Это задача не про quickselect, а про хеширование плюс сортировку. Если k мало, можно держать heap на частоты и вставлять только лучшие значения. В главе 64 (64-arrays-hashing-two-pointers.md) есть уже идеи про хеш-таблицы; здесь мы используем их в сочетании с порядком.

Решение на Java.

Java
static List<Integer> topFreq(int[] a, int k) {
    Map<Integer, Integer> freq = new HashMap<>();
    for (int x : a) freq.merge(x, 1, Integer::sum);
    return freq.entrySet().stream()
        .sorted((e1, e2) -> Integer.compare(e2.getValue(), e1.getValue()))
        .limit(k)
        .map(Map.Entry::getKey)
        .toList();
}

Решение на Kotlin.

Kotlin
fun topFreq(a: IntArray, k: Int): List<Int> {
    val freq = mutableMapOf<Int, Int>()
    for (x in a) freq[x] = (freq[x] ?: 0) + 1
    return freq.entries
        .sortedByDescending { it.value }
        .take(k)
        .map { it.key }
}

Сложность. O(n + m log m), где m — число уникальных значений, обычно m <= n.

Крайние случаи и ловушки. Если нужна очередь по частоте и значению, у Comparator должны быть оба ключа. Если k > m, возвращаем все m элементов и не падаем. Если a пустой, возвращаем пустой список.

Дополнительные вопросы. «А если сделать это в потоке?» — top-K в потоках через heap или sketch-структуры. «А если значений много и память ограничена?» — Count-Min Sketch и Heavy hitters, что взято в главе 76 (76-algorithms-in-backend.md).

4.5 Задача: next greater element в отсортированном массиве

Уровень: средний. Встречается как: Search in sorted array.

Условие. Дан отсортированный массив a и число x; вернуть наименьший элемент, который строго больше x, либо -1, если такого нет.

Пример. [1, 3, 5, 7, 9], x = 5 → 7. x = 9 → -1.

Ход решения. Это variant of lower bound: найти первую позицию, где a[i] > x. В отсортированном массиве это типичная задача для бинарного поиска, а не quickselect: здесь нужен не k-й элемент, а точная граница. Мы ищем первую позицию, где условие a[mid] <= x ложно, а затем перемещаем границы. Это хорошо отрабатывает на собеседовании и на реальных данных.

Решение на Java.

Java
static int nextGreater(int[] a, int x) {
    int lo = 0, hi = a.length;
    while (lo < hi) {
        int mid = lo + (hi - lo) / 2;
        if (a[mid] <= x) lo = mid + 1;
        else hi = mid;
    }
    return lo < a.length ? a[lo] : -1;
}

Решение на Kotlin.

Kotlin
fun nextGreater(a: IntArray, x: Int): Int {
    var lo = 0
    var hi = a.size
    while (lo < hi) {
        val mid = lo + (hi - lo) / 2
        if (a[mid] <= x) lo = mid + 1 else hi = mid
    }
    return if (lo < a.size) a[lo] else -1
}

Сложность. O(log n) времени, O(1) памяти.

Крайние случаи и ловушки. Не пишите if (a[mid] < x) lo = mid + 1, иначе найдёте первое >= x вместо > x. Если x больше всех элементов, lo уходит в конец и надо вернуть -1. На собеседовании часто спрашивают «а что, если есть дубликаты?» — тогда вы работаете с lower/upper bound и граничными условиями.

Дополнительные вопросы. «А если нужно найти первый элемент, который >= x, а не > x?» — это lower bound. «А если массив не отсортирован?» — быстрое решение не существует без сортировки.

5. Бинарный поиск и его варианты

Бинарный поиск — это алгоритм для отсортированного массива, который уменьшает диапазон поиска вдвое на каждом шаге. Он выглядит простым, но в реальных задачах ломаются не сама идея, а граничные условия: low, high, mid, проверка <= vs <, и выбор, что возвращать при дубликатах. Для бэкенда бинарный поиск — это способ ускорить любой поиск в упорядоченном наборе, а также основа бинарного поиска по ответу, который строит решение в задачах про вместимость, временную цену или разбиение на кластеры.

5.1 Задача: поиск элемента в отсортированном массиве

Уровень: разминка. Встречается как: Binary Search.

Условие. Дан отсортированный массив a и число x; вернуть индекс x, если он есть, иначе -1.

Пример. [1, 3, 5, 7, 10], x = 7 → 3; x = 8 → -1.

Ход решения. Выбираем lo и hi, а затем вычисляем mid = lo + (hi - lo) / 2. Если a[mid] == x, ответ найден; если a[mid] < x, сдвигаем lo вправо; иначе двигаем hi влево. После каждого шага диапазон сокращается примерно вдвое. Это пример верификации через инвариант: при каждом шаге куска массива слева от lo точно не содержит x, справа от hi тоже не содержит, а x может быть только в [lo, hi].

Решение на Java.

Java
static int binarySearch(int[] a, int x) {
    int lo = 0, hi = a.length - 1;
    while (lo <= hi) {
        int mid = lo + (hi - lo) / 2;
        if (a[mid] == x) return mid;
        if (a[mid] < x) lo = mid + 1;
        else hi = mid - 1;
    }
    return -1;
}

Решение на Kotlin.

Kotlin
fun binarySearch(a: IntArray, x: Int): Int {
    var lo = 0
    var hi = a.size - 1
    while (lo <= hi) {
        val mid = lo + (hi - lo) / 2
        when {
            a[mid] == x -> return mid
            a[mid] < x -> lo = mid + 1
            else -> hi = mid - 1
        }
    }
    return -1
}

Сложность. O(log n) времени, O(1) памяти.

Крайние случаи и ловушки. Пустой массив. Один элемент. x меньше всех элементов or больше. Если hi = a.length и использовать lo < hi, а не lo <= hi, возможно пропуск ответа. В бинарном поиске очень часто теряется одно из двух условий: либо используйте закрытый диапазон [lo, hi], либо открытый [lo, hi), но не смешивайте их в одной реализации.

Дополнительные вопросы. «А если массив может быть неотсортирован?» — без сортировки искать логарифмически нельзя. «А если нужен первый индекс, где a[i] >= x?» — lower bound. «А если в массиве дубликаты?» — lower bound/upper bound.

5.2 Задача: поиск первого вхождения x

Уровень: средний. Встречается как: Lower bound; first occurrence.

Условие. Дан отсортированный массив с дубликатами a, найти индекс первого элемента, равного x, или -1, если его нет.

Пример. [1, 2, 2, 2, 3], x = 2 → 1. x = 4 → -1.

Ход решения. Это задача lower bound: искать первую позицию, в которой a[pos] >= x. После нахождения проверяем, равен ли элемент x; если да, это первый индекс. Если не равен, значит x нет. Важное отличие от обычного binary search: перемещаем hi не влево при a[mid] == x, а держим в кандидатах до тех пор, пока не сужаем к первой левой границе. Стандартная реализация: while (lo < hi) { mid = ...; if (a[mid] >= x) hi = mid; else lo = mid + 1; }

Решение на Java.

Java
static int firstIndex(int[] a, int x) {
    int lo = 0, hi = a.length;
    while (lo < hi) {
        int mid = lo + (hi - lo) / 2;
        if (a[mid] >= x) hi = mid;
        else lo = mid + 1;
    }
    return (lo < a.length && a[lo] == x) ? lo : -1;
}

Решение на Kotlin.

Kotlin

Крайние случаи и ловушки. Важна корректная семантика hi = a.length и lo < hi. Если x меньше всех элементов, lo = 0. Если x больше всех элементов, lo = a.length и возвращается -1. Для x в середине дубликатов важна проверка a[mid] >= x, а не >.

Дополнительные вопросы. «А как найти lastIndex?» — lower bound на x + 1, то есть upper bound. «А если массив полностью заполнен одинаковыми значениями?» — ответом будет начало массива, и lowerBound это корректно находит.

5.3 Задача: поиск последнего вхождения x

Уровень: средний. Встречается как: Upper bound; last occurrence.

Условие. Дан отсортированный массив a с дубликатами, найти индекс последнего элемента, равного x.

Пример. [1, 2, 2, 2, 3], x = 2 → 3.

Ход решения. Ищем first index для x + 1 и отнимаем единицу. Это основная техника: upperBound(x) возвращает позицию первого элемента строго больше x, а последняя позиция x равна upperBound(x) - 1. Более прямой вариант — бинарный поиск на a[mid] <= x, и в конце lo будет индексом последнего x.

Решение на Java.

Java
static int lastIndex(int[] a, int x) {
    int lo = 0, hi = a.length;
    while (lo < hi) {
        int mid = lo + (hi - lo) / 2;
        if (a[mid] <= x) lo = mid + 1;
        else hi = mid;
    }
    int pos = lo - 1;
    return pos >= 0 && a[pos] == x ? pos : -1;
}

Решение на Kotlin.

Kotlin

Дополнительные вопросы. «Как найти число элементов в диапазоне [L, R]?» — upperBound(R) - lowerBound(L). «Как это применяется в реестрах?» — поведение строится на индексе и сортировке по ключам.

5.4 Задача: поиск в повернутом отсортированном массиве

Уровень: сложный. Встречается как: Rotated Sorted Array Search.

Условие. Дан массив, который был отсортирован по возрастанию, а затем циклически сдвинут. Найдите индекс целевого элемента x или -1.

Пример. [4, 5, 6, 7, 0, 1, 2], x = 0 → 4.

Ход решения. Сначала проверяем, какая половина массива отсортирована: если a[lo] <= a[mid], левая половина отсортирована; иначе отсортирована правая. Затем проверяем, лежит ли x в отсортированной половине и сузить диапазон. Это стандартный пример «сортированный участок + выброс», где можно сократить поиск не в два раза, а в среднем вдвое за каждый шаг. Здесь нужен инвариант: один участок полный и упорядочен, второй — сдвинут.

Решение на Java.

Java
static int searchRotated(int[] a, int x) {
    int lo = 0, hi = a.length - 1;
    while (lo <= hi) {
        int mid = lo + (hi - lo) / 2;
        if (a[mid] == x) return mid;
        if (a[lo] <= a[mid]) {
            if (a[lo] <= x && x < a[mid]) hi = mid - 1;
            else lo = mid + 1;
        } else {
            if (a[mid] < x && x <= a[hi]) lo = mid + 1;
            else hi = mid - 1;
        }
    }
    return -1;
}

Решение на Kotlin.

Kotlin

Дополнительные вопросы. «А что, если поворот больше одного?» — это всё тот же сдвиг, но задача не меняется. «А если нужен поиск максимума?» — это peak element и тоже сводится к половине, где массив монотонен.

5.5 Задача: поиск пика в массиве

Уровень: средний. Встречается как: Peak element.

Условие. Найдите индекс элемента, который больше соседей: a[i] > a[i - 1] и a[i] > a[i + 1], либо значение удовлетворяет другим критериям. Массив не обязательно отсортирован, но можно предполагать локальный пик.

Пример. [1, 3, 20, 4, 1, 0] → 20 на индексе 2.

Ход решения. В массиве есть локальный пик, потому что есть максимум. Если a[mid] < a[mid + 1], пик обязан быть справа; если a[mid] > a[mid + 1], пик обязан быть слева. Это типичный вариационный бинарный поиск: на каждом шаге сравниваем соседей и смотрим, где ещё есть рост. Массив не отсортирован целиком, но в любой момент есть направление, куда идти.

Решение на Java.

Java
static int findPeak(int[] a) {
    int lo = 0, hi = a.length - 1;
    while (lo < hi) {
        int mid = lo + (hi - lo) / 2;
        if (a[mid] < a[mid + 1]) lo = mid + 1;
        else hi = mid;
    }
    return lo;
}

Решение на Kotlin.

Дополнительные вопросы. «А если нужно найти не один пик, а все пики?» — это уже задача по сканированию и разбиению на восходящие/нисходящие участки. «А если массив содержит плоские вершины?» — нужно уточнить, что считать «пиком» и как сравнивать >= и >.

5.6 Задача: search space / check by predicate

Уровень: средний. Встречается как: Binary search on predicate.

Условие. Дан массив мест, где каждая позиция означает время, и ограничение: можно обслужить до m клиентов за limit. Нужно найти минимальный limit, при котором условие выполняется.

Пример. times = [1, 3, 5, 7], m = 3 → минимальный limit = 3.

Ход решения. Это уже не поиск по массиву, а поиск по ответу: значение limit является не элементом массива, а параметром. Мы определяем предикат can(limit): можно ли обслужить всех клиентов за это время. Этот предикат монотонен по limit — если limit достаточно велик, всё выполняется; при малых значениях не выполняется. Поэтому бинарный поиск по limit работает: ищем наименьшее допустимое значение. Отсюда и следующее разделение главы — бинарный поиск по ответу.

Решение на Java.

Java
static boolean canServe(int[] times, int limit, int m) {
    int cnt = 0;
    for (int t : times) cnt += (t <= limit ? 1 : 0);
    return cnt >= m;
}

static int minLimit(int[] times, int m) {
    int lo = 0, hi = 1_000_000_000;
    while (lo < hi) {
        int mid = lo + (hi - lo) / 2;
        if (canServe(times, mid, m)) hi = mid;
        else lo = mid + 1;
    }
    return lo;
}

Решение на Kotlin.

Kotlin
fun canServe(times: IntArray, limit: Int, m: Int): Boolean =
    times.count { it <= limit } >= m

Крайние случаи и ловушки. Предикат должен быть монотонным: если при limit = L он истинный, то и для больших значений он истинный. Если предикат не монотонен, бинарный поиск по ответу теряет смысл. Важна проверка hi = maxPossible. Если массив пустой, возвращается 0 или выбрасывается исключение.

Дополнительные вопросы. «А если надо найти максимальный limit, при котором условие ещё сохраняется?» — то же самое, только меняем логику на can и ищем hi. «А если can занимает O(log n)`?» — общее время умножается на это.

6. Бинарный поиск по ответу

Бинарный поиск не всегда ищет элемент в массиве. Часто вопрос в условии звучит так: «какой максимум/минимум/порог можно выбрать, если контракт — свойство от этого параметра монотонно меняется?» Это класс задач, которые на языке собеседования называются «binary search on answer». Он встречается при распределении нагрузки, проверке вместимости, минимизации времени маршрута, выборе пропускной способности и максимальной допустимой длины сегмента.

6.1 Задача: минимальное число дней для покраски сада

Уровень: средний. Встречается как: Minimum number of days to make bouquets.

Условие. Есть массив bloomDay — день, когда конкретный цветок расцветает. Нужно собрать m букетов, каждый из k цветов. За один день можно собрать ровно один букет. Найти минимальное число дней, при котором можно собрать все букеты.

Пример. bloomDay = [1, 10, 3, 10, 2], m = 3, k = 1 → 2.

Ход решения. Предикат can(day) говорит: можно ли сделать m букетов к дню day? Он монотонный: если можно сделать сегодня, то можно и позже. Поэтому бинарный поиск по дню от 0 до максимального раскрывает минимальный достаточный день. Внутри предиката идёт проход по массиву и считаем длину последовательности цветов, которые уже расцвели. Это универсальный подход для многих задач про пропускную способность и минимальное время.

Решение на Java.

Java
static boolean canMake(int[] bloomDay, int day, int m, int k) {
    int bouquets = 0, current = 0;
    for (int x : bloomDay) {
        if (x <= day) {
            current++;
            if (current == k) {
                bouquets++;
                current = 0;
                if (bouquets >= m) return true;
            }
        } else {
            current = 0;
        }
    }
    return false;
}

static int minDays(int[] bloomDay, int m, int k) {
    if (m * k > bloomDay.length) return -1;
    int lo = 0, hi = Arrays.stream(bloomDay).max().orElse(0);
    while (lo < hi) {
        int mid = lo + (hi - lo) / 2;
        if (canMake(bloomDay, mid, m, k)) hi = mid;
        else lo = mid + 1;
    }
    return lo;
}

Не забывайте, что can(day) монотонен: если на день d можно сделать максимум, то и на d + 1 тоже. Если не строить предикат, решение легко влетает в n² или просто ищет не тот параметр.

Дополнительные вопросы. «А если нужно распределить по разным типам ресурсов?» — предикат станет двумерным и потребует ещё одну структуру решения. «А если m и k большие?» — оценивайте диапазон ответа и n log R.

6.2 Задача: максимальная грузоподъёмность упаковки

Уровень: средний. Встречается как: Capacity to ship packages.

Условие. Есть массив weights с массами посылок; нужно распределить их по days дням так, чтобы грузоподъёмность на один день была не выше capacity, и минимизировать capacity.

Пример. [1, 2, 3, 4, 5, 6, 7, 8, 9], days = 3 → минимальный capacity = 29.

Ход решения. Предикат can(capacity) выглядит так: можно ли разбить массив на не более days групп, каждая группа не превышает capacity? Если это можно сделать при capacity = C, то при большем capacity тоже можно, поэтому предикат монотонный. Теперь бинарный поиск на capacity от max(weight) до sum(weights) находит минимально допустимую вместимость. Это стандартный шаблон для распределения ресурса и планирования времени.

Решение на Java.

Java
static boolean canShip(int[] weights, int cap, int days) {
    int used = 0, groups = 1;
    for (int w : weights) {
        if (used + w > cap) {
            groups++;
            used = w;
            if (groups > days) return false;
        } else {
            used += w;
        }
    }
    return true;
}

static int minCapacity(int[] weights, int days) {
    int lo = Arrays.stream(weights).max().orElse(0);
    int hi = Arrays.stream(weights).sum();
    while (lo < hi) {
        int mid = lo + (hi - lo) / 2;
        if (canShip(weights, mid, days)) hi = mid;
        else lo = mid + 1;
    }
    return lo;
}

Решение на Kotlin.

Kotlin
fun canShip(weights: IntArray, cap: Int, days: Int): Boolean {

Сложность. O(n log S) времени, где S = sum(weights) - max(weights), O(1) памяти.

Дополнительные вопросы. «А если нужно минимизировать не единую вместимость, а распределить по нескольким контейнерам с разными ограничениями?» — это уже задача про ограничение на несколько параллельных ресурсов. «А если дни имеют разные приоритеты?» — появляются более сложные предикаты.

6.3 Задача: минимальное время на выполнение задач с ограничением скорости

Уровень: сложный. Встречается как: Koko Eating Bananas / time to complete tasks.

Условие. Есть массив piles с количеством бананов в пещерах, а H — число часов. За один час можно съесть не более k бананов. Нужно найти минимальную скорость k, которую нужно поддерживать, чтобы съесть все бананы до истечения H часов.

Пример. [3, 6, 7, 11, 12], H = 8 → 4.

Ход решения. Предикат can(k) возвращает true, если все пещеры можно съесть не более чем за H часов при скорости k; это монотонно зависит от параметра. Далее бинарный поиск по k от 1 до max(piles) находит минимально допустимую скорость. Здесь важно правильно считать время: ceil(pile / k). И ни в коем случае не использовать double там, где можно считать в long и Math.ceilDiv.

Решение на Java.

Java
static boolean canEat(int[] piles, int speed, int hours) {
    long total = 0;
    for (int p : piles) total += (p + speed - 1L) / speed;
    return total <= hours;
}

static int minEatingSpeed(int[] piles, int hours) {
    int lo = 1, hi = Arrays.stream(piles).max().orElse(1);
    while (lo < hi) {
        int mid = lo + (hi - lo) / 2;
        if (canEat(piles, mid, hours)) hi = mid;
        else lo = mid + 1;
    }
    return lo;
}

6.4 Задача: минимальная сумма, при которой можно раздать заявки

Уровень: сложный. Встречается как: Allocate books / minimum sum to satisfy capacity.

Условие. Есть список страниц книг pages, и нужно разделить их на students сегментов так, чтобы каждый сегмент суммарно не превышал maxSum. Найти минимальный возможный maxSum.

Пример. [12, 34, 67, 90], students = 2 → 113.

Ход решения. Выбираем ответ maxSum и проверяем, можно ли разметить массив на students сегментов так, чтобы сумма в каждом сегменте не превышала ответ. Это монотонное условие, поэтому задача решается бинарным поиском по ответу. Если значение maxSum слишком мало, не хватает сегментов; если достаточно, решение допустимо.

Решение на Java.

Java
static boolean canSplit(int[] pages, int cap, int students) {
    int groups = 1, sum = 0;
    for (int p : pages) {
        if (sum + p > cap) {
            groups++;
            sum = p;
            if (groups > students) return false;
        } else {
            sum += p;
        }
    }
    return true;
}

static int minPages(int[] pages, int students) {
    int lo = Arrays.stream(pages).max().orElse(0);
    int hi = Arrays.stream(pages).sum();
    while (lo < hi) {
        int mid = lo + (hi - lo) / 2;
        if (canSplit(pages, mid, students)) hi = mid;
        else lo = mid + 1;
    }
    return lo;
}

6.5 Задача: минимальная пропускная способность потока с задержками

7. Внешняя сортировка, merge k списков и сортировка больших наборов

Внешняя сортировка нужна, когда данные не помещаются в память: их разбивают на части, сортируют каждую часть и объединяют результаты слиянием k отсортированных списков (k-way merge). На собеседовании об этом случае порой забывают. В бэкенде это реально встречается при обработке реестров, больших выгрузок, ежедневных репортов, ETL-потоков и консолидации данных между несколькими хранилищами. Она полезна и тогда, когда памяти хватает на одну часть, но не на весь объём данных целиком.

7.1 Сортировка больших файлов: chunk + merge

Внешняя сортировка (external sort) — это метод, который работает с данными, не помещающимися целиком в оперативную память. Сначала данные берутся порциями, каждая порция сортируется в памяти, затем записывается на диск или в временный файл. После этого выполняется k-way merge: несколько отсортированных файлов сливаются в один итоговый список. Основной признак задачи здесь — данные во много раз больше, чем память. Это не «магия» и не особая память на JVM; это проектирование порядка работы с файлами.

7.2 Задача: merge k отсортированных списков

Уровень: средний. Встречается как: K-way merge.

Условие. Дана коллекция List<List<Integer>> из k отсортированных массивов. Слить их в один отсортированный массив.

Пример. [[1, 4, 7], [2, 5], [3, 6, 8]] → [1, 2, 3, 4, 5, 6, 7, 8].

Ход решения. Для каждого списка сохраняем текущий указатель; выбираем минимальный из текущих элементов и добавляем его в итог. Это задача k-way merge на мини-куче: в куче хранятся текущие значения и индекс списка. Поскольку удаление минимального и вставка в кучу стоят O(log k), общая сложность O(n log k), где n — общее число элементов. Это важная техника для внешней сортировки и для систем, где данные материализуются по фрагментам.

Решение на Java.

Java
static int[] mergeK(int[][] lists) {
    PriorityQueue<int[]> heap = new PriorityQueue<>(Comparator.comparingInt(a -> a[0]));
    int total = 0;
    for (int i = 0; i < lists.length; i++) {
        if (lists[i].length > 0) {
            heap.offer(new int[]{lists[i][0], i, 0});
            total += lists[i].length;
        }
    }
    int[] out = new int[total];
    int idx = 0;
    while (!heap.isEmpty()) {
        int[] cur = heap.poll();
        out[idx++] = cur[0];
        int listIndex = cur[1], pos = cur[2];
        if (pos + 1 < lists[listIndex].length) {
            heap.offer(new int[]{lists[listIndex][pos + 1], listIndex, pos + 1});
        }
    }
    return out;
}

7.3 Задача: объединение двух отсортированных массивов

Уровень: разминка. Встречается как: Merge two sorted arrays.

Условие. Даны два отсортированных массива a и b; объедините их в один отсортированный массив.

Пример. [1, 3, 5] и [2, 4, 6] → [1, 2, 3, 4, 5, 6].

Ход решения. Это простая версия merge sort: поддерживаем два указателя и итеративно выбираем меньший элемент. Объём данных может быть большим, но операция не требует HashMap и не является n²; на каждом шаге один элемент переносится в output. Для массивов разных длин это особенно удобно.

Решение на Java.

Java
static int[] mergeTwo(int[] a, int[] b) {
    int[] out = new int[a.length + b.length];
    int i = 0, j = 0, k = 0;
    while (i < a.length && j < b.length) {
        if (a[i] <= b[j]) out[k++] = a[i++];
        else out[k++] = b[j++];
    }
    while (i < a.length) out[k++] = a[i++];
    while (j < b.length) out[k++] = b[j++];
    return out;
}

7.4 Задача: поиск медианы двух отсортированных массивов

Уровень: сложный. Встречается как: Median of two sorted arrays.

Условие. Dados две отсортированные половины left и right; найти медиану объединённого массива. Параметр n + m может быть чётным или нечётным.

Пример. [1, 3] и [2] → 2, [1, 2] и [3, 4] → 2.5.

Ход решения. Есть два подхода. Первый — объединить массивы (O(n + m)) и взять среднюю. Второй — бинарный поиск по меньшему массиву, чтобы найти точку разделения, где левая половина всех элементов не больше правой. Это классическая задача для внешней подготовки: по сути вы ищете оптимальный разрез так, чтобы max(leftPart) <= min(rightPart). Это стандартный подход, используемый в интервью на уровне middle/senior.

Решение на Java.

Java
static double medianOfTwo(int[] a, int[] b) {
    if (a.length > b.length) return medianOfTwo(b, a);
    int total = a.length + b.length;
    int lo = 0, hi = a.length;
    while (lo <= hi) {
        int partA = lo + (hi - lo) / 2;
        int partB = (total + 1) / 2 - partA;
        int leftA = partA == 0 ? Integer.MIN_VALUE : a[partA - 1];
        int rightA = partA == a.length ? Integer.MAX_VALUE : a[partA];
        int leftB = partB == 0 ? Integer.MIN_VALUE : b[partB - 1];
        int rightB = partB == b.length ? Integer.MAX_VALUE : b[partB];
        if (leftA <= rightB && leftB <= rightA) {
            if ((total & 1) == 1) return Math.max(leftA, leftB);
            return (Math.max(leftA, leftB) + Math.min(rightA, rightB)) / 2.0;
        }
        if (leftA > rightB) hi = partA - 1;
        else lo = partA + 1;
    }
    throw new IllegalArgumentException("invalid input");
}

fun medianOfTwo(a: IntArray, b: IntArray): Double {

Дополнительные вопросы. «А если массивы не отсортированы?» — решение уже не может быть O(log n). «А если количества очень велики и данные на диске?» — нужна внешняя сортировка и особые ограничения по памяти.

7.5 Задача: суммирование отсортированных диапазонов

Уровень: разминка. Встречается как: Sorted ranges / merge intervals.

Условие. Есть массив диапазонов [start, end], и надо вернуть объединённый набор непересекающихся диапазонов. Этот тип задач часто воспринимают как сортировку по началу и слияние. Сумма также может быть рассчитана по start и end в поиске событий.

Пример. [[1, 3], [2, 6], [8, 10], [15, 18]] → [[1, 6], [8, 10], [15, 18]].

Ход решения. Сначала сортируем диапазоны по началу, стабильно и по длине. Затем идём по списку: если текущий диапазон пересекается с предыдущим, расширяем его до максимума end; иначе добавляем новый в результат. Это классическая техника, которая встречается при планировании и выделении временных окон. У неё есть явная связь с сортировкой: first produce sorted intervals, then sweep by pointer.

Решение на Java.

Java
static int[][] mergeIntervals(int[][] intervals) {
    Arrays.sort(intervals, Comparator.comparingInt(a -> a[0]));
    List<int[]> merged = new ArrayList<>();
    for (int[] interval : intervals) {
        if (merged.isEmpty() || interval[0] > merged.get(merged.size() - 1)[1]) {
            merged.add(interval.clone());
        } else {
            merged.get(merged.size() - 1)[1] = Math.max(merged.get(merged.size() - 1)[1], interval[1]);
        }
    }
    return merged.toArray(new int[0][]);
}

Решение на Kotlin.

Сложность. O(n log n) времени на сортировку и O(n) памяти на результат.

Крайние случаи и ловушки. Если диапазоны уже отсортированы, можно избежать отдельной сортировки и использовать линейный sweep. Если они пересекаются по одному краю, > vs >= определяет, надо ли объединять их: [1, 2] и [2, 3] обычно объединяются при interval[0] <= lastEnd, потому что границы совпадают и они перекрываются.

Дополнительные вопросы. «А если нужно найти максимальный набор непересекающихся интервалов?» — это уже жадный алгоритм, и его можно лечить через сортировку по end. «А если есть тысячи интервалов и нужно быстро проверять запросы?» — тогда сгруппировка по start/end и индексирование.

8. Диагностика и отладка решений

Настоящий код на сортировку и поиск часто оказывается правильным по идее, но ломается на одном из типовых граничных случаев. Здесь важен не только ответ, но и набор проверок, которые считают корректность без «магии» и без хрупкого тестового набора. В этом разделе собраны самые типичные ошибки и диагностика: пустой массив, один элемент, повторяющиеся значения, Integer.MIN_VALUE, проверка == против >=, off-by-one и bad partition.

8.1 Классические ошибки в сортировке

  1. Сравнение >= вместо > в insertion sort ломает устойчивость.
  2. В quicksort проверка while (a[j] >= pivot) и while (a[i] < pivot) нужна именно в такой форме; иначе на равных элементах зацикливается.
  3. В merge sort ошибка на единицу в правом хвосте while (j < right.length) ведёт к потере последнего элемента.
  4. В heap sort или PriorityQueue забывают, что top-K uses min-heap, а не max-heap.
  5. В quickselect при неудачном pivot и left/right одна и та же часть массива может повторно анализироваться.
  6. В binary search смешиваются режимы [lo, hi] и [lo, hi): это почти всегда ошибка на единицу и результат — либо утечка за границу, либо бесконечный цикл.
  7. В upper bound/lower bound путаница <= и < приводит к поиску предыдущего/следующего элемента, а не первого нужного.
  8. В radix sort для signed int забывают про >>> и беззнаковое смещение, и код ломается на отрицательных значениях.
  9. В задачах по поиску в повёрнутом массиве нужно проверять a[lo] и a[mid], а не только x relative to mid.
  10. В бинарном поиске по ответу забывают, что предикат должен быть монотонен: если он не монотонен, поиск на обе стороны некорректен.

8.2 Тестирование сортировки и поиска

Самый полезный набор работает так:

  • пустой массив;
  • один элемент;
  • два элемента;
  • все элементы одинаковые;
  • уже отсортированный массив;
  • обратный порядок;
  • массив с дубликатами и одним уникальным числом;
  • массив с отрицательными значениями;
  • Integer.MIN_VALUE, Integer.MAX_VALUE и границы long при переводе в long;
  • для поиска: элемент в начале, в середине, в конце, отсутствующий элемент;
  • для quicksort: равные элементы и pivot на крайнем правом индексе;
  • для binary search on answer: проверка монотонности предиката на нескольких mid.

На практике полезно держать маленький тестовый скрипт, где для случайного массива n = 10..200 сравнивается результат вашей функции с той же задачей, но через Arrays.sort и проверяемых предикатов. Для задач с большой n достаточно 1000–10000 случайных входов и проверки на корректность и флексируемость на крайних случаях.

8.3 Задача: диагностический стресс-тест для quicksort

Уровень: средний. Встречается как: Randomized correctness check.

Условие. Напишите минимальный стресс-тест, который сравнивает quickSort на 500 случайных массивах против Arrays.sort и убеждается, что массив всегда корректно отсортирован.

Ход решения. Генерируйте случайный массив длиной от 0 до 100, заполняйте его случайными числами от -100 до 100, затем копируйте в expected и сортируйте стандартным способом. Сравните результат с вашей сортировкой. Важно проверять не только корректность на нескольких примерах, но и повторы, отрицательные значения и равные элементы. Если код в сортировке зависает или даёт некорректный порядок из-за partition, стресс-тест быстро находит его.

Решение на Java.

Java
static void stressQuickSort() {
    Random rnd = new Random(0);
    for (int t = 0; t < 1000; t++) {
        int n = rnd.nextInt(100);
        int[] a = new int[n];
        int[] expected = new int[n];
        for (int i = 0; i < n; i++) {
            int v = rnd.nextInt(201) - 100;
            a[i] = v;
            expected[i] = v;
        }
        quickSort(a, 0, a.length - 1);
        Arrays.sort(expected);
        if (!Arrays.equals(a, expected)) {
            throw new AssertionError("quickSort mismatch: " + Arrays.toString(a) + " vs " + Arrays.toString(expected));
        }
    }
}

Сложность. O(T · n log n): перебор случайных случаев.

Крайние случаи и ловушки. Не используйте assert в production-скрипте: часть проекта требует check(boolean, String) и исключение, а не assert-сценарий. Случайный генератор должен быть детерминированным, чтобы сбой не пропал после повторного запуска. Если в коде есть >= на равных элементах, тесты быстро начнут показывать пустые или бесконечные циклы.

Дополнительные вопросы. «А как стрессировать binary search for answer?» — то же самое, но с can(mid) и expected computed by brute force. «А если нужно измерить скорость?» — JMH, но это уже тема главы 45 (45-performance.md).

9. Вопросы на интервью

  1. Что такое устойчивость и почему она важна при сортировке проводок по нескольким полям? Ответ: устойчивость сохраняет исходный порядок равных элементов по главному ключу и позволяет делать многоключевую сортировку как последовательность сортировок по одному полю; без этого можно потерять исходный порядок внутри одной и той же группы.
  2. Почему сортировка слиянием стабильна, а quicksort не обязан быть устойчивым? Ответ: merge sort объединяет два отсортированных массива, сохраняя порядок равных элементов, а quicksort работает через partition, где равные элементы могут пересекаться и менять местами.
  3. Что такое lower bound и upper bound? Ответ: lower bound — первая позиция >= x, upper bound — первая позиция > x; их разница — это число элементов равных x.
  4. Почему бинарный поиск на массиве требует отсортированного порядка? Ответ: только при отсортированном массиве можно сказать, что левая часть массива заведомо меньше x, а правая — больше, и тем самым сократить диапазон вдвое.
  5. Что такое quickselect и в чём отличие от quicksort? Ответ: quicksort сортирует обе стороны partition, а quickselect продолжает искать только область, где лежит индекс k, поэтому он может быть O(n) в среднем вместо O(n log n).
  6. Почему поразрядная сортировка может быть линейной по n на фиксированном размере ключа? Ответ: она проходит фиксированное число раз по данным и каждый раз делает линейное устойчивое распределение по диапазону 0..255 или 0..9.
  7. Когда counting sort быстрее, чем сортировка по сравнению? Ответ: когда диапазон значений мал и фиксирован, такой как возраст 0..120 или символы 26-алфавита.
  8. Что такое n log n lower bound в сравнительной модели? Ответ: на n элементов любая сортировка, которая сравнивает элементы только через </>, имеет не меньше log₂(n!) сравнений в худшем случае.
  9. Какие данные лучше сортировать кучей, а какие — merge sort? Ответ: heap sort хорошо подходит для top-K, order statistics и ограниченного побочного пространства; merge sort — для стабильной сортировки и внешней сортировки больших файлов.
  10. Почему в binary search по ответу предикат должен быть монотонным? Ответ: иначе нет гарантий, что ответ лежит в одном непрерывном отрезке, и двоичный поиск не имеет логики сокращения диапазона.
  11. Как распознать задачу на first true? Ответ: это поиск минимального x, для которого predicate(x) == true; условие должно быть монотонным.
  12. Что такое partitions в quicksort и почему равные элементы опасны? Ответ: partition выделяет блоки меньше/больше pivot; если не корректно обработать равные элементы, возможны бесконечные циклы или потеря данных.
  13. Какую задачу решает k-way merge? Ответ: слить несколько отсортированных потоков в один отсортированный результат за O(n log k), где k — количество входных списков.
  14. Что важнее: O(n log n) или постоянные множители? Ответ: для больших n асимптотика всё равно решает, но на маленьких массивах insertion sort может побеждать в реальном времени за счёт маленькой константы и кэш-локальности.
  15. Почему ArrayList / IntArray используют разные асимптотики? Ответ: int[] и IntArray хранят примитивы подряд, а ArrayList<Integer> хранит ссылки на объекты, а значит больше расход памяти и меньше локальность; это обыгрывается на практике.
  16. Что делать, если массив не помещается в память? Ответ: внешне сортировать по фрагментам и делать k-way merge на диске, а не пытаться держать всё в JVM.
  17. В чем разница между сортировкой по amount и по status? Ответ: ключ и порядок направления задаются бизнес-логикой, а стабильность гарантирует сохранение порядка внутри равных ключей.
  18. Что такое sentinel в бинарных поисках? Ответ: искусственный диапазон [lo, hi] / [lo, hi) с проверкой границ, который помогает избежать ArrayIndexOutOfBoundsException.
  19. Какой вид бинарного поиска использовать при дубликатах? Ответ: lower bound и upper bound, а не обычный search, если важна граница массива.
  20. Как определить, что задача требует binary search on answer вместо binary search in array? Ответ: если искомое значение не содержится в массиве как элемент, а является параметром от решения, и предикат монотонен по этому параметру.

11. Дополнительные задачи

11.1 Задача: поиск первой отсутствующей положительной величины

Уровень: средний. Встречается как: First Missing Positive.

Условие. Дан массив целых чисел nums; найдите наименьшее положительное целое число, которого нет в массиве, и верните его. Считайте, что n <= 10^5.

Пример. [1, 2, 0] → 3; [3, 4, -1, 1] → 2.

Ход решения. Элементы можно «перекладывать» на место по индексу: если nums[i] лежит в диапазоне [1, n] и не на своём месте, меняем его местами; если уже стоит на месте, пропускаем. После перестановки все небольшие числа занимают корректно свои позиции, и ответ — первое число, которое не нашлось.

Решение на Java.

Java
static int firstMissingPositive(int[] nums) {
    int n = nums.length;
    for (int i = 0; i < n; i++) {
        while (nums[i] > 0 && nums[i] <= n && nums[nums[i] - 1] != nums[i]) {
            int t = nums[nums[i] - 1];
            nums[nums[i] - 1] = nums[i];
            nums[i] = t;
        }
    }
    for (int i = 0; i < n; i++) {
        if (nums[i] != i + 1) return i + 1;
    }
    return n + 1;
}

Решение на Kotlin.

Kotlin
fun firstMissingPositive(nums: IntArray): Int {
    val n = nums.size
    var i = 0
    while (i < n) {
        val x = nums[i]
        if (x > 0 && x <= n && nums[x - 1] != x) {
            val tmp = nums[x - 1]
            nums[x - 1] = x
            nums[i] = tmp
        } else {
            i++
        }
    }
    for (j in nums.indices) {
        if (nums[j] != j + 1) return j + 1
    }
    return n + 1
}

Сложность. O(n) времени и O(1) памяти.

Крайние случаи и ловушки. Если массив пустой, ответ 1. Если элемент вне диапазона [1, n], его пропускают. Ошибка — не писать условие на nums[nums[i] - 1] != nums[i], иначе бесконечный цикл.

Дополнительные вопросы. «А если надо не минимальное число, а удалить дубликаты на месте?» — это уже задача про cyclic sort и индексы. «А если в массиве есть long?» — правило такое же, но диапазон должен быть скорректирован.

11.2 Задача: перестановка двух чисел местами без временной переменной

Уровень: разминка. Встречается как: Swap without temp.

Условие. Обменять местами элементы массива a[i] и a[j], не используя дополнительную переменную.

Пример. [1, 5, 9, 3] с i = 1, j = 3 → [1, 3, 9, 5].

Ход решения. Используем XOR: a[i] ^= a[j]; a[j] ^= a[i]; a[i] ^= a[j]. Это классический трюк для чисел, но он работает только на целых типах и требует осторожности с int-переполнением. В Java/Kotlin это быстро, но не всегда лучше читается, поэтому в продакшене чаще применяют временную переменную.

Решение на Java.

Java
static void swapXor(int[] a, int i, int j) {
    a[i] ^= a[j];
    a[j] ^= a[i];
    a[i] ^= a[j];
}

Решение на Kotlin.

Kotlin
fun swapXor(a: IntArray, i: Int, j: Int) {
    a[i] = a[i] xor a[j]
    a[j] = a[j] xor a[i]
    a[i] = a[i] xor a[j]
}

Сложность. O(1) времени и O(1) памяти.

Крайние случаи и ловушки. Для одинаковых индексов всё остаётся корректным, но это обычно не имеет смысла. Если значения превышают диапазон int, то XOR-решение перестаёт быть корректным для big-endian / 64-bit cases; для long используют Long-вариант. В коде как на собеседовании это допустимо, но только когда условие явно про int/long.

Дополнительные вопросы. «А если нужен обмен объектов?» — XOR не работает для ссылок, а обычная временная переменная или value copy — единственный безопасный способ. «А если в массиве двоичные данные?» — не используйте эту технику без строгого контракта.

11.3 Задача: удалить дубликаты в отсортированном массиве

Уровень: разминка. Встречается как: Remove Duplicates from Sorted Array.

Условие. Дан отсортированный массив nums; удалить дубликаты на месте, оставив каждый элемент не более одного раза.

Пример. [1, 1, 2, 2, 3] → [1, 2, 3] с новым размером 3.

Ход решения. Два указателя: write указывает на место записи, read — на текущий просмотренный элемент. Если nums[read] отличается от nums[write - 1], записываем его в позицию write и сдвигаем write. Идея в том, что отсортированный массив позволяет сравнивать только соседние элементы, а не весь префикс.

Решение на Java.

Java
static int removeDuplicates(int[] nums) {
    if (nums.length == 0) return 0;
    int write = 1;
    for (int read = 1; read < nums.length; read++) {
        if (nums[read] != nums[write - 1]) nums[write++] = nums[read];
    }
    return write;
}

Решение на Kotlin.

Kotlin
fun removeDuplicates(nums: IntArray): Int {
    if (nums.isEmpty()) return 0
    var write = 1
    for (read in 1 until nums.size) {
        if (nums[read] != nums[write - 1]) nums[write++] = nums[read]
    }
    return write
}

Сложность. O(n) времени, O(1) памяти.

Крайние случаи и ловушки. Для пустого массива и одиночного элемента решение корректно. Если сравнивать с nums[read - 1], а не с nums[write - 1], то результат будет тем же, но при write = 0 можно легко уйти в ошибку. При неотсортированном массиве алгоритм неверен.

Дополнительные вопросы. «А если нужно оставить не один, а k копий каждого значения?» — это та же самая схема с write and read, но условие сравнения чуть сложнее. «А если массив не сортирован?» — сначала сортировка, затем дубликаты.

11.4 Задача: contains duplicate и расстояние по индексу

Уровень: средний. Встречается как: Contains Duplicate II.

Условие. Даны числа nums и допустимое расстояние k; проверьте, есть ли два одинаковых значения на расстоянии не больше k по индексам.

Пример. [1, 2, 3, 1], k = 3 → true; [1, 0, 1, 1], k = 1 → true.

Ход решения. Скользящее окно по индексу: словарь value -> lastIndex. Если число уже встретилось и i - lastIndex <= k, возвращаем true; иначе обновляем lastIndex. Общее правило: если условие касается расстояния по индексам, то HashMap/MutableMap с последним индексом делает задачу линейной.

Решение на Java.

Java
static boolean containsNearbyDuplicate(int[] nums, int k) {
    Map<Integer, Integer> last = new HashMap<>();
    for (int i = 0; i < nums.length; i++) {
        Integer prev = last.put(nums[i], i);
        if (prev != null && i - prev <= k) return true;
    }
    return false;
}

Решение на Kotlin.

Kotlin
fun containsNearbyDuplicate(nums: IntArray, k: Int): Boolean {
    val last = mutableMapOf<Int, Int>()
    for ((i, x) in nums.withIndex()) {

    }

}

Сложность. O(n) времени, O(n) памяти.

Крайние случаи и ловушки. Если k отрицательный, задача некорректна. Если k больше длины массива, проверка естественно работает. Нужно помнить, что для двух одинаковых чисел на расстоянии k бывает достаточно последнего индекса, а не самого раннего.

Дополнительные вопросы. «А если расстояние по значению, а не по индексу?» — это уже другая задача. «А если нужно найти все повторяющиеся пары?» — надо хранить все вхождения в Map.

11.5 Задача: элемент большинства по Бойеру–Муру

Уровень: средний. Встречается как: Majority Element.

Условие. Дан массив nums; если есть элемент, который встречается больше n/2 раз, верните его.

Пример. [2, 2, 1, 2, 3] → 2.

Ход решения. Схема голосования Бойера–Мура: выберите кандидата и count. Когда следующий элемент совпадает с кандидатом, увеличиваем count; иначе уменьшаем count. Когда count становится 0, переходим к новому кандидату. После первого прохода есть кандидат, но его ещё нужно проверить через второй проход; такого элемента гарантированно не более одного.

Решение на Java.

Java
static int majorityElement(int[] nums) {
    int candidate = 0, count = 0;
    for (int x : nums) {
        if (count == 0) {
            candidate = x;
            count = 1;
        } else if (x == candidate) count++;
        else count--;
    }
    int verify = 0;
    for (int x : nums) if (x == candidate) verify++;
    return verify > nums.length / 2 ? candidate : -1;
}

Решение на Kotlin.

Kotlin
fun majorityElement(nums: IntArray): Int {
    var candidate = 0
    var count = 0
    for (x in nums) {
        if (count == 0) {
            candidate = x
            count = 1
        } else if (x == candidate) count++ else count--
    }
    val verify = nums.count { it == candidate }
    return if (verify > nums.size / 2) candidate else -1
}

Сложность. O(n) времени и O(1) памяти.

Крайние случаи и ловушки. Если элемента большинства нет, функция возвращает -1. В задачах сборки запроса иногда нужен count и неистинный кандидат, а не просто HashMap. Не забывайте второй проход верификации: кандидат после первого прохода ещё не доказан.

Дополнительные вопросы. «А если нужно найти более чем один кандидат с > n / 3?» — это уже Boyer-Moore на два кандидата и несколько счетчиков. «А если массив большой и потоки идут бесконечно?» — это вероятностные решения и sketch-структуры.

11.6 Задача: пересечение двух массивов без повторов

Уровень: разминка. Встречается как: Intersection of two arrays.

Условие. Даны два массива nums1 и nums2; вернуть их пересечение без повторов.

Пример. [1, 2, 2, 1] и [2, 2] → [2].

Ход решения. Используем Set для одного массива, затем проходим по другому и проверяем, есть ли элемент в множестве; в случае да — добавляем в результат и удаляем из множества, чтобы исключить дубликаты. Это понятно и красиво, но асимптотика памяти O(n + m), а не O(1).

Решение на Java.

Java
static int[] intersect(int[] nums1, int[] nums2) {
    Set<Integer> set = new HashSet<>();
    for (int x : nums1) set.add(x);
    List<Integer> res = new ArrayList<>();
    for (int x : nums2) {
        if (set.remove(x)) res.add(x);
    }
    int[] out = new int[res.size()];
    for (int i = 0; i < res.size(); i++) out[i] = res.get(i);
    return out;
}

Решение на Kotlin.

Kotlin
fun intersect(nums1: IntArray, nums2: IntArray): IntArray {
    val set = nums1.toHashSet()
    val res = mutableListOf<Int>()
    for (x in nums2) {
        if (set.remove(x)) res.add(x)
    }
    return res.toIntArray()
}

Сложность. O(n + m) времени и O(n) памяти.

Крайние случаи и ловушки. Если нужно не только пересечение, но и подсчёт повторов, надо использовать Map<Integer, Integer>. Если нужно, чтобы результат был отсортирован, после сбора данных вызывают Arrays.sort или sorted().

Дополнительные вопросы. «А если массивы большие и памяти не хватает?» — можно сортировать оба и идти двумя указателями, что даёт O((n + m) log(n + m)) за меньшее дополнительное пространство. «А если нужно найти симметрическую разницу?» — это уже другая задача.

11.7 Задача: проверка анаграммы двух строк

Уровень: разминка. Встречается как: Valid Anagram.

Условие. Даны две строки s и t; проверить, являются ли они анаграммами.

Пример. s = "anagram", t = "nagaram" → true.

Ход решения. Подсчитываем частоты символов в s, вычитаем встречающиеся в t; после прохода все счётчики должны быть нулевыми. Если алфавит мал, используем массив int[26], а для Unicode — Map<Character, Integer>, но для собеседований чаще всего латиница.

Решение на Java.

Java
static boolean isAnagram(String s, String t) {
    if (s.length() != t.length()) return false;
    int[] freq = new int[26];
    for (int i = 0; i < s.length(); i++) {
        freq[s.charAt(i) - 'a']++;
        freq[t.charAt(i) - 'a']--;
    }
    for (int v : freq) if (v != 0) return false;
    return true;
}

Решение на Kotlin.

Kotlin
fun isAnagram(s: String, t: String): Boolean {
    if (s.length != t.length) return false
    val freq = IntArray(26)
    for (i in s.indices) {
        freq[s[i] - 'a']++
        freq[t[i] - 'a']--
    }
    return freq.all { it == 0 }
}

Сложность. O(n) времени и O(1) памяти при алфавите фиксированной длины.

Крайние случаи и ловушки. Если символы не только латиница, нужна другая таблица или Map. При пустых строках и одинаковых строках функция true корректна. Если длины разняются, сразу false.

Дополнительные вопросы. «А если строки очень длинные и в памяти ограничение?» — можно считать хеш-строки или делать потоковый проход по символам, но это уже другой масштаб. «А если нужно сравнить не строки, а бинарные файлы?» — аналогично, но без ASCII-таблицы.

11.8 Задача: longest consecutive sequence

Уровень: средний. Встречается как: Longest Consecutive Sequence.

Условие. Дан массив целых чисел. Найдите длину самой длинной последовательности подряд идущих чисел в произвольном порядке.

Пример. [100, 4, 200, 1, 3, 2] → 4.

Ход решения. Сначала добавляем все числа в Set; затем для каждого числа проверяем, есть ли x - 1; если нет, начинаем последовательность и идём по x + 1, x + 2 и так далее. Это стратегия «проверять только стартовые числа» — она сокращает повторные проходы и даёт O(n) время в среднем.

Решение на Java.

Java
static int longestConsecutive(int[] nums) {
    Set<Integer> set = new HashSet<>();
    for (int x : nums) set.add(x);
    int best = 0;
    for (int x : nums) {
        if (!set.contains(x - 1)) {
            int len = 1;
            while (set.contains(x + len)) len++;
            best = Math.max(best, len);
        }
    }
    return best;
}

Решение на Kotlin.

Kotlin
fun longestConsecutive(nums: IntArray): Int {
    val set = nums.toHashSet()
    var best = 0

Сложность. O(n) времени и O(n) памяти.

Крайние случаи и ловушки. Массив пустой — ответ 0. Для всех одинаковых элементов последовательность длиной 1. Если нужно не только длину, но и сами числа, нужно хранить крайние значения и возвращать диапазон.

Дополнительные вопросы. «А если последовательность в строке?» — это уже другой тип задачи. «А если числа очень большие?» — long вместо int и проверка Long.

11.9 Задача: ближайшая пара по сумме к целевой величине

Уровень: средний. Встречается как: Two Sum Closest.

Условие. Дан массив nums, нужно найти пару чисел с суммой, максимально близкой к target.

Пример. [1, 2, 5, 10], target = 9 → 10 и -1 или 1 и 10 gives 11, 2 and 10 gives 12, closest is 10 + 1 = 11. Здесь при отборе ориентируемся на минимальную абсолютную разницу.

Ход решения. Сортируем массив и двигаем два указателя: left и right. Вычисляем sum и сравниваем его с target по модулю, поддерживая лучший результат. Если sum < target, двигаем left вправо; иначе right влево. Идея та же, что и в двух указателях по отсортированному массиву.

Решение на Java.

Java
static int[] twoSumClosest(int[] nums, int target) {
    Arrays.sort(nums);
    int bestDiff = Integer.MAX_VALUE;
    int[] best = new int[2];
    int left = 0, right = nums.length - 1;
    while (left < right) {
        int sum = nums[left] + nums[right];
        int diff = Math.abs(sum - target);
        if (diff < bestDiff) {
            bestDiff = diff;
            best[0] = nums[left];
            best[1] = nums[right];
        }
        if (sum < target) left++;
        else right--;
    }
    return best;
}

Решение на Kotlin.

Kotlin
fun twoSumClosest(nums: IntArray, target: Int): IntArray {
    val a = nums.sortedArray()
    var bestDiff = Int.MAX_VALUE
    var left = 0
    var right = a.size - 1
    var best = intArrayOf(a[left], a[right])
    while (left < right) {
        val sum = a[left] + a[right]
        val diff = kotlin.math.abs(sum - target)
        if (diff < bestDiff) {
            bestDiff = diff
            best = intArrayOf(a[left], a[right])
        }
        if (sum < target) left++ else right--
    }
    return best
}

Сложность. O(n log n) времени на сортировку и O(1) дополнительной памяти после сортировки.

Крайние случаи и ловушки. Если массив пустой или содержит один элемент, задача не имеет решения за контрактом. Если несколько пар дают одинаковую разницу, обычно берут одну из них, и это следует уточнить в условии. Если target отрицательный, формула Math.abs(sum - target) всё равно корректна.

Дополнительные вопросы. «А если надо найти три числа, сумма которых ближе к target?» — это уже заход в three sum and sliding window. «А если target большой и sum переполняет int?» — используйте long.

11.10 Задача: поиск ближайшего элемента по порядку в отсортированном массиве

Уровень: разминка. Встречается как: Search insert and nearest value.

Условие. Дан отсортированный массив a и число x; найдите элемент массива, ближайший к x, и если есть два кандидата на равном расстоянии, верните меньший.

Пример. [1, 3, 5, 7, 9], x = 6 → 5 или 7 имеют равное расстояние 1, выбираем 5 как меньший.

Ход решения. Находим lowerBound(x) и сравниваем ближайшие элементы слева и справа. Это классическая комбинация бинарного поиска и сравнения дистанций. Благодаря релевантной границе задача становится O(log n), а не O(n).

Решение на Java.

Java
static int nearest(int[] a, int x) {
    int lo = 0, hi = a.length;
    while (lo < hi) {
        int mid = lo + (hi - lo) / 2;
        if (a[mid] < x) lo = mid + 1;
        else hi = mid;
    }
    int candidate = lo;
    int left = candidate == 0 ? Integer.MAX_VALUE : a[candidate - 1];
    int right = candidate < a.length ? a[candidate] : Integer.MAX_VALUE;
    if (Math.abs(x - left) <= Math.abs(x - right)) return left;
    return right;
}

Решение на Kotlin.

Kotlin
fun nearest(a: IntArray, x: Int): Int {
    var lo = 0
    var hi = a.size
    while (lo < hi) {
        val mid = lo + (hi - lo) / 2
        if (a[mid] < x) lo = mid + 1 else hi = mid
    }
    val left = if (lo == 0) Int.MAX_VALUE else a[lo - 1]
    val right = if (lo < a.size) a[lo] else Int.MAX_VALUE
    return if (kotlin.math.abs(x - left) <= kotlin.math.abs(x - right)) left else right
}

Сложность. O(log n) времени, O(1) памяти.

Крайние случаи и ловушки. Если x меньше всех элементов, ответ — первый. Если больше всех, ответ — последний. Если есть два равных по расстоянию кандидата, нужно определить, какой по правилу из условия должен победить. Проверяйте границу lo и не выходите за пределы массива.

Дополнительные вопросы. «А если нужен не ближайший, а ближайший строго меньше/больше?» — это уже lower bound/upper bound. «А если после сортировки данных попадает поток?» — использование индексной структуры и поиск по окну.
