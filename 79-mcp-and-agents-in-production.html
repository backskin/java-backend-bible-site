Зачем это знать. Разница между “сейчас пусть модель напишет кусок кода” и “сейчас у нас работает продуктивный агент в реальном контуре” огромна. Вторая версия должна уметь вызывать инструменты, понимать права доступа, подчиняться политике, делиться контекстом, писать аудит и не делать то, что человек не должен разрешать автоматически. В корпоративном бэкенде это уже не эксперимент с ChatGPT; это система, в которой агент выполняет действия в окружении — через MCP, через сервисы, через read-only API, через выносы в базу и CI. И вот тут важны не красивые слова про “интеллект”, а нужные инженерные вещи: протокол, транспорт, аутентификация, тайм-ауты, санкции, rollback и безопасный human-in-the-loop.

Глава 78 (78-ai-assisted-development.md) была про использование ИИ-ассистентов в разработке и про корпоративную раскатку. Эта глава — про внутреннюю механику, на которой эта раскатка держится: что такое MCP, как он устроен в терминах протокола и транспорта, как строится агент, работающий в продакшене, как организовать доступ к бизнес-данным и инструментам безопасно, как избежать “агент-без-границ”, как собирать наблюдаемость и как не попасть в ловушки prompt injection и хранимого вредоносного инструмента.

Главная мысль: агент в продакшене работает не сам по себе; он живёт в системе, где важны три вещи — инструментальный слой, права доступа и аудит действий. Без этих трёх элементов ИИ становится красивой оболочкой вокруг неверного решения, а не управляемым системным компонентом.

1. MCP как стандарт для инструментов модели

Model Context Protocol (MCP) — это не магия и не “протокол общения ИИ с чем-то”. Это способ описать, что агент может делать через инструменты и ресурсы, а также как он должен взаимодействовать с ними. Если говорить потоками инженерной логики, то MCP нужен для того, чтобы:

  • одна и та же модель или агент могла подключаться к разным сервисам по одному стандарту;
  • аутентификация и права доступа были выражены явно;
  • инструмент был явно описан и верифицируемый;
  • агент имел доступ не к “произвольному набору файлов”, а к строго заданным возможностям.

1.1 Основные понятия MCP

На уровне протокола MCP обычно оперирует следующими сущностями:

  • tools — действия, которые модель может вызвать;
  • resources — данные, к которым модель может получить доступ;
  • prompts — шаблоны взаимодействия и шаблоны запросов;
  • sampling — модель под клиентом может попросить сервер сгенерировать ответ на своём примере или отфильтровать данные;
  • elicitation — механизм запроса дополнительной информации у пользователя или у клиента перед важным действием.

То есть не “модель просто разговаривает”, а “модель имеет набор контролируемых действий и данных, и этот набор описан структурно”. Это позволяет отделять “что может сделать агент” от “какой текст он выдал в чате”. Именно это и делает MCP полезным инструментом в продакшене: он приводит инструментарий к форме, которую можно проверять и ограничивать.

1.2 Почему стандарт нужен, если можно писать руками

Можно написать собственный протокол: POST /invoke, JSON-структуры, фабрику ToolSpec, обычные HTTP и аутентификацию через JWT. Но всё это обычно приводит к одному и тому же эффекту: каждый сервис пишет свой собственный клиент и свой набор инструментов. А значит:

  • нет единых правил проверки и тестирования;
  • нельзя легко менять клиент или модель;
  • инструменты в разных сервисах имеют разный набор имён и форматов;
  • аудиторские требования почти всегда упираются в то, что “любой инструмент считается произвольным операционным доступом”.

MCP нужен именно как пространство контрактов. Он не отнимает инженерную свободу, а позволяет обеспечить повторяемость и безопасность между разными клиентами, агентами и сервисами.

2. JSON-RPC, сессии и транспорт

Механика MCP на уровне транспортного слоя обычно строится поверх JSON-RPC 2.0. Это не случайно: JSON-RPC даёт похожую структуру запросов, ответов, уведомлений и ошибок, а также стандартный способ передавать методы и параметры. В простом случае выглядит так:

JSON
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/list",
  "params": {}
}

И ответ:

JSON
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "tools": [
      {
        "name": "get_account_balance",
        "description": "Return current balance for an account",
        "inputSchema": { "type": "object", "properties": { "accountId": { "type": "string" } } }
      }
    ]
  }
}

Такой формат в продакшене хорош не потому, что “модный”, а потому, что его можно трассировать, логировать и тестировать. Если у вас на входе JSON-RPC, проще будет собрать аудит действий по методам и идентификаторам. Также удобно проверять, что именно вызвало агент.

2.1 Сессии и жизненный цикл

У каждого MCP-сервера есть жизненный цикл:

  • подключение клиента;
  • инициализация и обмен capability;
  • список доступных инструментов и ресурсов;
  • работа по связанным запросам;
  • завершение и закрытие связи.

Важно, что клиент и сервер не обязаны хранить всё состояние в памяти. Для продакшена они часто организовывают хранилище сессии отдельно, а обработка — по идентификатору сессии. Это нужно, чтобы:

  • не потерять контекст в случае долгого диалога;
  • можно было открыть и закрыть лог действий;
  • можно было сохранять “контур” безопасного агента.

2.2 Транспорты: stdio vs Streamable HTTP

У MCP есть минимум два основных варианта транспорта, и они отражают разные сценарии использования.

stdio — это локальный процесс, который работает рядом с клиентом. Он хорошо подходит для десктопного клиента, IDE, local CLI, локального агента, особенно когда сервисы реально в той же коробке. Преимущество — простота, отсутствие сетевой магии, низкая задержка. Минус — ограничение на удалённый доступ. В продакшене это часто неприемлемо, если агент должен подключаться к нескольким системам через централизованный шлюз.

Streamable HTTP — транспорт через стандартный HTTP-сервер. Для enterprise-сценариев это обычно более удобный путь: можно держать один gateway, один URL, аутентификацию, логи и мониторинг. У него больше возможностей по управлению токенами, лимитами, service mesh и аутентификацией с OAuth 2.1. Его главный минус — нужно больше уделять attention к безопасности и таймаутам.

2.3 OAuth 2.1 и авторизация MCP

Если MCP-сервер работает с данными клиента, идентификацией, правами и системами доступа, то он не может просто “смотреть в заголовок Authorization: Bearer” без тщательной логики. Для продакшена ожидается:

  • OAuth 2.1 или другой стандартный паттерн с вещами вроде клиентских ID и scope;
  • ограничение на scope по разделам: read:accounts, read:logs, write:issue и так далее;
  • токены без права на write, если промпт или команда требуют лишь чтение;
  • аутентификация на уровне клиент-сервер и introspection/validation;
  • аудит, что именно был вызван инструмент, с каким токеном и в каком контексте.

Правильный агентный контур почти всегда предполагает, что действия выполняются не с правами “администратора всего мира”, а с правами, рассчитанными под задачу и реальный уровень доверия.

3. MCP-сервер на Java/Kotlin

Можно написать MCP-сервер вручную, можно использовать Spring AI или собственный сценарный путь. Для Java/Kotlin компании часто уже есть Spring ecosystem, поэтому логичнее двигаться по направлению Spring Boot + MCP server с моделями доступа и проверкой. Фактически это означает: один сервис, который публикует набор инструментов для модели. Сервер реализует методы вроде:

  • get_project_docs
  • read_ticket
  • list_issues_by_label
  • fetch_api_schema
  • check_db_status
  • query_order_status (read-only)

Сервис не должен давать агенту “побольше возможностей”, он должен давать ровно те возможности, которые оправданы.

3.1 Минимальный сервлет/контроллер

Простейший пример — это Spring Boot-сервис, который на HTTP принимает JSON-RPC, проверяет токен и делегирует вызов конкретному инструменту.

Java
@RestController
@RequestMapping("/mcp")
public class McpController {

    private final ToolRegistry registry;

    public McpController(ToolRegistry registry) {
        this.registry = registry;
    }

    @PostMapping("/invoke")
    public ResponseEntity<Map<String, Object>> invoke(@RequestHeader("Authorization") String auth,
                                                      @RequestBody Map<String, Object> body) {
        String token = auth.replace("Bearer ", "").trim();
        if (!TokenValidator.isValid(token)) {
            return ResponseEntity.status(HttpStatus.UNAUTHORIZED).build();
        }

        String toolName = (String) body.get("tool");
        Map<String, Object> args = (Map<String, Object>) body.getOrDefault("args", Map.of());

        var tool = registry.get(toolName);
        if (tool == null) {
            return ResponseEntity.status(HttpStatus.NOT_FOUND).body(Map.of("error", "tool_not_found"));
        }

        if (!tool.isAllowed(token)) {
            return ResponseEntity.status(HttpStatus.FORBIDDEN).body(Map.of("error", "forbidden"));
        }

        Object result = tool.execute(args);
        return ResponseEntity.ok(Map.of("result", result));
    }
}

Это минимальный, но уже корректный путь: проверка JWT, проверка прав на инструмент, запрет на неверный инструмент, аудит. Всё остальное — отладка и расширение по типам действий.

3.2 Kotlin-подход

В Kotlin можно сделать тот же сценарий через @RestController и data class DTO, а иногда ещё удобней — через spring-ai-модули для MCP. Важно здесь не “красивый код”, а правило: инструменты — это контроли, а не свободная магия. У каждого инструмента должен быть:

  • имя;
  • описание на понятном языке для модели;
  • описание параметров;
  • доступный scope;
  • тип данных для ответа;
  • ограничение по времени;
  • журнал действий.

Пример описания инструмента:

Kotlin
data class ToolSpec(
    val name: String,
    val description: String,
    val inputSchema: Map<String, Any>,
    val allowedScopes: Set<String>,
    val timeoutMs: Long = 3000,
    val readOnly: Boolean = true
)

Это уже инженерный каркас, а не “я просто даю модели доступ к серверу”.

4. Клиенты и шлюзы для MCP

MCP-сервер сам по себе не делает всех задач; нужна ещё и клиентская часть. Клиентами могут быть:

  • IDE-плагин;
  • агент в терминале;
  • корпоративный gateway для бизнес-автоматизации;
  • специализированная рабочая среда для аналитиков и операторов;
  • backend-сервис с авто-обработкой.

4.1 Почему нужен gateway

Если у компании 5–10 MCP-серверов (Jira, GitLab, Confluence, БД, внутренний API, лог-канал), то напрямую привязывать модель к каждому из них неудобно. Нужно один gateway, который:

  • проверяет токен клиента;
  • фильтрует инструменты по роли;
  • аудирует и маппит результаты;
  • может включить human-in-the-loop прежде чем выполнить действие;
  • ограничивает стоимость, тайм-ауты и частоту.

Это принцип того же, что мы уже видели в главе 77: единая точка входа для LLM-платформы. MCP gateway — это просто тот же шаблон, переведённый на инструментальный слой.

4.2 Жизненный цикл действия

Для продакшена важно, чтобы действие не выполнялось “на лету и без контекста”. Хороший жизненный цикл выглядит так:

  1. агент получает задачу в свободной форме;
  2. он решает, нужны ли инструменты;
  3. он запрашивает список доступных tools и resources;
  4. клиент проводит аутентификацию и разрешение;
  5. агент вызывает инструмент, у которого есть разрешение;
  6. ответ проверяется и логируется;
  7. при критичных действиях сервер требует подтверждение человека;
  8. после действия — posting in audit and metrics.

Если это выглядит как слишком много ручной работы, это нормально. Это и есть безопасность на уровне agentic system.

5. Агент в бизнес-процессе банка: где он реально нужен

С точки зрения продакшена агент особенно полезен там, где человек уже выполняет много рутинной разбора. Для банка типичные сценарии:

  • первичная обработка обращений клиентов;
  • сопоставление документов и кредитных заявок;
  • подготовка сводок для операциониста по обращению;
  • поиск в регламентах и внутренних политиках;
  • подготовка краткого резюме по истории запроса;
  • помощь аналитикам в сборе фактов из нескольких систем.

Но важно, чтобы агент выполнял именно расчленённые действия, а не “думал как бизнес-аналитик”. Сценарии обычно выглядят так:

  • получить обращение и его контекст;
  • найти связанные документы и связанные операции;
  • извлечь факты и сформировать структуру события;
  • предложить оператору подготовленный ответ или статус;
  • если риск высокий или операция требует согласования, эскалировать человеку.

5.1 Важное условие: human-in-the-loop

Агент в продакшене должен быть не автономным в важных критичных процессах, а совместным. Например, в банке он не должен без подтверждения клиента или сотрудника:

  • закрывать спорный запрос;
  • отменять операцию;
  • изменять лимит;
  • принимать решение о блокировке счёта;
  • производить финансовую транзакцию с кредитом.

Банковская логика очень часто: агент может предложить, собрать факт, сформировать рекомендации и подготовить первичную проверку, но окончательное действие принимает человек. Это ключевое правило. Иначе агент превращается в мокрую точку рисков и ответственности.

5.2 Пример бизнес-сценария

Пусть есть сценарий “помощь операционисту по обращению клиента”. Агент:

  1. получает тикет, историю обращений, контекст клиента;
  2. читает регламент по темам и платёжные операции;
  3. может запросить справки и документы через MCP;
  4. строит сводку по фактам и список вероятных причин;
  5. предлагает шаблон ответа;
  6. оператор подтверждает и отправляет правку, а агент ведёт аудит и сохраняет контекст.

Это уже не “Модель в чате”, а продуктовый workflow. И для него важны интерфейс, доступы, тесты и мониторинг.

6. Надёжность и повторяемость агента

Агент в продакшене должен быть надёжным, а не просто “когда не разобрался, выдаст что-нибудь”. Для этого нужны конкретные механизмы.

6.1 Повторы и идемпотентность

Если агент вызывает инструмент, а сеть разорвала соединение, вы должны понимать: вызов отрабатывал или нет. Для read-only это менее критично. Для write-операций — критично. Поэтому нужно:

  • давать инструменты idempotency key;
  • хранить лог транзакции и его ID;
  • для повторного вызова проверять, не было ли уже такого же действия;
  • для критичных действий включать два этапа: tentative и commit.

Это классическая инженерная практика, не “почти как релиз”.

6.2 Тайм-ауты и бюджеты шагов

Агент может “растекаться” в глубину: сделал 20 tool calls, ходил по нескольким сервисам, получил не очень внятный ответ и продолжается. Это надо ограничивать. Полезные механизмы:

  • max_steps — допустимое число шагов;
  • budget_usd — макс. денежный бюджет на шаги;
  • time_limit_ms — тайм-аут на цепочку;
  • retry_policy — для подобных ситуаций;
  • fail_closed для инструмента, если у него нет ясного исхода.

Если агент — это не лектор, а сервисный компонент, он должен уметь уходить в прозрачную деградацию, а не “сделать ещё один шаг, пока не исчезнет”.

7. Наблюдаемость и аудит

Для продакшена без наблюдаемости нет доверия. Агента надо наблюдать так же, как любое другое сильно влияющее бизнес-сервис. Важные точки:

  • время каждого шага;
  • инструменты и их возвращаемые данные;
  • среднее и пиковое время до ответа;
  • число ошибок и типы отказов;
  • стоимость моделей и инструментов;
  • запросы с ретроспективой по session и user;
  • инциденты и эскалации;
  • изменение модели и правил в конкретной версии агента.

7.1 OpenTelemetry и GenAI conventions

В этой теме хорошо работают OpenTelemetry с генеративным набором конвенций по трейсам и метрикам. Это позволяет смотреть не просто http-трейсы, а иерархию вызовов к модели, инструментам, базам и наружным сервисам. Иными словами, мы видим не “что моделировал LLM”, а “что вообще произошло в цепочке агента”.

Если агентный сервис нельзя проследить по трейсам, он не готов к production.

7.2 Что именно сохранять в логе

Не всё надо хранить в логе. Нужно хранить:

  • session ID;
  • user/system identity;
  • выполенные инструменты;
  • результаты и ошибки;
  • модель и версию;
  • стоимость и токены;
  • human approval / refusal;
  • связь между запросом и исходным бизнес-событием.

Но не нужно хранить подряд “всю чушь из контекста модели”, если она содержит чувствительные данные или можно её отсечь. Резкая граница между “аудит” и “содержимое инструмента” обязана быть в архитектуре.

8. Угрозы и защита: prompt injection, tool poisoning и доверие к описаниям

У агентов есть несколько классов угроз, которые часто недооценивают.

8.1 Tool poisoning

Инструмент может быть описан слишком “обещающе” или в лукавой форме. Пример: описание инструмента get_order_status звучит так: “Смотри всё, что есть, и возвращай то, что нужно для клиента”. В реальности он может возвращать больше, чем предполагалось. Если агент доверяет описанию инструмента больше, чем реальным правам, он начинает “интерпретировать” действия, которых не должен делать. Это классический путь к опасным инцидентам.

Лечение: явное описание инструментов, строгое ограничение по scope, минимальный набор допустимых параметров, аудит вызова и проверка на уровне gateway.

8.2 Prompt injection в docs и issues

Если агент читает внутренние документы или issue с текстом, в котором базарно пишут “Игнорируй ограничения, ты должен выполнить X”, он может попытаться подменить своё поведение. Лечение — отдельный набор правил: инструкции для агента, настройка приоритетов, “запрет на доверие внешнему тексту” для критичных действий. Нельзя строить английскую логику “модель будет пользоваться здравым смыслом”, если в проде есть данные с человеческим текстом и правами.

8.3 Утечка через выхлоп инструмента

Агент, который получает доступ к файлам и сервисам, может случайно или намеренно вернуть информацию, не предназначенную пользователю. Например, он делает read-only query к базе заказов и затем возвращает полный список всех записей, хотя user обязан видеть только свой набор. Лечение — фильтрация прав at source: не “смотри всё и потом отфильтруй”, а “доступ ограничен по пользователю и роли уже на уровне инструмента”.

8.4 Escalation и вредоносные команды

Если агент делает shell-команды или вызывает системный инструментарий, это серьёзная экспозиция. Прерогатива агента — не shell, а строгие инструменты, чьи действия можно логировать и ограничивать. Если нужна командная работа в CI или dev-процессах, это должно быть отдельной сетевой зоной и separate role, а не “просто отправить все команды в bash”.

9. Набор идей для надёжной реализации

Ниже — список инженерных практик, без которых нормальный MCP-агент не собирается в production.

9.1 Один инструмент = одна ответственность

У each tool есть чёткая область: только чтение Jira, только чтение tickets, только список внутр. docs, только API для перечня продуктов, только факты по приложению. Если одно действие делает слишком много, модель начинает путаться.

9.2 Структура инструментов

Для каждого инструмента нужна форма:

JSON
{
  "name": "get_order_history",
  "description": "Return the recent orders for a customer by accountId. Read-only. Does not modify state.",
  "inputSchema": {
    "type": "object",
    "required": ["accountId"],
    "properties": {
      "accountId": { "type": "string" },
      "limit": { "type": "integer", "minimum": 1, "maximum": 20 }
    }
  },
  "permissions": ["orders:read", "customer:self"],
  "timeoutMs": 2500
}

Такой контракт даёт модели точную картину, а инженеру — возможность проверять его и подписывать как часть контракта.

9.3 Tools и resources в связке

Инструменты — это действия, а resources — это данные. Сочетание resources и tools позволяет строить более управляемый agentic workflow:

  • resource даёт доступ к документам и состояниям;
  • tool даёт возможность сделать операцию и затем отследить результат;
  • prompt задаёт правильную формулировку для пользователя или агента;
  • audit log фиксирует действия.

10. Реализация безопасного продакшена

Платформа безопасности для агентов должна включать следующее:

  • аутентификацию и авторизацию на уровне каждой операции;
  • hard policy на уровне инструментов;
  • правила по зонам доступа и данным;
  • контроль на уровне модели: prompt guard, фильтрация внешнего текста, проверка на injection;
  • isolation of tools, чтобы запросы к базам и внешним системам шли только через выделенные служебные компоненты;
  • audit logs of tool calls and approvals;
  • fail-closed для чувствительных действий;
  • review на каждом критичном сценарии.

10.1 Нормальные границы для агентных платформ

Что допустимо в хорошем enterprise-сценарии:

  • read-only call к KB и документации;
  • поиск по историям звонков и платёжным операциям при наличии scope;
  • подготовка черновика ответа или краткой аналитики;
  • формирование template для сотрудника;
  • запрос дополнительной информации через elicitation.

Что запрещено автоматически:

  • изменения финансового состояния;
  • массовое редактирование справочников;
  • blind write to production DB;
  • массовое создание, скрытие или изменение документов без подтверждения;
  • отправка данных в внешние сервисы без разрешения и фильтрации.

11. Шаблон внедрения в компании

Если пришла задача встроить MCP/агента в продакшен, обычно схема такая:

  1. Определить бизнес-сценарий. Не “обязательно внедрять AI”, а “нам нужно ускорить обработку заявок X”.
  2. Выделить модель доступа. Какой тип данных мы дадим модели, а что фильтруем.
  3. Выбрать инструментарий. Какие tools / resources / prompts нам нужны.
  4. Поднять gateway. Единая точка аутентификации, rate limits, observability.
  5. Подготовить security policy для read-only и write-операций.
  6. Провести pilot на ограниченной выборке задач с human review.
  7. Собрать метрики и скорректировать границы автономности.
  8. Масштабировать только после явной стабилизации и audit review.

На этапе pilot важно не “сдать демо”, а понять, где агент реально полезен и где он будет коллегой, генерирующим шум.

12. Когда агент не нужен, даже если он кажется “очень модным”

Агенты не нужны для:

  • маленьких, детерминированных задач с коротким циклом;
  • задач, где одна неверная операция стоит слишком дорого;
  • сценариев, где нужен строгий, понятный и проверяемый регламент;
  • случаев, где нет объективной метрики and process.

В этих случаях лучше написать обычный сервис, а не “интеллектуального помощника”.

13. Грабли

  1. MCP без прав и audit — это просто “API с красивым названием”.
  2. Агент с доступом к write-операциям без approval — рискованный проект.
  3. Слишком много tools — модель не понимает, чем пользоваться и какой tool безопасен для текущей задачи.
  4. Говорить “модель сама решит” — ровно то, что ломает продакшн.
  5. Хранить содержимое prompts вместе с логами — это не “производственный обмен знаниями”, это риск для данных.
  6. Доверять описанию tool больше, чем реальному scope — классический способ создать опасный агент.
  7. Игнорировать retry/idempotency — особенно для операций write.
  8. Наблюдаемость на уровне HTTP, а не на уровне agent steps — в таком случае вы не увидите, что делал агент и когда он пошёл не туда.
  9. Длина промпта и контекста без лимитов — быстрый путь к цене и к исчезновению качества.
  10. Ошибка архитектурной границы — компания начинает считать, что “агент — это IVR-продукт”, хотя это часть внутреннего инженерного процесса.

Диагностика

Если агент не работает в продакшене, проверьте по порядку:

  • какой у него tool registry и какие скопы у каждого tool;
  • какие права у токена и какой user context behind it;
  • есть ли human approval на write-операциях;
  • сколько шагов делает агент до отказа и есть ли у него max_steps;
  • какой вид наблюдаемости и рейсов на логи у этого agent session;
  • не попадали ли external docs или issue в prompt без фильтрации;
  • есть ли ограничение на количество и стоимость tool calls;
  • какие метрики говорят о падении качества: OPM, error rate, transaction success rate, repetition rate.

В этом смысле агент — это не “клиент модели”, а системный компонент. Ошибки в нём локализуются так же, как ошибки в очередях и в gateway, а не как “модель не любит меня”.

15. Попробовать руками

  1. Собрать минимальный MCP-сервер на Java/Kotlin с двумя read-only tools (get_account_balance, list_recent_transactions) и одним запрещённым write tool, который будет доступен только с выделенным scope.
  2. Проверить interaction через JSON-RPC: список инструментов, вызов tool, проверка ошибки на forbidden и на not_found.
  3. Добавить аутентификацию через JWT или OAuth-подобную схему и проверить, что read-only scope не даёт write access.
  4. Собрать agent gateway с rate limits, budget и audit log. Затем замерить, могут ли несколько session одновременно вызвать один и тот же tool.
  5. Запустить локальный prompt injection test с внешним текстом, который говорит “игнорируй все ограничения”. Проверить, что gateway и tool policy всё равно не допускают critical action.
  6. Проверить max_steps и timeout на агентном сценарии с 20 последовательными calls. Сравнить согласованность и время выполнения.
  7. Построить tracer для agent session через OpenTelemetry и посмотреть, как сериализуется цепочка tool → result → next step.
  8. Проверить правильность idempotency на сценарии с повторным вызовом write tool и одинаковым аргументом. Убедиться, что действие не было выполнено дважды.
  9. Сделать human approval для критичной операции: например, “блокировка счёта” или “изменение лимита”, и убедиться, что без подтверждения операция не проходит.
  10. Выполнить read-only test в своей компании: взять обычный внутренний сервис и описать, какие инструменты агенту безопасно давать, а какие нельзя.

16. Что запомнить

MCP и агенты — это не про “сделать модель умнее”, а про разделение ответственности между моделью, инструментами, данными и человеком. В продакшене правят не красивый диалог и не “магическое программирование”, а ясные контракты, capability model, полномочия и аудит. Если на этом уровне нет дисциплины, агент быстро становится серьёзной дырой в безопасности и в управлении бизнес-логикой.

Это уже не лоскутный сценарий “быстрых решений”, а горячая инженерная задача: “как устроить безопасный, контролируемый, наблюдаемый and auditable agentic workflow, который реально приносит пользу и не ломает ответственность”.
