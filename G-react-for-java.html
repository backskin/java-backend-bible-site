Приложение закрывает пробел, который вакансии всё чаще формулируют прямо: «преимущественно бэкенд, но нужен человек, который быстро разберётся в React и с помощью ИИ напишет полный стек». На собеседовании по такой вакансии не ждут от Java-разработчика стажа фронтенд-разработчика. Ждут другого: понимания механики (почему компонент перерисовался, откуда двойной запрос, чем опасен эффект без очистки), умения договориться с клиентом о контракте и способности проверить код, который сгенерировала модель. Учебника по React здесь нет, есть карта перехода. Что устроено иначе, чем в Java. Какие ошибки делает человек с опытом бэкенда. Какие ошибки делает ИИ-ассистент, когда пишет фронтенд. И как собрать фронт и бэк в один репозиторий и один артефакт, чтобы фулстек был одним модулем, а не двумя командами по разные стороны API.

G1. Что спрашивают у бэкенд-разработчика на фулстек-вакансии и чего не спрашивают

Вопросы по React для бэкенд-разработчика укладываются в три слоя, и полезно знать их заранее, чтобы не тратить вечер на то, что не спросят. Первый слой — механика: что такое рендер, почему состояние ведёт себя как снимок, зачем ключи, как работает эффект и его очистка. Второй — стык с бэкендом: как клиент загружает данные, повторяет запросы, кэширует их, что он делает с деньгами и длинными идентификаторами, где хранит токен. Третий — организация: как собрать фронт и бэк, как тестировать, как проверять код, написанный ИИ. Вёрстку, CSS-фреймворки, анимации и дизайн-системы на такой вакансии почти не спрашивают: это работа фронтенд-разработчика, и честный ответ «вёрстку беру из готовой библиотеки компонентов» никого не смущает.

G2. TypeScript и JavaScript глазами Java-разработчика

Синтаксис TypeScript читается за вечер, потому что он похож на смесь Java и Kotlin: классы, интерфейсы, обобщения, лямбды, async/await. Подвох в другом. Модель типов и модель выполнения устроены иначе, и ровно здесь бэкенд-разработчик ошибается, когда переносит привычки из Java. Ниже таблица соответствий, затем три опыта, которые показывают различия на деле: структурная типизация, стирание типов на границе с сервером и цикл событий.

Опыт 1: структурная типизация. В файле с намеренными ошибками (contract-errors.ts) объявлены два типа одинаковой формы, AccountId и CardId, оба { value: string }, и функция block(card: CardId). Вызов block(acc) со счётом вместо карты компилятор принял молча: для него это один и тот же тип. В Java два класса с одинаковыми полями несовместимы, и такая подмена не скомпилируется. Номинальность возвращают «брендированным» типом: type CardNo = string & { readonly __brand: 'CardNo' }. После этого вызов с номером счёта дал error TS2345: Argument of type 'AccountNo' is not assignable to parameter of type 'CardNo'. Вторая особенность структурной модели — проверка лишних свойств. Объект-литерал с полем cvv, которого нет в типе Limit, дал ошибку TS2353: Object literal may only specify known properties, and 'cvv' does not exist. Тот же объект, сначала положенный в переменную, присвоился без ошибки: проверка лишних полей срабатывает только для литералов. Номер карты может «проехать» в чужой объект, и компилятор этого не заметит.2

Классы тоже структурны (опыт E-3). Привычка из Java подсказывает, что объект класса получается только через конструктор, а значит, проверка в конструкторе надёжна. В TypeScript это не так. Дэн Вандеркам в «Effective TypeScript» показывает это на классе с проверкой в конструкторе и отмечает, что такое поведение сильно отличается от C++ и Java (Item 4, с. 21). На стенде класс Limit бросает исключение, если сумма не больше нуля. Строка const fake: Limit = { amount: -500 } компилируется без ошибок: литерал той же формы совместим с классом. Во время выполнения fake instanceof Limit ложно, а amount равно −500. Инвариант, который в Java держит конструктор, здесь держится только на дисциплине команды. Если он важен (сумма, номер карты), объект создают фабрикой, которая возвращает брендированный тип, а данные проверяют на границе (G6).26

private не прячет данные (опыт E-4). Модификаторы private и protected в TypeScript существуют только для компилятора и при сборке стираются. Вандеркам показывает, что такое поле читается и через as any, и через Object.entries (Item 72, с. 311–312). Опыт подтвердил это на токене. У класса с private secret вызов Object.entries вернул [["secret","tok_dev.team"]], а JSON.stringify выдал {"secret":"tok_dev.team"}. Такой объект, записанный в журнал или отправленный в ответе, уносит секрет. Поле со стандартным модификатором ECMAScript #secret не попало ни в Object.entries, ни в JSON, а (obj as any).secret дал undefined. Вандеркам советует брать #private и вообще предпочитать возможности ECMAScript собственным возможностям TypeScript. К тем же исключениям он относит enum. Числовому перечислению можно присвоить любое число. Строковое оказывается единственным номинальным типом языка, поэтому из JavaScript функцию вызывают строкой 'vanilla', а из TypeScript та же строка не компилируется и нужен импорт перечисления. Вместо enum берут объединение литералов 'RUB' | 'USD', которое в JSON выглядит так же, как в коде (с. 306–308).26

Особые значения внутри домена. Ещё одна привычка из Java — возвращать −1, когда ничего не найдено, как это делает indexOf. Вандеркам связывает её именно с Java, где примитив не может быть null (Item 36, с. 162–165). В TypeScript для «значения нет» служит null в типе: number | null заставит вызывающего проверить результат, а −1 молча уйдёт в арифметику. Его пример знаком финтеху: неизвестную цену записали как −1, и разбор инцидента начинается с вопроса, почему система зачисляла деньги на карты клиентов. В Java тот же дефект закрывают OptionalLong или BigDecimal, допускающий null, вместо long с магическим значением.26

Где система типов молчит (опыты L-1, L-3, L-4). Джош Голдберг в «Learning TypeScript» прямо называет систему типов TypeScript технически несостоятельной: она почти всегда права, но иногда ошибается в том, что лежит в переменной. Первым источником он называет массивы (гл. 6, с. 79). Три таких места проверены на TypeScript 5.9.3 под --strict.

Первое — доступ по индексу. Функция dailyLimit возвращает limits[merchantId] * 100 для типа { [merchantId: string]: number }. Компилятор считает результат числом, а для незнакомого мерчанта во время выполнения вышло NaN. Вызов amounts[0].toFixed(2) на пустом массиве упал с Cannot read properties of undefined (reading 'toFixed'). Голдберг упоминает флаг noUncheckedIndexedAccess, называет его слишком строгим для большинства проектов и в книге не разбирает (с. 79, 94). С флагом обе строки дали TS2532: Object is possibly 'undefined'. Для Java-разработчика это знакомый Map.get, только без NullPointerException: undefined молча уходит в арифметику, и в отчёт попадает NaN. Совет книги хранить такие данные в Map, у которого get честно возвращает number | undefined, верен (с. 94), а tsc --init в версии 5.9 сам включает этот флаг (G10).

Второе — методы бивариантны. Голдберг описывает флаг strictFunctionTypes как переход параметров функций от бивариантности к контравариантности (гл. 13, с. 216). Он не говорит, что член интерфейса, объявленный синтаксисом метода, под этот флаг не попадает. На стенде обработчик, принимающий только VirtualCard, присвоен двум интерфейсам с параметром Card. Вариант со свойством handle: (c: Card) => void дал TS2322. Вариант с методом handle(c: Card): void скомпилировался, и вызов с обычной картой упал с Cannot read properties of undefined (reading 'length'). Отсюда правило для интерфейсов обработчиков и обратных вызовов: объявлять их свойствами-функциями, тогда компилятор проверит параметр.

Третье — предикат, который проверяет больше, чем тип. Функция isLongReference(input): input is string возвращает true только для строк длиной от семи символов. Голдберг предупреждает, что тогда ветка else сужается неверно (гл. 9, с. 128–129). Опыт это подтвердил: в else строка const shown: undefined = ref скомпилировалась, хотя ref был "AB12". В TypeScript 5.5, вышедшем после книги, предикаты выводятся сами. [100, undefined, 250].filter(x => x !== undefined) дал number[] без ручного x is number. С дополнительным условием && x > 150 вывод не сработал, и тип остался (number | undefined)[]: компилятор выводит предикат, только если условие говорит о типе и ни о чём больше.3233

Глобальные имена из DOM и enum в TypeScript 5 (опыт L-2). В файле без import и export строка let status: PaymentStatus дала TS2451: Cannot redeclare block-scoped variable 'status'. Обе причины Голдберг объясняет порознь. Файл без import и export считается скриптом с общей глобальной областью (гл. 2, с. 25–26). Типы DOM включены по умолчанию, даже если код работает в Node (гл. 11, с. 172–173), а в них есть глобальное window.status. В Node-сервисе dom убирают из lib, а конфиг tsc --init версии 5.9 ставит moduleDetection: "force", и каждый файл считается модулем. Тот же опыт уточняет совет о перечислениях. По Голдбергу числовому enum можно присвоить любое число, даже −1 (гл. 14, с. 240–241). В TypeScript 5.9 строка status = -1 дала TS2322: Type '-1' is not assignable to type 'PaymentStatus', а status = 2 прошла. Но число из переменной, как придёт из колонки базы, присвоилось без ошибки, и PaymentStatus[7] вернул undefined. Проверка ловит опечатку в литерале, а данные снаружи по-прежнему не проверяет. Врезка Голдберга о том, что смена порядка членов числового enum портит значения, уже сохранённые в базе (с. 242), — та же ловушка, что @Enumerated(EnumType.ORDINAL) в JPA (глава 12).3233

JavaScript там, где бэкенд-разработчик ждёт Java (опыты FL-1…FL-7). Дэвид Фланаган в седьмом издании «JavaScript: The Definitive Guide» описывает язык без TypeScript. Многие его оговорки компилятор не ловит, потому что ошибка сидит в значении, а тип у него правильный: number остаётся number, а string — string. Семь таких мест проверены на Node 22.11.

Запасное значение. Оператор || подставляет запасное значение для любого ложного операнда, а ?? из ES2020 — только для null и undefined (гл. 4, с. 85–86, 92). В платёжном коде разницу видно на лимите. Ноль в настройке означает «операции запрещены», но limit || 500 вернул 500 и тем самым операции разрешил. limit ?? 500 вернул 0. В Kotlin такой ошибки нет, потому что элвис-оператор ?: срабатывает только на null.

Сортировка. Без компаратора sort() сравнивает элементы как строки (гл. 7, с. 175). Суммы в копейках [150000, 9900, 25000] встали в порядке [150000, 25000, 9900]. Строки сравниваются по кодам UTF-16 (гл. 4, с. 82), и список «яблоко, ёлка, Ежевика, арбуз, ель, Яшма» отсортировался как «Ежевика, Яшма, арбуз, ель, яблоко, ёлка»: заглавные ушли вперёд, «ё» — после «я». С new Intl.Collator("ru").compare получилось «арбуз, Ежевика, ёлка, ель, яблоко, Яшма». В Java это разница между String.compareTo и Collator.getInstance(new Locale("ru")).

Порядок ключей. Свойства объекта перечисляются в таком порядке: сначала целочисленные ключи по возрастанию, затем строковые в порядке добавления (гл. 6, с. 141). Для ответа сервера это значит, что порядок из JSON не сохраняется. Объект {"b":1,"978":2,"643":3,"840":4,"007":5} с кодами валют дал ключи 643, 840, 978, b, 007: "007" не считается каноническим целым и осталось в конце. Если порядок важен, сервер отдаёт массив, а не словарь.

Ключи от пользователя. Для словаря с произвольными ключами Фланаган советует Map (гл. 6, с. 135), и опыт показал почему. "constructor" in {} вернул true, то есть проверка «такой ключ уже есть» солгала. Присваивание portfolio["__proto__"] = 50 молча не создало ключа. Если во входном JSON есть ключ __proto__, JSON.parse создаёт обычное собственное свойство с таким именем. Но Object.assign({}, parsed) превратил его в прототип результата, и у результата появились поля, которых в нём не было. Спред {...parsed} так не делает. Функция merge из книги копирует только отсутствующие ключи (с. 143) и защищена случайно: "__proto__" in {} уже истинно. Рекурсивное слияние, которое часто пишут для конфигов, записало поле прямо в Object.prototype, и оно появилось у всех объектов процесса. Это загрязнение прототипа (prototype pollution). Защита — Map, Object.create(null) для словарей и схема на входе, отбрасывающая лишние ключи (G6).

Неизменяемость. Object.freeze замораживает только сам объект (гл. 14, с. 384–385). У замороженного тарифа вложенный limits.daily поменялся с 1000 на 10⁹ без ошибки. В Java так же ведёт себя Collections.unmodifiableMap над изменяемыми значениями.

Даты. Методы set* объекта Date при переполнении переносят лишнее в следующую единицу, и Фланаган подаёт это как удобство (гл. 11, с. 303). Для графика платежей это ловушка: new Date(2026, 0, 31) после setMonth(getMonth() + 1) превратилось в 3 марта. LocalDate.plusMonths(1) в Java даёт 28 февраля (глава 4). Вторая ловушка — разбор строк: new Date("2026-03-01") читается как полночь UTC, а new Date("2026-03-01T00:00") — как полночь по местному времени, в Москве это 2026-02-28T21:00Z.

Регулярные выражения. Классы \w, \d и граница \b понимают только ASCII (гл. 11, с. 283–284). /\bперевод\b/.test("перевод") вернул false, в том числе с флагом u. Пример автора /\b\p{Alphabetic}+\b/gu (с. 296) на строке «Перевод денег по СБП» не нашёл ни одного слова: \p{Alphabetic} кириллицу понимает, а \b вокруг него нет. Сработал /\p{L}+/gu. Ещё одну ловушку автор называет сам (с. 297–300): регулярное выражение с флагом g помнит lastIndex. Общий объект /(\w)\1/g вернул true на «apple», а сразу после этого false на «book», потому что поиск начался с третьей позиции. Валидатор, который держит такое регулярное выражение в константе модуля, отвечает по-разному в зависимости от предыдущего вызова.3435

Опыт 2: тип не проверяет данные. Ответ сервера разобран через JSON.parse(...) as Limit, хотя сервер «сломал» контракт и прислал dailyLimit числом. typeof body.dailyLimit вернул number, хотя тип обещал string: конструкция as — это указание компилятору, а не проверка. С any то же самое, только хуже. Строка fromServer.dailyLimit.toFixed(2) при типе any скомпилировалась без единого предупреждения. Для unknown компилятор потребовал сначала сузить тип (TS18046: 'fromServer2' is of type 'unknown'). Правило для бэкенд-разработчика: на границе с сетью тип ничего не гарантирует, нужна проверка во время выполнения (G6).

Опыт 3: числа. Четыре строки в тесте показывают, почему деньги и идентификаторы нельзя отдавать браузеру числом:

Number("0.10") + 0.2 = 0.30000000000000004
"500000.00" + 1 = 500000.001
id 9007199254740993 после JSON.parse = 9007199254740992; Number.MAX_SAFE_INTEGER = 9007199254740991
копейки BigInt 50000000 + 20 = 50000020; Intl ru-RU: "500 000,20 ₽"

Первая строка — двоичная дробь. Вторая — склейка строки с числом вместо сложения. Третья важнее всего для бэкенда: 64-битные идентификаторы (Snowflake, последовательности Oracle и PostgreSQL на bigint) больше 2^53 молча теряют младшие разряды. Ошибки при этом нет, просто приходит соседний номер. Четвёртая строка показывает рабочий вариант: суммы в копейках как bigint, а показ через Intl.NumberFormat.3

Опыт 4: цикл событий. Скрипт eventloop.mjs на Node 22 расставил шесть действий в таком порядке: «2 async-функция до await», «1 синхронный код», «3 then (микрозадача)», «4 queueMicrotask», «4б после await (микрозадача)», «5 setTimeout 0 (макрозадача)». Тело async-функции до первого await выполняется синхронно, поэтому оно оказалось раньше строки, записанной после вызова. Микрозадачи (продолжения промисов) выполняются до любого таймера. Вторая часть опыта: таймер на 10 мс при занятом 300 мс синхронным циклом сработал через 302 мс. В браузере тот же механизм, и долгий синхронный расчёт на клиенте замораживает страницу целиком: клики и перерисовка ждут конца цикла. Аналог из Java — работа в потоке обработки событий Swing (EDT). Только здесь поток один на всё, и отдать работу пулу нельзя: тяжёлое выносят в Web Worker или на сервер.4

🎲 Редкий случай. Тест сравнил отформатированную сумму со строкой и упал, хотя на экране всё совпадало. Intl.NumberFormat('ru-RU', { style: 'currency', currency: 'RUB' }) вернул 500 000,20 ₽, но коды символов в выводе такие: 35 30 30 a0 30 30 30 2c 32 30 a0 20bd. Разряды и знак рубля отделены неразрывным пробелом U+00A0, а не обычным. Строка в тесте, набранная с клавиатуры, с ним не совпадает. Сравнивайте суммы до форматирования, а форматированный вывод проверяйте по нормализованной строке или через toLocaleString в самом тесте. Та же ловушка ждёт бэкенд, если отчёт в Excel собирается из строк, отформатированных на клиенте.

❓ Спрашивают на интервью. Чем система типов TypeScript отличается от Java? Типизация структурная, а не номинальная: совместимость определяется формой объекта. Типы полностью стираются при компиляции, и во время выполнения их нет, поэтому as ничего не проверяет. Есть объединения и пересечения типов, сужение по условию и поле-дискриминатор, литеральные типы ('RUB' | 'USD'). any выключает проверку, unknown требует сужения. Число одно, number (double), целые точны до 2^53 − 1, для больших есть bigint.2

G3. Модель React: рендер, снимок состояния, позиция в дереве

React проще понять как функцию, а не как набор классов с жизненным циклом. Компонент — функция, которая получает пропсы и состояние и возвращает описание интерфейса (JSX). React вызывает её, сравнивает результат с прошлым и вносит в DOM только разницу. Эти две фазы в документации называются рендером и фиксацией (render и commit). Из этой модели следуют три правила, на которых бэкенд-разработчик спотыкается чаще всего. Состояние в обработчике события — снимок на момент рендера. Функция компонента должна быть чистой. Состояние привязано к позиции компонента в дереве, а не к переменной.

Снимок состояния (опыт G-1). Кнопка трижды вызывает setN(n + 1) в одном обработчике. После клика на ней 1, а не 3. Внутри этого рендера n равно 0, и три вызова трижды просят установить 1. Если записать обновление функцией, setN(x => x + 1) трижды, получится 3: React ставит обновления в очередь и применяет каждое к результату предыдущего. Документация формулирует так: значение переменной состояния никогда не меняется внутри одного рендера, даже если код обработчика асинхронный. Для Java-разработчика полезна аналогия с эффективно финальной переменной, захваченной лямбдой. Обработчик замыкает значения своего рендера, и setTimeout внутри него через три секунды увидит старые значения.5

Чистота и StrictMode (опыт G-2). В режиме разработки StrictMode вызывает функцию компонента дважды, а каждый эффект прогоняет лишний раз по схеме «установка → очистка → установка». Делает он это намеренно, чтобы проявились нечистый рендер и забытая очистка. Опыт с эффектом, который «открывает подключение» к ленте событий:

StrictMode без очистки: запусков 2, открыто 2
StrictMode с очисткой:  запусков 2, открыто 1
без StrictMode:         запусков 1

Без очистки два «подключения» живут одновременно, и это тот же дефект, который в проде проявится при переходе между экранами: подключения копятся, а сервер видит рост числа открытых WebSocket от одного пользователя. Проверки StrictMode работают только в режиме разработки и не влияют на продакшен-сборку. Значит, двойной запрос, который бэкенд-разработчик видит в журнале со стенда разработчика, ещё не дефект клиента. Если же он приходит из продакшена, это дефект.6

Позиция в дереве и ключи (опыт G-4). React связывает состояние с местом компонента в дереве. В списке «место» — это ключ (key). Если ключом служит индекс массива, то после удаления первой строки вторая строка занимает место первой и наследует её состояние. В опыте у каждой строки платежа есть поле комментария со своим состоянием (неуправляемый input). Пользователь пишет комментарий к платежу 1 и удаляет первую строку:

key=индекс: после удаления строки 1 поле «Платёж 2» содержит «комментарий к платежу 1»
key=id:     после удаления строки 1 поле «Платёж 2» содержит «»

Для финтеха это не косметика: комментарий, сумма в поле ввода или отметка «подтверждаю» уезжает к соседней операции. Ключ должен быть устойчивым идентификатором записи из данных, обычно её id с сервера. Вторая сторона того же механизма полезна: смена ключа сбрасывает состояние целиком. <Profile key={userId} /> гарантирует, что при переходе к другому клиенту форма не сохранит черновик от предыдущего. Документация приводит именно этот пример с комментарием на чужом профиле.7

Что происходит внутри (по Кумару). Тежас Кумар в «Fluent React» разбирает механизм на уровне исходников React. Элемент — обычный объект с полем $$typeof, типом (строка для тегов DOM, функция для компонента), ключом и пропсами. Рендер компонента — повторный вызов его функции. Главное, что стоит помнить бэкенд-разработчику: когда меняется состояние компонента, React перерисовывает его и всех потомков, не проверяя, изменились ли их пропсы. Дочерний компонент со статичным пропсом всё равно вызывается заново. Пропуск включает только memo (G4). Внутри работает Fiber-реконсилер (с React 16). Это два дерева, текущее и рабочее, как двойная буферизация в играх. Фаза рендера (beginWork вниз по дереву, completeWork вверх) строит следующее состояние вне экрана, поэтому её можно прервать и выбросить. Фаза фиксации (commit) применяет изменения к DOM. Layout-эффекты (useLayoutEffect) идут до отрисовки, пассивные (useEffect) после неё. Планировщик, по Кумару, отдаёт управление главному потоку каждые 5 мс: это меньше кадра даже при 120 кадрах в секунду. Приоритеты задаются «полосами» (lanes) в битовой маске. Клик попадает в SyncLane, ответ сети и таймер — в DefaultLane, startTransition — в одну из TransitionLanes. Аналогия для Java-разработчика: рендер — чистая функция, которая строит план изменений, а commit — короткая транзакция, которая его применяет.23

🎲 Редкий случай. Компонент, объявленный внутри другого компонента, теряет состояние на каждом рендере. Функция function MyTextField() {...}, определённая в теле MyComponent, на каждом рендере создаётся заново. Для React это новый тип компонента на той же позиции, поэтому поле ввода сбрасывается после любого клика по соседней кнопке. ИИ-ассистенты делают так часто, когда «выносят кусок разметки во вспомогательный компонент» прямо в теле функции. Компоненты объявляют только на верхнем уровне модуля.7

❓ Спрашивают на интервью. Зачем нужен key и почему плохо использовать индекс? Ключ сообщает React, какой элемент списка какой записи соответствует между рендерами. По ключу React сохраняет состояние и DOM-узлы. Индекс меняется при вставке, удалении и сортировке, поэтому состояние и введённые данные переезжают к другой записи. Брать нужно устойчивый идентификатор из данных. Тот же механизм позволяет намеренно сбросить состояние поддерева сменой ключа.7

G4. Хуки: состояние, эффекты, мемоизация, контекст

Хуки — функции с именем на use, через которые компонент-функция получает состояние и доступ к внешнему миру. Их два правила кажутся произвольными, пока не знаешь устройства. Хуки вызывают только на верхнем уровне компонента или своего хука и только из функций React. Нельзя вызывать их в условиях, циклах, после раннего return, в обработчиках и в try/catch. Причина в том, что React различает хуки одного компонента по порядку вызова. Первый useState получает первую ячейку, второй — вторую. Условный вызов сдвигает порядок, и состояние читается из чужой ячейки. Ловит это eslint-plugin-react-hooks, и в любом проекте он должен быть включён.8

useEffect и когда он не нужен. Эффект нужен, чтобы синхронизировать компонент с внешней системой: сетью, подпиской, виджетом не на React, API браузера. Если внешней системы нет, эффект почти всегда лишний. В документации этому посвящена отдельная страница «You Might Not Need an Effect», и её стоит прочитать целиком. Вот типичные лишние эффекты, а по опыту автора именно так пишет ИИ-ассистент:

  • Производное значение. Значение вычисляют через эффект и кладут в состояние (useEffect(() => setFullName(first + ' ' + last))). Это лишний проход рендера со старым значением, а нужно вычислить прямо в рендере.
  • Сброс состояния при смене пропса. Делают эффектом, хотя достаточно сменить ключ.
  • Действие пользователя. Отправку формы, POST, уведомление переносят в эффект, хотя место им в обработчике события.
  • Цепочки эффектов. Каждый эффект меняет состояние, чтобы запустить следующий.

Критерий из документации простой. Если код должен выполниться потому, что компонент показан пользователю, его место в эффекте. Если потому, что пользователь что-то сделал, — в обработчике.9

Бесконечный эффект (опыт G-5). Зависимости эффекта сравниваются по ссылке, через Object.is. Объект-литерал { page: 1 }, созданный в теле компонента, на каждом рендере новый. Эффект, который зависит от него и кладёт «ответ сервера» в состояние, запускает новый рендер, новый объект и снова эффект:

зависимость объект-литерал: эффект выполнился 50 раз за один показ   (остановлен счётчиком в тесте)
зависимость строка:         эффект выполнился 1 раз за один показ

Без искусственного ограничителя цикл продолжался бы бесконечно. Если в эффекте fetch, бэкенд видит от одного пользователя поток одинаковых запросов, похожий на атаку. Именно этот случай описан в главе 59 (раздел 3.6) как редкий: здесь механизм воспроизведён и измерен. Лечится он тремя способами: примитив в зависимостях вместо объекта, объект за пределами компонента или в useMemo, данные через библиотеку запросов (G5). Со стороны бэкенда помогают ограничение частоты по пользователю (глава 35) и метрика «одинаковые запросы от одного клиента за секунду».

memo, useCallback, useMemo (опыт G-6). memo пропускает перерисовку компонента, если пропсы не изменились по ссылке. Таблица из десяти строк, обёрнутых в memo, получает в пропсах обработчик onPay. Родитель перерисован пять раз:

стрелка в рендере: строк при первом показе 10, после 5 перерисовок родителя всего 60
useCallback:       строк при первом показе 10, после 5 перерисовок родителя всего 10

Стрелочная функция в рендере каждый раз новая, поэтому memo бесполезен: все строки перерисовываются. useCallback сохраняет одну и ту же функцию между рендерами, и строки не трогаются. useMemo делает то же для вычисленного значения. Документация советует мемоизировать только то, что измеримо дорого: расчёт дольше 1 мс или тысячи объектов. Для нового кода есть компилятор React 1.0. Он мемоизирует автоматически и точнее ручного (в том числе после раннего return, где хуки вызывать нельзя), а useMemo и useCallback оставлены как ручное управление. По данным команды React, в Meta Quest Store компилятор ускорил первую загрузку и переходы до 12 %, отдельные взаимодействия — более чем в 2,5 раза. Обещанием для любого приложения это не считается.10

Контекст (опыт G-7). Контекст передаёт значение вниз по дереву без пропсов: текущего пользователя, тему, права. Каждый потребитель перерисовывается, когда значение меняется по ссылке. Провайдер, который создаёт объект value={{ user: 'dev.team' }} прямо в рендере, отдаёт новый объект на каждой своей перерисовке. Три потребителя в memo при показе отрисовались 3 раза, после пяти перерисовок провайдера — 18 раз, то есть все потребители на каждую перерисовку, хотя пользователь не менялся. Значение контекста стабилизируют через useMemo или выносят часто меняющееся в отдельный контекст. Для бэкенд-разработчика тут знакомый мотив: контекст в React играет роль глобального бина, и его «горячие» поля так же портят производительность, как общий изменяемый объект в синглтоне.

Кумар показывает, почему memo бессилен против контекста, прямо по исходнику реконсилера. memo() возвращает объект с $$typeof: REACT_MEMO_TYPE и функцией сравнения. Функция updateMemoComponent пропускает работу (bailoutOnAlreadyFinishedWork), только если поверхностное сравнение пропсов вернуло «равны», ссылка ref та же и нет запланированных обновлений состояния или контекста. Изменение контекста перерисовывает memo-компонент без всякой смены пропсов, что опыт G-7 и показал. Там же разобрано, где useCallback бесполезен: обработчик на хост-элементе вроде <button> не нужно стабилизировать. React вешает один слушатель на корень приложения (делегирование) и просто подменяет функцию, а перерисовывать «внутри» кнопки нечего. useCallback имеет смысл, только когда функция уходит в memo-компонент, иначе это лишняя работа. Сам Кумар формулирует: memo — подсказка реконсилеру, а не гарантия.23

Что ещё нужно знать. useRef — изменяемая ячейка, которая переживает рендеры и не вызывает перерисовку (идентификатор таймера, DOM-узел). useReducer — состояние с переходами через функцию (state, action) => newState, удобен для форм и автоматов, и бэкенд-разработчику он ближе всего: это конечный автомат из главы 5. useEffectEvent (React 19.2) выносит из эффекта «событийную» часть: функция видит последние пропсы, но не входит в зависимости. Пример из анонса — уведомление о подключении к чату, которое использует тему оформления, но не должно переподключать чат при смене темы. useSyncExternalStore подписывает компонент на внешнее хранилище и заменяет ручную подписку в эффекте.11

🎲 Редкий случай. Удаление «лишнего» useMemo при обновлении компилятора изменило поведение. В статье о компиляторе 1.0 команда React предупреждает: мемоизированное значение может служить зависимостью эффекта где-то ниже по дереву. Если поменять, как и мемоизируется ли оно, эффект начнёт срабатывать чаще или реже. Поэтому существующую ручную мемоизацию советуют не удалять без тестов, а компилятор при слабом покрытии фиксировать точной версией (--save-exact), как фиксируют версию аннотационного процессора в Maven.10

❓ Спрашивают на интервью. Почему хуки нельзя вызывать в условии? React хранит состояние хуков компонента по порядку вызова: первый вызов получает первую ячейку и так далее. Условный вызов сдвигает порядок между рендерами, и хук читает чужое состояние. Поэтому хуки вызывают на верхнем уровне компонента или своего хука, до любого раннего return, а проверяет это eslint-plugin-react-hooks. Исключение — API use из React 19: его можно вызывать в условии.8

G5. Данные с сервера: гонки, отмена, кэш и повторы

Для бэкенд-разработчика самая важная часть фронтенда — то, как клиент обращается к его API. Отсюда приходят всплески одинаковых запросов, повторы после ошибок, устаревшие ответы на экране и запросы, отменённые на полпути. Документация React прямо пишет, что загрузка данных в эффекте возможна, но требует очистки от гонок, а кэширование, загрузку на сервере и устранение «водопадов» запросов лучше отдать фреймворку или библиотеке. Ниже два опыта: гонка ответов при ручной загрузке и поведение TanStack Query по умолчанию.

Гонка ответов (опыт G-3). Поиск по мере ввода отправляет запрос на каждую букву. Запрос «hell» отвечает за 80 мс, «hello» — за 10 мс. Пользователь видит последний пришедший ответ, а не последний отправленный:

запрос «hello», без защиты на экране:   результаты для «hell»
запрос «hello», с флагом ignore на экране: результаты для «hello»

Исправление из документации — флаг ignore в очистке эффекта: при смене запроса старый эффект помечает свой ответ как неактуальный. В стенде фулстек-приложения (G8) вместо флага используется AbortController. Очистка вызывает ctrl.abort(), и браузер действительно обрывает запрос. Во вкладке Network такой запрос помечен (canceled), а сервер видит оборванное клиентом соединение (как именно это отражается в журнале Tomcat, автор не проверял, ⚠️). Отмена запросов, которые больше не нужны, снижает нагрузку. Но обработчик на сервере всё равно доработает до конца, если не проверяет обрыв соединения, поэтому дорогой поиск лучше защищать таймаутом и на стороне сервера.9

TanStack Query (опыт G-8). Библиотеки запросов (TanStack Query, SWR, RTK Query) держат кэш серверного состояния по ключу, дедуплицируют одинаковые запросы, обновляют данные в фоне и повторяют неудачные запросы. Два опыта с настройками по умолчанию:

два компонента с одним queryKey → запросов к серверу: 1
сервер отвечает 500 → запросов до показа ошибки: 4, прошло 7.0 с (настройки по умолчанию)

Первое — дедупликация: два компонента на экране, а запрос один. Второе важнее для бэкенда. По документации неудачный запрос «молча повторяется 3 раза с экспоненциальной задержкой», прежде чем ошибка попадёт в интерфейс. Отсюда 4 запроса и 1 + 2 + 4 = 7 секунд, что и показал опыт. Ещё три умолчания:

  • данные из кэша сразу считаются устаревшими (staleTime: 0);
  • устаревшие данные перезапрашиваются при монтировании нового экземпляра, при возврате фокуса в окно и при восстановлении сети;
  • неактивные запросы удаляются из кэша через 5 минут.

Что из этого следует для бэкенда:

  1. Каждый 5xx от вашего сервиса умножается на 4. При частичном отказе нагрузка от фронтенда вырастает, а не падает. Это та же лавина повторов, что разобрана в главе 35, только источник — браузеры всех пользователей.
  2. Пользователь, который переключается между вкладками, создаёт фоновые запросы при каждом возврате.
  3. Мутации (useMutation) по умолчанию не повторяются. Если фронтенд включит повторы для POST, на бэкенде нужна идемпотентность по ключу (глава 27, раздел 4.3).

Договариваются об этом явно:

  • retry отключают для 4xx и ограничивают для 5xx;
  • staleTime выставляют по смыслу данных (справочник валют — часы, баланс — секунды);
  • бэкенд отдаёт Retry-After на 429 и 503, а клиент его соблюдает.12

Инвалидация после мутации (опыт B-2). После создания записи список надо перезапросить, и в TanStack Query это делают через queryClient.invalidateQueries. Даниэль Бюгль в «Modern Full-Stack React Projects» пишет вызов как invalidateQueries(['posts']) (с. 117). В пятой версии библиотеки метод принимает объект фильтров, и массив без поля queryKey фильтром не служит. На TanStack Query 5.12.1, той же версии, что в книге, вызов с массивом пометил устаревшими и ['posts'], и не связанный с ним ['users', '1']. Вариант invalidateQueries({ queryKey: ['posts'] }) пометил только посты. Код из книги работает, но случайно: после каждой мутации перезапрашивается всё, что есть в кэше. Под нагрузкой это лишние запросы ко всем API экрана, а на TypeScript такой вызов не скомпилировался бы.3031

🎲 Редкий случай. На графике нагрузки ровно четыре пика на каждую ошибку. После выката с дефектом сервис начал отвечать 500 на один запрос, и число обращений к нему выросло в четыре раза, а метрика ошибок — в три. Ничего загадочного: одна ошибка в интерфейсе — это четыре попытки библиотеки запросов. Сначала их приняли за атаку, и разбирать пришлось по журналу доступа. Если на стенде виден такой рисунок, спросите фронтенд о политике повторов до того, как включать защиту от DDoS.12

❓ Спрашивают на интервью. Чем серверное состояние отличается от клиентского и почему для него берут TanStack Query, а не Redux? Клиентское состояние принадлежит интерфейсу: открыт ли диалог, что введено в поле. Серверное — копия данных, владелец которых сервер. Оно устаревает, его надо перезапрашивать, дедуплицировать и сбрасывать после изменений. Redux и useState хранят значение, но не знают о свежести и повторах. Библиотека запросов закрывает это из коробки. Ценой идут умолчания (повторы, фоновая перезагрузка), о которых бэкенд должен знать.12

Обработка ошибок в примерах «JavaScript: The Definitive Guide» (опыты FL-20…FL-27). Фланаган разбирает fetch подробно и честно предупреждает, что ответ 404 или 500 обещание не отклоняет (гл. 15, с. 519–520). Но в его примерах есть ошибки ровно на тех путях, которые бэкенд-разработчик проверит первыми.

Строгое сравнение типа. «Реалистичный» пример проверяет response.headers.get("Content-Type") !== "application/json" и бросает TypeError (гл. 13, с. 357; гл. 15, с. 520). Сервер на стенде отдал application/json; charset=utf-8, и проверка признала корректный ответ сломанным. Тип медиа сравнивают без параметров: type.split(";")[0].trim().

Несуществующий класс ошибки. В том же примере ветка catch различает ошибки через e instanceof NetworkError (с. 357–358). Глобального NetworkError нет. При обрыве сети fetch в Node отклоняется с TypeError: fetch failed, и проверка в catch сама бросает ReferenceError: NetworkError is not defined. Обработчик падает ровно тогда, когда должен сработать. В книге 2020 года нет и AbortSignal.timeout(ms): свой fetchWithTimeout автор строит на setTimeout и не снимает таймер после ответа (с. 527).

Обещания, созданные заранее. Цикл for await по массиву urls.map(url => fetch(url)) автор показывает как способ обработать ответы по порядку (гл. 13, с. 370–371). На стенде первый ответ шёл 300 мс, а третий запрос отклонился сразу. Процесс завершился с кодом 1 до того, как цикл получил первый ответ, и catch вокруг цикла не сработал: отказ третьего обещания никто не ждал, и Node счёл его необработанным. По Фланагану необработанный отказ с Node 13 только печатает предупреждение, а фатальным станет «в будущем» (гл. 16, с. 581). Это будущее наступило в Node 15. Для параллельных запросов берут Promise.all или Promise.allSettled, а не цикл по заранее созданным обещаниям.

Мелочи с большими последствиями. .catch(e => console.error) (гл. 15, с. 529) ничего не пишет в лог: стрелка возвращает функцию console.error, а не вызывает её. new URL("/api/search") (с. 521) бросает TypeError: Invalid URL, потому что относительному адресу нужна база, например new URL("/api/search", location.origin). Функция поиска из листинга не выполнилась бы ни разу.3435

G6. Контракт: OpenAPI, типы TypeScript и проверка на границе

Фулстек-разработчик выигрывает у двух отдельных команд в одном: контракт между клиентом и сервером у него проверяет компилятор, а не созвон. Цепочка выглядит так. Бэкенд описывает API в OpenAPI (вручную или генерирует из кода, глава 27, раздел 8). По описанию генерируются типы TypeScript. Клиент пишется против этих типов, и несовместимое изменение ломает сборку. Ниже то, что эта цепочка ловит и чего не ловит, и почему на границе нужна ещё и проверка во время выполнения.

Генерация типов. Описание limits.yaml (OpenAPI 3.1, схема Limit с полями clientId: string, dailyLimit: string с шаблоном ^[0-9]+[.][0-9]{2}$, used: string | null и currency из перечисления RUB, USD) превращено в типы командой npx openapi-typescript api/limits.yaml -o src/api.d.ts за 25 мс. Схема Limit в результате выглядит так:

TypeScript
Limit: {
    /** @description 64-битный идентификатор строкой */
    clientId: string;
    dailyLimit: string;
    used?: string | null;
    /** @enum {string} */
    currency: "RUB" | "USD";
};

Генератор даёт и типы операций: путь, параметры, ответы 200 и 404 с телом application/problem+json. Шаблон pattern в тип не попал: TypeScript не умеет выражать регулярные выражения, и формат суммы остаётся на совести проверки во время выполнения.

Что ловит компилятор. В файле с намеренными ошибками tsc --noEmit нашёл все шесть:

(7,3)   TS2322: Type 'string' is not assignable to type 'number'.        ← dailyLimit + 1 в функции, обещающей number
(11,10) TS18049: 'l.used' is possibly 'null' or 'undefined'.             ← необязательное поле без проверки
(14,66) TS2322: Type '"EUR"' is not assignable to type '"RUB" | "USD"'. ← валюты нет в перечислении
(29,29) TS2345: Argument of type 'AccountNo' is not assignable to parameter of type 'CardNo'.
(34,81) TS2353: Object literal may only specify known properties, and 'cvv' does not exist in type ...
(40,27) TS18046: 'fromServer2' is of type 'unknown'.

Три места, где ошибка есть по смыслу, компилятор пропустил: счёт вместо карты при одинаковой форме типов, лишнее поле через переменную и any. Вторая строка закрывает редкий случай из главы 59 (раздел 3.2), где поле used стало null и экран упал: при сгенерированных типах и strict такой код не соберётся.

Проверка на границе (опыт G-10). Тип не защищает от сервера, который прислал не то, что описано. Схема zod, написанная по тому же контракту, разобрала ответ с числом вместо строки и вернула ошибку dailyLimit: invalid_type. as Limit тот же ответ пропустил. Ставить проверку на каждый ответ дорого и не нужно. Ставят её на границе с внешними и плохо контролируемыми источниками: ответы партнёров, данные из localStorage, сообщения WebSocket, параметры URL.

Три способа получить тип и проверку из одного источника (опыт E-1). Писать тип и проверку отдельно — худший вид дублирования: они разойдутся на первом же новом поле. Вандеркам разбирает три выхода (Item 74, с. 319–324). Первый — генерировать типы из описания, которое уже есть (OpenAPI, GraphQL), и проверять данные валидатором JSON Schema. Этот путь он советует, когда описание API существует, то есть ровно в нашем случае. Второй — описать схему в библиотеке вроде zod и вывести тип из неё через z.infer. Третий — сгенерировать JSON Schema из типа TypeScript утилитой typescript-json-schema и проверять её через Ajv. В книге способы различаются ценой (лишний шаг сборки или второй язык описания типов), а результат подразумевается одинаковым. Опыт показал, что по умолчанию они проверяют разное. Одни и те же четыре тела запроса получили: ручная проверка из книги (ровно три ключа нужных типов), z.object, z.strictObject, Ajv со схемой, сгенерированной как в книге, и Ajv со схемой, сгенерированной с флагами required и noExtraProps:

                       вручную  z.object           z.strictObject  Ajv, как в книге  Ajv, required + noExtraProps
корректное             200      200                200             200               200
пустой объект {}       400      400                400             200               400
лишнее поле authorId   400      200, поле срезано  400             200               400
title числом           400      400                400             400               400

Схема, которую typescript-json-schema 0.68 выдаёт по умолчанию, совпадает с листингом книги и не содержит массива required. Все поля в ней необязательны, поэтому Ajv пропустил пустой объект. z.object не отверг лишнее поле, а молча срезал его, и обработчик получил объект без authorId. От подмены полей (mass assignment, глава 42, раздел 7.1) срезание защищает. Но клиент не узнает, что сервер проигнорировал часть запроса, и ошибку в контракте никто не заметит. Отвергать лишние поля умеет z.strictObject. Тот же выбор есть на сервере: в Jackson 3 FAIL_ON_UNKNOWN_PROPERTIES выключен по умолчанию, и лишнее поле в JSON тоже молча пропадает (глава 14, раздел 6.1). Правило одно для обеих сторон: договориться, что делает граница с лишними и недостающими полями, и закрепить это тестом, а не полагаться на умолчания инструмента.2627

Утверждение типа — в одном месте (опыт E-2). Если проверка во время выполнения не нужна или дорога, as всё равно не разбрасывают по вызывающему коду. Вандеркам советует спрятать небезопасное утверждение в одну функцию с правильной сигнатурой: fetchPeak(id): Promise<MountainPeak>, а не Promise<unknown>, на который каждый вызывающий напишет своё as (Item 45, с. 190–194). Совет верный, а листинг с проверкой формы ответа содержит ошибку. Результат checkedFetchJSON(...) присвоен переменной без await, поэтому в maybePeak лежит Promise, а не данные. Проверка 'firstAscentYear' in maybePeak всегда ложна, и функция всегда бросает Invalid mountain peak: {}: JSON.stringify от промиса даёт пустой объект. tsc в строгом режиме принял этот код, потому что промис — объект и оператор in к нему применим. Даже с добавленным await в листинге остаётся второй вызов checkedFetchJSON в return, то есть два запроса вместо одного. Исправленный вариант возвращает проверенное значение первого запроса. В Kotlin та же ошибка с Deferred вместо результата await() не скомпилировалась бы: у Deferred нет полей данных. Здесь структурная проверка in её пропустила.2627

any на входе запрещают целиком. JSON.parse и Response.json() возвращают any по историческим причинам: тип unknown появился только в TypeScript 3.0 в июле 2018 года, и менять сигнатуры было поздно. Вандеркам предлагает переопределить их слиянием объявлений (interface JSON { parse(...): unknown }, interface Body { json(): Promise<unknown> }) или подключить пакет ts-reset (Item 71, с. 301–304). После этого каждый ответ сервера приходит как unknown, и компилятор требует либо проверку, либо явное утверждение в одной функции. Сгенерированные типы держат в синхронизации так, как он советует для любой кодогенерации: генерировать в CI и проверять через git diff, что результат не изменился (Item 58, с. 257–259). Для api.d.ts из openapi-typescript это одна строка конвейера.26

Деньги и long из Spring Boot. Самый частый разрыв контракта у Java-бэкенда — сериализация чисел. В стенде G8 контроллер на Spring Boot 4.1.1 отдаёт один и тот же лимит двумя способами: record с long и BigDecimal как есть, и record с аннотацией @JsonFormat(shape = JsonFormat.Shape.STRING) на этих полях. Ответы сервера и то, что увидел JavaScript в Chromium:

{"clientId":9007199254740993,"dailyLimit":500000.10,"currency":"RUB"}
  → в JS: clientId=9007199254740992, dailyLimit=500000.1
{"clientId":"9007199254740993","dailyLimit":"500000.10","currency":"RUB"}
  → в JS: clientId=9007199254740993, dailyLimit=500000.10

Jackson отдал BigDecimal числом с двумя знаками, а JSON.parse превратил его в double и потерял незначащий ноль, то есть масштаб суммы. Идентификатор клиента стал соседним номером. Со строкой всё дошло без потерь. Правило фулстек-контракта для финтеха: идентификаторы long и деньги — строкой, даты — в ISO 8601 со смещением, валюта — отдельным полем. Всё это записывается в OpenAPI, чтобы генератор дал клиенту string, а не number.13

🎲 Редкий случай. Генератор типов перестал запускаться после обновления TypeScript. На стенде стоял TypeScript 7.0.2 — новая нативная реализация компилятора. openapi-typescript 7.13.0 упал на первой строке: TypeError: Cannot read properties of undefined (reading 'createKeywordTypeNode') в ts.factory. Генератор строит код через программный API компилятора на JavaScript, а пакет typescript@7 этого API не предоставляет. Пакет генератора честно объявляет peerDependencies: typescript ^5.x. Но npm с --legacy-peer-deps (без него установка падала на другом дефекте, см. G10) это требование не проверил. С TypeScript 5.9.3 генерация прошла. Инструменты, которые зависят от API компилятора (генераторы, часть плагинов линтера), держат на TypeScript 5, пока они не объявят поддержку 7. Сочетание версий фиксируют в package.json так же жёстко, как плагины Maven.

❓ Спрашивают на интервью. Как вы обеспечиваете, чтобы фронтенд и бэкенд не разошлись в контракте? Контракт описан в OpenAPI и хранится в репозитории. Типы TypeScript генерируются из него при сборке, поэтому несовместимое изменение ломает сборку клиента. На границе с ненадёжными данными стоит проверка во время выполнения (zod или аналог). Деньги и 64-битные идентификаторы передаются строкой, даты — в ISO 8601. В одном репозитории (G8) всё это проверяется одной командой сборки.13

G7. Безопасность на клиенте: XSS, токены, секреты в бандле

Безопасность фронтенда для бэкенд-разработчика сводится к четырём вопросам. Может ли чужой скрипт выполниться на странице? Где лежит токен и кто может его прочитать? Что из конфигурации попало в файлы, которые скачивает любой посетитель? Насколько безопасна серверная часть фреймворка? На каждый вопрос ниже есть опыт или первоисточник. Общая теория веб-безопасности (OWASP, CSRF, CSP, OAuth в браузере) разобрана в главах 13 и 42. Здесь только то, что специфично для React и сборки.

XSS (опыт G-9). JSX экранирует строки. Комментарий к платежу <img src=x onerror="window.__xss=1">, выведенный как {payload}, попал в DOM текстом: innerHTML содержит &lt;img src=x onerror="window.__xss=1"&gt;, элементов img — 0. Тот же текст через dangerouslySetInnerHTML создал настоящий элемент img (1 штука). В браузере его обработчик onerror выполнился бы. Название свойства длинное и пугающее нарочно: это единственный штатный путь вставить HTML в обход экранирования. Если HTML действительно нужен (письмо, описание продукта из CMS), его очищают санитайзером. React 19.3 вдобавок поддерживает Trusted Types: при политике Content-Security-Policy: require-trusted-types-for 'script' браузер принимает в innerHTML только объекты, созданные вашей политикой очистки, и React больше не превращает их обратно в строки. Остальные пути XSS в React-приложении: ссылки href со схемой javascript:, данные, вставленные в <script> при серверном рендеринге, сторонние библиотеки, работающие с DOM напрямую.14

Почему у элемента $$typeof — символ (опыт K-8). Это защита именно от бэкенда. Себастьян Маркбоге добавил метку в React в сентябре 2015 года в PR с веткой xssfix, чтобы «безопасно отличать элементы от обычных объектов, которые могли прийти из пользовательского JSON». Если сервер вернул в поле комментария объект {"type": "img", "props": {...}}, а клиент вывел его как {data.comment}, React откажется: в опыте получилось Objects are not valid as a React child. Символ нельзя передать через JSON.parse, и подделать элемент из данных нельзя. Кумар в главе о серверных компонентах для учебного сериализатора предлагает обратное: при JSON.parse превращать любой ключ "$$typeof" обратно в символ. Проверка на React 19.3 дала два результата. С символом из книги, Symbol.for("react.element"), React 19 падает с ошибкой A React Element from an older version of React was rendered, потому что с 19-й версии элементы помечены символом react.transitional.element. С актуальным символом JSON с ключом "$$typeof" из пользовательских данных превратился в настоящий <img> в DOM. Защита отключена одной строкой reviver. Для бэкенда вывод такой: если клиент или BFF «оживляет» объекты из JSON по признаку в данных, это та же уязвимость десериализации, что разобрана ниже на примере CVE-2025-55182.24

CSRF не зависит от того, где рендерится страница. Кумар утверждает, что клиентское приложение уязвимо к CSRF, а серверный рендеринг с токеном в HTML её снимает (гл. 6). Для Java-бэкенда это смещение акцента. CSRF возникает при аутентификации куками без проверки происхождения запроса. Лечится она одинаково для SPA и для SSR: токен (в SPA его отдают через API или куку, как CookieCsrfTokenRepository в Spring Security), атрибут SameSite и проверка Origin на сервере (глава 13, раздел 9.1). Сам по себе серверный рендеринг ни от чего не защищает.23

Где хранить токен. localStorage доступен любому скрипту на странице, поэтому одна XSS уводит токен целиком, и сервер не отличит злоумышленника от пользователя. Куки с флагами HttpOnly, Secure и SameSite скрипту не видна, браузер прикладывает её сам, но тогда нужна защита от CSRF (глава 13, раздел 9.1). Схема, которую сегодня рекомендуют для браузерных приложений с OAuth, — Backend for Frontend: токены живут на сервере, браузер держит только сессионную куку, а BFF сам передаёт вызовы к API. В фулстеке одним модулем (G8) это получается почти бесплатно: Spring Boot и есть BFF, страница и API на одном origin, кука сессии работает без CORS. Подробности OAuth 2.0 для браузерных приложений — в главе 42.

Что в советах про JWT не так (опыты B-3, B-4, B-5). У Бюгля аутентификация на JWT проходит через всю книгу, и бэкенд-разработчику полезно увидеть, где учебный код расходится с тем, что спросят на собеседовании. Первое — утверждение, что токен в заголовке вместо куки избавляет от проблем CORS (с. 154). Всё наоборот. Заголовок Authorization делает запрос «непростым», и браузер перед ним отправит предварительный OPTIONS. Кука на том же источнике, как в G8, CORS не требует вовсе. Второе — хранение. В главе 6 токен лежит в контексте React и пропадает при перезагрузке страницы (автор это признаёт), в главе 13 — снова в localStorage, в главе 17 — в куке с httpOnly и secure, но без SameSite (с. 155, 338, 418). Третье — перебор имён. В REST-маршруте входа ошибка маскируется общей фразой (с. 160). Но распознаватель GraphQL отдаёт исключение сервиса как есть, и Apollo Server 4.10.0 вернул клиенту «invalid username!» для несуществующего имени и «invalid password!» для существующего. Так было и при NODE_ENV=production. Даже с одинаковым текстом существование имени выдаёт время ответа: при несуществующем имени bcrypt.compare не вызывается. На стенде медиана ответа была 0,03 мс против 56,5 мс при стоимости 10. Лечится сравнением с фиктивным хешем. Четвёртое — проверка прав в реальном времени. После рефакторинга чата клиент передаёт комнату в каждом сообщении, и сервер пишет туда без проверки socket.rooms.has(room) (с. 367). На socket.io 4.7.2 пользователь, состоящий только в public, отправил сообщение в закрытую комнату, и его участник это сообщение получил. Для Java всё это знакомо по Spring Security: одинаковое сообщение и одинаковое время при неудачном входе, проверка прав на каждое действие, а не только при подключении.3031

Секреты в бандле (опыт). Vite подставляет переменные окружения при сборке. В .env стенда три переменные: VITE_API_URL, VITE_PAYMENT_KEY и DB_PASSWORD. После vite build поиск по собранному JavaScript нашёл адрес API и значение sk_live_DEMO_dev_team_123 открытым текстом, а пароля базы нет. Так задумано, документация Vite прямо пишет: переменные с префиксом VITE_ попадают в клиентский код после сборки, поэтому секретов в них быть не должно. Всё, что попало в бандл, доступно любому посетителю через вкладку Sources. Ключ платёжного шлюза, токен карты или ключ LLM-провайдера в переменной VITE_* уже утёк. Такие вызовы идут через бэкенд.15

Карты исходников в продакшене. Карта (source map) связывает собранный файл с исходным кодом, и отладчик браузера показывает по ней TypeScript вместо сгенерированного JavaScript. Вандеркам предупреждает о двух вещах (Item 73, с. 313–319). Карту, встроенную в сам файл, браузер скачивает всегда. Карта со встроенным исходником публикует его целиком, вместе с комментариями и адресами внутреннего трекера задач. У Vite генерация карт при сборке по умолчанию выключена: в каталоге сборки стенда после vite build оказался один файл index-DXsPkNVa.js и ни одного .map. Если карты нужны для разбора ошибок из продакшена, их выгружают в систему сбора ошибок и не публикуют рядом с бандлом.2627

Серверные компоненты и CVE-2025-55182. 3 декабря 2025 года команда React опубликовала уязвимость в React Server Components: удалённое выполнение кода без аутентификации, CVSS 10.0. Её нашёл Лахлан Дэвидсон 29 ноября и сообщил через программу Meta Bug Bounty. Дефект был в том, как React декодирует данные, присланные на эндпоинты серверных функций, и затрагивал пакеты react-server-dom-webpack, -parcel и -turbopack версий 19.0, 19.1.0, 19.1.1 и 19.2.0. Исправления вышли в 19.0.1, 19.1.2 и 19.2.1. Уязвимы были и приложения без единой серверной функции, если они поддерживали серверные компоненты: Next.js, React Router в режиме RSC и другие фреймворки. Чисто клиентское приложение без серверной части React, вроде стенда G8, не затронуто. Позже к той же теме добавились отказ в обслуживании (CVE-2025-55184, CVE-2025-67779, CVE-2026-23864, все CVSS 7.5) и раскрытие исходного кода (CVE-2025-55183, CVSS 5.3). Для бэкенд-разработчика урок знакомый по Log4Shell (глава 42): десериализация недоверенных данных на сервере остаётся главным классом критических уязвимостей, и фронтенд-фреймворк с серверной частью — такой же серверный код, который надо обновлять по бюллетеням.16

🎲 Редкий случай. Секрет удалили из .env, но он остался в продакшене. Значение VITE_* вшивается в файл с хешем в имени (index-D6rOdBHG.js) в момент сборки. CDN и браузеры кэшируют такие файлы надолго, потому что хеш гарантирует неизменность содержимого. Исправленная сборка получит новый хеш, но старый файл останется доступен по старому адресу, пока его не удалят из хранилища и кэша CDN. Утёкший ключ всё равно отзывают и выпускают новый. Удалить его из следующей сборки недостаточно.15

❓ Спрашивают на интервью. Как защититься от XSS в React-приложении? JSX экранирует строки по умолчанию. Опасен dangerouslySetInnerHTML: туда передают только очищенный санитайзером HTML. Ещё опасны href с javascript: и сторонние библиотеки, работающие с DOM. Сверху ставят CSP, в React 19.3 — с Trusted Types. Чтобы XSS не превратилась в кражу сессии, токен держат не в localStorage, а на сервере (BFF) или в куке HttpOnly с защитой от CSRF.14

Три ошибки экранирования в листингах Фланагана (опыты FL-15, FL-32, FL-33). У них общая причина: String.prototype.replace со строкой в первом аргументе заменяет только первое вхождение. Для бэкенд-разработчика это важно, потому что все три листинга поданы как безопасные, а экранируют лишь частично.

Тег шаблона html (гл. 14, с. 396) обрабатывает значение цепочкой .replace("&", "&amp;").replace("<", "&lt;") и дальше по списку. На строке с двумя угловыми скобками экранировалась только первая: вторая пара < и > прошла в разметку как есть. Для функции, названной средством безопасной подстановки, это пробел в защите. Правильно — .replace(/&/g, "&amp;") с флагом g или replaceAll. Любопытно, что в другом месте той же книги (гл. 15, с. 426) автор экранирует правильно, через /&/g: внутри одной книги два несовместимых варианта.

Сервер чата на Server-Sent Events (гл. 15, с. 531–533) форматирует сообщение как "data: " + body.replace("\n", "\ndata: "). Префикс data: получает только первая строка тела. Если в теле несколько строк, вторая и последующие попадают в поток как отдельные поля протокола — тип события, идентификатор переподключения. На стенде клиент EventSource разобрал многострочное тело как событие чужого типа с подменённым идентификатором, и это ушло всем подключённым клиентам. Лечится тем же replace(/\n/g, ...), а надёжнее — кодированием каждой строки отдельно.

Статический сервер (гл. 16, с. 615–617) защищается от обхода каталога строкой filename.replace(/\.\.\//g, ""). Здесь флаг g есть, но замена нерекурсивна: из ....// после вырезания одного ../ остаётся ../. На стенде запрос /....//secret.txt (и на Windows /....\\secret.txt) вернул файл, лежащий выше корня. Строковая чистка пути ненадёжна в принципе. Правильно — path.resolve(root, "." + decodeURIComponent(pathname)) и проверка resolved.startsWith(root + path.sep); на стенде она отбила все варианты. В Spring тот же класс ошибки закрывают нормализацией пути и проверкой, что он остался внутри корня (глава 42).

Чего в книге 2020 года нет (чтение). Во врезке про клиентские хранилища сказано, что там нельзя держать пароли и номера счетов (с. 536) — это согласуется с правилом не класть токен в localStorage. Но в разделе про cookie (с. 539–543) нет ни флага HttpOnly (делает cookie недоступной для JavaScript — именно то, что нужно для сессии), ни SameSite (защита от CSRF). Для книги о клиентском JavaScript это заметный пропуск. Basic-авторизация через btoa(${username}:${password}) (с. 521) на стенде упала с InvalidCharacterError для логина «Иван»: btoa принимает только Latin-1. Для не-ASCII нужен TextEncoder и ручное кодирование в base64.3435

G8. Фулстек в одном модуле: React внутри Spring Boot, Vaadin, Hilla

Фулстек можно понимать как две роли в одном человеке: отдельный репозиторий фронтенда, отдельный бэкенда, CORS между ними, две сборки, два выката, контракт по договорённости. Можно понимать и как один модуль: один репозиторий, одна сборка, один артефакт, один origin, контракт проверяется компилятором. Для внутренних банковских систем, админок, кабинетов операционистов и инструментов поддержки второй вариант почти всегда проще и надёжнее. Именно его имеют в виду вакансии вида «бэкенд, который с ИИ пишет полный стек». Ниже он собран и запущен, а затем сравнён с вариантами, где фронтенд пишется на Java целиком.

Устройство проекта. Стенд tmp/fullstack-mono — обычный Spring Boot 4.1.1 со стартером spring-boot-starter-webmvc и каталогом frontend/ внутри:

  src/main/java/team/dev/limits/LimitsApp.java
  frontend/

Сборку фронтенда вызывает сам Maven: exec-maven-plugin 3.6.4 в фазе generate-resources запускает npm run build в каталоге frontend. Vite кладёт результат прямо в target/classes/static. Spring Boot по умолчанию раздаёт статические файлы из каталога /static на classpath, а index.html оттуда становится приветственной страницей. Одна команда:

Артефакт весит 20 МБ, и фронтенд лежит внутри jar рядом с классами. Выкатывается он тем же конвейером, тем же образом Docker и с той же версией, что и бэкенд. Страница и API отвечают с одного origin, поэтому CORS не нужен вовсе (сравните с главой 59, раздел 3.1). В режиме разработки фронтенд запускают через npm run dev: Vite отдаёт страницу с горячей перезагрузкой и перенаправляет /api на Spring Boot, так что origin и там остаётся один. В CI вместо npm install ставят npm ci: он ставит ровно то, что записано в package-lock.json.17

Глубокие ссылки. Первый дефект такой схемы проявляется, когда пользователь обновляет страницу не на главной. Клиентский маршрутизатор показывает экран /payments/42 без запроса к серверу. Но при обновлении страницы браузер запрашивает /payments/42 у Spring Boot, а такого файла и контроллера нет:

/              → 200 text/html
/payments/42   → 404

Нужно переадресовать на index.html все пути, которые не относятся к API и не указывают на файл. Популярный рецепт из ответов на форумах, шаблон /**/{path:[^\\.]*}, в Spring Framework 7 не запускается. Приложение упало при старте с сообщением Invalid mapping pattern detected: ... {*...} or ** pattern elements should be placed at the start or end of the pattern: парсер PathPatternParser, который Spring MVC использует по умолчанию, не разрешает ** в середине шаблона. Рабочий вариант:

Java
@Controller
static class SpaForward {
    @GetMapping({"/{first:(?!api$|assets$)[^.]*}", "/{first:(?!api$|assets$)[^.]*}/{*rest}"})
    String forward() { return "forward:/index.html"; }
}

Проверка после пересборки:

/                        → 200 text/html
/payments/42             → 200 text/html
/payments/42/receipt     → 200 text/html
/api/clients/1/limit     → 200 application/json
/api/nope                → 404 application/json
/assets/index-D6rOdBHG.js → 200 text/javascript
/assets/nope.js          → 404 application/json

Исключение api важно: без него опечатка в адресе API вернула бы клиенту HTML страницы со статусом 200, и r.json() упал бы с непонятной ошибкой разбора. Исключение assets нужно, чтобы отсутствующий файл давал честный 404, а не страницу.

Где фронтенд пишется на Java. Фулстек одним модулем существует и без JavaScript в проекте:

  • Vaadin Flow. Интерфейс пишется целиком на Java: компоненты, маршруты, привязка форм к бинам, состояние живёт на сервере в сессии. Документация формулирует это как «Build web applications with only Java». Актуальная ветка документации на момент проверки — Vaadin 25. Сильная сторона Flow — внутренние системы с формами и таблицами, которые пишет команда без фронтенд-разработчиков. Цена: память под сессию каждого пользователя и сетевой обмен на каждое действие.
  • Hilla (тоже от Vaadin). Описана как фулстек-фреймворк, который соединяет бэкенд на Spring Boot и фронтенд на React. Java-класс с аннотацией @BrowserCallable становится сервисом, вызываемым из браузера. Плагин Vaadin для Maven при сборке генерирует для него модуль TypeScript с типизированными функциями и интерфейсами для DTO в src/main/frontend/generated. Это та же цепочка контракта, что в G6, только без OpenAPI посередине: источник истины — Java-код. Методы унаследованных классов наружу не попадают, если класс не помечен @EndpointExposed. Так защищаются от случайной публикации.
  • Серверный HTML. Thymeleaf или JTE, плюс htmx для частичных обновлений. Самый короткий путь для простых экранов, и о нём стоит помнить, прежде чем тянуть SPA.

Vaadin и Hilla в этом приложении не запускались: описание сверено по документации Vaadin 25, ⚠️ поведение сборки не проверено.18

Фулстек на JavaScript (по Бюглю). Тот же замысел «один репозиторий», только без Java, разобран в «Modern Full-Stack React Projects». Мотивацию автор формулирует так, как её слышат на собеседованиях: компании сокращают разрыв между фронтендом и бэкендом, и им нужен «backend for frontend», который собирает данные из разных систем и готовит их для экрана (с. xvii). Проект у него — корень с Vite и вложенный backend/ со своим package.json и общими хуками в корне (с. 93–94). Это одна кодовая база, но две сборки и два образа Docker. В конце книги автор переходит на Next.js с серверными компонентами и называет три способа работы с данными (с. 402). HTTP API нужен, когда бэкенд пишет другая команда или его потребляют другие сервисы. Слой доступа к данным подходит для нового проекта на RSC. Запросы к базе прямо в компоненте годятся только для прототипа. Первый вариант — ровно наш случай с Java-бэкендом, и автор сам оставляет его крупным организациям (с. 400). Полезен и его критерий выбора между SSR и одним агрегирующим запросом (с. 191). SSR выгоден, когда данные одинаковы для всех и меняются редко. Для персональных и часто меняющихся данных лучше один маршрут BFF или GraphQL, который отдаёт экрану всё за один запрос.30

🎲 Редкий случай. После выката у части пользователей белый экран. Пользователь открыл приложение до выката, и вкладка хранит старый index.html со ссылкой на index-D6rOdBHG.js. Новый jar содержит только index-<новый хеш>.js. Первый же переход на ленивый модуль просит старый файл и получает 404, а с переадресацией без исключения assets — HTML вместо JavaScript. В одном модуле это проявляется чаще, чем с CDN: старые файлы исчезают ровно в момент выката. Если нужна мягкая смена версий, старые файлы держат в общем хранилище один-два релиза.

❓ Спрашивают на интервью. Как вы понимаете фулстек-разработку? Одна фича — один модуль. Схема API и бэкенд, клиент с типами, сгенерированными из контракта, и тесты обеих частей живут в одном репозитории и собираются одной командой в один артефакт. Например, Spring Boot jar со встроенной сборкой Vite, где страница и API работают на одном origin, без CORS, а сессия держится в куке на BFF. Если команде не нужен React, есть Vaadin Flow, где интерфейс целиком на Java, или Hilla, где React-клиент получает типы прямо из Java-сервисов.17

G9. Где рендерится страница: CSR, SSR, SSG, серверные компоненты

Вопрос «где выполняется React» задают почти на каждом собеседовании, потому что от ответа зависит архитектура бэкенда. Вариантов четыре, и они комбинируются. Ниже каждый в одной фразе, с ценой и с тем, что он меняет для сервера, затем замечание о гидратации, где чаще всего ломается.

Режим Где строится HTML Что получает браузер Цена
CSR, клиентский рендеринг (стенд G8) В браузере Пустой index.html и бандл Первый экран ждёт загрузки и выполнения JS (224 КБ в стенде), плохо для SEO
SSR, серверный рендеринг На сервере Node на каждый запрос Готовый HTML, затем гидратация Нужен сервер Node, нагрузка на каждый запрос
SSG, статическая генерация При сборке Готовые HTML-файлы с CDN Только для данных, которые не меняются между сборками
RSC, серверные компоненты Заранее, отдельно от клиента: при сборке или на сервере на запрос Результат рендера и бандл только для клиентских компонентов Сложность фреймворка, отдельный класс уязвимостей (G7)

Серверные компоненты — самая новая и самая путаная часть. По документации это компоненты, которые рендерятся заранее, до сборки бандла, в среде, отдельной от клиента и от SSR-сервера. Они могут читать базу или файлы прямо в теле компонента (async function Note({id}) { const note = await db.notes.get(id); ... }). Их код и библиотеки в бандл не попадают. Интерактивность добавляют клиентскими компонентами, помеченными директивой 'use client'. Частая ошибка на собеседовании — сказать, что серверный компонент помечается 'use server'. Директивы для серверных компонентов нет вообще, а 'use server' помечает серверные функции, которые клиент вызывает по сети. Для Java-бэкенд-разработчика RSC выглядят как старый добрый серверный шаблонизатор, который научился вставлять интерактивные островки. Но держать при этом слой Node.js между браузером и Spring Boot придётся постоянно.19

Гидратация — это когда React на клиенте «оживляет» HTML, присланный сервером, и вешает обработчики. Если клиентский рендер не совпал с серверным, React перерисовывает дерево и пишет в консоль Hydration failed because the server rendered HTML didn't match the client. Типовые причины из самой документации:

  • ветвление typeof window !== 'undefined';
  • Date.now() и Math.random();
  • форматирование даты в локали пользователя, которая не совпала с серверной;
  • внешние изменяемые данные без снимка в HTML;
  • неверная вложенность тегов.

Третья причина хорошо знакома финтеху. Сервер в UTC и клиент в Москве показывают разное время операции, если время форматируется при рендере. Поэтому бэкенд отдаёт время в ISO 8601 со смещением, а форматирование в часовом поясе пользователя делают только на клиенте. В React 19.3 для этого есть use(browser()): компонент пропускает серверный рендер и показывает запасной вариант из Suspense.1

SSR глазами бэкенд-разработчика (по Кумару). В «Fluent React» серверный рендеринг разобран как серверный код, и два места оттуда полезны Java-разработчику напрямую. Первое — цена синхронного renderToString. Он блокирует цикл событий Node: пока сервер строит строку для одного клиента, тридцать других ждут. Поэтому в проде берут потоковые renderToPipeableStream (потоки Node) или renderToReadableStream (Web Streams). Сначала уходит «оболочка» (shell) с запасными вариантами Suspense, а данные дописываются в тот же ответ по мере готовности. Кумар показывает, как это выглядит в HTML: скрытый <div hidden id="S:0"> с готовым фрагментом, шаблон-заглушка <template id="B:0"> и маленькая встроенная функция $RC, которая переставляет фрагмент на место заглушки. Это работает даже без клиентского React. Для бэкенд-разработчика это знакомая потоковая отдача ответа с обратным давлением (backpressure и событие drain), а не магия. Второе — пример утечки данных между пользователями. Переменная let cachedUserData = null на уровне модуля сервера кэширует ответ /user/:userId для всех запросов, и второй пользователь получает данные первого. Кумар использует его как довод «не пишите свой SSR, берите фреймворк». Бэкенд-разработчик узнает классическую ошибку синглтона с состоянием в Spring-бине: в Node-слое фреймворка состояние модуля тоже общее для всех запросов, и кэш должен быть по ключу пользователя или вовсе вне процесса.23

Свой SSR и кэш Next.js (по Бюглю). У Бюгля свой серверный рендеринг на Express и Vite строится шаг за шагом, и цифры наглядные. Список постов при имитации Slow 3G грузился около 9 секунд, потому что запросы шли каскадом: HTML, затем JavaScript, затем список, затем имена авторов по одному (с. 188–190). SSR с предзагрузкой данных сократил FCP и LCP примерно вдвое (с. 209). Но в его сервере видно и то, что фреймворк обычно прячет. Шаблон читается синхронным fs.readFileSync на каждый запрос, хотя во второй главе автор сам предупреждает не блокировать цикл событий (с. 26, 194, 209). Имена авторов подгружаются циклом с await, то есть последовательно. Любой URL отдаётся с кодом 200, даже несуществующий, а для поисковика это «мягкий 404» (с. 211). В Next.js 14 автор показывает обратную сторону кэша. Маршрут GET /api/v1/posts в сборке для прода отдавал время момента сборки, даже после перезапуска сервера (с. 428). А веб-хук для сброса кэша объявлен как GET без секрета (с. 434–435), то есть сбросить кэш может любой. ⚠️ В Next.js 15 умолчания кэширования fetch и GET-обработчиков изменились, и по документации это не перепроверялось.30

🎲 Редкий случай. «Двойной рендер» на стенде с серверным рендерингом стал тройным. В React 19.3 StrictMode прогоняет эффекты дважды и при гидратации, как уже делал при клиентском рендере (изменение #35961 в журнале 19.3). Команда, которая раньше видела на стенде SSR по одному запросу из эффекта, после обновления увидела два и решила, что виновато обновление. На деле проявилась та же забытая очистка, что в G3, просто в новом месте.1

❓ Спрашивают на интервью. Чем SSR отличается от серверных компонентов? SSR превращает в HTML всё дерево, включая клиентские компоненты, а затем браузер гидратирует его и загружает весь код. Серверные компоненты рендерятся отдельно, до бандла. Их код в браузер не попадает вовсе, они могут читать данные прямо в теле и передают результат клиентским компонентам. Эти механизмы совмещаются: результат RSC обычно ещё и рендерится через SSR в HTML. Серверного компонента директивой не помечают, 'use server' относится к серверным функциям.19

G10. Сборка, пакеты и цепочка поставки

Инструменты фронтенда бэкенд-разработчику проще всего понять через соответствие с Maven. Отличия при этом важнее сходств, и стенд это показал: за одну установку пакетов автор встретил три разных дефекта инструментов. Ниже соответствия, затем находки установки, а под конец то, что отсюда следует для безопасности цепочки поставки.

Находки установки на стенде:

  1. npm 10.9.0 упал внутри собственного кода с Cannot read properties of null (reading 'edgesOut') в #loadPeerSet. Причиной было разрешение необязательных peer-зависимостей Vitest. Обошёл флагом --legacy-peer-deps, который отключает проверку peer-зависимостей, а вместе с ней и защиту от несовместимых сочетаний. Цена этого видна в G6: генератор типов встал рядом с несовместимым TypeScript 7.
  2. jsdom 27 не запустился на Node 22.11: require() of ES Module ... not supported (ERR_REQUIRE_ESM). Новые версии пакетов рассчитывают на Node 22.12 и выше, где require() ES-модулей включён. jsdom 26 заработал. Версию Node фиксируют так же, как JDK: полем engines в package.json, файлом .nvmrc или образом сборки.
  3. Две версии компилятора TypeScript (7.0.2 и 5.9.3) несовместимы для инструментов, и это видно только при запуске (G6).
  4. Сборка Vite не проверяет типы. В main.tsx добавлена строка const limitKop: number = "500000.10". vite build собрал бандл за 0,8 с без единого предупреждения, а tsc --noEmit на том же проекте выдал TS2322: Type 'string' is not assignable to type 'number'. Vite стирает типы и не проверяет их. Вандеркам называет такое разделение правильным: быструю сборку оставляют без проверки, а tsc обязательно запускают в CI (Item 78, с. 336–337; в его замере ts-node --transpileOnly укладывается в 0,12 с против 1,6 с с проверкой). Поэтому в package.json стенда есть отдельный скрипт typecheck, и в конвейере его ставят раньше сборки. В фулстеке одним модулем (G8) mvn package должен запускать и tsc --noEmit, иначе jar с ошибкой типов уйдёт в прод.
  5. Тот же прогон нашёл неточную модель окружения. tsc выдал ещё три ошибки TS2339: Property 'env' does not exist on type 'ImportMeta' на import.meta.env. Стенд не подключал типы vite/client, и компилятор не знал, что Vite добавляет import.meta.env. Вандеркам посвящает этому отдельный пункт: TypeScript проверяет код настолько хорошо, насколько точно описано окружение, то есть lib, глобальные переменные страницы, импорт картинок и CSS, версия @types/node (Item 76, с. 329–332). Лечится файлом vite-env.d.ts со строкой /// <reference types="vite/client" />.

Что Node выполнит без сборки (опыт L-6). Голдберг пишет, что код TypeScript перед запуском в Node нужно скомпилировать в JavaScript (гл. 1, с. 14). Для Node 22.11 это уже не так: с флагом --experimental-strip-types файл .ts с аннотациями выполнился, Node лишь предупредил ExperimentalWarning. Флаг вырезает типы и ничего не преобразует, поэтому файл с enum и параметрами-свойствами конструктора упал с ERR_INVALID_TYPESCRIPT_SYNTAX: «TypeScript enum is not supported in strip-only mode» и «TypeScript parameter property is not supported in strip-only mode». С флагом --experimental-transform-types тот же файл выполнился. Компилятор умеет заранее найти такой синтаксис: tsc --erasableSyntaxOnly (TypeScript 5.8) выдал на этом файле три ошибки TS1294. Голдберг называет enum, namespace и параметры-свойства первородным грехом TypeScript — расширениями JavaScript, которые меняют код во время выполнения, и советует их избегать (гл. 14, с. 235–237). Теперь у этого совета есть механическая проверка.

Значения по умолчанию у tsc (опыты L-8…L-10). Без tsconfig.json компилятор 5.9.3 выдал var и x !== null && x !== void 0 вместо ?? (цель ES5), exports.f и __esModule (модули CommonJS), а функцию с параметром без типа пропустил молча (strict выключен). Книга здесь противоречит сама себе: цель по умолчанию на с. 171 — ES5, на с. 208 — ES3. Верно первое, а --target es3 в версии 5.9 даёт TS5108: Option 'target=ES3' has been removed. Сильнее всего изменился tsc --init. В книге это длинный файл с комментариями ко всем опциям и целью ES2016 (с. 202, 208). Версия 5.9.3 создала короткий конфиг без комментариев: module: "nodenext", target: "esnext", strict, noUncheckedIndexedAccess, exactOptionalPropertyTypes, verbatimModuleSyntax, isolatedModules, jsx: "react-jsx", skipLibCheck и ещё несколько. Два проекта, созданные этой командой с разницей в год, проверяются по-разному. Ещё одна находка — опечатки в ключах. В листингах книги верхний ключ записан как "includes" (с. 225–226), а правильно "include". Компилятор 5.9.3 молча проигнорировал неизвестный ключ и проверил все файлы каталога, включая черновик вне src, на котором упал с TS2322. С "include" проверка прошла. Так же молча проигнорирован "composite": true, вынесенный из compilerOptions (с. 228): файл .tsbuildinfo не появился. Это поведение знакомо по Spring Boot, где опечатка в имени свойства в application.yml тоже ничего не ломает и ничего не включает.3233

Зависимости ради типов. typescript и пакеты @types/* ставят в devDependencies, потому что во время выполнения их нет. Вандеркам объясняет это облегчённым серверным образом (Item 65, с. 283–285). Флаг для такой установки сегодня другой: npm 10.9 на --production ответил npm warn config production Use --omit=dev instead. У каждой типизированной библиотеки три версии: сама библиотека, пакет @types к ней и TypeScript. Major и minor у пакета и его @types совпадают, патчи независимы. Бот обновления зависимостей, поднявший react без @types/react, даёт ошибки типов на новом API или, наоборот, пропускает вызовы, которых во время выполнения ещё нет (Item 66, с. 286–290). Это та же история, что с версией JDK и версией плагина компилятора в Maven.2627

Размер. Минимальное приложение с React 19.3 и StrictMode собралось в 224 КБ JavaScript, 69,6 КБ после gzip. Это нижняя граница для React-приложения: каждая библиотека компонентов, маршрутизатор и библиотека запросов добавляют своё. Для внутренней системы в локальной сети это несущественно, для мобильного клиента на 3G — заметно.20

🎲 Редкий случай. npm install прошёл, а сборка в CI собрала другую версию. Разработчик удалил «мешающий» package-lock.json, чтобы обойти конфликт, и добавил в коммит новый. Диапазон ^ в package.json разрешился в свежие минорные версии, вышедшие накануне, и в одной из них поменялось поведение. Каждый lock-файл в запросе на слияние — изменение зависимостей, и его проверяют на ревью так же, как поднятие версии в pom.xml (глава 55, раздел 9). Заодно это главная точка атак на цепочку поставки npm.

❓ Спрашивают на интервью. Чем npm ci отличается от npm install? npm ci ставит ровно то, что записано в package-lock.json, удаляет node_modules перед установкой и падает, если lock-файл не соответствует package.json. npm install может обновить lock-файл в пределах диапазонов. В CI и в Docker-сборке используют только npm ci, иначе сборка невоспроизводима.

Node без сборки и неочевидные края (опыты FL-19, FL-23, FL-28…FL-31). Пять мест из глав о Node проверены на 22.11.

Тип модуля. Фланаган пишет, что CommonJS-модуль не может загрузить ES-модуль через require() (гл. 16, с. 582). На Node 22.11 это ещё так: require() файла .mjs дал ERR_REQUIRE_ESM (без флага это разрешили в 22.12 — ⚠️ версию стоит сверить по журналу изменений). А вот .js-файл с import и без поля type в package.json выполнился как ES-модуль без единого предупреждения: сработало автоопределение, которого в книге нет. Узнаваемо для бэкенд-разработчика: Spring Boot точно так же молча пропускает опечатку в имени свойства в application.yml.

Переменные окружения — строки. process.env.PORT всегда строка (гл. 16, с. 580). process.env.PORT + 1 при PORT=8080 дал "80801", а process.env.FLAG = false сохранилось как строка "false", которая в условии истинна. Число берут через Number(process.env.PORT), флаг — сравнением со строкой "true".

Потоки. .pipe() не передаёт ошибку по цепочке и не закрывает источник (гл. 16, с. 593). На стенде ошибка в середине преобразующего потока обернулась неперехваченным исключением: callback не вызвался, читающий поток остался открытым. stream.pipeline ту же ошибку отдал в callback и закрыл всё. Поэтому в современном Node берут pipeline из node:stream/promises, а не pipe. Вторая ловушка — _flush у Transform из примера grep вызывает callback только при совпадении хвоста (с. 595): на несовпавшем хвосте поток не завершился, событие end не наступило.

Дескрипторы файлов. Листинг с fs.open закрывает дескриптор в блоке finally вокруг асинхронного fs.read (гл. 16, с. 606). finally выполняется до того, как чтение завершится, то есть по уже закрытому дескриптору. Из 3000 прогонов 66 упали с EBADF — плавающая ошибка, которую на одном прогоне не поймать. В асинхронном коде ресурс освобождают в обратном вызове завершения, а не в finally вокруг его запуска.

Листинг copyFile (гл. 16, с. 609–610) просто не компилируется: node --check дал SyntaxError — незакрытая обратная кавычка и лишняя ; перед .catch. После исправления на Windows он упал с ENOENT, потому что в имя файла попали двоеточия из new Date().toISOString(), а их файловая система Windows не допускает.3435

G11. Тестирование: Vitest, Testing Library, Playwright

Все опыты этого приложения — обычные тесты, и это лучший ответ на вопрос «как вы тестируете фронтенд»: так же, как бэкенд, слоями. Модульные и компонентные тесты идут без браузера, в jsdom, проверяют поведение компонента через то, что видит пользователь, и выполняются за секунды. Сквозные идут в настоящем браузере против стенда. Ниже устройство компонентного теста стенда и то, что важно бэкенд-разработчику.

Компонентный тест на Vitest с Testing Library выглядит так (из hooks.test.tsx):

TSX
render(<Rows useIndex={true} />);
fireEvent.change(screen.getByLabelText('Платёж 1'), { target: { value: 'комментарий к платежу 1' } });
fireEvent.click(screen.getByText('удалить первую'));
expect((screen.getByLabelText('Платёж 2') as HTMLInputElement).value).toBe('');

Принцип Testing Library — искать элементы так, как их ищет пользователь: по подписи, роли, тексту, а не по классам CSS и внутреннему состоянию. Такой тест переживает рефакторинг вёрстки. Vitest использует ту же конфигурацию, что Vite (плагин React подключён в vitest.config.ts), и запускает 10 тестов стенда за 8,2 секунды. Из них 7 секунд — честное ожидание повторов TanStack Query. Внешние HTTP-вызовы в компонентных тестах подменяют на уровне сети (MSW или подменённый fetch), как WireMock подменяет их в Java (глава 43, раздел 7.1).

Сколько тестов какого уровня. Лукас да Коста, мейнтейнер Chai и Sinon, в «Testing JavaScript Applications» делит тесты не по цели (функция, сервис, интерфейс), как в пирамиде Майка Кона, а по ширине охвата. Чем больше кода проходит тест, тем выше он в пирамиде, тем сильнее гарантия и тем дороже и медленнее он сам (с. 20–22). Компонентный тест React у него лежит между модульным и интеграционным, а тест одного компонента он называет модульным. При этом изолировать компонент от React ради ярлыка «unit» он прямо запрещает: логика рендера и обновления — часть того, что делает приложение рабочим (с. 261). Если выбирать один тест, да Коста советует интеграционный, и пример у него из бэкенда. Подменить knex двойником — значит написать эмулятор базы, которому самому понадобятся тесты. Тест с настоящей тестовой базой пишется быстрее и даёт гарантию сильнее (с. 102–105). То же правило работает и в Java: подменять стоит только то, что легко подменить или нельзя использовать в тесте (платный внешний сервис), а базу поднимают в Testcontainers (глава 43, раздел 6).28

Детерминизм — граница, а не украшение. Вторая мысль книги, полезная бэкенд-разработчику, — у недетерминированного теста нет ценности. Да Коста ссылается на Фаулера и разбирает три источника недетерминизма (гл. 5). Первый — общий ресурс при параллельном запуске. Jest выполняет файлы в разных процессах, и два теста, пишущих в одну таблицу, мешают друг другу. Решение — не --runInBand, а свой экземпляр ресурса на процесс по process.env.JEST_WORKER_ID (с. 163–167). Второй — время: вместо ожидания шести часов ставят поддельные часы и сдвигают их (с. 167–176). Третий — внешний API: вместо подмены функции fetch, которая повторяет поведение библиотеки, лучше nock. Он подменяет ответ сервера и роняет тест при запросе на неописанный адрес (с. 152–160). Опыт D-16 показывает, почему «просто повторить упавший тест» нельзя оставлять насовсем. Ошибка удваивала сумму корзины в половине вызовов, и из 200 одинаковых тестов с тремя повторами (jest.retryTimes(3)) прошли 189. Сам да Коста формулирует это так: нестабильные тесты ловят только постоянные ошибки (с. 443). Повторы допустимы как временная мера на дедлайн и для отдельных describe, а не для всего набора.2829

Снимок фиксирует то, что есть, а не то, что верно. Снимки (toMatchSnapshot) удобны для длинного вывода, но да Коста предупреждает: если компонент выводит неверное, неверным станет и эталон (с. 299). В его же примере это и произошло (опыт D-7). Функция отчёта считает итог как сумму цен без умножения на количество. Снимок в книге и снимок, записанный Jest 30 на стенде, совпали: «Total value: 63» при сумме строк 674. Тест зелёный, отчёт неверный. Для финтеха вывод прямой: итоговые суммы реестров и отчётов проверяют явным утверждением с числом, посчитанным независимо, а снимок оставляют для формы вывода. Тот же класс ошибок создаёт и toEqual: он игнорирует свойства со значением undefined (опыт D-1, G17).2829

Что проверять тестом, а что типом. Вандеркам формулирует разделение так: модульные тесты дают нижнюю границу корректности (код верен хотя бы на этих входах), а проверка типов — верхнюю границу некорректности (целого класса ошибок в коде нет) (Item 77, с. 332–335). Отсюда правило: не писать тесты на входы, которые не пройдут компиляцию. Исключение одно. Если функцию с опасным побочным эффектом защищает только тип, тест на «недопустимый» вход нужен. Его пример — updateUserById, которой тип { id?: never } запрещает менять id. Из JavaScript или из непроверенного JSON поле id всё равно придёт, и один пользователь перезапишет запись другого. Тест вызывает функцию с id под директивой // @ts-expect-error и ждёт отказа. Для бэкенд-разработчика это знакомая подмена полей (глава 42, раздел 7.1). На клиенте тип стирается, и граница проходит там же, где на сервере, — там, где входят данные.26

Сквозные тесты на Playwright (или Cypress) проходят сценарий в Chromium, Firefox и WebKit против развёрнутого стенда. В фулстеке одним модулем их удобно запускать против того же jar, что уходит в прод: java -jar в CI, затем Playwright. Стенд и данные под контролем одной команды, поэтому сквозные тесты реже «мигают» (глава 59, раздел 3.7). В этом приложении Playwright не запускался: ⚠️ не проверено.21

🎲 Редкий случай. Тест прошёл, а в браузере тот же код ломается. jsdom — модель DOM на JavaScript, а не браузер. В нём нет вёрстки (размеры элементов нулевые), нет настоящей сети, CORS и CSP. Тест в jsdom не поймает ни ошибку CORS из главы 59, ни блокировку скрипта политикой CSP, ни белый экран из-за 404 на ассете (G8). Поэтому хотя бы один сквозной тест «страница открылась, данные показались» запускают в настоящем браузере против собранного артефакта.

❓ Спрашивают на интервью. Как вы тестируете React-компоненты? Vitest или Jest с Testing Library в jsdom: рендерю компонент, действую как пользователь (ввод, клик), проверяю видимый результат, ищу элементы по ролям и подписям. Сеть подменяю на уровне fetch или MSW. Для критичных сценариев — Playwright против собранного приложения, для контракта — типы из OpenAPI и проверки на границе. Отдельно проверяю StrictMode и очистку эффектов, потому что их дефекты не видны в одиночном рендере.

G12. Фулстек с ИИ-ассистентом: процесс и ревью сгенерированного

Вакансии, где «бэкенд с помощью ИИ пишет полный стек», на деле спрашивают одно: сможете ли вы отличить работающий черновик от правильного кода. ИИ-ассистент пишет React быстро и уверенно, но воспроизводит самые частые ошибки из обучающих данных, а значит, из старых учебников и ответов на форумах. Ниже порядок работы, в котором ассистент полезен, затем опыт: типичный черновик и что из его дефектов находят автоматические проверки. Общая часть (рамка задачи, правила проекта, контрольные точки) разобрана в главе 78. Здесь её применение к фронтенду.

Порядок работы. Рабочая последовательность для фичи «показать лимит клиента и дать его изменить» в одном модуле:

  1. Спецификация задачи и критерии приёмки (глава 78, раздел 11.2).
  2. Изменение OpenAPI-описания. Его пишет человек или ассистент, рецензирует человек, потому что это контракт.
  3. Бэкенд: контроллер, сервис, тест контракта.
  4. Генерация типов TypeScript. Ассистента к этому не подпускают, это делает генератор.
  5. Компонент. Здесь ассистент выигрывает больше всего, но пишет против сгенерированных типов.
  6. Компонентный тест, затем сквозной.
  7. Ревью по чеклисту ниже.

Главная мысль: ассистенту дают писать код между двумя проверками, которые он не может обойти. Это компилятор с типами из контракта и тесты, записанные до кода.

Опыт: черновик «от ИИ». Файл AiDraft.tsx воспроизводит типичный ответ ассистента на запрос «покажи платежи клиента». Код компилируется и на первый взгляд работает. В нём шесть дефектов:

  1. fetch в эффекте без отмены и без проверки r.ok.
  2. Зависимости эффекта неполные: filter и token в них не указаны.
  3. Количество записей вычисляется через эффект и состояние.
  4. Ключ списка — индекс.
  5. Сумма и комментарий выводятся через dangerouslySetInnerHTML (так проще склеить строку).
  6. Токен читается из localStorage.

Компилятор не нашёл ничего: все шесть дефектов типобезопасны. Линтер хуков с правилами на основе компилятора React нашёл два: неполные зависимости и состояние в эффекте. Чеклист ревью React-кода от ИИ. Порядок — от дорогих дефектов к дешёвым:

  1. Данные и безопасность. Нет ли dangerouslySetInnerHTML, href из данных, токенов в localStorage, секретов в VITE_*. Деньги и идентификаторы — строки, ответ проверяется на r.ok.
  2. Эффекты. Нужен ли эффект вообще (производное значение, действие пользователя). Есть ли очистка и отмена. Нет ли объектов и функций в зависимостях. Не отключено ли правило exhaustive-deps комментарием.
  3. Состояние. Ключи — устойчивые идентификаторы. Компоненты объявлены на верхнем уровне. Нет дублирования состояния, которое можно вычислить.
  4. Контракт. Используются сгенерированные типы, а не написанные заново. Нет any и as на ответах сервера.
  5. Поведение при сбоях. Что видит пользователь при 4xx, 5xx, долгом ответе и отмене. Не повторяются ли мутации.
  6. Тесты. Проверяют поведение, а не реализацию. Есть сценарий с ошибкой сервера.

В правила проекта для ассистента (CLAUDE.md или аналог, глава 78, раздел 4) эти пункты записывают явно. Например: «загрузка данных только через TanStack Query с retry, настроенным в queryClient», «dangerouslySetInnerHTML запрещён», «типы API только из src/api.d.ts». Ассистент следует явному правилу гораздо надёжнее, чем угадывает принятое в проекте.

🎲 Редкий случай. Ассистент «починил» предупреждение линтера, отключив его. На просьбу убрать предупреждение exhaustive-deps ассистент добавил комментарий // eslint-disable-next-line react-hooks/exhaustive-deps. Это самый частый «ремонт» в ответах на форумах. Эффект перестал реагировать на смену фильтра: пользователь меняет статус платежей, а список прежний. Команда React пишет о том же в анонсе useEffectEvent: большинство просто отключает правило, и это ведёт к ошибкам. Запрет таких комментариев без пояснения ставят в линтер (--report-unused-disable-directives, правило на обязательное пояснение) и в чеклист ревью.11

G13. Вопросы на собеседовании с короткими ответами

Ниже вопросы, которые чаще всего задают бэкенд-разработчику на фулстек-вакансии, с ответом в две-три фразы и ссылкой на раздел, где механизм разобран подробно и проверен запуском. Ответ стоит начинать с механизма, а не с определения из документации: интервьюер проверяет понимание, а не память. Где уместно, добавляйте пример из бэкенда, потому что для бэкенд-разработчика это самый убедительный способ показать, что механизм понят.

  1. Что такое рендер в React? Вызов функции компонента, которая возвращает JSX. React сравнивает результат с прошлым и фиксирует разницу в DOM (G3).
  2. Почему setCount(count + 1) три раза подряд даёт +1? Состояние в обработчике — снимок рендера. Для последовательных обновлений нужна функция-обновитель (G3, опыт G-1).
  3. Зачем StrictMode вызывает эффекты дважды? Чтобы проявить забытую очистку. Это только режим разработки, в проде одиночный вызов (G3, опыт G-2).
  4. Когда useEffect не нужен? Для производных значений, сброса состояния при смене пропса и действий пользователя. Эффект нужен только для синхронизации с внешней системой (G4).
  5. Почему хуки нельзя вызывать в условиях? React различает их по порядку вызова (G4).
  6. Чем useMemo отличается от useCallback и memo? useMemo кэширует значение, useCallback — функцию, memo пропускает перерисовку компонента при тех же пропсах. Без стабильных пропсов memo бесполезен (G4, опыт G-6).
  7. Что делает компилятор React? Автоматически мемоизирует компоненты и хуки на этапе сборки. Ручная мемоизация остаётся для точного управления (G4).
  8. Почему контекст тормозит? Все потребители перерисовываются при смене значения по ссылке. Объект, созданный в рендере провайдера, новый каждый раз (G4, опыт G-7).
  9. Зачем key и почему не индекс? Ключ связывает элемент с записью. При индексе состояние переезжает к соседней записи (G3, опыт G-4).
  10. Что такое гонка ответов и как её избежать? Старый ответ приходит позже нового и перезаписывает экран. Лечится флагом ignore или AbortController в очистке эффекта, а лучше библиотекой запросов (G5, опыт G-3).
  11. Почему эффект может выполняться бесконечно? Объект или функция в зависимостях новые на каждом рендере, а эффект меняет состояние (G4, опыт G-5).
  12. Чем серверное состояние отличается от клиентского? Серверное — копия чужих данных, оно устаревает, его надо кэшировать, дедуплицировать и сбрасывать (G5).
  13. Сколько запросов сделает TanStack Query на ответ 500 по умолчанию? Четыре: первый и три повтора с экспоненциальной задержкой, около 7 секунд до ошибки (G5, опыт G-8).
  14. Чем TypeScript отличается от Java по типам? Структурная типизация, стирание всех типов, объединения и сужение, any и unknown (G2).
  15. Почему as опасен на ответе сервера? Он ничего не проверяет во время выполнения. На границе нужна проверка схемой (G6, опыт G-10).
  16. Как передавать деньги и 64-битные id в JSON для браузера? Строкой. Число теряет масштаб BigDecimal и точность выше 2^53 (G6, опыт со Spring Boot).
  17. Как синхронизировать контракт фронта и бэка? OpenAPI в репозитории, генерация типов при сборке, проверка на границе (G6).
  18. Как защититься от XSS? JSX экранирует строки. Опасен dangerouslySetInnerHTML, нужны санитайзер и CSP с Trusted Types (G7, опыт G-9).
  19. Где хранить токен? Не в localStorage. Лучше BFF с сессионной кукой HttpOnly, Secure, SameSite и защитой от CSRF (G7).
  20. Почему ключ API нельзя класть в VITE_API_KEY? Переменные VITE_* вшиваются в бандл открытым текстом (G7, опыт).
  21. Что такое CSR, SSR, SSG и RSC? Где и когда строится HTML; серверные компоненты рендерятся отдельно, и их код не попадает в браузер (G9).
  22. Что такое гидратация и почему она ломается? Клиент оживляет серверный HTML. Расхождение из-за времени, случайных чисел, локали и неверной вложенности тегов (G9).
  23. Как собрать фронт и бэк в один артефакт? Maven вызывает npm run build, Vite кладёт файлы в static, Spring Boot их раздаёт; глубокие ссылки переадресуются на index.html (G8).
  24. Что такое Vaadin и Hilla? Flow — интерфейс целиком на Java. Hilla — React с типами, сгенерированными из Java-сервисов (G8).
  25. Как вы проверяете React-код от ИИ? Типы из контракта, тесты до кода, линтер хуков, чеклист: безопасность, эффекты, ключи, ошибки (G12).
  26. Что такое цикл событий? Один поток. Синхронный код, затем микрозадачи (промисы), затем макрозадачи (таймеры, события). Долгий расчёт блокирует страницу (G2, опыт 4).

G14. Что сказать про себя, если вы бэкенд-разработчик

Короткую версию ответа удобно проговорить за минуту, и она должна быть честной: интервьюер легко отличает пройденный вечером учебник от опыта, а честная граница знаний вызывает больше доверия, чем широкие обещания. Заготовка ниже рассчитана на Java-разработчика, который писал интерфейсы на Swing, JavaFX или Vaadin и готов писать React вместе с ИИ-ассистентом. Слоты в квадратных скобках заполняете своим опытом.

«Основной опыт у меня в бэкенде на Java и Kotlin. С интерфейсами работал на [Swing, JavaFX, Vaadin — где и что], поэтому событийная модель, однопоточный UI и состояние экрана мне знакомы. В React я понимаю механику: рендер как функция от состояния, снимок состояния, эффекты и их очистка, ключи, мемоизация. Знаю, где он бьёт по бэкенду: гонки ответов, повторы библиотеки запросов, деньги и 64-битные id в JSON. Фулстек понимаю как один модуль: контракт в OpenAPI, типы TypeScript из него, клиент собирается Maven в тот же jar и работает с API на одном origin. С ИИ-ассистентом пишу компоненты между двумя проверками, которые он не может обойти: компилятором с типами из контракта и тестами. И ревьюю результат по чеклисту, потому что сгенерированный код компилируется, даже когда в нём XSS и гонка».

Чего не говорить:

  • Не называйте себя фронтенд-разработчиком и не обещайте вёрстку под пиксель.
  • Не говорите «React — это просто шаблонизатор»: это модель состояния и обновлений, и интервьюер это знает.
  • Не обещайте, что ИИ сделает фронтенд за вас: правильный ответ про проверку, а не про скорость генерации.
  • Не создавайте проект через create-react-app в рассказе: он объявлен устаревшим в феврале 2025 года (G1).

Файлы стенда лежат в каталогах tmp/react-lab (тесты hooks.test.tsx, fullstack.test.tsx и kumar.test.tsx, contract-errors.ts, AiDraft.tsx, eventloop.mjs, api/limits.yaml) и tmp/fullstack-mono (Spring Boot и Vite в одном pom) рабочей копии автора; в репозиторий они не входят.

G16. Проверка книги запуском: «Effective TypeScript»

«Effective TypeScript» Дэна Вандеркама (2-е издание, O'Reilly, май 2024) устроена по образцу «Effective Java» Блоха. В ней 83 пункта, и каждый — правило с разбором и итоговым списком.
