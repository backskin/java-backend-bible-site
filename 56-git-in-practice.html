56. Git на практике

Часть XI. Процесс инструменты и команда28 510 слов≈ 2 ч 40 мин чтения
Зачем это знать

Git — единственный инструмент, которым backend-разработчик пользуется каждый день без исключений, и единственный, где ошибка стоит не «переписать код», а «потерять две недели работы команды». Большинство инженеров с семью годами опыта знают десять команд и боятся остальных: rebase для них — лотерея, reflog — что-то из мемов, а reset --hard — кнопка «сделать страшно». Это не про удобство: разъехавшаяся история релизной ветки перед регуляторной отчётностью, revert merge-коммита, после которого фича «потерялась», секрет в истории, который «удалили», но он остался — это реальные инциденты в финтехе, стоящие недель. На интервью Git спрашивают реже, чем Java, но спрашивают точечно и зло: «чем reset отличается от revert», «что физически произойдёт при rebase», «почему --force-with-lease иногда не спасает». Все эти ответы выводятся из одной вещи — модели данных, и именно с неё начинается глава.

1. Модель данных Git

Git не является системой контроля версий в том смысле, в котором ею были CVS и Subversion. Это контент-адресуемое key-value хранилище с тонкой прослойкой команд сверху. Всё, что вас пугает в Git, перестаёт пугать ровно в тот момент, когда вы перестаёте думать командами и начинаете думать объектами и ссылками. Команда — это всегда «создать объекты» и/или «подвинуть ссылку». Больше Git ничего не умеет.

1.1 Четыре типа объектов Git

В базе .git/objects живут объекты ровно четырёх типов:

Тип Что хранит На что ссылается
blob байты содержимого файла ни на что
tree список записей «режим + тип + хеш + имя» на blob'ы и другие tree
commit снимок (корневой tree), родители, автор, коммиттер, сообщение на один tree и 0..N родителей
tag аннотированный тег: объект, тип, имя, тегер, сообщение, опционально подпись на любой объект

Имя объекта — это SHA-1 (или SHA-256, см. 1.2) от строки "<тип> <длина>\0<содержимое>". Отсюда два следствия, которые надо понимать буквально:

  1. Одинаковое содержимое = один объект. Если в репозитории тысяча файлов package-info.java с одним и тем же текстом, в базе лежит один blob. Если вы переименовали файл, не меняя содержимого, новый blob не создаётся вообще — меняется только tree.
  2. Объекты неизменяемы. Нельзя «поправить коммит». Можно только создать новый объект и передвинуть на него ссылку. Всё, что выглядит как редактирование истории (commit --amend, rebase, filter-repo), — это создание новых объектов плюс движение ссылок. Старые объекты остаются лежать в базе, пока их не соберёт gc. Именно на этом стоит всё восстановление после аварий.

Посмотрим своими глазами. Заводим репозиторий банковского сервиса:

git init -q -b main pay-service && cd pay-service
git config user.name "Ivan Petrov"
git config user.email "i.petrov@bank.example"
mkdir -p src/main/java/ru/bank/pay
printf 'rootProject.name = "pay"\n' > settings.gradle
printf 'package ru.bank.pay;\n\npublic class Payment {\n    private long amount;\n}\n' \
  > src/main/java/ru/bank/pay/Payment.java
git add .
git commit -m "feat(pay): скелет платежа"

Теперь вскрываем коммит. git cat-file -p печатает объект в человекочитаемом виде, -t — тип, -s — размер:

$ git rev-parse HEAD
d75fb0bacf9e7063dc1f9a39abfd66a6f3c60e8c

$ git cat-file -t HEAD
commit

$ git cat-file -p HEAD
tree b511b3509efaf0a7d0b3532829f11fd268cc2dfd
author Ivan Petrov <i.petrov@bank.example> 1772435700 +0300
committer Ivan Petrov <i.petrov@bank.example> 1772435700 +0300

feat(pay): скелет платежа

Это весь коммит целиком — текстовый объект из нескольких строк. Никакого «diff» внутри нет и никогда не было.

🔧 Под капотом. Формат коммита: заголовочные строки tree, ноль или больше строк parent, author, committer, опционально gpgsig/gpgsig-sha256, encoding, mergetag; затем пустая строка и сообщение. Время автора и коммиттера хранится как unix timestamp плюс текстовое смещение (1772435700 +0300). Часовой пояс как таковой (Europe/Moscow) не сохраняется — только смещение на момент коммита. Поэтому сортировка по дате в Git всегда сортировка по UTC-моменту, а отображение — по сохранённому смещению. Именно это ломает наивные скрипты, которые парсят дату регулярными выражениями.

1.2 Автор и коммиттер

Строки author и committer — самая недооценённая часть объекта. author — кто написал изменение, committer — кто в последний раз создал этот объект коммита. При обычном git commit они совпадают. Они расходятся в трёх ситуациях:

  • rebase — вы пересоздаёте чужие коммиты, автор остаётся прежним, коммиттером становитесь вы;
  • cherry-pick — то же самое;
  • применение патча (git am, git apply + commit) — автор берётся из письма/патча.

Следствия для практики:

# «сегодняшние» коммиты по дате коммиттера, но авторская дата — двухнедельной давности
git log --format='%h | a:%an %ad | c:%cn %cd | %s' --date=short
  • git log --since=... по умолчанию фильтрует по коммиттерской дате, а --pretty=%ad печатает авторскую. Классический источник «почему в отчёте не сходится».
  • Плагины, считающие вклад разработчиков по %an, после rebase-ориентированного процесса покажут правильную картину, а по %cn — покажут того, кто последним делал rebase релизной ветки.
  • В банке при разборе инцидента важен именно коммиттер: он отвечает на вопрос «кто и когда физически положил это в ветку».

git shortlog -sne группирует по автору, git shortlog -sne --committer — по коммиттеру (⚠️ не проверено на 2.55; в старых версиях группировка по коммиттеру делается через --format).

1.3 Объекты tree и blob

Корневой tree — это каталог верхнего уровня:

$ git cat-file -p HEAD^{tree}
100644 blob 922de2ea765a1a7c7941329c0372b42aa9967c5a    settings.gradle
040000 tree 2b428c34a2577eacfa1f54b4e91d7c764cbcc621    src

Записи tree хранят режим (100644 обычный файл, 100755 исполняемый, 120000 симлинк, 040000 подкаталог, 160000 gitlink — коммит подмодуля), тип, хеш и имя. Прав доступа в привычном POSIX-смысле Git не хранит: только бит «исполняемый». Владельца, группу, mtime, ACL — нет. Поэтому «после клонирования скрипт не запускается» — это про 100644 вместо 100755, лечится git update-index --chmod=+x path.

Вложенные деревья разворачиваются рекурсивно:

$ git ls-tree -r HEAD
100644 blob 922de2e...  settings.gradle
100644 blob e676251...  src/main/java/ru/bank/pay/Payment.java

Имя blob'а можно вычислить, не обращаясь к репозиторию вообще:

$ git hash-object -t blob --stdin < settings.gradle
922de2ea765a1a7c7941329c0372b42aa9967c5a

Совпадает с записью в tree. Это и есть контент-адресация: хеш — функция только от содержимого, никакой связи с путём, датой и историей.

⚠️ Осторожно. Пустые каталоги Git не хранит — просто потому, что нет объекта, который бы их описывал. Запись в tree обязана ссылаться на blob или tree, а пустого каталога в этой модели не существует. Отсюда вековая практика с .gitkeep. Разработчики регулярно теряют на этом полчаса, пытаясь понять, почему после клонирования нет logs/ и приложение падает на старте. Правильное лечение — создавать каталог в коде или в Dockerfile, а не хранить его в Git.

1.4 Снимки и дельты в хранилище Git

Логическая модель Git — снимки. Каждый коммит указывает на полный tree, описывающий всё дерево проекта целиком в этот момент. Никаких «изменений относительно предыдущего» в модели нет: diff вычисляется на лету при запросе, сравнением двух деревьев.

Это выглядит расточительно, пока не вспомнить про дедупликацию по содержимому: файл, который не менялся между тысячей коммитов, физически хранится один раз, и тысяча tree'в просто ссылается на один blob. Дельты не нужны для неизменённых файлов вообще.

Физически же, для изменённых версий одного файла, Git всё-таки использует дельты — но не в модели, а в формате хранения. Свободные (loose) объекты — по одному файлу на объект, zlib-сжатые. Когда их становится много, Git упаковывает их в packfile (.pack + индекс .idx), где похожие объекты хранятся как дельты друг к другу.

$ git count-objects -v
count: 10          # loose-объектов
size: 0            # их размер (в KiB)
in-pack: 0         # объектов в пакетах
packs: 0
size-pack: 0
prune-packable: 0  # loose-объекты, которые уже есть в пакете
garbage: 0
size-garbage: 0

$ git count-objects -vH   # то же с человекочитаемыми размерами
count: 10
size: 893 bytes

Ключевые моменты про packfile:

  • Дельта-цепочки строятся по эвристике «похожести», а не по истории. Git сортирует объекты по типу, пути и размеру, и дельтит объект относительно похожего. Дельта может указывать «назад по времени» — новая версия файла может быть базой, а старая — дельтой к ней. Это оптимизирует чтение свежего состояния.
  • Глубина цепочки ограничена (pack.depth, по умолчанию 50), окно поиска базы — pack.window (по умолчанию 10).
  • git gc запускает git repack, перепаковывает loose-объекты и старые пакеты, чистит недостижимое старше gc.pruneExpire (по умолчанию 2 недели, Documentation/config/gc.adoc, проверено 2026-09-22).
  • git gc --auto вызывается неявно после многих операций и срабатывает, когда loose-объектов «примерно больше» gc.auto (по умолчанию 6700) или пакетов больше gc.autoPackLimit (50).

📊 Цифры. Значения по умолчанию gc (Git 2.55): gc.auto=6700, gc.autoPackLimit=50, gc.pruneExpire=2.weeks.ago, gc.reflogExpire=90 days, gc.reflogExpireUnreachable=30 days, gc.bigPackThreshold=0 (выключено). Источник — Documentation/config/gc.adoc, проверено 2026-09-22.

Практическое следствие: недостижимый объект живёт минимум две недели, а запись в reflog — 90 дней (30 для недостижимых). Это ваш запас времени на восстановление после любой аварии. Не «Git потерял коммит», а «у вас есть 14–90 дней, чтобы его найти».

1.5 SHA-1, SHA-256 и миграция хеш-функции

Исторически имена объектов — SHA-1. SHA-1 криптографически сломан: коллизия найдена (SHAttered, 2017), а в 2020 году показана chosen-prefix коллизия. Для Git это означает теоретическую возможность подменить объект другим с тем же именем.

Что сделано в самом Git:

  1. Детектор коллизий. Git собирается с sha1collisiondetection и отказывается работать с объектами, в которых обнаружены признаки известных атак на SHA-1. Это не защита от будущих атак, но закрывает SHAttered-класс.
  2. Полноценная поддержка SHA-256 как формата объектов. Репозиторий создаётся флагом --object-format=sha256:
$ git init --object-format=sha256 -b main repo256 && cd repo256
$ echo hi > f.txt && git add f.txt && git commit -q -m t
$ git rev-parse HEAD
2bab7078693ed76aaefe4bf26454877c1f225d2b24ab524ab633c0ec7d2d6b98
$ cat .git/config
[extensions]
    objectformat = sha256
[core]
    repositoryformatversion = 1
    ...

Обратите внимание на repositoryformatversion = 1 — это механизм расширений: Git старой версии, увидев версию формата 1 и незнакомое расширение, откажется работать вместо того, чтобы молча испортить репозиторий.

Почему массовой миграции не произошло и в 2026 году:

  • Совместимость по сети не готова. Документ hash-function-transition прямо говорит: «Until Git protocol gains SHA-256 support, using SHA-256 based storage on public-facing Git servers is strongly discouraged» (проверено 2026-09-22). Для реального сосуществования нужен режим compatObjectFormat, при котором репозиторий держит двойное отображение SHA-1↔SHA-256 и умеет говорить по протоколу в обоих. Эта часть остаётся незавершённой.
  • Незакрытые сценарии по тому же документу: shallow-клоны в SHA-256-репозиторий, невыкачанные подмодули, alternates из SHA-1-репозитория, перенос notes.
  • Экосистема. GitHub/GitLab/Bitbucket, CI-исполнители, инструменты сканирования, Gerrit, зависимости в сборке, ссылающиеся на коммиты по SHA-1 — всё это упирается в 40-символьные идентификаторы. Миграция монорепозитория означает переписывание всех хешей, то есть новый репозиторий: все ссылки в задачах, релиз-нотах, логах аудита и конфигурации становятся мёртвыми.
  • Ценность/риск. Практическая атака требует контроля над содержимым, попадающим в репозиторий, и проходит мимо детектора коллизий с трудом. При этом цена миграции — разрыв всей трассируемости.

💡 На интервью. «SHA-256 в Git есть как формат объектов с 2.29 и работает локально; репозиторий помечается extensions.objectFormat=sha256 и repositoryformatversion=1. Чего нет — взаимодействия по сети с SHA-1-репозиториями: режим compatObjectFormat не доведён, и документация прямо не рекомендует SHA-256 на публичных серверах. Поэтому индустрия живёт на SHA-1 с детектором коллизий: миграция означает переписывание всех имён объектов и обрыв всех внешних ссылок на коммиты.»

1.6 Ссылки: refs, HEAD и packed-refs

Ссылка (ref) — это файл в .git/refs/, содержащий 40 (или 64) шестнадцатеричных символов. Всё.

$ cat .git/refs/heads/main
d75fb0bacf9e7063dc1f9a39abfd66a6f3c60e8c

Пространства имён:

Путь Что это Кто двигает
refs/heads/<name> локальная ветка ваши коммиты, merge, rebase, reset
refs/tags/<name> тег только вы явно; сервер обычно запрещает перезапись
refs/remotes/<remote>/<name> remote-tracking ветка — снимок состояния сервера на момент последнего fetch только fetch/push, вручную не трогают
refs/stash верхушка стека stash git stash
refs/notes/* git notes git notes
refs/pull/*, refs/merge-requests/* серверные ссылки на PR/MR (не приходят по умолчанию) хостинг

HEAD — файл с символической ссылкой:

$ cat .git/HEAD
ref: refs/heads/main
$ git symbolic-ref HEAD
refs/heads/main

После git switch --detach там лежит голый хеш:

$ git switch --detach HEAD && cat .git/HEAD
d75fb0bacf9e7063dc1f9a39abfd66a6f3c60e8c

Это и есть detached HEAD: вы стоите на коммите, а не на ветке. Коммиты в этом состоянии создаются нормально, но на них не указывает ни одна ветка — стоит переключиться, и они станут недостижимыми (найти можно через reflog, см. раздел 5). Detached HEAD — не ошибка, это штатный режим: в нём работают bisect, rebase, CI-исполнители (клонируют и делают checkout по SHA).

🔧 Под капотом. packed-refs. Когда ссылок становятся тысячи (типично для репозитория с многолетней историей релизных тегов), Git упаковывает их в один файл .git/packed-refs — текстовый список «хеш пробел имя». Отдельные файлы в refs/ при этом удаляются. Поэтому cat .git/refs/heads/release/2026.03 может вернуть «нет такого файла», хотя ветка существует. Никогда не читайте ссылки из файловой системы в скриптах — используйте git rev-parse и git for-each-ref, они знают про оба хранилища. В свежих версиях Git есть и альтернативный бэкенд ссылок — reftable (git init --ref-format=reftable), бинарный формат, рассчитанный на репозитории с сотнями тысяч ссылок; в банковских монорепо он уже осмыслен, но по умолчанию не включён.

git rev-parse — универсальный разрешитель имён. Он понимает всё, что вы пишете в командах:

git rev-parse HEAD               # хеш текущего коммита
git rev-parse HEAD^{tree}        # хеш корневого дерева
git rev-parse HEAD:pom.xml       # хеш blob'а конкретного файла
git rev-parse main@{2.days.ago}  # где была ветка два дня назад (по reflog!)
git rev-parse --abbrev-ref HEAD  # имя текущей ветки
git rev-parse --show-toplevel    # корень рабочего дерева
git rev-parse --git-dir          # путь к .git
git rev-parse --verify -q refs/heads/foo  # есть ли такая ветка (для скриптов)

Синтаксис ревизий, который обязан знать наизусть каждый:

  • HEAD~3 — три шага назад по первому родителю;
  • HEAD^2 — второй родитель (для merge-коммита — верхушка влитой ветки);
  • HEAD^ = HEAD~1 = HEAD^1;
  • main..feature — коммиты, достижимые из feature, но не из main (то, что «в ветке нового»);
  • main...feature — симметричная разность (в log), а в diff — «изменения feature относительно merge base»;
  • @{u} или @{upstream} — upstream текущей ветки, @{push} — куда она пушится.

Разница .. и ... в git diff — источник половины недоразумений на ревью. git diff main feature покажет в том числе изменения, которые попали в main после ответвления (как «удаления» в feature). git diff main...feature покажет ровно то, что сделано в ветке. Именно ... соответствует тому, что показывает GitLab/GitHub в MR/PR.

1.7 Индекс (staging area)

Индекс (он же staging area, он же cache) — это бинарный файл .git/index. Внутри — отсортированный по пути список записей: путь, режим, хеш blob'а, размер, метаданные stat (device, inode, ctime, mtime, size) для быстрой проверки «изменился ли файл», флаг stage и флаги разрешения конфликтов.

$ git ls-files --stage
100644 922de2ea765a1a7c7941329c0372b42aa9967c5a 0   settings.gradle
100644 e6762514178a9d2cd244006b53bd9995fa44a1a3 0   src/main/java/ru/bank/pay/Payment.java

Третья колонка — stage number: 0 означает «конфликта нет». Во время неразрешённого конфликта вместо одной записи появляются три: 1 — база (merge base), 2 — наша версия, 3 — их версия. Это и есть весь механизм конфликта, никакой магии:

$ git ls-files -u
100644 9ff7d02...  1    src/main/java/ru/bank/pay/Limit.java
100644 bf67cd7...  2    src/main/java/ru/bank/pay/Limit.java
100644 f341a6d...  3    src/main/java/ru/bank/pay/Limit.java

Теперь главное про git add:

git add — это не «пометить файл». Это записать blob в базу объектов и положить его хеш в индекс.

То есть содержимое файла становится неизменяемым объектом в .git/objects до коммита. Отсюда прямое практическое следствие, спасающее нервы: если вы сделали git add, а потом случайно затёрли файл, содержимое уже в базе и восстанавливается через git fsck --lost-found даже без коммита. И обратное: git add больших файлов «на попробовать» уже раздул базу, и git rm --cached её не уменьшит.

Три дерева. Вся работа Git объясняется тремя состояниями одного и того же набора путей:

HEAD            индекс (index)           рабочее дерево (worktree)
последний       что войдёт                 что вы видите
коммит          в следующий коммит         в файлах на диске
Команда HEAD Индекс Рабочее дерево
git add <f> — ← worktree —
git commit ← индекс — —
git reset --soft <c> → <c> — —
git reset [--mixed] <c> → <c> ← <c> —
git reset --hard <c> → <c> ← <c> ← <c>
git restore --staged <f> — ← HEAD —
git restore <f> — — ← индекс
git restore --source=HEAD --staged --worktree <f> — ← HEAD ← HEAD
git checkout <branch> → branch ← branch ← branch
git stash — ← HEAD ← HEAD (содержимое сохранено в объектах)

Эта таблица закрывает 90 % вопросов «а что эта команда сделает». git status — просто два diff'а: HEAD↔индекс («Changes to be committed») и индекс↔worktree («Changes not staged»).

⚠️ Осторожно. Индекс хранит stat-метаданные, и Git считает файл неизменённым, если совпали mtime и размер. При работе через сетевые/шаренные тома, в контейнерах с пробросом каталога и при переводе часов это ломается: git status показывает изменения там, где их нет, либо не показывает там, где они есть. Лечение — git update-index --refresh, в тяжёлых случаях — git status после touch файлов; для Windows-репозиториев помогает core.fscache, для macOS/Linux — core.untrackedCache и feature.manyFiles.

1.8 Пример: создание коммита низкоуровневыми командами

Чтобы модель окончательно перестала быть абстракцией, соберём коммит низкоуровневыми командами, вообще не вызывая git add/git commit:

# 1. blob
BLOB=$(printf 'hello\n' | git hash-object -w --stdin)
# 2. дерево через индекс
git update-index --add --cacheinfo 100644,$BLOB,hello.txt
TREE=$(git write-tree)
# 3. коммит
COMMIT=$(echo "ручной коммит" | git commit-tree $TREE -p HEAD)
# 4. двигаем ветку
git update-ref refs/heads/main $COMMIT

Четыре шага — и это буквально всё, что делает git commit. Любая «страшная» команда Git — композиция этих операций. Когда вы в следующий раз будете разбирать поломанный rebase, держите эту последовательность в голове: там нет ничего, кроме создания объектов и движения ссылок, а старые объекты никуда не делись.

2. Ветки и слияние

2.1 Ветка как указатель: git branch

$ git branch feature/pay-limit
$ cat .git/refs/heads/feature/pay-limit
d75fb0bacf9e7063dc1f9a39abfd66a6f3c60e8c

Один файл, 41 байт. Вот и всё создание ветки. Поэтому:

  • ветка создаётся за микросекунды независимо от размера репозитория;
  • «слишком много веток» не влияет на производительность до тысяч ссылок (а дальше лечится packed-refs/reftable);
  • удаление ветки не удаляет коммиты — оно удаляет файл-указатель; коммиты становятся недостижимыми и живут до gc;
  • ветка «отстала на 200 коммитов» — это не свойство ветки, а расстояние между двумя указателями по графу.

git switch <branch> (с 2.23) и git checkout <branch> делают одно и то же в части переключения: меняют HEAD на символическую ссылку, переписывают индекс из целевого коммита и обновляют рабочее дерево. Разделение на switch (ветки) и restore (файлы) появилось именно потому, что перегруженный checkout десятилетиями был источником катастроф: git checkout foo мог означать и «переключись на ветку foo», и «выброси мои изменения в файле foo» — в зависимости от того, что такое foo. Используйте switch/restore, а checkout оставьте для скриптов и старых инструкций.

Полезные формы:

git switch -c feature/x            # создать и перейти
git switch -c hotfix/y release/2026.03   # создать от конкретной точки
git switch -                       # вернуться на предыдущую ветку
git switch --detach v1.4.2         # встать на тег без ветки
git branch -vv                     # ветки + upstream + расхождение
git branch --merged main           # что уже влито (кандидаты на удаление)
git branch --no-merged main        # что ещё не влито
git for-each-ref --sort=-committerdate --format='%(refname:short) %(committerdate:relative) %(authorname)' refs/heads

Последняя команда — рабочий инструмент при чистке репозитория: показывает, какие ветки мертвы полгода и кем брошены.

2.2 Перемотка (fast-forward)

Если main — предок feature, то «слить» их означает просто передвинуть указатель main вперёд. Новый коммит не нужен: история уже линейна.

до:    A---B---C  (main)
                \
                 D---E  (feature)

после git merge feature (fast-forward):
       A---B---C---D---E  (main, feature)

Fast-forward невозможен, если после ответвления в main появились свои коммиты — тогда нужен merge-коммит с двумя родителями.

--no-ff заставляет создать merge-коммит даже при возможности fast-forward:

       A---B---C-----------M  (main)
                \         /
                 D---E---'  (feature)

Зачем это требуют в банках:

  1. Граница фичи видна. Merge-коммит — единственная запись в истории, говорящая «вот эта группа из семи коммитов — это задача PAY-1234». Без него коммиты растворяются в линейной истории.
  2. Откат целиком. git revert -m 1 <merge> откатывает всю фичу одной командой (с оговорками из раздела 5.4).
  3. Аудит. Merge-коммит содержит коммиттера — того, кто нажал «Merge» после апрува. Это и есть машинная запись факта «изменение прошло ревью и было принято таким-то в такое-то время». Для регуляторных требований (кто допустил код в релиз) это часто и есть доказательство.
  4. --first-parent (раздел 6.2) превращает историю релизной ветки в список фич, а не в кашу из тысяч коммитов — но это работает только если merge-коммиты есть.

Обратная сторона: история становится «лохматой», git log --graph без --first-parent нечитаем, а git bisect вынужден спускаться внутрь фич. Конфигурация на уровне репозитория:

git config merge.ff false      # всегда merge-коммит при git merge
git config pull.ff only        # но pull без слияния — только fast-forward

2.3 Трёхстороннее слияние и merge base

Слияние в Git — трёхстороннее. Берутся три состояния:

  • base — общий предок (merge base);
  • ours — верхушка текущей ветки;
  • theirs — верхушка сливаемой ветки.

Merge base ищется командой git merge-base:

$ git merge-base main feature/daily
d8d1ce0945557638c07a9a6f757cd707013e4705
$ git merge-base --all main feature/daily   # может быть несколько!
d8d1ce0945557638c07a9a6f757cd707013e4705

Алгоритм для каждого файла прост:

base ours theirs результат
X X X X (никто не трогал)
X Y X Y (изменили только мы)
X X Y Y (изменили только они)
X Y Y Y (изменили одинаково)
X Y Z конфликт
X X (удалён) удалён
X Y (удалён) конфликт modify/delete

Внутри файла то же самое применяется к блокам строк, найденным diff-алгоритмом. Конфликт возникает тогда и только тогда, когда обе стороны изменили пересекающиеся или соседние блоки. Именно поэтому:

  • перенос метода на 200 строк вверх конфликтует со всем, что было внутри;
  • изменение отступов во всём файле конфликтует с любой правкой в нём;
  • два человека, добавившие зависимость в конец build.gradle, конфликтуют, хотя изменения семантически не противоречат;
  • а два человека, поправившие разные методы одного класса, не конфликтуют — и это чаще всего правильно, но иногда даёт семантический конфликт: Git слил текст, а код не компилируется. Git не понимает Java. Компиляция и тесты после merge — не формальность.

🔧 Под капотом. Несколько merge base. Если ветки сливали туда-сюда, общих предков может быть несколько (criss-cross merge). Стратегия ort (как и старая recursive) в этом случае рекурсивно сливает сами merge base между собой, получает виртуальную базу и уже с ней делает three-way. Отсюда название recursive. Практическое следствие: в запутанной истории конфликты могут выглядеть «взявшимися из ниоткуда» — это разрешение виртуальной базы. git merge-base --all покажет, что баз действительно несколько.

2.4 Стратегии слияния: ort, опции -X и -s

С Git 2.34 стратегией по умолчанию является ort («Ostensibly Recursive's Twin») — полная переписка recursive без зависимости от индекса как рабочей структуры. Это видно прямо в выводе:

$ git merge -X ours feature/daily
Auto-merging src/main/java/ru/bank/pay/Limit.java
Merge made by the 'ort' strategy.

Что даёт ort по сравнению с recursive: заметно быстрее на больших деревьях, корректнее обрабатывает переименования каталогов (merge.directoryRenames), лучше сообщает о конфликтах типов (файл↔каталог, файл↔симлинк), не трогает рабочее дерево при git merge-tree (что позволило серверам считать слияния без checkout).

Стратегии (-s):

Стратегия Что делает Когда нужна
ort three-way с рекурсивной виртуальной базой; значение по умолчанию для двух веток всегда
recursive предшественник ort; оставлен для совместимости почти никогда
resolve простой three-way, одна merge base отладка странного поведения ort
octopus слияние >2 веток сразу; отказывается при конфликтах сборка интеграционной ветки из независимых фич
ours (-s ours) создаёт merge-коммит, полностью игнорируя содержимое другой ветки; дерево = наше «пометить как влитое», не беря код
subtree вариант ort со сдвигом путей слияние подпроекта в подкаталог

Самая частая путаница в Git — -s ours против -X ours:

  • -s ours — стратегия. Результат: дерево merge-коммита побайтово равно нашему. Все изменения другой ветки отбрасываются, но граф говорит «влито». Применение: закрыть устаревшую ветку, чтобы она перестала мешать --no-merged; или «съесть» релизную ветку в main, когда содержимое уже перенесено cherry-pick'ами.
  • -X ours — опция стратегии ort. Обычное трёхстороннее слияние, но в конфликтующих местах автоматически берётся наша сторона. Неконфликтующие изменения другой ветки применяются полностью.

Ошибка «хотел -X ours, написал -s ours» тихо теряет работу целой ветки и выглядит в истории как штатное слияние. Это один из самых противных инцидентов: ветка помечена как влитая, MR закрыт, кода нет.

Симметрично -X theirs. Полезные родственники: -X ignore-all-space (игнорировать изменения пробелов при слиянии — спасает при смешении табов и пробелов), -X renormalize (перенормализовать concerning CRLF, см. 9.6), -X find-renames=<n>.

2.5 Стили маркеров конфликта: merge, diff3, zdiff3

Стиль по умолчанию (merge) показывает только две стороны:

public class Limit {
<<<<<<< HEAD
    static final long DAILY = 150_000L;
=======
    static final long DAILY = 300_000L;
>>>>>>> feature/daily
    static final long SINGLE = 50_000L;
}

Этого достаточно, чтобы понять «есть два варианта», и недостаточно, чтобы понять кто что изменил. diff3 добавляет базу:

<<<<<<< HEAD
    static final long DAILY = 150_000L;
||||||| d8d1ce0
    static final long DAILY = 100_000L;
=======
    static final long DAILY = 300_000L;
>>>>>>> feature/daily

Теперь видно: было 100 000, комплаенс поднял до 150 000, фича — до 300 000. Решение принимается осмысленно, а не подбрасыванием монетки. Включайте diff3/zdiff3 глобально — это единственная настройка Git, которая окупается в первый же день.

zdiff3 (появился в Git 2.35) делает то же, что diff3, но дополнительно выносит за пределы конфликта строки, одинаковые у обеих сторон. Разницу видно только на многострочных конфликтах. Вот проверенный пример (Git 2.55): база 1/2/3, обе стороны добавили одинаковую строку SHARED и разные следующие.

--- merge.conflictStyle=diff3 ---
1
<<<<<<< HEAD
SHARED
ours
||||||| c1a6f2a
2
=======
SHARED
theirs
>>>>>>> k1
3

--- merge.conflictStyle=zdiff3 ---
1
SHARED
<<<<<<< HEAD
ours
||||||| c1a6f2a
2
=======
theirs
>>>>>>> k1
3

На конфликте в 200 строк, где стороны реально разошлись в трёх, zdiff3 сокращает разбираемый объём на порядок. Настройка:

git config --global merge.conflictStyle zdiff3

Работа с конфликтом на уровне команд:

git status                        # список "both modified" / "deleted by us" и т.п.
git diff                          # комбинированный diff: только конфликтующие места
git diff --ours / --theirs / --base <file>   # сравнение с конкретной стадией
git checkout --ours <file>        # взять целиком нашу версию файла
git checkout --theirs <file>      # взять целиком их версию
git checkout --merge <file>       # вернуть маркеры (перегенерировать конфликт)
git checkout --conflict=zdiff3 <file>  # перегенерировать в другом стиле
git add <file>                    # пометить разрешённым (стадии 1/2/3 схлопываются в 0)
git merge --abort                 # вернуться в состояние до merge

⚠️ Осторожно. --ours/--theirs во время rebase означают противоположное интуиции. При rebase Git прикладывает ваши коммиты поверх чужой ветки, поэтому «ours» — это ветка, на которую вы ребейзитесь (upstream), а «theirs» — ваши собственные изменения. Люди регулярно выбрасывают свою работу, автоматически набрав --ours. Проверяйте стадии через git diff --base --ours прежде, чем рубить.

Ещё один важный момент: пустое разрешение — это разрешение. Если вы вырезали оба варианта и сделали git add, Git радостно примет это. Ни одна проверка не скажет «ты потерял код». Единственная защита — git diff HEAD после разрешения и обязательная компиляция/тесты.

Для сложных конфликтов удобен git mergetool (настраивается merge.tool), но в IDEA встроенный трёхпанельный распознаватель обычно лучше — см. главу 57 (57-intellij-idea.md).

2.6 Повторное использование разрешений конфликтов (rerere)

Долгоживущая релизная ветка + регулярный merge/rebase из main = разрешение одних и тех же конфликтов раз за разом. rerere это снимает.

Механика: при возникновении конфликта Git сохраняет в .git/rr-cache/<хеш-конфликта>/ «преконфликтную» форму (нормализованный текст с маркерами) и, после того как вы разрешили конфликт и сделали коммит, — «постконфликтную». Хеш считается от самого конфликта, а не от коммитов. В следующий раз, встретив тот же конфликт, Git молча применяет сохранённое разрешение.

git config --global rerere.enabled true
git config --global rerere.autoUpdate true   # ещё и git add за вас

$ git rerere diff

+++ b/z.txt
@@ -2,10 +2,6 @@

Обратите внимание на последнюю строку: без rerere.autoUpdate файл остаётся в состоянии UU. Это сделано намеренно — чтобы вы посмотрели на результат. rerere не «решает конфликты», он «повторяет ваше решение». Если контекст изменился, повторённое решение может быть неверным.

Где rerere реально спасает:

  • Долгий rebase. Вы делаете rebase, упираетесь в конфликт на 12-м коммите из 60, доходите до конца, понимаете, что надо переделать, — rebase --abort и заново. Без rerere — второй раз те же 15 конфликтов руками. С rerere — ноль.
  • Релизная ветка. Каждую неделю сливаете main в release/2026.03, и каждую неделю тот же конфликт в application.yml. Записали один раз.
  • Проверка «а как бы слилось» — сделали пробный merge, разрешили, откатили; настоящий merge через неделю пройдёт с готовым разрешением.

Управление кэшем: git rerere forget <path> — забыть разрешение для файла в текущем конфликте (когда записали неверно); git rerere gc — чистка (сроки gc.rerereResolved, по умолчанию 60 дней, и gc.rerereUnresolved, 15 дней — ⚠️ значения по памяти, точную формулировку смотрите в git help config).

⚠️ Осторожно. rerere тихо применяет старое разрешение в новом контексте. Если фичу переписали, а конфликт текстуально совпал — вы получите разрешение «из прошлой жизни» и не заметите, потому что merge пройдёт без вопросов. Правило: при включённом rerere обязательно смотреть git diff HEAD перед коммитом слияния и гонять тесты. Второе правило: rerere — локальный кэш, он не шарится с командой; «у меня слилось чисто, а в CI конфликт» — типичное последствие.

2.7 Слияние без рабочего дерева: merge-tree

Отдельно стоит знать про git merge-tree --write-tree <branch1> <branch2> (режим появился в 2.38): он вычисляет результат слияния в памяти, печатает хеш получившегося дерева и список конфликтов, ничего не трогая в рабочем каталоге. Это то, чем хостинги считают «Can be merged automatically» и чем удобно делать предварительную проверку в CI («упадёт ли merge в main») без checkout:

if ! git merge-tree --write-tree --name-only origin/main HEAD >/dev/null 2>&1; then
  echo "ветка конфликтует с main" >&2
fi

3. Rebase и merge

3.1 Механизм rebase

git rebase upstream делает ровно следующее:

  1. Вычисляет список коммитов, которые есть в текущей ветке и нет в upstream (грубо — upstream..HEAD, с отсеиванием тех, чьи изменения уже есть в upstream, — про это ниже).
  2. Запоминает текущий HEAD в ORIG_HEAD и в reflog.
  3. Переводит HEAD на upstream (detached).
  4. Для каждого коммита из списка по порядку вычисляет патч (diff относительно его родителя) и применяет его как новый коммит, сохраняя авторские данные и сообщение, но подставляя себя коммиттером и новую дату коммиттера.
  5. Переставляет ссылку ветки на последний созданный коммит.

Ключевое: коммиты не «переезжают», они пересоздаются. У нового коммита другой родитель, другое дерево, другая дата коммиттера — значит, другой SHA. Старые объекты остаются в базе и достижимы через reflog ещё 90 дней.

до:       A---B---C  (main)
               \
                D---E  (feature)

после git rebase main (находясь на feature):
          A---B---C  (main)
                   \
                    D'---E'  (feature)

D и E никуда не делись — они недостижимы по веткам,
но лежат в базе и видны в `git reflog feature`.

Из этого выводятся все свойства rebase:

  • История становится линейной — нет merge-коммитов, git log читается как список изменений.
  • Все SHA после точки вставки меняются. Если кто-то уже забрал старые коммиты — у него и у вас разные объекты с одинаковыми сообщениями. При его git pull получится «дубликат истории»: те же изменения дважды.
  • Конфликты разрешаются покоммитно. Если ветка из 30 коммитов и конфликтует базовый файл — вы разрешите конфликт до 30 раз. Merge разрешил бы его один раз. Это главный практический аргумент против rebase длинных веток (и главный аргумент за rerere).
  • Промежуточные коммиты могут не собираться. Rebase гарантирует корректность только конечного состояния: патчи применяются к новому контексту, и промежуточный коммит может оказаться несобираемым. Это ломает bisect, если не проверять сборку через --exec (см. 3.5).

🔧 Под капотом. Начиная с Git 2.26 по умолчанию используется «merge backend» вместо старого «apply backend» (git am-подход через текстовые патчи). Merge backend применяет каждый коммит как трёхстороннее слияние, поэтому: понимает переименования, работает с rerere, умеет --rebase-merges и --update-refs, честно сообщает конфликты. Старое поведение — --apply; его единственное преимущество — некоторые опции git apply (--ignore-whitespace, -C<n>).

3.2 Переписывание истории публичных веток

Классическая формулировка: не переписывайте историю, которую уже видел кто-то другой. Причина не в этике, а в механике: у коллеги в его refs/remotes/origin/feature лежат старые объекты, и его Git не знает, что D' — это D. Любой git pull (который merge) склеит обе версии, и в истории окажутся оба набора коммитов, а git log покажет каждое изменение дважды.

Где правило нарушают осознанно и это нормально:

  1. Собственная фича-ветка перед ревью. Она «публична» только технически — вы запушили её ради бэкапа и pipeline. Договорённость в команде: ветки feature/<имя>/* принадлежат автору, их переписывают свободно, кто-то другой на них не работает.
  2. Ветка в PR после замечаний рецензента. Многие команды требуют не «фиксап-коммитов» вроде «поправил по ревью», а переписанной чистой истории. Тогда после git rebase -i идёт git push --force-with-lease — и это штатная операция, а не авария. Рецензенту при этом помогает git range-diff (см. 4.4) и вкладка «Changes since last review» в хостинге.
  3. Совместная работа над одной веткой — вот здесь нарушать нельзя. Если над feature/big-refactoring работают трое, rebase этой ветки — гарантированная авария у двоих.

Единственный по-настоящему запретный случай — интеграционные ветки: main, develop, release/*. Они защищаются на сервере (см. главу 54, 54-cicd-platforms.md): protected branches, запрет force-push, запрет удаления. Если на вашем сервере force-push в main технически возможен — это дефект конфигурации, а не вопрос дисциплины.

Если коллеге всё-таки прилетела переписанная ветка, правильное лечение у него:

git fetch origin
git rebase --onto origin/feature/x <старая-база> feature/x   # перенести свои новые коммиты
# либо, если своих коммитов нет:
git reset --hard origin/feature/x

А не git pull.

3.3 Перенос части истории: --onto

Полная форма — git rebase --onto <новая-база> <старая-база> <ветка>: «возьми коммиты из <старая-база>..<ветка> и приложи их к <новая-база>».

Реальные применения:

1. Ветка ответвлена не от того. Вы начали feature/report от feature/limits, а лимиты отменили:

# было: main---A---B (feature/limits)---C---D (feature/report)
git rebase --onto main feature/limits feature/report
# стало: main---C'---D' (feature/report)

2. Выкинуть диапазон коммитов из середины. Нужно убрать B и C из A---B---C---D---E:

git rebase --onto A C E   # приложить D,E прямо к A

3. Перенести «хвост» ветки на релизную. Часть работы уже влита в main через squash, а оставшиеся три коммита нужны в релизной ветке:

git rebase --onto release/2026.03 main feature/x

4. Убрать коммит-«секрет» из недавней истории. Если утёкший файл добавлен 3 коммита назад и ветку никто не забрал — --onto быстрее filter-repo (но помните: объект уже в базе и на сервере, ротация секрета обязательна — см. 10.5).

3.4 Интерактивный rebase

git rebase -i main        # править все коммиты ветки относительно main
git rebase -i HEAD~5      # последние 5
git rebase -i --root      # вообще всю историю, включая первый коммит

Открывается список коммитов в порядке от старого к новому (обратно git log) с командами:

Команда Что делает
pick (p) взять коммит как есть
reword (r) взять коммит, но открыть редактор сообщения
edit (e) остановиться после применения — можно менять содержимое и разбивать
squash (s) слить с предыдущим, открыв редактор объединённого сообщения
fixup (f) слить с предыдущим, выбросив сообщение этого коммита
fixup -C слить с предыдущим, оставив сообщение этого коммита
drop (d) выбросить коммит целиком
exec (x) выполнить shell-команду после этого шага
break (b) остановиться здесь (как edit, но без изменения коммита)
label/reset/merge примитивы для --rebase-merges

Перестановка строк меняет порядок коммитов. Удаление строки эквивалентно drop (и Git с версии 2.9+ по умолчанию ругается, если вы удалили строку случайно — rebase.missingCommitsCheck).

Разбиение коммита — операция, которую почти никто не знает, а она нужна регулярно (рецензент сказал «здесь две разные вещи в одном коммите»):

git rebase -i HEAD~3
# ставим 'edit' напротив нужного коммита, сохраняем

# rebase остановился на этом коммите; распускаем его в рабочее дерево:
git reset HEAD^            # --mixed: HEAD назад, индекс назад, файлы остались

# теперь набираем первый коммит по кусочкам
git add -p src/main/java/ru/bank/pay/Fee.java    # интерактивно: y/n/s/e по ханкам
git commit -m "refactor(pay): выделить расчёт комиссии"

# остальное — во второй
git add -A
git commit -m "feat(pay): комиссия для переводов между своими счетами"

git rebase --continue

git add -p — ключевой инструмент атомарности коммитов. Отвечать можно: y (взять ханк), n (пропустить), s (разбить ханк мельче), e (редактировать ханк вручную), q (выйти). Полноценно то же самое делается в IDEA через частичный коммит по строкам (глава 57).

--autosquash — то, что должно быть включено у всех. Вы делаете правку по ревью и вместо «fix review comments» пишете:

git commit --fixup <sha-исходного-коммита>     # сообщение станет "fixup! <тема>"
git commit --squash <sha>                      # "squash! <тема>" — с объединением сообщений
git commit --fixup=amend:<sha>                 # изменить и сообщение целевого коммита (2.32+)
git commit --fixup=reword:<sha>                # только сообщение

Потом:

git rebase -i --autosquash main

Git сам поставит fixup-коммиты сразу после их целей и пометит их fixup. Вам остаётся сохранить файл. Включить навсегда:

git config --global rebase.autoSquash true
git config --global rebase.autoStash true   # автоматически прятать локальные изменения

Практика в банковской команде: пока MR на ревью, все правки идут --fixup; перед слиянием — rebase -i --autosquash; рецензент при этом видит каждую итерацию отдельным коммитом и не теряет контекст, а в main уходит чистая история.

3.5 --update-refs, --rebase-merges, --exec

--update-refs (Git 2.38) решает проблему стека веток. Если у вас main ← part1 ← part2 ← part3 (каждая следующая ответвлена от предыдущей — stacked PRs), то обычный rebase part3 на main оставит part1 и part2 висеть на старых коммитах. Проверенный вывод (2.55):

$ git switch part2 && git rebase --update-refs main
Successfully rebased and updated refs/heads/part2.
Updated the following refs with --update-refs:
    refs/heads/part1

$ git log --oneline --decorate -n 4
3a953dd (HEAD -> part2) part2
ff5f6f7 (part1) part1
d848ebb (main) main moved
feb76ba base

Включить по умолчанию: git config --global rebase.updateRefs true. Это единственная настройка, делающая stacked-workflow выносимым без внешних инструментов.

--rebase-merges сохраняет структуру слияний вместо того, чтобы «расплющивать» их. В todo-списке появляются label, reset и merge, описывающие топологию. Нужно, когда ветка сама содержит осмысленные merge-коммиты (например, в неё вливали подветки). Без этого флага merge-коммиты просто выбрасываются, а их содержимое применяется линейно — и это часто совсем не то, что вы хотели.

--exec прогоняет команду после каждого коммита. Идеальный способ гарантировать, что после rebase каждый коммит собирается (и bisect останется рабочим):

git rebase -i --exec './gradlew --offline -q compileJava test' main

При падении rebase останавливается на проблемном коммите — чините и git rebase --continue.

3.6 Прерывание и отмена неудачного rebase

Порядок действий, который должен быть в мышечной памяти:

git rebase --abort      # вернуться ровно в состояние до rebase. Работает всегда, пока rebase идёт
git rebase --skip       # выбросить текущий коммит (он не применяется вовсе!) и продолжить
git rebase --continue   # после разрешения конфликта и git add
git rebase --edit-todo  # переписать оставшийся план прямо посреди rebase

⚠️ Осторожно. --skip — не «пропустить конфликт», а выбросить коммит целиком. Люди жмут его, чтобы «проскочить», и теряют изменения. Если конфликт пустой (изменение уже есть в upstream), Git сам скажет об этом и предложит --skip — вот тогда он уместен.

Если rebase уже завершился, а результат плохой:

git reset --hard ORIG_HEAD          # ORIG_HEAD ставится перед rebase/merge/reset
# или точнее, по reflog:
git reflog                          # ищем строку "rebase (start): checkout ..."
git reset --hard HEAD@{7}
# либо по ветке:
git reflog show feature/x
git reset --hard feature/x@{1}

ORIG_HEAD перезаписывается следующей «большой» операцией, поэтому надёжнее reflog. Подробности — в разделе 5.6.

Ещё одна страховка, которую стоит завести привычкой перед любым нетривиальным rebase длинной ветки:

git branch backup/feature-x-before-rebase

Одна строка, ноль стоимости, снимает весь класс паники.

3.7 Сравнение merge, rebase и squash-merge

Атрибуция авторства точная, у каждого коммита свой автор точная (автор сохраняется, коммиттер меняется) теряется при нескольких авторах — спасают trailer'ы Co-authored-by
Соответствие тому, что реально происходило точное приукрашенное (коммиты «как будто писались поверх main») утрачено
Риск аварий минимальный средний (force-push, потеря при ошибке) низкий
Требует force-push нет да нет (делает сервер)

Практическая рекомендация для банковского backend-сервиса:

  • внутри фича-ветки — rebase на main регулярно (раз в день), чтобы не копить расхождение; интерактивный rebase перед ревью, чтобы история была осмысленной;
  • в main — merge с --no-ff (или squash-merge для мелких фич), чтобы была граница фичи и запись «кто принял»;
  • в release/* — только cherry-pick или merge из main; никогда не rebase, потому что релизную ветку читают все;
  • --first-parent в релиз-нотах и отчётности.

💡 На интервью. «Merge сохраняет то, что реально происходило, и создаёт коммит с двумя родителями; rebase пересоздаёт коммиты с новыми SHA поверх другой базы, давая линейную историю ценой переписывания. Я использую rebase внутри своей ветки, пока её никто не забрал, и merge --no-ff при вливании в main — это даёт и чистую историю фичи, и явную границу задачи для отката и аудита. Squash-merge беру для мелких изменений: одна фича — один коммит, идеально для bisect, но теряется промежуточная история и авторство соавторов.»

4. Cherry-pick и перенос изменений

4.1 Механизм cherry-pick

git cherry-pick <commit> вычисляет diff указанного коммита относительно его родителя и применяет его к текущему HEAD как трёхстороннее слияние, создавая новый коммит с тем же сообщением и автором, но новым SHA и новым деревом.

То есть cherry-pick — это rebase одного коммита. Все следствия те же: новый объект, новая дата коммиттера, изменения могут не примениться при конфликте контекста.

Для merge-коммита нужен -m <номер-родителя>, чтобы указать, относительно какого родителя считать патч:

git cherry-pick -m 1 <merge-sha>     # изменения фичи относительно main

4.2 Флаг -x и трассируемость

$ git cherry-pick -x 26bfb5b
$ git log -1 --format=%B
fix(pay): NPE в расчёте комиссии

(cherry picked from commit 26bfb5bd556dbd99ff5e9d1d09c2a6e725544d0d)

Строка (cherry picked from commit ...) добавляется только с -x. Ставьте -x всегда, когда переносите между долгоживущими ветками: через полгода при разборе инцидента это единственный способ понять, откуда взялся этот код в релизной ветке. При переносе внутри своей приватной ветки -x бессмысленен (исходный коммит всё равно исчезнет).

Ещё два флага:

  • -n (--no-commit) — применить изменения в индекс и рабочее дерево, не коммитя. Позволяет накопить несколько cherry-pick в один коммит: git cherry-pick -n A B C && git commit -m "backport: исправления расчёта комиссии".
  • -e — отредактировать сообщение; --signoff — добавить Signed-off-by.

Диапазоны: git cherry-pick A..B (без A, до B включительно), git cherry-pick A^..B (включая A). При конфликте — git cherry-pick --continue / --abort / --quit (последний бросает всё как есть, не откатывая).

4.3 Дублирование коммитов при последующем merge

Самое неприятное свойство cherry-pick: один и тот же логический патч существует в двух коммитах с разными SHA. Когда ветку с оригиналом потом вливают туда, куда уже сделан cherry-pick, возможны два исхода:

  1. Git разрешит это молча. Трёхстороннее слияние увидит, что обе стороны пришли к одному содержимому, и конфликта не будет. В истории останутся два коммита с одинаковым сообщением — визуальный шум, но не поломка.
  2. Будет конфликт. Если после cherry-pick код в целевой ветке правили, three-way увидит расхождение и потребует разрешения — причём конфликт будет выглядеть бессмысленно («я же уже это применял»).

Инструмент, который помогает не запутаться, — git cherry:

$ git cherry -v main release/2026.03
- 26bfb5b fix(pay): NPE в расчёте комиссии     # знак «-»: патч УЖЕ есть в main
+ a11c93f fix(pay): округление вниз            # знак «+»: в main такого патча нет

git cherry сравнивает коммиты не по SHA, а по patch-id — хешу нормализованного diff'а. Это тот же механизм, которым rebase отбрасывает уже применённые коммиты. Именно поэтому «rebase выкинул мои коммиты» обычно означает «эти изменения уже есть в upstream, просто под другими SHA».

4.4 Сверка перенесённых коммитов: git range-diff

range-diff сравнивает два диапазона коммитов и показывает, чем отличаются соответствующие друг другу коммиты. Это diff от diff'ов.

$ git range-diff 26bfb5b~1..26bfb5b HEAD~1..HEAD
1:  26bfb5b ! 1:  e7935a9 fix(pay): NPE в расчёте комиссии
    @@ Metadata
      ## Commit message ##
         fix(pay): NPE в расчёте комиссии

    +    (cherry picked from commit 26bfb5bd556dbd99ff5e9d1d09c2a6e725544d0d)
    +
      ## a.txt ##
     @@
      v1

Читается так: коммит №1 из первого диапазона соответствует коммиту №1 из второго (знак ! — «есть отличия»; = — идентичны, >/< — есть только в одном из диапазонов). Дальше показано, чем отличается сам патч — здесь только добавленная строка (cherry picked from ...), то есть код перенесён один в один.

Где range-diff незаменим:

  • проверка бэкпорта: «точно ли срочное исправление в релизной ветке делает ровно то же, что в main» — git range-diff main~1..main release/2026.03~1..release/2026.03;
  • ревью после rebase: «что изменилось в ветке между первой и второй итерацией ревью» — git range-diff origin/main..@{u} origin/main..HEAD;
  • аудит: доказать регулятору/безопасности, что в релиз ушло ровно то, что проревьюено.

4.5 Сценарий переноса срочного исправления

Продакшен-инцидент: в release/2026.03 NPE. Правильная последовательность:

# 1. чиним ТАМ, где горит, — в релизной ветке
git switch release/2026.03
git pull --ff-only
git switch -c hotfix/PAY-4711-npe
# ... правка + тест ...
git commit -m "fix(pay): NPE при расчёте комиссии без тарифа

Комиссия считалась до проверки наличия тарифа у продукта.
Тариф отсутствует у закрытых продуктов, отсюда NPE в проде.

Refs: PAY-4711"
git push -u origin hotfix/PAY-4711-npe
# MR в release/2026.03, ускоренное ревью, мерж, сборка, деплой

# 2. переносим в main — ОБЯЗАТЕЛЬНО и сразу, пока помнишь
git switch main && git pull --ff-only
git cherry-pick -x <sha-хотфикса-из-релизной>
# конфликт возможен: в main код мог уйти вперёд
git push

Почему именно в таком направлении. Правка сначала в релизной ветке, потом перенос в main — потому что горит прод, а main может содержать несовместимые изменения, из-за которых патч не применится или потребует доработки. Обратный порядок («сначала в main, потом backport») тоже применяют — он лучше тем, что main никогда не отстаёт, и хуже тем, что удлиняет время до выката фикса.

Почему обратный перенос (из релизной в main) обычно хуже штатного процесса и требует дисциплины:

  • о нём забывают — и следующий релиз приезжает с регрессом, потому что фикса в main нет. Это самый частый способ «починить одно и то же дважды»;
  • он делается второпях, в пятницу, без ревью — и ошибка переноса (конфликт разрешили не туда) попадает в main незамеченной;
  • если срочных исправлений много, cherry-pick накапливается и main с релизной начинают расходиться в невыносимую сторону.

Защита процессом (детали — в главе 53, 53-cicd-process.md): обязательная задача-«перенос в main» в трекере, проверка в CI «все коммиты из release/* имеют patch-id, присутствующий в main» (то самое git cherry), и правило «релиз не закрывается, пока git cherry -v main release/X не пуст».

# проверка в пайплайне: что из релизной не доехало в main
MISSING=$(git cherry -v origin/main origin/release/2026.03 | grep '^+' || true)
if [ -n "$MISSING" ]; then
  echo "Не перенесено в main:"; echo "$MISSING"; exit 1
fi

5. Отмена и восстановление изменений

5.1 reset и модель трёх деревьев

git reset [--soft|--mixed|--hard] <commit> делает от одного до трёх шагов:

  1. переставить HEAD (точнее, текущую ветку) на <commit> — делают все три режима;
  2. привести индекс к состоянию <commit> — --mixed (по умолчанию) и --hard;
  3. привести рабочее дерево к состоянию <commit> — только --hard.
$ git log --oneline
5b6f250 commit 5
2182b5e commit 4
3b16a81 commit 3
0435994 commit 2
d79ea8c commit 1

$ git reset --hard HEAD~3
HEAD is now at 0435994 commit 2

Практические смыслы:

  • --soft HEAD~1 — «разкоммитить»: изменения остаются в индексе, можно сразу сделать git commit заново. Классика: забыли файл, неправильное сообщение (хотя для последнего есть commit --amend), нужно разбить последний коммит на два.
  • --mixed HEAD~1 (значение по умолчанию) — «разкоммитить и расстейджить»: изменения в рабочем дереве, индекс чист. Это же — способ «снять с индекса всё»: git reset без аргументов (эквивалент git restore --staged .).
  • --hard <commit> — «сделать так, будто ничего не было». Единственная команда Git, которая безвозвратно уничтожает данные: незафиксированные изменения рабочего дерева нигде не сохранены и через reflog не восстанавливаются. Всё остальное (коммиты, ветки) восстановимо.
$ git reset --soft HEAD~1 && git status --short
M  f.txt          # в индексе

$ git reset --mixed HEAD && git status --short
 M f.txt          # только в рабочем дереве

Обратите внимание на позицию буквы M — первая колонка это индекс, вторая рабочее дерево. Читать git status --short надо именно так: M = попадёт в коммит, M = нет, MM = в коммит попадёт часть, ?? = неотслеживаемый, UU = конфликт.

Отдельная форма: git reset <commit> -- <path> — не двигает HEAD вообще, а только обновляет индекс для указанных путей из <commit>. Сейчас это делают через понятный git restore --source=<commit> --staged <path>.

5.2 Команда restore

С Git 2.23 работу с файлами вынесли из checkout в restore:

git restore <file>                      # взять из ИНДЕКСА в рабочее дерево (= checkout -- <file>)
git restore --staged <file>             # взять из HEAD в индекс (= reset HEAD <file>)
git restore --source=HEAD~2 <file>      # взять из произвольного коммита в рабочее дерево
git restore --source=HEAD --staged --worktree <file>   # вернуть файл в состояние HEAD полностью
git restore --patch <file>              # интерактивно, по ханкам

Разница с git checkout -- <file> не в поведении, а в однозначности: restore никогда не переключит ветку и не создаст detached HEAD, а --staged/--worktree явно называют, какое из трёх деревьев меняется. В командах, где есть junior'ы, замена checkout на switch/restore в инструкциях снимает целый класс инцидентов.

⚠️ Осторожно. git restore <file> безвозвратно затирает несохранённые правки — как и checkout --. Никакой reflog не поможет: содержимое не было ни в индексе, ни в объектах. Единственная страховка — Local History в IDEA (глава 57, 57-intellij-idea.md) или git stash вместо «просто откачу».

5.3 Команда clean

git clean удаляет неотслеживаемые файлы. Никакой Git-механизм их не восстановит — их никогда не было в базе.

git clean -n                 # dry-run: что будет удалено. ВСЕГДА начинать с этого
git clean -f                 # удалить неотслеживаемые файлы
git clean -fd                # + каталоги
git clean -fdx               # + игнорируемые (target/, build/, .idea/ !!!)
git clean -fdX               # ТОЛЬКО игнорируемые (чистка сборочного мусора)
git clean -i                 # интерактивный режим

-x — самый опасный флаг в Git после reset --hard: он снесёт .env с локальными настройками, *.p12 с тестовыми ключами, не зафиксированную папку local/ — всё, что перечислено в .gitignore. В CI git clean -fdx уместен (workspace одноразовый), на рабочей машине — почти никогда; для чистки сборки используйте -fdX или ./gradlew clean.

5.4 revert и отмена merge-коммита

git revert <commit> создаёт новый коммит, который применяет обратный патч. История не переписывается, SHA не меняются, публичные ветки в безопасности. Это единственный корректный способ откатить то, что уже ушло в main/прод.

git revert <sha>                 # один коммит
git revert -n <sha1> <sha2>      # накопить без коммита
git revert --no-edit HEAD~3..HEAD   # диапазон (Git применяет в обратном порядке)
git revert --abort / --continue

Для merge-коммита обязателен -m <номер родителя>: надо сказать, какую «линию» считать основной. -m 1 — первый родитель (обычно main), то есть «откатить всё, что пришло из влитой ветки».

Теперь ловушка, ради которой этот подраздел существует. Полная воспроизводимая последовательность (Git 2.55):

$ git switch main
$ git merge --no-ff -m "Merge branch 'feature/cashback'" feature/cashback
$ ls
Cashback.java  README.md                 # фича на месте

$ git revert -m 1 --no-edit HEAD
 delete mode 100644 Cashback.java
$ ls
README.md                                # откатили, всё правильно

# ...через две недели фичу доработали и хотят вернуть...
$ git merge feature/cashback
Already up to date.
$ ls
README.md                                # ФАЙЛА НЕТ. И merge говорит, что всё влито.

Почему так. Merge-коммит уже является частью истории main, значит все коммиты ветки feature/cashback достижимы из main. С точки зрения графа фича влита. Revert откатил только содержимое, не топологию. Повторный merge вычисляет merge base = верхушка feature (она уже предок main), разницы нет — «Already up to date». Ветка «перестала сливаться», а код исчез.

Как выходить. Три варианта, по убыванию предпочтительности:

Вариант 1 — revert of revert (годится, если ветку после этого не дорабатывали):

$ git revert --no-edit <sha-того-самого-revert-коммита>
 create mode 100644 Cashback.java
$ ls
Cashback.java  README.md

В свежих версиях Git такой коммит автоматически получает сообщение Reapply "Merge branch 'feature/cashback'" — это удобно для читаемости истории. Метод простой, но у него есть неприятное свойство: если после revert'а ветку доработали, «revert of revert» вернёт старое состояние, а новые коммиты ветки придётся вливать поверх — со всеми конфликтами.

Вариант 2 — новая ветка от текущего main (предпочтительно при доработке):

git switch -c feature/cashback-v2 main
git cherry-pick <первый-коммит-фичи>..<последний-коммит-фичи>

Ветка становится обычной невлитой веткой, ревью и merge идут штатно. Именно этот путь рекомендуется, если между revert'ом и возвратом прошло время.

Вариант 3 — не revert'ить merge, а revert'ить содержимое. Если вы знаете заранее, что фичу придётся возвращать, откатывайте не merge-коммит, а коммиты фичи по отдельности (git revert A..B) либо вообще не сливайте ветку, а используйте feature toggle: выключить флаг дешевле и безопаснее любого revert'а (см. главу 53).

💡 На интервью. «Revert merge-коммита откатывает изменения, но не топологию: коммиты влитой ветки остаются достижимыми из main, поэтому повторный merge скажет Already up to date, а кода в дереве не будет. Выхода два: revert of revert, если ветку не дорабатывали, либо новая ветка с cherry-pick диапазона — она снова становится невлитой и проходит обычное ревью. Именно поэтому в командах, где фичи откатывают часто, предпочитают feature flags или squash-merge: у squash-коммита revert обратим без этой ловушки.»

5.5 Исправление последнего коммита: commit --amend

git commit --amend создаёт новый коммит с тем же родителем, заменяя текущий. Старый остаётся в reflog. Ключевые формы:

git commit --amend                       # изменить сообщение и/или добавить staged-изменения
git commit --amend --no-edit             # добавить изменения, сообщение не трогать
git commit --amend --author="Ivan Petrov <i.petrov@bank.example>"   # исправить автора
git commit --amend --reset-author        # переставить автора и дату на себя/сейчас
git commit --amend --date=now

Типовая авария: сделали коммит с неправильным user.email (корпоративная почта против личной), хостинг не связал коммит с аккаунтом, проверка «все коммиты от сотрудников» в CI падает. Лечение для одного коммита — --amend --reset-author; для ветки — git rebase -i с exec git commit --amend --reset-author --no-edit, либо git filter-repo --mailmap.

5.6 Журнал ссылок reflog

Reflog — журнал перемещений ссылок. Каждый раз, когда HEAD или любая ветка меняет значение, Git дописывает строку в .git/logs/HEAD или .git/logs/refs/heads/<branch>: старое значение, новое значение, кто, когда, и текст операции.

$ git reflog
0435994 HEAD@{0}: reset: moving to HEAD~3
5b6f250 HEAD@{1}: commit: commit 5
2182b5e HEAD@{2}: commit: commit 4
3b16a81 HEAD@{3}: commit: commit 3
0435994 HEAD@{4}: commit: commit 2
d79ea8c HEAD@{5}: commit (initial): commit 1

Что важно знать:

  • Reflog локален. Он не клонируется, не пушится и не приходит с сервера. У коллеги свой reflog. Если вы потеряли коммит, а он был запушен — ищите на сервере (см. инцидент 12.1).
  • Пишется по умолчанию только в репозиториях с рабочим деревом (core.logAllRefUpdates). В bare-репозиториях на сервере — выключено по умолчанию, и это обязательно надо включать на Git-сервере, если он свой.
  • Срок жизни: gc.reflogExpire = 90 дней для достижимых записей, gc.reflogExpireUnreachable = 30 дней для недостижимых (Documentation/config/gc.adoc, проверено 2026-09-22). Настраивается пер-ref через gc.<pattern>.reflogExpire.
  • Записи можно адресовать по времени: main@{yesterday}, HEAD@{2.hours.ago}, feature/x@{5}.

Типовые спасения:

После reset --hard:

$ git reset --hard HEAD~3        # ой
$ git reflog | head -2
0435994 HEAD@{0}: reset: moving to HEAD~3
5b6f250 HEAD@{1}: commit: commit 5
$ git reset --hard HEAD@{1}      # или git reset --hard ORIG_HEAD
HEAD is now at 5b6f250 commit 5

ORIG_HEAD ставится перед reset, merge, rebase, pull — это готовая ссылка на «где я был». Но она одна и перезаписывается, поэтому надёжнее reflog.

После удаления ветки:

$ git branch -D feature/pay-limit
Deleted branch feature/pay-limit (was 9a3f1c2).
$ git switch -c feature/pay-limit 9a3f1c2     # SHA прямо в сообщении!
# если сообщение потеряно:
$ git reflog | grep -i "pay-limit"
$ git fsck --lost-found

Reflog самой удалённой ветки (.git/logs/refs/heads/feature/pay-limit) удаляется вместе с ней, поэтому ищите в reflog HEAD — там остались все переключения.

После неудачного rebase:

$ git reflog show feature/x
3a953dd feature/x@{0}: rebase (finish): refs/heads/feature/x onto d848ebb
ff5f6f7 feature/x@{1}: rebase (pick): part1
d848ebb feature/x@{2}: rebase (start): checkout main
9c1d0aa feature/x@{3}: commit: part2       <- вот исходное состояние
$ git reset --hard feature/x@{3}

Строка rebase (start) — граница: всё, что выше неё, сделано rebase'ом; то, что прямо под ней, — состояние до.

5.7 fsck --lost-found и dangling-объекты

Если reflog не помог (например, коммит создавался в detached HEAD в другом клоне, или запись уже истекла, но gc не отработал), остаётся прямой обход базы объектов:

$ git fsck --lost-found
dangling commit 770a7a7ef24beaf93ceb889e4f8e9683baf637f2
dangling commit 5b6f2505a03a3ec8f487218dbe3d12ddbf1d144b

dangling — объект в базе, на который не указывает ни одна ссылка. Дальше смотрим содержимое и восстанавливаем:

git log --oneline --all --not --all   # ничего не даст, нужен именно fsck
for c in $(git fsck --no-reflogs --lost-found 2>/dev/null | awk '/dangling commit/ {print $3}'); do
  git log -1 --format='%h %ad %an %s' --date=short $c
done
git switch -c rescue <нужный-sha>

Флаг --no-reflogs важен: без него всё, что есть в reflog, считается достижимым, и «потеряшек» не видно.

Отдельный случай — потерянные stash'и: git stash drop удаляет запись, но объект остаётся. git fsck --unreachable | grep commit плюс git show <sha> находят их; восстановление — git stash apply <sha>.

Ещё: git fsck --lost-found кладёт найденные объекты в .git/lost-found/ — коммиты как ссылки, blob'ы как файлы. Для поиска «потерянного, но добавленного через git add файла» это единственный способ:

git fsck --lost-found
ls .git/lost-found/other/     # blob'ы
grep -rl "SecretKeySpec" .git/lost-found/other/

5.9 Устройство stash

git stash — не «буфер обмена», а пара коммитов (для рабочего дерева и для индекса; при -u ещё один для неотслеживаемых файлов), подвешенных на ссылку refs/stash с собственным reflog. Поэтому:

  • stash'и пронумерованы как записи reflog: stash@{0}, stash@{1};
  • их содержимое — полноценные объекты, доступные git show stash@{0} и восстановимые через fsck даже после drop;
  • stash не привязан к ветке: спрятали на feature/a, достали на main — Git не возражает (и это часто именно то, что нужно).
git stash push -m "недоделанный расчёт лимитов"   # современная форма
git stash push -u                                 # включая неотслеживаемые
git stash push -- src/main/java/ru/bank/pay/      # только эти пути
git stash list
git stash show -p stash@{1}       # что внутри
git stash apply stash@{1}         # применить, оставив в стеке
git stash pop                     # применить и удалить (при конфликте НЕ удаляет)
git stash branch feature/rescue   # создать ветку от коммита, на котором прятали, и применить
git stash drop stash@{0}
git stash clear                   # удалить всё — опасно, восстановление только через fsck

⚠️ Осторожно. git stash без -u не прячет новые файлы. Вы прячете изменения, переключаетесь, собираете — и новый класс, который вы создали, но не добавляли, едет с вами и ломает сборку на другой ветке. Второе: git stash pop при конфликте применяет изменения, но не удаляет запись из стека — люди потом применяют её второй раз. Третье: stash — худшее место для хранения работы дольше часа. Ветка с коммитом wip стоит тех же трёх секунд и не теряется.

5.10 worktree: несколько рабочих деревьев на один репозиторий

git worktree даёт второе (третье, десятое) рабочее дерево, разделяющее одну базу объектов:

git worktree add ../pay-hotfix release/2026.03      # новое дерево на существующей ветке
git worktree add -b hotfix/PAY-4711 ../pay-hotfix release/2026.03
git worktree list
git worktree remove ../pay-hotfix
git worktree prune            # подчистить записи об удалённых вручную каталогах

Зачем backend-разработчику:

  • Срочное исправление без stash. У вас на feature/big полдня несохранённой работы и падает прод. Вместо «stash, switch, потом вспоминать» — новое дерево на релизной ветке в соседнем каталоге. Обе IDE-сессии живут параллельно, Gradle-кэши раздельные.
  • Долгая сборка/тест на одной ветке, работа на другой. Один worktree занят прогоном интеграционных тестов на Testcontainers, во втором вы пишете код.
  • Сравнение поведения двух версий — запустить два приложения бок о бок.

Ограничения: одну ветку нельзя чекаутить в двух деревьях одновременно (Git запретит) — используйте --detach. Каждое дерево имеет свой индекс, свой HEAD и свой ORIG_HEAD; reflog и объекты общие. Файл .git в дополнительном дереве — не каталог, а текстовый файл со строкой gitdir: ..., что иногда путает старые инструменты и сборочные плагины.

6. Инструменты исследования истории

Половина работы в старом сервисе — не «написать», а «понять, почему это так». Git знает ответ; вопрос в том, умеете ли вы его спросить.

6.1 Возможности git log

Базовый набор, который стоит завести псевдонимом:

git config --global alias.lg "log --oneline --graph --decorate --all"
git config --global alias.lga "log --graph --abbrev-commit --decorate \
  --format=format:'%C(bold blue)%h%C(reset) %C(dim white)(%ar)%C(reset) %C(white)%s%C(reset) %C(dim white)— %an%C(reset)%C(auto)%d%C(reset)'"

Фильтры, которые реально используются:

git log --since="2026-03-01" --until="2026-04-01"   # по дате КОММИТТЕРА
git log --author="Petrov"                            # регэксп по автору
git log --grep="PAY-4711"                            # регэксп по сообщению
git log --grep="fix" --grep="hotfix" --all-match     # И вместо ИЛИ
git log --merges / --no-merges                       # только слияния / без слияний
git log --invert-grep --grep="^chore"                # всё, кроме рутины
git log -- src/main/java/ru/bank/pay/Fee.java        # история пути
git log --diff-filter=D -- path/to/deleted.java      # коммит, где файл удалён
git log --stat / --shortstat / --name-status         # что менялось
git log --cherry-mark --left-right main...release    # где какие патчи (по patch-id)

6.2 История первых родителей: --first-parent

Merge-коммит имеет двух родителей: первый — это ветка, в которую вливали (main), второй — влитая (feature). --first-parent заставляет log идти только по первому родителю, то есть игнорировать внутренности фич:

$ git log --oneline --graph --first-parent
* 58ae193 Reapply "Merge branch 'feature/cashback'"
* c531de3 Revert "Merge branch 'feature/cashback'"
* 2b17fb9 Merge branch 'feature/cashback'
* 662ba05 base

Это и есть история релизной ветки в терминах фич, а не в терминах чужих «wip», «fix typo» и «после ревью». На ней строятся:

  • релиз-ноты: git log --first-parent --no-merges v1.4.0..v1.5.0 либо git log --first-parent --pretty='%s' v1.4.0..v1.5.0;
  • ответ на вопрос «когда фича попала в релиз»;
  • git bisect --first-parent (поддерживается с Git 2.29) — искать не среди 3000 коммитов, а среди 120 слияний. Находит «фичу, которая сломала», а не «коммит внутри фичи»; часто это ровно то, что нужно, и в 20 раз быстрее.

Важное условие: это работает, только если первый родитель всегда main. То есть если слияние делает сервер по кнопке «Merge» (или вы всегда git switch main && git merge feature), а не наоборот — «влить main в свою ветку и запушить». Второй способ переворачивает семантику родителей и превращает --first-parent в кашу. Это ещё один аргумент за merge только через MR/PR.

6.3 Поиск изменений (pickaxe): -S и -G

Поиск по содержимому изменений (pickaxe) отвечает на вопрос, в каком коммите появился или исчез фрагмент кода, и у git log для этого есть два ключа, которые ищут по-разному:

  • -S<строка> — «когда изменилось количество вхождений». Находит коммиты, где строка была добавлена или удалена. Перемещение кода, переформатирование, изменение соседних строк — не находит.
  • -G<регэксп> — «когда в diff'е была строка, совпавшая с регэкспом». Находит любой коммит, у которого в патче встречается совпадение, включая перемещения и косметику.

Проверенный пример (Git 2.55) на файле, где после правки ставки был массовый reformat:

$ git log -S'a / 100' --oneline
ed83d67 fix: ставка 0.5%                        # здесь строка исчезла
0fca12a feat: расчёт комиссии                   # здесь появилась

$ git log -G'a / [0-9]+' --oneline
d733c39 style: spotlessApply по всему проекту   # reformat тоже попал
ed83d67 fix: ставка 0.5%
0fca12a feat: расчёт комиссии

Правило: -S — когда ищете «кто это ввёл», потому что он даёт короткий и точный список; -G — когда -S ничего не нашёл, потому что код переехал или менялся частично. Для -S есть модификатор --pickaxe-regex, делающий аргумент регэкспом при сохранении семантики «изменилось число вхождений».

Прикладные запросы, которые стоит помнить:

git log -S'jdbc:postgresql' --oneline -- src/main/resources   # когда поменяли строку подключения
git log -S'@Transactional' --oneline -- src/main/java/ru/bank/pay/FeeService.java
git log -G'password|secret|token' --oneline --all             # грубый поиск утечек (см. 10.5)
git log --all -S'<версия-библиотеки>' -- pom.xml build.gradle # когда подняли зависимость

6.4 История файла и фрагмента: --follow и -L

git log --follow <file> продолжает историю через переименования. Ограничение: работает только для одного пути и использует эвристику определения переименований (--find-renames, порог схожести 50 %). Если файл переименовали и сильно переписали в одном коммите — история оборвётся.

git log -L показывает историю фрагмента файла:

git log -L 42,58:src/main/java/ru/bank/pay/FeeService.java   # по номерам строк
git log -L :calcFee:src/main/java/ru/bank/pay/FeeService.java # по имени функции

Форма :функция:файл требует, чтобы Git умел находить границы функций в этом языке. Для Java это включается атрибутом:

# .gitattributes
*.java diff=java
*.kt   diff=kotlin

Без этого атрибута получите ровно то, что получил я при проверке:

$ git log -L :calc:Fee.java --oneline
fatal: -L parameter 'calc' starting at line 1: no match

После добавления *.java diff=java та же команда отрабатывает и показывает полную историю метода, включая reformat. Встроенных драйверов много (java, kotlin, python, golang, rust, xml, html…), и они же улучшают заголовки ханков в обычном git diff — вместо бессмысленного контекста в @@ ... @@ появляется сигнатура метода. Одна строка в .gitattributes окупается ежедневно.

6.5 git blame и массовое форматирование

Базово:

git blame -L 40,60 src/main/java/ru/bank/pay/FeeService.java
git blame --line-porcelain <file> | grep '^author '   # машиночитаемо

Три флага, без которых blame врёт:

  • -w — игнорировать изменения пробелов;
  • -M — определять перемещение строк внутри файла;
  • -C — определять копирование/перемещение строк из других файлов в этом же коммите; -C -C расширяет поиск на файлы, изменённые в коммите; -C -C -C — на все файлы.

git blame -w -C -C -M вместо «Петров, рефакторинг 2025» покажет реального автора логики, написанной в другом классе три года назад.

Но главный инструмент — --ignore-rev и .git-blame-ignore-revs. Сценарий известен всем: команда внедрила Spotless/google-java-format, один коммит переформатировал 1200 файлов, и git blame на всём проекте теперь показывает автора этого коммита. История не потеряна, но пользоваться blame невозможно.

Проверенный вывод (Git 2.55). До:

$ git blame --line-porcelain Fee.java | grep -E '^(author |summary )' | paste - -
author A    summary feat: расчёт комиссии
author A    summary style: spotlessApply по всему проекту
author A    summary style: spotlessApply по всему проекту
author A    summary style: spotlessApply по всему проекту
...

После указания коммита-форматирования:

$ git blame --ignore-rev d733c39 Fee.java
^0fca12a (A 2026-09-22 1) class Fee {
d733c39a (A 2026-09-22 2) 
^0fca12a (A 2026-09-22 3)     long calc(long a) {
ed83d67c (A 2026-09-22 4)         return a / 200;
^0fca12a (A 2026-09-22 5)     }

Строки вернулись к своим настоящим авторам; за форматирующим коммитом остались только те строки, которые он реально породил (пустые).

Правильная настройка — файл в репозитории плюс конфиг:

# .git-blame-ignore-revs (в корне репозитория, коммитится)
# Массовое форматирование google-java-format, PAY-3901
d733c39a84f4b1a2c0e1f2d3a4b5c6d7e8f9a0b1
# Переход на 4 пробела, PAY-4102
9c1d0aa...

# каждому разработчику один раз (или в onboarding-скрипте):
git config blame.ignoreRevsFile .git-blame-ignore-revs

blame.ignoreRevsFile нельзя задать в .gitattributes — это локальная настройка, поэтому её кладут в CONTRIBUTING.md, в скрипт инициализации или в git config --local через make setup. GitHub и GitLab уважают .git-blame-ignore-revs в своём веб-blame (⚠️ поддержка GitLab — проверьте на своей версии).

Правила гигиены при массовом форматировании:

  1. Форматирование — отдельный коммит, ничего кроме форматирования. Смешение с логикой уничтожает и blame, и ревью.
  2. SHA этого коммита сразу дописывается в .git-blame-ignore-revs (следующим коммитом, поскольку своего SHA коммит знать не может).
  3. Дата — перед длинными выходными, чтобы минимизировать конфликты в открытых ветках; открытым MR потребуется git merge -X ignore-all-space или повторный прогон форматтера и rebase.
  4. Сразу же включается проверка формата в CI, иначе через месяц всё повторится.

6.6 Двоичный поиск по истории: git bisect

Бинарный поиск по истории. Формально — O(log n): 1000 коммитов = ~10 проверок.

Ручной режим:

git bisect start
git bisect bad                 # текущий сломан
git bisect good v2026.02.14    # последний заведомо рабочий (тег или SHA)
# Git переключает на середину; проверяем
./gradlew test --tests '*FeeServiceTest*'
git bisect good   # или bad, или skip
# ... повторяем ...
git bisect reset   # вернуться туда, где были

git bisect skip — для коммитов, которые невозможно проверить (не собирается, миграция БД поломана). Git исключит их и попробует соседние; если непроверяемых слишком много, он сообщит о диапазоне, а не о точном коммите.

Автоматический режим — то, ради чего bisect стоит освоить. git bisect run <команда>: код возврата 0 = good, 1–124/126/127 = bad, 125 = skip, 128+ = прервать.

git bisect start HEAD v2026.02.14
git bisect run ./gradlew -q --offline test --tests '*FeeServiceTest.commissionForClosedProduct*'

Проверенный вывод на синтетическом репозитории (Git 2.55, тест — grep по файлу):

$ git bisect run sh -c 'grep -q x6 v.txt && exit 1 || exit 0'
...
    c6
 v.txt | 1 +
 1 file changed, 1 insertion(+)
bisect found first 'bad' commit

Скрипт для реального Java-проекта обычно выглядит так — обратите внимание на код 125:

#!/usr/bin/env bash
# bisect-check.sh
set -u
./gradlew -q --offline compileJava compileTestJava || exit 125   # не собирается — пропустить
./gradlew -q --offline test --tests '*FeeServiceTest*' || exit 1 # тест упал — плохой
exit 0

git bisect start HEAD v2026.02.14
git bisect run ./bisect-check.sh
git bisect log > /tmp/bisect.log    # журнал для отчёта в задаче
git bisect reset

Bisect не только для «сломалось». Критерий good/bad — любая проверка с кодом возврата. Реально полезные варианты:

  • «когда это стало медленным»: скрипт замеряет время и возвращает 1, если p95 больше порога.
#!/usr/bin/env bash
./gradlew -q --offline :pay:jmh -PbenchFilter=FeeBenchmark > /tmp/b.txt || exit 125
NS=$(awk '/FeeBenchmark.calc/ {print $4}' /tmp/b.txt)
awk -v n="$NS" 'BEGIN{exit !(n > 850)}' && exit 1   # деградация
exit 0
  • «когда вырос размер jar»: test $(stat -c%s build/libs/pay.jar) -lt 45000000;
  • «когда в логах появился WARN»: поднять приложение через Testcontainers и грепнуть;
  • «когда изменился формат ответа API»: сравнить с эталонным JSON.

Ускорители:

  • git bisect start --first-parent HEAD v2026.02.14 — шагать только по слияниям;
  • git bisect start HEAD v2026.02.14 -- src/main/java/ru/bank/pay — ограничить путями: коммиты, не трогавшие эти пути, пропускаются;
  • git bisect replay /tmp/bisect.log — воспроизвести сессию (например, после ошибочного good);
  • git bisect terms --term-old=fast --term-new=slow — переименовать good/bad, когда «плохое» не является поломкой.

⚠️ Осторожно. Bisect ломается на трёх вещах: (1) shallow clone — история обрезана, git bisect не увидит good (см. 11.4); (2) коммиты, которые не собираются, — лечится кодом 125; (3) внешнее состояние: схема БД, кэш Gradle, версия зависимости из snapshot-репозитория. Перед bisect'ом фиксируйте окружение: --offline, локальный Testcontainers, откат миграций в скрипте.

6.7 shortlog и describe

git shortlog -sne v1.4.0..v1.5.0          # кто сколько коммитов, по авторам
git shortlog -sne --no-merges --since="3 months"
git shortlog v1.4.0..v1.5.0               # сгруппированный по авторам список тем — готовые релиз-ноты

git describe даёт человекочитаемое имя коммита относительно ближайшего тега — это стандартный источник версии для сборки:

$ git tag -a v1.0.0 -m "release 1.0.0"
$ git describe
v1.0.0
# после трёх коммитов:
$ git describe
v1.0.0-3-g58ae193        # тег-количество коммитов-g<хеш>
$ git describe --tags --always --dirty
v1.0.0-3-g58ae193-dirty  # --dirty: в рабочем дереве есть изменения
  • --tags — учитывать и лёгкие теги (по умолчанию только аннотированные);
  • --always — если тегов нет вообще, вернуть хеш (иначе команда падает, ломая сборку);
  • --dirty — обязательно в CI: артефакт, собранный из грязного дерева, не воспроизводим;
  • --match 'v[0-9]*' — игнорировать служебные теги.
// build.gradle.kts — версия из git
version = providers.exec {
    commandLine("git", "describe", "--tags", "--always", "--dirty", "--match", "v[0-9]*")
}.standardOutput.asText.get().trim().removePrefix("v")

⚠️ Осторожно. git describe в CI регулярно возвращает «fatal: no names found» или неверную версию, потому что исполнитель клонировал с --depth=1 и без тегов. В GitLab это лечится GIT_DEPTH: 0 и git fetch --tags; подробности — глава 54 (54-cicd-platforms.md).

7. Работа с удалёнными репозиториями

7.1 Remote и refspec

remote — именованный URL плюс правила отображения ссылок (refspec):

$ git remote -v
origin  git@git.bank.example:payments/pay-service.git (fetch)
origin  git@git.bank.example:payments/pay-service.git (push)

$ git config --get-all remote.origin.fetch
+refs/heads/*:refs/remotes/origin/*

Читается refspec так: <+><источник>:<назначение>. «Все ветки сервера (refs/heads/*) положи в мои refs/remotes/origin/*; + означает — разрешить неперемоточное обновление (force)».

Отсюда всё поведение:

  • remote-tracking ветки (origin/main) — это локальные копии, обновляемые только fetch/push. Они не «смотрят в сеть»; git log origin/main показывает состояние на момент последнего fetch.
  • Можно править refspec: например, забирать только нужные ветки на огромном репозитории:
git config remote.origin.fetch '+refs/heads/main:refs/remotes/origin/main'
git config --add remote.origin.fetch '+refs/heads/release/*:refs/remotes/origin/release/*'
  • Можно забирать то, что по умолчанию не приходит, — например, ссылки merge-request'ов GitLab:
git fetch origin '+refs/merge-requests/*/head:refs/remotes/origin/mr/*'
git switch --detach origin/mr/4711
  • Пуш с явным refspec решает задачи, которые иначе выглядят невозможными:
git push origin HEAD:refs/heads/feature/x        # запушить текущее в ветку с другим именем
git push origin :refs/heads/feature/x            # удалить ветку на сервере (пустой источник!)
git push origin --delete feature/x               # то же в понятной форме
git push origin <sha>:refs/heads/restored-main   # восстановить ветку из любого коммита
git push origin v1.5.0                           # запушить один тег
git push --follow-tags                           # запушить аннотированные теги, достижимые из пушимого

7.2 fetch и pull

git fetch — безопасная операция: скачивает объекты и обновляет refs/remotes/*. Ваши ветки, индекс и рабочее дерево не трогаются вообще. Её нельзя сделать «неправильно».

git pull = fetch + merge (по умолчанию) в текущую ветку. Отсюда проблемы:

  1. Неожиданные merge-коммиты. У вас два локальных коммита, на сервере три чужих — pull создаст merge-коммит «Merge branch 'main' of ...». Такие коммиты замусоривают историю, ломают --first-parent и никому ничего не сообщают.
  2. Конфликты в неподходящий момент. pull может остановиться посреди слияния, когда вы просто хотели посмотреть, что нового.
  3. Скрытая семантика. Что именно сделает pull, зависит от pull.rebase, pull.ff, branch.<name>.rebase и наличия upstream — то есть на разных машинах команды одна команда делает разное.

Рекомендуемая конфигурация (ставьте глобально всей командой):

git config --global pull.ff only        # pull = fetch + fast-forward, иначе отказ
git config --global fetch.prune true    # удалять origin/* для удалённых на сервере веток
git config --global fetch.pruneTags false
git config --global push.default simple # пушить только текущую ветку в одноимённую upstream
git config --global push.autoSetupRemote true  # (2.37+) первый push сам создаёт upstream

С pull.ff only команда git pull либо перематывает вперёд, либо честно отказывается, и вы сознательно выбираете git pull --rebase или git merge origin/main. Это ровно то поведение, которое нужно в команде.

Альтернатива — pull.rebase:

git config --global pull.rebase true          # pull = fetch + rebase
git config --global pull.rebase merges        # сохранять структуру слияний (= --rebase-merges)
git config --global rebase.autoStash true     # прятать локальные изменения на время rebase

pull --rebase хорош для линейной истории и плох тем, что автоматически переписывает ваши локальные коммиты — включая ситуацию, когда вы этого не ожидали (например, локальный merge-коммит будет расплющен без pull.rebase=merges).

Что стоит выработать как рефлекс:

git fetch --all --prune          # посмотреть, что в мире
git log --oneline --graph HEAD..@{u}    # что нового на сервере
git log --oneline --graph @{u}..HEAD    # что у меня не запушено
git status -sb                   # строка вида ## main...origin/main [ahead 2, behind 5]

7.3 Отслеживающие ветки и upstream

Upstream — конфигурация branch.<name>.remote + branch.<name>.merge, которая связывает локальную ветку с серверной. От неё зависят git status («ahead/behind»), git pull/git push без аргументов и сокращение @{u}.

git switch -c feature/x
git push -u origin feature/x        # -u = --set-upstream
git branch --set-upstream-to=origin/main main    # задать явно
git branch --unset-upstream
git branch -vv                       # увидеть привязки и расхождения

⚠️ Осторожно. «Ahead 3, behind 7» считается относительно вашей локальной копии origin/main, то есть относительно последнего fetch. Если вы не делали fetch три дня, git status показывает трёхдневной давности правду и уверенно врёт. Отсюда привычка: git fetch перед любым разговором о состоянии ветки. Автоматизировать можно через git maintenance start (раздел 11.2), который заводит фоновый prefetch.

7.4 --force-with-lease и --force-if-includes

git push --force означает «поставь ветку на сервере в это значение, что бы там ни было». Если коллега за эти пять минут запушил свои коммиты — они исчезают из ветки (объекты остаются, но ссылки нет).

git push --force-with-lease проверяет: текущее значение ветки на сервере должно совпадать с моей remote-tracking копией. Если кто-то пушил после вашего последнего fetch — push отклоняется.

Документация (git-push, проверено 2026-09-22) формулирует это как «взять lease на ref без явного блокирования» и там же честно предупреждает: опция «interacts very badly with anything that implicitly runs git fetch on the remote» в фоне.

Вот почему --force-with-lease иногда не спасает. Ваша remote-tracking ссылка обновляется не только вашим явным git fetch, но и:

  • IDE (IntelliJ IDEA по умолчанию периодически делает fetch — см. главу 57);
  • git maintenance prefetch;
  • git pull кого-то из ваших же скриптов/хуков;
  • плагином статусной строки в shell.

Если фоновый fetch подтянул чужой коммит, ваша копия origin/feature уже «знает» о нём, lease совпадёт, и force-push его затрёт — ровно то, от чего вы защищались.

Два уровня защиты:

1. Явное ожидаемое значение:

BASE=$(git rev-parse origin/feature/x)     # зафиксировали, что видим
# ... rebase ...
git push --force-with-lease=feature/x:$BASE origin feature/x

2. --force-if-includes (Git 2.30+). Документация: «Force an update only if the tip of the remote-tracking ref has been integrated locally… verifies if the tip of the remote-tracking ref is reachable from one of the 'reflog' entries». То есть проверяется не «совпадает ли», а «видел ли я эту верхушку и включил ли её в свою работу». Фоновый fetch этой проверке не помогает — он обновил ссылку, но вы её не интегрировали.

git push --force-with-lease --force-if-includes

Практическая рекомендация: заведите псевдоним и пользуйтесь только им.

git config --global alias.pushf 'push --force-with-lease --force-if-includes'

И помните главное: настоящая защита — на сервере. Protected branches с запретом force-push в main/release/* делают весь этот класс аварий невозможным (глава 54, 54-cicd-platforms.md).

7.5 Удаление влитых веток

git branch -d feature/x            # удалить, только если влита (в upstream или HEAD)
git branch -D feature/x            # удалить принудительно
git push origin --delete feature/x # удалить на сервере
git fetch --prune                  # убрать протухшие origin/*
git remote prune origin            # то же явно
git remote prune origin --dry-run  # посмотреть, что будет удалено

Массовая чистка влитых веток (безопасный вариант — сначала посмотреть список):

git fetch --prune
git branch --merged origin/main | grep -vE '^\*|main|release/' | xargs -r git branch -d

Ветки, оставшиеся без серверного аналога (gone):

git branch -vv | awk '/: gone]/ {print $1}' | xargs -r git branch -D

7.6 Несколько remote и форки

Модель «форк + upstream» обязательна в open source и встречается в банках для vendor-библиотек:

git clone git@git.bank.example:my-team/spring-boot-fork.git
git remote add upstream https://github.com/spring-projects/spring-boot.git
git fetch upstream --tags
git switch -c fix/PAY-5001 upstream/3.5.x
# ... правка ...
git push -u origin fix/PAY-5001

Полезные приёмы:

git remote set-url --push upstream DISABLED   # защита от случайного пуша в upstream
git remote update --prune                     # fetch по всем remote
git fetch upstream 'refs/tags/v3.5.*:refs/tags/upstream/v3.5.*'   # теги в своё пространство имён

Обновление форка (частая операция, частая ошибка): не сливать upstream/main в свой main, а перематывать:

git fetch upstream
git switch main
git merge --ff-only upstream/main    # откажется, если у вас есть свои коммиты в main — и это правильно
git push

Свои патчи держите в отдельной ветке и ребейзите на новый upstream — тогда вы всегда знаете, что именно вы изменили относительно вендора (git log upstream/main..HEAD), и умеете это предъявить безопасности при аудите зависимостей (глава 42, 42-appsec-oauth-keycloak.md).

8. Стратегии ветвления

Стратегия ветвления — не вопрос вкуса, а функция от трёх вещей: как часто вы выкатываете, сколько версий поддерживаете одновременно и какие согласования требует регулятор. Всё остальное — детали. Процессная часть (гейты, окружения, feature flags как практика) — в главе 53 (53-cicd-process.md); здесь только Git-механика и критерии выбора.

8.1 Trunk-based development

Trunk-based development — это модель ветвления, в которой у репозитория одна долгоживущая ветка (main, она же trunk). Фича-ветки живут часы, максимум день-два, и вливаются в trunk. Релиз — либо прямо из trunk (continuous deployment), либо короткоживущей release-веткой, которая только фиксирует состояние и принимает cherry-pick'и срочных исправлений.

Что физически требуется, чтобы это работало:

  1. Feature flags. Незаконченная фича вливается в trunk выключенной. Без этого невозможно вливать по чуть-чуть. Это самая дорогая часть: флаги нужно заводить, выкатывать, а потом убирать — иначе через год у вас 300 мёртвых флагов и комбинаторный взрыв в тестах.
  2. Быстрый CI. Если pipeline идёт 40 минут, вливать 5 раз в день нельзя. Цель — 10 минут до «можно сливать».
  3. Дисциплина «trunk всегда зелёный». Красный trunk блокирует всю команду, поэтому нужны обязательные проверки до слияния (merge trains в GitLab, merge queue в GitHub — глава 54).
  4. Маленькие изменения. MR на 2000 строк несовместим с trunk-based физически: он не проходит ревью за день.

Git-следствия: почти нет долгих веток → почти нет тяжёлых конфликтов → rebase дешёвый → --first-parent даёт идеальную историю релиза.

8.2 GitHub Flow

main всегда готова к выкатке; на каждую задачу — ветка; PR; ревью; merge в main; деплой. Без develop, без релизных веток.

Это trunk-based с чуть более длинными ветками и без обязательных feature flags: ветка живёт до готовности фичи (дни). Подходит веб-сервисам с непрерывной поставкой и одной версией в проде.

Слабое место — ровно то, ради чего его берут: нет места, куда «отложить» готовый, но не разрешённый к выкату код. Как только появляется релизное окно раз в две недели, GitHub Flow либо вырождается в trunk-based с флагами, либо обрастает release-ветками.

8.3 GitLab Flow

GitHub Flow плюс ветки окружений (main → staging → production) или релизные ветки (release/2026.03), куда изменения попадают только через merge из main (принцип «upstream first»).

Ключевое правило: код всегда сначала в main, потом вниз по течению. Срочное исправление делается в main и cherry-pick'ается в production — а не наоборот. Это снимает главную беду банковских процессов, когда фикс в релизе забывают перенести в основную ветку.

Подходит, когда: деплой не автоматический (нужен человек/окно), но версий в проде одна-две.

8.4 GitFlow и позиция его автора

Классика 2010 года: main (только релизы, теги), develop (интеграция), feature/* от develop, release/* для стабилизации, hotfix/* от main с двойным merge (в main и develop).

Автор, Vincent Driessen, в 2020 году добавил к статье примечание (nvie.com, проверено 2026-09-22): web-приложения обычно поставляются непрерывно, не откатываются и не требуют поддержки нескольких версий «в дикой природе»; для команд с continuous delivery он прямо советует взять что-то гораздо более простое — вроде GitHub Flow — вместо того, чтобы «впихивать git-flow». GitFlow остаётся уместным, если ПО явно версионируется или если нужно поддерживать несколько версий одновременно.

Где GitFlow всё ещё правильный ответ: дистрибутивы, коробочные продукты, библиотеки с LTS-ветками, встроенное ПО, прошивки терминалов, банковские АБС-модули, поставляемые заказчикам версиями.

Где он приносит только боль: один сервис в Kubernetes, деплоящийся из main. Здесь develop становится «второй main», отстающей и конфликтующей, а release/* — местом, где живут расхождения.

8.5 Release-ветки и поддержка нескольких версий

Если вы поддерживаете 2026.03 у одного клиента и 2026.06 у другого, ветки release/* — не вопрос моды, а необходимость. Механика:

main ────●────●────●────●────●────●───►
          \              \
           ● release/2026.03 (тег v2026.03.0, .1, .2)
                          \
                           ● release/2026.06

Правила, без которых это разваливается:

  1. Разработка только в main. В релизную ветку попадают исключительно cherry-pick'и (с -x) и точечные фиксы, которых физически не может быть в main (например, откат несовместимой миграции).
  2. git cherry в конвейере — проверка, что всё из релизной есть в main (код из 4.5).
  3. Теги на каждую поставку, аннотированные и подписанные: git tag -s v2026.03.2 -m "...".
  4. Срок жизни ветки объявлен заранее. Ветка, живущая год, — это форк, который надо либо сливать, либо убивать.
  5. merge --no-ff из main в релизную не делают (принесёт всё, включая незарелизенное). Только cherry-pick.

8.6 Стек зависимых PR (stacked PRs)

Стек зависимых PR (stacked PRs) — это цепочка небольших запросов на слияние, каждый из которых построен поверх предыдущего. К нему приходят, когда задача слишком велика для одного MR, но разбить её на независимые части нельзя, потому что вторая часть опирается на первую. Строится стек так:

main ← part1/рефакторинг ← part2/новый API ← part3/интеграция

Каждый MR проходит ревью отдельно, целевая ветка каждого — предыдущий MR, а не main. Когда part1 вливается, остальные нужно перебазировать.

Что даёт Git из коробки: git rebase --update-refs (раздел 3.5) и rebase.updateRefs=true — один rebase верхней ветки двигает весь стек. Этого достаточно для стека из 2–4 веток.

Что не даёт: автоматического перенацеливания MR в хостинге, пересчёта «что изменилось с прошлого ревью», автоматического слияния стека по очереди. Для этого берут внешние инструменты — Graphite, Sapling (форк Git-workflow от Meta), git-branchless, spr, ghstack. В банке с закрытым контуром их обычно нет, и стек из более чем трёх веток становится ручной работой. Практический предел без инструментов — три ветки.

Альтернатива стеку в банковской реальности: договориться о слиянии «неполных, но выключенных» частей в main за feature flag. Обычно это дешевле.

Stacked PRs дни средняя (rebase стека) нет высокая

8.8 Долгоживущие ветки в банковской разработке

В финтехе почти всегда есть то, чего нет в статьях про trunk-based: релизное окно раз в две недели, согласование с ИБ и комплаенсом, регрессионное тестирование на отдельном стенде, «заморозка» перед отчётным периодом и невозможность разворачивать в пятницу. Следствие — ветки живут дольше, чем хотелось бы. Это надо принять и минимизировать ущерб.

1. Регулярная синхронизация с main — ежедневно, а не «перед слиянием».

# в фича-ветке, каждое утро
git fetch origin
git rebase origin/main          # пока ветку никто не забрал
# или, если ветка общая:
git merge origin/main

Стоимость конфликта растёт нелинейно: разрешить расхождение в 3 коммита и в 200 — это разные задачи. Правило «в понедельник утром все ребейзятся» снимает 80 % боли.

2. rerere включён у всех. Для долгоживущей ветки это буквально разница между «15 минут в неделю» и «полдня».

3. Feature toggles вместо ветки. Даже в банке можно влить выключенный код. Ветка, которая не сливается, — риск; выключенный код в main — управляемый риск. Требует дисциплины по удалению флагов (глава 53).

4. Ветка ограничена по сроку явным правилом. Например: «ветка старше 10 рабочих дней обсуждается на дейли». Автоматизируется скриптом:

git for-each-ref --format='%(refname:short)|%(committerdate:unix)|%(authorname)' refs/remotes/origin \
 | while IFS='|' read -r ref ts author; do
     age=$(( ( $(date +%s) - ts ) / 86400 ))
     [ "$age" -gt 10 ] && echo "$ref — $age дн., $author"
   done

5. Дробить задачу, а не ветку. Рефакторинг отдельно от фичи, миграции отдельно от кода (глава 19, 19-schema-design-migrations.md), контракты API — первым MR. Это единственный способ уменьшить конфликтность, который работает всегда.

6. Merge-направление зафиксировано. «Из main в фичу — сколько угодно; из фичи в main — только через MR». Никаких локальных git merge feature && git push origin main.

9. Соглашения о коммитах и настройки репозитория

9.1 Conventional Commits

Формат (conventionalcommits.org v1.0.0, проверено 2026-09-22):

<type>[optional scope]: <description>

[optional body]

[optional footer(s)]

Связь с SemVer, зафиксированная спецификацией: fix → PATCH, feat → MINOR, BREAKING CHANGE (в любом типе) → MAJOR. Ломающее изменение обозначается либо футером BREAKING CHANGE: ..., либо восклицательным знаком перед двоеточием — и тогда футер можно опустить.

feat(pay)!: комиссия рассчитывается по тарифу продукта

Раньше ставка была константой 0.5%. Теперь берётся из справочника
тарифов; при отсутствии тарифа операция отклоняется, а не считается
по нулю — это требование комплаенса от 2026-02-10.

BREAKING CHANGE: PaymentRequest.fee больше не заполняется клиентом
Refs: PAY-4711
Co-authored-by: Anna Smirnova <a.smirnova@bank.example>

Типы, которые реально используются: feat, fix, perf, refactor, docs, test, build, ci, chore, style, revert.

Что это даёт на практике (иначе это просто бюрократия):

  • автогенерация changelog — git-cliff, conventional-changelog, semantic-release, release-please. Релиз-ноты перестают быть ручной работой перед выкатом;
  • автоматический расчёт версии — по типам коммитов с прошлого тега;
  • фильтрация: git log --grep '^fix' --oneline v1.4.0..v1.5.0 — что именно чинили в релизе;
  • быстрый ответ на «было ли ломающее изменение»: git log --grep 'BREAKING CHANGE' v1.4.0..v1.5.0.

Проверка формата — в CI, а не только в хуке (см. 10.2):

# commitlint в pipeline: проверяем только коммиты MR
git log --format=%s origin/main..HEAD | grep -vE \
  '^(feat|fix|perf|refactor|docs|test|build|ci|chore|style|revert)(\([a-z0-9-]+\))?!?: .{1,72}$' \
  && { echo "Нарушен формат Conventional Commits"; exit 1; }

9.2 Тело сообщения коммита

Заголовок отвечает на «что», тело — на «зачем». «Что» видно из diff'а; «зачем» не восстанавливается никогда. Через год единственный источник ответа «почему здесь стоит эта странная проверка» — тело коммита или ADR.

Плохо: «Исправил NPE». Хорошо:

fix(pay): не считать комиссию для закрытых продуктов

FeeService брал тариф из ProductRef без проверки статуса.
У закрытых продуктов тариф удаляется ночным джобом (см. PAY-3310),
поэтому у платежей по закрытому продукту падал NPE.

Решение: проверяем статус до расчёта и отклоняем операцию
с кодом PRODUCT_CLOSED. Альтернатива «считать по нулю»
отклонена комплаенсом: нулевая комиссия = недополученный доход
и расхождение с тарифным справочником.

Refs: PAY-4711

Правила оформления: заголовок ≤ 72 символов, повелительное наклонение («добавить», «исправить»), пустая строка, тело с переносами по 72 символа (иначе git log в терминале нечитаем), футеры в конце.

9.3 Атомарность коммитов

Атомарный коммит = одно логическое изменение, проект собирается и тесты проходят. Критерий проверки: «можно ли этот коммит отревертить в одиночку, не сломав ничего». Если нет — коммит не атомарен.

Зачем это нужно инженерно, а не эстетически: атомарные коммиты делают работоспособными bisect (каждая точка проверяема), revert (можно откатить одно), blame (строка привязана к осмысленному изменению) и cherry-pick (перенос фикса без волочения половины фичи).

Инструменты достижения:

git add -p                  # по ханкам
git add -p <file>           # с выбором s (split), e (edit hunk)
git restore --staged -p     # обратно, тоже по ханкам
git stash push -p           # спрятать часть изменений и проверить, что остаток собирается
git commit -v               # видеть diff в редакторе сообщения — лучший способ поймать лишнее

Отдельный приём для разбора «кучи»: сложить всё в один wip-коммит, затем git rebase -i с edit, git reset HEAD^ и разложить по add -p (см. 3.4).

9.4 Трейлеры сообщения коммита

Футеры вида Ключ: значение в конце сообщения — машиночитаемые метаданные. Git знает о них: git interpret-trailers умеет их добавлять и парсить, а git log --format='%(trailers:key=Co-authored-by,valueonly)' — извлекать.

Употребительные:

Trailer Зачем
Co-authored-by: Имя <email> парное программирование; хостинги показывают обоих авторов
Signed-off-by: Имя <email> DCO — подтверждение прав на код (git commit -s)
Refs: PAY-4711, Closes: #123 связь с задачей; Jira/GitLab подхватывают
Reviewed-by:, Tested-by: принято в ядре Linux, полезно при формальном аудите
Cherry-picked-from: / (cherry picked from commit ...) добавляется cherry-pick -x
Fixes: <sha> ссылка на коммит, который чинится 
git commit --trailer "Refs: PAY-4711" --trailer "Co-authored-by: Anna Smirnova <a.smirnova@bank.example>"
git config trailer.refs.key "Refs: "

9.5 Подписывание коммитов: GPG и SSH

Подпись отвечает на вопрос «этот коммит действительно создал тот, кто указан в author». Без неё поле author — просто строка, которую любой может подделать (git -c user.email=ceo@bank.example commit). В регулируемой среде это существенно: подписи + protected branches дают доказуемую цепочку «кто внёс изменение».

GPG — классика, но операционно тяжёлая: генерация ключа, выгрузка публичной части на сервер, срок действия, отзыв, gpg-agent, pinentry, проблемы в контейнерах и на Windows.

SSH-подписи (Git 2.34+) проще на порядок: у вас уже есть SSH-ключ для доступа к репозиторию — им же можно подписывать. Конфигурация (Documentation/config/gpg.adoc, проверено 2026-09-22; gpg.format по умолчанию openpgp, допустимы x509 и ssh):

git config --global gpg.format ssh
git config --global user.signingkey ~/.ssh/id_ed25519.pub
git config --global commit.gpgsign true
git config --global tag.gpgsign true

Проверка подписей локально требует файла доверенных подписантов — «A file containing ssh public keys which you are willing to trust. The file consists of one or more lines of principals followed by an ssh public key»:

# ~/.config/git/allowed_signers
i.petrov@bank.example ssh-ed25519 AAAAC3Nza...
a.smirnova@bank.example ssh-ed25519 AAAAC3Nza...

git config --global gpg.ssh.allowedSignersFile ~/.config/git/allowed_signers
git log --show-signature -1
git verify-commit HEAD
git log --format='%h %G? %an %s'     # %G? : G=good, B=bad, U=untrusted, N=нет подписи, E=ошибка

Отзыв ключей — gpg.ssh.revocationFile (SSH KRL либо список отозванных публичных ключей); подписи отозванным ключом становятся некорректными.

Практика проверки в вашем репозитории и в CI:

# в пайплайне: все коммиты MR подписаны?
git log --format='%H %G?' origin/main..HEAD | awk '$2!="G" {print "Неподписанный коммит: "$1; bad=1} END{exit bad}'

Обратите внимание: в моём тестовом репозитории подпись включена глобально, и это видно прямо в объекте коммита — поле gpgsig с телом -----BEGIN SSH SIGNATURE----- идёт после committer и перед сообщением. Подпись покрывает весь остальной коммит, поэтому любая операция, пересоздающая коммит (rebase, amend, cherry-pick), уничтожает подпись, если вы не подписываете заново. Для rebase есть git rebase --exec 'git commit --amend --no-edit -S' и опция rebase.gpgSign/-S у самого rebase. Это же причина, по которой серверный squash-merge даёт коммит, подписанный хостингом, а не автором.

Ограничения, о которых надо знать:

  • подпись покрывает коммит, а не «работу»: подписанный коммит с чужим кодом внутри — валиден;
  • GitHub/GitLab показывают «Verified» на основании загруженных публичных ключей, а не вашего allowed_signers;
  • Sigstore/gitsign — альтернатива, где вместо долгоживущего ключа используются короткоживущие сертификаты, выданные по OIDC-логину, с записью в прозрачный журнал Rekor. Удобно в CI (нет секрета, который можно украсть), но требует доверия к внешней инфраструктуре и доступности Fulcio/Rekor — в закрытом контуре банка обычно неприменимо без собственного развёртывания. ⚠️ Детали и статус проекта не проверялись при подготовке главы.

9.6 Файл .gitattributes

Файл, который недооценивают. Он управляет тем, как Git обрабатывает пути — и хранится в репозитории, то есть действует у всех.

# нормализация переводов строк: в репозитории всегда LF
* text=auto

# явные правила для тех, кто требует конкретного окончания
*.sh      text eol=lf
*.bat     text eol=crlf
*.cmd     text eol=crlf
gradlew   text eol=lf

# бинарники: не diff'ить, не мержить, не трогать переводы строк
*.p12     binary
*.jks     binary
*.pdf     binary
*.png     binary
*.xlsx    binary

# драйверы diff для осмысленных ханков и `log -L :функция:файл`
*.java    diff=java
*.kt      diff=kotlin
*.py      diff=python
*.md      diff=markdown

# генерируемые файлы: всегда берём свою версию при слиянии
src/main/generated/**   merge=ours
# (требует один раз настроить драйвер:
#  git config merge.ours.driver true)

# классификация языков на хостинге и скрытие сгенерированного из diff'ов
*.sql          linguist-detectable
src/generated/* linguist-generated=true
docs/*         linguist-documentation

# не показывать огромный lock-файл в diff по умолчанию
package-lock.json  -diff
gradle/verification-metadata.xml  -diff

Пояснения к неочевидному:

  • binary — это сокращение для -text -diff -merge: не нормализовать переводы строк, не пытаться показать diff, не пытаться слить текстово (конфликт бинарника всегда «выбери одну из версий»).
  • -diff на текстовом файле оставляет нормализацию, но делает файл «бинарным» для показа. Удобно для lock-файлов и снимков: не засоряет ревью.
  • merge=ours на генерируемых файлах убирает бессмысленные конфликты. Драйвер ours надо один раз объявить (git config merge.ours.driver true) — иначе атрибут ничего не делает; это классическая ловушка.
  • export-ignore исключает пути из git archive (сборка дистрибутива без тестов и CI-конфигов).
  • filter=lfs diff=lfs merge=lfs -text — то, что git lfs track дописывает сам (раздел 11.5).

9.7 .gitignore и проверка через check-ignore

Порядок правил и приоритет источников путают всех. Git читает (от низшего приоритета к высшему): $XDG_CONFIG_HOME/git/ignore (глобальный), .git/info/exclude (локальный, в репозиторий не попадает), .gitignore в корне, .gitignore в подкаталогах (чем глубже — тем выше приоритет), и внутри файла — последнее совпавшее правило побеждает.

Отладка — одной командой:

$ git check-ignore -v target/app.jar debug.log important.log
.gitignore:1:target/    target/app.jar
.gitignore:2:*.log  debug.log
.gitignore:3:!important.log important.log

Вывод даёт файл, номер строки и само правило, которое приняло решение. Это закрывает вопрос «почему мой файл игнорируется» за три секунды вместо получаса чтения.

Два правила, которые надо помнить наизусть:

  1. .gitignore не действует на уже отслеживаемые файлы. Добавили application-local.yml в ignore, а он всё равно в diff'ах — потому что он уже в индексе. Лечение: git rm --cached application-local.yml + коммит.
  2. Нельзя разигнорировать файл внутри игнорируемого каталога. logs/ + !logs/keep.txt не сработает: Git не заходит внутрь исключённого каталога. Нужно logs/* + !logs/keep.txt.

Типовой .gitignore для Java-сервиса:

# сборка
target/
build/
out/
!gradle/wrapper/gradle-wrapper.jar
.gradle/

# IDE
.idea/
*.iml
.vscode/
# но общие настройки инспекций — коммитим
!.idea/inspectionProfiles/

# локальное окружение и секреты
*.env
.env.local
application-local.yml
*.p12
*.jks
*.pem

# логи и дампы
*.log
*.hprof
heapdump*

9.8 Концы строк: core.autocrlf и text=auto

Проблема живая: разработчики на Windows, сборка в Linux-контейнере, скрипты и property-файлы, чувствительные к окончаниям строк.

Механика. core.autocrlf — локальная настройка:

  • true (типично на Windows): при add CRLF → LF, при checkout LF → CRLF;
  • input (типично на Linux/macOS): при add CRLF → LF, при checkout — как есть;
  • false: не трогать ничего.

.gitattributes с * text=auto — репозиторная настройка, которая говорит: «в базе объектов всегда LF; при checkout — по платформе/core.eol». Она главнее и не зависит от того, что каждый разработчик настроил у себя.

⚠️ Осторожно. Когда я создавал тестовый репозиторий для этой главы, Git честно предупреждал на каждом add: warning: in the working copy of 'settings.gradle', LF will be replaced by CRLF the next time Git touches it. Это сигнал того, что нормализация работает: в репозитории LF, в рабочем дереве CRLF. Опасно другое — когда файлы уже лежат в базе с CRLF. Тогда любое добавление text=auto превращает следующий коммит в «изменены все строки всех файлов»: катастрофа для blame, ревью и всех открытых веток.

Правильная последовательность внедрения нормализации:

# 1. добавили .gitattributes с * text=auto — отдельным коммитом
git add .gitattributes && git commit -m "chore: нормализация переводов строк"

# 2. перенормализовали ВЕСЬ репозиторий одним коммитом
git add --renormalize .
git commit -m "chore: renormalize line endings (см. .git-blame-ignore-revs)"

# 3. SHA этого коммита — в .git-blame-ignore-revs
# 4. всем открытым веткам: git rebase (или merge -X renormalize)

Дополнительные меры:

  • git config --global core.eol native (по умолчанию) — что писать в рабочее дерево;
  • проверка в CI: git diff --exit-code --stat после git add --renormalize . — падает, если кто-то отправил в коммит CRLF;
  • для Windows-разработчиков не core.autocrlf=true, а false + .gitattributes: меньше сюрпризов;
  • .editorconfig синхронизируется с .gitattributes, иначе IDE вернёт CRLF обратно.

Симптомы, по которым узнаётся проблема: git diff показывает весь файл изменённым; ^M в конце строк; shell-скрипт в контейнере падает с bad interpreter: /bin/bash^M; тест сравнения строк падает только на машине одного разработчика.

10. Хуки и автоматизация

10.1 Клиентские хуки

Хуки — исполняемые файлы в .git/hooks/. При установке Git кладёт туда примеры с суффиксом .sample:

$ ls .git/hooks | head -5
applypatch-msg.sample
commit-msg.sample
fsmonitor-watchman.sample
post-update.sample
pre-applypatch.sample

Клиентские хуки, которые реально используют:

Хук Когда Типичное применение Может отменить операцию
pre-commit до формирования коммита формат, линтеры, поиск секретов, быстрые тесты да (ненулевой код)
prepare-commit-msg до открытия редактора подставить номер задачи из имени ветки да
commit-msg после ввода сообщения проверка Conventional Commits да
post-commit после коммита уведомления, статистика нет
pre-push до отправки на сервер прогон тестов, запрет push в main да
pre-rebase до rebase запрет rebase защищённых веток да
post-checkout, post-merge после переключения/слияния пересборка, ./gradlew --write-locks нет

Почему это не гарантия. Каталог .git/hooks не версионируется и не приходит при клонировании. Любой разработчик может не установить хуки вовсе, а установивший — обойти их одним флагом:

git commit --no-verify     # пропускает pre-commit и commit-msg
git push --no-verify       # пропускает pre-push

Отсюда правило: клиентские хуки — это удобство (быстрая обратная связь), а не контроль. Всё, что должно выполняться обязательно, проверяется на сервере: в CI-конвейере и в настройках защищённых веток (глава 54, 54-cicd-platforms.md).

10.2 Распространение хуков в команде

Хуки Git лежат в .git/hooks и в репозиторий не попадают, поэтому, чтобы у всей команды работали одни и те же проверки, их приходится распространять отдельно. Рабочих способов три.

1. core.hooksPath + каталог в репозитории — самый простой и без зависимостей:

# .githooks/pre-commit (коммитится, chmod +x)
#!/usr/bin/env bash
set -e
./gradlew -q --offline spotlessCheck || {
  echo "Формат не соответствует. Запусти ./gradlew spotlessApply"; exit 1; }

# однократно, в onboarding-скрипте или в задаче Gradle
git config core.hooksPath .githooks

Автоматизировать установку можно задачей сборки, которая выполняется при любом запуске Gradle:

// build.gradle.kts
tasks.register<Exec>("installGitHooks") {
    commandLine("git", "config", "core.hooksPath", ".githooks")
}
tasks.named("build") { dependsOn("installGitHooks") }

⚠️ Осторожно. core.hooksPath отключает .git/hooks целиком — если у вас там лежали локальные хуки (или их положил Git LFS!), они перестанут работать. Git LFS ставит post-checkout, post-commit, post-merge, pre-push; при переезде на core.hooksPath их надо перенести (git lfs install --force после настройки).

2. pre-commit framework (pre-commit.com, Python) — декларативный .pre-commit-config.yaml, автоматическая установка инструментов в изолированные окружения, большой набор готовых хуков (включая detect-private-key, check-merge-conflict, gitleaks). Плюс: единая конфигурация, работает и в CI (pre-commit run --all-files). Минус: требует Python на машине разработчика — в закрытом контуре это иногда проблема.

3. lefthook / husky — lefthook (Go, один бинарник, YAML-конфиг, умеет параллельный запуск и фильтрацию по glob) в Java-командах удобнее, чем husky (требует Node.js и package.json).

# lefthook.yml
pre-commit:
  parallel: true
  commands:
    format:
      glob: "*.{java,kt}"
      run: ./gradlew -q --offline spotlessCheck
    secrets:
      run: gitleaks protect --staged --no-banner
commit-msg:
  commands:
    conventional:
      run: grep -qE '^(feat|fix|perf|refactor|docs|test|build|ci|chore|style|revert)(\(.+\))?!?: ' {1}

Что не надо класть в pre-commit: всё, что дольше 5 секунд. Разработчик, ждущий полминуты на каждый коммит, начнёт писать --no-verify рефлекторно, и вы потеряете даже быстрые проверки. Тяжёлые вещи — в pre-push (и то опционально) и в CI.

10.3 Серверные хуки и защищённые ветки

На стороне сервера работают pre-receive, update, post-receive. Их нельзя обойти с клиента — это и есть настоящий контроль. В managed-хостингах (GitLab, Bitbucket Cloud, GitHub) прямого доступа к ним нет, но есть эквиваленты:

  • Protected branches: запрет прямого push, запрет force-push, запрет удаления ветки, список ролей, которым разрешён merge.
  • Push rules (GitLab Premium): регулярное выражение на сообщение коммита, запрет коммитов от неавторизованных email, запрет файлов по маске и по размеру, проверка подписи, «commit author must be a GitLab user».
  • Merge request approvals: минимум N апрувов, обязательный апрув владельцев кода (CODEOWNERS), запрет самоапрува.
  • Required pipelines/status checks: без зелёного конвейера merge невозможен.
  • Signed commits required.

Для самостоятельно развёрнутого Git (bare-репозиторий, Gitolite, Gerrit) pre-receive выглядит так:

#!/usr/bin/env bash
# pre-receive: запрет force-push в release/* и проверка формата сообщений
while read -r oldrev newrev refname; do
  case "$refname" in
    refs/heads/release/*|refs/heads/main)
      if [ "$oldrev" != "0000000000000000000000000000000000000000" ] &&
         ! git merge-base --is-ancestor "$oldrev" "$newrev"; then
        echo "Неперемоточное обновление $refname запрещено" >&2
        exit 1
      fi
      ;;
  esac
  for c in $(git rev-list "$oldrev".."$newrev" 2>/dev/null); do
    msg=$(git log -1 --format=%s "$c")
    echo "$msg" | grep -qE '^(feat|fix|perf|refactor|docs|test|build|ci|chore)(\(.+\))?!?: ' || {
      echo "Коммит $c: нарушен формат Conventional Commits: $msg" >&2; exit 1; }
  done
done

Обратите внимание на проверку oldrev == 0000... — так выглядит создание новой ветки, для неё сравнение предков бессмысленно.

Проверка формата коммитов в CI (работает на любом хостинге, не требует прав):

# .gitlab-ci.yml (фрагмент; подробности пайплайнов — глава 54)
commit-lint:
  stage: test
  script:
    - git fetch origin $CI_MERGE_REQUEST_TARGET_BRANCH_NAME
    - |
      bad=$(git log --format='%H %s' origin/$CI_MERGE_REQUEST_TARGET_BRANCH_NAME..HEAD |
            grep -vE ' (feat|fix|perf|refactor|docs|test|build|ci|chore|style|revert)(\([a-z0-9-]+\))?!?: ' || true)
      [ -z "$bad" ] || { echo "$bad"; exit 1; }
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"

10.4 Защита от секретов в репозитории

Секрет в Git — это не «файл, который надо удалить». Это объект в базе, который скопировался во все клоны, форки и кэши хостинга. Поэтому стратегия двухслойная: не пускать и, если пустили, — правильно реагировать.

Не пускать:

  1. .gitignore для типовых файлов (*.p12, *.jks, .env, application-local.yml).
  2. Сканер в pre-commit: gitleaks protect --staged (проверяет только то, что в индексе — быстро) или trufflehog git file://. --since-commit HEAD.
  3. Сканер в CI на каждый MR — обязательный гейт: gitleaks detect --source . --redact --exit-code 1. Именно он является гарантией, в отличие от хука.
  4. Периодический полный скан всей истории (ночной заданий): gitleaks detect --log-opts="--all".
  5. Организационно: секреты в Vault/k8s Secrets/переменных CI, а не в репозитории (главы 42 и 54).

Отличие инструментов: gitleaks — быстрый, регулярные выражения + энтропия, удобен как гейт; trufflehog дополнительно верифицирует найденные ключи (пробует их на живых API) и потому даёт меньше ложных срабатываний, но медленнее и требует сетевого доступа.

Ложные срабатывания гасятся файлом .gitleaks.toml с allowlist — не отключением проверки целиком.

10.5 Процедура при утечке секрета

Порядок действий именно такой, менять нельзя.

Шаг 1 (немедленно, до любых операций с Git): ротация. Отозвать и перевыпустить ключ/пароль/токен. Всё остальное — уборка; безопасность обеспечивает только ротация. Если утёк ключ подписи или ключ к HSM — процедура инцидента по регламенту ИБ.

Почему это первично: секрет уже в клонах у 15 разработчиков, в кэше CI, в артефактах сборки, в бэкапах репозитория, в форках и в поисковых индексах, если репозиторий был публичным. Вы физически не можете это отозвать. Вы можете отозвать только сам секрет.

Шаг 2: зафиксировать факт. Завести инцидент, записать: какой секрет, с какого коммита, в каких ветках и тегах, когда обнаружен, кто имел доступ.

git log --all --oneline -S'PRIVATE KEY' -- .          # где появился
git log --all --diff-filter=A --oneline -- src/main/resources/keystore.p12
git rev-list --objects --all | grep keystore.p12      # все версии объекта

Шаг 3: переписать историю. Инструмент — git filter-repo, а не filter-branch. Сам Git при вызове filter-branch печатает (проверено на 2.55):

WARNING: git-filter-branch has a glut of gotchas generating mangled history
     rewrites.  Hit Ctrl-C before proceeding to abort, then use an
     alternative filtering tool such as 'git filter-repo'
     (https://github.com/newren/git-filter-repo/) instead.

filter-repo (github.com/newren/git-filter-repo, проверено 2026-09-22) — один Python-скрипт, требует Git ≥ 2.36 и Python ≥ 3.6, работает на порядки быстрее и «detect[s] and bail[s] if we're not in a fresh clone» без --force — то есть намеренно заставляет работать на свежем клоне, чтобы ошибку можно было откатить, просто выбросив каталог.

# на СВЕЖЕМ зеркальном клоне
git clone --mirror git@git.bank.example:payments/pay-service.git
cd pay-service.git

# удалить файл из всей истории
git filter-repo --invert-paths --path src/main/resources/keystore.p12

# или заменить строку во всех коммитах
printf 'AKIAIOSFODNN7EXAMPLE==>***REMOVED***\n' > /tmp/replacements.txt
git filter-repo --replace-text /tmp/replacements.txt

# или выбросить всё крупнее 10 МБ (см. 11.1)
git filter-repo --strip-blobs-bigger-than 10M

filter-repo намеренно удаляет remote origin после работы (чтобы вы не запушили случайно «наполовину») — это та самая «clean separation… prevent accidental re-pushing of old stuff». Возвращаете его вручную:

git remote add origin git@git.bank.example:payments/pay-service.git
git push --force --all
git push --force --tags

BFG Repo-Cleaner — альтернатива на JVM (bfg --delete-files keystore.p12, bfg --replace-text passwords.txt). Быстрее и проще в типовых задачах, но по умолчанию не трогает верхушки веток (защита «текущее состояние — ваше дело») и менее гибок. В банке, где Java есть всегда, а Python не везде, BFG часто практичнее.

Шаг 4: координация команды. После force-push у всех локальные клоны указывают на старые объекты. Инструкция рассылается заранее:

# всем разработчикам
git fetch origin
git switch main
git reset --hard origin/main
# для своих веток — перебазировать на новую историю:
git rebase --onto origin/main <старый-sha-базы> feature/x
# самое надёжное: сохранить патчи и переклонировать
git format-patch origin/main --stdout > /tmp/my-work.patch
# ... заново клонировать ... git am /tmp/my-work.patch

Незапушенные ветки, основанные на старой истории, — главный источник рецидива: разработчик пушит свою ветку, и старые объекты возвращаются на сервер. Поэтому на время операции ветки блокируются (protected/read-only), а после — запускается повторный скан.

Шаг 5: остаточные копии. Секрет остаётся:

  • в форках — хостинг не переписывает форки; каждый владелец должен сделать то же самое, а форки в банке проще удалить централизованно;
  • в кэше хостинга: GitHub/GitLab держат «висящие» коммиты доступными по прямой ссылке на SHA ещё некоторое время (и в MR-ссылках/refs/merge-requests/* — долго); нужно обращение в поддержку/к администратору экземпляра с просьбой запустить сборку мусора;
  • в кэшах CI, артефактах и Docker-образах — их надо чистить отдельно, иначе секрет живёт в слоях образа;
  • в открытых MR и в комментариях к ним — текст diff'а в обсуждении переписыванием истории не удаляется;
  • в локальных клонах и IDE-индексах каждого разработчика.

Отсюда и порядок: сначала ротация. Подробнее про управление секретами и модель угроз — глава 42 (42-appsec-oauth-keycloak.md).

11. Большие и сложные репозитории

11.1 Рост размера репозитория

Размер клона определяется всей историей, а не текущим состоянием. Удалить файл — значит добавить коммит, где его нет; объект остаётся навсегда. Типовые источники:

  • бинарники: .jar зависимостей, .war, дистрибутивы, дампы БД;
  • артефакты сборки, случайно зафиксированные (target/, build/);
  • медиа и тестовые данные на десятки мегабайт;
  • сгенерированный код и node_modules;
  • бинарные дампы для тестов (PDF-выписки, XLSX-отчёты).

Диагностика:

$ git count-objects -vH
count: 0                     # loose-объектов
in-pack: 15
packs: 1
size-pack: 295.75 KiB        # вот реальный размер истории

Поиск крупнейших blob'ов по всей истории (проверенная команда):

$ git rev-list --objects --all |
  git cat-file --batch-check='%(objecttype) %(objectname) %(objectsize) %(rest)' |
  awk '$1=="blob"' | sort -k3 -n -r | head -20
blob fd150adf6ed83f26a8b8bb54e6dd934e3cf4eb4a 300000 big.bin
blob 8b9bf451f5d8e54de9c0feb2ac05e838874e6af6 70 Fee.java

Третья колонка — размер в байтах, четвёртая — путь (последний известный). Альтернатива, показывающая размер в упакованном виде:

$ git verify-pack -v .git/objects/pack/*.idx | sort -k3 -n -r | head -5
fd150adf... blob   300000 300105 839
           # объект   размер  размер-в-паке  смещение

Видно, что случайные данные не сжимаются (300 000 → 300 105 байт — даже чуть больше). Это ключевая причина, по которой бинарники разрушают репозиторий: они не сжимаются и не дельтятся, и каждая новая версия файла добавляет его полный размер.

Кто виноват в истории:

git log --all --numstat --format='%H' -- path/to/huge.bin | head
git filter-repo --analyze     # отчёты в .git/filter-repo/analysis/ — самый удобный способ

Лечение: git filter-repo --strip-blobs-bigger-than 10M или --invert-paths --path <...> с последующей координацией (процедура из 10.5 — те же пять шагов, кроме ротации). Профилактика: push rule на максимальный размер файла в GitLab и проверка в CI.

11.2 Обслуживание репозитория: gc, repack, maintenance

git gc                      # авто-режим: упаковать, удалить недостижимое старше 2 недель
git gc --aggressive --prune=now   # долго, перестраивает все дельты; НЕ рутинная операция
git repack -adf --window=250 --depth=50   # более контролируемая перепаковка
git prune --expire=now      # удалить недостижимые объекты немедленно (ОПАСНО)

⚠️ Осторожно. git gc --prune=now после reset --hard немедленно уничтожает возможность восстановления через fsck. Никогда не запускайте её «чтобы почистить», пока разбираетесь с аварией. И помните, что многие команды вызывают gc --auto неявно.

git maintenance (появился в 2.30) — современная замена «раз в месяц запускать gc»:

git maintenance register              # добавить репозиторий в список обслуживаемых
git maintenance start                 # завести системный планировщик (cron/systemd/launchd/schtasks)
git maintenance run --task=prefetch   # разово
git config maintenance.strategy incremental

Задачи: prefetch (фоновое скачивание объектов — git fetch становится мгновенным), commit-graph (кэш графа коммитов, ускоряет log --graph, merge-base, bisect в разы), loose-objects, incremental-repack, pack-refs. Для репозитория в 50 000 коммитов commit-graph — единственная настройка, дающая заметное ускорение повседневных команд.

Полезные сопутствующие:

git config core.fsmonitor true        # встроенный file system monitor (2.37+), Windows/macOS
git config feature.manyFiles true     # набор настроек под большие рабочие деревья
git config index.version 4            # компактный индекс
git config core.untrackedCache true

11.3 Частичный клон: --filter=blob:none

Partial clone скачивает граф коммитов и деревья, но не все blob'ы; недостающие докачиваются по требованию у «promisor remote» (partial-clone, проверено 2026-09-22).

git clone --filter=blob:none git@git.bank.example:payments/monorepo.git
git clone --filter=blob:limit=1m <url>     # без блобов крупнее 1 МБ
git clone --filter=tree:0 <url>            # только коммиты (для CI, который делает checkout одной ревизии)

Что происходит дальше: git checkout любой ревизии вызывает массовую докачку нужных blob'ов одним запросом, а git log -p, git blame, git log -S — докачку по одному объекту за раз. Документация прямо перечисляет это как известное ограничение: такие команды «inherently slow with partial clone», потому что требуют множества исторических объектов, которых нет локально.

Когда реально помогает:

  • репозиторий с тяжёлой историей бинарников, но нормальным текущим состоянием: клон уменьшается в разы, работа с текущим кодом не страдает;
  • CI, который собирает одну ревизию: --filter=blob:none --no-checkout + sparse-checkout + checkout даёт минимальный трафик и не ломает describe/bisect, в отличие от --depth (см. 11.4).

Когда вредит: разработчику, который часто ходит по истории (archaeology, blame, ревью старых версий) и работает в сети с высокой латентностью или вообще офлайн. Документация отдельно предупреждает: partial clone требует доступности promisor remote; офлайн работать не получится, если нужные объекты не были подтянуты заранее.

11.4 Частичное рабочее дерево (sparse-checkout)

Partial clone уменьшает скачиваемое, sparse-checkout — раскладываемое в рабочее дерево. В монорепозитории на 4000 модулей вам нужны три.

git clone --filter=blob:none --no-checkout <url> monorepo && cd monorepo
git sparse-checkout set services/pay services/common libs/money
git checkout main

Режимы (git-sparse-checkout, проверено 2026-09-22):

  • cone mode (по умолчанию и рекомендуемый): вы перечисляете каталоги; попадают все файлы верхнего уровня, все файлы непосредственно в родительских каталогах и всё содержимое указанных каталогов. Быстро, потому что проверка — префиксная.
  • non-cone mode (--no-cone): полноценные gitignore-паттерны. Документация называет его deprecated и «strongly discouraged»: сложность O(N×M) по числу паттернов и путей, отсутствие команды remove, несовместимость со sparse index, путаная семантика.

Sparse index (--sparse-index) сжимает сам файл индекса, заменяя целые «выключенные» каталоги одной записью — это то, что делает git status быстрым на монорепозитории. Документация предупреждает: формат «not completely understood by external tools», и при проблемах надо вернуться к --no-sparse-index.

git sparse-checkout set --sparse-index services/pay libs/money
git sparse-checkout list
git sparse-checkout add services/notifications
git sparse-checkout check-rules            # проверить, подпадает ли путь под правила
git sparse-checkout reapply                # после ручных изменений
git sparse-checkout disable                # вернуть всё дерево

⚠️ Осторожно. Файлы вне конуса не исчезают из индекса, они помечаются флагом skip-worktree. Инструменты, читающие файловую систему напрямую (Gradle с includeBuild, IDE-индексация, скрипты с find), увидят «отсутствующие» модули и упадут. И сборка, требующая весь реактор Maven (-am, -amd), при sparse-checkout не соберётся. Перед внедрением проверьте, что ваша сборка умеет работать с частичным деревом.

11.5 Неглубокий клон (shallow clone) в CI

git clone --depth=1 <url>                  # только последний коммит
git clone --depth=50 --branch main <url>
git fetch --unshallow                      # превратить обратно в полный
git fetch --deepen=100                     # добавить глубины

Плюс очевиден: клон 2 ГБ превращается в 30 МБ, старт задания ускоряется на минуты. В GitLab это GIT_DEPTH (по умолчанию shallow и задан небольшим числом), в GitHub Actions actions/checkout по умолчанию fetch-depth: 1.

Что ломается:

Команда Симптом при shallow
git describe fatal: No names found, cannot describe anything — теги не скачаны и/или предки обрезаны; версия артефакта становится «unknown»
git blame обрывается на границе истории: все строки приписываются граничному коммиту
git bisect good-ревизия недоступна, бинарный поиск невозможен
git log --follow, -S, -L ищут в обрезанном куске и дают ложноотрицательный ответ
git merge-base / проверка «конфликтует ли с main» нет общего предка → неверный результат или ошибка
SonarQube blame-аннотации «shallow clone detected», анализ «нового кода» нерабочий
Conventional-changelog по диапазону тегов тегов нет

Практическое правило: shallow — только для заданий, которые просто собирают и не анализируют историю. Для sonar, релиза, describe, генерации changelog — либо полный клон (GIT_DEPTH: 0), либо git fetch --unshallow --tags первым шагом. Более здоровая альтернатива — partial clone (--filter=blob:none), который даёт похожую экономию, но сохраняет весь граф коммитов.

11.6 Устройство Git LFS

LFS подменяет содержимое больших файлов текстовыми указателями, а сами данные держит на отдельном сервере. Формат указателя (git-lfs spec, проверено 2026-09-22):

version https://git-lfs.github.com/spec/v1
oid sha256:4d7a214614ab2935c943f9e0ff69d22eadbb8f32b1258daaa5e2ca24d17e2393
size 12345

Требования спецификации: только UTF-8, строки вида {key} {value}\n, ключи отсортированы (кроме version, идущего первым), размер файла-указателя менее 1024 байт, кодирование однозначно.

Механика — через clean/smudge фильтры .gitattributes:

git lfs install
git lfs track "*.pdf" "*.xlsx" "*.zip"
cat .gitattributes
# *.pdf filter=lfs diff=lfs merge=lfs -text
  • clean (при git add): поток читается, считается SHA-256, файл кладётся в .git/lfs/objects/, в индекс попадает указатель;
  • smudge (при checkout): читаются первые байты, если это указатель — объект ищется локально или скачивается, в рабочее дерево пишется настоящее содержимое.

Цена и ловушки:

  1. Миграция существующей истории — это переписывание всей истории (git lfs migrate import --include="*.zip" --everything), то есть новые SHA у всех коммитов, force-push и процедура из 10.5. Просто «начать трекать» — значит, старые версии останутся в базе, и репозиторий не похудеет.
  2. Стоимость хранения и трафика. GitHub/GitLab считают LFS отдельно от репозитория и отдельно тарифицируют трафик. CI, клонирующий LFS-объекты на каждом задании, съедает квоту очень быстро — лечится GIT_LFS_SKIP_SMUDGE=1 и явным git lfs pull только там, где нужно.
  3. Нет LFS на исполнителе — самая частая авария (инцидент 12.6): вместо файлов в рабочем дереве лежат текстовые указатели по 130 байт, сборка формально проходит, артефакт битый.
  4. Блокировки (git lfs lock) нужны, потому что бинарники не сливаются; это чужеродная для Git модель работы.
  5. Зависимость от LFS-сервера: он недоступен — вы не можете сделать checkout. Зеркалирование репозитория не копирует LFS-объекты автоматически.
  6. git lfs prune нужен локально, иначе .git/lfs растёт бесконечно.

Проверка «а точно ли выкачалось»:

git lfs env                  # конфигурация и endpoint
git lfs ls-files             # список отслеживаемых файлов и их OID
git lfs fsck                 # целостность
file docs/report-template.xlsx   # если "ASCII text" — это указатель, а не файл
head -1 docs/report-template.xlsx | grep -q '^version https://git-lfs' && echo "ЭТО УКАЗАТЕЛЬ"

Главный вопрос перед внедрением LFS: а обязан ли этот файл лежать в Git? Дистрибутивы, шаблоны отчётов, тестовые дампы почти всегда лучше живут в артефактном хранилище (Nexus/Artifactory/S3) с версией в build.gradle — см. главу 55 (55-build-and-dependencies.md).

11.7 Submodule, subtree и монорепозиторий

Submodule — ссылка на конкретный коммит другого репозитория; в дереве родителя хранится запись типа 160000 (gitlink).

git submodule add git@git.bank.example:libs/money-core.git libs/money-core
git clone --recurse-submodules <url>
git submodule update --init --recursive
git submodule update --remote          # подтянуть новые коммиты подмодуля
git -c submodule.recurse=true pull

Ловушки: клон без --recurse-submodules даёт пустые каталоги; коммит в подмодуле легко забыть запушить (у коллег «commit not found»); git status в родителе показывает подмодуль как «modified», не объясняя почему; переключение веток не переключает подмодули без submodule.recurse=true; CI требует отдельной настройки доступа к подмодулям.

Subtree — содержимое чужого репозитория копируется в подкаталог и живёт в вашей истории.

git subtree add --prefix=libs/money-core git@...:libs/money-core.git main --squash
git subtree pull --prefix=libs/money-core <url> main --squash
git subtree push --prefix=libs/money-core <url> main

Плюс: обычный клон, никаких дополнительных действий у потребителя, всё работает «из коробки». Минус: история чужого проекта размывается в вашей (или теряется при --squash), обратная отдача изменений (subtree push) неудобна, команду знают полтора человека в компании.

Монорепо — всё в одном репозитории.

Критерий Submodule Subtree Монорепо
Сложность для потребителя высокая низкая нулевая
Атомарный коммит через границу невозможен возможен возможен
Размер клона маленький растёт большой
Независимые версии библиотеки да, явно (по SHA) ручное управление нет (всё одной версии)
Прозрачность «какая версия у нас» отличная (SHA в дереве) плохая н/д
Барьер входа команды высокий средний низкий
Инструментальная поддержка встроенная встроенная, но редкая требует Bazel/Gradle-композит

Честный вывод: если можно опубликовать библиотеку как артефакт в Nexus/Artifactory — делайте так и не связывайтесь ни с submodule, ни с subtree. Submodule оправдан, когда нужна именно фиксация конкретной ревизии стороннего кода (vendoring с аудитом), subtree — когда нужен «вендоринг с возможностью локально править и изредка отдавать назад».

11.8 Java-монорепозиторий

  • Сборка. Gradle с composite builds / configuration cache и Maven с реактором на 300 модулей ведут себя по-разному. Без инкрементальной сборки и удалённого кэша (--build-cache, Develocity, Bazel) полная сборка монорепо становится часовой — а значит, ломается trunk-based. Детали — глава 55.
  • CI. Нужна сборка только затронутых модулей: определение изменений через git diff --name-only origin/main...HEAD и отображение путей на модули; в GitLab — rules:changes и child pipelines (глава 54).
  • CODEOWNERS. В монорепо это единственный способ маршрутизировать ревью; файл быстро разрастается до сотен строк, и порядок правил (побеждает последнее совпадение) регулярно даёт «не тех» рецензентов.
  • Права. Git не умеет разграничивать доступ на уровне каталогов. Если часть кода видна не всем (платёжный модуль, антифрод), монорепо противоречит требованию — и это чаще всего непреодолимый аргумент в банке.
  • git log/blame на путях становятся основным интерфейсом: git log -- services/pay вместо git log.
  • Теги и версии. Один v1.5.0 на всё — либо версия на модуль (pay/v1.5.0), что ломает git describe без --match.

12. Разобранные инциденты

Шесть реальных по сюжету аварий. Формат: симптом → диагностика → причина → лечение → как не допустить.

12.1 git push --force в main затёр чужие коммиты

Симптом. Четверг, 17:40. Разработчик пишет в чат: «я запушил, а моих коммитов нет». Ещё двое обнаруживают, что их вчерашняя работа пропала из main. git log origin/main короче, чем был утром. CI собирает не то, что ожидалось.

Диагностика. Первое — остановить запись в ветку: включить protected branch / поставить репозиторий в read-only, написать в канал «не пушьте в main». Каждый новый push усложняет восстановление.

Дальше — понять, что было. У виновника:

$ git reflog show origin/main        # reflog remote-tracking ссылки!
a1b2c3d refs/remotes/origin/main@{0}: update by push
9f8e7d6 refs/remotes/origin/main@{1}: fetch origin: fast-forward

Строка @{1} — значение main до force-push. Если у виновника её нет (он не делал fetch), ищем у любого, кто делал git fetch сегодня:

# на машине любого коллеги
git reflog show origin/main --date=iso | head
# или, если fetch был давно, но локально была актуальная ветка:
git reflog show main --date=iso | head

Второй источник — серверный reflog. В GitLab/GitHub нужен администратор экземпляра или поддержка; в самостоятельно развёрнутом bare-репозитории (при включённом core.logAllRefUpdates) это:

ssh git@git.bank.example
cd /srv/git/payments/pay-service.git
git reflog show main
git log --oneline <старый-sha>

Третий источник — артефакты CI: в логе любого конвейера есть CI_COMMIT_SHA. Задание, отработавшая до аварии, знает утраченный SHA. Четвёртый — уведомления в чате/почте о пушах, где SHA указан явно.

Причина. Разработчик делал rebase своей ветки, ошибся в имени ветки в команде push и использовал --force вместо --force-with-lease; сервер не имел защиты main от force-push, потому что репозиторий создавали скриптом без применения шаблона настроек.

Лечение. Найденный SHA возвращается на сервер:

git fetch origin
git switch -c rescue-main <старый-sha>       # проверяем, что это действительно то состояние
git log --oneline | head
# восстанавливаем ветку, не теряя того, что успели запушить после аварии:
git switch -c merge-back <старый-sha>
git merge origin/main                        # вливаем то, что попало после force-push
git push origin merge-back:main              # или force-with-lease, если потребуется

Если после аварии никто ничего не пушил, проще:

git push --force-with-lease origin <старый-sha>:main

Отдельно: коммиты не пропали из базы сервера сразу — они стали недостижимыми и живут до серверного gc. Пока не прошёл gc, их можно вытащить по прямому SHA даже обычным git fetch origin <sha> (если сервер это разрешает: uploadpack.allowReachableSHA1InWant/allowAnySHA1InWant).

Как не допустить. Protected branches на main и release/* с запретом force-push и прямого push (только через MR) — применяется шаблоном к группе проектов, а не вручную на каждый репозиторий. Псевдоним pushf с --force-with-lease --force-if-includes вместо голого --force. Запрет push.default = matching (он пушит все совпадающие ветки сразу). Серверный reflog включён и бэкапится.

12.2 Фича пропала после revert merge-коммита

Симптом. Фичу «кэшбэк» влили в main, на стенде нашли дефект, релиз-менеджер откатил её git revert -m 1. Через две недели дефект починили и попросили вернуть фичу. Разработчик делает git merge feature/cashback — Git отвечает Already up to date., а кода в main нет. MR показывает «No changes». Команда два дня считает, что «Git сломался», и в итоге кто-то копирует файлы руками через архив.

Диагностика.

$ git log --oneline --graph --first-parent -5
* c531de3 Revert "Merge branch 'feature/cashback'"
* 2b17fb9 Merge branch 'feature/cashback'
* 662ba05 base

$ git branch --merged main | grep cashback
  feature/cashback                       # ветка числится влитой

$ git merge-base --is-ancestor feature/cashback main && echo "верхушка ветки — предок main"
верхушка ветки — предок main

$ git log --oneline main..feature/cashback     # пусто — с точки зрения графа нечего вливать

Причина. Разобрана в 5.4: revert откатывает содержимое, а не топологию. Коммиты ветки остаются достижимыми из main, поэтому merge base = верхушка ветки, разницы нет, слияние — no-op.

Лечение. Поскольку ветку дорабатывали, revert-of-revert даст старую версию, а новые коммиты придётся вливать сверху. Чище — новая ветка:

git switch -c feature/cashback-v2 origin/main
git cherry-pick <первый-коммит-фичи>^..<последний-коммит-фичи>
# разрешаем конфликты один раз, прогоняем тесты
git push -u origin feature/cashback-v2
# обычный MR, обычное ревью

Проверка, что перенесли ровно то же:

git range-diff <первый>^..<последний> origin/main..feature/cashback-v2

Если бы ветку не трогали, хватило бы:

git revert --no-edit c531de3     # "Reapply 'Merge branch feature/cashback'"

Как не допустить.

  1. Откатывать фичу не revert'ом merge-коммита, а feature flag — выключение занимает секунды и обратимо.
  2. Если revert merge-коммита всё же сделан — сразу же дописать в описание MR и в задачу: «откат сделан revert'ом merge-коммита , для возврата — revert-of-revert либо новая ветка». Это знание теряется за три дня.
  3. Использовать squash-merge для фич, которые с высокой вероятностью придётся откатывать: у squash-коммита revert обратим без ловушки.
  4. Добавить в чек-лист релиз-менеджера ссылку на этот раздел.

12.3 Массовое форматирование испортило git blame

Симптом. После внедрения spotlessApply на весь проект (1247 файлов, один коммит) git blame на любом файле показывает одного и того же автора и один и тот же коммит style: apply google-java-format. Расследование инцидента упирается в «кто и зачем добавил эту проверку» — ответа нет. Плюс: у восьми открытых MR конфликты в каждом изменённом файле.

Диагностика.

$ git blame --line-porcelain FeeService.java | grep '^summary ' | sort | uniq -c | sort -rn
    412 summary style: apply google-java-format
      6 summary feat: расчёт комиссии

Причина. Косметический коммит в истории каждой строки. Это не потеря данных — данные есть, просто blame по умолчанию показывает последний коммит, коснувшийся строки.

Лечение.

# 1. Найти SHA форматирующего коммита
FMT=$(git log --oneline --all --grep 'google-java-format' | head -1 | cut -d' ' -f1)

# 2. Разовая проверка
git blame --ignore-rev $FMT FeeService.java

# 3. Постоянное решение — файл в репозитории
cat >> .git-blame-ignore-revs <<'TXT'
# Массовое форматирование google-java-format, PAY-3901, 2026-04-12
d733c39a84f4b1a2c0e1f2d3a4b5c6d7e8f9a0b1
TXT
git add .git-blame-ignore-revs
git commit -m "chore: игнорировать форматирующий коммит в blame"

# 4. Каждому разработчику (в onboarding-скрипт / make setup):
git config blame.ignoreRevsFile .git-blame-ignore-revs

Дополнительно git blame -w -C -C -M вытаскивает авторство перемещённых строк.

Открытым MR помогает:

git switch feature/x
git merge -X ignore-all-space origin/main
# либо чище: прогнать форматтер в своей ветке и перебазироваться
./gradlew spotlessApply && git commit -am "style: spotlessApply" && git rebase origin/main

Как не допустить. Правило из 6.5: форматирование — отдельный коммит, ничего кроме; SHA сразу в .git-blame-ignore-revs; проверка формата включается в CI в тот же день, иначе история повторится; настройка blame.ignoreRevsFile — в скрипте инициализации проекта, чтобы не зависеть от памяти разработчиков.

12.4 Секрет попал в репозиторий и остался после «удаления файла»

Симптом. Служба ИБ присылает оповещение: в репозитории pay-service обнаружен приватный ключ. Разработчик отвечает: «я его удалил ещё в марте, вот коммит». Сканер продолжает находить.

Диагностика.

$ git log --all --oneline --diff-filter=A -- src/main/resources/tls/client.key
3f2a1b0 chore: добавить тестовый сертификат            # добавление

$ git log --all --oneline --diff-filter=D -- src/main/resources/tls/client.key
9c8d7e6 chore: убрать сертификат из репозитория        # удаление

$ git rev-list --objects --all | grep 'tls/client.key'
a7b3c9d1... src/main/resources/tls/client.key           # объект жив

$ git cat-file -p a7b3c9d1 | head -1
-----BEGIN PRIVATE KEY-----                             # да, это он

Проверяем масштаб распространения: сколько форков, был ли репозиторий доступен подрядчикам, есть ли зеркала, попадал ли ключ в собранные образы (docker history, слои с COPY src/main/resources).

Причина. Коммит, удаляющий файл, — это коммит без файла. Blob никуда не делся и достижим из старых коммитов.

Лечение — процедура из 10.5, в правильном порядке:

# ШАГ 1. РОТАЦИЯ. Ключ отозван и перевыпущен. Всё остальное — уборка.

# ШАГ 2. Зафиксировать инцидент, определить область распространения.

# ШАГ 3. Переписать историю на свежем зеркале.
git clone --mirror git@git.bank.example:payments/pay-service.git
cd pay-service.git
git filter-repo --invert-paths --path src/main/resources/tls/client.key
# либо оставить файл, но вычистить содержимое:
#   printf '-----BEGIN PRIVATE KEY-----...==>***REMOVED***\n' > /tmp/r.txt
#   git filter-repo --replace-text /tmp/r.txt
git remote add origin git@git.bank.example:payments/pay-service.git
git push --force --all && git push --force --tags

# ШАГ 4. Координация: всем переклонировать, ветки перебазировать (инструкция из 10.5).
# ШАГ 5. Остаточные копии: форки, кэш хостинга, артефакты, образы, MR-обсуждения.

Верификация после уборки:

git clone git@git.bank.example:payments/pay-service.git verify && cd verify
git rev-list --objects --all | grep -c 'client.key'      # должно быть 0
gitleaks detect --source . --log-opts="--all" --exit-code 1

Как не допустить. gitleaks в pre-commit (быстрая обратная связь) и обязательным гейтом в MR-конвейере (гарантия). Push rule на маски *.key, *.p12, *.jks, *.pem. Тестовые сертификаты генерируются в @BeforeAll или Testcontainers, а не хранятся в репозитории. Секреты — в Vault/CI-переменных (главы 42 и 54). Ночной полный скан истории всех репозиториев группы.

12.5 Rebase долгоживущей ветки на 200 коммитов

Симптом. Ветка feature/new-limits живёт полтора месяца (релизное окно, согласования). Перед демо разработчик делает git rebase origin/main — main ушла на 214 коммитов вперёд. Rebase останавливается на конфликте, разработчик разрешает, --continue, снова конфликт в том же файле и тех же строках, и так 23 раза. Через два часа он делает --abort, и вся работа по разрешению пропадает. На следующий день всё повторяется.

Диагностика.

$ git log --oneline origin/main..HEAD | wc -l
37                                  # столько коммитов будет применяться заново
$ git log --oneline HEAD..origin/main | wc -l
214                                 # настолько разошлись
$ git diff --stat origin/main...HEAD | tail -1
 64 files changed, 2841 insertions(+), 930 deletions(-)

Причина — двойная:

  1. Ветка жила полтора месяца и ни разу не синхронизировалась с main.
  2. Rebase применяет коммиты по одному, и каждый из 37 коммитов пересекается с изменениями в main в одних и тех же файлах. Один и тот же конфликт вы разрешаете столько раз, сколько ваших коммитов его затрагивает.

Лечение — здесь и сейчас:

# 0. Страховка
git branch backup/new-limits-before-rebase

# 1. Включить rerere — конфликты будут запоминаться
git config rerere.enabled true
git config rerere.autoUpdate true

# 2. Уменьшить число применяемых коммитов: сначала схлопнуть свои 37 в 4-5 осмысленных
git rebase -i origin/main --onto HEAD~37   # нет: проще интерактивно по своей ветке
git rebase -i $(git merge-base origin/main HEAD)   # squash/fixup внутри своей ветки
# теперь в ветке 5 коммитов вместо 37

# 3. Только теперь — rebase на main
git rebase origin/main
# конфликты разрешаются по разу на коммит, а не по разу на каждый из 37

Альтернатива, которая часто правильнее: один merge вместо rebase.

git merge origin/main      # один трёхсторонний merge — конфликты разрешаются ОДИН раз

История будет не такой красивой, но конфликт вы разберёте единожды. Для ветки, которую всё равно будут squash-сливать, разница в красоте истории нулевая.

Что даёт rerere в этом сценарии: даже если вы сделали --abort, разрешения сохранены. Повторный rebase применяет их автоматически, и вместо двух часов уходит десять минут (плюс обязательная проверка git diff HEAD и тесты — rerere повторяет решение вслепую).

Как не допустить. Ежедневный git fetch && git rebase origin/main в фича-ветке. rerere включён глобально у всех (это строка в onboarding-скрипте). Ветка старше 10 дней — предмет обсуждения на дейли. Крупная задача дробится на выкатываемые части за feature flag. Перед любым нетривиальным rebase — git branch backup/....

12.6 LFS-объекты не выкачались на исполнителе, сборка собрала пустые файлы

Симптом. Конвейер зелёный, артефакт собран, задеплоен на стенд. Тестировщик открывает сформированную выписку — PDF-шаблон битый, приложение падает с Invalid Excel file format. Локально всё работает. В логе сборки ничего подозрительного.

Диагностика. Смотрим, что в рабочем дереве исполнителя:

$ ls -l src/main/resources/templates/statement.xlsx
-rw-r--r-- 1 root root 132 Sep 22 10:14 statement.xlsx     # 132 байта вместо 84 КБ

$ head -3 src/main/resources/templates/statement.xlsx
version https://git-lfs.github.com/spec/v1
oid sha256:4d7a214614ab2935c943f9e0ff69d22eadbb8f32b1258daaa5e2ca24d17e2393
size 86016

Это LFS-указатель, попавший в jar вместо файла. Проверка окружения исполнителя:

$ git lfs version
git: 'lfs' is not a git command.          # клиента нет
$ git config --get filter.lfs.smudge      # фильтр не настроен
$ echo $GIT_LFS_SKIP_SMUDGE               # или намеренно выставлена 1
1

Причина — одна из четырёх, встречаются все:

  1. На образе исполнителя не установлен git-lfs — Git не знает про фильтр lfs, clean/smudge не вызываются, в дерево ложится указатель.
  2. Установлен, но не выполнен git lfs install (фильтры не прописаны в конфиге).
  3. В переменных CI стоит GIT_LFS_SKIP_SMUDGE=1 (частая «оптимизация» ради скорости) без последующего git lfs pull.
  4. Нет доступа к LFS-endpoint: отдельная аутентификация, прокси, firewall в закрытом контуре. Тогда git lfs pull падает, но если он в конвейере не вызывается явно — падать нечему.

Самое неприятное: сборка не падает. Gradle кладёт «файл» в jar, jar валиден, тесты (если они не читают этот файл) проходят.

Лечение.

# .gitlab-ci.yml (фрагмент)
default:
  image: eclipse-temurin:25-jdk
  before_script:
    - git lfs version || (apt-get update && apt-get install -y git-lfs)
    - git lfs install --local
    - git lfs pull
    - |
      # ГЕЙТ: ни одного указателя в рабочем дереве
      if git lfs ls-files -n | xargs -r -I{} sh -c \
         'head -c 40 "{}" | grep -q "^version https://git-lfs" && echo "УКАЗАТЕЛЬ: {}"' | grep .; then
        echo "LFS-объекты не выкачаны"; exit 1
      fi

Быстрое разовое лечение на локальной машине с тем же симптомом:

git lfs install
git lfs pull                     # или: git lfs fetch --all && git checkout -- .
git lfs fsck

Как не допустить.

  1. git-lfs — часть базового образа исполнителя, а не устанавливается в каждом задании.
  2. Явная проверка-гейт (код выше) в самом начале конвейера: дешевле любого разбора.
  3. Тест, который реально читает шаблон и проверяет магические байты (PK\x03\x04 для xlsx, %PDF для pdf) — такой тест ловит проблему на уровне сборки, а не на стенде.
  4. Ещё лучше — не держать шаблоны в Git: положить в Nexus/S3 и подтягивать задачей сборки с проверкой контрольной суммы (глава 55, 55-build-and-dependencies.md).

13. Ошибки и антипаттерны

  1. git pull по привычке. Симптом: в истории «Merge branch 'main' of git.bank.example…», --first-parent показывает мусор, git log нечитаем. Причина: pull = fetch + merge в текущую ветку. Лечение: git config --global pull.ff only; осознанно выбирать pull --rebase или merge origin/main.

  2. git push --force вместо --force-with-lease. Симптом: чужие коммиты исчезли из ветки. Причина: force ставит ссылку без проверки её текущего значения. Лечение: псевдоним pushf = push --force-with-lease --force-if-includes; protected branches на сервере.

  3. Надежда на --force-with-lease при фоновом fetch. Симптом: «я же использовал lease, и всё равно затёр». Причина: IDE/maintenance/скрипт обновили origin/<branch>, lease совпал. Лечение: --force-if-includes либо явное --force-with-lease=<ref>:<sha>.

  4. -s ours вместо -X ours. Симптом: ветка «влита», MR закрыт, кода нет. Причина: -s ours — стратегия, отбрасывающая содержимое чужой ветки целиком. Лечение: git show --stat <merge> покажет пустое слияние; исправлять cherry-pick'ом диапазона в новую ветку.

  5. git rebase --skip, чтобы «проскочить» конфликт. Симптом: после rebase исчезли изменения. Причина: --skip выбрасывает коммит целиком. Лечение: только --continue после разрешения; восстановление — git reset --hard <branch>@{n} до rebase (start).

  6. --ours/--theirs во время rebase поняты наоборот. Симптом: разработчик «разрешил конфликты» и потерял всю свою работу. Причина: при rebase ours = upstream, theirs = ваши коммиты. Лечение: перед выбором смотреть git diff --base --ours и --base --theirs; включить zdiff3.

  7. Revert merge-коммита без понимания последствий. Симптом: Already up to date, кода нет. Причина: топология не откатывается. Лечение и профилактика: разделы 5.4 и 12.2; предпочитать feature flags и squash-merge.

  8. Стиль конфликтов по умолчанию. Симптом: «выбираю наугад, потом чиню в проде». Причина: без базы непонятно, кто что менял. Лечение: git config --global merge.conflictStyle zdiff3 — одна команда, окупается в первый день.

  9. Коммит маркеров конфликта в код. Симптом: сборка падает на <<<<<<< HEAD, иногда только в другом модуле. Причина: разрешили не все файлы, git add -A, commit. Лечение: git diff --check и хук check-merge-conflict; гейт в CI: grep -rn '^<<<<<<< ' --include='*.java' src/.

  10. Пустое разрешение конфликта. Симптом: фича молча не работает; в diff'е «удалено 40 строк». Причина: вырезали оба варианта, Git это принял. Лечение: обязательный git diff HEAD перед коммитом слияния и прогон тестов; ревью merge-коммитов, а не только фич.

  11. Тяжёлый pre-commit. Симптом: вся команда пишет --no-verify. Причина: хук идёт 40 секунд. Лечение: в pre-commit только то, что укладывается в 5 секунд; остальное — в pre-push и в CI.

  12. Клиентские хуки как «гарантия». Симптом: в main прилетают коммиты, нарушающие все конвенции. Причина: хуки не приезжают при клонировании и обходятся --no-verify. Лечение: обязательные проверки — только серверные (pipeline + protected branches).

  13. core.hooksPath убил хуки LFS. Симптом: после настройки своих хуков LFS-файлы перестали подтягиваться при checkout. Причина: core.hooksPath отключает .git/hooks целиком. Лечение: перенести хуки LFS в свой каталог или git lfs install --force после настройки.

  14. git clean -fdx на рабочей машине. Симптом: пропали .env, локальные сертификаты, настройки IDE. Причина: -x удаляет и игнорируемое. Лечение: всегда сначала -n; для чистки сборки -fdX или ./gradlew clean.

  15. git stash как хранилище. Симптом: «где моя работа за прошлую неделю?». Причина: stash без имени, применён не тот, pop при конфликте не удалил запись, stash clear. Лечение: ветка wip/... с коммитом вместо stash; git stash push -m при необходимости; восстановление — git fsck --unreachable.

  16. git stash без -u. Симптом: новый класс «переехал» на другую ветку и сломал сборку. Причина: неотслеживаемые файлы не прячутся. Лечение: git stash push -u.

  17. Секрет «удалён» коммитом. Симптом: сканер продолжает находить ключ. Причина: blob остаётся достижимым из старых коммитов. Лечение: ротация → git filter-repo → координация (раздел 10.5).

  18. git filter-branch вместо filter-repo. Симптом: переписывание идёт часами, ломаются теги и подписи, «mangled history». Причина: сам Git предупреждает о «glut of gotchas». Лечение: git filter-repo (или BFG).

  19. Shallow clone в CI + git describe. Симптом: fatal: No names found, версия артефакта «unknown», Sonar не видит «новый код». Причина: --depth=1 без тегов. Лечение: GIT_DEPTH: 0 для заданий, работающих с историей, либо git fetch --unshallow --tags.

  20. Бинарники в репозитории. Симптом: клон 3 ГБ, git status секундами, CI тратит минуты на checkout. Причина: бинарники не дельтятся и не сжимаются, каждая версия — полный размер. Лечение: артефактное хранилище; в крайнем случае LFS; чистка истории filter-repo --strip-blobs-bigger-than.

  21. LFS без проверки на исполнителе. Симптом: в артефакте текстовые указатели вместо файлов, сборка зелёная. Причина: нет git-lfs/GIT_LFS_SKIP_SMUDGE=1/нет доступа к endpoint. Лечение: гейт из инцидента 12.6.

  22. Массовое форматирование вперемешку с логикой. Симптом: ревью невозможно, blame бесполезен, конфликты во всех ветках. Причина: один коммит меняет 1200 файлов и заодно правит код. Лечение: отдельный коммит + .git-blame-ignore-revs + проверка формата в CI в тот же день.

  23. .gitignore не помогает уже добавленному файлу. Симптом: application-local.yml в каждом diff'е. Причина: ignore не действует на отслеживаемые файлы. Лечение: git rm --cached <file>; отладка правил — git check-ignore -v.

  24. Разъехавшиеся переводы строк. Симптом: diff показывает весь файл, bad interpreter: /bin/bash^M, тесты падают у одного человека. Причина: смешение CRLF/LF без .gitattributes. Лечение: * text=auto + разовый git add --renormalize . отдельным коммитом (и его SHA — в blame-ignore).

  25. Долгоживущая ветка без синхронизации. Симптом: rebase на 200 коммитов, одни и те же конфликты по 20 раз. Причина: ветка не сливалась с main полтора месяца. Лечение: ежедневный rebase/merge from main, rerere, дробление задачи, feature flags (инцидент 12.5).

  26. rerere применил старое разрешение вслепую. Симптом: merge прошёл чисто, но код неверный. Причина: конфликт текстуально совпал, а смысл изменился. Лечение: при включённом rerere обязательный git diff HEAD и тесты; git rerere forget <path> для неверной записи.

  27. git commit --amend после push. Симптом: «ветка разошлась», у коллеги дубли коммитов. Причина: amend создаёт новый объект, ветка перестаёт быть перемоткой. Лечение: push --force-with-lease только для своих веток; для общих — новый коммит.

  28. Неверный user.email в коммитах. Симптом: проверка «все коммиты от сотрудников» падает, хостинг не связывает коммит с аккаунтом. Причина: глобальный конфиг с личной почтой. Лечение: git config --global user.useConfigOnly true (заставляет задавать email явно в каждом репозитории) и includeIf по каталогам:

# ~/.gitconfig
[user]
    useConfigOnly = true
[includeIf "gitdir:~/work/"]
    path = ~/.gitconfig-work
[includeIf "gitdir:~/personal/"]
    path = ~/.gitconfig-personal

  1. Подписи, потерянные при rebase. Симптом: «Verified» пропало у всех коммитов ветки после rebase. Причина: rebase пересоздаёт коммиты, подпись покрывает старый объект. Лечение: git rebase -S / rebase.gpgSign=true.

  2. git log --since и авторская дата. Симптом: отчёт «что сделано за спринт» не сходится с реальностью. Причина: фильтрация по дате коммиттера, вывод — авторской. Лечение: явно --committer-date-is-author-date при rebase либо фильтровать --since вместе с --date=committer и понимать, что именно считаете.

14.1 Основные команды диагностики

# Где я и что вокруг

git log --oneline --graph --decorate --all -20
git branch -vv                       # ветки, upstream, расхождение
git remote -v && git config --get-all remote.origin.fetch
git rev-parse --abbrev-ref HEAD      # имя текущей ветки ('HEAD' = detached)

# Что физически лежит в объектах

git ls-files --stage                 # индекс
git ls-files -u                      # конфликтующие записи (стадии 1/2/3)

# Что произошло со ссылками

cat .git/ORIG_HEAD

git diff main...feature              # как в MR: изменения ветки от merge base

git cherry -v main release/2026.03   # что не перенесено (по patch-id)

14.2 Чеклист «история разъехалась»

Симптомы: git status показывает «have diverged», в логе дубли коммитов с одинаковыми сообщениями, MR показывает больше изменений, чем ожидалось.

  1. Зафиксировать факты. bash git fetch origin git status -sb # ## feature/x...origin/feature/x [ahead 4, behind 7] git log --oneline --graph --left-right --boundary HEAD...@{u} --left-right покажет, какие коммиты «мои» (<), какие «их» (>).

  2. Понять, переписывалась ли история. bash git reflog show origin/feature/x # была ли строка "forced-update" git merge-base HEAD @{u} # общий предок; если он далеко — историю переписали

  3. Сравнить по содержимому, а не по SHA. bash git cherry -v @{u} HEAD # '-' = патч уже есть на той стороне, '+' = нет git range-diff @{u}...HEAD # чем мои коммиты отличаются от их аналогов Если все патчи помечены -, значит, это те же изменения с другими SHA: ваша локальная ветка — старая версия переписанной.

  4. Выбрать действие.

    • «Мои коммиты уже есть на сервере под другими SHA» → git reset --hard @{u} (предварительно git branch backup/...).
    • «У меня есть уникальные коммиты, у них тоже» → git rebase --onto @{u} <старая-база> HEAD (перенести только своё).
    • «Ветка общая и переписывать нельзя» → git merge @{u}, разрешить конфликт один раз.

  5. Проверить результат. bash git log --oneline --graph -15 git diff @{u} # что реально отличается от сервера ./gradlew test

14.3 Чеклист «что-то потерялось»

  1. Не запускать gc, prune, reset --hard и clean. Любая из них может уничтожить остатки. Если операция уже выполняется — не прерывать процесс наполовину.
  2. Определить, был ли коммит. Если изменения только в рабочем дереве и не было ни add, ни commit — Git не поможет: смотрите Local History в IDEA (глава 57) или бэкап.
  3. Если был git add — содержимое в базе: bash git fsck --lost-found grep -rl 'уникальная строка из файла' .git/lost-found/other/
  4. Если был коммит — reflog: bash git reflog --date=iso | head -40 git reflog show <branch> git log -g --grep='часть сообщения' # поиск по reflog как по логу git log --all --oneline --source -S'уникальная строка'
  5. Если reflog пуст (другой клон, CI, истёк срок): bash git fsck --no-reflogs --lost-found for c in $(git fsck --no-reflogs --lost-found 2>/dev/null | awk '/dangling commit/{print $3}'); do git log -1 --format='%h %ci %an %s' $c done
  6. Если пропало на сервере — серверный reflog (bare-репозиторий, админ хостинга), SHA из логов CI, уведомления о пушах, локальные клоны коллег (git reflog show origin/main у каждого).
  7. Зафиксировать найденное сразу: bash git switch -c rescue/<описание> <sha> git push -u origin rescue/<описание> # вынести из локальной машины
  8. Убедиться, что это то самое: git log --stat, git diff <rescue> <текущее>, тесты.

14.4 Чеклист «репозиторий распух»

  1. Измерить. bash du -sh .git git count-objects -vH # size-pack — это и есть история
  2. Найти виновников. bash git rev-list --objects --all | git cat-file --batch-check='%(objecttype) %(objectname) %(objectsize) %(rest)' | awk '$1=="blob"' | sort -k3 -n -r | head -30 git filter-repo --analyze && head -40 .git/filter-repo/analysis/path-all-sizes.txt
  3. Проверить, не локальная ли это проблема. Может, у вас просто много loose-объектов и старых пакетов: bash git gc git count-objects -vH # если size-pack упал в разы — дело было в мусоре git maintenance start # чтобы не повторялось
  4. Решить, нужна ли перезапись истории. Она стоит координации всей команды (10.5). Часто дешевле:
    • --filter=blob:none при клонировании (история остаётся, трафик падает);
    • sparse-checkout для монорепо;
    • git maintenance + commit-graph для скорости.
  5. Если перезапись нужна: bash git clone --mirror <url> && cd <repo>.git git filter-repo --strip-blobs-bigger-than 10M # или --invert-paths --path-glob '*.jar' git remote add origin <url> && git push --force --all && git push --force --tags
  6. Закрыть входные ворота: push rule на размер файла, .gitignore для сборочных каталогов, проверка в CI, артефактное хранилище для бинарников.

14.5 Чеклист «сложный конфликт слияния»

  1. git status — какие файлы и какого типа конфликт (both modified, deleted by us, added by both).
  2. git log --merge --oneline -- <file> — только коммиты, затрагивающие конфликтующий файл с обеих сторон. Это отвечает на «кто и зачем это менял».
  3. git diff --base --ours -- <file> и git diff --base --theirs -- <file> — что сделала каждая сторона относительно базы, по отдельности.
  4. git show :1:<file> > /tmp/base && git show :2:<file> > /tmp/ours && git show :3:<file> > /tmp/theirs — вытащить три версии файлами и открыть в нормальном сравнении.
  5. Переключить стиль, если конфликт большой: git checkout --conflict=zdiff3 -- <file>.
  6. Разрешить, затем обязательно: git diff HEAD -- <file> (что получилось относительно вашей исходной версии), компиляция, тесты.
  7. git add <file> и только после проверки всех файлов — git merge --continue.

15. Вопросы на интервью

  1. Что физически представляет собой коммит в Git? Это объект в базе .git/objects, текстовый по содержимому: ссылка на корневой tree, ноль или больше строк parent, строки author и committer с unix-временем и смещением, опционально подпись, затем сообщение. Имя объекта — SHA-1 (или SHA-256) от типа, длины и содержимого, поэтому коммит неизменяем: «изменить» его можно только создав новый. Diff внутри коммита не хранится — он вычисляется на лету сравнением двух деревьев. Понимание этого объясняет всё остальное: rebase, amend и cherry-pick просто создают новые объекты и двигают ссылки.

  2. Git хранит снимки или дельты? Логически — снимки: каждый коммит ссылается на дерево, описывающее весь проект целиком. Экономия достигается дедупликацией по содержимому: неизменившийся файл — это один и тот же blob, на который ссылаются тысячи деревьев. Дельты существуют, но только в формате хранения: при упаковке в packfile похожие объекты сохраняются как дельты друг к другу, причём база выбирается по эвристике похожести, а не по истории. Поэтому git gc/git repack уменьшают репозиторий, не меняя модель.

  3. Чем git reset --soft, --mixed и --hard отличаются? Через модель трёх деревьев: --soft двигает только HEAD (ветку), --mixed — HEAD и индекс, --hard — HEAD, индекс и рабочее дерево. Отсюда применение: --soft HEAD~1 разкоммичивает, оставляя всё в индексе; --mixed дополнительно снимает со staging; --hard приводит всё в состояние указанного коммита. --hard — единственная команда, безвозвратно уничтожающая незафиксированные изменения: коммиты восстанавливаются через reflog, а несохранённые правки рабочего дерева — нет.

  4. reset против revert — когда что? reset переставляет указатель ветки, то есть переписывает историю; применим только к тому, что ещё не опубликовано. revert создаёт новый коммит с обратным патчем, история не меняется, все SHA остаются — это единственный корректный способ откатить то, что уже в main или в проде. Правило простое: не ушло с машины — reset, ушло — revert. Для отката merge-коммита у revert есть обязательный -m и известная ловушка с повторным слиянием.

  5. Что произойдёт, если сделать revert merge-коммита, а потом захотеть вернуть фичу? git merge ответит «Already up to date», а кода не будет. Причина: revert откатывает содержимое, но не топологию — коммиты влитой ветки остаются достижимыми из main, поэтому merge base равна верхушке ветки и вливать нечего. Выхода два: revert-of-revert, если ветку после этого не дорабатывали, либо новая ветка с cherry-pick диапазона коммитов, которая снова становится невлитой. Именно из-за этой ловушки откат фич предпочитают делать feature-флагом или squash-merge'ем.

  6. Что физически происходит при rebase и почему это опасно для опубликованных веток? Rebase берёт коммиты, которых нет в upstream, и применяет их патчи по одному поверх новой базы, создавая новые объекты: у них другой родитель, другое дерево, другая дата коммиттера и, следовательно, другой SHA. Старые коммиты остаются в базе и доступны через reflog. Опасность в том, что у коллеги в его remote-tracking ветке лежат старые объекты; его Git не знает, что новый коммит — «тот же самый», и при pull склеит обе версии, продублировав все изменения. Поэтому интеграционные ветки защищают на сервере, а свои фича-ветки ребейзят свободно и пушат с --force-with-lease.

  7. Как работает three-way merge и почему конфликт возникает именно там, где возник? Берутся три состояния: merge base (общий предок, git merge-base), наша верхушка и их верхушка. Для каждого блока строк смотрится, изменила ли его одна сторона или обе: изменение одной стороной применяется автоматически, изменение обеими в пересекающихся или соседних блоках даёт конфликт. Отсюда следствия: перемещение кода конфликтует со всем, что внутри; массовое форматирование конфликтует со всеми ветками; а два человека, правившие разные методы, не конфликтуют — но могут получить семантический конфликт, который Git не увидит, потому что он не понимает Java.

  8. В чём разница между -s ours и -X ours? -s ours — это стратегия: создаётся merge-коммит, чьё дерево равно нашему, а содержимое другой ветки отбрасывается полностью. -X ours — опция стратегии ort: выполняется нормальное трёхстороннее слияние, и только в конфликтующих местах автоматически берётся наша версия, а все неконфликтующие изменения другой ветки применяются. Перепутать их — значит тихо потерять работу целой ветки, при этом она будет числиться влитой. -s ours используют осознанно: например, чтобы «закрыть» устаревшую ветку.

  9. Что такое rerere и когда он спасает? Это кэш разрешений конфликтов: при конфликте Git запоминает его нормализованную форму и ваше решение, а при точно таком же конфликте в будущем применяет его автоматически. Главные сценарии — долгоживущая релизная ветка, которую регулярно синхронизируют с main, и длинный rebase, который приходится повторять после --abort. Важная оговорка: rerere повторяет решение вслепую, не понимая, изменился ли смысл, поэтому после автоматического разрешения обязательны git diff HEAD и тесты. И это локальный кэш — у коллег и в CI его нет.

  10. Чем --force-with-lease отличается от --force и когда он всё равно не спасает? --force ставит ссылку на сервере в нужное значение безусловно. --force-with-lease сначала проверяет, что текущее значение серверной ветки совпадает с вашей remote-tracking копией, то есть что после вашего последнего fetch туда никто не пушил. Не спасает он тогда, когда ваш origin/<branch> обновился фоновым fetch'ем — от IDE, git maintenance или скрипта в статусной строке: lease совпадёт, и чужой коммит будет затёрт. Лечение — --force-if-includes, который проверяет, что верхушка серверной ветки присутствует в вашем reflog, то есть что вы её реально интегрировали.

  11. Почему git pull считают вредным по умолчанию? Потому что это fetch + merge, и он делает изменение в вашей ветке там, где вы ожидали просто «посмотреть, что нового»: создаёт неожиданные merge-коммиты, может остановиться посреди конфликта, а его поведение зависит от конфигурации, то есть на разных машинах одна команда делает разное. Практика: pull.ff only — тогда pull либо перематывает, либо честно отказывается; а слияние или rebase вы выбираете осознанно. Для повседневной работы достаточно git fetch плюс просмотр HEAD..@{u} и @{u}..HEAD.

  12. Что такое detached HEAD и опасно ли это? Это состояние, когда .git/HEAD содержит не символическую ссылку на ветку, а голый хеш коммита. Оно штатное: в нём работают bisect, внутренности rebase, и в него встают CI-исполнители при checkout по SHA. Коммиты в detached HEAD создаются нормально, но на них не указывает ни одна ветка, поэтому после переключения они становятся недостижимыми. Опасности нет ровно до тех пор, пока помнишь, что перед уходом надо создать ветку; а если забыл — коммиты находятся через reflog HEAD и живут до gc.

  13. Что такое индекс и почему git add — это не «пометить файл»? Индекс — бинарный файл .git/index с отсортированным списком записей: путь, режим, хеш blob'а, stat-метаданные и номер стадии. git add физически записывает содержимое файла как blob в базу объектов и кладёт его хеш в индекс. Отсюда следствия: добавленное восстановимо через fsck даже без коммита, а git add большого файла уже раздул базу, и git rm --cached её не уменьшит. Во время конфликта в индексе появляются три записи со стадиями 1/2/3 — база, наша и их версии, и именно это и есть механизм конфликта.

  14. Как найти коммит, сломавший поведение, и можно ли это автоматизировать? git bisect: задаём заведомо плохую и заведомо хорошую ревизии, Git бинарным поиском предлагает коммиты для проверки — порядка десяти шагов на тысячу коммитов. Автоматизация — git bisect run <скрипт>, где код возврата 0 означает good, 1 — bad, а 125 — «пропустить, не проверяется». Критерий не обязан быть «упало»: можно искать деградацию производительности, рост размера артефакта или изменение формата ответа. Ломают bisect три вещи — shallow clone, несобирающиеся коммиты и внешнее состояние вроде схемы БД.

  15. Как массовое форматирование ломает git blame и что с этим делать? Blame показывает последний коммит, изменивший строку, поэтому после переформатирования всех файлов автором каждой строки становится автор косметического коммита. Лечится флагом --ignore-rev <sha> и файлом .git-blame-ignore-revs в репозитории вместе с локальной настройкой blame.ignoreRevsFile. Профилактика: форматирование — отдельный коммит без изменений логики, его SHA сразу дописывается в файл, а проверка формата включается в CI в тот же день. Дополнительно git blame -w -C -C -M восстанавливает авторство перемещённых и скопированных строк.

  16. Чем git log -S отличается от -G? -S находит коммиты, где изменилось количество вхождений строки, то есть где её добавили или удалили; -G находит коммиты, в diff'е которых встретилось совпадение с регулярным выражением. Практически -S даёт короткий точный список «кто это ввёл и кто убрал», а -G ловит ещё и перемещения, переформатирование и частичные правки. Начинают с -S, а если он ничего не нашёл — переходят на -G. Оба работают по всей истории и не требуют, чтобы файл существовал сейчас.

  17. Что происходит при git cherry-pick и какие у него подводные камни? Вычисляется diff коммита относительно его родителя и применяется к текущему HEAD как трёхстороннее слияние, создавая новый коммит с тем же автором и сообщением, но новым SHA. Подводные камни: один логический патч живёт в двух коммитах, поэтому при последующем merge возможны дубли в истории или неожиданные конфликты; для merge-коммита нужен -m. Флаг -x дописывает строку «cherry picked from commit …» и обязателен при переносе между долгоживущими ветками — иначе через полгода происхождение кода не восстановить. Сверить перенесённое с оригиналом помогает git range-diff.

  18. Как узнать, что из релизной ветки не перенесено в main? git cherry -v main release/2026.03: команда сравнивает коммиты не по SHA, а по patch-id — хешу нормализованного diff'а, поэтому находит «те же изменения под другими именами». Знак «минус» означает, что патч уже есть в main, «плюс» — что его там нет. Это же объясняет, почему rebase иногда «выбрасывает» коммиты: их изменения уже есть в upstream. В конвейере такую проверку ставят гейтом, чтобы релиз не закрывался, пока есть неперенесённые фиксы.

  19. Как реагировать, если в репозиторий попал секрет? Первое и главное — ротация: отозвать и перевыпустить ключ, потому что он уже в клонах, кэшах CI, артефактах и бэкапах, и отозвать это невозможно. Второе — зафиксировать инцидент и область распространения. Третье — переписать историю на свежем зеркальном клоне через git filter-repo (не filter-branch, о чём предупреждает сам Git) и сделать force-push. Четвёртое — координация: все переклонируют, ветки перебазируют, иначе старые объекты вернутся на сервер. Пятое — остаточные копии: форки, кэш хостинга, образы, обсуждения MR; поэтому уборка без ротации бессмысленна.

  20. Что даёт --first-parent и почему это важно? У merge-коммита первый родитель — ветка, в которую вливали, второй — влитая. --first-parent заставляет log идти только по первому родителю, то есть показывать историю в терминах фич, а не отдельных коммитов внутри них. Это база для релиз-нот, ответа на вопрос «когда фича попала в релиз» и для git bisect --first-parent, который ищет среди сотни слияний вместо тысяч коммитов. Работает только при дисциплине «слияние всегда делается в main», иначе семантика родителей переворачивается.

  21. Какой статус у SHA-256 в Git в 2026 году? Формат объектов SHA-256 реализован и работает локально: репозиторий создаётся с --object-format=sha256, помечается repositoryformatversion=1 и расширением extensions.objectFormat. Чего нет — совместимости по сети с SHA-1-репозиториями: режим compatObjectFormat не доведён, и документация прямо не рекомендует SHA-256 на публичных серверах, пока протокол его не поддерживает. Плюс экосистема: миграция означает смену всех имён объектов, то есть обрыв всех ссылок на коммиты в задачах, релиз-нотах и логах аудита. Поэтому практика — SHA-1 со встроенным детектором коллизий.

  22. Partial clone, sparse-checkout, shallow clone — что и когда? Shallow (--depth) обрезает историю: даёт максимальную экономию и ломает describe, blame, bisect, merge-base и анализ «нового кода» в Sonar. Partial clone (--filter=blob:none) сохраняет весь граф коммитов и не скачивает содержимое файлов, подтягивая его по требованию: экономия сопоставимая, история цела, но log -p, blame и log -S становятся медленными и требуют доступности сервера. Sparse-checkout ограничивает не скачиваемое, а раскладываемое в рабочее дерево, и нужен для монорепо; в cone-режиме плюс sparse index он делает git status быстрым. В CI разумный выбор — partial clone, а не shallow, если задание хоть как-то работает с историей.

  23. Что такое Git LFS и какова его цена? LFS заменяет содержимое больших файлов текстовым указателем с версией спецификации, oid sha256: и размером, а данные хранит на отдельном сервере; подмена делается фильтрами clean при add и smudge при checkout. Цена: миграция существующей истории — это её переписывание со всеми последствиями; отдельная тарификация хранения и трафика; зависимость от доступности LFS-сервера; необходимость git lfs prune. Самая частая авария — отсутствие клиента или GIT_LFS_SKIP_SMUDGE=1 на исполнителе: в артефакт попадают указатели по сто с лишним байт, сборка при этом зелёная. Перед внедрением стоит спросить, обязан ли этот файл вообще лежать в Git, а не в артефактном хранилище.

  24. Submodule, subtree или монорепо? Submodule хранит в дереве родителя gitlink на конкретный коммит другого репозитория: точная фиксация ревизии и маленький клон ценой высокой сложности для потребителя и невозможности атомарного коммита через границу. Subtree копирует содержимое в подкаталог и живёт в вашей истории: обычный клон и атомарные коммиты ценой размытой истории и неудобной обратной отдачи. Монорепо снимает обе проблемы, но упирается в скорость сборки, необходимость CODEOWNERS и, главное, в невозможность разграничить доступ по каталогам — в банке это часто решающий аргумент. Если библиотеку можно опубликовать артефактом в Nexus — так и надо делать, не связываясь ни с тем, ни с другим.

  25. Что произойдёт, если два человека одновременно создадут одинаковый файл в разных ветках и ветки сольют? Если содержимое побайтово одинаково, blob будет один и тот же, и конфликта не возникнет — Git увидит, что обе стороны пришли к одному состоянию. Если содержимое отличается хоть на пробел, будет конфликт типа «added by both»: в индексе появятся стадии 2 и 3 без стадии 1, потому что базы для этого пути не существует. Такой конфликт нельзя разрешить трёхсторонним слиянием автоматически — придётся выбирать или объединять вручную. Это же объясняет, почему сгенерированные файлы стоит помечать merge=ours в .gitattributes — иначе они конфликтуют при каждом слиянии.

16. Попробовать руками

Все упражнения делаются в отдельном каталоге и ничего не ломают. Используйте git config user.email/user.name локально, чтобы не мешать основным настройкам.

Упражнение 1. Увидеть объекты своими глазами. Создайте репозиторий, сделайте один коммит с двумя файлами в подкаталоге. Выполните git cat-file -p HEAD, затем git cat-file -p HEAD^{tree}, затем git cat-file -p <хеш blob'а>. Отдельно посчитайте git hash-object -t blob --stdin < файл. Ожидаемый результат: хеш из hash-object совпадает с хешем в дереве; в объекте коммита нет ни одного diff'а; git count-objects -v показывает ровно столько объектов, сколько уникальных blob'ов + деревьев + 1 коммит.

Упражнение 2. Собрать коммит низкоуровневыми командами. Выполните последовательность из раздела 1.8: hash-object -w, update-index --cacheinfo, write-tree, commit-tree, update-ref. Ожидаемый результат: git log показывает ваш коммит, git status чист, при этом вы ни разу не вызвали git add и git commit.

Упражнение 3. Конфликт и три стиля маркеров. Создайте файл из пяти строк, ответвите ветку, измените в обеих ветках одну и ту же строку и сделайте merge. Посмотрите файл. Затем git merge --abort и повторите с -c merge.conflictStyle=diff3, затем с zdiff3. Отдельно постройте случай, где обе стороны добавили одинаковую строку в начале блока (пример из 2.5). Ожидаемый результат: в diff3 появляется секция ||||||| с базой; в zdiff3 на многострочном конфликте общие строки вынесены за маркеры. git ls-files -u показывает три записи со стадиями 1, 2, 3.

Упражнение 4. rerere в действии. Включите rerere.enabled, вызовите конфликт, разрешите, закоммитьте (увидите «Recorded resolution»). Затем git reset --hard HEAD~1 и повторите тот же merge. Ожидаемый результат: маркеров в файле нет — разрешение применено автоматически; git status при этом показывает UU, то есть файл всё ещё требует git add. ls .git/rr-cache содержит каталог с хешем конфликта.

Упражнение 5. Воспроизвести ловушку revert'а merge-коммита. Создайте ветку с новым файлом, влейте её с --no-ff, сделайте git revert -m 1 HEAD, затем попробуйте git merge той же ветки. Ожидаемый результат: Already up to date., файла в дереве нет. После git revert --no-edit <sha-revert-коммита> файл возвращается, а сообщение коммита начинается с Reapply "…". Затем повторите с доработкой ветки и убедитесь, что revert-of-revert приносит старую версию.

Упражнение 6. Потерять и восстановить коммиты. Сделайте пять коммитов, выполните git reset --hard HEAD~3, затем восстановите тремя способами: через ORIG_HEAD, через git reflog и через git fsck --lost-found (для последнего сначала удалите reflog-запись: git reflog expire --expire=now --all). Ожидаемый результат: все три способа приводят к одному SHA; после git reflog expire git fsck --no-reflogs --lost-found показывает dangling commit с нужным хешем.

Упражнение 7. Разбить коммит на два. Сделайте один коммит, меняющий два файла. Запустите git rebase -i HEAD~1, поставьте edit, выполните git reset HEAD^, затем git add -p первого файла и git commit, затем остальное и git commit, затем git rebase --continue. Ожидаемый результат: git log --oneline показывает два коммита вместо одного; git diff <старый-коммит> HEAD пуст — итоговое состояние идентично.

Упражнение 8. --autosquash как ежедневная практика. Сделайте три коммита, затем правку и git commit --fixup <sha-первого>. Выполните git rebase -i --autosquash <база>. Ожидаемый результат: в todo-списке fixup-коммит уже стоит сразу после своей цели и помечен fixup; после сохранения в истории снова три коммита, а изменения из fixup вошли в первый.

Упражнение 9. bisect run на реальном критерии. Создайте 15 коммитов, в седьмом внесите «поломку» (например, строку, которую ищет grep). Запустите git bisect start HEAD <первый> и git bisect run sh -c 'grep -q ПОЛОМКА file && exit 1 || exit 0'. Ожидаемый результат: вывод bisect found first 'bad' commit с SHA седьмого коммита, порядка четырёх шагов вместо пятнадцати. Повторите, добавив в середину несобираемый коммит и возвращая из скрипта 125, — bisect его пропустит.

Упражнение 10. Убить и вылечить git blame. Сделайте два содержательных коммита в Java-файле, затем третий — массовое переформатирование. Посмотрите git blame. Создайте .git-blame-ignore-revs с SHA третьего коммита и настройте blame.ignoreRevsFile. Ожидаемый результат: до настройки почти все строки приписаны форматирующему коммиту, после — вернулись к настоящим авторам. Отдельно проверьте, что git log -L :имяМетода:File.java падает с «no match» без *.java diff=java в .gitattributes и работает после его добавления.

Упражнение 11. Найти и вырезать крупный объект. Закоммитьте файл на 5–10 МБ (head -c 10000000 /dev/urandom > big.bin), сделайте ещё пару коммитов, удалите файл коммитом. Посмотрите git count-objects -vH — размер не уменьшился. Найдите объект командой из 11.1. Затем на клоне --mirror выполните git filter-repo --invert-paths --path big.bin (или --strip-blobs-bigger-than 1M). Ожидаемый результат: до чистки size-pack порядка 10 МБ и blob виден в списке крупнейших; после — size-pack в килобайтах, git rev-list --objects --all | grep big.bin пуст, а origin у зеркала удалён самим filter-repo.

Упражнение 12. Сэмулировать force-push-аварию и восстановиться. Сделайте локальный «сервер»: git clone --bare repo server.git, затем два клона от него. В первом сделайте коммит и запушьте. Во втором, не делая fetch, сделайте свой коммит и git push --force. Убедитесь, что коммит из первого клона исчез из server.git. Восстановите его: найдите SHA в первом клоне (git reflog show origin/main либо git log), выполните git push --force-with-lease origin <sha>:main или merge-back. Затем повторите эксперимент с --force-with-lease --force-if-includes. Ожидаемый результат: голый --force затирает чужой коммит; --force-with-lease отклоняется с stale info; после git fetch (имитация фонового fetch от IDE) lease перестаёт защищать, а --force-if-includes продолжает отклонять push. Восстановление через прямой push SHA возвращает ветку в прежнее состояние.

Упражнение 13 (дополнительное). Стек веток и --update-refs. Создайте part1 от main, part2 от part1, добавьте коммит в main, затем на part2 выполните git rebase --update-refs main. Ожидаемый результат: вывод содержит «Updated the following refs with --update-refs: refs/heads/part1», и git log --oneline --decorate показывает part1 на своём месте в новой линейной истории, а не на старом коммите.
