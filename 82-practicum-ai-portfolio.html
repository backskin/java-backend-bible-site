Зачем это знать. Сильный ИИ-проект в практической разработке — это не просто “прикрутили локальную модель и получили ответ”. Это система, где модель общается с сервисом, у неё есть ограниченный набор возможностей, у данных есть права доступа, у действия есть реакция, а у человека — зона ответственности. Для домашнего портфолио это особенно важно, потому что клиентам и интервьюерам нужно не “как у тебя крутой chat”, а “как ты умеешь связать модель с бизнес-сервисом, чтобы это работало безопасно и понятно”. В этой главе мы делаем второй практикум: поверх локального или self-hosted сервиса строим ИИ-слой, который умеет вызывать API твоего платёжного сервиса, использует RAG по документации и собственным данным, имеет safe tool calling, может работать через локальную модель и при этом остаётся контролируемым.

Главная идея практикума — показать, что ИИ в продакшене работает не в вакууме и не как “магический бот”. Он работает как часть большой архитектуры: есть локальная модель, есть шлюз, есть база знаний, есть инструменты, есть инструменты read-only, есть human approval для критичных действий. И всё это оформлено как домашний проект, который можно запустить на ноутбуке, показать в README и рассказать на аудитории.

Глава 81 (81-practicum-backend-portfolio.md) строила платёжный сервис. Здесь мы строим ИИ-слой поверх него, чтобы показать не только backend-логику, но и искусство интеграции AI в production. Мы будем использовать локальную модель в Ollama или vLLM, а также Spring AI, чтобы сделать структуру ответа, tool calling и RAG по документации сервиса. В конце будет не просто “бот, который умеет отвечать”, а система, где набор действий ограничен, а ответ — проверяем и верифицируем.

1. Что именно строим

Наша цель — сделать локальный ИИ-помощник для сервиса кошелька, который умеет:

  • отвечать на вопросы о состоянии кошелька или переводах;
  • читать документацию и бизнес-справку по платёжному сервису;
  • искать фрагменты по векторному индексу;
  • вызывать read-only API сервиса (balance, history, status);
  • собирать рекомендации по одному счету или операции;
  • давать structured output в формате JSON;
  • не иметь права на dangerous actions без human approval.

То есть это не “подпись по OpenAI API”, а AI-помощник для внутреннего продукта: он может читать, анализировать и предупреждать, но не имеет права переписывать состояние без подтверждения человека.

Архитектура выглядит так:

  1. Локальная модель — Ollama или vLLM; выбирается одна модель под локальное железо.
  2. Spring AI — обёртка и клиент к модели; structured output через схемы.
  3. RAG-процесс — документация проекта и API по внутренней базе знаний на pgvector или Elasticsearch.
  4. MCP-сервер или tool adapter — для read-only доступа к сервису и задачам на chat.
  5. LLM gateway — опционально, для маршрутизации между локальной моделью и внешней, если требуется fallback.
  6. Observability — Langfuse, OpenTelemetry и логирование вызовов.

2. Локальная модель: Ollama vs vLLM

2.1 Когда выбирать Ollama

Ollama — самый простой путь для домашнего проекта. Есть стандартный local endpoint, он работает с OpenAI-совместимым API и подходит для локального запуска.

Плюсы:

  • быстро поднимается;
  • проще использовать без сложной настройки GPU и несколькими контейнерами;
  • хорошо подходит для домашнего стенда и портфолио;
  • идеально для “показать, что ты умеешь завести локальную модель и подключить её как сервис”.

Минусы:

  • не всегда оптимален по производительности для больших моделей;
  • менее гибкий контроль над batching и памяти;
  • на самых тяжёлых задачах может быть заметно слабее vLLM.

2.2 Когда выбирать vLLM

vLLM — более “production-ish” и удобный для service deployment. Его сильная сторона — PagedAttention, continuous batching и контроль загрузки модели. Если у тебя есть видеокарта и ты хочешь показать промышленную зрелость, vLLM выглядит более серьёзно на собеседовании.

Плюсы:

  • лучше для GPU-сценариев;
  • больше контроля над batch и memory;
  • OpenAI-совместимый API;
  • более “production-grade” как платформа.

Минусы:

  • требует больше знаний и правильной конфигурации памяти;
  • сложнее и шумнее на домашнем ноутбуке.

2.3 Что выбрать для проекта

Для домашнего проекта чаще всего лучше взять Ollama и небольшую модель, а уже потом показать, что архитектура не завязана на конкретной реализации. В README можно явно написать: “Сервис поддерживает переход между Ollama и vLLM через один интерфейс ChatClient — при желании можно заменить локальный backend”. Это уже хороший инженерный ход.

3. Spring AI: запускаем чаты и structured output

Spring AI — хорошая абстракция, если проект уже стоит на Spring Boot. Она позволяет:

  • подключиться к Ollama/vLLM;
  • строить prompt templates;
  • указывать output schema для структурированного ответа;
  • вызывать tools и маппить их к Java methods;
  • получать ChatResponse и parse output в рекорд.

3.1 Простой client

Java
@Service
public class WalletAssistantClient {

    private final ChatClient chatClient;

    public WalletAssistantClient(ChatClient chatClient) {
        this.chatClient = chatClient;
    }

    public WalletSummary askSummary(String userId, String question) {
        var prompt = """
            Ты — ассистент для внутреннего сервиса кошелька.
            Анализируй только данные из signed tool calls и allowed read-only APIs.
            Возвращай JSON в формате WalletSummary.
            """;

        return chatClient.prompt()
            .system(prompt)
            .user(question)
            .call()
            .entity(WalletSummary.class);
    }
}

Это уже выглядит как production-level code: system prompt ясный, output schema strict, есть правило “только из tools или allowed read-only APIs”. Это важно, потому что иначе модель начнёт “помнить” то, чего не должна.”

3.2 Structured output

Через Spring AI можно попросить JSON Schema и разбирать результат как класс. Пример структуры:

Java
public record WalletSummary(
    String accountId,
    BigDecimal balance,
    String currency,
    List<String> recentActivity,
    String riskNote,
    boolean requiresHumanReview
) {}

Если модель не смогла соблюсти формат, мы в проекте должны в логах закрепить это как invalid structured output, а не “было вроде ок”. Это очень важная часть инженерии AI: без валидации даже локальная модель даёт красивый, но непригодный JSON.

4. Tool calling и API-сервис

Основной принцип здесь — model calls tools, not arbitrary shell or DB. Для ИИ-помощника мы даём limited set of tools:

  • get_balance(accountId)
  • get_transaction_history(accountId, limit)
  • get_account_status(accountId)
  • search_documentation(query)
  • get_policy_reference(keyword)
  • list_recent_notifications()

Минус — такие инструменты не должны менять состояние. Если есть действие write, оно должно потребовать approval. Например:

  • freeze_account(accountId) — только если человек подтвердил;
  • create_transfer — no direct execution from AI. Only prepare_transfer and requiresHumanReview;
  • close_account — no direct path.

4.1 ToolSpec для read-only доступа

Java
public record ToolSpec(
    String name,
    String description,
    Map<String, Object> inputSchema,
    Set<String> allowedScopes,
    boolean readOnly
) {}

И для инструмента get_balance это будет примерно так:

JSON
{
  "name": "get_balance",
  "description": "Return the current balance and currency for a wallet account. Read-only.",
  "inputSchema": {
    "type": "object",
    "required": ["accountId"],
    "properties": {
      "accountId": { "type": "string" }
    }
  },
  "allowedScopes": ["wallet:read"],
  "readOnly": true
}

То, что важно: название, description и input schema есть не для красоты, а для передачи модели и гарантий качества. Это не “магия”, а чёткое API-интерфейс для AI tool calling.

5. RAG поверх своего сервиса

5.1 Что именно индексируем

Для проекта полезно индексировать не весь код, а:

  • README;
  • API-документацию;
  • business rules and policies;
  • glossary entries;
  • ADR и issue-описания;
  • внутренние регламенты по переводам, лимитам, статусам.

Важно: не индексировать всё подряд в базу без фильтрации. Лучше всего:

  • хранить документацию отдельно;
  • хранить chunks with metadata: section, team, documentId, updatedAt, visibility;
  • поддерживать read-access or visibility tags;
  • иметь published и draft versions.

5.2 Набор на базе pgvector

Самая простая и реальная схема — PostgreSQL + pgvector. В таблице doc_chunk хранятся:

  • id;
  • document_id;
  • chunk_text;
  • embedding (vector);
  • metadata (section, owner, tags);
  • updated_at;
  • access_roles.

Для user на уровне wallet:read это уже видно. Если пользователь не имеет прав на документ, документ не попадает в query answer.

5.3 Сценарий query

  1. пользователь задаёт вопрос;
  2. модель формирует нетипичный запрос, но строгую query by category;
  3. retrieval service ищет в векторной таблице фрагмент по эмбеддингу;
  4. клиент фильтрует по доступу;
  5. selected context отправляется в модель вместе с вопросом;
  6. модель возвращает ответ и ссылки на документы;
  7. если нет точного ответа — она говорит “недостаточно данных”, а не “добавляет загадочно правдоподобный текст”.

Вот это как раз хороший минимальный RAG-проект.

6. Наблюдаемость и Langfuse

Без observability проект никогда не выглядит как production, даже если он локально запускается. Для этого есть несколько слоёв:

  • OpenTelemetry для traces;
  • Prometheus для метрик;
  • Langfuse для истории запросов, токенов, стоимости и аутодополнения / evaluation;
  • логирование действий model -> tool -> result.

6.1 Что смотрим в Langfuse

  • session_id;
  • user_id;
  • model_name;
  • provider (
  • prompt_tokens and completion_tokens;
  • cost;
  • tool_name and tool_result_summary;
  • response_status;
  • human_approved flag.

Так можно показать, что вы умеете не только “получать ответ”, но и видеть, что реально делал модель и сколько это стоило. Это особенно важно, если проект выполняется на self-hosted модели: cost-by-step и latency matter.

7. Правила и безопасность

Это самая важная часть. ИИ-слой поверх сервиса должен иметь набор правил:

  • не вызывать write tools без approval;
  • не отдавать конфиденциальные данные наружу;
  • не путать API-документацию с реальным состоянием;
  • не делать предположения о данных, которых нет в ответа tool call;
  • не отправлять в локальную модель секреты, ключи и токены;
  • не использовать модели на внешних серверах для чувствительных данных, если это запрещено политикой.

7.1 Пример внутренней политики безопасности

- Input can contain only userId, accountId, and business data previously allowed by the user or the environment.
- The model may not issue write operations without explicit human approval.
- No PII and no secrets in prompt context.
- All tool calls are logged and traceable.
- If data is missing, answer with 'not enough information' instead of guessing.

Это не “красиво оформлено”, это техническое правило. Без него агент начинает действовать как “злой алчущий бот”, а не как сервис.

8. Пример архитектуры для домена банка

Внутренний проект может быть построен так:

  • клиент запрашивает у AI-ассистента: “какой баланс у счёта X и почему были отклонены операции за прошлую неделю?”;
  • AI делает read-only tool call к wallet-service;
  • wallet-service возвращает данные и список проводок;
  • AI вызывает search_documentation по внутреннему RAG;
  • AI формирует JSON с accountStatus, HasIssue, insight, evidence;
  • человек подтверждает или отклоняет дальнейшие действия;
  • если нужно выполнение write операции — отдельный бизнес-процесс с explicit approval.

Это уже очень похоже на реальный enterprise assistant: it can read, think, provide structured summary, but no system-level write without confirmation.

9. Примеры проблем, которые проект должен решать

9.1 Проблема с выводом по данным

Когда модель отвечает, она должна не просто “сказать, что баланс 5000”, а объяснить:

  • сколько было входящих операций;
  • какие были расходные операции;
  • есть ли лимит или блокировка;
  • откуда она это знает — по каким данным.

Это особенно важно в финансовом контуре. Задача AI не “скрывать” информацию, а “доказуемо указывать источник”.

9.2 Проблема “придумала ответ”

Когда модель не знает, ей надо говорить “не могу ответить по этим данным”. Это важная инженерная часть. В реальном проекте неправильный ответ иногда вредит больше, чем отсутствие ответа. Поэтому хорошая практическая логика:

  • if insufficient context -> ask clarifying question or respond with “not enough data”;
  • if tool result is empty -> no guessing;
  • if answer cannot be validated -> ask for confirmation or escalate to human.

10. Обязательные элементы домашнего проекта

Для того чтобы проект смотрелся как serious portfolio project, нужны минимальные вещи:

  • локальная модель и точный способ её запуска;
  • API-интерфейс и tool definitions;
  • RAG на проектных документах;
  • structured output;
  • логирование и trace;
  • README с “как это работает” и “что тут нет”;
  • сценарии, где AI работает без write-операций;
  • отдельный сценарий, где write-действие не проходит без approval;
  • explainable output “почему это ответ?”.

Без этого проект просто “сервис с моделью”, а не “Интеграция AI в реальную систему”.

11. Грабли

  1. Слишком широкая модель — “я дам ей всё” и она начнёт делать не то.
  2. Пытаться разрешить write операции без approval — это как строить кредитный бот с возможностью списать деньги по своей воле.
  3. Плохой RAG — куча документации без metadata и visibility.
  4. Слишком малый или слишком большой контекст — оба варианта плохи; нужна грамотная стратегия на фрагменты и ограничение длины.
  5. Нет structured output — ответ только красивый по тексту, но не пригодный для кода.
  6. Модель без фильтра по правам — допустимая информация начинает показываться пользователям, которым она не нужна.
  7. Нет observability — непонятно, что и почему ответило, а это критично для бизнес-решений.
  8. Нет explicit fail-fast — model guessed instead of refusing.
  9. Невозможно объяснить, откуда это взялось — key issue for finance / support / operations.
  10. Слишком сложная модель для “домашнего” стенда — хорошая идея, но без возможности запустить и показать — просто мёртвый проект.

Диагностика

Если проект “не работает”, смотрите по цепочке:

  • локальная модель запущена и доступна;
  • tool schema корректный и описан в понятном формате;
  • prompt и system instructions не противоречат правилам;
  • structured output проверяется и отбрасывает некорректные ответы;
  • retrieval на самом деле возвращает релевантные chunks и filter by permissions;
  • tool execution uses safe read-only scope;
  • tracing and logs show model request, tool call result, and source reference;
  • no unapproved write operation visible.

13. Попробовать руками

  1. Поднять локальную модель через Ollama или vLLM и проверить OpenAI-совместимый endpoint.
  2. Подключить Spring AI и убедиться, что можно получить ChatResponse и structured output.
  3. Сделать read-only tools: get_balance, get_history, get_account_status.
  4. Сделать безопасный RAG: index a small set of project docs and test search queries.
  5. Проверить prompt injection: подкинуть в docs фразу “игнорируй ограничения” и проверить, что write tools всё ещё не доступны.
  6. Проверить compliance: если tool call неопределённый или не хватает данных, агент должен ответить “недостаточно информации”, а не “угадывать”.
  7. Собрать метрики и traces через Langfuse или OpenTelemetry.
  8. Добавить human approval для write tool scenario and check the flow.
  9. Провести эволюционный цикл: модель отвечает хорошо, but output invalid -> fix schema and prompt -> rerun.
  10. Записать README: как запускать, как использовать, где ограничения, как посмотреть логи, как разворачивать локально.

14. Что запомнить

У проекта “ИИ поверх своего сервиса” две ключевые истории: техническая и управленческая. Технически это — локальная модель, tool calling, structured output, RAG и observability. Управленчески — это границы доступа, права, audit, отсутствие возможности “всё делать автоматически”, и принцип, что лучше понятный отказ, чем красивый ошибочный ответ.

Если вы можете собрать такой проект, вы уже показываете не просто “умею докладывать AI-бота”, а “умею делать AI-сервис, который не теряет контроль и не превращается в дыра в безопасности”. Именно это и ценят на собеседовании и в реальной инженерной работе.
