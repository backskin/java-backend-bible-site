Зачем это знать

Три часа ночи, прод не отвечает, DevOps в отпуске, а у тебя есть только SSH и пятнадцать минут до эскалации. Разница между «сервис лежит» и «сервис жив, но упёрся в accept-очередь, потому что пул потоков занят ожиданием DNS» — это пять команд в терминале, которые надо знать наизусть. 1. Процессы и их жизненный цикл

1.1 PID, PPID и дерево процессов

Процесс в Linux — это адресное пространство плюс один или несколько потоков выполнения. В ядре и то и другое представлено структурой task_struct; с точки зрения ядра поток — это «task», который делит адресное пространство с другими task'ами. Отсюда важное следствие, которое постоянно всплывает при диагностике JVM: каждый Java-поток — это отдельная запись в ядре, у неё есть свой TID, своё состояние, свой счётчик CPU-времени, и всё это видно в /proc/<pid>/task/<tid>/.

Идентификаторы:

  • PID — идентификатор процесса (в терминах ядра — TGID, thread group ID);
  • TID — идентификатор потока; у главного потока TID == PID;
  • PPID — PID родителя;
  • PGID / SID — группа процессов и сессия, нужны для доставки сигналов группе (kill -TERM -<PGID>).

Дерево процессов смотрят так:

Bash
# Полное дерево с PID и аргументами
ps -eo pid,ppid,pgid,stat,rss,etime,cmd --forest

# Дерево от конкретного процесса
pstree -paul 12345

# Кто родитель — из /proc
grep -E '^(Name|Pid|PPid|Threads|State)' /proc/12345/status

Типичный вывод status:

Name:	java
State:	S (sleeping)
Tgid:	12345
Pid:	12345
PPid:	1
Threads:	287

PPid: 1 в контейнере означает, что процесс — прямой потомок PID 1, а если ещё и Pid: 1, то JVM сама является init-процессом со всеми вытекающими (не пожинает сирот, игнорирует сигналы без явного обработчика). Подробности про PID 1, --init, tini и зомби — в главе 46 (46-docker-jvm.md).

1.2 Состояния процесса: R, S, D, Z, T

Колонка STAT в ps и S в top — одна буква, которая часто решает инцидент. Значения документированы в proc_pid_stat(5) (man7.org):

Код Название по man Практический смысл
R Running Выполняется на CPU или стоит в runqueue готовый к выполнению. R не значит «жрёт процессор прямо сейчас» — значит «хочет процессор».
S Sleeping in an interruptible wait Ждёт события и может быть разбужен сигналом. Нормальное состояние 95 % потоков JVM: ждут на epoll_wait, futex, poll.
D Waiting in uninterruptible disk sleep Ждёт завершения операции ввода-вывода в ядре и не реагирует на сигналы, включая SIGKILL.
Z Zombie Завершился, но родитель не вызвал wait(). Занимает только запись в таблице процессов.
T Stopped (on a signal) Остановлен SIGSTOP/SIGTSTP, продолжается SIGCONT.
t Tracing stop (Linux 2.6.33+) Остановлен отладчиком (ptrace), в том числе strace/gdb/jattach.
I Idle (Linux 4.14+) Простаивающий поток ядра; не учитывается в load average.
X Dead Переходное, в выводе практически не встречается.

К букве добавляются модификаторы: < — высокий приоритет, N — низкий (nice > 0), l — многопоточный, s — лидер сессии, + — в foreground-группе терминала.

🔧 Под капотом. Почему D — это почти всегда диск. TASK_UNINTERRUPTIBLE — состояние, в которое ядро переводит задачу, когда пробуждение не может быть отменено сигналом без нарушения инварианта в ядре. Классический пример: страница подкачивается с блочного устройства, драйвер уже отправил запрос, структуры заняты. Прервать это по сигналу нельзя, потому что некому корректно откатить состояние. Отсюда и знаменитое «процесс не убивается kill -9»: сигнал доставлен, помечен как pending, но обработается только после выхода из D. Если диск (или NFS, или сетевой том EBS/Cinder) не отвечает — процесс висит в D бесконечно. Не только диск: D бывает при обращении к «залипшему» NFS-маунту, при работе с FUSE-файловой системой, у которой умер userspace-демон, при прямой записи в медленное устройство, изредка при mlock/madvise и при работе с overlayfs поверх медленного хранилища. Но в 9 случаях из 10 в бэкенд-контексте это блочный I/O.

Как быстро проверить, чем занят процесс в D:

Bash
# Все задачи в D-состоянии по всей системе (включая потоки)
ps -eL -o pid,tid,stat,wchan:30,comm | awk '$3 ~ /D/'

# Ядровый стек конкретного потока — что именно он ждёт
sudo cat /proc/12345/task/12399/stack

# Точка ожидания в ядре одной строкой
cat /proc/12345/task/12399/wchan; echo

Пример стека, который однозначно указывает на блочный I/O:

[<0>] wait_on_page_bit_common+0x1c8/0x3f0
[<0>] folio_wait_bit+0x30/0x40
[<0>] folio_wait_writeback+0x28/0x80
[<0>] __filemap_fdatawait_range+0x8b/0x120
[<0>] file_write_and_wait_range+0x74/0xb0
[<0>] ext4_sync_file+0x8d/0x350
[<0>] do_fsync+0x38/0x70

Это fsync() — приложение (или, чаще, драйвер БД / commit-log Kafka / сам JVM при записи heap dump) ждёт подтверждения записи. Если такой стек висит секундами, проблема в хранилище, а не в Java.

⚠️ Осторожно. Java-поток в состоянии D не виден в thread dump как проблемный. jstack покажет его как RUNNABLE, потому что с точки зрения JVM поток не заблокирован на Java-мониторе — он выполняет нативный вызов. Классическая ловушка: thread dump «чистый», все потоки RUNNABLE, а приложение стоит. Проверка — top -H -p <pid> и колонка S: если там пачка D, дело не в Java.

1.3 Псевдофайловая система /proc/<pid>/

Псевдофайловая система /proc — единственное место, где можно посмотреть реальное состояние процесса без всяких агентов. Всё документировано в proc(5). Что реально нужно бэкенд-разработчику:

Путь Польза Применение
status Имя, состояние, PPid, Threads, VmRSS, VmSwap, VmPeak, FDSize, Cpus_allowed_list, voluntary_ctxt_switches Первое, что читаешь. Всё важное одной командой.
limits Эффективные лимиты этого конкретного процесса (soft/hard) Когда ulimit -n в твоей shell говорит одно, а сервис упал с Too many open files.
fd/ Символические ссылки на все открытые дескрипторы Поиск утечки fd.
fdinfo/<n> Позиция, флаги, для epoll — список отслеживаемых fd Разбор поведения Netty/NIO.
maps Карта виртуальной памяти: диапазоны, права, файл Что замапплено, где нативные библиотеки.
smaps / smaps_rollup То же плюс RSS/PSS/USS/Swap по каждому отображению Разбор роста RSS. smaps_rollup — итог одной строкой, читается на порядок быстрее.
stack Ядровый стек (нужен root и CONFIG_STACKTRACE) Разбор D-состояния.
environ Переменные окружения на момент старта (\0-разделённые) Проверить, какие JAVA_OPTS реально долетели.
cmdline Аргументы запуска То же самое для флагов JVM.
task/<tid>/ То же для каждого потока Поиск потока-пожирателя CPU.
io read_bytes, write_bytes, rchar, wchar Кто пишет на диск.
sched / schedstat Время на CPU, время в runqueue, число переключений Доказательство, что процесс ждёт CPU, а не работает.
net/ Сетевые счётчики сетевого namespace процесса В контейнере — единственный способ увидеть его собственную статистику.
cgroup В какой cgroup находится процесс Найти путь под /sys/fs/cgroup.

Рабочие приёмы:

Bash
# Переменные окружения в читаемом виде
tr '\0' '\n' < /proc/12345/environ | sort

# Командная строка в читаемом виде
tr '\0' ' ' < /proc/12345/cmdline; echo

# Сколько дескрипторов открыто и каков лимит
ls /proc/12345/fd | wc -l
grep 'Max open files' /proc/12345/limits

# Сводка по памяти одной командой
grep -E '^(VmPeak|VmSize|VmRSS|VmSwap|RssAnon|RssFile|RssShmem|Threads)' /proc/12345/status

# Сколько процесс прочитал/записал с диска за всю жизнь
cat /proc/12345/io

Вывод io стоит расшифровать, потому что его постоянно путают:

rchar: 918273645          # байт прочитано через read()/pread() — включая page cache
wchar: 273645918          # байт записано через write() — включая page cache
syscr: 1204551            # число вызовов чтения
syscw: 883412             # число вызовов записи
read_bytes: 4096000       # реально поднято с блочного устройства
write_bytes: 12582912     # реально отправлено на блочное устройство
cancelled_write_bytes: 0  # записи, отменённые до сброса (truncate/delete)

Разрыв между wchar и write_bytes — это page cache: приложение «записало» в память, ядро сбросит позже. Если read_bytes близок к нулю при большом rchar — всё читается из кеша, диск не при чём.

💡 На интервью. «Как посмотреть, что процесс делает прямо сейчас?» — правильный ответ не «strace». Порядок: top -H -p <pid> (какой поток горит), /proc/<pid>/task/<tid>/stack и wchan (что ждёт в ядре), jstack/jcmd Thread.print (что делает в Java), и только если этого мало — strace -f -p <pid> -c на несколько секунд, помня, что он замедляет процесс в разы.

1.4 Приоритеты: nice и ionice

nice — от −20 (наивысший приоритет) до +19 (низший), по умолчанию 0. Влияет на вес задачи в планировщике CFS. Повысить приоритет (уменьшить nice) может только root.

Bash
# Запустить с пониженным приоритетом
nice -n 10 ./batch-job.sh

# Изменить приоритет работающего процесса
renice -n 5 -p 12345

# Приоритет ввода-вывода: класс 3 = idle, 2 = best-effort (0..7), 1 = realtime
ionice -c 2 -n 7 -p 12345

Практическая ценность для бэкенд-разработчика ограничена, но есть два реальных сценария. Первый: ночной пакет (генерация отчётов, реиндексация) на той же машине, что и онлайн-сервис — nice 10 + ionice -c 3 заметно снижает влияние на latency онлайна. Второй: ionice -c 3 для процесса, который снимает heap dump или делает rsync бэкапа, — иначе он выест весь IOPS-бюджет.

⚠️ Осторожно. ionice работает только с планировщиками ввода-вывода, которые его поддерживают (CFQ/BFQ). На современных ядрах с none/mq-deadline для NVMe класс приоритета фактически игнорируется. Проверить: cat /sys/block/nvme0n1/queue/scheduler.

В контейнерах вместо nice правильнее использовать cpu.weight в cgroup — см. раздел 3.

1.5 Сигналы

Сигнал — асинхронное уведомление процессу. Номера и действия по умолчанию — из signal(7) (man7.org):

Сигнал № (x86/ARM) Действие по умолчанию Смысл Действие JVM
SIGHUP 1 Term Обрыв терминала / «перечитай конфиг» по соглашению Завершение (shutdown hooks выполняются)
SIGINT 2 Term Ctrl+C Завершение через shutdown hooks
SIGQUIT 3 Core Ctrl+\ Печатает thread dump в stdout и продолжает работать
SIGABRT 6 Core abort(), внутренняя ошибка Аварийное завершение, hs_err_pid*.log
SIGBUS 7 Core Некорректный доступ к памяти (выравнивание, обрезанный mmap-файл) hs_err_pid*.log, краш
SIGKILL 9 Term Убить немедленно Перехватить нельзя, hooks не выполняются
SIGUSR1 10 Term Пользовательский Используется JVM внутренне (в т.ч. для safepoint-механик на некоторых платформах)
SIGSEGV 11 Core Обращение по некорректному адресу JVM штатно ловит для null-check и обработки stack banging; настоящий краш → hs_err_pid*.log
SIGUSR2 12 Term Пользовательский Используется JVM внутренне
SIGPIPE 13 Term Запись в закрытый сокет/пайп JVM игнорирует, write() возвращает EPIPE → IOException: Broken pipe
SIGTERM 15 Term Вежливая просьба завершиться Запускает shutdown hooks
SIGCHLD 17 Ign Дочерний процесс завершился Обрабатывается механизмом Process
SIGCONT 18 Cont Продолжить после остановки —
SIGSTOP 19 Stop Остановить Перехватить нельзя

Два сигнала неперехватываемы: «The signals SIGKILL and SIGSTOP cannot be caught, blocked, or ignored» (signal(7)). Это архитектурная гарантия: администратор всегда может убить или заморозить процесс.

Диспозиции сигналов наследуются через fork() («A child created via fork(2) inherits a copy of its parent's signal dispositions»), а при execve() обработчики сбрасываются в значение по умолчанию, но игнорируемые остаются игнорируемыми. Отсюда практическое следствие: если родительский shell-скрипт сделал trap '' PIPE, запущенная из него JVM унаследует игнорирование — обычно это не мешает, но при отладке «почему процесс не реагирует на сигнал» проверять стоит: grep -E 'SigIgn|SigBlk|SigCgt' /proc/<pid>/status (маски в hex, бит N+1 = сигнал N).

Bash
# Расшифровать маску пойманных сигналов
grep SigCgt /proc/12345/status
# SigCgt:	2000000181005ccf
# Проверить бит для SIGTERM (15): (0x2000000181005ccf >> 14) & 1

1.6 Thread dump по сигналу SIGQUIT

Это самый недооценённый приём в арсенале. HotSpot JVM устанавливает обработчик SIGQUIT, который печатает полный thread dump в stdout процесса и продолжает работу:

Bash
kill -3 12345
# или
kill -QUIT 12345

Почему это важнее, чем jstack:

  • работает, когда jstack не может присоединиться (например, attach-механизм сломан, файл /tmp/.java_pid<pid> удалён по cron'у, процесс в другом PID namespace);
  • не требует, чтобы jcmd/jstack той же версии лежал в образе (в distroless-образе JDK-тулов просто нет);
  • гарантированно работает из другого контейнера в том же поде через kubectl exec + nsenter, если PID namespace общий.

Куда попадёт дамп: в stdout JVM. В Kubernetes — в лог пода (kubectl logs), в systemd — в journal, при запуске через nohup — в nohup.out. Если приложение перенаправляет stdout в /dev/null (иногда делают в Docker-entrypoint), дамп потеряется. Явно задать файл можно флагом:

Bash
java -XX:+UnlockDiagnosticVMOptions -XX:LogFile=/var/log/app/vm.log ...

Полезные соседи по той же механике:

Bash
# Thread dump без SIGQUIT
jcmd 12345 Thread.print

# Гистограмма объектов в heap без полного дампа
jcmd 12345 GC.class_histogram

# Native Memory Tracking (нужен запуск с -XX:NativeMemoryTracking=summary)
jcmd 12345 VM.native_memory summary

# Все флаги JVM, включая вычисленные эргономикой
jcmd 12345 VM.flags -all

⚠️ Осторожно. kill -3 в цикле каждую секунду — плохая идея: печать thread dump останавливает все потоки в safepoint. На приложении с 2000 потоков дамп занимает сотни миллисекунд. Три дампа с интервалом 5–10 секунд дают достаточно информации для поиска «залипшего» потока; больше не нужно.

1.7 Shutdown hooks в JVM

SIGTERM в JVM приводит к запуску shutdown hooks, зарегистрированных через Runtime.getRuntime().addShutdownHook(Thread). Spring Boot регистрирует свой хук, который закрывает ApplicationContext; с версии 3.4 graceful shutdown включён по умолчанию (см. FACTS и главу 10).

Java
public final class GracefulShutdown {

    public static void install(ExecutorService pool, Duration grace) {
        Runtime.getRuntime().addShutdownHook(new Thread(() -> {
            pool.shutdown();                       // перестать принимать задачи
            try {
                if (!pool.awaitTermination(grace.toSeconds(), TimeUnit.SECONDS)) {
                    pool.shutdownNow();            // прервать оставшиеся
                    pool.awaitTermination(5, TimeUnit.SECONDS);
                }
            } catch (InterruptedException e) {
                pool.shutdownNow();
                Thread.currentThread().interrupt();
            }
        }, "graceful-shutdown"));
    }
}

Правила, нарушение которых стоит инцидентов:

  1. Хуки выполняются параллельно и в непредсказуемом порядке. Если нужен порядок — один хук, внутри которого последовательность. Spring решает это за тебя через SmartLifecycle и фазы.
  2. Нельзя вызывать System.exit() из хука — это deadlock: exit() ждёт завершения хуков, а ты в одном из них.
  3. Нельзя блокироваться надолго. Оркестратор даёт ограниченное время (terminationGracePeriodSeconds, по умолчанию 30 с в Kubernetes), после чего прилетает SIGKILL. Хук, который ждёт 60 с, просто не доработает.
  4. Нельзя рассчитывать на живость других подсистем. Логгер мог уже закрыться (у Logback свой shutdown hook), пул соединений мог быть остановлен другим хуком, контекст Spring — закрыт. Логировать из хука можно, но не удивляйся пустоте в логе.
  5. Нельзя рассчитывать, что хук вообще выполнится. SIGKILL, kill -9, OOM killer, падение хоста, Runtime.halt() — всё это проходит мимо хуков.

📊 Цифры. В Kubernetes типовой контракт такой: preStop (выполняется до SIGTERM) → SIGTERM → ожидание до terminationGracePeriodSeconds (значение по умолчанию 30 с) → SIGKILL. Удаление пода из эндпоинтов и отправка SIGTERM идут параллельно и без синхронизации — отсюда стандартная рекомендация ставить preStop: sleep 5–15 с, чтобы балансировщики успели перестать слать трафик. Детали — глава 47.

Проверить, что происходит на самом деле, можно вручную:

Bash
# Отправить SIGTERM и засечь, сколько процесс умирает
time (kill -TERM 12345; while kill -0 12345 2>/dev/null; do sleep 0.1; done)

kill -0 не посылает сигнала, а только проверяет существование процесса и права — идиома для «жив ли».

1.8 fork/exec и стоимость Runtime.exec в большой JVM

Классический способ создать процесс в Unix — fork() + execve(). fork() создаёт копию адресного пространства родителя. Копия ленивая (copy-on-write): физические страницы не дублируются, дублируются таблицы страниц. И вот здесь начинается проблема.

У JVM с heap 32 ГБ таблицы страниц занимают порядка десятков мегабайт (при страницах 4 КБ на 32 ГБ приходится 8 388 608 PTE по 8 байт ≈ 64 МБ только на последний уровень, плюс промежуточные уровни). Копирование этих структур при каждом fork() — это миллисекунды CPU и всплеск выделения памяти в ядре. Если приложение дёргает внешний процесс на каждый запрос (конвертация документа, вызов openssl, дёрганье shell-скрипта), под нагрузкой это превращается в стабильный расход процессора и в latency-хвост.

Вторая проблема — memory overcommit. Классический fork() в момент вызова требует, чтобы система теоретически могла предоставить столько же памяти, сколько занимает родитель. При vm.overcommit_memory=2 (strict) fork() из 32-гигабайтной JVM просто провалится с ENOMEM, хотя дочерний процесс собирался сразу сделать exec десятикилобайтного бинарника. Это знаменитая ошибка «Cannot allocate memory» при Runtime.exec() на машине, где памяти вроде бы полно.

Решения на уровне ОС:

  • vfork() — не копирует адресное пространство вовсе, родитель приостанавливается до exec или _exit ребёнка. Быстро, но опасно и ограниченно.
  • posix_spawn() — библиотечная обёртка, которая на Linux реализована через clone(CLONE_VM|CLONE_VFORK); фактически даёт производительность vfork с безопасным API.

JVM позволяет выбрать механизм:

Bash
# Варианты на Linux: FORK, POSIX_SPAWN, VFORK (доступность зависит от версии JDK)
java -Djdk.lang.Process.launchMechanism=POSIX_SPAWN -jar app.jar

В современных JDK (начиная с 13) POSIX_SPAWN — значение по умолчанию на Linux, что убрало большую часть проблемы. Но на старых средах выполнения и в некоторых сборках значение по умолчанию было VFORK/FORK, и явная установка спасала. ⚠️ Точное значение по умолчанию для конкретной версии стоит проверять на месте: java -XshowSettings:properties -version 2>&1 | grep -i launchMechanism ничего не покажет (свойство read-only и не выводится), проще посмотреть исходник java.lang.ProcessImpl или замерить.

Практический вывод для архитектуры: не запускай внешние процессы из горячего пути большой JVM. Варианты:

  1. Вынести работу в отдельный маленький сервис или sidecar, общаться по HTTP/gRPC/unix-сокету.
  2. Держать пул заранее запущенных процессов-воркеров и общаться через stdin/stdout (паттерн «process pool»).
  3. Использовать нативную библиотеку через FFM API (Java 22+) вместо запуска бинарника.
  4. Если всё же запускаешь — делай это из маленького «launcher»-процесса, который сам был запущен на старте.
Java
// Правильно: ProcessBuilder с явным перенаправлением и таймаутом.
// Без перенаправления вывода процесс может зависнуть, заполнив буфер пайпа (64 КБ).
var pb = new ProcessBuilder("/usr/bin/convert", "in.pdf", "out.png")
        .redirectErrorStream(true)
        .redirectOutput(ProcessBuilder.Redirect.to(new File("/tmp/convert.log")));
Process p = pb.start();
if (!p.waitFor(10, TimeUnit.SECONDS)) {
    p.destroy();                      // SIGTERM
    if (!p.waitFor(2, TimeUnit.SECONDS)) {
        p.destroyForcibly();          // SIGKILL
    }
    throw new TimeoutException("convert timed out");
}

⚠️ Осторожно. Не читать stdout/stderr дочернего процесса — самая частая ошибка. Буфер пайпа в Linux по умолчанию 64 КБ (/proc/sys/fs/pipe-max-size ограничивает максимум). Как только процесс напишет больше, он заблокируется на write() навсегда, а твой waitFor() будет ждать вечно. Либо redirectOutput в файл/DISCARD, либо отдельный поток-читатель, либо redirectErrorStream(true) + чтение.

2. Память процесса

2.1 Виртуальная и физическая память: VSZ, RSS, PSS, USS

Процесс видит виртуальное адресное пространство. Ядро отображает его куски на физические страницы — не все и не сразу. Отсюда четыре разные метрики, которые постоянно путают, и путаница стоит неверных решений о лимитах.

Метрика Считает Источник Источник ошибки
VSZ (VmSize) Весь зарезервированный виртуальный адрес: heap, стеки, все mmap, включая никогда не тронутые страницы ps -o vsz, /proc/<pid>/status → VmSize Для JVM всегда огромен (десятки-сотни ГБ) и почти ничего не значит. -Xmx32g даёт +32 ГБ к VSZ в момент старта, даже если занято 200 МБ.
RSS (VmRSS) Физические страницы, реально отображённые на процесс ps -o rss, top, /proc/<pid>/status → VmRSS Считает shared-страницы целиком у каждого процесса. Два процесса, разделяющие 100 МБ библиотеки, дадут суммарно 200 МБ RSS при 100 МБ реальных.
PSS (Proportional Set Size) Приватные страницы полностью + shared-страницы, делённые на число разделяющих процессов /proc/<pid>/smaps, smaps_rollup → Pss Считается только Linux-специфично; сумма PSS всех процессов = реально занятая память. Самая честная метрика.
USS (Unique Set Size) Только приватные страницы (Private_Clean + Private_Dirty) сумма из smaps Показывает, сколько освободится, если убить процесс.

Для JVM важно ещё разбиение RSS по типам, оно есть прямо в status:

Bash
grep -E '^(VmSize|VmRSS|RssAnon|RssFile|RssShmem|VmSwap|VmData|VmStk|VmExe|VmLib|VmPTE)' /proc/12345/status
VmSize:	 18432164 kB      # ~17.6 ГБ виртуальных — не пугайся
VmRSS:	  4823140 kB      # ~4.6 ГБ реальных
RssAnon:  4612288 kB      # анонимная память: heap, metaspace, стеки, нативные аллокации
RssFile:   208704 kB      # отображённые файлы: .so, jar (если mmap), code cache файлы
RssShmem:    2148 kB      # разделяемая память / tmpfs
VmSwap:         0 kB      # если тут не ноль на JVM — беда, см. 2.4
VmPTE:      12884 kB      # ~12.6 МБ только на таблицы страниц

💡 На интервью. «Чем RSS отличается от heap?» Формулировка: heap — это область, которой управляет GC, её размер задаётся -Xmx и виден в jcmd GC.heap_info. RSS — это вся физическая память процесса: heap плюс metaspace, code cache, стеки потоков (по умолчанию 1 МБ виртуально на поток), GC-структуры (карты, remembered sets — у G1 это порядка нескольких процентов от heap), direct byte buffers, нативные выделения памяти JNI и библиотек, арены malloc, mmap-нутые файлы. Нормальный коэффициент RSS/Xmx для серверного приложения — 1.3–1.6. Если RSS/Xmx > 2, надо разбираться.

2.3 Страничный кеш (page cache)

Самая частая ложная тревога у разработчиков, впервые попавших на сервер:

Bash
free -h
               total        used        free      shared  buff/cache   available
Mem:            31Gi        18Gi       512Mi       128Mi        12Gi        12Gi
Swap:          4.0Gi          0B       4.0Gi

free = 512 МБ — «памяти нет!» Нет, память есть: колонка available = 12 ГБ. Это оценка ядра, сколько можно выделить новому приложению без ухода в swap, с учётом того, что page cache будет вытеснен.

Что такое page cache: ядро кеширует содержимое файлов в свободной памяти. Прочитал файл — он остался в кеше, следующее чтение идёт из RAM. Записал файл — данные лежат в кеше как «грязные» и сбрасываются на диск позже (или по fsync). Неиспользуемая память — потраченная зря память, поэтому ядро заполняет её кешем.

Правило чтения free: смотри только на available. free без кеша — бесполезная цифра.

Bash
# Сколько грязных страниц ждёт сброса (если много — всплеск I/O впереди)
grep -E 'Dirty|Writeback' /proc/meminfo
# Dirty:            184320 kB
# Writeback:             0 kB

# Параметры сброса
sysctl vm.dirty_ratio vm.dirty_background_ratio vm.dirty_expire_centisecs
# vm.dirty_ratio = 20                  # при 20% RAM грязных — пишущий процесс блокируется
# vm.dirty_background_ratio = 10       # при 10% — фоновый сброс
# vm.dirty_expire_centisecs = 3000     # страница старше 30 с подлежит сбросу

⚠️ Осторожно. vm.dirty_ratio = 20 на машине с 128 ГБ RAM означает, что ядро накопит до 25 ГБ грязных страниц, а потом синхронно заблокирует пишущий процесс до их сброса. Приложение, которое спокойно писало логи, внезапно встаёт на десятки секунд в D-состоянии. На машинах с большой памятью и медленным диском ставят vm.dirty_bytes/vm.dirty_background_bytes в абсолютных значениях (например, 512 МБ / 128 МБ) вместо процентов.

Сбросить кеш для чистого замера (только на тестовом стенде!):

Bash
sync && echo 3 | sudo tee /proc/sys/vm/drop_caches

2.4 Swap и JVM

Swap для обычного процесса — страховка: редко используемые страницы уезжают на диск, освобождая RAM. Для JVM — механизм саморазрушения, и вот почему.

GC периодически обходит весь живой набор объектов. Любая сборка, затрагивающая старое поколение (Full GC у G1, параллельный марк у любого сборщика), трогает страницы, которые не трогались давно — именно те, которые ядро сочло холодными и выгрузило. Результат: пауза GC, которая должна была занять 200 мс, превращается в минуты чтения с диска по 4 КБ случайным доступом. На HDD это буквально десятки минут; приложение считается мёртвым, liveness-проба убивает под, и всё начинается заново на соседнем узле.

Bash
# Есть ли своп у процесса — первое, что смотришь при странных паузах
grep VmSwap /proc/12345/status

# Кто свопится по всей системе
for p in /proc/[0-9]*; do
  s=$(awk '/VmSwap/{print $2}' $p/status 2>/dev/null)
  [ -n "$s" ] && [ "$s" -gt 0 ] && echo "$s kB  $(cat $p/comm)"
done | sort -rn | head

# Активность свопа в динамике: колонки si/so должны быть нулями
vmstat 1 5

Настройки:

Bash
sysctl vm.swappiness        # 0..200 (до ядра 5.8 — 0..100); дефолт 60

vm.swappiness — не «процент свопа», а относительный вес: насколько охотно ядро вытесняет анонимные страницы по сравнению с page cache. swappiness=1 практически запрещает выгрузку анонимной памяти, но не гарантирует её отсутствие при реальной нехватке. swappiness=0 (с ядра 3.5) означает «свопить только при угрозе OOM».

Что делать на практике:

  • В контейнерах swap обычно и так выключен — Kubernetes исторически требовал --fail-swap-on=true; поддержка swap для узлов появилась как alpha/beta-фича, но в типовых кластерах swap выключен. Проблема остаётся для bare-metal и VM.
  • На выделенной под JVM машине: vm.swappiness=1, и лучше вообще отключить swap (swapoff -a + убрать из /etc/fstab), если ты уверен в sizing'е. Без swap нехватка памяти даёт быстрый и понятный OOM kill вместо многочасовой агонии.
  • Компромисс: оставить небольшой swap (2–4 ГБ) как буфер против мгновенной смерти, но swappiness=1 и мониторинг VmSwap процесса JVM с оповещением на любое ненулевое значение.
  • Если swap запрещено трогать, можно прибить heap к RAM флагом -XX:+AlwaysPreTouch (выделяет физическую память и трогает все страницы heap на старте — старт дольше, зато страницы «горячие») в сочетании с mlockall. Последнее JVM штатно не умеет; для huge pages есть -XX:+UseLargePages, которые не свопятся по определению.

2.5 Прозрачные большие страницы (Transparent Huge Pages)

Страница в x86-64 по умолчанию 4 КБ. Huge page — 2 МБ (и 1 ГБ для «gigantic»). Меньше страниц → меньше записей в TLB → меньше промахов TLB → быстрее доступ к памяти. Для JVM с большим heap выигрыш реальный: 5–15 % на memory-bound нагрузках.

THP (Transparent Huge Pages) — механизм, при котором ядро само собирает huge pages из обычных, без участия приложения. Настройки (kernel.org):

Bash
cat /sys/kernel/mm/transparent_hugepage/enabled
# [always] madvise never

cat /sys/kernel/mm/transparent_hugepage/defrag
# always defer defer+madvise [madvise] never

enabled:

  • always — THP для всей анонимной памяти системы;
  • madvise — только там, где приложение явно попросило madvise(MADV_HUGEPAGE);
  • never — выключено.

defrag — что делать, когда свободной непрерывной 2-мегабайтной области нет:

  • always — «Applications requesting THP will pause during allocation failures while the kernel reclaims pages and compacts memory immediately» — то есть приложение синхронно ждёт дефрагментации;
  • defer — отдать работу фоновым kswapd/kcompactd, приложению сразу выдать обычные страницы;
  • defer+madvise — синхронно только для явно попросивших;
  • madvise — прямая уплотнение только для MADV_HUGEPAGE-регионов (частое значение по умолчанию современных дистрибутивов);
  • never — никакой уплотнения.

⚠️ Осторожно: ловушка историческая и до сих пор живая. Комбинация enabled=always + defrag=always даёт непредсказуемые паузы в приложении: поток пытается выделить память, ядро уходит в синхронную дефрагментацию, поток стоит. На фрагментированной памяти это десятки и сотни миллисекунд, попадающих в 99.9-перцентиль запроса. Именно из-за этого MongoDB, Redis, Elasticsearch, Couchbase и Oracle годами рекомендовали в документации выключать THP полностью. Для JVM ситуация мягче (heap выделяется большими кусками на старте, а не по мере работы), но всплески latency при THP=always наблюдаются.

Практическая рекомендация: enabled=madvise, defrag=madvise или defer+madvise — и включать huge pages для heap явно через -XX:+UseTransparentHugePages (JVM тогда делает madvise(MADV_HUGEPAGE) на heap-регионе). В паре с -XX:+AlwaysPreTouch это даёт выигрыш без пауз во время выполнения.

Bash
# Проверить, сколько THP реально используется процессом
grep AnonHugePages /proc/12345/smaps_rollup
# AnonHugePages:   1048576 kB

# Системная статистика по компакции — рост thp_fault_fallback и compact_stall это плохо
grep -E 'thp_fault_alloc|thp_fault_fallback|compact_stall|compact_fail' /proc/vmstat

Альтернатива THP — явные huge pages (hugetlbfs): резервируются на старте системы, не свопятся, не дефрагментируются:

Bash
sudo sysctl vm.nr_hugepages=8200           # 8200 × 2 МБ ≈ 16 ГБ
java -XX:+UseLargePages -Xmx16g -Xms16g ...

Минус: если страниц не хватит, JVM либо не стартует, либо без предупреждения откатится на обычные (зависит от -XX:+UseLargePages vs -XX:LargePageSizeInBytes). И память забронирована навсегда, даже если JVM не запущена.

Bash
# Текущий счёт и корректировка процесса
cat /proc/12345/oom_score        # итоговый счёт
cat /proc/12345/oom_score_adj    # корректировка

# Кто первый кандидат на вылет
for p in /proc/[0-9]*; do
  echo "$(cat $p/oom_score 2>/dev/null) $(basename $p) $(cat $p/comm 2>/dev/null)"
done | sort -rn | head -5

В Kubernetes oom_score_adj выставляется автоматически по QoS-классу: Guaranteed получает −997, BestEffort — 1000, Burstable — значение между 2 и 999, обратно пропорциональное отношению request к памяти узла. То есть Guaranteed-под почти никогда не убивается при глобальной нехватке, но всё равно убивается при превышении собственного memory.max. Детали QoS — глава 47.

⚠️ Осторожно. Если в Kubernetes под перезапустился с exitCode: 137 и reason: OOMKilled, это не OutOfMemoryError. Heap dump не появится, shutdown hooks не выполнятся, в логах приложения — обрыв на полуслове. Диагностика: смотреть container_memory_working_set_bytes в метриках и сравнивать с -Xmx + non-heap. Почти всегда причина — non-heap: metaspace, direct buffers, потоки или нативные выделения памяти, о которых забыли при расчёте MaxRAMPercentage. Расчёт — глава 46.

2.7 Арены glibc malloc и рост RSS без роста кучи

Классический инцидент: heap стабильно 2 ГБ по метрикам JVM, метаспейс 200 МБ, а RSS процесса растёт неделями и доходит до 8 ГБ. Native memory leak? Часто — нет. Часто это арены glibc.

Механизм. malloc в glibc, чтобы не сериализовать все выделения памяти на одном мьютексе, создаёт несколько независимых «арен» — областей, каждая со своим локом. Поток при первой выделения памяти привязывается к арене. Если все арены заняты, создаётся новая, пока не достигнут лимит. Лимит по умолчанию — 8 × число ядер на 64-битных системах. На машине с 32 ядрами это 256 арен.

Каждая арена (кроме главной) резервирует область через mmap кратно 64 МБ и не возвращает её ядру целиком, даже когда память освобождена: glibc держит освобождённые фрагменты для повторно использования и возвращает страницы системе только при выполнении довольно жёстких условий (непрерывный свободный хвост сверху арены больше M_TRIM_THRESHOLD). Результат — фрагментация: полезных данных мало, RSS большой.

Java-нагрузка провоцирует это идеально: сотни потоков, каждый изредка дёргает нативную выделение памяти (JNI, сжатие, SSL, DirectByteBuffer через Unsafe.allocateMemory идёт мимо, но многие библиотеки — через malloc), потоки создаются и умирают.

Признак в pmap: много регионов ровно по 65536 КБ.

Bash
pmap -x 12345 | awk '$2 == 65536' | wc -l
# 48     <- 48 арен, потенциально 3 ГБ виртуально

Лечение:

Bash
# Ограничить число арен. 2-4 — типичный компромисс для JVM.
export MALLOC_ARENA_MAX=4
java -jar app.jar

Или в Dockerfile / Deployment:

YAML
env:
  - name: MALLOC_ARENA_MAX
    value: "4"

Цена: больше contention на малloc-локе, если нативных выделений памяти действительно много. На практике для типичного Spring-приложения снижение с 256 до 4 арен не заметно по CPU, а RSS падает на гигабайты.

Альтернатива — заменить распределитель памяти целиком:

Bash
# jemalloc
LD_PRELOAD=/usr/lib/x86_64-linux-gnu/libjemalloc.so.2 java -jar app.jar

# tcmalloc (gperftools)
LD_PRELOAD=/usr/lib/x86_64-linux-gnu/libtcmalloc.so.4 java -jar app.jar
Распределитель памяти Сильная сторона Слабая сторона
glibc malloc Везде есть, ничего не надо ставить Фрагментация, арены, плохо возвращает память
jemalloc Низкая фрагментация, агрессивный возврат (decay), встроенный профилировщик кучи Отдельная зависимость; надо следить за версией
tcmalloc Быстрые thread-local кеши, хорош на многопоточных выделениях памяти Профилирование слабее, возврат памяти консервативнее
mimalloc Часто быстрее обоих на микробенчмарках Реже встречается в дистрибутивах, меньше опыта эксплуатации

Локализация настоящей утечки нативной памяти — комбинация трёх инструментов:

  1. NMT (Native Memory Tracking) — покрывает то, что выделяет сама JVM:
Bash
java -XX:NativeMemoryTracking=detail -jar app.jar
jcmd 12345 VM.native_memory baseline
# ... подождать час ...
jcmd 12345 VM.native_memory summary.diff
Total: reserved=9478MB +142MB, committed=5382MB +138MB
-                 Java Heap (reserved=4096MB, committed=4096MB)
-                     Class (reserved=1058MB +2MB, committed=42MB +2MB)
-                    Thread (reserved=289MB +88MB, committed=289MB +88MB)   <- +88 МБ на потоки!
-                      Code (reserved=248MB, committed=42MB)
-                        GC (reserved=214MB, committed=214MB)
-                  Internal (reserved=8MB, committed=8MB)
-                     Other (reserved=512MB +48MB, committed=512MB +48MB)

Рост в Thread — утечка потоков. Рост в Other — обычно DirectByteBuffer/Unsafe.allocateMemory. Рост в Class — утечка классов/загрузчиков.

⚠️ NMT не видит выделения памяти, сделанные нативными библиотеками напрямую через malloc: если течёт JDBC-драйвер с нативной частью, OpenSSL или сжатие, NMT покажет ровную картину при растущем RSS. Это и есть признак «утечка вне JVM».

  1. Сравнение RSS с суммой NMT-committed. Разрыв — размер утечки вне JVM.
Bash
echo "RSS: $(awk '/VmRSS/{print $2/1024" MB"}' /proc/12345/status)"
jcmd 12345 VM.native_memory summary | head -3
  1. jemalloc profiling — единственный способ получить стек нативной выделения памяти:
Bash
MALLOC_CONF=prof:true,prof_prefix:/tmp/jeprof,lg_prof_interval:30 \
LD_PRELOAD=/usr/lib/x86_64-linux-gnu/libjemalloc.so.2 \

# через час собрать дампы
jeprof --show_bytes --pdf /usr/bin/java /tmp/jeprof.*.heap > leak.pdf
# или текстом
jeprof --text --show_bytes /usr/bin/java /tmp/jeprof.*.heap | head -30

В выводе будут нативные фреймы: Java_java_util_zip_Inflater_init, SSL_new, rocksdb::.... Это прямое указание на виновника.

📊 Цифры. Порядки, которые стоит держать в голове для типового Spring Boot приложения с -Xmx4g: heap до 4 ГБ, metaspace 150–400 МБ, code cache 100–250 МБ, GC-структуры у G1 ≈ 5–10 % heap, стеки — число потоков × реально использованный объём (обычно 30–100 КБ, а не 1 МБ), direct buffers — по -XX:MaxDirectMemorySize (значение по умолчанию = -Xmx!), символы и загрузчики классов 50–150 МБ. Сумма ≈ 5–6 ГБ RSS. Лимит контейнера 4.5 ГБ при -Xmx4g — гарантированный OOMKilled.

3. cgroups и контейнерные лимиты

3.1 Различия cgroups v1 и v2

cgroups (control groups) — механизм ядра для учёта и ограничения ресурсов группы процессов. Две несовместимые версии.

cgroup v1: несколько независимых иерархий, по одной на контроллер. /sys/fs/cgroup/memory/, /sys/fs/cgroup/cpu,cpuacct/, /sys/fs/cgroup/pids/ — каждая со своим деревом. Процесс мог быть в разных местах разных иерархий, что порождало странные конфигурации.

cgroup v2: «Unlike v1, cgroup v2 has only single hierarchy» (kernel.org). Одно дерево, контроллеры включаются на узлах через cgroup.subtree_control. Плюс жёсткое правило: «Non-root cgroups can distribute domain resources to their children only when they don't have any processes of their own» — процессы живут только в листьях.

Как определить версию на машине:

Bash
stat -fc %T /sys/fs/cgroup/
# cgroup2fs   -> v2
# tmpfs       -> v1 (или гибрид)

mount | grep cgroup

Актуальные дистрибутивы (RHEL 9+, Ubuntu 22.04+, Debian 11+, Fedora 31+) по умолчанию на v2. Kubernetes поддерживает v2 стабильно с 1.25.

Предмет cgroup v1 cgroup v2
Лимит памяти memory/memory.limit_in_bytes memory.max
Мягкий лимит memory/memory.soft_limit_in_bytes memory.high (реально работает, в отличие от soft_limit)
Текущее потребление memory/memory.usage_in_bytes memory.current
Статистика memory/memory.stat memory.stat
События OOM memory/memory.oom_control memory.events (oom, oom_kill)
Swap memory/memory.memsw.limit_in_bytes (суммарно mem+swap) memory.swap.max (отдельно)
Квота CPU cpu/cpu.cfs_quota_us + cpu.cfs_period_us cpu.max = "<quota> <period>"
Доля CPU cpu/cpu.shares (2..262144, значение по умолчанию 1024) cpu.weight (1..10000, значение по умолчанию 100)
Throttling cpu/cpu.stat cpu.stat
Лимит процессов pids/pids.max pids.max
I/O blkio/* (плохо работал с buffered writes) io.max, io.stat, io.pressure

Первое, что делаешь в контейнере при подозрении на лимиты:

Bash

# v1:  12:memory:/kubepods/burstable/pod.../crio-abc...

# v2: лимиты и потребление

cat /sys/fs/cgroup/memory.current      # 3982135296
cat /sys/fs/cgroup/memory.high         # max
cat /sys/fs/cgroup/memory.swap.max     # 0
cat /sys/fs/cgroup/cpu.max             # 200000 100000   -> 2 CPU
cat /sys/fs/cgroup/cpu.weight          # 79

cpu.max в формате $MAX $PERIOD — «indicates that the group may consume up to $MAX in each $PERIOD duration». Значение по умолчанию max 100000: без ограничения, период 100 мс. Значение 200000 100000 = 200 мс CPU-времени на каждые 100 мс реального времени = 2 ядра.

memory.events — счётчики, а не мгновенные значения:

Bash
cat /sys/fs/cgroup/memory.events
low 0
high 0
max 1842          # сколько раз потребление упиралось в memory.max
oom 3             # сколько раз не удалось выделить
oom_kill 2        # сколько процессов убито OOM killer'ом

oom_kill > 0 — железное доказательство OOMKilled, даже если события в Kubernetes уже уехали из истории.

memory.stat расшифровывает, из чего сложилось memory.current:

Bash
grep -E '^(anon|file|kernel_stack|slab|sock|shmem|file_mapped|file_dirty|file_writeback|pgmajfault) ' \
  /sys/fs/cgroup/memory.stat
anon 3623878656          # анонимная память — heap, стеки, нативка
file 298450944           # page cache, относимый к этой cgroup
kernel_stack 5242880     # стеки ядра для потоков (8 КБ × число потоков)
slab 41943040            # структуры ядра (inode, dentry)
sock 12582912            # буферы сокетов
file_mapped 104857600
file_dirty 8388608
pgmajfault 12            # major page faults — чтение с диска

⚠️ Осторожно. memory.current включает page cache (file). Контейнер, который активно читает или пишет файлы, набирает memory.current до лимита за счёт кеша. Это не приводит к OOM автоматически — ядро вытеснит кеш. Но метрика в Grafana выглядит как «под на 99 % памяти», и дежурный паникует. Правильная метрика для оповещений — container_memory_working_set_bytes (= memory.current − неактивный file cache), именно её использует kubelet при принятии решения об eviction.

3.3 Обнаружение ограничения скорости CPU

Самая коварная проблема в контейнерах: средний CPU по метрикам 30 %, а latency прыгает до секунд. Причина — CFS-квота.

Механизм. Квота выдаётся окнами по period (100 мс). Контейнер с cpu.max = 200000 100000 получает 200 мс CPU-времени на окно. Если у приложения 40 потоков и все они одновременно захотели работать, они сожрут квоту за 5 мс реального времени, после чего все потоки контейнера замораживаются до конца окна — на 95 мс. Средняя утилизация за секунду: 20 %. Реальный эффект: каждый запрос, попавший в замороженное окно, получает +95 мс.

Доказательство — cpu.stat:

Bash
cat /sys/fs/cgroup/cpu.stat
usage_usec 184729384
user_usec 152839211
system_usec 31890173
nr_periods 982431
nr_throttled 148229        # <- в 15% окон была заморозка
throttled_usec 4192884201  # <- суммарно 4192 секунды заморозки

Интерпретация:

  • nr_throttled / nr_periods — доля окон с throttling. Больше 1 % — уже стоит разбираться, больше 5 % — точно бьёт по latency.
  • throttled_usec / nr_throttled — средняя длительность заморозки. Если она близка к period (100 000 мкс), значит квота выжигается в самом начале окна — типично для многопоточного всплеска.

Скрипт для наблюдения в динамике (то, что реально запускаешь в инциденте):

Bash
#!/usr/bin/env bash
set -euo pipefail
prev_p=0; prev_t=0; prev_u=0
while true; do
  read -r _ p _ t _ u < <(
    awk '/nr_periods/{p=$2} /nr_throttled/{t=$2} /throttled_usec/{u=$2}
         END{print "p", p, "t", t, "u", u}' /sys/fs/cgroup/cpu.stat)
  if [ "$prev_p" -ne 0 ]; then
    dp=$((p - prev_p)); dt=$((t - prev_t)); du=$((u - prev_u))
    pct=0; [ "$dp" -gt 0 ] && pct=$((dt * 100 / dp))
    printf '%s periods=%-5d throttled=%-5d (%d%%) stalled=%dms\n' \
      "$(date +%T)" "$dp" "$dt" "$pct" "$((du / 1000))"
  fi
  prev_p=$p; prev_t=$t; prev_u=$u
  sleep 1
done

Вывод во время инцидента:

14:22:01 periods=10   throttled=7    (70%) stalled=612ms
14:22:02 periods=10   throttled=8    (80%) stalled=701ms
14:22:03 periods=10   throttled=6    (60%) stalled=548ms

70 % окон с заморозкой и 600+ мс суммарной заморозки в секунду — это приговор. При этом top покажет ~1.9 CPU при лимите 2, и «всё в норме».

Лечение по убыванию эффективности:

  1. Убрать CPU limit, оставить request. Спорный, но часто правильный ход: request даёт гарантию через cpu.weight, limit только вредит. Аргумент против — «шумный сосед», аргумент за — latency важнее. Многие команды в проде идут именно этим путём для латентно-чувствительных сервисов.
  2. Поднять limit до реального пика, а не до среднего.
  3. Сократить параллелизм внутри JVM — размер пулов, ForkJoinPool.commonPool параллелизм, число GC-потоков. Если лимит 2 CPU, а -XX:ParallelGCThreads=16, GC сам себя дросселирует.
  4. Уменьшить period (cpu.cfs_period_us = 10000, то есть 10 мс) — заморозки станут короче и чаще, хвост latency сгладится. В Kubernetes это настройка kubelet --cpu-cfs-quota-period, не поддаётся изменению из манифеста.
  5. Проверить ActiveProcessorCount, см. дальше.

📊 Цифры. Формула: заморозка длится до period × (1 − used/quota_at_freeze). При period=100ms максимальная единовременная задержка — почти 100 мс. Если квота 0.5 CPU (50000 100000), а приложение однопоточно и постоянно занято, оно будет работать 50 мс и стоять 50 мс — то есть любой запрос с вероятностью 50 % получит +50 мс. Дробные лимиты меньше 1 CPU для Java-сервисов с SLA по latency — почти всегда ошибка.

3.4 Число процессоров, видимое JVM

Runtime.getRuntime().availableProcessors() определяет размер ForkJoinPool.commonPool, число GC-потоков, JIT-компиляторов, размер пулов по умолчанию в Netty, Tomcat, Reactor и половине библиотек. Ошибка здесь тиражируется на всё приложение.

Контейнерная поддержка включена по умолчанию: -XX:+UseContainerSupport — «The default for this flag is true, and container support is enabled by default» (man java, JDK 25; см. FACTS гл. 46). JVM читает cpu.max и вычисляет число процессоров как ceil(quota / period).

Но nproc в контейнере не учитывает квоту — он смотрит на affinity-маску (sched_getaffinity), которая обычно включает все ядра узла:

Bash
nproc                                          # 64 — число ядер хоста
nproc --all                                    # 64
cat /sys/fs/cgroup/cpu.max                     # 200000 100000 -> лимит 2
grep Cpus_allowed_list /proc/self/status       # 0-63
java -XX:+PrintFlagsFinal -version | grep ActiveProcessorCount

Проверить, что реально видит JVM:

Bash
jcmd 12345 VM.flags -all | grep -E 'ActiveProcessorCount|ParallelGCThreads|ConcGCThreads|CICompilerCount'
# или изнутри приложения
jshell -s <<'EOF'
System.out.println(Runtime.getRuntime().availableProcessors());
EOF

⚠️ Осторожно. Скрипты запуска, которые считают размер пула через nproc в entrypoint (-Dserver.tomcat.threads.max=$(( $(nproc) * 50 ))), в контейнере с лимитом 2 CPU создадут 3200 потоков. Каждый — 1 МБ виртуально, 8 КБ ядрового стека, запись в планировщике. Результат: pids.max исчерпан или OOMKilled из-за kernel_stack. Считать надо от cpu.max, а не от nproc.

Принудительно задать:

Bash
java -XX:ActiveProcessorCount=2 -jar app.jar

Флаг «is honored even if UseContainerSupport is not enabled» (man java). Полезен, когда квота дробная и ceil даёт не то, что хочется, или когда хочется дать JIT больше потоков, чем квота.

1. Файловые дескрипторы (RLIMIT_NOFILE).

Симптом исчерпания: java.lang.OutOfMemoryError: unable to create native thread — обманчивое сообщение, памяти может быть полно, кончились слоты задач.

3. vm.max_map_count.

Bash

JVM упирается реже, но упирается: ZGC/Shenandoah создают много отображений, приложения с тысячами потоков (каждый стек — отдельное отображение плюс гардовая страница), приложения с интенсивным FileChannel.map(), jemalloc с большим числом арен.

Bash

4. Файловые дескрипторы и ввод-вывод

4.1 Файловые дескрипторы

Файловый дескриптор — маленькое неотрицательное целое, индекс в таблице открытых файлов процесса. Дескриптором в Unix является всё: обычный файл, сокет, пайп, eventfd, timerfd, epoll-экземпляр, inotify-watch, memfd, /dev/null, unix-сокет, даже открытый каталог.

Для Java-приложения главный потребитель — сокеты. Каждое входящее HTTP-соединение — fd. Каждое соединение в пуле к БД — fd. Каждое соединение HTTP-клиента к внешнему API — fd. Каждый Kafka-брокер в кластере — fd на соединение. Плюс jar-файлы (JVM держит их открытыми), файлы логов, epoll-экземпляры Netty (по одному на event loop), eventfd для пробуждения селекторов.

Bash
# Сколько открыто
ls /proc/12345/fd | wc -l

# Разбивка по типам — самая полезная команда при подозрении на утечку
ls -l /proc/12345/fd | awk '{print $11}' | sed 's/:\[.*//' | sort | uniq -c | sort -rn
   3891 socket
    412 /var/lib/app/data
     87 pipe
     24 anon_inode
     12 /opt/app/lib
      5 /dev/urandom

3891 сокетов при лимите 4096 — до аварии осталось недолго.

Более детально — через lsof:

Bash
# Все дескрипторы процесса
lsof -p 12345

# Только сетевые, с состоянием TCP
lsof -p 12345 -iTCP -sTCP:ESTABLISHED -n -P

# Сгруппировать по удалённому адресу — кто держит соединения
lsof -p 12345 -iTCP -n -P | awk '{print $9}' | cut -d'>' -f2 | sort | uniq -c | sort -rn | head

# Кто в системе держит больше всего fd
lsof -n 2>/dev/null | awk '{print $1, $2}' | sort | uniq -c | sort -rn | head

Флаги -n (не разрешать адреса в имена хостов) и -P (не превращать номера портов в имена) обязательны: без них lsof на машине с проблемным DNS будет выполняться минутами.

Быстрая альтернатива без lsof (его часто нет в distroless-образах):

Bash
# Куда указывают сокеты — через inode и ss
ls -l /proc/12345/fd | grep socket | grep -o '[0-9]*\]' | tr -d ']' > /tmp/inodes
ss -tanp | grep -F -f /tmp/inodes

4.2 Поиск утечки файловых дескрипторов

java.net.SocketException: Too many open files или java.io.IOException: Too many open files — самая классическая эксплуатационная ошибка Java-приложений. Алгоритм разбора:

Шаг 1. Убедиться, что это действительно лимит, а не что-то ещё.

Bash
echo "open: $(ls /proc/12345/fd | wc -l)"
grep 'Max open files' /proc/12345/limits

Шаг 2. Определить, растёт ли число во времени.

Bash
watch -n 5 'ls /proc/12345/fd | wc -l'
# или в лог
while true; do echo "$(date +%s) $(ls /proc/12345/fd | wc -l)"; sleep 10; done | tee /tmp/fd.log

Линейный рост = утечка. Пила = нормальная работа под нагрузкой (и тогда просто мал лимит).

Шаг 3. Найти, что именно течёт. Сравнить две «фотографии» с интервалом:

Bash
ls -l /proc/12345/fd | awk '{print $11}' | sed 's/:\[.*//' | sort | uniq -c | sort -rn > /tmp/fd-t0
sleep 300
ls -l /proc/12345/fd | awk '{print $11}' | sed 's/:\[.*//' | sort | uniq -c | sort -rn > /tmp/fd-t1
diff /tmp/fd-t0 /tmp/fd-t1

Шаг 4. Для сокетов — найти адресата.

Bash
ss -tanp | grep 'pid=12345' | awk '{print $1, $6}' | sort | uniq -c | sort -rn | head
   2841 CLOSE-WAIT 10.20.3.44:8080
    312 ESTAB      10.20.5.11:5432
     42 ESTAB      10.20.7.8:9092

2841 соединений в CLOSE-WAIT к одному адресу — это конкретный HTTP-клиент, который не закрывает ответы. См. раздел 6.4 и инцидент 9.5.

Шаг 5. Найти место в коде. Сопоставить адрес с клиентом в приложении. Если непонятно — включить -Djdk.net.debug не поможет, лучше взять async-profiler в режиме нативных вызовов или простой JFR:

Bash
jcmd 12345 JFR.start name=fdleak settings=profile duration=120s filename=/tmp/fd.jfr
# в JFR есть события jdk.SocketRead / jdk.SocketWrite / jdk.FileRead с стеками

Либо, если приложение под твоим контролем, поставить временный счётчик:

Java
// Быстрая инструментация: метрика открытых fd прямо из JVM
@Bean
MeterBinder openFdBinder() {
    var os = ManagementFactory.getOperatingSystemMXBean();
    return registry -> {
        if (os instanceof com.sun.management.UnixOperatingSystemMXBean unix) {
            Gauge.builder("process.files.open", unix, UnixOperatingSystemMXBean::getOpenFileDescriptorCount)
                 .register(registry);
            Gauge.builder("process.files.max", unix, UnixOperatingSystemMXBean::getMaxFileDescriptorCount)
                 .register(registry);
        }
    };
}

Micrometer регистрирует process.files.open и process.files.max автоматически при наличии ProcessorMetrics/FileDescriptorMetrics — оповещение на process_files_open / process_files_max > 0.8 должно быть в каждом сервисе.

Типовые причины утечки fd в Java:

  1. InputStream/Response HTTP-клиента не закрыт. Apache HttpClient и OkHttp требуют прочитать или закрыть тело ответа, иначе соединение не возвращается в пул и не закрывается.
  2. Files.list() / Files.walk() / Files.lines() возвращают Stream, который держит fd. Без try-with-resources — утечка.
  3. Statement/ResultSet не закрыты (утечка соединения пула, а через него — fd).
  4. Собственный ExecutorService на каждый запрос с ServerSocket/Selector внутри.
  5. ZipFile/JarFile без закрытия.
  6. Netty-каналы, для которых не вызван close() при ошибке.
  7. Runtime.exec без закрытия трёх потоков процесса (getInputStream, getOutputStream, getErrorStream) — каждый висящий процесс уносит три fd.

4.3 Лимиты дескрипторов и systemd

Лимит на число открытых файловых дескрипторов в Linux задаётся на трёх уровнях, и путаница между ними — источник половины инцидентов, когда сервис падает с «Too many open files», хотя лимит вроде бы подняли. Разберём уровни по очереди.

Уровень 1: /etc/security/limits.conf — применяется PAM при интерактивном логине и через su/login. Не применяется к сервисам, запускаемым systemd.

appuser  soft  nofile  65536
appuser  hard  nofile  1048576

Уровень 2: systemd-юнит — единственное, что работает для сервиса:

INI
[Service]
User=appuser
ExecStart=/usr/bin/java -jar /opt/app/app.jar
LimitNOFILE=1048576
LimitNPROC=65536
LimitMEMLOCK=infinity
LimitCORE=infinity

Есть ещё глобальные значения по умолчанию systemd: /etc/systemd/system.conf → DefaultLimitNOFILE. С systemd 240 soft-лимит по умолчанию для сервисов — 1024, hard — 524288; с systemd 254 soft-лимит по-прежнему консервативный. Явное LimitNOFILE обязательно.

Уровень 3: контейнер. Docker: --ulimit nofile=1048576:1048576 или default-ulimits в /etc/docker/daemon.json. Kubernetes не даёт задать ulimit в манифесте пода — лимит наследуется от container runtime, который наследует от systemd-юнита containerd/CRI-O. Это регулярный сюрприз: под получает nofile=1048576 на одном узле и 1024 на другом, потому что узлы разных поколений.

Bash
# Проверка внутри пода — единственный надёжный способ
kubectl exec -it mypod -- sh -c 'cat /proc/1/limits | grep "open files"'

С ядра 5.x и containerd свежих версий значение по умолчанию часто уже 1048576, но проверять надо.

⚠️ Осторожно. ulimit -n unlimited не существует: RLIMIT_NOFILE всегда конечен и ограничен сверху /proc/sys/fs/nr_open (значение по умолчанию 1048576). Попытка выставить больше даёт ошибку. Также: выставление гигантского LimitNOFILE (миллионы) замедляет некоторые программы, которые в цикле закрывают все fd от 0 до лимита перед exec — это была реальная проблема в старых версиях ряда демонов. Разумный потолок для JVM-сервиса — 65536…262144.

4.4 Блокирующий и неблокирующий I/O, epoll

Модель ввода-вывода определяет, чем занят поток, пока данные из сети ещё не пришли: ждёт их сам, получает отказ и спрашивает снова или узнаёт о готовности от ядра через epoll. От этого выбора зависит, сколько соединений сервис выдержит на одном потоке. Моделей три:

  1. Блокирующая (thread-per-connection). read() на сокете блокирует поток до прихода данных. Классический Tomcat в BIO-режиме, ServerSocket + new Thread(). Простая модель, цена — поток на соединение. С виртуальными потоками (JDK 21+) цена резко упала, и эта модель вернулась в моду.
  2. Неблокирующая с мультиплексированием (epoll). Один поток обслуживает тысячи сокетов: спрашивает у ядра «кто готов», обрабатывает готовых. Java NIO Selector, Netty, WebFlux/Reactor Netty, Tomcat NIO-коннектор.
  3. Асинхронная (io_uring, Windows IOCP). Ядро само выполняет операцию и сообщает о завершении.

epoll — Linux-специфичный мультиплексор (man7.org). Три вызова: epoll_create1() создаёт экземпляр (сам по себе fd!), epoll_ctl() добавляет/меняет/удаляет наблюдаемые дескрипторы, epoll_wait() блокируется до готовности.

Два режима:

  • Level-triggered (по умолчанию) — «epoll is simply a faster poll(2), and can be used wherever the latter is used since it shares the same semantics». Пока в буфере есть данные, epoll_wait будет их возвращать снова и снова.
  • Edge-triggered (EPOLLET) — «delivers events only when changes occur on the monitored file descriptor». Событие приходит один раз на изменение состояния; не вычитал всё — следующего события не будет. Требование: «An application that employs the EPOLLET flag should use nonblocking file descriptors to avoid having a blocking read or write starve a task that is handling multiple file descriptors», и читать в цикле до EAGAIN.

Java NIO Selector на Linux реализован через epoll в level-triggered режиме. Netty с EpollEventLoopGroup (нативный транспорт) использует EPOLLET и даёт заметно меньше системных вызовов. Подробности реактивной модели и event loop — глава 11 (11-reactive.md).

Диагностика epoll изнутри:

Bash
# Сколько fd отслеживает epoll-инстанс fd=7 процесса 12345
cat /proc/12345/fdinfo/7

flags:	02000002
mnt_id:	15

Каждая строка tfd: — отслеживаемый дескриптор. Число строк = сколько соединений висит на этом event loop. Неравномерное распределение между event loop'ами — признак проблемы с балансировкой соединений.

EPOLLEXCLUSIVE решает thundering herd: когда несколько потоков ждут на одном listening-сокете, «just one of the threads (or processes) is awoken from epoll_wait(2)». Актуально для многопроцессных серверов; в Java обычно не всплывает, но объясняет, почему SO_REUSEPORT + отдельный сокет на acceptor-поток масштабируется лучше.

io_uring — интерфейс асинхронного I/O, появившийся в ядре 5.1 (2019). Два кольцевых буфера в разделяемой памяти: submission queue и completion queue. Приложение кладёт запросы в SQ, ядро выполняет и кладёт результаты в CQ. Главное преимущество — операция в среднем стоит меньше одного системного вызова (при IORING_SETUP_SQPOLL — ноль системных вызовов в установившемся режиме). Работает и для файлов, и для сокетов, в отличие от POSIX AIO.

Статус для Java на сентябрь 2026:

  • В JDK нет штатной поддержки io_uring. Проект Loom и NIO продолжают использовать epoll.
  • Netty имеет инкубационный транспорт netty-incubator-transport-native-io_uring; он рабочий, но статус инкубации не снят, и API может меняться.
  • Многие дистрибутивы и облачные провайдеры отключают io_uring из соображений безопасности (в 2023–2024 через него нашли значимое число эскалаций привилегий; Google отключил его в ChromeOS и Android, ряд seccomp-профилей по умолчанию блокируют io_uring_setup). Проверить: sysctl kernel.io_uring_disabled (0 — разрешено, 1 — только для группы, 2 — запрещено).

⚠️ Практический вывод: для бэкенд-разработчика в 2026 году io_uring — это то, что стоит знать на интервью и не стоит тащить в прод без веской причины и согласования с безопасностью.

4.5 Page cache, fsync и durability

Запись в файл по умолчанию идёт в page cache и возвращается немедленно. Данные попадут на диск когда-нибудь: по таймеру (vm.dirty_expire_centisecs), по достижению порогов (vm.dirty_background_ratio), или по явному fsync()/fdatasync().

Для бэкенд-разработчика это означает: write() вернул успех ≠ данные сохранены. При потере питания или падении ядра теряется всё, что было в page cache. Именно поэтому PostgreSQL делает fsync на WAL при коммите (synchronous_commit=on), Kafka имеет flush.messages/flush.ms, а RabbitMQ подтверждает publish для persistent-сообщения только после fsync (см. FACTS, гл. 30).

Java
// Разница на уровне Java
try (var raf = new RandomAccessFile("data.bin", "rw")) {
    var ch = raf.getChannel();
    ch.write(ByteBuffer.wrap(payload));
    ch.force(false);   // fdatasync: только данные, без метаданных (быстрее)
    ch.force(true);    // fsync: данные + метаданные (mtime, размер)
}

force(false) → fdatasync(): не синхронизирует метаданные, если они не нужны для чтения данных. На ext4 экономит одну операцию с журналом. Для append-only лога, где размер файла меняется, разница меньше, чем кажется, потому что размер — тоже метаданные, нужные для чтения.

Что реально стоит fsync:

📊 Цифры (порядки, зависят от железа). NVMe с конденсатором на плате: 20–100 мкс. Обычный consumer NVMe без защиты питания: 0.3–2 мс. SATA SSD enterprise: 0.1–0.5 мс. SATA SSD consumer: 1–10 мс. HDD 7200 rpm: 8–15 мс (один оборот). Сетевой том (EBS gp3, Cinder): 0.5–3 мс, с хвостами до десятков мс. Отсюда простая арифметика: база данных с synchronous_commit=on на HDD физически не может дать больше ~70–120 коммитов в секунду на одно соединение.

Проверить реальную задержку fsync на конкретной машине:

Bash
# Утилита из поставки PostgreSQL — золотой стандарт для этого замера
pg_test_fsync -f /var/lib/postgresql/testfile

# Грубая альтернатива через fio
fio --name=fsynctest --rw=write --bs=4k --size=64M --fsync=1 \
    --filename=/data/testfile --direct=0 --runtime=30 --time_based

Прочие параметры файловых систем, которые задевают бэкенд:

  • noatime — не обновлять время последнего доступа при чтении. Без него каждое чтение порождает запись метаданных. Современные ядра по умолчанию монтируют с relatime (обновление не чаще раза в сутки), что почти так же хорошо. Для БД и логов noatime всё равно ставят.
  • Размер блока и выравнивание — для БД важно, чтобы FS-блок совпадал с размером страницы БД (8 КБ у PostgreSQL) или был его делителем.
  • Барьеры записи (barrier=1, значение по умолчанию) — гарантируют порядок записи через кеш диска. Отключать нельзя, если нет батарейки/конденсатора на контроллере.
  • Тип FS: ext4 и XFS — рабочие лошадки. XFS лучше на больших файлах и параллельной записи, ext4 — на множестве мелких. Btrfs/ZFS с CoW дают неожиданную фрагментацию под нагрузкой БД; для PostgreSQL на ZFS обязательно recordsize=8K и отключение full_page_writes.
  • overlayfs (файловая система Docker) — copy-on-write при первой записи в файл из нижнего слоя. Пишешь 1 байт в 500-мегабайтный файл из образа — копируется весь файл. Поэтому данные и логи всегда выносят на volume.

Подробности durability в PostgreSQL — глава 17 (17-postgresql-internals.md).

4.6 Исчерпание диска: место и inodes

Классика, которую нужно уметь разобрать за 30 секунд.

Bash
df -h          # свободное место в байтах
df -i          # свободные inodes
$ df -h /var
Filesystem      Size  Used Avail Use% Mounted on
/dev/sda2        50G   21G   27G  44% /var

$ df -i /var
Filesystem      Inodes   IUsed   IFree IUse% Mounted on
/dev/sda2      3276800 3276791       9  100% /var

Место есть (27 ГБ), а запись падает с No space left on device. Причина — кончились inodes: структура, описывающая файл. Число inodes фиксируется при создании файловой системы (ext4) и не растёт. Миллионы мелких файлов — типично для кеша на диске, для сессий, для распакованных временных архивов, для /var/lib/docker/overlay2 — выедают inodes при пустом диске.

Bash
# Где именно сидят файлы — топ каталогов по числу файлов
sudo find /var -xdev -type f 2>/dev/null | awk -F/ '{print "/"$2"/"$3"/"$4}' | sort | uniq -c | sort -rn | head -20

# Топ каталогов по размеру
sudo du -xhd 3 /var 2>/dev/null | sort -rh | head -20

Второй классический сюрприз — удалённый, но открытый файл. rm удаляет имя (link), но пока файл открыт хоть одним процессом, место не освобождается:

Bash
# Место занято, du ничего не находит -> ищем удалённые открытые файлы
sudo lsof -nP +L1 | head -20
# COMMAND  PID USER FD TYPE DEVICE     SIZE/OFF NLINK NODE NAME
# java   12345 app  27w REG  8,2    19327352832     0  891 /var/log/app/app.log (deleted)

NLINK = 0 и (deleted) — файл удалён, 18 ГБ заняты, пока процесс жив. Лечение без рестарта: обнулить через /proc:

Bash
# Опустошить удалённый файл через его дескриптор (fd=27 у процесса 12345)
: > /proc/12345/fd/27

Это и есть причина, по которой logrotate с copytruncate иногда «не помогает», а без сигнала приложению create-режим ломает логирование: приложение продолжает писать в старый (удалённый) inode.

Правильная конфигурация logrotate для Java-сервиса:

/var/log/app/*.log {
    daily
    rotate 14
    size 256M
    compress
    delaycompress
    missingok
    notifempty
    copytruncate
}

copytruncate — копирует файл и обнуляет исходный, не меняя inode. Приложению ничего сообщать не надо. Минус: между копированием и обнулением можно потерять несколько строк. Альтернатива — create + postrotate с сигналом приложению; для Logback это означает настроить RollingFileAppender и вообще не использовать logrotate, что и есть правильный путь:

XML
<appender name="FILE" class="ch.qos.logback.core.rolling.RollingFileAppender">
  <file>/var/log/app/app.log</file>
  <rollingPolicy class="ch.qos.logback.core.rolling.SizeAndTimeBasedRollingPolicy">
    <fileNamePattern>/var/log/app/app.%d{yyyy-MM-dd}.%i.log.gz</fileNamePattern>
    <maxFileSize>256MB</maxFileSize>
    <maxHistory>14</maxHistory>
    <totalSizeCap>10GB</totalSizeCap>
  </rollingPolicy>
  ...
</appender>

totalSizeCap — обязательный параметр, который забывают. Без него maxHistory ограничивает только по времени, и всплеск логирования (например, при шторме исключений) забивает диск за час.

⚠️ Осторожно. В Kubernetes логи контейнера пишет kubelet в /var/log/pods/... и ротирует по containerLogMaxSize (значение по умолчанию 10 Mi) и containerLogMaxFiles (значение по умолчанию 5). Итого 50 МБ на контейнер. Приложение, логирующее в stdout со скоростью 5 МБ/с, переживает ротацию каждые две секунды, и kubectl logs показывает последние 10 секунд. Диагностика «что было час назад» становится невозможной — отсюда требование отправлять логи в централизованное хранилище (см. главу 51).

5. CPU и планировщик

5.1 Средняя загрузка (load average)

Средняя загрузка (load average) — это три числа в uptime и top: среднее число задач, которые выполняются или ждут выполнения, за последние 1, 5 и 15 минут. Это самая неверно интерпретируемая метрика Linux, и ниже разобрано, почему.

Bash
uptime
# 14:22:03 up 47 days,  3:11,  2 users,  load average: 18.42, 12.09, 8.77
cat /proc/loadavg
# 18.42 12.09 8.77 12/1843 28419
#  ^1м   ^5м  ^15м  ^runnable/всего задач  ^последний PID

Два факта, которые надо знать.

Факт 1. В Linux load average учитывает не только процессы, ждущие CPU, но и процессы в TASK_UNINTERRUPTIBLE. Формулировка Брендана Грегга: «Linux load averages track not just runnable tasks, but also tasks in the uninterruptible sleep state» (brendangregg.com). Это отличие Linux от классических Unix, введённое патчем 1993 года с обоснованием: «processes which are swapping or waiting on 'fast', i.e. noninterruptible, I/O, also consume resources».

Следствие прямое и важное: высокий LA на Linux может означать проблему с диском, а не с процессором. Машина с LA = 40 и CPU idle 95 % — это почти наверняка забитое или залипшее хранилище, а не нехватка ядер.

Факт 2. Это не средние, а экспоненциально затухающие суммы. Грегг: «exponentially-damped moving sums of a five second average». Один постоянно занятый CPU-поток за 60 секунд даст не 1.0, а примерно 0.62 на одноминутной метрике. Поэтому сравнивать LA с числом ядер можно только очень грубо.

Как правильно читать:

  • Тренд важнее абсолюта. 1м > 5м > 15м — нагрузка растёт. 1м < 15м — спадает.
  • LA > числа ядер не всегда плохо: для batch-нагрузки это нормальная утилизация. Для latency-чувствительного сервиса плохо уже при LA ≈ числу ядер, потому что появляется очередь в runqueue.
  • Чтобы понять природу LA, разложи его: посмотри vmstat 1 — колонка r (runnable) против b (blocked в uninterruptible).

Грегг рекомендует вместо LA смотреть per-CPU utilization, run queue latency (задержка от готовности до попадания на CPU) и метрики диска по методу USE. Run queue latency доступна через PSI:

Bash
cat /proc/pressure/cpu
# some avg10=12.34 avg60=8.91 avg300=4.02 total=1829384712
cat /proc/pressure/io
# some avg10=45.12 avg60=38.44 avg300=22.10 total=9182736451
# full avg10=31.02 avg60=27.15 avg300=15.88 total=7182736451
cat /proc/pressure/memory

PSI (Pressure Stall Information, ядро 4.20+) — куда более честная метрика: some = доля времени, когда хотя бы одна задача ждала ресурс; full = доля времени, когда все задачи ждали. io some avg10=45 означает: 45 % времени за последние 10 секунд кто-то ждал диск. Это прямое доказательство проблемы с I/O.

В cgroup v2 PSI есть на каждом уровне:

Bash
cat /sys/fs/cgroup/cpu.pressure
cat /sys/fs/cgroup/io.pressure
cat /sys/fs/cgroup/memory.pressure

💡 На интервью. «Что такое load average?» Ответ на четыре предложения: это экспоненциально сглаженные оценки числа задач, которые в среднем находились в состоянии «готов выполняться» или «ждёт непрерываемого I/O» за 1, 5 и 15 минут. В Linux, в отличие от классических Unix, туда попадают задачи в TASK_UNINTERRUPTIBLE, поэтому высокий LA может означать не нехватку CPU, а залипший диск или NFS. Сравнивать LA напрямую с числом ядер — грубое приближение, потому что это не мгновенное значение и не среднее в обычном смысле. Для реальной диагностики я смотрю vmstat 1 (колонки r и b), per-CPU загрузку и PSI в /proc/pressure/.

us/sy/id/wa/st То же, что в top wa высок — диск; st — гипервизор

Важно: первая строка вывода vmstat — средние с момента загрузки системы, её всегда игнорируют. Смотреть со второй.

Context switches (cs). Переключение контекста стоит порядка 1–5 мкс прямых затрат плюс потеря содержимого кешей и TLB (косвенные затраты часто больше прямых). Порядок величин: на нормально работающем сервере 5–50 тысяч переключений в секунду. 200 000+ — признак проблемы.

Типовые причины взрыва cs в Java-приложении:

  1. Пул потоков много больше числа ядер при CPU-bound работе. 500 потоков на 8 ядрах — планировщик только и делает, что перекладывает их.
  2. Contention на synchronized/ReentrantLock. Каждое неудачное взятие лока после спина — futex_wait, то есть добровольное переключение.
  3. Producer-consumer с маленькими порциями. Очередь на 1 элемент — переключение на каждое сообщение.
  4. Слишком маленький batch/linger у Kafka-производителя или fetch-size у потребителя.
  5. Таймеры с коротким периодом — ScheduledExecutorService с периодом 1 мс на сотне задач.

6. TCP в работе бэкенда

6.1 Установление соединения и диаграмма состояний TCP

Установление соединения — три пакета:

Клиент                                    Сервер
  |                                          | LISTEN
  |------------- SYN (seq=x) --------------->| SYN_RECV  (запись в SYN queue)
  | SYN_SENT                                 |
  |<-------- SYN+ACK (seq=y, ack=x+1) -------|
  |------------- ACK (ack=y+1) ------------->| ESTABLISHED (перенос в accept queue)
  | ESTABLISHED                              |

Цена — один RTT до первого байта данных. Если между сервисами 20 мс, каждое новое соединение стоит 20 мс до отправки запроса. Плюс TLS: TLS 1.2 — ещё 2 RTT, TLS 1.3 — 1 RTT (и 0-RTT при возобновлении, со своими рисками replay, см. FACTS гл. 40). Итого новое HTTPS-соединение через TLS 1.3 = 2 RTT = 40 мс, через TLS 1.2 = 3 RTT = 60 мс до первого байта запроса. Это и есть главная причина, по которой пулы соединений и keep-alive не роскошь, а обязательное требование.

Закрытие — четыре пакета (по два в каждую сторону):

Инициатор (активное закрытие)             Отвечающий (пассивное закрытие)
  |----------------- FIN ------------------->| CLOSE_WAIT
  | FIN_WAIT_1                               |
  |<----------------- ACK --------------------|
  | FIN_WAIT_2                               |   <- приложение должно вызвать close()
  |<----------------- FIN --------------------| LAST_ACK
  | TIME_WAIT                                |
  |----------------- ACK -------------------->| CLOSED
  | (2×MSL = 60 с в Linux)                   |
  | CLOSED                                   |

Полная таблица состояний, которые ты увидишь в ss:

Состояние Участники Значение Проблема при
LISTEN Сервер Сокет ждёт соединений —
SYN-SENT Клиент Отправил SYN, ждёт ответа Много и надолго → сервер недоступен, firewall дропает
SYN-RECV Сервер Получил SYN, отправил SYN+ACK, ждёт ACK Много → SYN flood или потери пакетов
ESTABLISHED Оба Рабочее состояние Количество > ожидаемого → утечка соединений
FIN-WAIT-1 Активный закрыватель Отправил FIN, ждёт ACK Много → пир не отвечает
FIN-WAIT-2 Активный закрыватель Свой FIN подтверждён, ждёт FIN от пира Много → пир не закрывает свою сторону (у него CLOSE_WAIT)
CLOSE-WAIT Пассивный закрыватель Получил FIN, ждёт, когда приложение вызовет close() Почти всегда баг в приложении
LAST-ACK Пассивный закрыватель Отправил свой FIN, ждёт последний ACK Обычно мимолётно
TIME-WAIT Активный закрыватель Ждёт 2×MSL, чтобы «дозревшие» пакеты не попали в новое соединение Десятки тысяч → исчерпание портов
CLOSING Оба Одновременное закрытие Редко
CLOSED — Сокета нет —

Ключевая асимметрия, которую надо понять раз и навсегда: TIME_WAIT — проблема того, кто закрыл первым; CLOSE_WAIT — проблема того, кто закрыл вторым (точнее, ещё не закрыл).

6.3 Состояние TIME_WAIT

TIME_WAIT длится 2×MSL (Maximum Segment Lifetime). В Linux это захардкожено: 60 секунд (константа TCP_TIMEWAIT_LEN, изменить можно только пересборкой ядра — net.ipv4.tcp_fin_timeout относится к FIN_WAIT_2, а не к TIME_WAIT, и это самая частая ошибка в интернет-советах).

Зачем TIME_WAIT существует — две причины:

  1. Не дать запоздавшим сегментам старого соединения попасть в новое с той же четвёркой (src IP, src port, dst IP, dst port). Если бы порт повторно использовался мгновенно, пакет, задержавшийся в сети на 30 секунд, был бы принят новым соединением как корректные данные.
  2. Гарантировать надёжное закрытие: если последний ACK потерялся, пир повторит FIN, и сторона в TIME_WAIT сможет ответить ACK. Если бы сокет был уже закрыт, пир получил бы RST.

Когда становится проблемой: на стороне, которая закрывает соединения первой и делает это часто. Чаще всего это клиент, который на каждый запрос создаёт новое соединение.

Арифметика исчерпания портов. Эфемерный диапазон по умолчанию: «The default values are 32768 and 60999 respectively» (kernel.org) — это 28 232 порта. Каждый закрытый клиентом порт занят на 60 секунд. Максимальная скорость создания соединений к одному адресу:порту:

28232 портов / 60 секунд ≈ 470 новых соединений в секунду

Превысил — получаешь java.net.NoRouteToHostException: Cannot assign requested address или BindException: Address already in use. Это очень распространённый потолок для сервисов, которые ходят в один backend без пула.

Bash
# Сколько TIME_WAIT и к кому
ss -tan state time-wait | awk 'NR>1 {print $4}' | cut -d: -f1 | sort | uniq -c | sort -rn | head

# Свободные эфемерные порты
sysctl net.ipv4.ip_local_port_range
ss -tan | awk 'NR>1 {split($3,a,":"); if (a[2]+0 >= 32768) print a[2]}' | sort -u | wc -l

Что делать, по убыванию правильности:

  1. Использовать keep-alive и пул соединений. Это не обходной путь, это правильное решение. Соединение, которое повторно используется, не закрывается и не попадает в TIME_WAIT. Настройка пулов HTTP-клиентов — глава 27.
  2. Сделать так, чтобы первым закрывал сервер, а не клиент — тогда TIME_WAIT накапливается на сервере, где портов сколько угодно (порт сервера один, различаются клиентские четвёрки). Именно так работает HTTP keep-alive с Connection: close от сервера.
  3. Расширить диапазон портов:
    Bash
    sysctl -w net.ipv4.ip_local_port_range="10240 65535"   # ~55 тыс. портов → ~920 conn/s
  4. net.ipv4.tcp_tw_reuse — «Enable reuse of TIME-WAIT sockets for new connections when it is safe from protocol viewpoint. 0 - disable, 1 - global enable, 2 - enable for loopback traffic only» (kernel.org). Работает только для исходящих соединений и опирается на TCP timestamps: ядро разрешает повторно использовать порт, если timestamp нового SYN больше последнего виденного. Относительно безопасно, широко применяется.
    Bash
    sysctl -w net.ipv4.tcp_tw_reuse=1
  5. net.ipv4.tcp_tw_recycle — НЕ ИСПОЛЬЗОВАТЬ. Этот параметр удалён из ядра в версии 4.12. До удаления он ломал соединения от клиентов за NAT: ядро отбрасывало SYN от адресов, чей timestamp «отстал», а за одним NAT-адресом сидят машины с разными timestamp. Классический инцидент 2010-х: «половина мобильных клиентов не может подключиться». Если видишь tcp_tw_recycle=1 в чьём-то runbook — это устаревший и вредный совет.
  6. SO_LINGER с таймаутом 0 — заставляет отправить RST вместо FIN, соединение закрывается без TIME_WAIT. Ценой потери данных в буфере отправки. Допустимо для аварийного сброса зависших соединений, недопустимо как общая политика.

💡 На интервью. «Что такое TIME_WAIT и когда он вреден?» — Это состояние активной стороны закрытия, длящееся 2×MSL (60 с в Linux), которое защищает от попадания дозревших сегментов старого соединения в новое с той же четвёркой и гарантирует доставку последнего ACK. Вреден он на клиенте, который часто открывает и закрывает соединения к одному адресу: эфемерных портов около 28 тысяч, и при более чем ~470 новых соединений в секунду они кончаются. Правильное лечение — пул и keep-alive, а не тюнинг ядра; из тюнинга допустим tcp_tw_reuse=1 и расширение ip_local_port_range. tcp_tw_recycle использовать нельзя — он удалён в ядре 4.12 и ломал клиентов за NAT.

6.4 Состояние CLOSE_WAIT

CLOSE_WAIT означает: пир прислал FIN, ядро его подтвердило, и теперь оно ждёт, когда приложение вызовет close() на этом сокете. Ядро ждать может вечно — у него нет таймера на это состояние.

Если CLOSE_WAIT накапливается, значит приложение читает из сокета (или не читает), видит конец потока, и не закрывает дескриптор. Это утечка fd с гарантией: рано или поздно будет Too many open files.

Bash
# Сколько и к кому
ss -tan state close-wait | awk 'NR>1 {print $5}' | sort | uniq -c | sort -rn | head

# С процессом
ss -tanp state close-wait | head -20

# Динамика
watch -n 2 "ss -tan state close-wait | wc -l"

Типовые причины в Java:

  1. HTTP-клиент не закрывает ответ. Apache HttpClient 5: CloseableHttpResponse должен быть закрыт, а тело — вычитано (EntityUtils.consume). OkHttp: Response.body() надо закрыть. Иначе соединение не возвращается в пул; когда сервер его закроет по своему keep-alive timeout, у клиента появится CLOSE_WAIT.
  2. Исключение в обработчике до close(). Классика: try { ... } catch { log } без finally.
  3. Пул соединений с maxIdleTime больше, чем у сервера. Сервер закрывает по 60 с простоя, клиент считает соединение живым ещё 300 с. Все 240 секунд соединение висит в CLOSE_WAIT, занимая fd. Правило: idle timeout клиента должен быть строго меньше idle timeout сервера, обычно в 2 раза.
  4. Собственный NIO-код без обработки read() == -1. -1 из SocketChannel.read() означает, что пир закрыл. Если это не обработать и не вызвать channel.close(), канал останется в CLOSE_WAIT навсегда, а селектор будет бесконечно сообщать о его готовности к чтению (level-triggered!) — получишь 100 % CPU на event loop вдобавок.
Java
// Правильно: HttpClient из JDK — тело надо потребить
HttpResponse<InputStream> resp = client.send(req, HttpResponse.BodyHandlers.ofInputStream());
try (InputStream in = resp.body()) {
    in.transferTo(sink);
}   // без этого соединение не вернётся в пул

// Правильно: NIO — обработка конца потока
int n = channel.read(buffer);
if (n == -1) {
    key.cancel();
    channel.close();     // без этого — CLOSE_WAIT навсегда
    return;
}

⚠️ Осторожно. Перезапуск приложения «решает» проблему CLOSE_WAIT — дескрипторы закрываются вместе с процессом. Именно поэтому баг живёт годами: сервис рестартуют раз в неделю при деплое, и накопление не успевает дойти до лимита. Потом наступает праздничная неделя без деплоев — и сервис падает в новогоднюю ночь. Оповещение на process_files_open / process_files_max > 0.5 и на число CLOSE_WAIT ловит это заранее.

6.5 Backlog и очередь accept

На сервере есть две очереди, и их путают постоянно.

SYN пришёл  ──>  [ SYN queue ]  ──(пришёл ACK)──>  [ accept queue ]  ──(accept())──>  приложение
                 размер:                            размер:
                 tcp_max_syn_backlog                min(backlog, somaxconn)

  1. SYN queue (очередь полуоткрытых соединений). Соединения в состоянии SYN_RECV: сервер отправил SYN+ACK, ждёт финальный ACK. Размер — net.ipv4.tcp_max_syn_backlog («Maximal number of remembered connection requests (SYN_RECV), which have not received an acknowledgment from connecting client. This is a per-listener limit»).

  2. Accept queue (очередь установленных соединений). Рукопожатие завершено, соединение ESTABLISHED, но приложение ещё не вызвало accept(). Размер — min(backlog, net.core.somaxconn), где backlog — второй аргумент системного вызова listen().

net.core.somaxconn: «Limit of socket listen() backlog, known in userspace as SOMAXCONN. Defaults to 4096. (Was 128 before linux-5.4)» (kernel.org). На ядрах до 5.4 значение по умолчанию было 128 — вот откуда все советы «поднимите somaxconn».

Что задают серверы на Java:

  • Tomcat: server.tomcat.accept-count (по умолчанию 100).
  • Netty/Reactor Netty: опция канала SO_BACKLOG (у Netty значение по умолчанию берётся из somaxconn, но Spring Boot часто выставляет явно).
  • Jetty: acceptQueueSize на ServerConnector (значение по умолчанию 0 → системный).
  • Чистая Java: new ServerSocket(port, backlog) или ServerSocketChannel.bind(addr, backlog).
YAML
# Spring Boot: accept queue и число рабочих потоков
server:
  tomcat:
    accept-count: 1000          # длина accept-очереди
    max-connections: 8192       # сколько соединений сервер держит одновременно
    threads:
      max: 200
      min-spare: 20

Переполнение accept-очереди. Ключевая команда:

Bash
ss -lnt
State   Recv-Q   Send-Q      Local Address:Port      Peer Address:Port
LISTEN  0        1000              0.0.0.0:8080           0.0.0.0:*
LISTEN  129      128               0.0.0.0:8443           0.0.0.0:*

Для сокетов в состоянии LISTEN колонки означают не то, что для остальных:

  • Recv-Q = текущее число соединений в accept-очереди, ожидающих accept();
  • Send-Q = максимальный размер accept-очереди (эффективный backlog).

Recv-Q 129 при Send-Q 128 — очередь переполнена, новые соединения дропаются (или получают RST, если tcp_abort_on_overflow=1). На порту 8080 всё хорошо: 0 из 1000.

Для не-LISTEN сокетов Recv-Q — непрочитанные приложением байты, Send-Q — неподтверждённые отправленные байты. Большой Recv-Q на ESTAB-сокете = приложение не успевает читать.

Счётчики переполнения:

Bash
netstat -s | grep -iE 'listen|overflow|SYNs to LISTEN'
# или
nstat -az | grep -iE 'ListenOverflows|ListenDrops|TCPReqQFullDrop'
    18291 times the listen queue of a socket overflowed
    18291 SYNs to LISTEN sockets dropped

Растущее «listen queue overflowed» — прямое доказательство того, что приложение не успевает принимать соединения. Мониторить надо дельту, а не абсолютное значение.

Ещё точнее — eBPF-инструмент:

Bash
# Ловит момент переполнения с именем процесса
sudo /usr/sbin/bpftrace -e 'kprobe:tcp_v4_syn_recv_sock { }' 2>/dev/null
# Готовый инструмент из bcc:
sudo /usr/share/bcc/tools/tcpaccept
sudo /usr/share/bcc/tools/tcpdrop

⚠️ Осторожно. Поведение при переполнении accept-очереди по умолчанию — без уведомления выбросить финальный ACK. Клиент считает соединение установленным (он отправил ACK и перешёл в ESTABLISHED), отправляет запрос — и ничего не получает. Через несколько секунд сервер по таймеру повторит SYN+ACK, клиент повторит ACK, и если к тому моменту очередь освободится, соединение заработает. Симптом со стороны клиента: случайные запросы занимают ровно 1, 3 или 7 секунд (экспоненциальная задержка повторных передач SYN+ACK). Если увидел бимодальное распределение latency с пиками на 1 с и 3 с — смотри ss -lnt и ListenOverflows. Альтернатива — net.ipv4.tcp_abort_on_overflow=1: «If listening service is too slow to accept new connections, reset them» — клиент получит быстрый RST вместо таинственного зависания. Часто это лучше для диагностики, но клиенты начнут видеть Connection reset by peer.

SYN flood и SYN cookies. При атаке SYN queue забивается полуоткрытыми соединениями. Механизм защиты — SYN cookies: сервер не хранит состояние, а кодирует его в начальный sequence number SYN+ACK, восстанавливая при получении ACK. «Send out syncookies when the syn backlog queue of a socket overflows... Default: 1» (kernel.org).

Bash
sysctl net.ipv4.tcp_syncookies        # 1 = включать при переполнении
nstat -az | grep -i syncookie
# TcpExtSyncookiesSent   1842
# TcpExtSyncookiesRecv   1801

Цена SYN cookies: теряются TCP-опции, согласуемые в SYN (частично восстанавливаются через timestamps), окно ограничено. Для нормальной работы это не режим, а аварийный клапан. Ненулевой SyncookiesSent на внутреннем сервисе — не атака, а перегрузка: SYN queue переполнилась от легитимного трафика.

6.6 Два механизма keep-alive

Слово «keep-alive» означает две совершенно разные вещи, и их постоянно смешивают.

Критерий TCP keep-alive HTTP keep-alive (persistent connections)
Уровень Транспортный, в ядре Прикладной, в HTTP
Что делает Периодически шлёт пустые пробы, чтобы понять, жив ли пир Не закрывает TCP-соединение после ответа, повторно использует для следующего запроса
Настраивается SO_KEEPALIVE + sysctl / per-socket опции Connection: keep-alive (HTTP/1.1 — по умолчанию), Keep-Alive: timeout=N, max=M
Зачем Обнаружить мёртвого пира, не дать NAT/firewall выбросить запись Сэкономить RTT и TLS-handshake
Значение по умолчанию Выключен на уровне сокета Включён в HTTP/1.1

TCP keep-alive. По умолчанию SO_KEEPALIVE выключен. Если включить, применяются системные параметры (man7.org tcp(7)):

Bash
sysctl net.ipv4.tcp_keepalive_time     # 7200 — 2 часа простоя до первой пробы
sysctl net.ipv4.tcp_keepalive_intvl    # 75   — интервал между пробами
sysctl net.ipv4.tcp_keepalive_probes   # 9    — сколько проб до признания мёртвым

Два часа — это значение по умолчанию из 1980-х, и он ломает всё в современной инфраструктуре. Промежуточные устройства (NAT, stateful firewall, облачный NLB, conntrack на узле) выбрасывают записи о неактивных соединениях гораздо раньше:

📊 Цифры (типовые idle timeout промежуточных устройств). AWS Network Load Balancer — 350 секунд (не настраивается), AWS Application Load Balancer — 60 секунд по умолчанию (настраивается). Azure Load Balancer — 4 минуты по умолчанию. Linux nf_conntrack_tcp_timeout_established — 432000 секунд (5 дней) по умолчанию, но админы часто урезают до часов. Корпоративные firewall — обычно 30–60 минут. ⚠️ Значения облачных балансировщиков приведены по памяти и не сверялись с документацией провайдеров при подготовке главы.

Итог: соединение в пуле простояло 10 минут, промежуточный firewall тихо выбросил запись о нём (не послав RST!), приложение берёт соединение из пула, отправляет запрос — и получает таймаут через 15 минут (пока ядро не исчерпает tcp_retries2, который «default value of 15 yields a hypothetical timeout of 924.6 seconds»). Симптом: редкие запросы висят ровно ~15 минут и падают по таймауту.

Лечение — три уровня, применять все:

  1. Per-socket keep-alive с адекватными значениями. В Java с JDK 11 есть расширенные опции:
    Java
    import jdk.net.ExtendedSocketOptions;

socket.setKeepAlive(true);
socket.setOption(ExtendedSocketOptions.TCP_KEEPIDLE, 60);     // 60 с простоя
socket.setOption(ExtendedSocketOptions.TCP_KEEPINTERVAL, 10); // проба каждые 10 с
socket.setOption(ExtendedSocketOptions.TCP_KEEPCOUNT, 3);     // 3 пробы → 90 с до разрыва
    В Netty: .childOption(ChannelOption.SO_KEEPALIVE, true) плюс EpollChannelOption.TCP_KEEPIDLE и соседние.
  2. Validation/idle eviction в пуле. HikariCP: maxLifetime (значение по умолчанию 1800000 мс = 30 мин) и keepaliveTime; Apache HttpClient: evictIdleConnections и validateAfterInactivity; Reactor Netty: maxIdleTime в ConnectionProvider. Правило: maxLifetime пула меньше idle timeout любого промежуточного устройства на пути.
  3. Прикладной heartbeat там, где протокол его поддерживает (gRPC keepalive, AMQP heartbeat — значение по умолчанию 60 с, WebSocket ping/pong, Kafka connections.max.idle.ms — значение по умолчанию 9 минут).
Java

cfg.setKeepaliveTime(Duration.ofMinutes(5).toMillis());  // пинг простаивающих

6.7 Алгоритм Нейгла и отложенное подтверждение (delayed ACK)

Алгоритм Нейгла и отложенное подтверждение (delayed ACK) — два независимых механизма TCP, которые экономят пакеты: первый придерживает маленькие сегменты у отправителя, второй откладывает подтверждение у получателя. По отдельности каждый полезен, а при встрече они дают патологию: обе стороны ждут друг друга, и маленький запрос задерживается на десятки миллисекунд.

Алгоритм Нейгла (RFC 896): не отправлять новый маленький сегмент, пока есть неподтверждённые данные в полёте. Цель — не забивать сеть пакетами по 1 байту (telnet-трафик 1980-х). TCP_NODELAY отключает: «If set, disable the Nagle algorithm. This means that segments are always sent as soon as possible, even if there is only a small amount of data» (tcp(7)).

Delayed ACK (RFC 1122): не подтверждать сразу, подождать до 40 мс (в Linux — от 40 мс до 200 мс, TCP_DELACK_MIN = 40 мс) в надежде приклеить ACK к ответным данным или накопить два сегмента.

Патология: приложение делает write() заголовка, потом write() тела. Первый сегмент улетает. Второй Nagle придерживает, потому что первый не подтверждён. Получатель не отвечает ACK сразу, потому что delayed ACK. Через 40 мс срабатывает таймер delayed ACK, приходит ACK, Nagle отпускает второй сегмент. Плюс 40 мс к каждому запросу — стабильно, воспроизводимо, необъяснимо без знания механизма.

Симптом: латентность запроса ровно ~40 мс при пинге 0.2 мс, и она не зависит от нагрузки.

Лечение:

Java
socket.setTcpNoDelay(true);      // почти всегда правильно для RPC

В Netty: .option(ChannelOption.TCP_NODELAY, true) — и Netty включает это по умолчанию (в отличие от голых сокетов JDK, где по умолчанию Nagle включён). Tomcat/Jetty также ставят TCP_NODELAY по умолчанию на соединениях. То есть большинство современных Java-стеков уже защищены; проблема всплывает в самописном NIO-коде, в старых клиентах и в нативных библиотеках.

Более правильное решение, чем TCP_NODELAY — не делать несколько мелких write(): собрать сообщение в один буфер и отправить одним вызовом (или writev/gathering write). Тогда Nagle не мешает вовсе.

Есть ещё TCP_CORK (противоположность TCP_NODELAY): явно придержать отправку, пока не накопится полный сегмент или не снимут cork. Используется в файловых серверах с sendfile. Из Java недоступен напрямую.

⚠️ Осторожно. TCP_NODELAY=true на соединении, по которому идёт поток мелких сообщений (например, много flush() в лог-агент), даёт взрыв числа пакетов и нагрузку на сеть. Правило: TCP_NODELAY для request-response с низкой latency, буферизация в приложении — для потоковых нагрузок.

6.8 Буферы, окно TCP и произведение полосы на задержку (BDP)

Пропускная способность TCP ограничена не только шириной канала, но и размером окна:

максимальная пропускная способность = размер окна / RTT

Отсюда BDP (Bandwidth-Delay Product) — сколько данных должно быть «в полёте», чтобы канал был загружен:

BDP = полоса × RTT

Примеры:

  • LAN: 10 Гбит/с × 0.2 мс = 250 КБ;
  • между дата-центрами внутри региона: 1 Гбит/с × 5 мс = 625 КБ;
  • трансатлантика: 1 Гбит/с × 80 мс = 10 МБ.

Если буфер приёма меньше BDP, канал недогружен независимо от его ширины. Классический случай: репликация БД между регионами идёт со скоростью 30 Мбит/с при канале 1 Гбит/с — потому что окно упёрлось в буфер размера по умолчанию.

Bash
# Автотюнинг буферов: min default max (в байтах)
sysctl net.ipv4.tcp_rmem     # 4096  131072  6291456
sysctl net.ipv4.tcp_wmem     # 4096   16384  4194304
sysctl net.core.rmem_max     # потолок для SO_RCVBUF, задаваемого вручную
sysctl net.core.wmem_max
sysctl net.ipv4.tcp_moderate_rcvbuf   # 1 — автотюнинг включён

Linux по умолчанию автоматически подстраивает буфер приёма (tcp_moderate_rcvbuf=1) в пределах tcp_rmem. Это работает хорошо, и в 95 % случаев трогать ничего не надо.

⚠️ Осторожно: важнейшая ловушка этого раздела. Если приложение явно вызывает setReceiveBufferSize() / setSendBufferSize() (или SO_RCVBUF/SO_SNDBUF в Netty), автотюнинг отключается для этого сокета. Программист «оптимизировал», поставив 64 КБ, и на трансатлантическом канале получил потолок 64 КБ / 80 мс = 6.4 Мбит/с. Правило: не задавай размеры буферов вручную, если не измерил, что автотюнинг не справляется.

Для очень «длинных и толстых» каналов (long fat networks) нужны:

Bash
sysctl net.ipv4.tcp_window_scaling      # 1 — масштабирование окна (RFC 7323), обязательно
sysctl net.core.rmem_max=16777216
sysctl net.ipv4.tcp_rmem="4096 131072 16777216"

Без window scaling максимальное окно — 65535 байт, что на 80 мс RTT даёт 6.5 Мбит/с. Опция согласуется в SYN; если промежуточный firewall вырезает неизвестные TCP-опции (такие ещё встречаются), соединение работает, но медленно и загадочно.

6.9 MTU, фрагментация и потеря пакетов при PMTU discovery

MTU (Maximum Transmission Unit) — максимальный размер кадра. Ethernet: 1500 байт. MSS (Maximum Segment Size) — сколько в нём остаётся под данные TCP: 1500 − 20 (IP) − 20 (TCP) = 1460. С опциями (timestamps) — 1448, что ты и видишь в ss -i.

Проблема начинается с туннелей. VPN (IPsec, WireGuard), overlay-сети Kubernetes (VXLAN, Geneve), GRE — все добавляют заголовки и уменьшают эффективный MTU: VXLAN съедает 50 байт (MTU 1450), IPsec — 50–80, WireGuard — 60 (MTU 1420).

Path MTU Discovery: отправитель ставит бит DF (Don't Fragment); если по пути встретился участок с меньшим MTU, маршрутизатор отвечает ICMP «Fragmentation Needed» с указанием MTU. Отправитель уменьшает сегменты.

PMTU black hole — если firewall блокирует ICMP (а его блокируют постоянно «из соображений безопасности»), сообщение не доходит. Результат: маленькие пакеты проходят, большие — пропадают бесследно. Симптомы:

  • ping работает, curl к health-эндпоинту работает, а запрос с большим телом висит и падает по таймауту;
  • TLS handshake зависает на ServerHello с сертификатом (он большой);
  • SELECT из БД, возвращающий много строк, зависает, а SELECT 1 работает.

Диагностика:

Bash
# Найти реальный PMTU: пингуем с DF и растущим размером
ping -M do -s 1472 10.20.3.44     # 1472 + 28 = 1500
ping -M do -s 1422 10.20.3.44     # 1422 + 28 = 1450 (VXLAN)
# "Frag needed and DF set (mtu = 1450)" -> нашли

# Что ядро запомнило про PMTU к адресу
ip route get 10.20.3.44

# MTU интерфейсов
ip link show
Bash
# Лечение на стороне сервера: зажать MSS в SYN (MSS clamping)
sudo iptables -t mangle -A FORWARD -p tcp --tcp-flags SYN,RST SYN \
     -j TCPMSS --clamp-mss-to-pmtu

В Kubernetes MTU задаётся CNI-плагином; несогласованность MTU между CNI и физической сетью — стандартная причина «странных зависаний» в новом кластере. Детали — глава 49.

Алгоритм управления перегрузкой определяет, как быстро наращивать окно и как реагировать на потери.

Bash

# reno cubic bbr
Алгоритм Модель Сильная сторона Слабая сторона
Reno Потеря = перегрузка, AIMD Простой, всегда доступен («The algorithm 'reno' is always available») Плохо масштабируется на быстрых каналах
CUBIC Потеря = перегрузка, кубический рост окна Значение по умолчанию Linux с 2006 года, хорошо работает на LFN Заполняет буферы маршрутизаторов до потерь → bufferbloat, растущая latency
BBR Моделирует полосу и минимальный RTT, не ждёт потерь Заметно выше пропускная способность на каналах с потерями (WAN, мобильные сети), не раздувает очереди Может быть агрессивным к CUBIC-потокам на общем узком месте; поведение v1 и v3 различается

Практика: внутри дата-центра менять не надо, CUBIC работает. BBR даёт выигрыш на междугородних/международных каналах с ненулевыми потерями — там его включают на edge-серверах и CDN (Google и Cloudflare используют BBR в проде). Включение:

Bash
sysctl -w net.ipv4.tcp_congestion_control=bbr
sysctl -w net.core.default_qdisc=fq          # BBR требует fq или fq_codel для pacing
echo 'net.ipv4.tcp_congestion_control=bbr' >> /etc/sysctl.d/99-net.conf

Ещё один параметр, который стоит знать:

Bash
sysctl net.ipv4.tcp_slow_start_after_idle    # 1 (enabled)

«If enabled, provide RFC2861 behavior and time out the congestion window after an idle period» (kernel.org). То есть соединение, простоявшее дольше одного RTO, сбрасывает congestion window и начинает slow start заново. Для пула долгоживущих соединений с редкими всплесками это означает: первый запрос после паузы идёт медленно. Для внутренних сервисов с надёжной сетью обычно выключают:

Bash
sysctl -w net.ipv4.tcp_slow_start_after_idle=0

6.11 Стоимость нового соединения

Новое соединение обходится дорого, потому что до первого байта ответа клиент проходит разрешение имени, TCP-рукопожатие и TLS, и каждый этап добавляет круги по сети. Соберём разобранные выше этапы вместе и посчитаем, во что обходится одно новое HTTPS-соединение к сервису с RTT 20 мс:

Фаза Стоимость Комментарий
Разрешение имени в DNS (если не в кеше) 1–2 RTT до распознавателя + возможные таймауты См. раздел 7
TCP handshake 1 RTT = 20 мс Обязательно
TLS 1.3 handshake 1 RTT = 20 мс TLS 1.2 — 2 RTT = 40 мс
Slow start Начальное окно 10 сегментов ≈ 14 КБ; ответ 100 КБ потребует ещё 2–3 RTT tcp_slow_start_after_idle возвращает это и на «отдохнувших» соединениях
Порт в TIME_WAIT после закрытия 60 секунд занятости эфемерного порта Потолок ~470 conn/s к одному адресу
Память ядра ~4–10 КБ на сокет (структуры + буферы) При 100 тыс. соединений — сотни МБ
fd 1 на соединение Лимит nofile

Итого: новое HTTPS-соединение = 40–60 мс до первого байта запроса плюс ещё 40–60 мс на раскачку окна для большого ответа. Повторно использованное соединение = 0 мс.

Следствия для кода и конфигурации:

  1. Пул соединений обязателен для всего: БД (HikariCP), HTTP-клиенты, Kafka, Redis, gRPC-каналы.
  2. Размер пула считается по закону Литтла: размер = RPS × latency. При 500 RPS и 40 мс latency нужно 20 соединений, а не 200. Избыточный пул — это простаивающие соединения, которые протухают и создают CLOSE_WAIT.
  3. Таймауты обязательны на каждом уровне: connect timeout (1–3 с), socket/read timeout (по SLA зависимости), timeout пула на получение соединения. Отсутствие connect timeout означает, что при сетевом разделении поток встанет на tcp_syn_retries × экспоненциальный backoff — это 127 секунд при значении по умолчанию 6 попыток.
    Bash
    sysctl net.ipv4.tcp_syn_retries    # 6 -> ~127 с до отказа connect()
  4. Idle timeout клиента < idle timeout сервера < idle timeout сетевого оборудования.
  5. HTTP/2 мультиплексирование решает часть проблемы: один TCP-коннект несёт сотни параллельных стримов. Цена — head-of-line blocking на уровне TCP (потеря одного пакета тормозит все стримы), что и решает HTTP/3 поверх QUIC. Детали — глава 27.

Словарь: DNS

7.1 Порядок разрешения имени

Когда Java вызывает InetAddress.getByName("db.prod.internal"), происходит следующая цепочка. Знать её нужно целиком, потому что сломаться может любое звено.

Шаг 1. /etc/nsswitch.conf — определяет источники и порядок:

hosts: files dns myhostname

files — /etc/hosts, dns — распознаватель, myhostname — модуль systemd для собственного имени. Бывают ещё mdns4_minimal (Avahi), nis, resolve (systemd-resolved напрямую). Если в цепочке стоит mdns4_minimal [NOTFOUND=return], любое имя с одной точкой уйдёт в mDNS и получит таймаут.

Шаг 2. /etc/hosts — статическое сопоставление. Проверяется первым, если files идёт первым.

Шаг 3. /etc/resolv.conf — конфигурация распознавателя:

nameserver 10.96.0.10
search my-namespace.svc.cluster.local svc.cluster.local cluster.local
options ndots:5 timeout:1 attempts:2

Ограничения по resolv.conf(5): «Up to MAXNS (currently 3) name servers may be listed». Больше трёх — без предупреждения игнорируются. Значения по умолчанию: timeout — «the default is RES_TIMEOUT (currently 5)» секунд, максимум 30; attempts — «The default is RES_DFLRETRY (currently 2)», максимум 5.

Шаг 4. ndots и search-домены. «Sets a threshold for the number of dots which must appear in a name... before an initial absolute query will be made. The default for n is 1.»

Логика: если в имени меньше ndots точек, распознаватель сначала перебирает search-домены, и только потом пробует имя как абсолютное. Если точек ndots или больше — сначала абсолютный запрос.

В Kubernetes kubelet ставит ndots:5 (см. FACTS, гл. 49). Значит, имя api.external-vendor.com (2 точки, меньше 5) сначала будет искаться как:

api.external-vendor.com.my-namespace.svc.cluster.local   -> NXDOMAIN
api.external-vendor.com.svc.cluster.local                -> NXDOMAIN
api.external-vendor.com.cluster.local                    -> NXDOMAIN
api.external-vendor.com                                  -> ответ

Четыре запроса вместо одного. А с включённым IPv6 — восемь, потому что glibc параллельно спрашивает A и AAAA для каждого варианта. Это и есть знаменитый «DNS тормозит в Kubernetes».

Лечение — точка в конце имени делает его FQDN и отключает перебор:

Java
// Точка в конце — абсолютное имя, ровно один запрос
var uri = URI.create("https://api.external-vendor.com./v1/payments");

⚠️ Не все библиотеки корректно работают с trailing dot (некоторые проверяют hostname в TLS-сертификате буквально и ломаются). Более надёжный путь — dnsConfig в спецификации пода:

YAML
spec:
  dnsConfig:
    options:
      - name: ndots
        value: "2"
      - name: timeout
        value: "1"
      - name: attempts
        value: "2"
      - name: single-request-reopen

Шаг 5. Сам запрос. UDP-пакет на порт 53 распознавателю, ожидание ответа. Если ответ не помещается в 512 байт (или EDNS-размер) — флаг TC (truncated) и повтор по TCP.

7.2 Три уровня кеширования DNS

Уровень 1: DNS-сервер (CoreDNS, BIND, Unbound). Кеширует по TTL записи.

Уровень 2: ОС. Здесь главный сюрприз: классический glibc-распознаватель не кеширует вообще. Каждый getaddrinfo() — сетевой запрос. Кеш появляется только если установлен:

  • systemd-resolved (слушает на 127.0.0.53, кеширует, поддерживает DNSSEC и DoT);
  • nscd (старый демон кеширования, кеширует hosts, passwd, group);
  • dnsmasq / unbound в режиме локального кеша;
  • в Kubernetes — NodeLocal DNSCache (DaemonSet с CoreDNS на каждом узле, слушает на link-local адресе).

В минимальном контейнере (alpine, distroless, debian-slim) никакого кеша нет. Каждый HTTP-запрос к внешнему хосту, если JVM не закешировала, — поход в CoreDNS. При 1000 RPS это 1000 (а с ndots:5 — до 8000) DNS-запросов в секунду с одного пода. CoreDNS в кластере ложится, и «тормозит всё».

Bash
# Есть ли кеш в системе
systemctl is-active systemd-resolved
resolvectl statistics            # если systemd-resolved: hit/miss кеша
cat /etc/resolv.conf             # 127.0.0.53 = systemd-resolved
getent hosts example.com         # резолв через nsswitch (как это делает приложение!)

Уровень 3: JVM. Это то, что обязан знать каждый Java-разработчик.

InetAddress кеширует результаты в статическом кеше процесса. Управление — свойствами безопасности (docs.oracle.com JDK 21):

Свойство Назначение Значение по умолчанию
networkaddress.cache.ttl Сколько секунд кешировать успешные разрешения имён. -1 = «cache forever» «Implementation specific period of time»
networkaddress.cache.negative.ttl Сколько кешировать неудачные. 0 = не кешировать, -1 = вечно 10 секунд
networkaddress.cache.stale.ttl (JDK 21+) Сколько держать протухшие имена, чтобы отдавать их при недоступности DNS «Implementation specific»; 0 или не задано = не использовать

Исторический контекст, который важен: раньше при установленном SecurityManager значение по умолчанию networkaddress.cache.ttl было «вечно». SecurityManager удалён (JDK 24, см. главу 02), и в современных JDK кеш успешных разрешений имён ограничен (в HotSpot — 30 секунд, но это implementation specific и формально не гарантировано). ⚠️ Полагаться на конкретное число нельзя — задавай явно.

Критичность. Сценарий: приложение разрешает payments-db.internal в 10.20.3.44 и кеширует «навсегда». DBA делает failover, DNS-запись переезжает на 10.20.3.55 с TTL 30 секунд. Все клиенты переключаются за полминуты — кроме твоей JVM, которая продолжает долбиться в мёртвый IP до рестарта. То же самое при смене IP у AWS RDS, при переезде сервиса, при смене IP у внешнего API.

Задавать явно — двумя способами:

Bash
# 1. Системное свойство (работает с JDK 8u and later; официально документированный путь — java.security)
java -Dsun.net.inetaddr.ttl=30 -Dsun.net.inetaddr.negative.ttl=5 -jar app.jar
properties
# 2. Правильный путь: файл java.security или override
# $JAVA_HOME/conf/security/java.security
networkaddress.cache.ttl=30
networkaddress.cache.negative.ttl=5
networkaddress.cache.stale.ttl=60
Bash
# Подключить свой файл поверх дефолтного
java -Djava.security.properties=/opt/app/extra.security -jar app.jar

Или программно, на старте приложения:

Java
public final class DnsCacheConfig {
    static {
        java.security.Security.setProperty("networkaddress.cache.ttl", "30");
        java.security.Security.setProperty("networkaddress.cache.negative.ttl", "5");
    }
}

⚠️ Важно: Security.setProperty должен выполниться до первого разрешения имени, иначе значение уже прочитано и закешировано в InetAddressCachePolicy.

Рекомендуемые значения для облачной/кубернетесной среды: ttl=30, negative.ttl=0…5. Негативный кеш особенно коварен: под стартует раньше, чем сервис-зависимость получила эндпоинты, получает NXDOMAIN, кеширует его на 10 секунд — и первые запросы падают уже после того, как всё поднялось.

7.3 IPv6 и таймауты разрешения имён

Если в системе включён IPv6, glibc при getaddrinfo() без указания семейства запрашивает и A, и AAAA, обычно параллельно двумя UDP-пакетами с одного сокета. Если DNS-сервер или промежуточное оборудование плохо обрабатывает параллельные запросы с одного порта (встречалось у старых firewall и у некоторых реализаций conntrack), один из ответов теряется, и запрос ждёт timeout (5 с по умолчанию) и делает attempts попыток. Итого до 10 секунд на одно разрешение имени.

Признаки: getent hosts foo отрабатывает мгновенно, а curl foo — за 5 или 10 секунд. Или наоборот, всё быстро на одном узле и медленно на другом.

Лечение на уровне распознавателя:

options single-request-reopen

«single-request disables parallel IPv4/IPv6 lookups, while single-request-reopen closes and reopens sockets between sequential requests» (resolv.conf(5)).

Лечение на уровне JVM:

Bash
# Не запрашивать AAAA и не использовать IPv6-сокеты
java -Djava.net.preferIPv4Stack=true -jar app.jar

# Использовать IPv6-стек, но предпочитать IPv4-адреса при резолве
java -Djava.net.preferIPv6Addresses=false -jar app.jar

preferIPv4Stack=true — грубо, но эффективно, если IPv6 в инфраструктуре не используется. Побочный эффект: приложение не сможет слушать на IPv6 и не подключится к IPv6-only сервисам.

Отдельная ловушка: сервис разрешается в AAAA, но IPv6-маршрутизации нет. Java пытается подключиться по IPv6, получает ENETUNREACH или зависает до connect timeout, потом (если реализована политика Happy Eyeballs — в JDK HttpClient она есть, в старых клиентах нет) пробует IPv4. В голом Socket фоллбэка нет вовсе — будет исключение.

Поэтому фраза «я проверил, dig разрешает нормально» ничего не доказывает. Проверять надо через getent hosts, который идёт через nsswitch, как и getaddrinfo() в JVM.

Замер времени разрешения имён в динамике:

Bash
# Сколько времени занимает резолв, 20 раз
for i in $(seq 20); do
  /usr/bin/time -f '%e' getent hosts api.example.com > /dev/null
done 2>&1 | sort -n | tail -5

И изнутри JVM — чтобы увидеть, что реально видит приложение:

Java
// Разовая проверка резолва и кеша
public static void main(String[] args) throws Exception {
    for (int i = 0; i < 5; i++) {
        long t = System.nanoTime();
        InetAddress[] addrs = InetAddress.getAllByName(args[0]);
        long ms = (System.nanoTime() - t) / 1_000_000;
        System.out.printf("%d ms -> %s%n", ms, Arrays.toString(addrs));
        Thread.sleep(1000);
    }
}

Первый вызов — сетевой (десятки мс), последующие — из кеша JVM (0 мс). Если все пять по 20 мс, кеш выключен; если через минуту всё ещё 0 мс — кеш вечный.

tcpdump — снять трафик.

Bash

# Только RST — быстро найти, кто рвёт соединения

# HTTP-запросы в открытом виде (только для нешифрованного)
sudo tcpdump -i any -nn -A -s 0 'tcp port 8080 and tcp[((tcp[12:1] & 0xf0) >> 2):4] = 0x47455420'
#                                                                              ^^^^^^^^^^ "GET "

Флаги, которые нужны всегда: -nn (не превращать в имена ни адреса, ни порты — иначе tcpdump сам породит DNS-трафик и будет тормозить), -s 0 (не обрезать пакеты), -i any (все интерфейсы).

Что смотреть в Wireshark:

  • tcp.analysis.duplicate_ack — дубликаты ACK, предвестник fast retransmit;
  • tcp.flags.reset == 1 — кто и когда прислал RST;
  • Statistics → Conversations → TCP — топ по объёму и длительности;
  • Statistics → TCP Stream Graphs → Time Sequence — визуально видно застревания.

8.3 eBPF-инструменты

eBPF позволяет загружать в ядро верифицированные программы, срабатывающие на точках трассировки, без перезагрузки и без накладных расходов ptrace. Для диагностики это качественный скачок: то, что раньше требовало strace с 50-кратным замедлением, теперь измеряется с накладными расходами в доли процента.

bpftrace — высокоуровневый язык поверх eBPF (github.com/bpftrace/bpftrace):

Bash
# Гистограмма латентности блочного I/O
sudo bpftrace -e '
  kprobe:blk_account_io_start { @start[arg0] = nsecs; }
  kprobe:blk_account_io_done /@start[arg0]/ {
    @usecs = hist((nsecs - @start[arg0]) / 1000); delete(@start[arg0]);
  }'

# Кто открывает файлы
sudo bpftrace -e 'tracepoint:syscalls:sys_enter_openat {
    printf("%s %s\n", comm, str(args->filename)); }'

# Сколько раз какой процесс вызывает какой syscall
sudo bpftrace -e 'tracepoint:raw_syscalls:sys_enter { @[comm, args->id] = count(); }'

# Все новые TCP-соединения с адресами
sudo bpftrace -e 'kprobe:tcp_connect { printf("%s pid=%d\n", comm, pid); }'

9. Разобранные инциденты

9.1 Too many open files под нагрузкой

Симптом. Платёжный сервис, пик нагрузки в 12:00. С 12:04 в логах лавина:

java.net.SocketException: Too many open files
	at java.base/sun.nio.ch.Net.socket0(Native Method)
	at java.base/sun.nio.ch.Net.socket(Net.java:551)

Одновременно перестал отвечать health-эндпоинт (Tomcat не может принять соединение), Kubernetes убил под по liveness-пробе, под перезапустился и работал ещё 4 минуты — и цикл повторился.

Проверено.

Bash
kubectl exec -it payments-7f8-x2k -- sh -c 'ls /proc/1/fd | wc -l; grep "open files" /proc/1/limits'
# 1024
# Max open files            1024                 1024                 files

Лимит 1024. В манифесте про ulimit ничего нет, значит он унаследован. Проверили на узле:

Bash
systemctl show containerd | grep -i limitnofile
# LimitNOFILE=1024

Дальше — разбивка:

Bash
kubectl exec -it payments-7f8-x2k -- sh -c \
  "ls -l /proc/1/fd | awk '{print \$11}' | sed 's/:\[.*//' | sort | uniq -c | sort -rn"
#    812 socket
#     94 /app/lib
#     41 /var/log
#     ...

812 сокетов при 1024 лимите. Нормально ли это? Посчитали по закону Литтла: 800 RPS × 60 мс = 48 одновременных входящих, пул к БД 30, пул к трём внешним API по 50 = 150, Kafka 6 брокеров × 2 = 12. Итого ожидалось ~250. Было 812.

Bash
kubectl exec -it payments-7f8-x2k -- sh -c "ss -tan | awk 'NR>1 {print \$1}' | sort | uniq -c"
#    468 ESTAB
#    301 TIME-WAIT
#     38 CLOSE-WAIT

301 в TIME_WAIT — это закрытые соединения, которые всё ещё занимают порт, но не занимают fd (TIME_WAIT живёт в ядре, у процесса дескриптора уже нет). А вот 468 ESTAB — вдвое больше расчётного.

Bash
ss -tanp state established | awk '{print $5}' | cut -d: -f1 | sort | uniq -c | sort -rn
#    220 10.20.44.19        <- внешний антифрод-API
#     31 10.20.3.44         <- postgres
#     ...

220 соединений к антифрод-API при настроенном пуле в 50.

Находка. В коде вызов антифрода делался через новый HttpClient на каждый запрос:

Java
// Было — катастрофа
public FraudVerdict check(Payment p) {
    var client = HttpClient.newBuilder()                     // новый клиент = новый пул
            .connectTimeout(Duration.ofSeconds(2))
            .build();
    ...
}

Каждый HttpClient в JDK несёт собственный пул соединений и собственный SelectorManager-поток. Пул настроить нельзя, а GC собирает клиента не сразу — соединения держатся, пока объект жив. Два независимых бага в одном месте: утечка соединений и утечка потоков.

Лечение.

  1. Немедленно: подняли LimitNOFILE на containerd-юните узлов до 1048576, перезапустили containerd (rolling по узлам).
  2. В коде — один HttpClient на приложение, синглтон-бин:
Java
@Bean
HttpClient httpClient() {
    return HttpClient.newBuilder()
            .version(HttpClient.Version.HTTP_2)
            .connectTimeout(Duration.ofSeconds(2))
            .executor(Executors.newVirtualThreadPerTaskExecutor())
            .build();
}
  1. Таймаут на каждый запрос (HttpRequest.timeout), иначе соединение может висеть вечно.

Профилактика.

  • Оповещение: process_files_open / process_files_max > 0.6 (warning) и > 0.8 (critical). Метрики Micrometer доступны из коробки.
  • Явный LimitNOFILE=1048576 в юнитах containerd/CRI-O, зафиксированный в конфигурации узлов (Ansible/Terraform), а не «поправили руками».
  • ArchUnit-правило или code review чеклист: HttpClient.newBuilder() / new RestTemplate() / OkHttpClient() не должны создаваться вне конфигурационных классов.
  • Проверка cat /proc/1/limits в smoke-тесте после деплоя на новый узел.

fluent-bit пишет 412 МБ/с. Оказалось: на соседнем поде включили debug-логирование, log-агент захлебнулся и начал агрессивно писать буфер на тот же локальный диск.

Находка. Три накладывающихся проблемы: (1) log-агент и данные приложения на одном диске без ограничения IOPS; (2) у узла локальный NVMe без io.max в cgroup; (3) само приложение делало fsync на каждый обработанный документ вместо пакета.

Лечение.

  1. Немедленно: вернули уровень логирования на соседнем сервисе, диск разгрузился за 40 секунд, приложение ожило само.
  2. Ограничили I/O log-агента через cgroup v2:
    Bash
    echo "259:0 wbps=104857600" > /sys/fs/cgroup/system.slice/fluent-bit.service/io.max
  3. В приложении заменили fsync на документ на групповой fsync раз в 200 документов или 100 мс.

Профилактика.

  • Оповещение по PSI: io.pressure some avg60 > 20 % — ловит насыщение диска до того, как всё встанет.
  • Оповещение на node_disk_io_time_weighted_seconds_total (avg queue) и на w_await, а не на %util.
  • Hung task в dmesg — отдельное критическое оповещение (kernel_hung_task).
  • Разнести логи и данные по разным устройствам либо ограничить io.max для системных сервисов.
  • В runbook первым пунктом при «приложение не отвечает, CPU низкий»: ps -eL -o stat | grep -c D.

9.3 RSS растёт без роста heap

Симптом. Сервис с -Xmx3g в контейнере с лимитом 4 ГБ. По метрикам JVM heap стабильно колеблется 1.2–2.4 ГБ, metaspace 280 МБ, GC работает нормально. Но container_memory_working_set_bytes линейно растёт со скоростью ~80 МБ в сутки, и на 12-й день под получает OOMKilled. Перезапуск — и цикл заново.

Проверено.

Bash
grep -E 'VmRSS|RssAnon|RssFile' /proc/1/status
# VmRSS:   3921844 kB
# RssAnon: 3798122 kB
# RssFile:  118204 kB

RSS 3.7 ГБ, из них анонимной 3.6 ГБ. Heap 2.4 максимум. Разрыв — 1.2 ГБ.

Bash

# (приложение запускалось с -XX:NativeMemoryTracking=summary)
Total: reserved=6182MB, committed=3102MB
-  Java Heap (reserved=3072MB, committed=2458MB)
-      Class (reserved=1082MB, committed=312MB)
-     Thread (reserved=218MB, committed=218MB)
-       Code (reserved=248MB, committed=98MB)
-         GC (reserved=182MB, committed=182MB)
-   Internal (reserved=12MB, committed=12MB)
-      Other (reserved=64MB, committed=64MB)

NMT насчитал 3.1 ГБ committed, RSS — 3.8 ГБ. Разрыв 700 МБ вне учёта JVM. Это либо нативная библиотека, либо распределитель памяти.

Bash
pmap -x 1 | awk '$2 == 65536' | wc -l
# 38

38 регионов ровно по 64 МБ. Сигнатура арен glibc.

Bash
nproc
# 32          <- видит 32 ядра хоста
cat /sys/fs/cgroup/cpu.max
# 200000 100000   <- реальный лимит 2 CPU

Лимит арен = 8 × 32 = 256, потому что glibc смотрит на sysconf(_SC_NPROCESSORS_ONLN), а не на cgroup. Приложение с 180 потоками постепенно разбрелось по 38 аренам, каждая накопила фрагментацию.

Находка. Не утечка, а фрагментация арен glibc. Ускорителем послужил конкретный код: обработка входящих сообщений использовала java.util.zip.Inflater на каждое сообщение, а Inflater выделяет нативно через zlib → malloc. При 500 сообщений в секунду это сотни тысяч нативных выделений памяти разного размера в час.

Лечение.

  1. MALLOC_ARENA_MAX=2 в манифесте:
    YAML
    env:
  - name: MALLOC_ARENA_MAX
    value: "2"
    RSS через сутки: 2.9 ГБ вместо 3.8. Рост прекратился.
  2. Вторым шагом повторно использовали Inflater через пул с обязательным end():
    Java
    // Inflater/Deflater держат нативную память; без end() она освобождается
// только при финализации/Cleaner — то есть недетерминированно.
Inflater inf = inflaterPool.borrow();
try {
    inf.setInput(data);
    ...
} finally {
    inf.reset();
    inflaterPool.release(inf);   // при выводе из пула обязательно inf.end()
}
  3. Явно задали -XX:ActiveProcessorCount=2, чтобы и JVM, и производные пулы соответствовали лимиту.

Профилактика.

  • MALLOC_ARENA_MAX в базовом образе или в шаблоне Deployment по умолчанию (значение 2–4).
  • Оповещение на отношение container_memory_working_set_bytes / jvm_memory_committed_bytes{area="heap"} — если больше 1.8 и растёт, есть проблема вне heap.
  • -XX:NativeMemoryTracking=summary включён всегда в проде: накладные расходы 5–10 % по памяти на учётные структуры и единицы процентов CPU — приемлемая цена за возможность диагностики.
  • Правило в code review: любой класс, у которого есть close()/end()/free() и нативная часть (Inflater, Deflater, MappedByteBuffer, ZipFile, JNI-обёртки), должен освобождаться детерминированно.

9.4 Тормоза из-за DNS: ndots и отсутствие кеша

Симптом. После переезда сервиса из VM в Kubernetes p99 latency выросла с 80 мс до 420 мс. Профилирование приложения ничего не показывает: async-profiler говорит, что CPU почти не занят, все потоки ждут. Метрики внешнего API говорят, что он отвечает за 30 мс.

Проверено. Разложили запрос по фазам прямо из пода:

Bash
kubectl exec -it svc-x -- curl -sS -o /dev/null -w \
  'dns=%{time_namelookup} conn=%{time_connect} tls=%{time_appconnect} ttfb=%{time_starttransfer} total=%{time_total}\n' \
  https://api.vendor.com/v1/rates
dns=0.312 conn=0.318 tls=0.341 ttfb=0.374 total=0.375

312 мс на DNS. Всё остальное быстро.

Bash
kubectl exec -it svc-x -- cat /etc/resolv.conf
# nameserver 10.96.0.10
# search prod.svc.cluster.local svc.cluster.local cluster.local
# options ndots:5

ndots:5, имя api.vendor.com имеет 2 точки → перебор search-доменов.

Bash
kubectl exec -it svc-x -- sh -c 'time getent hosts api.vendor.com'
# real 0m0.308s

Снял дамп с узла в namespace пода:

Bash

Восемь запросов на одно разрешение имени: A и AAAA для каждого из четырёх вариантов имени. Плюс CoreDNS под нагрузкой отвечал не за 1 мс, а за 30–40 мс, потому что получал в 8 раз больше запросов, чем предполагал sizing.

И главное — JVM не кешировала: приложение запускалось без настройки networkaddress.cache.ttl, а негативные ответы (NXDOMAIN для трёх search-вариантов) кешировались только 10 секунд и в кеш JVM вообще не попадали, потому что getaddrinfo возвращал успех на четвёртой попытке.

Находка. Три множителя: ndots:5 × IPv6 × отсутствие кеша на всех уровнях.

Лечение.

  1. dnsConfig в поде — снизить ndots и ускорить отказ:
    YAML
    spec:
  dnsConfig:
    options:
      - name: ndots
        value: "2"
      - name: timeout
        value: "1"
      - name: attempts
        value: "2"
      - name: single-request-reopen
  2. Кеш в JVM:
    properties
    networkaddress.cache.ttl=30
networkaddress.cache.negative.ttl=2
  3. Развернули NodeLocal DNSCache (DaemonSet) — разрешение внутрикластерных имён стало локальным, нагрузка на CoreDNS упала в 6 раз.
  4. Для внешних имён с редко меняющимися IP — повысили TTL в JVM до 60 с.

Итог: p99 вернулась к 95 мс.

Профилактика.

  • Метрика coredns_dns_request_count_total и coredns_dns_request_duration_seconds с оповещением на p99 > 20 мс.
  • В шаблон Deployment — dnsConfig с ndots:2 по умолчанию для сервисов, которые ходят во внешний мир.
  • networkaddress.cache.ttl задан явно в базовом образе.
  • В чеклист «первые 5 минут после деплоя» (глава 51) — разложить один запрос через curl -w и убедиться, что time_namelookup < 5 мс.

9.5 CLOSE_WAIT растёт и упирается в лимит

Симптом. Раз в 8–10 дней сервис интеграции падает с Too many open files. Между падениями — идеальная работа. Утечки памяти нет, потоков нет, число запросов стабильно.

Проверено. Поставили наблюдение на неделю:

Bash
while true; do
  printf '%s fd=%s estab=%s cw=%s\n' "$(date +%FT%T)" \
    "$(ls /proc/1/fd | wc -l)" \
    "$(ss -tan state established | wc -l)" \
    "$(ss -tan state close-wait | wc -l)"
  sleep 60
done >> /tmp/conn.log

Через сутки:

2026-09-14T09:00:11 fd=612  estab=104 cw=381
2026-09-15T09:00:11 fd=1024 estab=101 cw=798

ESTAB стабилен, CLOSE_WAIT растёт ровно на ~420 в сутки. Это линейная утечка.

Bash
ss -tan state close-wait | awk 'NR>1 {print $5}' | sort | uniq -c | sort -rn | head -3
#    798 10.30.7.12:8443

Все к одному адресу — SOAP-шлюз партнёра. Посчитали: партнёрский шлюз вызывается примерно 420 раз в сутки — по одной утечке на вызов. Значит течёт каждый вызов.

Находка. Код вызова:

Java
// Было
HttpURLConnection conn = (HttpURLConnection) url.openConnection();
conn.setRequestMethod("POST");
conn.setDoOutput(true);
try (OutputStream os = conn.getOutputStream()) {
    os.write(soapEnvelope);
}
int code = conn.getResponseCode();
if (code == 200) {
    try (InputStream in = conn.getInputStream()) {
        return parse(in);
    }
}
throw new IntegrationException("HTTP " + code);   // <- тело ошибки не прочитано!

Шлюз партнёра возвращал HTTP 500 с SOAP Fault примерно в 100 % случаев в некоторых сценариях, и на этой ветке getErrorStream() не читался и не закрывался. HttpURLConnection держит соединение в своём внутреннем keep-alive-кеше до тех пор, пока тело не вычитано целиком. Партнёрский сервер по своему idle timeout (300 с) присылал FIN, а приложение никогда не вызывало close() — соединение оставалось в CLOSE_WAIT навсегда.

Ещё одна деталь, объясняющая «раз в 8–10 дней»: релизы выходили раз в неделю, и перезапуск обнулял счётчик. Когда был двухнедельный код-фриз, сервис упал.

Лечение.

Java
// Стало: гарантированное потребление тела на всех ветках
HttpURLConnection conn = (HttpURLConnection) url.openConnection();
conn.setConnectTimeout(3000);
conn.setReadTimeout(15000);
try {
    ...
    int code = conn.getResponseCode();
    InputStream body = (code >= 400) ? conn.getErrorStream() : conn.getInputStream();
    byte[] payload = (body == null) ? new byte[0] : body.readAllBytes();
    if (body != null) body.close();
    if (code != 200) throw new IntegrationException("HTTP " + code + ": " + new String(payload));
    return parse(payload);
} finally {
    conn.disconnect();
}

Правильнее — вообще уйти с HttpURLConnection на java.net.http.HttpClient или RestClient (RestTemplate в Spring Framework 7.0 ещё не помечен устаревшим, но в 7.1 получает @Deprecated(forRemoval = true), а удалят его в 8.0), где потребление тела встроено в API:

Java
// Spring Framework 7: RestClient — тело читается всегда, даже при ошибке
String body = restClient.post()
        .uri("/soap")
        .body(envelope)
        .exchange((req, res) -> new String(res.getBody().readAllBytes()));

Профилактика.

  • Оповещение на абсолютное число CLOSE_WAIT соединений (экспортер node_netstat или собственная метрика): > 100 — warning.
  • Оповещение на тренд process_files_open: линейный рост за 24 часа — сигнал утечки, даже если до лимита далеко.
  • Правило: maxIdleTime клиента строго меньше idle timeout сервера; для внешних партнёров — узнавать и документировать.
  • Code review: любой HTTP-вызов должен потреблять тело на всех ветках, включая ошибочные.
  • Нагрузочный тест с эмуляцией 500-х ответов — WireMock со сценарием ошибок, проверка fd до и после.

9.6 CPU throttling при нормальном среднем CPU

Симптом. Сервис расчёта лимитов. Дашборд: CPU usage 45 % от лимита, память 60 %, GC-паузы < 30 мс, БД отвечает за 4 мс. При этом p99 latency — 680 мс при p50 в 22 мс. Ни одна метрика приложения не объясняет разрыв.

Проверено. Разложили запрос — всё время внутри приложения. Профилировали — async-profiler в режиме wall-clock показал, что потоки просто «не выполняются», без явного блокирования.

Bash
kubectl exec -it limits-6b4-qz9 -- cat /sys/fs/cgroup/cpu.stat
usage_usec 98217384012
user_usec 81023844712
system_usec 17193539300
nr_periods 1204812
nr_throttled 291842
throttled_usec 18293847112

291842 / 1204812 = 24 % окон с throttling. Средняя длительность заморозки: 18293847112 / 291842 ≈ 62 700 мкс = 62.7 мс.

Запустили наблюдение в динамике (скрипт из 3.3):

11:04:02 periods=10   throttled=3    (30%) stalled=188ms
11:04:03 periods=10   throttled=2    (20%) stalled=124ms
11:04:04 periods=10   throttled=4    (40%) stalled=251ms

Находка.

YAML
resources:
  requests: { cpu: "500m", memory: "2Gi" }
  limits:   { cpu: "1", memory: "3Gi" }

Лимит 1 CPU. При этом:

Bash
kubectl exec -it limits-6b4-qz9 -- jcmd 1 VM.flags -all | grep -E 'ParallelGCThreads|ActiveProcessorCount|CICompilerCount'
# uintx ParallelGCThreads = 1
# intx ActiveProcessorCount = -1

JVM корректно увидела 1 CPU. Проблема была не в JVM, а в архитектуре обработки: запрос выполнял 6 параллельных обращений к кешу и правилам через CompletableFuture.allOf на ForkJoinPool.commonPool. При лимите в 1 CPU параллелизм commonPool = 0 (то есть он выполняет задачи в вызывающем потоке), но 200 потоков Tomcat всё равно одновременно требовали CPU. За 5–10 мс реального времени 200 потоков выжигали 100 мс квоты, и все замирали до конца окна.

Лечение.

  1. Подняли limits.cpu до 3 при requests.cpu: 1 — доля окон с throttling упала до 0.4 %, p99 стала 41 мс.
  2. Сократили server.tomcat.threads.max со 200 до 40 — при 1–3 CPU держать 200 потоков бессмысленно, они только усиливают выжигание квоты и context switches (cs упал с 140 тыс./с до 22 тыс./с).
  3. Для критичного сервиса обсудили снятие CPU-лимита вовсе, оставив request как гарантию.

Профилактика.

  • Обязательная метрика и оповещение: rate(container_cpu_cfs_throttled_periods_total[5m]) / rate(container_cpu_cfs_periods_total[5m]) > 0.02. Эта метрика есть в cAdvisor из коробки и почти всегда отсутствует на дашбордах — добавь её сегодня.
  • Правило sizing: CPU limit ≥ 2 для любого сервиса с SLA по latency; дробные лимиты (500m) допустимы только для фоновых задач.
  • Правило: размер пула HTTP-потоков соотносить с CPU-лимитом, а не оставлять значение по умолчанию в 200.
  • В нагрузочном тесте сравнивать p99 в контейнере с лимитом и без — расхождение больше 30 % означает throttling.

💡 На интервью. Этот инцидент — отличный ответ на «расскажи про сложный баг». Ключевая мысль: средняя утилизация CPU не отражает throttling, потому что квота выдаётся окнами по 100 мс, и приложение может простаивать 60 мс из каждых 100, имея «45 % средней загрузки». Доказательство — nr_throttled и throttled_usec в cpu.stat.

10.3 Разбор логов с помощью awk

Это то, ради чего стоит выучить awk. Возьмём типичный access-лог nginx:

10.20.1.5 - - [19/Sep/2026:03:14:22 +0000] "POST /api/v1/payments HTTP/1.1" 200 1842 0.342 "-" "okhttp/4.12"
$1                                          $6    $7                  $8   $9  $10  $11

Здесь $9 — код ответа, $11 — время обработки ($request_time).

Bash
# 1. Распределение по кодам ответа
awk '{print $9}' access.log | sort | uniq -c | sort -rn
#  184291 200
#    4812 404
#     891 500
#     112 502

# 2. Топ-10 самых медленных запросов
awk '{print $11, $6, $7}' access.log | sort -rn | head -10
# 12.041 "POST /api/v1/reports
#  8.912 "POST /api/v1/reports
#  ...

# 3. Средняя и максимальная latency по эндпоинту
awk '{ep=$7; sum[ep]+=$11; n[ep]++; if ($11>max[ep]) max[ep]=$11}
     END {for (e in n) printf "%8.3f avg  %8.3f max  %7d n  %s\n", sum[e]/n[e], max[e], n[e], e}' \
  access.log | sort -rn | head -20

# 4. Перцентиль по колонке (p95 времени ответа)
awk '{print $11}' access.log | sort -n |
  awk '{a[NR]=$1} END {printf "p50=%.3f p95=%.3f p99=%.3f max=%.3f n=%d\n",
        a[int(NR*0.50)], a[int(NR*0.95)], a[int(NR*0.99)], a[NR], NR}'

# 5. RPS по минутам — найти пик
awk '{split($4, t, ":"); print t[2]":"t[3]}' access.log | uniq -c |
  awk '{printf "%s %d rps\n", $2, $1/60}'

# 6. Только запросы медленнее секунды, сгруппированные по эндпоинту
awk '$11 > 1.0 {print $7}' access.log | sort | uniq -c | sort -rn | head

# 7. Доля ошибок по эндпоинту
awk '{tot[$7]++; if ($9 >= 500) err[$7]++}
     END {for (e in tot) if (err[e]) printf "%6.2f%%  %5d/%-7d  %s\n",
          err[e]*100/tot[e], err[e], tot[e], e}' access.log | sort -rn | head

# 8. Топ клиентов по числу запросов (поиск источника шторма)
awk '{print $1}' access.log | sort | uniq -c | sort -rn | head -10

# 9. Байты, переданные за период
awk '{s+=$10} END {printf "%.2f GB\n", s/1024/1024/1024}' access.log

# 10. Гистограмма latency (логарифмические бакеты)

10.7 Строгий режим set -euo pipefail

Скрипт по умолчанию в POSIX shell:

  • продолжает выполнение после ошибки команды;
  • считает неопределённую переменную пустой строкой;
  • возвращает код возврата последней команды конвейера.

Каждое из этих поведений порождает незаметные катастрофы.

Bash
#!/usr/bin/env bash
set -euo pipefail
IFS=$'\n\t'
Флаг Действие Предотвращает
-e (errexit) Прервать скрипт при ненулевом коде возврата cd /nonexistent; rm -rf * — классика удаления не того каталога
-u (nounset) Ошибка при использовании неустановленной переменной rm -rf "$PREFIX/data" при пустом PREFIX = rm -rf /data
-o pipefail Код возврата конвейера = код первой упавшей команды curl bad-url | jq . вернёт 0, потому что jq отработал
IFS=$'\n\t' Убрать пробел из разделителей полей Разваливание путей с пробелами при word splitting

Демонстрация, почему pipefail критичен:

Bash
$ curl -sf https://nonexistent.invalid/data | jq -r '.value'; echo "exit=$?"
exit=0          # !!! скрипт считает, что всё хорошо

$ set -o pipefail
$ curl -sf https://nonexistent.invalid/data | jq -r '.value'; echo "exit=$?"
exit=6

Без pipefail конвейер из curl в CI выглядит успешным, деплой продолжается с пустым конфигом.

Оговорки к -e, которые надо знать:

Bash
# -e не срабатывает для команды в условии — это by design
if ! grep -q 'pattern' file; then echo "not found"; fi

# Явно разрешить неуспех
some_command || true

# При -u дать значение по умолчанию
: "${TIMEOUT:=30}"
echo "${OPTIONAL_VAR:-default}"

# Проверить обязательную переменную с понятной ошибкой
: "${DB_URL:?DB_URL must be set}"

# Ловушка на выход — гарантированная очистка
tmp=$(mktemp -d)
trap 'rm -rf "$tmp"' EXIT

Проверять скрипты статически:

Bash

shellcheck находит отсутствие кавычек, неправильные сравнения, useless use of cat и десятки классов реальных ошибок. В CI для любого .sh в репозитории — обязателен.

10.8 Переход со скрипта на Python

Признаки, что shell-скрипт пора переписать:

  1. Больше 100 строк или больше двух уровней вложенности функций.
  2. Нужны структуры данных — ассоциативные массивы глубже одного уровня, списки списков.
  3. Разбор JSON/XML сложнее пары jq-выражений. jq — прекрасный фильтр и плохой язык программирования.
  4. Арифметика с плавающей точкой. В bash её нет; bc и awk в качестве калькулятора — признак проблемы.
  5. Нужны повторы, таймауты, параллелизм с ограничением — всё это в shell пишется, но получается хрупко.
  6. Скрипт пойдёт в прод и будет жить годами. Тогда ему нужны тесты, а тестировать bash больно.

Граница проста: однократная задача в терминале или в инциденте — shell; то, что будет жить в репозитории и меняться — Python (или Go, если нужен один бинарник без зависимостей).

Полезная промежуточная форма — однострочник на Python прямо из shell:

Bash

python3 -c "

v = sorted(float(x) for x in sys.stdin)
print(f'n={len(v)} p50={s.median(v):.3f} p95={v[int(len(v)*0.95)]:.3f} p99={v[int(len(v)*0.99)]:.3f}')

11. Ошибки и антипаттерны

  1. Читать ulimit -n в своей shell и делать вывод о лимите сервиса. Симптом: «у нас лимит миллион, а сервис падает с Too many open files». Причина: сервис запущен systemd/containerd со своим LimitNOFILE. Лечение: всегда cat /proc/<pid>/limits.

  2. Считать, что free без кеша — это «свободная память». Симптом: паника «памяти нет» при free: 200Mi. Причина: page cache. Лечение: смотреть колонку available, а в контейнере — container_memory_working_set_bytes, а не memory.current.

  3. Приравнивать RSS к heap. Симптом: -Xmx4g, лимит 4.5 Gi, регулярный OOMKilled. Причина: metaspace, code cache, стеки, GC-структуры, direct buffers, арены glibc — суммарно 30–60 % сверх heap. Лечение: считать non-heap явно, ставить -XX:MaxDirectMemorySize, -XX:MaxMetaspaceSize, держать запас 25–40 %.

  4. Оставлять swap включённым на узле с JVM. Симптом: GC-пауза на 90 секунд, liveness убивает под. Причина: GC трогает выгруженные страницы. Лечение: vm.swappiness=1 или swapoff, оповещение на VmSwap > 0.

  5. THP enabled=always + defrag=always. Симптом: необъяснимые всплески latency в 99.9-перцентиле. Причина: синхронная дефрагментация в момент выделения памяти. Лечение: madvise + -XX:+UseTransparentHugePages + -XX:+AlwaysPreTouch.

  6. Путать OutOfMemoryError, OOM killer и OOMKilled. Симптом: ищут утечку в heap dump, а его нет, потому что процесс убит SIGKILL. Лечение: таблица в разделе 2.6; смотреть dmesg -T | grep -i oom и memory.events.

  7. Оставлять MALLOC_ARENA_MAX по умолчанию в контейнере. Симптом: RSS растёт на десятки МБ в сутки при стабильном heap. Причина: glibc считает арены от числа ядер хоста, а не от квоты. Лечение: MALLOC_ARENA_MAX=2..4.

  8. Считать размер пулов от nproc. Симптом: 3200 потоков в контейнере с лимитом 2 CPU. Причина: nproc показывает ядра хоста. Лечение: считать от cpu.max или от Runtime.availableProcessors().

  9. Дробный CPU-лимит (500m) на latency-чувствительном сервисе. Симптом: p99 в 20 раз больше p50 при «45 % CPU». Причина: CFS-throttling окнами по 100 мс. Лечение: лимит ≥ 2 CPU или снятие лимита; оповещение на nr_throttled.

  10. Не читать stdout/stderr дочернего процесса из Runtime.exec. Симптом: waitFor() висит вечно. Причина: буфер пайпа 64 КБ переполнен, ребёнок заблокирован на write(). Лечение: redirectOutput, redirectErrorStream(true) или отдельный поток-читатель.

  11. Вызывать System.exit() из shutdown hook. Симптом: процесс не завершается, приходит SIGKILL через 30 с. Причина: deadlock — exit() ждёт хуки, ты в хуке. Лечение: Runtime.halt() если очень нужно, а лучше просто вернуться из хука.

  12. Рассчитывать на shutdown hook как на гарантию. SIGKILL, OOM killer, падение узла его не вызывают. Критичное состояние надо фиксировать сразу, а не «дописывать при выходе».

  13. Не читать тело HTTP-ответа на ветке ошибки. Симптом: рост CLOSE_WAIT, через недели — Too many open files. Лечение: потреблять тело всегда, включая getErrorStream().

  14. maxLifetime пула больше idle timeout сервера или firewall. Симптом: редкие запросы падают по таймауту через 15 минут или Connection reset by peer. Лечение: idle клиента < idle сервера < idle сетевого оборудования; TCP keep-alive с TCP_KEEPIDLE=60.

  15. Надеяться на TCP keep-alive «из коробки». SO_KEEPALIVE по умолчанию выключен, а системный tcp_keepalive_time — 7200 секунд. Лечение: включать явно и задавать TCP_KEEPIDLE через ExtendedSocketOptions.

  16. Советовать tcp_tw_recycle. Параметр удалён в ядре 4.12 и ломал клиентов за NAT. Использовать tcp_tw_reuse (для исходящих) и расширение ip_local_port_range.

  17. Тюнить tcp_fin_timeout, чтобы «уменьшить TIME_WAIT». tcp_fin_timeout относится к FIN_WAIT_2. Длительность TIME_WAIT в Linux захардкожена — 60 секунд.

  18. Оставлять accept-count по умолчанию (100 у Tomcat). Симптом: при всплеске часть запросов занимает ровно 1 или 3 секунды. Причина: переполнение accept-очереди, потеря финального ACK, повторная передача. Диагностика: ss -lnt (Recv-Q на LISTEN) и nstat | grep -i overflow.

  19. Вручную задавать SO_RCVBUF/SO_SNDBUF. Это отключает автотюнинг («the kernel doubles this value... when it is set using setsockopt», socket(7)) и ставит жёсткий потолок пропускной способности на длинных каналах. Лечение: не трогать, если не измерил.

  20. Игнорировать ndots:5 в Kubernetes для внешних имён. Симптом: 300 мс на разрешение имени в DNS. Лечение: dnsConfig с ndots:2, trailing dot в FQDN, NodeLocal DNSCache.

  21. Не настраивать networkaddress.cache.ttl в JVM. Симптом: после failover БД приложение продолжает ходить на мёртвый IP. Лечение: networkaddress.cache.ttl=30, negative.ttl=2, задавать до первого разрешения имени.

  22. Проверять DNS через dig и делать вывод о приложении. dig не использует nsswitch.conf, /etc/hosts и search-домены как getaddrinfo. Проверять через getent hosts.

  23. Запускать strace на проде без -c и без timeout. Замедление до 100×. Лечение: timeout 15 strace -f -c -p PID, а лучше eBPF.

  24. Ориентироваться на %util в iostat для NVMe. У параллельных устройств 100 % %util не означает насыщения. Смотреть await и aqu-sz.

  25. Использовать %CPU из top для Java без -H. Суммарный процент по процессу не показывает, какой поток горит. top -H -p <pid> + перевод TID в hex + поиск в thread dump.

  26. Писать логи в файл внутри контейнера без volume. overlayfs с CoW, неограниченный рост, потеря при рестарте. Лечение: stdout + централизованный сбор (глава 51).

  27. Забыть totalSizeCap в Logback rolling policy. Симптом: диск заполнен за час при шторме исключений.

  28. Не ставить set -euo pipefail в скриптах. Скрипт «успешно» отработал с пустыми данными, и деплой поехал с битым конфигом.

12.1 Чеклист «сервис не отвечает»

Расширение по методу USE (Brendan Gregg): для каждого ресурса — utilization, saturation, errors. CPU: mpstat -P ALL / runqlat / (нет). Память: free / si-so, PSI / oom_kill. Диск: iostat %util / await, aqu-sz / dmesg. Сеть: ip -s link (байты) / ss -tani retrans, дропы очередей / ip -s link errors.

13. Вопросы на интервью

1. Что такое load average и как его правильно интерпретировать?

Это три экспоненциально сглаженных оценки числа задач, которые находились в состоянии «готов выполняться» или «непрерываемый сон» за 1, 5 и 15 минут. Ключевое отличие Linux от классических Unix — включение задач в TASK_UNINTERRUPTIBLE, то есть ждущих диска. Поэтому LA = 40 при 95 % idle CPU означает не нехватку процессора, а залипшее хранилище. Сравнивать LA с числом ядер можно только очень грубо, потому что это не мгновенное значение; для реальной диагностики я смотрю vmstat 1 (колонки r и b), mpstat -P ALL и PSI в /proc/pressure/.

2. Чем RSS отличается от heap? Почему RSS больше -Xmx?

Heap — область, которой управляет GC, ограничена -Xmx. RSS — вся физическая память процесса. Сверх heap там metaspace, code cache, стеки потоков, структуры GC (у G1 remembered sets и карты — несколько процентов от heap), direct byte buffers, символы, нативные выделения памяти библиотек и арены glibc malloc. Нормальный коэффициент RSS/Xmx — 1.3–1.6; если больше двух, я иду смотреть NMT и smaps_rollup, а разрыв между RSS и NMT-committed означает утечку вне JVM.

3. Что такое PSS и когда он нужен вместо RSS?

RSS считает разделяемые страницы целиком у каждого процесса, поэтому сумма RSS всех процессов больше физической памяти. PSS делит shared-страницы на число разделяющих процессов, и сумма PSS равна реально занятой памяти. Он нужен, когда на машине много процессов с общими библиотеками или общей tmpfs. Читается из /proc/<pid>/smaps_rollup, а не из ps.

4. Что означает состояние D и почему процесс в нём не убивается kill -9?

D — TASK_UNINTERRUPTIBLE: задача ждёт завершения операции в ядре, которую нельзя корректно прервать сигналом. Сигнал доставляется и помечается как pending, но обработается только после выхода из D. В бэкенд-контексте это почти всегда блочный I/O: медленный или залипший диск, NFS, мёртвый FUSE. Диагностика — ps -eL -o stat, /proc/<pid>/task/<tid>/stack, iostat -xz и dmesg на предмет blocked for more than 120 seconds.

5. Чем SIGTERM отличается от SIGKILL?

SIGTERM (15) — перехватываемый сигнал: JVM запускает shutdown hooks, Spring закрывает контекст, приложение успевает доработать текущие запросы. SIGKILL (9) перехватить, заблокировать или проигнорировать нельзя — ядро снимает процесс немедленно, хуки не выполняются, данные в буферах теряются. В Kubernetes сначала приходит SIGTERM, и только через terminationGracePeriodSeconds (значение по умолчанию 30 с) — SIGKILL. Поэтому graceful shutdown должен укладываться в этот бюджет, а preStop нужен, чтобы балансировщики успели перестать слать трафик.

6. Как получить thread dump, если jstack не работает?

kill -3 <pid> — HotSpot по SIGQUIT печатает полный thread dump в stdout процесса и продолжает работу. В Kubernetes он попадёт в kubectl logs, в systemd — в journal. Это работает в distroless-образах без JDK-тулов и когда attach-механизм сломан. Снимать надо три дампа с интервалом 5–10 секунд — один дамп не показывает, застрял поток или просто был занят в этот момент.

7. Что такое TIME_WAIT и когда он становится проблемой?

Состояние стороны, закрывшей соединение первой; длится 2×MSL, в Linux это 60 секунд и не настраивается. Нужно, чтобы дозревшие сегменты старого соединения не попали в новое с той же четвёркой и чтобы можно было переотправить последний ACK. Проблема возникает на клиенте, который часто создаёт новые соединения: эфемерных портов около 28 тысяч, значит потолок — примерно 470 новых соединений в секунду к одному адресу. Лечение — пул и keep-alive; из тюнинга допустимы tcp_tw_reuse=1 и расширение ip_local_port_range, а tcp_tw_recycle использовать нельзя, он удалён в ядре 4.12.

8. Что такое CLOSE_WAIT и о чём он говорит?

Это состояние пассивной стороны: пир прислал FIN, ядро его подтвердило, и теперь оно ждёт, когда приложение вызовет close(). У этого состояния нет таймера, поэтому накопление CLOSE_WAIT — это гарантированная утечка дескрипторов и почти всегда баг приложения: не закрыт HTTP-ответ, не обработан read() == -1 в NIO, не закрыт сокет в ветке исключения. Диагностика: ss -tanp state close-wait, группировка по удалённому адресу — она сразу указывает на конкретного клиента в коде.

9. Как найти утечку файловых дескрипторов?

Сначала подтвердить факт: ls /proc/<pid>/fd | wc -l против grep 'open files' /proc/<pid>/limits, и посмотреть динамику — линейный рост означает утечку. Дальше разбивка по типам: ls -l /proc/<pid>/fd | awk '{print $11}' | sort | uniq -c | sort -rn. Если течёт сокетами — ss -tanp с группировкой по состоянию и адресу; CLOSE_WAIT укажет на незакрытые ответы. В приложении обязательно должна быть метрика process.files.open / process.files.max с оповещением на 0.6 и на растущий тренд.

10. Почему на диске есть место, а запись падает с No space left on device?

Три типовых причины. Первая — кончились inodes: df -i покажет IUse% 100 % при свободных гигабайтах; бывает при миллионах мелких файлов. Вторая — файл удалён, но открыт процессом: место не освобождается до закрытия, находится через lsof +L1, лечится : > /proc/<pid>/fd/<n> или рестартом. Третья — квота (quota) или резерв для root (5 % по умолчанию в ext4, видно как расхождение между Avail и Size−Used).

11. Как посмотреть, что процесс делает прямо сейчас?

По возрастанию инвазивности: top -H -p <pid> покажет, какой поток горит и в каком он состоянии; /proc/<pid>/task/<tid>/wchan и stack покажут, что поток ждёт в ядре; kill -3 или jcmd Thread.print даст Java-стек; strace -f -c -p <pid> под timeout на 10 секунд покажет распределение системных вызовов. Если нужен профиль без таких накладных расходов — async-profiler или eBPF (offcputime, profile). Важный момент: поток в D-состоянии в thread dump выглядит как RUNNABLE, поэтому чистый дамп не означает, что всё хорошо.

12. Как доказать, что приложение страдает от CPU throttling?

Прочитать /sys/fs/cgroup/cpu.stat и посчитать nr_throttled / nr_periods — долю окон, в которых контейнер был заморожен, и throttled_usec / nr_throttled — среднюю длительность заморозки. Больше 2 % окон уже бьёт по хвостам latency. Ключевая мысль: средняя утилизация CPU этого не показывает, потому что квота выдаётся окнами по 100 мс, и приложение может простаивать 60 мс из каждых 100 при «45 % средней загрузки». В Prometheus это container_cpu_cfs_throttled_periods_total / container_cpu_cfs_periods_total.

13. Как разложить медленный HTTP-запрос по фазам?

curl -w с форматом, выводящим time_namelookup, time_connect, time_appconnect, time_starttransfer, time_total. Разности дают DNS, TCP handshake, TLS handshake, TTFB (обработка на сервере) и передачу тела. Дальше: большой DNS — смотреть ndots, кеш и распознаватель; time_connect много больше RTT — accept-очередь или потери SYN; большой TLS — цепочка сертификатов или CPU; большой TTFB — это уже приложение, и дальше идут профилировщик, GC-логи и cpu.stat.

14. Чем отличаются OutOfMemoryError, OOM killer и OOMKilled?

OutOfMemoryError бросает сама JVM, когда не может выделить в управляемой области — это Java-исключение со трассировкой стека, есть heap dump, хуки выполняются. OOM killer — механизм ядра при глобальной нехватке памяти хоста: процесс получает SIGKILL, в логах приложения обрыв, запись есть только в dmesg. OOMKilled — то же самое, но триггер — превышение memory.max cgroup; в Kubernetes это exitCode: 137, и подтверждается счётчиком oom_kill в memory.events. В двух последних случаях искать утечку в heap dump бессмысленно — надо смотреть non-heap и native.

15. Что такое backlog и как увидеть переполнение accept-очереди?

Очередей две: SYN queue (полуоткрытые, лимит tcp_max_syn_backlog) и accept queue (установленные, ждущие accept(), лимит min(backlog, somaxconn)). Переполнение accept-очереди видно в ss -lnt: для LISTEN-сокетов Recv-Q — текущее число ожидающих, Send-Q — максимум. Плюс счётчик «listen queue of a socket overflowed» в netstat -s. Симптом со стороны клиента — запросы, занимающие ровно 1 или 3 секунды: сервер без уведомления выбросил финальный ACK, и сработала повторная передача SYN+ACK.

16. В чём разница между TCP keep-alive и HTTP keep-alive?

TCP keep-alive — механизм ядра: периодические пустые пробы, чтобы понять, жив ли пир, и не дать NAT/firewall выбросить запись о соединении. По умолчанию он выключен на сокете, а системный tcp_keepalive_time — 7200 секунд, что бесполезно при idle timeout балансировщиков в 60–350 секунд. HTTP keep-alive — прикладной механизм: не закрывать TCP-соединение после ответа и повторно использовать его, что экономит RTT и TLS-handshake. Это независимые вещи, и в проде нужны обе: HTTP keep-alive с пулом плюс TCP keep-alive с TCP_KEEPIDLE порядка 60 секунд.

17. Откуда берётся стабильная задержка в 40 мс?

Это взаимодействие алгоритма Нейгла и delayed ACK. Nagle придерживает маленький сегмент, пока есть неподтверждённые данные; получатель откладывает ACK до 40 мс, надеясь приклеить его к ответным данным. Возникает патовая ситуация, которая разрешается по таймеру delayed ACK. Лечение — TCP_NODELAY (в Netty, Tomcat и Jetty он включён по умолчанию, в голых JDK-сокетах — нет) или, что правильнее, собирать сообщение в один буфер и отправлять одним write().

18. Почему новое TCP-соединение дорого?

Handshake — один RTT, TLS 1.3 — ещё один (TLS 1.2 — два). При RTT 20 мс это 40–60 мс до отправки первого байта запроса. Плюс slow start: начальное окно около 14 КБ, ответ на 100 КБ потребует ещё несколько RTT. Плюс порт уходит в TIME_WAIT на 60 секунд после закрытия, что ограничивает частоту создания соединений. Отсюда обязательность пулов и keep-alive; размер пула я считаю по закону Литтла как RPS × latency, а не «побольше».

19. Что произойдёт, если не задать connect timeout?

Поток встанет на время, которое определяется net.ipv4.tcp_syn_retries — по умолчанию 6 попыток с экспоненциальным backoff, то есть примерно 127 секунд. При сетевом разделении или недоступном хосте это означает, что весь пул потоков выест себя за пару минут, и сервис перестанет отвечать целиком — каскадный отказ. Поэтому connect timeout 1–3 секунды обязателен на каждом клиенте, вместе с read timeout и таймаутом получения соединения из пула.

20. Как JVM кеширует DNS и почему это опасно?

InetAddress держит статический кеш процесса, управляемый свойствами безопасности networkaddress.cache.ttl (успешные разрешения имён, -1 = вечно, значение по умолчанию implementation-specific) и networkaddress.cache.negative.ttl (значение по умолчанию 10 секунд). Опасность в том, что при вечном или длинном кеше приложение продолжает ходить на старый IP после failover БД или переезда сервиса, пока его не перезапустят. Я всегда задаю явно: ttl=30, negative.ttl=2, и делаю это до первого разрешения имени, потому что значение читается один раз.

21. Почему DNS в Kubernetes «тормозит»?

Из-за options ndots:5 в /etc/resolv.conf пода: имена с числом точек меньше пяти сначала перебираются по всем search-доменам. Для api.vendor.com это четыре варианта, а с включённым IPv6 — восемь запросов (A и AAAA на каждый), из которых шесть-семь вернут NXDOMAIN. Лечение: dnsConfig с ndots:2, FQDN с точкой в конце, NodeLocal DNSCache и кеш в JVM. Проверять надо через getent hosts, а не dig, потому что dig не использует nsswitch и search-домены.

22. Что такое cgroups v2 и что из них видит JVM?

cgroup v2 — единая иерархия контроллеров с файлами memory.max, memory.current, cpu.max, cpu.stat, pids.max. JVM с -XX:+UseContainerSupport (включён по умолчанию) читает лимит памяти и вычисляет heap по MaxRAMPercentage, а число процессоров — как ceil(quota/period) из cpu.max. Важно, что nproc, free и /proc/cpuinfo внутри контейнера показывают характеристики хоста, поэтому любые скрипты запуска, считающие пулы от nproc, ломаются. И memory.current включает page cache, поэтому для оповещений надо брать working set, а не его.

23. Почему Runtime.exec из большой JVM дорог и как это обойти?

Классический fork() копирует таблицы страниц родителя — у JVM с 32 ГБ heap это десятки мегабайт структур на каждый вызов, плюс при строгом overcommit fork() может просто упасть с ENOMEM, хотя ребёнок сразу сделал бы exec маленького бинарника. В современных JDK на Linux по умолчанию используется posix_spawn (jdk.lang.Process.launchMechanism), что снимает большую часть проблемы. Архитектурно правильнее вообще не запускать внешние процессы из горячего пути: вынести в sidecar, держать пул заранее запущенных воркеров или использовать FFM API.

24. Что такое vm.max_map_count и когда о нём вспоминают?

Это лимит на число областей виртуальной памяти у процесса, исторически 65530. Elasticsearch отказывается стартовать при значении меньше 262144, потому что mmap-ит сегменты Lucene. JVM упирается реже, но упирается: много потоков (каждый стек — отдельное отображение с гардовой страницей), интенсивный FileChannel.map(), ZGC/Shenandoah, jemalloc с большим числом арен. Симптомы — Native memory allocation (mmap) failed или OutOfMemoryError: Map failed при свободной памяти. Это настройка узла, а не пода, в Kubernetes задаётся через privileged initContainer, sysctls или DaemonSet-тюнер.

25. Что даёт eBPF по сравнению со strace?

strace работает через ptrace и на каждый системный вызов дважды останавливает процесс — замедление от 2× до 100×, на проде это способ уронить сервис. eBPF-программы верифицируются и выполняются в ядре, накладные расходы — доли процента, и они видят то, чего strace не видит вовсе: латентность блочного I/O гистограммой (biolatency), время ожидания в runqueue (runqlat), время вне CPU со стеками (offcputime), каждую повторную передачу (tcpretrans). Требования — ядро 5.x, CAP_BPF, и в Kubernetes запускать надо с узла или из privileged-пода.

awk '{print $11}' /tmp/access.log | sort -n |
  awk '{a[NR]=$1} END {printf "p50=%.3f p95=%.3f p99=%.3f max=%.3f\n", a[int(NR*.5)],a[int(NR*.95)],a[int(NR*.99)],a[NR]}'
awk '{tot[$7]++; if ($9>=500) err[$7]++} END {for (e in tot) printf "%5.2f%% %s\n", err[e]*100/tot[e], e}' /tmp/access.log

Ожидаемо: видно, что p99 в разы больше p50 — искусственно внесённые «медленные» запросы создают хвост, невидимый в среднем.

7. Увидеть разницу между RSS и heap.

Bash
java -Xms256m -Xmx256m -XX:NativeMemoryTracking=summary -jar app.jar &
PID=$!; sleep 30
grep VmRSS /proc/$PID/status
jcmd $PID GC.heap_info
jcmd $PID VM.native_memory summary | head -20

Ожидаемо: RSS в 1.5–2.5 раза больше 256 МБ. В выводе NMT видно, из чего складывается разница: Class, Thread, Code, GC.

8. Увидеть арены glibc.

Bash
java -Xmx512m -jar app.jar & PID=$!
sleep 60; pmap -x $PID | awk '$2 == 65536' | wc -l

MALLOC_ARENA_MAX=2 java -Xmx512m -jar app.jar & PID2=$!
sleep 60; pmap -x $PID2 | awk '$2 == 65536' | wc -l

Ожидаемо: во втором случае регионов по 64 МБ существенно меньше, и VmRSS ниже. Эффект тем заметнее, чем больше ядер у машины и чем интенсивнее нативные выделения памяти.

9. Разложить HTTP-запрос по фазам.

Bash
curl -sS -o /dev/null -w 'dns=%{time_namelookup} conn=%{time_connect} tls=%{time_appconnect} ttfb=%{time_starttransfer} total=%{time_total}\n' https://example.com
curl -sS -o /dev/null -w 'dns=%{time_namelookup} ...\n' https://example.com   # второй раз

Ожидаемо: при втором запуске time_namelookup резко меньше, если в системе есть DNS-кеш. Сравни с --resolve, чтобы полностью убрать DNS из измерения.

10. Проверить кеш DNS в JVM.

Java
public class DnsTtl {
    public static void main(String[] a) throws Exception {
        java.security.Security.setProperty("networkaddress.cache.ttl", "5");
        for (int i = 0; i < 12; i++) {
            long t = System.nanoTime();
            java.net.InetAddress.getByName("example.com");
            System.out.printf("%d ms%n", (System.nanoTime()-t)/1_000_000);
            Thread.sleep(1000);
        }
    }
}

Ожидаемо: первый вызов десятки миллисекунд, следующие четыре — 0 мс, затем снова ненулевое значение (кеш истёк через 5 с). Поменяй TTL на 60 и убедись, что ненулевых вызовов больше нет.

Ожидаемо: Recv-Q близок к Send-Q (3), счётчик TcpExtListenOverflows растёт. Часть nc подключится мгновенно, часть — через 1 или 3 секунды (повторные передачи).

12. Увидеть D-состояние. На тестовой машине (не в проде!):

Bash
# Создать интенсивную синхронную запись
dd if=/dev/zero of=/tmp/bigfile bs=1M count=4096 oflag=dsync &
watch -n 1 "ps -eo pid,stat,wchan:25,comm | grep -E ' D' | head"

Ожидаемо: процесс dd регулярно в состоянии D, w_await в iostat растёт, vmstat 1 показывает ненулевую колонку b.

13. Измерить цену strace.

Bash
time (for i in $(seq 20000); do :; done)                     # baseline shell
time (strace -f -o /dev/null bash -c 'for i in $(seq 20000); do true; done')

Ожидаемо: под strace в разы медленнее. Повтори с -c вместо -o — сводка дешевле, но всё равно заметно.

14. Проверить лимиты изнутри контейнера.

Bash
docker run --rm --cpus=0.5 --memory=256m --ulimit nofile=1024:1024 eclipse-temurin:21 sh -c '
  echo "cpu.max: $(cat /sys/fs/cgroup/cpu.max 2>/dev/null)"
  echo "memory.max: $(cat /sys/fs/cgroup/memory.max 2>/dev/null)"
  echo "nproc says: $(nproc)"
  echo "nofile: $(ulimit -n)"
  java -XX:+PrintFlagsFinal -version 2>/dev/null | grep -E "MaxHeapSize|ActiveProcessorCount"
'

Ожидаемо: nproc покажет число ядер хоста (например, 16), cpu.max — 50000 100000, а MaxHeapSize JVM вычислит от 256 МБ (примерно 128 МБ при MaxRAMPercentage=50 или 64 МБ при 25 %). Это наглядная демонстрация, почему nproc нельзя использовать в скриптах запуска.
