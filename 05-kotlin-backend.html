Зачем это знать. Kotlin на бэкенде давно перестал быть «Java с лямбдами», потому что он меняет сразу три модели, на которых держится сервис: модель ошибок, где null стал частью типа, модель concurrency, где корутины работают поверх тех же потоков JVM, и модель классов, где всё по умолчанию final, а рядом появились data class и value class. Каждое из этих изменений сталкивается с экосистемой, которую писали под Java: Spring оборачивает классы в прокси через CGLIB, Hibernate требует конструктор без аргументов и плохо переносит equals по полям, а Jackson ищет сеттеры рефлексией. Почти все продакшен-инциденты «на Kotlin» случаются именно на этих стыках, будь то NullPointerException из platform type, LazyInitializationException из hashCode data class, утечка задач из GlobalScope или взаимоблокировка из-за runBlocking на event loop. Поэтому и на интервью senior-уровня спрашивают об этом же: как suspend превращается в state machine, чем coroutineScope отличается от supervisorScope, почему Dispatchers.IO не решает проблему JDBC и в каких случаях корутины проигрывают виртуальным потокам.

1. Kotlin на бэкенде: преимущества и издержки

Прежде чем разбирать механику языка, стоит честно ответить на вопрос, что Kotlin меняет в бэкенд-сервисе и чем за это приходится платить. Ответ важен и на интервью, и при выборе языка для нового сервиса: Kotlin не ускоряет JVM, зато переносит часть ошибок из прода в компиляцию и в обмен добавляет медленную сборку, стык с Java-фреймворками и лишние зависимости. В этом разделе сначала разобрано, какие три вещи язык действительно навязывает команде, затем перечислена цена по статьям, а в конце собрана таблица сценариев, в которых Kotlin окупается и в которых нет.

1.1 Изменения по сравнению с Java

Kotlin компилируется в обычный байткод JVM и исполняется на том же HotSpot, с тем же JIT и тем же GC, пользуется тем же java.util.concurrent и тем же Netty под WebFlux. Поэтому никакого «быстрее Java» здесь нет и быть не может: горячий код после JIT получается почти идентичным. Разница сводится к трём вещам, которые компилятор навязывает команде, и именно их стоит называть, когда спрашивают, зачем вообще нужен Kotlin:

  1. Nullability в системе типов. String и String? — это разные типы, и компилятор не даст вызвать метод на String?, пока вы не проверите значение. Так целый класс ошибок NPE переезжает со стадии прода на стадию компиляции, но только для того кода, который компилятор видит целиком; где эта гарантия кончается, разобрано в разделе 2 про platform types.
  2. Неизменяемость по умолчанию как идиома. val, read-only List и data class с copy() подталкивают к неизменяемым структурам данных. В параллельном коде это снижает число гонок, а вот с JPA, как показано в разделе 11, те же идиомы создают проблемы.
  3. Корутины как модель concurrency. Единственная языковая конструкция здесь suspend, а всё остальное, включая launch, Flow и диспетчеры, живёт в библиотеке kotlinx.coroutines. Благодаря этому асинхронный код пишется линейно, без цепочек flatMap, но взамен нужно понимать, что при этом происходит с потоками, чему посвящены разделы 6–9.

Кроме того, язык даёт синтаксический сахар, который действительно сокращает объём кода: свойства вместо геттеров и сеттеров, именованные аргументы и значения по умолчанию вместо телескопических конструкторов и строителей, when как выражение, sealed-иерархии с exhaustive-проверкой и extension-функции вместо классов *Utils. С выходом Java 21 разрыв сократился, потому что в Java появились records, sealed, pattern matching и text blocks (см. главу 02, 02-modern-java.md), однако nullability в типах и корутин в Java по-прежнему нет.

1.2 Издержки перехода на Kotlin

У Kotlin на бэкенде четыре статьи расходов, и о каждой стоит знать до того, как команда переведёт на него сервис: время компиляции, интероп с Java, размер зависимостей и то, что экосистема думает на Java. Ниже они разобраны по порядку, с цифрами там, где их удалось измерить.

Компиляция. Компилятор Kotlin работает медленнее javac, потому что делает больше работы: выводит типы, проверяет smart casts, встраивает функции и генерирует state machine для корутин. Новый фронтенд компилятора K2, который стал стандартным с Kotlin 2.0.0 (май 2024), компиляцию ускорил, но паритета с javac не достиг, да это и не заявлялось. Текущая стабильная версия на момент проверки Kotlin 2.4.20 (7 сентября 2026; Kotlin releases). В версии 2.4.0 поддержка -language-version=1.9, то есть старого фронтенда K1, объявлена устаревшей, так что K1 фактически завершён (What's new in Kotlin 2.4.0). Для сборки из этого вытекают три практических следствия:

  • Gradle с Kotlin DSL (build.gradle.kts) сам компилируется компилятором Kotlin, поэтому первый запуск конфигурации идёт медленнее, чем с Groovy; лечат это configuration cache и build cache.
  • Инкрементальная компиляция чувствительна к изменениям в inline-функциях и константах: стоит изменить тело inline fun, и перекомпилируются все, кто её вызывает.
  • kapt (аннотационный процессинг) исторически был самым медленным местом сборки, и хотя в 2.x его перевели на K2, там, где это возможно, лучше обходиться KSP или компиляторными плагинами (kotlinx.serialization, all-open) вместо kapt.

Интероп. Он работает в обе стороны, но даром не даётся. Когда Kotlin вызывает Java, приходится иметь дело с platform types и с тем, что checked exceptions в Kotlin нет, а Java, вызывающая Kotlin, видит Kt-классы для top-level функций, mangling имён у value class, Companion., Unit, аннотации @JvmStatic/@JvmOverloads и отсутствие значений по умолчанию; подробно всё это разобрано в разделе 14.

Размер и зависимости. Размеры артефактов измерены по Maven Central: kotlin-stdlib 2.2.0 весит 1 750 373 байта (≈1,67 МиБ) (Maven Central: kotlin-stdlib/2.2.0), kotlinx-coroutines-core-jvm 1.10.2 весит 1 479 317 байт (≈1,41 МиБ) (Maven Central), а kotlin-reflect 2.2.0 весит 3 298 629 байт (≈3,15 МиБ) (Maven Central). Без kotlin-reflect не обойтись, потому что он нужен Spring для конструкторной инъекции и Jackson для десериализации. В GraalVM native image kotlin-reflect превращается в отдельную головную боль, так как для него требуются reachability metadata.

Экосистема и найм. Spring, Hibernate, Jackson и Micrometer написаны на Java и «думают» на Java, поэтому Kotlin-специфичные грабли из разделов 10–12 и есть цена, которую команда платит за язык. С наймом ситуация двоякая: пул Kotlin-бэкендов-разработчиков меньше, но Java-разработчик осваивает Kotlin за недели, и обратное тоже верно.

💡 На интервью. «Kotlin не делает код быстрее, потому что байткод тот же самый. Зато он превращает три класса ошибок в ошибки компиляции: NPE, забытую ветку when по sealed-иерархии и мутацию там, где ожидалась неизменяемость. Платить за это приходится более медленной компиляцией, стыком с Java-фреймворками, которые ожидают открытых классов и конструкторов без аргументов, и необходимостью понимать корутины глубже, чем suspend в сигнатуре».

Выигрыш от Kotlin сильно зависит от того, чем занят сервис: в одних сценариях язык заметно сокращает код и число ошибок, в других почти ничего не даёт и только добавляет трения. Таблица ниже сопоставляет пять типовых сценариев; в ней стоит смотреть на правую колонку, потому что именно она подсказывает, где язык начнёт мешать.

2. Null-safety

Null-safety в Kotlin означает, что возможность null записана в самом типе: String не может быть null, а String? может, и компилятор не пропустит обращение к nullable-значению без проверки. На практике эта гарантия дырявая, потому что null приходит из Java-кода, из рефлексии и из данных, которые компилятор не видит, и именно на этих стыках случаются NPE в Kotlin-сервисах. В разделе разобрано, во что гарантия превращается в байткоде, где она заканчивается на platform types, чего стоят !!, lateinit и ?.let и как null проникает через Jackson, JPA и JDBC.

2.1 Гарантии компилятора и их реализация в байткоде

Чтобы понимать, где гарантия null-safety работает, а где нет, нужно знать, что от неё остаётся после компиляции. В байткоде String? и String превращаются в один и тот же java.lang.String, а различие между ними живёт в метаданных (@kotlin.Metadata и аннотации @Nullable/@NotNull от org.jetbrains.annotations, которые компилятор ставит на публичные сигнатуры) и в проверках, которые он вставляет в код. На входе каждой публичной функции с non-null параметром компилятор генерирует вызов Intrinsics.checkNotNullParameter(value, "name"), и именно поэтому Java-вызов kotlinFun(null) падает сразу с осмысленным сообщением Parameter specified as non-null is null: method X, parameter name, а не где-то глубже и позже (Calling Kotlin from Java). Эти проверки можно отключить флагом -Xno-param-assertions, но делать этого не стоит: они дешёвые, обходятся одним branch, который JIT на горячем пути убирает, а диагностическая ценность у них высокая.

Внутри самого Kotlin-кода таких проверок нет, потому что компилятор уже доказал, что null туда не попадёт. Smart cast (if (x != null) x.length) тоже существует только во время компиляции, и в байткоде от него остаётся одна ifnull-проверка, та самая, которую вы написали.

2.2 Platform types

Platform type возникает там, где Kotlin получает значение из Java и не знает, может ли оно быть null. Любой тип, пришедший из Java без nullability-аннотаций, Kotlin видит как platform type T!, что означает «T или T?, компилятор не знает». Такое значение можно присвоить и в String, и в String?, причём в первом случае компилятор вставит Intrinsics.checkNotNullExpressionValue в точке присваивания (Calling Java from Kotlin). Из этого следует, что NPE переезжает из места использования в место присваивания, и в сообщении будет имя выражения, а не строка с .length. Три варианта присваивания в примере ниже ведут себя по-разному, и смотреть стоит на то, где именно упадёт каждый из них:

// Java: public String findName(long id) { return map.get(id); } // без аннотаций
val name: String = javaRepo.findName(42)   // NPE здесь, если вернулся null
val safe: String? = javaRepo.findName(42)  // компилятор заставит проверять
val inferred = javaRepo.findName(42)       // тип String!, проверка отложена до первого использования как non-null

Коварнее всего третья строка, потому что inferred можно передать в функцию с параметром String, и NPE случится уже там, в другом файле, далеко от вызова Java. Отсюда правило: всё, что пришло из Java без аннотаций, объявлять с явным типом, а если есть хоть малейшее сомнение, то с nullable-типом.

Kotlin понимает nullability-аннотации из многих источников: JetBrains, JSpecify (@Nullable, @NonNull, @NullMarked), JSR-305, FindBugs, Eclipse, Lombok @NonNull и RxJava 3 (Calling Java from Kotlin). Для Spring это критично, потому что начиная со Spring Framework 7 его API размечен JSpecify, а Kotlin с версии 2.1 трактует org.jspecify.annotations строго (Spring Boot: Kotlin support). Это значит, что repository.findById(id) из Spring Data вернёт Optional<T> с известной nullability, а jdbcTemplate.queryForObject(...) вернёт T?, и компилятор заставит этот случай обработать. Со Spring Framework 6.x, который размечен JSR-305, поведение по сути то же, но в деталях местами отличается, поэтому при миграции с 6 на 7 стоит внимательно просмотреть предупреждения компилятора.

⚠️ Грабли. Библиотека, размеченная JSR-305 через пакетную аннотацию @ParametersAreNonnullByDefault, даёт Kotlin строгие типы только в том случае, если включён флаг -Xjsr305=strict. Без него вы получите warning вместо ошибки, и типы останутся platform. Поэтому проверьте kotlinOptions/compilerOptions в сборке: строка freeCompilerArgs.add("-Xjsr305=strict") считается стандартной рекомендацией для Spring-проектов.

2.3 !!, lateinit и ?.let

Когда компилятор не может доказать, что значение не null, у разработчика есть три инструмента, чтобы его обойти: !!, lateinit и ?.let. Каждый из них во что-то компилируется и где-то оправдан, но каждым легко злоупотребить, и ниже разобрано, где проходит граница.

!! означает явное «я знаю лучше компилятора». В байткоде он превращается в Intrinsics.checkNotNull(x), который бросает NullPointerException. Оправдан он там, где проверку сделали, но компилятор её не видит (map.containsKey(k) → map[k]!!), а также в тестах и в коде, который мигрирует с Java. Во всех остальных местах, где можно написать ?: с осмысленным исключением, он не нужен: x ?: error("order $id has no customer") даст диагностируемый IllegalStateException вместо голого NPE.

lateinit var объявляет свойство без инициализатора, но с non-null типом, и проверяет его при каждом чтении: компилятор генерирует if (field == null) Intrinsics.throwUninitializedPropertyAccessException("name"). Применять его можно только к var, и тип при этом не может быть примитивом или nullable. Проверить, инициализировано ли свойство, можно через ::prop.isInitialized. Основной сценарий для lateinit составляют field injection в тестах (@Autowired lateinit var mockMvc: MockMvc) и инициализация в @BeforeEach, а вот в продакшен-бинах он обычно говорит о том, что не сделана конструкторная инъекция (раздел 10.2).

?.let { } работает как ленивый if (x != null). Компилируется он во встроенный код, потому что let объявлен как inline fun: лямбда не выделяется, и в байткоде остаются ifnull и тело. Злоупотребляют им в цепочках вроде a?.let { b?.let { c?.let { ... } } } вместо if (a != null && b != null && c != null), где семантика та же, а читаемость падает. Есть и классическая ошибка: в выражении x?.let { doSomething(it) } ?: fallback() функция fallback() вызовется не только когда x == null, но и когда doSomething вернул null. Поэтому для логики «если null, то одно, иначе другое» лучше брать if или when, как в примере ниже:

// Ловушка ?.let ?:, где fallback двусмысленный
val cached: String? = cache.get(key)?.let { decode(it) } ?: loadFromDb(key)
// Если decode вернул null (битая запись), код тихо пойдёт в БД. Возможно, так и задумано, но из кода это не очевидно.

// Явно:
val raw = cache.get(key)
val result = if (raw != null) decode(raw) else loadFromDb(key)

2.4 Nullability на границах: Jackson, JPA, JDBC

Компилятор отвечает только за код, который он видел, а в работающем сервисе значения создаются ещё и десериализатором, ORM и драйвером базы. Есть три таких границы, через которые null приходит во время выполнения в обход компилятора, и для каждой важно знать, что именно там происходит:

  1. Десериализация. jackson-module-kotlin уважает Kotlin-типы, поэтому null в JSON для val name: String даст MismatchedInputException/DatabindException, а не объект с null внутри (jackson-module-kotlin). Однако если поле объявлено как non-null примитив (val count: Int), а в JSON пришёл явный null, то без FAIL_ON_NULL_FOR_PRIMITIVES в поле подставится 0, о чём сказано на той же странице README. Без Kotlin-модуля Jackson создаст объект через Unsafe или конструктор без аргументов и запишет null в поле типа String, и val перестанет что-либо гарантировать.
  2. JPA. Hibernate заполняет поля рефлексией, поэтому, если свойство объявлено как val email: String, а в БД колонка допускает null (@Column(nullable = true)), во время выполнения в поле окажется null, и NPE вылетит при первом обращении из Kotlin-кода в самом неожиданном месте (раздел 11.4).
  3. JDBC / R2DBC. rs.getString("name") возвращает platform type String!, а jdbcTemplate.queryForObject(sql, String::class.java) вернёт String?, потому что Spring размечен аннотациями. Kotlin extensions для Spring Data JDBC/R2DBC возвращают корректные nullable-типы.

🔧 Под капотом. Nullability оказывается единственной частью системы типов Kotlin, которая полностью стирается в байткоде и продолжает жить только в метаданных и во вставленных проверках. Отсюда правило: гарантии действуют ровно там, где объект создан Kotlin-кодом через конструктор. Всё, что создано рефлексией, будь то Hibernate, Jackson без модуля или Mockito с RETURNS_DEFAULTS, может нарушить инварианты, и компилятор об этом не узнает.

3. Классы: data, sealed, enum, value, object

Kotlin добавляет к обычному классу несколько модификаторов, каждый из которых заставляет компилятор сгенерировать заметный объём кода: data порождает equals, hashCode и copy, sealed закрывает иерархию, value убирает обёртку из байткода, а object делает синглтон. Знать, что именно генерируется, нужно потому, что сгенерированный код сталкивается с Java-фреймворками: data class ломает JPA-сущности, value class ломает вызовы из Java, а companion не даёт настоящей статики. Раздел разбирает пять видов классов по очереди, и для каждого сказано, во что он компилируется и где его применять.

3.1 Генерируемые методы data class

Data class предназначен для объектов, которые определяются своими значениями, а не идентичностью, и компилятор дописывает к нему методы, нужные такому объекту. Для data class он генерирует equals()/hashCode(), toString(), componentN() и copy(), причём только по свойствам первичного конструктора, а свойства, объявленные в теле класса, в них не участвуют (Data classes). Если equals, hashCode или toString написаны явно, компилятор их не перезаписывает, а вот copy и componentN написать явно нельзя. Копирование через copy() поверхностное, так что вложенные изменяемые объекты оказываются общими у оригинала и копии.

Байткод equals вполне обычный: проверка this === other, затем instanceof, затем сравнение полей через Intrinsics.areEqual для ссылочных типов и через == для примитивов, причём Float/Double обрабатываются особо, через compare. hashCode вычисляется как 31 * h + field.hashCode() с 0 для null. Ничего магического в этом нет, но сгенерированный код реализует семантику value-объекта, при которой два экземпляра с одинаковыми полями равны. Именно это и ломает JPA (раздел 11.2), потому что сущность определяется идентичностью, а не значением.

copy() компилятор генерирует как публичный метод с параметрами по умолчанию, и из этого следует, что если у data class приватный конструктор с валидацией, то copy() эту валидацию обходит. Kotlin 2.0.20+ выдаёт на этот случай предупреждение, а с версии 2.1 есть аннотации @ConsistentCopyVisibility, при которой copy наследует видимость конструктора, и @ExposedCopyVisibility (What's new in Kotlin 2.1.0).

Следствие для практики. Data class подходит для DTO, событий, конфигурации (@ConfigurationProperties), ключей кэша и результатов запросов, то есть проекций. Для JPA-сущностей, Spring-бинов и вообще для всего, у чего есть identity или изменяемое состояние, он не подходит.

3.2 sealed и enum: exhaustive when и его байткод

Оба вида классов описывают закрытое множество вариантов, и компилятор пользуется этим, чтобы проверить, что when разобрал их все. sealed class/sealed interface задают закрытую иерархию, все прямые наследники которой известны компилятору; начиная с 1.5 они должны лежать в пределах одного модуля и пакета, но не обязательно в одном файле. when по sealed-типу без else проверяется на полноту, и добавление нового наследника ломает компиляцию всех таких when. В этом и состоит главная ценность sealed для доменного моделирования, например для результата платежа sealed interface PaymentResult { data class Ok(...); data class Declined(...); data object Timeout }.

В байткоде sealed class становится обычным абстрактным классом с приватным конструктором и синтетическим конструктором для наследников из других файлов, а sealed interface становится обычным интерфейсом. JVM-sealed (PermittedSubclasses, JEP 409) Kotlin не использует, поэтому Java-код может реализовать Kotlin sealed interface, и компилятор Kotlin об этом не узнает (⚠️ поведение проверено для 1.x–2.3; для 2.4 отдельно не перепроверял). when по типу компилируется в цепочку instanceof, а не в tableswitch, так что порядок веток влияет на число проверок в худшем случае, хотя для 5–10 веток это несущественно.

enum class компилируется в стандартный java.lang.Enum с values()/valueOf(). when по enum генерирует tableswitch через синтетический класс WhenMappings с массивом int[], причём такой класс создаётся отдельно для каждого файла, где встречается этот when. В Kotlin 1.9+ появилось свойство entries (immutable EnumEntries), которое заменяет values() и не выделяет массив на каждый вызов, поэтому пользоваться стоит именно entries.

data object, стабильный с 1.9, ведёт себя как обычный object, но печатает toString() без хеша в имени и корректно сравнивается через equals после десериализации, и его место в терминальных состояниях sealed-иерархии.

3.3 value class: inline, упаковка и mangling

Value class нужен, чтобы дать значению собственный тип и не платить за это выделением памяти обёртки. @JvmInline value class UserId(val value: Long) объявляет обёртку над одним значением, которую компилятор в байткоде по возможности заменяет самим значением: параметр UserId становится long, и выделения памяти не происходит. Однако компилятор боксит value class всякий раз, когда тип нужен как ссылочный: в generic-параметре (List<UserId> хранит боксы), в nullable-типе (UserId?), в интерфейсном типе, если value class реализует интерфейс, и в Any (Inline value classes). На сам класс наложены ограничения: в первичном конструкторе ровно одно свойство, у других свойств нет backing fields, нельзя использовать lateinit и делегаты, класс final, а === запрещён.

Имена функций, у которых value class стоит в параметрах, манглируются: fun find(id: UserId) в байткоде превращается в find-<hash>(long), чтобы find(UserId) и find(OrderId), которые оба сводятся к long, не конфликтовали. Из Java такой метод вызвать нельзя, пока вы не зададите ему имя через @JvmName("findByUserId"), и по той же причине без @JvmName его нельзя объявить в интерфейсе, который реализует Java-класс. В примере ниже видно и то, как денежная сумма остаётся long в сигнатуре, и то, где она всё-таки боксится:

@JvmInline value class Money(val minor: Long) {
    init { require(minor >= 0) }         // init разрешён (с 1.4.30)
    operator fun plus(o: Money) = Money(minor + o.minor)
}

fun charge(amount: Money) { }             // байткод: charge-XXXX(long)
val list: List<Money> = listOf(Money(1))  // элементы боксятся в Money-объекты

Окупается value class на идентификаторах (UserId, OrderId), где он защищает от перепутанных аргументов без выделений памяти на горячем пути, на единицах измерения и на обёртках над String, которые проверяют значение. Не окупается он в коллекциях, где упаковка происходит всё равно, в JPA, где Hibernate 6 умеет работать с ним через AttributeConverter, но опять же с упаковкой, и в Jackson, где поддержка появилась с jackson-module-kotlin 2.17, но с оговорками, перечисленными в README модуля.

3.4 object, companion object и статика

Статических членов в Kotlin нет, и их роль играют объявления object и companion object, которые из Java выглядят совсем не так, как привычная статика. object Foo объявляет синглтон, который инициализируется лениво при первом обращении через статическое поле INSTANCE, и потокобезопасность ему обеспечивает class init lock самой JVM, то есть тот же механизм, что у holder idiom в Java. companion object превращается во вложенный объект Companion с полем Foo.Companion, и его члены не статические, так что из Java к ним обращаются как Foo.Companion.bar(). Настоящий статический метод-делегат генерирует @JvmStatic, статическую константу даёт const val (только для примитивов и String), а статическое поле без геттера даёт @JvmField (Calling Kotlin from Java).

Для Spring и Jackson отсюда вытекает несколько следствий. @JsonCreator в companion требует @JvmStatic, @Bean-методы в companion не работают, потому что Spring ищет их на самом классе конфигурации, а Mockito не умеет подменять заглушкой object, тогда как MockK умеет через mockkObject. Логгер, объявленный в companion как companion object { private val log = LoggerFactory.getLogger(Foo::class.java) }, создаётся в одном экземпляре на класс, как private static final в Java. Top-level private val log в файле тоже становится статикой класса FooKt, но если вызывать getLogger {} с рефлексией, в логах появится имя класса FooKt.

4. Функции: extension, scope functions, inline/reified, делегирование, DSL

Функции в Kotlin умеют больше, чем методы в Java: их можно объявлять как расширения чужих классов, встраивать вместе с лямбдами, сохранять реальный generic-тип, делегировать свойства и строить из них DSL. За каждой из этих возможностей стоит конкретная схема компиляции, и от неё зависит, во что обходится вызов, как он выглядит из Java и где он ведёт себя неожиданно. Раздел проходит по пяти механизмам: extension-функциям, scope functions, inline/reified, делегированию свойств и DSL-строителям с lambda with receiver.

4.1 Extension-функции и их компиляция

Extension-функция позволяет добавить метод к классу, который вы не можете изменить, но никакого метода в классе при этом не появляется. fun String.isBlankOrNull() компилируется в public static boolean isBlankOrNull(String $this) в классе <File>Kt (Calling Kotlin from Java), и из этой схемы вытекают все её особенности:

  • Такие функции разрешаются статически, по объявленному типу, а не по типу во время выполнения. Если объявить fun Payment.channel() = "generic"; fun CardPayment.channel() = "card"; val p: Payment = CardPayment(); p.channel(), результатом будет "generic", потому что extension-функции не полиморфны, и это не баг.
  • Действует правило member wins: если у класса есть метод с той же сигнатурой, extension никогда не вызовется, и компилятор предупреждает об этом как EXTENSION_SHADOWED_BY_MEMBER. Классические грабли возникают, когда вы пишете extension на Java-класс, а в следующей версии библиотеки у него появляется метод с таким же именем.
  • Extension на nullable receiver (fun String?.orEmpty()) вполне легален и полезен, и внутри такой функции this имеет тип String?.
  • Для Spring Data есть готовые расширения: spring-data-commons даёт repository.findByIdOrNull(id), расширение CrudRepository, которым заменяют findById(id).orElse(null); spring-jdbc даёт queryForObject<T>(sql) с reified-типом, а WebClient даёт awaitBody<T>() и bodyToMono<T>().

Стоит такой вызов ровно ноль, потому что это обычный статический вызов, который JIT встраивает, как любой другой.

4.2 Scope functions: let, run, apply, also, with

Scope functions выполняют блок кода в контексте объекта и нужны, чтобы не заводить временную переменную ради пары вызовов. Все пять объявлены как inline, поэтому лямбда не выделяется и в байткоде остаётся только её тело. Различаются они по двум осям: как внутри блока доступен объект (через it в let/also или через this в run/apply/with) и что блок возвращает (результат лямбды в let/run/with или сам объект в apply/also). Таблица ниже раскладывает функции по этим двум осям и даёт для каждой типовую идиому:

Функция Объект Возвращает Идиома
let it результат лямбды x?.let { transform(it) }, ввод переменной в scope
run this результат лямбды вычисление с несколькими членами объекта; run { } без receiver — блок-выражение
with(x) this результат лямбды группировка вызовов на объекте, без null-безопасности
apply this объект конфигурация строителя или объекта: Props().apply { host = ...; port = ... }
also it объект side effect в цепочке: .also { log.debug("loaded {}", it) }

Злоупотребляют ими тремя способами. Первый состоит во вложенных scope functions с this: в конструкции apply { run { with(x) { ... } } } читатель перестаёт понимать, что сейчас означает this, и вызовы могут неявно уйти во внешний receiver, особенно если в дело вмешиваются extension-функции. Второй способ заключается в том, чтобы применять let к не-null значениям просто ради «стиля»: val user = repo.find(id).let { it } ничего не делает и только создаёт шум. Третий способ связан с apply для объектов с побочными эффектами вместо явных вызовов: читая apply { save(); publish() }, приходится вспоминать, что apply возвращает объект, а не результат publish.

Отсюда простое правило: одна scope function на выражение, apply только для инициализации, also только для логирования и метрик, let для обработки null и переименования, а run и with лишь изредка.

4.3 inline и reified

Модификатор inline меняет саму схему вызова, и через неё же работает reified, который сохраняет generic-тип до среды выполнения. Для inline fun компилятор копирует тело функции и тела переданных лямбд прямо в место вызова, и из этого получаются три следствия. Во-первых, не создаётся Function-объект под лямбду и не происходит виртуального вызова invoke, что заметно на горячих путях вроде forEach, map и filter над коллекциями. Во-вторых, non-local return внутри лямбды возвращает из внешней функции. В-третьих, растёт байткод, потому что каждый вызов inline fun с большим телом копирует это тело целиком. Компилятор предупреждает, если inline-функция не принимает лямбд, так как там inline не даёт выигрыша, а рекурсивные функции встраивать нельзя вовсе.

reified T возможен только в inline fun, потому что только там тип известен в месте вызова и может быть подставлен как T::class.java. Именно так работают objectMapper.readValue<T>(json) из jackson-module-kotlin и restClient.get().retrieve().body<T>() из Spring, и без reified пришлось бы вручную передавать TypeReference<T>. Ограничение у этого механизма одно, но существенное: reified-функцию нельзя вызвать из Java. Строго говоря, в байткоде она есть, но с параметром-заглушкой, и компилятор Java не подставит в неё тип. Пример ниже показывает, как reified-параметр позволяет Jackson увидеть настоящий тип коллекции:

inline fun <reified T> ObjectMapper.readValueOrNull(json: String?): T? =
    json?.let { readValue(it, object : TypeReference<T>() {}) }
// Анонимный TypeReference<T> с reified T захватывает реальный тип, и Jackson видит List<Order>, а не List<Object>

Два модификатора уточняют поведение отдельных лямбд. crossinline запрещает non-local return, и нужен он тогда, когда лямбда будет вызвана из другого контекста, например из Runnable, а noinline запрещает встраивать конкретную лямбду, потому что её нужно сохранить или передать дальше как объект.

4.4 Делегирование свойств: by lazy, Delegates.observable, by map

Делегирование свойства означает, что чтение и запись свойства перенаправляются в отдельный объект-делегат, который решает, откуда брать значение и что делать при записи. Для val x by lazy { } компилятор создаёт поле типа Lazy<T> и геттер, который вызывает getValue(). По умолчанию lazy() работает в режиме SYNCHRONIZED с double-checked locking внутри SynchronizedLazyImpl; кроме него есть режим PUBLICATION, в котором значение могут посчитать несколько потоков, но побеждает первый результат, как у ConcurrentHashMap.computeIfAbsent без блокировки, и режим NONE без синхронизации, для однопоточного кода. Чтение такого свойства обходится в виртуальный вызов getValue плюс volatile read, и на очень горячих путях это измеримо, хотя обычно ничтожно.

У стандартной библиотеки есть и другие делегаты. Delegates.observable { prop, old, new -> } и Delegates.vetoable вызывают обратный вызов при записи, а Delegates.notNull() работает как lateinit, но, в отличие от него, подходит и для примитивов. При by map свойства читаются из Map<String, Any?> по имени, и на бэкенде так делают для конфигурации и динамических DTO, но ценой потери типобезопасности: если ключ перепутан, вы получите NoSuchElementException во время выполнения.

Делегирование классов (class Wrapper(val inner: Repo) : Repo by inner) устроено иначе: компилятор генерирует все методы интерфейса как делегаты к inner, и получается статический Decorator без boilerplate. В Spring им удобно оборачивать клиентов метриками или повторными попытками без всякого AOP.

4.5 DSL-строители: lambda with receiver и @DslMarker

DSL в Kotlin строится на lambda with receiver, то есть на лямбде, внутри которой this указывает на заранее заданный объект. В сигнатуре fun html(block: HTML.() -> Unit) внутри block this указывает на экземпляр HTML, и вызовы вроде body { } разрешаются как методы HTML. Так устроены coRouter { GET("/") { } } в Spring WebFlux, спецификации Kotest, Gradle Kotlin DSL, kotlinx.html и Exposed. Платить за это приходится выделениями памяти: каждая не-inline лямбда с receiver становится объектом Function1, и вложенные строители выделяют объекты при каждом вызове DSL. Для конфигурации при старте это неважно, а вот DSL на горячем пути запроса стоит замерить.

@DslMarker решает проблему видимости внешних receiver. Это аннотация на аннотацию, которой размечают receiver-типы, и когда они размечены, из вложенной лямбды нельзя неявно обратиться к внешнему receiver с тем же маркером, а нужно писать явный this@outer. Без маркера DSL страдает от той же беды, что вложенные apply: вызов молча уходит не в тот объект. В примере ниже маркер не даёт вложить group в group:

@DslMarker annotation class RouteDsl

@RouteDsl class RouteBuilder { val routes = mutableListOf<String>(); fun get(path: String) { routes += "GET $path" } }
@RouteDsl class ApiBuilder { val groups = mutableListOf<RouteBuilder>(); fun group(block: RouteBuilder.() -> Unit) { groups += RouteBuilder().apply(block) } }

fun api(block: ApiBuilder.() -> Unit) = ApiBuilder().apply(block)

val a = api {
    group { get("/users") }
    // group { group { } }  ← ошибка компиляции благодаря @DslMarker: group недоступен из RouteBuilder
}

5. Коллекции Kotlin и java.util

Коллекции Kotlin выглядят как отдельная библиотека с неизменяемыми и изменяемыми интерфейсами, но на JVM они лежат поверх тех же классов java.util, и разделение на read-only и mutable существует только в системе типов. Отсюда вытекают неприятные сюрпризы на границе с Java, где «неизменяемый» список спокойно мутируют, а также вопрос о цене операторов, которые на каждом шаге создают новый список. В разделе разобрано, что на самом деле скрывается за List<T>, во что обходятся цепочки операторов и когда вместо них брать Sequence или Stream.

5.1 Что такое List<T> в Kotlin

Главное, что нужно знать про kotlin.collections.List, состоит в том, что это интерфейс без мутирующих методов, а в байткоде он превращается в обычный java.util.List. listOf(1, 2, 3) возвращает Arrays$ArrayList (через Arrays.asList), длину которого изменить нельзя, но set у которого работает; mutableListOf() возвращает java.util.ArrayList, emptyList() возвращает синглтон EmptyList, а listOf(x) с одним элементом возвращает Collections.singletonList (⚠️ детали реализации зависят от версии stdlib и платформы; на JVM так с 1.x). Ни один из этих списков не иммутабелен в том смысле, в каком иммутабелен List.of() из Java 9+, потому что Kotlin-List даёт лишь read-only view: через него коллекцию можно только читать, но это ограничение интерфейса, а не объекта, и гарантия существует только на уровне типов. Приведение (list as MutableList).add(4) компилируется и дальше либо срабатывает, если под капотом ArrayList, либо бросает UnsupportedOperationException.

Из этого вытекают три практических следствия:

  • Java-код, получивший Kotlin List, видит java.util.List и может его мутировать. Если это ArrayList, полученный через toMutableList() или map {} (да, map возвращает ArrayList), мутация пройдёт, и ваш «неизменяемый» объект изменится. Поэтому в защищённых API отдавайте toList(), то есть копию, или java.util.List.copyOf/Collections.unmodifiableList.
  • Kotlin, получая Java List<T>, видит (Mutable)List<T>!, и объявить его можно как List<T> или как MutableList<T>, по своему усмотрению (Calling Java from Kotlin).
  • Настоящую неизменяемость со структурным разделением даёт библиотека kotlinx.collections.immutable (PersistentList, persistentListOf()). В Kotlin 2.4 появились экспериментальные collection literals [1, 2, 3] (What's new in Kotlin 2.4.0), но результат у них того же read-only типа List.

С Map<K, V> всё аналогично: mapOf() даёт LinkedHashMap, который сохраняет порядок вставки, и на этот порядок иногда неявно полагаются, чего с HashMap делать нельзя, а mutableMapOf() тоже даёт LinkedHashMap. Обычный HashMap нужно просить явно, через HashMap(), когда порядок не нужен, а память важна.

5.2 Операторы над коллекциями: eager и промежуточные списки

Операторы вроде filter и map над обычными коллекциями Kotlin выполняются жадно, то есть каждый из них сразу обрабатывает весь вход и отдаёт готовый результат. В цепочке list.filter { }.map { }.take(5) каждый шаг создаёт новый ArrayList и проходит всю коллекцию, а take(5) срабатывает последним, так что на коллекции в 1 млн элементов вы получаете 2 полных прохода и 2 промежуточных списка. Плюс такой схемы в том, что всё здесь inline и лямбды не выделяются, поэтому на маленьких коллекциях это быстрее Stream API, которому приходится платить за pipeline и Spliterator. Минус в том, что на больших коллекциях она расходует лишнюю память и делает лишнюю работу.

5.3 Sequence и Stream

Когда промежуточные списки начинают стоить дорого, в Kotlin переключаются на Sequence, ленивый аналог коллекции, который по устройству ближе всего к Java Stream. asSequence() переводит цепочку на ленивую поэлементную обработку, при которой каждый элемент проходит всю цепочку целиком, а take(5) останавливает её после пятого элемента (Sequences). Механически Sequence — это интерфейс с единственным методом iterator(), а каждый оператор заворачивает исходную последовательность в обёртку (FilteringSequence, TransformingSequence), которая выделяется один раз на цепочку, причём лямбды здесь не встраиваются, потому что сохраняются в этих объектах. Чем Sequence отличается от java.util.stream.Stream, показывает таблица:

Sequence Stream
Ленивость да да
Параллелизм нет parallel() через ForkJoin
Многократный обход зависит (constrainOnce() запрещает) нет, одноразовый
Примитивные специализации нет (упаковка Int) IntStream и т.д.
Реализация Iterator-based, простая Spliterator + pipeline, тяжелее
Interop asStream()/asSequence() из kotlin.streams.jdk8 —
yield-генераторы sequence { yield(x) } — на корутинной машинерии (restricted suspension) нет

Sequence стоит брать для длинных цепочек над большими коллекциями, для раннего выхода через first { } или take и для генераторов (generateSequence, sequence { }). Обычные операторы лучше на маленьких коллекциях, до сотен элементов, и на коротких цепочках, где накладные расходы sequence оказываются выше выигрыша. Stream нужен тогда, когда требуется parallel() или примитивные специализации на горячем пути (см. главу 03, 03-collections-and-streams.md).

📊 Цифры. На коллекции из 10 элементов filter+map через List обходится в единицы наносекунд на элемент без выделений памяти лямбд, тогда как через Sequence та же цепочка создаёт 2–3 объекта-обёртки и боксит Int. На 1 млн элементов с take(10) в конце sequence выигрывает на порядки, потому что обрабатывает ~10 элементов вместо миллиона. Точные числа для вашего кода даст только JMH (глава 44).

6. Корутины: устройство suspend

Корутина в Kotlin — это вычисление, которое умеет приостановиться, не занимая поток, и продолжиться позже, возможно на другом потоке. Чтобы понимать, почему корутины дёшевы, почему ThreadLocal через них не переживает и откуда в трассировке стека берутся странные кадры, нужно знать, во что компилятор превращает suspend fun. В этом разделе разобрано, что из машинерии корутин относится к языку, а что к библиотеке, как работает CPS-трансформация, как выглядит сгенерированная state machine и из чего состоят CoroutineContext, Job и CoroutineScope.

6.1 Модификатор suspend как языковая конструкция

Первое, что стоит понять про корутины, это граница между языком и библиотекой. В самом языке Kotlin из всей машинерии корутин есть ровно одно: модификатор suspend вместе с низкоуровневым API в kotlin.coroutines (Continuation, suspendCoroutine, createCoroutine, startCoroutine). Всё остальное, то есть launch, async, Dispatchers, Flow, Job и withContext, принадлежит библиотеке kotlinx.coroutines, которую в принципе можно заменить; именно так работают sequence { yield() } в stdlib и, например, Arrow. Поэтому начинать разбор нужно с языковой части, то есть с того, во что компилятор превращает suspend fun.

6.2 CPS-трансформация

Continuation-passing style (CPS) означает, что функция не возвращает результат вызывающему напрямую, а получает дополнительным параметром объект, которому этот результат нужно передать. Именно этот стиль компилятор применяет к suspend-функциям: каждая suspend fun foo(a: A): T в байткоде становится fun foo(a: A, $completion: Continuation<T>): Any? (KEEP: Kotlin Coroutines design). Возвращаемый тип Any? нужен потому, что функция может вернуть либо реальный результат T, если завершилась без приостановки, либо специальный маркер COROUTINE_SUSPENDED, который означает «я приостановилась, и результат придёт позже через continuation.resumeWith».

Сам Continuation<T> устроен как интерфейс всего с двумя членами:

interface Continuation<in T> {
    val context: CoroutineContext
    fun resumeWith(result: Result<T>)
}

По сути это обобщённый обратный вызов. suspendCoroutine { cont -> ... } отдаёт его вам в руки, и именно так оборачивают любые callback-API: Netty futures, асинхронные драйверы и CompletableFuture, для которого есть await() из kotlinx-coroutines-jdk8.

6.3 Конечный автомат (state machine)

CPS объясняет сигнатуру, но не то, как функция продолжает работу с середины после приостановки, и эту задачу решает state machine. Тело suspend-функции с N точками приостановки компилируется в одну функцию и один класс-континуацию (foo$1 extends ContinuationImpl), у которого есть поле label: Int и поля для тех локальных переменных, что живут через точку приостановки (KEEP). Схематично это удобнее всего показать на функции с двумя точками приостановки:

suspend fun loadUser(id: Long): UserView {
    val user = userClient.get(id)        // suspension point 1
    val orders = orderClient.list(id)    // suspension point 2
    return UserView(user, orders)
}

В упрощённом виде и в терминах Kotlin компилятор превращает её в следующий код, в котором стоит следить за полем label и за проверками на COROUTINE_SUSPENDED:

fun loadUser(id: Long, completion: Continuation<UserView>): Any? {
    val sm = completion as? LoadUserSM ?: LoadUserSM(completion)   // переиспользуем при resume
    when (sm.label) {
        0 -> {
            sm.id = id; sm.label = 1
            val r = userClient.get(id, sm)                 // передаём sm как continuation
            if (r === COROUTINE_SUSPENDED) return COROUTINE_SUSPENDED
            sm.user = r as User                            // не приостановилось — идём дальше сразу
        }
        1 -> sm.user = sm.result.getOrThrow() as User      // resume после приостановки
    }
    if (sm.label == 1) {
        sm.label = 2
        val r = orderClient.list(sm.id, sm)
        if (r === COROUTINE_SUSPENDED) return COROUTINE_SUSPENDED
        sm.orders = r as List<Order>
    } else {
        sm.orders = sm.result.getOrThrow() as List<Order>  // label == 2
    }
    return UserView(sm.user, sm.orders)
}

Когда вызов приостанавливается, функция возвращает маркер, а когда нижележащая функция готова, она вызывает sm.resumeWith(result), после чего ContinuationImpl.resumeWith снова вызывает loadUser(…, sm), и when(label) прыгает в нужное состояние; в реальном байткоде это tableswitch и goto, без дублирования кода. Локальные переменные user и id хранятся в полях объекта, поэтому корутина живёт в куче, а не на стеке потока, и именно поэтому миллион приостановленных корутин стоит десятки–сотни байт каждая, а не мегабайт стека.

У этого механизма четыре следствия, которые видны на практике:

  • Выделение памяти на вызов. Каждый вызов suspend-функции, которая действительно может приостановиться, создаёт объект state machine. Дешёвые suspend-функции, которые не приостанавливаются, стоят почти как обычные, потому что маркер не возвращается и when проходит насквозь. Кроме того, компилятор оптимизирует tail call: suspend fun a() = b() не создаёт собственной state machine, а передаёт continuation дальше (KEEP).
  • Трассировки стека. Реальный стек в момент исключения тянется от диспетчера до текущей функции, а «логический» стек, то есть кто кого вызывал через приостановки, восстанавливает библиотека (stack trace recovery, свойство kotlinx.coroutines.stacktrace.recovery, которое по умолчанию включено в debug-сборках). В Kotlin 2.4.20 для кастомных исключений добавлен интерфейс StackTraceRecoverable (What's new in Kotlin EAP). Recovery копирует исключение через рефлексию, для чего нужен конструктор (String) или (String, Throwable), и это стоит времени, так что в проде под нагрузкой его нередко отключают.
  • Дебаггер показывает панель Coroutines именно потому, что state machine корутин хранятся в обычных объектах, которые регистрирует kotlinx-coroutines-debug (агент или DebugProbes).
  • suspend в интерфейсе превращается в метод с дополнительным параметром Continuation. Из Java его вызвать можно, передав собственный Continuation, но это неудобно, поэтому для Java-потребителей лучше предоставлять CompletableFuture-обёртки через future { } из kotlinx-coroutines-jdk8.

6.4 CoroutineContext, Job, CoroutineScope

Эти три типа образуют каркас, на котором библиотека строит всё остальное: контекст хранит настройки корутины, Job отвечает за её жизненный цикл, а scope связывает новые корутины с родителем. CoroutineContext хранит элементы в immutable-наборе, индексированном по ключам, — по сути это persistent map с операцией +, куда входят Job, CoroutineDispatcher, CoroutineName, CoroutineExceptionHandler и ваши ThreadContextElement. У каждой корутины свой контекст, и withContext(X) создаёт дочерний контекст parent + X.

Job служит handle на корутину и проходит через состояния New → Active → Completing → Completed / Cancelling → Cancelled, а дочерние Job регистрируются у родителя. CoroutineScope просто оборачивает CoroutineContext и содержит одно свойство coroutineContext, а launch/async объявлены как extension-функции на CoroutineScope, поэтому вызвать их «из ниоткуда» нельзя: нужен scope, а значит, и родительский Job. Это и есть механическая основа structured concurrency, о которой пойдёт речь в следующем разделе.

7. Structured concurrency, диспетчеры, отмена, исключения

Предыдущий раздел объяснил, как устроена одна корутина, а этот посвящён тому, как корутины живут вместе: кто кого ждёт, на каких потоках они исполняются, как их останавливают и куда девается ошибка. Structured concurrency означает, что каждая корутина запускается внутри scope и привязана к родителю, поэтому ни одна задача не может незаметно пережить запрос, который её породил. На практике именно здесь сосредоточены самые частые грабли бэкенда на корутинах: исчерпанный лимит Dispatchers.IO, отмена, которую проглотил runCatching, и async, чья ошибка валит родителя раньше, чем кто-то вызвал await(). Раздел разбирает иерархию Job, диспетчеры, кооперативную отмену и правила распространения исключений.

7.1 Structured concurrency: иерархия Job

Принцип structured concurrency сформулировал Роман Елизаров в 2018 году (⚠️ статью на Medium открыть не удалось, формулировка приведена по официальному гайду), и звучит он так: корутина не может «потеряться», потому что у каждой есть родитель, родитель не завершится, пока не завершатся его дети, отмена родителя отменяет детей, а ошибка ребёнка по умолчанию отменяет родителя. Реализован этот принцип через Job: launch внутри scope создаёт Job с parent = scope.coroutineContext[Job] и регистрирует ChildHandle.

Получить scope можно тремя способами, и каждый задаёт свою политику ошибок:

  1. coroutineScope { } — это suspend-функция, которая создаёт дочерний scope, ждёт всех детей и возвращает результат блока. Если падает любой ребёнок, остальные отменяются, а исключение пробрасывается из coroutineScope. Это идиома для задачи «параллельно сделать N вещей и собрать результат», например для экрана клиента онлайн-банка, который собирается из трёх сервисов:
suspend fun loadDashboard(userId: Long): Dashboard = coroutineScope {
    val profile = async { profileClient.get(userId) }
    val orders = async { orderClient.recent(userId) }
    val balance = async { accountClient.balance(userId) }
    Dashboard(profile.await(), orders.await(), balance.await())
}
// Если orderClient упал, profile и balance отменяются, а loadDashboard бросает исключение. Ничего не утекает.
  1. supervisorScope { } устроен так же, но ошибка ребёнка здесь не отменяет ни siblings, ни родителя, и каждый ребёнок сам отвечает за свои исключения, а если не обработает их, они уйдут в CoroutineExceptionHandler (Coroutine exceptions handling). Это идиома для задачи «сделать N независимых вещей и собрать то, что получилось»:
suspend fun enrich(order: Order): EnrichedOrder = supervisorScope {
    val geo = async { geoClient.resolve(order.address) }
    val risk = async { riskClient.score(order) }
    EnrichedOrder(
        order,
        geo = runCatching { geo.await() }.getOrNull(),      // упавший geo не валит risk
        risk = runCatching { risk.await() }.getOrNull(),
    )
}
  1. Долгоживущий CoroutineScope(SupervisorJob() + Dispatchers.Default + handler), объявленный полем компонента, нужен для фоновых задач, которые живут столько же, сколько компонент. Для него обязателен cancel() в @PreDestroy/DisposableBean.destroy(). GlobalScope даёт то же самое, но без родителя и без возможности отменить всё разом, и в Spring-приложении это оборачивается утечкой корутин при пересоздании контекста в тестах и невозможностью graceful shutdown.

⚠️ Грабли. runCatching { } вокруг suspend-кода ловит CancellationException, и корутина, которую отменили, продолжает работать, как будто ничего не случилось: выражение runCatching { fetch() }.getOrNull() ?: fallback() при отмене пойдёт в fallback(), потом в следующую операцию и так до конца тела. Поэтому правило такое: в catch (e: Exception) и в runCatching внутри корутин всегда перебрасывать CancellationException (if (e is CancellationException) throw e) или вызывать currentCoroutineContext().ensureActive() после catch. В ту же ловушку попадают retry-обёртки, написанные без учёта отмены. Пример выше с runCatching { geo.await() } корректен только потому, что supervisorScope при отмене родителя всё равно отменит сам блок на следующей точке приостановки, а в цикле так писать нельзя.

7.2 Диспетчеры

Диспетчер (CoroutineDispatcher) решает, на каком потоке выполнять resume, то есть где продолжится корутина после приостановки. От выбора диспетчера зависит, сколько корутин реально работает одновременно и где они ждут, когда потоков не хватает. Таблица ниже перечисляет диспетчеры, которые kotlinx.coroutines предлагает на JVM; внимательнее всего стоит прочитать строки про Default и IO, потому что они делят один пул:

Диспетчер Потоки Для чего
Dispatchers.Default max(2, nCPU) в общем CoroutineScheduler (work-stealing, собственный планировщик, не ForkJoinPool) CPU-bound код, по умолчанию для launch без указания
Dispatchers.IO Вид того же пула с лимитом параллелизма max(64, nCPU), свойство kotlinx.coroutines.io.parallelism Блокирующий I/O: JDBC, файлы, legacy-клиенты
Dispatchers.Unconfined Стартует в вызывающем потоке, после первой приостановки продолжается там, где произошёл resume Тесты, низкоуровневые адаптеры; в прикладном коде — почти никогда
Dispatchers.Main Только Android/JavaFX/Swing На бэкенде отсутствует
newSingleThreadContext / newFixedThreadPoolContext Свои потоки, нужно закрывать Изоляция (например, для не-thread-safe клиента)
Executor.asCoroutineDispatcher() Любой Executor Интеграция с существующими пулами и virtual threads
limitedParallelism(n) Вид над любым диспетчером с лимитом n Изоляция ресурсов: «не более 10 одновременных обращений к этой БД»

Ключевой механизм здесь в том, что Dispatchers.Default и Dispatchers.IO разделяют один пул потоков (CoroutineScheduler), а IO работает как вид на этот пул с лимитом 64. Поэтому withContext(Dispatchers.IO) из Default-корутины часто не требует переключения потока: работа продолжается на том же потоке, и меняется только счётчик. Dispatchers.IO.limitedParallelism(100) создаёт вид, который не ограничен лимитом 64. Концептуально за этим стоит диспетчер с неограниченным пулом, а IO и его виды берут из него потоки, каждый в пределах своего лимита, так что на пике возможны 64 + 100 потоков (Dispatchers.IO).

Лимит 64 оказывается самыми частыми граблями бэкенда на корутинах. Представьте сервис, который делает JDBC-запросы через withContext(Dispatchers.IO) { jdbcTemplate.query(...) }. При 200 одновременных запросах 64 потока заняты ожиданием БД, а остальные 136 корутин стоят в очереди IO-диспетчера, причём не в пуле соединений и не в БД, а в очереди задач Kotlin, где их не видит ни метрика Hikari, ни pg_stat_activity. Латентность растёт, а все дашборды остаются зелёными. Лечится это тремя способами: (а) выделить под БД отдельный limitedParallelism(hikariMaxPoolSize), и тогда очередь становится осмысленной и совпадает по размеру с пулом соединений; (б) поднять kotlinx.coroutines.io.parallelism; (в) использовать virtual threads как диспетчер, как в следующем примере:

val vtDispatcher = Executors.newVirtualThreadPerTaskExecutor().asCoroutineDispatcher()

suspend fun <T> blocking(block: () -> T): T = withContext(vtDispatcher) { block() }
// Каждая блокирующая операция выполняется на своём виртуальном потоке, и лимита 64 нет;
// блокировка на JDBC-сокете размонтирует VT с carrier (кроме pinning, см. главу 02).

Такой диспетчер работает на Java 21+ и убирает лимит, но не устраняет проблему pinning в synchronized внутри драйвера на JDK до 24 (глава 02, 02-modern-java.md) и ничего не даёт для CPU-bound кода. Кроме того, asCoroutineDispatcher() поверх per-task executor означает новый VT на каждый resume, что дёшево, но не бесплатно.

Dispatchers.Unconfined опасен своей неочевидной семантикой: после delay() корутина продолжится на потоке DefaultExecutor, а после await() на Netty-future окажется на event loop Netty. Поэтому в продакшене его берут, только если точно понимают, зачем.

📊 Цифры. Лимит у Dispatchers.IO составляет max(64, cores), у Dispatchers.Default он равен max(2, cores), а limitedParallelism над IO базовым лимитом не ограничен (Dispatchers.IO). В контейнере с cpu.limit = 2 Dispatchers.Default получает 2 потока, и CPU-тяжёлая сериализация JSON на нём заблокирует все корутины сервиса, включая те, что могли бы отдать ответ.

7.3 Кооперативная отмена

Отмена в корутинах кооперативная, и это означает, что остановить корутину снаружи нельзя: её можно только попросить, а остановится она сама, когда дойдёт до места, где проверяет этот запрос. Отмена устроена не так, как Thread.interrupt(): job.cancel() переводит Job в состояние Cancelling, а код узнаёт об этом только в точках приостановки из kotlinx.coroutines (delay, yield, withContext, await, send/receive, emit в flow), которые проверяют isActive и бросают CancellationException (Cancellation and timeouts). Поэтому цикл while (true) { compute() } без suspend-вызовов не отменится никогда. Чтобы сделать его отменяемым, есть три инструмента: isActive просто проверяет состояние, ensureActive() бросает исключение, если корутина отменена, а yield() проверяет состояние и заодно даёт поработать другим.

Блокирующий вызов внутри withContext(Dispatchers.IO) { socket.read() } тоже не отменяется, потому что поток сидит в read(), и CancellationException бросится только тогда, когда управление вернётся из блока. runInterruptible { } транслирует отмену в Thread.interrupt(), но помогает только коду, который умеет реагировать на interrupt: JDBC обычно не умеет, Socket.read не умеет, а Thread.sleep, BlockingQueue.take и NIO с InterruptibleChannel умеют.

withTimeout(ms) { } бросает TimeoutCancellationException, подкласс CancellationException, а withTimeoutOrNull возвращает null. Ловушка в том, что TimeoutCancellationException наследует CancellationException, и код внутри блока правильно трактует его как отмену, а вот код снаружи должен помнить, что для него это ошибка, а не отмена внешней корутины. Если пробросить такое исключение выше через suspend-границу, вышестоящие coroutineScope увидят CancellationException и тихо завершатся без ошибки. Точнее, kotlinx.coroutines специально обрабатывает этот случай и превращает «чужой» TimeoutCancellationException в обычную ошибку родителя, но поведение здесь сложное и зависит от версии (⚠️ детали не перепроверял для 1.10). Поэтому идиома такая: ловить TimeoutCancellationException сразу за withTimeout и превращать его в доменное исключение.

withContext(NonCancellable) { } остаётся единственным способом выполнить suspend-код в уже отменённой корутине, например откатить транзакцию или закрыть ресурс через suspend-клиент в finally. Без него любой suspend-вызов в finally отменённой корутины немедленно бросит CancellationException. В примере ниже так освобождается аренда ключа при обработке сообщения:

suspend fun process(msg: Message) {
    val lease = leaseClient.acquire(msg.key)
    try {
        handle(msg)
    } finally {
        withContext(NonCancellable) { leaseClient.release(lease) }   // выполнится даже при отмене
    }
}

7.4 Исключения в launch и async

Исключения в корутинах распространяются не по стеку вызовов, а по дереву Job, и поэтому привычный try/catch вокруг вызова ловит далеко не всё. Правил пять (Coroutine exceptions handling), и почти каждое хотя бы раз становилось причиной инцидента, потому что ошибка всплывает не там, где её ждут, или не всплывает вовсе. Ниже они перечислены по порядку, от launch и async к обработчику и отмене:

  1. В launch исключение немедленно отменяет родителя, если это не supervisor, поднимается до корня иерархии и там уходит в CoroutineExceptionHandler из контекста корневой корутины, а если его нет, то в Thread.uncaughtExceptionHandler, который только пишет лог и больше ничего не делает (в Android это крэш).
  2. В async исключение сохраняется в Deferred и бросается при await(). Однако если async запущен в обычном, не supervisor, scope, он всё равно отменяет родителя сразу, не дожидаясь await(), а await() потом просто вернёт то же исключение. Отсюда путаница вида «я обернул await() в try/catch, а корутина всё равно упала»: на самом деле упал родитель, а не await.
  3. CoroutineExceptionHandler вызывается только для корневых корутин, то есть для launch в scope, где в роли родителя выступает SupervisorJob или родителя нет вовсе, а также для детей supervisorScope. Обработчик, установленный на дочернем launch внутри coroutineScope, игнорируется, потому что ребёнок делегирует ошибку родителю.
  4. CancellationException игнорируется всеми обработчиками, поскольку это нормальный способ завершения.
  5. Если упало несколько детей, основным считается первое исключение, а остальные добавляются к нему в suppressed.

Пример ниже показывает второе и третье правило в действии; обратите внимание на то, что async в supervisor-scope не вызывает обработчик вовсе:

val handler = CoroutineExceptionHandler { ctx, e -> log.error("Uncaught in {}", ctx[CoroutineName], e) }
val scope = CoroutineScope(SupervisorJob() + Dispatchers.Default + handler)

scope.launch(CoroutineName("indexer")) { throw IllegalStateException("boom") }  // → handler

val d = scope.async { throw IllegalStateException() }   // тихо: SupervisorJob не отменяется, handler НЕ вызывается для async
// d.await() бросит. Если await не вызвать, исключение потеряно навсегда.

Из этого следует, что async без последующего await() в supervisor-scope превращается в чёрную дыру для ошибок. Поэтому для fire-and-forget используйте launch, а когда нужен результат, берите async и обязательно вызывайте await().

💡 На интервью. «Structured concurrency устроена как дерево Job: launch внутри scope получает родителя из контекста, а родитель ждёт своих детей и отменяет их, если отменили его самого или упал любой из них. coroutineScope работает по принципу fail-fast, и одна ошибка валит всё, а в supervisorScope ошибки детей независимы, но тогда каждый ребёнок должен обработать их сам, иначе они уйдут в CoroutineExceptionHandler. async не бросает исключение до await(), но в обычном scope всё равно немедленно отменяет родителя, поэтому try/catch вокруг await() не спасает, и здесь нужен supervisor».

8. Flow и Channel

Flow и Channel отвечают в kotlinx.coroutines за потоки значений, то есть за ситуации, когда suspend-функция должна отдать не один результат, а последовательность. Flow описывает холодный поток, который начинает вычисляться только при подписке и получает backpressure бесплатно, прямо из семантики suspend, а Channel — это горячий примитив, через который корутины передают друг другу данные. Путать их на бэкенде дорого: ошибка в контексте эмиссии роняет поток с IllegalStateException, а незакрытый канал вешает потребителя навсегда. Ниже разобраны cold Flow и его backpressure, правило context preservation и flowOn, exception transparency, горячие SharedFlow/StateFlow и сам Channel.

8.1 Cold Flow и backpressure через suspend

Flow<T> описывает cold-поток: flow { emit(x) } ничего не делает до вызова collect(), а каждый collect запускает строитель потока заново (Asynchronous Flow). Механически Flow — это интерфейс с одним методом suspend fun collect(collector: FlowCollector<T>), а FlowCollector содержит один метод suspend fun emit(value: T). Каждый оператор оборачивает upstream в новый Flow, и его collect вызывает collect у upstream с трансформирующим коллектором.

Благодаря этому backpressure здесь встроена в семантику: emit объявлен как suspend-функция и не возвращается, пока downstream не обработал элемент. Производитель не может опередить потребителя, потому что сам же его и вызывает, и по умолчанию всё происходит в одной корутине, последовательно. Поэтому никаких request(n), как в Reactive Streams, здесь нет; подробное сравнение дано в разделе 9.

Эту связь меняют три оператора. buffer(n) запускает upstream в отдельной корутине и ставит между ними канал ёмкости n, так что производитель может уйти вперёд на n элементов. conflate() даёт буфер размера 1 с перезаписью, и потребитель получает только последнее значение. collectLatest { } отменяет обработку текущего элемента, как только появляется новый (Asynchronous Flow).

8.2 Context preservation и flowOn

Context preservation означает, что flow { } обязан вызывать emit из того же контекста, в котором работает коллектор, и нарушение этого правила ловится во время выполнения. Так, flow { withContext(Dispatchers.IO) { emit(x) } } бросит IllegalStateException: Flow invariant is violated (Asynchronous Flow). Изменить контекст upstream можно только через flowOn(dispatcher), который под капотом делает то же, что buffer: запускает upstream в отдельной корутине с указанным диспетчером и ставит между ними канал. Поэтому flowOn меняет контекст только для операторов выше него (upstream), а downstream остаётся в контексте коллектора. В отличие от Reactor, где у publishOn/subscribeOn две оси, здесь ось одна и простая. Если же нужно эмитить из нескольких корутин или из обратных вызовов, берут channelFlow { send(x) } или callbackFlow { } с явным awaitClose { }.

8.3 Exception transparency

Exception transparency означает, что Flow не прячет исключения от того, кто стоит ниже по цепочке, и из этого вытекает несколько неочевидных ограничений на catch. Исключения из downstream, то есть из collect { }, не ловятся оператором catch { }, стоящим выше по цепочке, потому что catch обрабатывает только upstream. Цепочка flow.catch { }.collect { throw } упадёт мимо catch, и идиома здесь такая: перенести обработку в onEach { } перед catch, а collect() оставить пустым (Asynchronous Flow). Запрещено также ловить исключения внутри flow { try { emit() } catch ... } и продолжать эмитить, потому что это нарушает exception transparency, и библиотека такое детектирует, бросая IllegalStateException при попытке emit после исключения из downstream.

Для повторов и завершения есть свои операторы: retry/retryWhen пересоздают подписку на upstream, а onCompletion { cause -> } играет для flow роль finally.

8.4 Hot flows: SharedFlow, StateFlow

Горячий поток, в отличие от холодного, живёт независимо от подписчиков и раздаёт одни и те же значения всем, кто на него подписан. MutableSharedFlow<T>(replay, extraBufferCapacity, onBufferOverflow) живёт и без подписчиков, а его emit объявлен как suspend и приостанавливается, когда буфер полон и onBufferOverflow = SUSPEND, то есть backpressure здесь идёт от самого медленного подписчика. tryEmit работает без suspend и при переполнении возвращает false. Режимы DROP_OLDEST/DROP_LATEST нужны для событий, где медленный подписчик не должен тормозить всех остальных. MutableStateFlow<T>(initial) работает как conflated SharedFlow с replay = 1 и дедупликацией по equals, так что повторное присвоение равного значения не эмитится, а value доступно синхронно. На бэкенде StateFlow подходит для конфигурации и фича-флагов с hot reload, а SharedFlow годится для внутренней шины событий внутри процесса. Помните только, что у такой шины нет персистентности и гарантий доставки при рестарте, так что Kafka она не заменяет.

Превратить cold в hot в заданном scope позволяют shareIn(scope, started, replay) и stateIn(scope, started, initial), а SharingStarted.WhileSubscribed(stopTimeout) останавливает upstream, когда подписчиков не остаётся.

8.5 Channel

Channel<T> служит примитивом передачи значений между корутинами и по смыслу похож на BlockingQueue, только send/receive у него suspend. Каналы бывают четырёх видов: RENDEZVOUS (ёмкость 0, по умолчанию), BUFFERED (по умолчанию 64, свойство kotlinx.coroutines.channels.defaultBuffer), UNLIMITED и CONFLATED. Channel горячий и одноразовый: каждый элемент получает только один потребитель, то есть fan-out работает «из коробки», в отличие от SharedFlow, где каждый подписчик получает всё. На бэкенде каналы используют для worker pool (produce { } плюс N launch { for (x in channel) }), для actor-подобных паттернов с единственным владельцем изменяемого состояния и для конвейеров с ограничением параллелизма. Channel нужно закрывать через close(), иначе for на принимающей стороне висит вечно, а неполученные элементы в BUFFERED-канале при отмене теряются, и для их очистки существует onUndeliveredElement.

Разница между Flow и Channel сводится к тому, что Flow декларативный и холодный и описывает, «что вычислить», а Channel императивный и горячий и описывает, «как передать». Поэтому в API выставляют Flow, в том числе как возвращаемый тип Spring-контроллера и репозитория, а для внутренней координации используют Channel. Если нужен Flow с fan-out на несколько корутин-обработчиков, берут flatMapMerge(concurrency) или produceIn(scope) с N потребителями.

9. Корутины, Reactor и virtual threads

На JVM сейчас есть три способа писать неблокирующий по смыслу код, и Kotlin-разработчику приходится выбирать между корутинами, Reactor и виртуальными потоками Java 21+. Все три решают одну задачу, а различаются тем, где хранится состояние ожидания, как выглядит код и во что обходятся ошибки, отмена и блокирующие вызовы. В разделе сначала собрана сравнительная таблица, затем сделаны честные выводы по парам, а в конце сформулированы правила для блокирующих вызовов внутри корутин.

9.2 Выбор модели параллельности

Таблица показывает различия, но не отвечает на вопрос, что выбрать, поэтому ниже подходы сравниваются попарно: сначала корутины против Reactor, затем корутины против виртуальных потоков, а в конце сказано, чего корутины не делают вовсе и от каких проблем они не спасают, как бы хорошо ни был написан код.

Корутины vs Reactor. По сути корутины дают Reactor без цепочек: kotlinx-coroutines-reactor предоставляет awaitSingle(), asFlow(), mono { } и flux { }, и Spring WebFlux пользуется ими для suspend-контроллеров, внутри которых работает Mono из mono { }. Выигрывает прежде всего читаемость, потому что условие, цикл и try/catch пишутся как обычный код. Backpressure проще, но менее гибкая: onBackpressureDrop из коробки нет, а вместо него есть conflate/buffer(DROP_OLDEST). Операторов у Flow меньше, чем у Flux, и часть из них до сих пор нестабильна: debounce во всех четырёх перегрузках помечен @FlowPreview (kotlinx.coroutines API: debounce), и то же относится к sample, flattenMerge и produceIn. На практике это значит, что компилятор потребует @OptIn(FlowPreview::class), а сигнатура может измениться в минорной версии, поэтому в библиотечном коде такие операторы лучше не выставлять наружу. Reactor Context соединяется с CoroutineContext через ReactorContext, и для suspend-контроллеров Spring делает это автоматически, а для трассировки нужны PropagationContextElement и Hooks.enableAutomaticContextPropagation() (Spring Framework: Coroutines).

Корутины vs virtual threads. Виртуальные потоки решают проблему «блокирующий код держит поток» без изменения кода и без suspend в сигнатурах, и для Java-проекта на Spring MVC это очевидный выбор. Корутины же дают то, чего у VT нет или что появилось там позже: structured concurrency в стабильном API (статус StructuredTaskScope в Java см. в главе 02), Flow как модель стриминга с backpressure, отмену как first-class концепцию и приостановку без копирования стека. Поэтому в Kotlin-проекте на WebFlux корутины остаются лучшим выбором, а в Kotlin-проекте на MVC с Java 21 разумно обрабатывать запросы на VT и добавлять корутины там, где нужна оркестрация, например fan-out на 5 клиентов с таймаутом и отменой. Оба подхода можно и совместить: если заменить Dispatchers.IO на VT-диспетчер (раздел 7.2), лимит 64 исчезает.

Что корутины не делают. Они не ускоряют CPU-bound код и не защищают от блокировки: Thread.sleep, JDBC, synchronized с ожиданием и CompletableFuture.get() внутри корутины блокируют поток диспетчера. На Dispatchers.Default в контейнере с 2 CPU это два потока, так что одного блокирующего вызова в неудачном месте хватает, чтобы половина сервиса встала.

9.3 Блокирующие вызовы внутри корутин

Блокирующий вызов внутри корутины занимает поток диспетчера целиком, и поскольку потоков у диспетчера мало, несколько таких вызовов останавливают весь сервис, причём ни одна метрика пулов этого не покажет. Чтобы этого не случилось, достаточно соблюдать три правила: не блокировать поток в suspend-функции, не вызывать runBlocking внутри корутин и ловить блокировки в тестах:

  1. Suspend-функция не должна блокировать поток, и это конвенция библиотеки: suspend в сигнатуре означает «безопасно вызывать из любого диспетчера». Если внутри есть блокирующий код, оборачивайте его в withContext(Dispatchers.IO) или в VT-диспетчер внутри функции, а не требуйте этого от вызывающего.
  2. runBlocking служит мостом из блокирующего мира в suspend, и его место в main, в тестах, в @Scheduled-методах MVC-приложения и в callback Java-библиотеки. Никогда не вызывайте его внутри корутины, внутри suspend-функции, внутри WebFlux-обработчика или на Netty event loop: он блокирует поток диспетчера, а если ожидаемая корутина должна выполниться на том же потоке (single-thread диспетчер, event loop), получается взаимоблокировка. Классический пример: runBlocking { } в @Transactional-методе, который вызывается из suspend-контроллера. Под малой нагрузкой такой код работает, а под большой виснет, когда все потоки Dispatchers.Default заняты runBlocking, а корутины внутри них ждут свободного потока того же пула.
  3. Для детекции подходит BlockHound с интеграцией kotlinx-coroutines-debug: в тестах любой блокирующий вызов на потоке диспетчера бросает BlockingOperationError. Зависшие корутины помогают искать -Dkotlinx.coroutines.debug и DebugProbes.dumpCoroutines() (раздел 23).

Пример ниже показывает второе правило в коде: сначала контроллер, который зовёт runBlocking и виснет под нагрузкой, а затем адаптер, который прячет блокирующий сервис за собственным диспетчером, так что вызывающий код о блокировке ничего не знает.

// ❌ Дедлок под нагрузкой
@RestController
class BadController(private val service: LegacyService) {
    @GetMapping("/x")
    suspend fun x(): Dto = runBlocking { service.fetch() }   // блокирует поток Netty/Default
}

// ✅ Блокирующий сервис работает на диспетчере для блокировок, и вызывающий не знает деталей
@Service
class LegacyAdapter(private val service: LegacyService) {
    private val blockingDispatcher = Executors.newVirtualThreadPerTaskExecutor().asCoroutineDispatcher()
    suspend fun fetch(): Dto = withContext(blockingDispatcher) { service.fetch() }
}

10. Kotlin + Spring

Spring поддерживает Kotlin официально, но сам фреймворк написан на Java и рассчитывает на открытые классы, конструкторы без аргументов и привязку транзакции к потоку, а Kotlin по всем трём пунктам ведёт себя иначе. Поэтому связка Kotlin + Spring держится на компиляторных плагинах и на нескольких правилах, нарушение которых не ломает компиляцию, а тихо отключает @Transactional или размазывает транзакцию по потокам. Раздел разбирает плагины all-open и no-arg, конструкторную инъекцию, suspend в контроллерах, транзакции на suspend-функциях, корутинные репозитории Spring Data и @ConfigurationProperties на data class.

10.1 kotlin-spring (all-open) и kotlin-jpa (no-arg)

Оба плагина нужны потому, что классы Kotlin по умолчанию final, а Spring оборачивает бины в прокси через CGLIB-подклассы для @Transactional, @Cacheable, @Async и @Configuration (см. главу 09, 09-spring-core.md). Final-класс подклассить нельзя, поэтому без плагина @Transactional на Kotlin-классе либо падает при старте с Cannot subclass final class, либо, что хуже, тихо игнорируется для final-методов. Компиляторный плагин all-open делает класс и его члены open, если класс помечен одной из указанных аннотаций, а kotlin-spring подключает его с готовым пресетом, который знает @Component, @Async, @Transactional, @Cacheable, @SpringBootTest, а через мета-аннотации ещё и @Configuration, @Controller, @RestController, @Service и @Repository (All-open compiler plugin). Подключается он строкой id("org.jetbrains.kotlin.plugin.spring").

Важно понимать, что именно плагин не открывает. Он не трогает классы без этих аннотаций, но здесь есть тонкость: сервис, созданный @Bean-методом, у которого на классе нет @Service, зато на методе стоит @Transactional, откроется, потому что @Transactional входит в список, а вот класс с одним только @Retryable не откроется, и эту аннотацию придётся добавить в allOpen { annotation("...") }. @Bean-методы в @Configuration открываются, потому что @Configuration мета-аннотирован @Component.

Плагин no-arg генерирует синтетический конструктор без аргументов для классов с указанной аннотацией. Вызвать этот конструктор из Kotlin или Java нельзя, только рефлексией, и это ровно то, что нужно Hibernate. kotlin-jpa подключает этот плагин с пресетом из @Entity, @Embeddable и @MappedSuperclass (No-arg compiler plugin). По умолчанию сгенерированный конструктор не выполняет инициализаторы свойств, так что val createdAt: Instant = Instant.now() после того, как Hibernate создаст объект, останется null, пока его не заполнят из БД; обычно именно это и нужно, а если нужны инициализаторы, их включают через noArg { invokeInitializers = true }.

Кроме того, Hibernate требует, чтобы сущности не были final, иначе он не сможет строить lazy-прокси: @ManyToOne(fetch = LAZY) создаёт подкласс через ByteBuddy. kotlin-spring про @Entity не знает, поэтому добавьте allOpen { annotation("jakarta.persistence.Entity"); annotation("jakarta.persistence.MappedSuperclass"); annotation("jakarta.persistence.Embeddable") }; start.spring.io для Kotlin+JPA генерирует ровно это.

10.2 Конструкторная инъекция и lateinit

В Kotlin зависимости бина идиоматично объявлять параметрами первичного конструктора с private val, и Spring внедряет их без единой аннотации, а зависимости бина видны прямо в сигнатуре и не прячутся в полях. Выглядит это так, на примере сервиса переводов, которому нужны репозиторий счетов, клиент главной книги и лимит из конфигурации:

@Service
class TransferService(
    private val accounts: AccountRepository,
    private val ledger: LedgerClient,
    @Value("\${transfer.limit}") private val limit: BigDecimal,   // $ экранируем
) {
    @Transactional
    fun transfer(cmd: TransferCommand): TransferResult { /* ... */ return TransferResult.Ok }
}

Когда конструктор один, @Autowired не нужен (Spring 4.3+). Spring читает параметры конструктора, значения по умолчанию и nullability через kotlin-reflect, поэтому параметр val cache: CacheManager? = null становится опциональной зависимостью, аналогом Optional<>/@Autowired(required = false), а значение по умолчанию у параметра используется, если подходящего бина нет (Spring Boot: Kotlin support). Без kotlin-reflect в classpath ничего этого не будет, но Boot добавляет его через стартер.

lateinit var с @Autowired на поле тоже работает, но у такого способа два недостатка: тесты теряют простоту, потому что объект уже нельзя создать конструктором, а зависимости бина прячутся. Оправдан он в тестовых классах (@Autowired lateinit var mockMvc: MockMvc) и в @Configuration с циклическими зависимостями, которых лучше не иметь вовсе.

Self-invocation создаёт ту же проблему, что и в Java: вызов this.transactionalMethod() из другого метода того же бина минует прокси, и @Transactional не срабатывает (глава 09). В Kotlin всё осложняется тем, что private-методы прокси не перехватывает, поскольку CGLIB не может их переопределить, и @Transactional на private fun тихо ничего не делает. Компилятор Kotlin об этом не предупредит, а Spring выдаст warning в логе только для @Transactional на не-public методах, и то лишь при определённых настройках.

10.3 suspend в контроллерах и Flow как ответ

Контроллер Spring может быть suspend-функцией, и тогда фреймворк сам запускает корутину на каждый запрос и превращает её результат в ответ. Spring WebFlux (5.2+) и Spring MVC (6.1+) поддерживают suspend fun в @RequestMapping-методах, а также возвращаемые Deferred<T> и Flow<T> (Spring Framework: Coroutines). Механика в WebFlux такая: InvocableHandlerMethod распознаёт suspend-метод по последнему параметру Continuation в JVM-сигнатуре и вызывает его через CoroutinesUtils.invokeSuspendingFunction, которая оборачивает вызов в mono { } из kotlinx-coroutines-reactor. Корутина стартует на Netty event loop, причём диспетчер здесь по сути Dispatchers.Unconfined, и resume происходит там, куда придёт ответ, а ReactorContext из Mono попадает в CoroutineContext. Поэтому блокирующий вызов в suspend-контроллере блокирует event loop Netty, а с ним и все запросы на этом потоке.

Если контроллер возвращает Flow<T>, он превращается во Flux<T> и дальше в streaming-ответ, который в зависимости от produces будет application/x-ndjson или text/event-stream (SSE). Backpressure от клиента проходит по цепочке TCP window → Netty → Reactor request(n) → Flow через asPublisher и доходит до emit, так что производитель приостановится, когда клиент перестанет читать.

В Spring MVC suspend работает через DeferredResult и async-режим Servlet: поток запроса освобождается, а корутина выполняется на Dispatchers.Unconfined и продолжается там, где произошёл resume. Если же в MVC включены virtual threads (spring.threads.virtual.enabled=true), выигрыш от suspend спорен, потому что проще писать блокирующий код на VT. Поэтому в сервисе на MVC и Java 21 используйте suspend только там, где нужна оркестрация (coroutineScope плюс N async).

В функциональном стиле маршруты описывают через coRouter { GET("/users/{id}", handler::get) }, где обработчик объявлен как suspend fun get(req: ServerRequest): ServerResponse, а suspend-фильтр пишут через CoWebFilter. У WebClient для корутин есть client.get().uri(...).retrieve().awaitBody<User>(), awaitExchange { } и bodyToFlow<T>().

10.4 @Transactional на suspend-функциях

Вопрос о транзакциях на suspend-функциях важнее остальных в этом разделе, потому что ответ на него зависит от менеджера транзакций, а ошибка не видна ни в тестах, ни при старте. Начиная со Spring Framework 6.1 @Transactional на suspend fun поддерживается для реактивного TransactionManager (R2DBC, MongoDB reactive): TransactionInterceptor распознаёт suspend-метод, оборачивает его в mono { }, применяет TransactionalOperator и возвращает результат корутине. Программный вариант даёт TransactionalOperator.executeAndAwait { } и Flow<T>.transactional(operator) (Spring Framework: Programmatic transaction management, Coroutines).

А вот чего нет, так это корректной работы @Transactional на suspend fun с JPA/JDBC (PlatformTransactionManager). JDBC-транзакция привязана к потоку через TransactionSynchronizationManager, то есть через ThreadLocal, а корутина после первой приостановки может продолжиться на другом потоке, и тогда Connection останется на старом. Формально документация Spring вообще не обещает @Transactional на suspend-функциях: в разделе «Coroutines» прямо сказано, что «transactions on Coroutines are supported via the programmatic variant of the Reactive transaction management», и показаны только TransactionalOperator.executeAndAwait и Flow<T>.transactional(operator) (Spring Framework: Coroutines). Раздел про декларативные транзакции демонстрирует @Transactional на классе с методами, которые возвращают Mono/Flow, и реактивный R2dbcTransactionManager, а про suspend там нет ни слова (Declarative transaction annotations). На практике TransactionInterceptor действительно распознаёт suspend-метод по последнему параметру Continuation и уводит его в реактивную ветку, но это деталь реализации, а не контракт, и при PlatformTransactionManager вы получите либо ошибку на старте прокси, либо транзакцию, «размазанную» по потокам. Поэтому считайте связку suspend + JPA неподдерживаемой и не спорьте с этим. Выходов три: (а) не делать метод suspend, а вызывать его из suspend-кода через withContext(Dispatchers.IO) или VT-диспетчер, и тогда вся транзакция пройдёт на одном потоке; (б) перейти на R2DBC ради действительно неблокирующего стека; (в) вызывать TransactionTemplate.execute { } внутри withContext, что по сути то же самое, что (а), только явно. Третий вариант показан ниже на примере размещения заказа:

@Service
class OrderService(private val tx: TransactionTemplate, private val repo: OrderRepository) {
    private val db = Executors.newVirtualThreadPerTaskExecutor().asCoroutineDispatcher()

    suspend fun place(cmd: PlaceOrder): OrderId = withContext(db) {
        tx.execute { repo.save(cmd.toEntity()).id }!!   // JDBC-транзакция целиком на одном VT
    }
}

Связка suspend + @Transactional + JPA даёт самую частую ошибку Kotlin+Spring-проектов на WebFlux: в тестах транзакция «работает», потому что всё выполняется на одном потоке runBlocking, а в проде коммит уходит на другом соединении, чем запросы.

10.5 Spring Data: Kotlin extensions и CoroutineCrudRepository

Spring Data даёт Kotlin-коду два вида поддержки: extension-функции, которые убирают Optional и Class<T> из вызовов, и корутинные репозитории для реактивных хранилищ. spring-data-commons даёт CrudRepository.findByIdOrNull(id), а spring-data-jdbc/jdbc-core даёт JdbcOperations.queryForObject<T>() с reified-типом. Для реактивных модулей (R2DBC, MongoDB, Redis, Cassandra) есть CoroutineCrudRepository<T, ID> с suspend fun findById(id): T?, fun findAll(): Flow<T> и derived-методами вроде suspend fun findByEmail(email: String): User? и fun findByStatus(s: Status): Flow<User> (Spring Data: Coroutines). Под капотом работают те же реактивные репозитории с awaitSingleOrNull()/asFlow(). Для JPA CoroutineCrudRepository нет, и это правильно: JPA блокирующий, и обёртка в suspend только скрыла бы блокировку.

10.6 @ConfigurationProperties с data class

Constructor binding означает, что Spring Boot создаёт объект конфигурации через конструктор, передавая в него значения свойств, и для Kotlin это идиоматичный способ описать настройки неизменяемым data class, потому что значения по умолчанию и nullability берутся прямо из объявления. Ниже так описана конфигурация платёжного шлюза с вложенным блоком аутентификации:

@ConfigurationProperties("payments.gateway")
data class GatewayProperties(
    val url: URI,
    val timeout: Duration = Duration.ofSeconds(5),
    val retries: Int = 3,
    val auth: Auth,
) {
    data class Auth(val clientId: String, val secret: String)
}

Когда конструктор один, @ConstructorBinding не нужен (Boot 3.0+), значения по умолчанию из Kotlin работают через kotlin-reflect, а nullable-тип делает свойство опциональным (Spring Boot: Kotlin support). Регистрируют такой класс через @EnableConfigurationProperties(GatewayProperties::class) или @ConfigurationPropertiesScan. Для валидации ставят @Validated на класс и @field:NotBlank на свойства, и use-site target @field: для Bean Validation на data class обязателен, иначе аннотация уйдёт на параметр конструктора, где Hibernate Validator её не увидит. Для @ConfigurationProperties с constructor binding Boot 3.x поддерживает и параметры, но для JPA/Jackson годятся только @field:/@get:. В Kotlin 2.2 изменились правила умолчания для use-site target (param-property), и Boot рекомендует флаг -Xannotation-default-target=param-property, чтобы убрать предупреждения (Spring Boot: Kotlin support).

11. Kotlin + JPA: типовые проблемы

Общие механизмы JPA/Hibernate разобраны в главе 12 (12-spring-data-jpa-hibernate.md), а здесь речь пойдёт только о том, что добавляет к ним Kotlin. Суть проблемы в том, что JPA-сущность по своей природе изменяема, открыта для наследования и определяется идентичностью, а Kotlin подталкивает к final-классам, val и data class с равенством по значению. В результате идиоматичный Kotlin-код в сущностях ломает lazy loading, теряет элементы в HashSet и роняет NPE там, где компилятор обещал безопасность. Ниже разобраны final и no-arg, причины, по которым data class не годится в сущности, особенности lazy-прокси, расхождение nullable-типов с DDL и несколько мелочей.

11.1 Final-классы и конструктор без аргументов

Два требования Hibernate к классу сущности, открытость и конструктор без аргументов, уже разобраны в 10.1, и здесь стоит только напомнить, чем кончается их нарушение. Без kotlin-jpa вы получите InstantiationException/No default constructor for entity, а без all-open на @Entity Hibernate не сможет создать lazy-прокси для @ManyToOne(LAZY) и тихо загрузит связь eager (Hibernate 6 пишет в лог warning, похожий на HHH000305, о final-классе; ⚠️ код сообщения не проверял). Симптомом служат N+1 запросов, которых «не должно быть».

11.2 data class в роли сущности

Желание объявить сущность как data class понятно, потому что это экономит строки, но у этого решения четыре независимых недостатка, и каждый из них сам по себе ломает работу с JPA, так что исправить один и оставить остальные не получится. Все четыре вытекают из того, что компилятор генерирует для data class, и разобраны ниже по порядку:

  1. equals/hashCode по всем полям. До persist у сущности id = null, а после него появляется сгенерированный. Если сущность до сохранения лежит в HashSet, например в @OneToMany Set<OrderLine>, то после присвоения id её hashCode изменится, и set.contains(line) вернёт false, потому что элемент «потерян» в неправильном бакете. Классический совет Влада Михалчи (глава 12) состоит в том, чтобы делать equals по бизнес-ключу или по id с константным hashCode. Data class этого не позволяет без ручного переопределения, а если переопределять вручную, непонятно, зачем тогда data class.
  2. hashCode трогает lazy-поля. hashCode() data class вызывает hashCode() каждого поля, включая @ManyToOne(LAZY) customer, и это инициализирует прокси, а вне сессии даёт LazyInitializationException. То же самое происходит с toString(): строка log.debug("saved {}", order) вытянет все связи, а на @OneToMany уйдёт в рекурсию Order → lines → order → ... и закончится StackOverflowError.
  3. val-свойства и мутация. Hibernate меняет состояние через рефлексию или field access, обходя val, и dirty checking работает по полям, так что val ему не мешает. Но код, который читает val, считает значение неизменным, а оно может измениться после refresh()/merge(). Ещё хуже copy(), который создаёт новый объект с тем же id в состоянии detached: save(copy) вызовет merge, а если у копии есть @Version, возможен OptimisticLockException на ровном месте.
  4. copy обходит инварианты, а componentN для сущности бессмысленны.

Идиоматичная Kotlin-сущность поэтому выглядит как обычный класс с var, у которого equals построен по id или бизнес-ключу, hashCode константный или тоже по бизнес-ключу, а toString не касается связей. Так выглядит сущность заказа, написанная по этим правилам:

@Entity
@Table(name = "orders")
class Order(
    @Column(nullable = false) var customerId: Long,
    @Enumerated(EnumType.STRING) @Column(nullable = false) var status: OrderStatus = OrderStatus.NEW,
) {
    @Id @GeneratedValue(strategy = GenerationType.SEQUENCE, generator = "orders_seq")
    var id: Long? = null                      // nullable до persist — честно отражает жизненный цикл

    @Version var version: Long = 0

    @OneToMany(mappedBy = "order", cascade = [CascadeType.ALL], orphanRemoval = true)
    var lines: MutableList<OrderLine> = mutableListOf()

    override fun equals(other: Any?) = other is Order && id != null && id == other.id
    override fun hashCode() = 31                  // константа: стабилен до и после persist; Vlad Mihalcea, гл. 12
    override fun toString() = "Order(id=$id, status=$status)"
}

Объявление id: Long? = null вместо lateinit или 0L остаётся единственным вариантом, который честен с системой типов, потому что до persist идентификатора действительно нет.

11.3 Lazy loading и equals в Kotlin-сущностях

Hibernate строит lazy-прокси как подкласс сущности, и от того, как код проверяет тип, зависит, распознает он прокси или нет. Для lazy-прокси order.customer имеет класс Customer$HibernateProxy$..., который наследует Customer, поэтому проверка customer is Customer даёт true, customer::class возвращает класс прокси, а customer.javaClass == Customer::class.java даёт false. when (entity) { is Customer -> } работает корректно. А вот с equals ситуация тоньше, и зависит она от того, кто его написал. Для data class компилятор генерирует проверку if (other !is Order) return false, то есть instanceof, и прокси её проходит, а вот кастомный equals со сравнением other.javaClass != javaClass прокси отбросит, потому что класс у него другой. Поэтому пишите other is Order, а не сравнение классов, а для случаев, когда нужен реальный класс, используйте Hibernate.unproxy()/Hibernate.getClass().

Smart cast на var-свойстве сущности не работает, потому что var может измениться между проверкой и использованием, и компилятор потребует локальную переменную: val c = order.customer; if (c != null) c.name. Это не грабли, а корректное поведение, хотя при миграции с Java оно раздражает.

11.4 Nullable-типы и @Column(nullable)

Nullable-тип свойства в Kotlin и NULL/NOT NULL у колонки в БД описывают одно и то же, но проверяются независимо, и когда они расходятся, NPE появляется в коде, который компилятор считал безопасным. Kotlin-тип и DDL — это два независимых контракта. Если объявить var email: String, а колонка при этом email VARCHAR NULL, Hibernate запишет в поле null, и первый же email.length даст NPE в месте, которое компилятор считал безопасным. В обратную сторону, при var phone: String? с NOT NULL, компилятор будет заставлять проверять то, что никогда не бывает null. Отсюда правило: тип свойства должен совпадать с nullable колонки, а @Column(nullable = false) для non-null типов нужно ставить явно, потому что Hibernate использует его в hbm2ddl и schema validation, а hibernate-validator использует для @NotNull-проверки до flush. Плагин kotlin-jpa автоматически этого не делает.

Для @Id с генерацией и для @ManyToOne(optional = false) есть два варианта: объявлять Long?/Customer? на время до persist или писать lateinit var customer: Customer. Второй вариант работает, потому что Hibernate заполняет поле рефлексией до первого чтения, но lateinit не даёт @Column(nullable = false) автоматически.

11.5 Прочие особенности Kotlin-сущностей

Напоследок четыре мелочи, каждая из которых ломается в своей точке: встраиваемые классы, проекции, коллекции в связях и перечисления. Ни одна из них не заслуживает отдельного подраздела, но каждую проще знать заранее, чем потом разбирать по логам и трассировкам стека в разгар инцидента:

  • @Embeddable value class не поддерживается, потому что для него нужен класс с полями, а @JvmInline value class в качестве типа колонки подключается только через AttributeConverter и с упаковкой.
  • Проекции, будь то data class OrderSummary(val id: Long, val total: BigDecimal) в JPQL SELECT new ... или интерфейсные проекции Spring Data, как раз то место, где data class уместен, потому что проекция — это не сущность.
  • kotlin.collections.List в @OneToMany не годится, так как Hibernate требует изменяемую коллекцию и подменяет поле своими PersistentBag/PersistentSet. Объявляйте MutableList/MutableSet, иначе, пока Hibernate ещё не подменил коллекцию, add в Kotlin-коде бросит UnsupportedOperationException.
  • Enum с @Enumerated(STRING) в Kotlin ничем не отличается от Java, разве что вместо values() стоит пользоваться entries.

12. Сериализация и конфигурация

Сериализация на границе сервиса оказывается ещё одним местом, где объекты создаются в обход конструктора, и от выбора библиотеки зависит, сохранятся ли гарантии Kotlin-типов при десериализации. Для бэкенда на Spring выбирают между jackson-module-kotlin, который учит Jackson понимать Kotlin через рефлексию, и kotlinx.serialization, который генерирует код сериализации компиляторным плагином. Ниже разобраны оба варианта, их грабли и сводная таблица для выбора.

12.1 jackson-module-kotlin

Без этого модуля Jackson обращается с Kotlin-классом как с Java-бином и ломается на первом же идиоматичном DTO. Ему требуется конструктор без аргументов или @JsonCreator с @JsonProperty на каждом параметре, он не понимает val без сеттера (сериализует, но не десериализует) и ничего не знает о значениях по умолчанию и nullability. jackson-module-kotlin (KotlinModule, который Boot регистрирует автоматически, если модуль есть в classpath) через kotlin-reflect читает имена параметров первичного конструктора, подставляет значения по умолчанию для отсутствующих полей, бросает MissingKotlinParameterException/DatabindException при null в non-null тип и с версии 2.17 поддерживает value class (jackson-module-kotlin). Текущие линии модуля на момент проверки: 3.x для Jackson 3 и 2.21.x для Jackson 2 (та же страница). Spring Boot 4 переходит на Jackson 3, поэтому проверяйте, какой модуль подтягивает ваш BOM.

Даже с модулем остаются пять мест, где поведение расходится с ожиданиями:

  • Non-null примитив и явный null в JSON. Если не включён DeserializationFeature.FAIL_ON_NULL_FOR_PRIMITIVES, вместо ошибки подставится 0/false (README модуля). В финтехе это критично, потому что amount: Long из {"amount": null} станет 0.
  • is-префикс. Свойство val isActive: Boolean Jackson по Java-bean конвенции видит как геттер isActive() и сериализует как "active", а десериализовать его по имени isActive без @JsonProperty("isActive") не сможет. Kotlin-модуль отчасти это исправляет (KotlinFeature.StrictNullChecks, обработка is-полей в новых версиях; ⚠️ поведение зависит от версии модуля), но безопаснее избегать is-префикса в DTO или ставить аннотацию явно.
  • Sealed-иерархии. Полиморфизм настраивается через @JsonTypeInfo + @JsonSubTypes, как в Java, потому что модуль не выводит подтипы автоматически (в README сказано: «still requires @JsonTypeInfo»).
  • kotlin-reflect обязателен, и при первом обращении к классу он заметно медленнее Java-рефлексии, поскольку строит метаданные KClass; в GraalVM native image ему нужны reachability metadata.
  • Значения по умолчанию и null. Для val retries: Int = 3 отсутствие поля даст 3, а явный null даст ошибку для non-null типа или null для Int?; KotlinFeature.NullIsSameAsDefault меняет это поведение на «null = default».

12.2 kotlinx.serialization

kotlinx.serialization решает ту же задачу без рефлексии: компиляторный плагин (kotlin("plugin.serialization")) генерирует для @Serializable-классов serializer(), и код сериализации известен уже на этапе компиляции (kotlinx.serialization). Поддерживаются форматы JSON, Protobuf, CBOR, HOCON и Properties (та же страница). Плюсов у такого подхода четыре: не нужен kotlin-reflect, sealed-полиморфизм поддерживается нативно через classDiscriminator, value class сериализуется без упаковки, а поведение детерминировано, что полезно для native image, где рефлексия доставляет много боли. Spring MVC/WebFlux поддерживают KotlinSerializationJsonHttpMessageConverter, и Boot включает его автоматически, если kotlinx-serialization-json есть в classpath, но с приоритетом ниже Jackson для классов без @Serializable, из-за чего иногда возникает вопрос «почему это поле сериализовалось иначе».

Для бэкенда у kotlinx.serialization есть и минусы. Он не сериализует произвольные Java-типы, и для java.time, BigDecimal и UUID нужны контекстуальные сериализаторы, часть которых есть в kotlinx-serialization через @Contextual, а часть приходится писать руками. У него нет аналога @JsonView, @JsonFilter и mixins, а экосистема (Spring Data, OpenAPI-генераторы, Kafka-сериализаторы) думает на Jackson. Поэтому для Spring-сервиса по умолчанию стоит брать Jackson, а kotlinx оставить для мультиплатформенных моделей, native image и Kafka-событий с sealed-иерархиями и жёстким контролем формата. 13. Тестирование

Общие практики тестирования собраны в главе 42 (42-testing.md), а здесь речь идёт только об инструментах, специфичных для Kotlin. Нужны они потому, что привычный стек Java-тестов спотыкается о final-классы, object, suspend-функции и корутины с их собственным временем. Ниже разобраны MockK как замена Mockito, runTest с виртуальным временем и Kotest с его стилями спецификаций и матчерами.

13.1 MockK

MockK — это библиотека заглушек, написанная под Kotlin, и берут её потому, что у Mockito в Kotlin-коде четыре слабых места. Mockito к Kotlin применим, но упирается в final-классы (для них нужен mockito-inline, который в Mockito 5 включён по умолчанию), в то, что any() возвращает null для non-null параметров, из-за чего matcher бросает NullPointerException (это лечится mockito-kotlin), в невозможность подменять заглушкой object и top-level функции и в отсутствие поддержки suspend. MockK решает все эти проблемы (MockK), и основные его возможности такие:

  • mockk<Repo>() создаёт строгую заглушку, у которой незаписанный вызов бросает MockKException. mockk(relaxed = true) возвращает значения по умолчанию (0, "", пустые коллекции, вложенные relaxed-заглушки), а relaxUnitFun = true делает relaxed только Unit-функции. Последний вариант служит компромиссом: не нужно писать justRun для каждого void-метода, но методы, возвращающие значения, остаются строгими.
  • every { repo.find(any()) } returns user записывает поведение обычного вызова, а для suspend есть coEvery { client.fetch(any()) } returns dto, coVerify(exactly = 1) { client.fetch(42) } и coJustRun { }. Без co-варианта компилятор просто не даст вызвать suspend-функцию внутри every.
  • spyk(realObject) создаёт частичную заглушку, mockkObject(Singleton) подменяет заглушкой object или companion, mockkStatic("com.acme.UtilsKt") и mockkStatic(::topLevelFun) подменяют моками top-level и extension-функции, а mockkConstructor(Foo::class) перехватывает Foo().
  • slot<T>() вместе с capture(slot) захватывает аргументы, а answers { firstArg<Long>() * 2 } вычисляет ответ по ним.
  • unmockkAll() нужно вызывать в @AfterEach, потому что статические и объектные заглушки глобальны и утекают между тестами.

Для Spring есть springmockk с @MockkBean/@SpykBean вместо @MockitoBean (Spring Boot: Kotlin support). За MockK приходится платить двумя вещами. Заглушки он создаёт медленнее Mockito, потому что использует inline-инструментацию ByteBuddy и читает Kotlin-метаданные. Кроме того, relaxed-заглушки маскируют ошибки: если в проекте relaxed включён по умолчанию, забытый стаб вернёт 0, и тест пройдёт. Пример ниже проверяет, что перевод сверх лимита отклоняется и до главной книги не доходит:

class TransferServiceTest {
    private val accounts = mockk<AccountRepository>()
    private val ledger = mockk<LedgerClient>(relaxUnitFun = true)
    private val service = TransferService(accounts, ledger, limit = BigDecimal("1000"))

    @Test
    fun `rejects transfer above limit`() = runTest {
        coEvery { accounts.balance(any()) } returns BigDecimal("5000")
        val result = service.transfer(TransferCommand(from = 1, to = 2, amount = BigDecimal("1500")))
        result shouldBe TransferResult.LimitExceeded
        coVerify(exactly = 0) { ledger.post(any()) }
    }
}

13.2 runTest и виртуальное время

Виртуальное время позволяет тестировать код с задержками и таймаутами, не дожидаясь их по-настоящему: тестовый планировщик просто перематывает часы вперёд. В kotlinx-coroutines-test это делает runTest { }, который запускает тело на StandardTestDispatcher с виртуальным временем, так что delay(1.hours) проходит мгновенно, а таймаут самого теста по умолчанию равен 60 с (свойство kotlinx.coroutines.test.default_timeout) (runTest). Дочерние корутины выполняются только тогда, когда тест приостанавливается на join, await, advanceUntilIdle() или runCurrent(). С UnconfinedTestDispatcher дети стартуют сразу, «как раньше» в runBlockingTest.

Главные грабли здесь в том, что виртуальное время работает только для диспетчеров с TestCoroutineScheduler, и withContext(Dispatchers.IO) { delay(5.seconds) } внутри runTest займёт реальные 5 секунд (та же страница). Поэтому код, который жёстко завязан на Dispatchers.IO/Default, с виртуальным временем не протестировать. Выход в том, чтобы внедрять CoroutineDispatcher через конструктор (class Service(private val io: CoroutineDispatcher = Dispatchers.IO)) и подставлять в тестах StandardTestDispatcher(testScheduler). Для Flow подходит turbine, библиотека для проверок вида test { awaitItem() }, или toList() с backgroundScope.launch.

runBlocking в тестах допустим, когда в коде нет delay и виртуальное время не нужно, как в интеграционных тестах с Testcontainers. Тем не менее runTest предпочтительнее, потому что он ещё и падает, если в тесте утекли незавершённые корутины.

13.3 Kotest

Kotest — это полноценный тестовый фреймворк для Kotlin со своим исполнителем, и выбирать его стоит, понимая, что именно он даёт сверх JUnit и во что обходится. В нём 9 стилей спецификаций (FunSpec, StringSpec, BehaviorSpec с given/when/then, DescribeSpec, FreeSpec и т.д.) (Kotest testing styles), матчеры (shouldBe, shouldThrow<T>, shouldContainExactly), property-based testing (checkAll, Arb), data-driven тесты (withData) и расширения для Spring (kotest-extensions-spring) и Testcontainers. В Kotest тело теста компилируется в suspend-лямбду, поэтому delay и coEvery вызываются внутри них без runTest. Матчеры можно подключить и к JUnit 5 (kotest-assertions-core отдельно), и это распространённый компромисс: JUnit 5 остаётся исполнителем со стабильной интеграцией в Gradle, IDE и Spring, а от Kotest берут матчеры и Arb для property-based тестов.

Платить за Kotest приходится собственным исполнителем (Gradle-плагин или JUnit Platform engine) и собственным жизненным циклом (beforeSpec, IsolationMode), с которым @SpringBootTest уживается через расширение и иногда требует настройки. Spring-слайсы и @MockkBean работают, но отлаживать контекст сложнее, чем в JUnit. Поэтому команды с Java-бэкграундом обычно берут JUnit 5, MockK и Kotest-assertions.

14. Сборка, интероп, миграция, производительность

Этот раздел собирает практические вопросы, с которыми команда сталкивается, когда Kotlin уже выбран: как настроить сборку, что сломается на границе с Java, в каком порядке переводить существующий код и сколько всё это стоит во время выполнения и при компиляции. Ответы на них определяют, будет ли переход на Kotlin постепенным и безболезненным или превратится в месяц борьбы со сборкой и NPE на стыках. Ниже разобраны Gradle Kotlin DSL, интероп-грабли при вызове Kotlin из Java, стратегия миграции по частям и цифры производительности.

14.1 Gradle Kotlin DSL

Gradle Kotlin DSL означает, что скрипт сборки пишется на Kotlin в файле build.gradle.kts, а не на Groovy. Типичная сборка Spring-сервиса на Kotlin подключает компиляторные плагины, задаёт toolchain и флаги компилятора и добавляет Kotlin-специфичные зависимости. Ниже приведён такой build.gradle.kts, и смотреть в нём стоит на совпадение версий Kotlin-плагинов, на флаги compilerOptions и на блок allOpen для JPA:

plugins {

    kotlin("plugin.spring") version "2.4.20"
    kotlin("plugin.jpa") version "2.4.20"
    kotlin("plugin.serialization") version "2.4.20"     // если kotlinx.serialization
    id("org.springframework.boot") version "4.1.1"       // текущая GA на 2026-09-21; см. главу 10
    id("io.spring.dependency-management") version "1.1.7"
}

kotlin {
    jvmToolchain(21)
    compilerOptions {
        freeCompilerArgs.addAll("-Xjsr305=strict", "-Xannotation-default-target=param-property")
        allWarningsAsErrors = true
    }
}

    annotation("jakarta.persistence.Entity")
    annotation("jakarta.persistence.MappedSuperclass")
    annotation("jakarta.persistence.Embeddable")

    implementation("org.jetbrains.kotlinx:kotlinx-coroutines-reactor")

Версии Kotlin-плагинов должны совпадать с версией kotlin("jvm"), а Boot-плагин автоматически выравнивает kotlin.version в dependency management (Spring Boot: Kotlin support). Скрипты .kts компилируются на этапе конфигурации, поэтому включите org.gradle.configuration-cache=true и org.gradle.caching=true в gradle.properties, иначе каждая сборка будет тратить секунды на компиляцию скриптов. Kotlin daemon (kotlin.daemon.jvmargs=-Xmx2g) запускается отдельным процессом, и в CI ему часто не хватает памяти; симптомом служит сообщение Kotlin compile daemon is not used и откат на in-process компиляцию, из-за которого растёт время сборки.

14.2 Проблемы вызова Kotlin из Java

Когда Kotlin-код вызывают из Java, компилятор Java видит только то, что реально лежит в байткоде, и многие удобства Kotlin для него исчезают или выглядят странно. Ниже перечислены места, где это проявляется чаще всего; подробная механика каждого разобрана в разделе 15:

  • Checked exceptions. Kotlin не различает checked и unchecked исключения, поэтому Java-код, вызывающий Kotlin-метод, который бросает IOException, не сможет написать catch (IOException e): компилятор Java скажет «exception is never thrown». Чтобы это исправить, на Kotlin-методе нужен @Throws(IOException::class) (Calling Kotlin from Java). В обратную сторону Kotlin спокойно игнорирует checked-исключения Java-методов: Files.readString() без try/catch компилируется, и IOException прилетит во время выполнения туда, где её не ждут (Calling Java from Kotlin).
  • Top-level функции становятся статическими методами класса FileNameKt; @file:JvmName("Utils") позволяет его переименовать, а @file:JvmMultifileClass объединяет несколько файлов в один класс.
  • Значения по умолчанию из Java не видны, потому что компилятор генерирует один метод со всеми параметрами и синтетический foo$default. @JvmOverloads генерирует перегрузки, но только справа налево: для f(a, b = 1, c = 2) появятся f(a), f(a, b) и f(a, b, c), но не f(a, c).
  • Companion из Java вызывается как Foo.Companion.bar(), для статического вызова нужен @JvmStatic, const val даёт статическую константу, а @JvmField даёт поле без геттера.
  • Unit Java видит как void у обычных функций, но в generic-позиции (Function1<T, Unit>) это kotlin.Unit.INSTANCE, который нужно явно возвращать из Java-лямбды.
  • SAM-конверсия Kotlin-лямбды в Java-интерфейс с одним методом происходит автоматически, а для Kotlin-интерфейсов работает только с fun interface. В обратную сторону Java-лямбда, переданная в параметр типа (A) -> B, становится Function1<A, B>, и для этого в classpath Java-модуля нужен kotlin.jvm.functions.
  • value class в сигнатуре приводит к манглированию имени метода, и для вызова из Java обязателен @JvmName.
  • suspend добавляет параметр Continuation, поэтому из Java такой метод вызывают через future { } из kotlinx-coroutines-jdk8 или через CompletableFuture-адаптеры на стороне Kotlin.
  • Nullability. Kotlin генерирует @NotNull/@Nullable (org.jetbrains.annotations) на публичных сигнатурах, и хотя компилятор Java их не проверяет, IDE и NullAway/Error Prone их учитывают.

14.3 Миграция Java → Kotlin по частям

Переводить существующий Java-сервис на Kotlin целиком не нужно, потому что оба языка компилируются в одном модуле: плагин kotlin-jvm сначала компилирует Kotlin, после чего javac видит Kotlin-классы, а Kotlin видит Java-исходники того же модуля напрямую. Благодаря этому миграцию можно вести по слоям, начиная с самых безопасных, и обычно порядок получается такой:

  1. Начать с тестов. Риск здесь нулевой, команда учит язык, а MockK и Kotest вводятся постепенно.
  2. Перейти к новым DTO, конфигурации и value-объектам, то есть к data class, @ConfigurationProperties и sealed-типам для результатов операций.
  3. Затем взяться за сервисный слой, по одному классу, конвертером IDE (J2K) и с обязательным ревью. J2K щедро расставляет !! и оставляет platform types, и каждый !! становится кандидатом на замену ?: или nullable-типом. Java-границы при этом стоит аннотировать JSpecify (@NullMarked на пакет), чтобы Kotlin видел точные типы.
  4. JPA-сущности переводить последними или не переводить никогда, потому что выигрыш здесь минимален, а грабли максимальны (раздел 11). Если всё же конвертировать, то в обычные классы, а не в data class.
  5. Корутины вводить отдельным этапом, после языка. Не стоит примешивать runBlocking к коду, который вызывается из Java; сначала нужно провести асинхронную границу на уровне контроллеров и потребителей.

Смешанная кодовая база стабильно живёт годами, и полная конвертация не должна быть целью, если legacy-код никто не трогает.

14.4 Производительность и размер байткода

Вопрос о производительности Kotlin распадается на три: сколько стоит сгенерированный код во время выполнения, насколько больше становится байткод и насколько медленнее идёт компиляция. На первый вопрос ответ короткий, а два других требуют цифр и оговорок о том, где они измерены, а где оценены по опыту, и ниже разобраны все три по порядку.

Среда выполнения. Для эквивалентного кода он идентичен Java, потому что классы те же и JIT тот же. Но у Kotlin есть собственные накладные расходы, о которых стоит знать:

  • Intrinsics.checkNotNullParameter на входе в публичные методы выполняет null-проверку, которую JIT удаляет на горячем пути; отключить её можно флагами -Xno-param-assertions -Xno-call-assertions, но делать это не рекомендуется.
  • Лямбды, переданные в inline-функции, не дают ни одной выделения памяти, а не-inline лямбда становится объектом Function. Начиная с Kotlin 2.0.0 лямбды на JVM по умолчанию генерируются через invokedynamic/LambdaMetafactory, как в Java: опция -Xlambdas=indy существовала с 1.5.0, а в 2.0.0 стала поведением по умолчанию. Бинарники от этого меньше, но такие лямбды не сериализуемы, не поддерживаются экспериментальным reflect() API и хуже читаются в toString(). Вернуть анонимные классы можно флагом -Xlambdas=class для модуля или аннотацией @JvmSerializableLambda на конкретной лямбде (What's new in Kotlin 2.0.0). Для бэкенда из этого следует практический вывод: если лямбда попадает туда, где её сериализуют (кэш с Java-сериализацией, задачи Hazelcast/Ignite, Spark), то после апгрейда на 2.0 вы получите NotSerializableException, и лечится это аннотацией.
  • for (i in 0 until n) и for (x in list) компилируются в обычные циклы без итераторов и выделений памяти для IntRange и массивов, а вот list.indices и withIndex() вне for выделяют IndexedValue на каждый элемент.
  • Упаковка происходит в Int?, List<Int> и у value class в generic-позиции, где значение становится java.lang.Integer, тогда как IntArray/LongArray остаются примитивными массивами.
  • when по String компилируется в hashCode + equals, как Java switch, а по sealed-типу в цепочку instanceof.
  • Корутины выделяют state machine на каждый suspend-вызов и Result-обёртки, что примерно соответствует выделениям памяти в цепочках CompletableFuture; при миллионах корутин в секунду это заметно в allocation profile (глава 44).
  • kotlin-reflect при первом обращении к KClass добавляет секунды к старту больших приложений (Jackson, Spring constructor binding), а в Spring Boot native image для него обязательны hints.

Размер байткода. Kotlin генерирует больше классов, чем Java: state machine на каждую suspend-функцию, WhenMappings на каждый файл с when по enum, Kt-классы, объекты Companion и синтетические $default-методы. В типичном Kotlin-модуле .class-файлов на 20–40 % больше, чем в эквивалентном Java-модуле (⚠️ оценка по опыту, систематически не измерялось). Для jar это единицы процентов, и заметно это только в native image, где растёт время компиляции, и на Android, который не наша тема.

Компиляция. K2 (2.0+) быстрее K1, но kotlinc по-прежнему в 1.5–3 раза медленнее javac на сравнимом объёме кода (⚠️ порядок величины по опыту команд; JetBrains заявляла ускорение K2 без паритета с javac). Инкрементальная компиляция работает, узким местом остаётся kapt, который заменяют KSP или компиляторными плагинами, а Gradle build cache и configuration cache обязательны. Kotlin 2.4.20 предлагает экспериментальный native-image компилятора для быстрого старта (What's new in Kotlin EAP).

15. Интероперабельность с Java

В разделе 14.2 интероп-грабли были перечислены списком, а здесь разобрана механика каждой из них. Подробности нужны потому, что в банковском монолите на Kotlin+Spring граница с Java проходит не «где-то», а через каждый вызов Spring, Hibernate, драйвера JDBC, клиента ISO 8583 и внутренней библиотеки, написанной пять лет назад на Java 8. Раздел проходит по platform types и местам, где через них прорывается NPE, по аннотациям nullability и статусу JSpecify, по тому, как Kotlin-код выглядит из Java, по аннотациям @Jvm*, checked exceptions, SAM-конверсиям, коллекциям на границе и по Unit, Nothing и DSL.

15.1 Platform types и источники NPE

Platform type — не настоящий тип системы типов Kotlin: он лишь обозначает «отсутствие информации» о том, может ли значение быть null. Компилятор записывает его как T!, но написать String! в коде нельзя, его можно только увидеть в сообщении об ошибке и в IDE. Правила работы с ним такие (Calling Java from Kotlin):

  • присвоение T! в T разрешено, и компилятор вставляет Intrinsics.checkNotNullExpressionValue(v, "expr");
  • присвоение T! в T? разрешено без всяких проверок;
  • вывод типа (val x = javaCall()) даёт T! и откладывает проверку до первого использования в non-null контексте.

Прорывается NPE через platform types в трёх точках, и ниже они перечислены по убыванию частоты в продакшене.

1. Generics. List<String> из Java превращается в (Mutable)List<String!>!, и проверка вставляется на контейнер, но не на элементы. Цикл for (s in javaList) s.length не содержит ни одной проверки, и NPE прилетит из s.length без имени переменной в сообщении. Хуже всего обстоит дело с Map<String, String> из Java, где map["k"].length компилируется, потому что get вернул String!, как в примере с заголовками запроса:

// Java: Map<String,String> headers() { ... }
val h = client.headers()
val len = h["X-Request-Id"].length     // компилируется! NPE в рантайме
val len2 = h["X-Request-Id"]?.length   // так правильно — приведите тип явно

Лечится это тем, что границу объявляют явно: val h: Map<String, String?> = client.headers(), и с этого момента компилятор снова работает на вас.

2. Массивы и varargs. String[] из Java становится Array<(out) String!>!. Если пройти по такому массиву и передать элементы в Kotlin-функцию с non-null параметром, checkNotNullParameter сработает уже внутри вызываемой функции, и стек укажет не на то место, где null появился, а на то, где его использовали.

3. Лямбды и обратные вызовы. Java-интерфейс Consumer<T> в Kotlin выглядит как Consumer<T!>, и лямбда Consumer { it.length } не получает проверки на входе. Типичный банковский случай выглядит как обратный вызов драйвера очередей, который раз в сутки отдаёт сообщение с null-телом.

🔧 Под капотом. Проверки checkNotNullExpressionValue вставляются только в Kotlin-коде и только на явных или выведенных non-null позициях, так что объявление типа переменной остаётся единственным рычагом. Отсюда практика: на каждом Java-клиенте в проекте держать тонкий Kotlin-адаптер, где типы объявлены явно и nullable, чтобы дальше по коду ходили уже честные типы. Обходится это в 20 строк на клиент и убирает целый класс инцидентов.

15.2 Аннотации nullability и статус JSpecify

Только аннотации nullability позволяют передать Kotlin из Java-кода информацию о том, может ли значение быть null, и от того, какое семейство аннотаций использует библиотека, зависит, получит Kotlin строгие типы или platform types. Kotlin распознаёт nullability из нескольких семейств аннотаций (Calling Java from Kotlin): org.jetbrains.annotations, JSpecify (@Nullable, @NonNull, @NullMarked, @NullUnmarked), JSR-305 (javax.annotation.*), FindBugs, Eclipse JDT, Lombok @NonNull, аннотации Android и RxJava 3. Таблица ниже показывает для основных семейств, на какую область действует аннотация и что нужно, чтобы Kotlin воспринимал её строго:

Семейство Область действия Как включить строгость
JetBrains @Nullable/@NotNull элемент по умолчанию строго
JSpecify @NullMarked пакет / класс / модуль по умолчанию строго с Kotlin 2.1
JSR-305 @ParametersAreNonnullByDefault пакет -Xjsr305=strict, иначе только warning
JSR-305 @TypeQualifierDefault custom по вашей аннотации -Xjsr305=under-migration:strict
Lombok @NonNull параметр по умолчанию

JSpecify — это совместная спецификация Google, JetBrains, Oracle, Uber и других компаний, и главное её отличие от JSR-305 в том, что значение по умолчанию задаётся на уровне области: @NullMarked на package-info.java объявляет весь пакет non-null-by-default, а @Nullable расставляется точечно. Именно эту модель Spring Framework 7 применил ко всему своему API (глава 09). Практическое следствие такое: после апгрейда на Spring 7 Kotlin-код, который раньше компилировался благодаря platform types, начинает выдавать ошибки типов, и это хорошо, потому что каждая такая ошибка была потенциальным NPE.

Для собственного Java-кода миграция идёт в четыре шага: (1) добавить зависимость org.jspecify:jspecify; (2) поставить @NullMarked в каждый package-info.java; (3) собрать Kotlin-модуль и разобрать ошибки; (4) не ставить @NonNull на каждый элемент, потому что это шум, а по умолчанию всё и так non-null.

⚠️ Грабли. -Xjsr305=strict меняет типы у чужих библиотек, поэтому после включения флага сборка может сломаться в десятках мест, и часть ошибок окажется ложной, потому что библиотека размечена неточно. Включайте флаг на новом модуле, а не на всём монолите сразу, а для точечного смягчения есть -Xjsr305=@com.acme.MyNullable:warn.

15.4 @JvmStatic, @JvmOverloads, @JvmField, @JvmName, @JvmDefault

Аннотации семейства @Jvm* управляют тем, как Kotlin-объявление выглядит в байткоде, и нужны они всякий раз, когда ваш код будут вызывать из Java. Пример ниже собирает их в одном файле с утилитами для комиссий; комментарии справа показывают, что в итоге увидит Java:

@file:JvmName("PaymentUtils")          // класс PaymentUtils вместо PaymentUtilsKt
@file:JvmMultifileClass                // склеить несколько файлов в один класс

package com.acme.payments

class Fees(val base: BigDecimal) {
    companion object {
        @JvmStatic fun of(v: String) = Fees(BigDecimal(v))   // Fees.of("1.00") из Java
        @JvmField val ZERO = Fees(BigDecimal.ZERO)           // Fees.ZERO — поле, не геттер
        const val CURRENCY = "RUB"                            // Fees.CURRENCY — static final
    }

    @JvmOverloads
    fun withSurcharge(pct: Int = 0, fixed: BigDecimal = BigDecimal.ZERO): Fees = /* ... */ this
}

@JvmName("parseAmountStrict")          // иначе конфликт стирания с другой перегрузкой
fun parse(raw: String): BigDecimal = BigDecimal(raw)

Отдельно стоит разобрать @JvmDefault. Kotlin-интерфейсы умеют объявлять методы с телом, но на JVM это исторически реализовывалось через класс DefaultImpls, а сам интерфейсный метод оставался абстрактным, так что Java-класс, реализующий такой интерфейс, обязан был реализовать все методы, включая те, у которых в Kotlin есть тело. Аннотация @JvmDefault и флаги -Xjvm-default появились для того, чтобы генерировать настоящие default-методы JVM. В современных версиях аргумент -Xjvm-default=all (или all-compatibility для бинарной совместимости со старыми сборками) стал нормой для библиотек, которые потребляет Java, а сама аннотация @JvmDefault устарела в пользу флага. Если Java-класс, реализующий ваш Kotlin-интерфейс, требует «реализовать» метод, у которого есть тело, значит, вы забыли флаг.

📊 Цифры. Каждый аргумент со значением по умолчанию удваивает набор синтетики: появляется метод f$default(a, b, c, mask, marker) с битовой маской mask, в которой по биту на параметр. При 8 параметрах со значениями по умолчанию это один дополнительный метод с пятью аргументами, а не 256 перегрузок, так что обходится это дёшево. @JvmOverloads же генерирует ровно N перегрузок, по числу параметров со значениями по умолчанию, и только «хвостом»: для f(a, b = 1, c = 2) появятся f(a), f(a, b) и f(a, b, c), но не f(a, c).

15.5 Checked exceptions и @Throws

Из всех дыр на границе с Java эта самая недооценённая, потому что она не ломает компиляцию Kotlin-кода и проявляется только у Java-потребителя. Checked-исключений в Kotlin нет, и сигнатура Kotlin-функции ничего не говорит о том, что она бросает. Атрибут Exceptions в байткод не пишется, если только на функции не стоит @Throws. Вот как это выглядит на функции, читающей конфигурацию, и на Java-коде, который пытается её вызвать:

// Kotlin
fun readConfig(path: Path): String = Files.readString(path)   // бросает IOException

// Java — не компилируется:
try {
    String s = ConfigKt.readConfig(p);
} catch (IOException e) { }   // error: exception IOException is never thrown in the corresponding try block

Java-компилятор видит метод, который формально ничего не бросает, и запрещает ловить IOException в try. Разработчику на Java остаётся одно из двух: ловить Exception целиком или не ловить ничего, и тогда IOException уходит наверх, минуя всю обработку ошибок сервиса. Лечится это аннотацией @Throws:

@Throws(IOException::class)
fun readConfig(path: Path): String = Files.readString(path)

После этого в байткоде появляется Exceptions: IOException, и Java-код компилируется как обычно (Calling Kotlin from Java).

В обратную сторону проблема симметрична: Kotlin-код не обязан обрабатывать checked-исключения Java. Files.readString(path) в Kotlin компилируется без try/catch, и IOException полетит наверх, туда, где её никто не ждёт. В Java компилятор служил вам чеклистом, а в Kotlin его нет, и компенсировать это приходится статическим анализом. Правда, правила detekt TooGenericExceptionCaught/SwallowedException этот случай не покрывают, поэтому помогают только code review и явная политика: любой I/O-вызов оборачивается в доменную ошибку на границе адаптера.

Для библиотек отсюда вытекает правило: @Throws обязателен на каждом публичном Kotlin-методе, который вызывается из Java и может бросить checked-исключение. Это касается и suspend-функций: в @Throws(IOException::class) suspend fun ... аннотация попадёт в сигнатуру, хотя для корутинного вызова из Kotlin она ничего не значит.

15.6 SAM-конверсии в обе стороны

SAM-конверсия (single abstract method) позволяет передать лямбду туда, где ожидается интерфейс с одним абстрактным методом, и на границе Kotlin и Java она работает по-разному в каждом из трёх направлений. Ниже разобраны все три: Java-интерфейс, принимающий Kotlin-лямбду, Kotlin-интерфейс, принимающий Kotlin-лямбду, и функциональный тип Kotlin, который вызывают из Java.

Java → Kotlin. Java-интерфейс с одним абстрактным методом (Runnable, Comparator, Consumer, ExecutorService.submit(Callable)) принимает Kotlin-лямбду напрямую, как в executor.submit { doWork() }, и компилятор создаёт для неё объект-адаптер. Ловушка возникает, когда у Java-метода есть перегрузки, принимающие разные SAM-интерфейсы (submit(Runnable) и submit(Callable<T>)). Kotlin выбирает перегрузку по типу результата лямбды, так что executor.submit { 42 } уйдёт в Callable, а executor.submit { println() } в Runnable, и при рефакторинге тела лямбды перегрузка молча меняется. Лечится это явным Runnable { } или Callable { }.

Kotlin → Kotlin. Обычный Kotlin-интерфейс SAM-конверсию не получает, и для неё нужен fun interface, как у правила антифрода в примере:

fun interface RiskRule { fun check(tx: Transaction): Boolean }
val rule = RiskRule { it.amount > BigDecimal(100_000) }     // работает благодаря fun interface

Kotlin → Java. Функциональный тип Kotlin (A) -> B в байткоде становится kotlin.jvm.functions.Function1<A, B>. Из Java такой параметр принимает лямбду, но эта лямбда обязана вернуть значение, а для (A) -> Unit значением будет kotlin.Unit.INSTANCE, и выглядит это так:

service.onEvent(e -> { log.info("{}", e); return Unit.INSTANCE; });   // придётся писать так

Поэтому API, предназначенное Java-потребителям, объявляйте не через функциональные типы, а через fun interface с осмысленным именем. Тогда из Java это будет обычная лямбда без Unit.INSTANCE, а из Kotlin тоже лямбда.

15.7 Коллекции на границе Kotlin и Java

В разделе 5.1 было сказано, что Kotlin List даёт только read-only view, и на границе с Java это перестаёт быть теорией, потому что Java никаких read-only интерфейсов не видит и спокойно вызывает мутирующие методы. Возьмём агрегат заказа, который в Kotlin отдаёт строки только на чтение, и Java-код, который с ним работает:

class OrderAggregate(val lines: List<Line>)   // read-only в Kotlin

// Java
List<Line> lines = aggregate.getLines();
lines.add(new Line(...));   // компилируется и, скорее всего, сработает

Java видит java.util.List, то есть интерфейс с методом add. Сработает ли add, зависит от того, что лежит под капотом: с ArrayList, который получается из map, filter и toMutableList, он сработает; с Arrays$ArrayList, который получается из listOf(a, b, c), add бросит UnsupportedOperationException, хотя set пройдёт; а с EmptyList/Collections.singletonList будет исключение. Выходит, что поведение зависит от того, как список был построен, и меняется при рефакторинге Kotlin-кода, которого Java-потребитель не видит.

Защититься от этого можно на трёх уровнях, которые различаются ценой: 1. toList() на выходе даёт копию, но выделяет её на каждый вызов геттера, что дорого в цикле; 2. Collections.unmodifiableList(...) или java.util.List.copyOf(...) дают обёртку или копию с честным UnsupportedOperationException; 3. kotlinx.collections.immutable PersistentList даёт настоящую неизменяемость со структурным разделением, но из Java это опять java.util.List с исключениями на мутацию.

У проблемы есть и обратная сторона. Java-метод, принимающий List<T>, в Kotlin имеет тип (Mutable)List<T>!, и вы можете передать туда результат listOf(), а если Java-код внутри вызовет add, вы получите UnsupportedOperationException в чужом коде. Поэтому передавайте ArrayList(list), если у Java-метода есть хоть намёк на мутацию, например если он называется fill, collectInto или addAll.

15.8 Unit, Nothing и Kotlin-DSL из Java

Последние три особенности границы связаны с типами, которых в Java нет, и с DSL, который из Java почти невозможно использовать. Unit — это настоящий объект-синглтон: в позиции возврата обычной функции компилятор ставит void, но в generic-позиции Unit остаётся классом. Отсюда правило: не объявляйте generic-API с Unit, если его будет вызывать Java.

Nothing — тип без единого значения, который компилятор считает подтипом всех типов. Его используют, чтобы сказать «функция не возвращается» (error(), TODO(), exitProcess()), а также в List<Nothing>/emptyList(). Из Java он выглядит как void (или как Object с @NotNull в generic-позиции), и Java не видит, что метод не возвращается.

Вызывать Kotlin-DSL из Java больно и обычно бессмысленно. DSL строится на лямбдах с receiver вроде fun api(block: ApiBuilder.() -> Unit), а в байткоде это Function1<ApiBuilder, Unit>, так что из Java вызов выглядит так:

PaymentsKt.api(builder -> {
    builder.group(b -> { b.get("/users"); return Unit.INSTANCE; });
    return Unit.INSTANCE;
});

Читаемость здесь нулевая, this нет, а @DslMarker не работает. Поэтому для Java-потребителей либо дублируйте DSL классическим строителем (ApiBuilder.create().group(...).build()), либо не отдавайте DSL в Java вообще. Это относится и к coRouter { }, и к Gradle Kotlin DSL: если возникло желание «вызвать наш DSL из Java-модуля», это сигнал, что граница модулей проведена неправильно.

💡 На интервью. «Граница Kotlin/Java асимметрична. При переходе из Java в Kotlin теряется nullability, отсюда platform types, и NPE прилетает в точке присваивания, а для generic и массивов вообще без проверок. При переходе из Kotlin в Java теряются checked-исключения, для которых нужен @Throws, аргументы со значениями по умолчанию, для которых нужен @JvmOverloads, и статика, для которой нужен @JvmStatic, а value class из-за mangling вообще недоступен. На практике я держу тонкий Kotlin-адаптер на каждый Java-клиент с явно объявленными nullable-типами и ставлю @Jvm*-аннотации на всё публичное API, которое читают из Java».

16. Корутины: реализация в JVM

Раздел 6 объяснил устройство корутин на уровне идеи, а этот спускается на уровень байткода и библиотечной механики, то есть туда, откуда берутся вопросы senior-интервью и причины реальных инцидентов. Знать эти подробности нужно, чтобы читать javap и трассировки стека, правильно оборачивать callback-API, понимать цену переключения диспетчеров и не терять корутины через GlobalScope. Ниже разобраны сгенерированный байткод, мост к callback-API через suspendCancellableCoroutine, цена диспетчеров и limitedParallelism, варианты CoroutineStart, различие Job и SupervisorJob, структурированная отмена по шагам и обработка исключений.

16.1 Байткод suspend-функций

В разделе 6.3 state machine была показана в терминах Kotlin, а здесь посмотрим на то же самое на уровне байткода, то есть на то, что вы увидите в javap -c или в «Show Kotlin Bytecode» и о чём спрашивают на интервью. Возьмём в качестве исходника функцию перевода с тремя точками приостановки:

suspend fun transfer(from: Long, to: Long, amount: BigDecimal): Receipt {
    val src = accounts.load(from)           // suspension point 1
    val dst = accounts.load(to)             // suspension point 2
    return ledger.post(src, dst, amount)    // suspension point 3 (tail call)
}

С этой функцией компилятор делает семь вещей:

  1. Меняет сигнатуру. Она становится transfer(JJLjava/math/BigDecimal;Lkotlin/coroutines/Continuation;)Ljava/lang/Object;, то есть к трём исходным параметрам добавляется Continuation, а возвращается Object.
  2. Генерирует класс-континуацию. Это вложенный класс TransferService$transfer$1 extends ContinuationImpl с полями result: Object, label: int, L$0, L$1, L$2 (spilled-переменные ссылочного типа), J$0 (spilled long) и ссылкой на this внешнего объекта. Имена L$n/J$n/I$n и есть «спиллинг» локальных переменных: всё, что живёт через точку приостановки, переезжает со стека JVM в поля объекта.
  3. В начале метода либо повторно использует существующую континуацию, когда метод вызывают повторно на resume, либо создаёт новую: INSTANCEOF TransferService$transfer$1 IFEQ newContinuation ... проверка (label & Integer.MIN_VALUE) != 0 ... Старший бит label служит маркером того, что «эта континуация принадлежит именно этому вызову», и позволяет отличить resume от вложенного вызова с чужой континуацией.
  4. Строит tableswitch по label, в котором по одной ветке на каждую точку приостановки плюс ветка 0 для входа. Ветка default бросает IllegalStateException("call to 'resume' before 'invoke' with coroutine"), и это сообщение иногда всплывает в логах при ручной работе с низкоуровневым API.
  5. После каждого suspend-вызова сравнивает результат с маркером: DUP INVOKESTATIC IntrinsicsKt.getCOROUTINE_SUSPENDED() IF_ACMPNE continueHere ARETURN // вернули COROUTINE_SUSPENDED — приостановились
  6. На resume вызывает ResultKt.throwOnFailure(result), прежде чем достать значение, и именно так исключение, случившееся в приостановленной операции, перебрасывается в точку вызова и создаёт иллюзию обычного try/catch.
  7. Оптимизирует tail call. Последний вызов ledger.post(...) хвостовой, поэтому компилятор не выделяет под него отдельного состояния, а передаёт нашу континуацию дальше, и в javap точек приостановки окажется на одну меньше, чем в исходнике.

Концептуально разницу «до и после» показывает схема ниже: сверху фрейм на стеке потока, который живёт, пока поток занят, а снизу объект в куче, в поля которого переехали те же переменные.

ДО (исходный фрейм на стеке потока)
  stack: [this, from, to, amount, src, dst]     ← живёт, пока поток занят

ПОСЛЕ (объект в куче)
  TransferService$transfer$1 {
      label = 2
      L$0 = this
      L$1 = src          ← spilled
      L$2 = amount       ← spilled
      J$0 = to           ← spilled (long не помещается в L$)
      completion = <родительская континуация>
      result = <значение или Result.failure>
  }
  поток свободен

Из этой схемы вытекают четыре практических следствия, и на интервью их нужно уметь назвать:

  • Размер корутины складывается из размера spilled-переменных и заголовка объекта и составляет десятки–сотни байт. Отсюда и сравнение «миллион корутин» против «тысячи потоков», ведь поток резервирует под стек 512 КБ–1 МБ.
  • Чем больше локальных переменных живёт через приостановку, тем толще объект. Длинная suspend-функция с 20 локальными переменными и 5 приостановками превращается в один жирный объект, который держит ссылки на всё подряд и не даёт GC собрать промежуточные результаты. Это реальный источник утечек памяти в долгоживущих корутинах, и лечится он тем, что функцию разбивают на мелкие suspend-функции, у каждой из которых spilled-набор меньше и живёт короче.
  • suspend в интерфейсе нельзя по-человечески реализовать из Java, потому что сигнатура требует Continuation, а корректно реализовать его вручную почти невозможно. Поэтому для Java-потребителей на стороне Kotlin делайте fun transferAsync(...): CompletableFuture<Receipt> = scope.future { transfer(...) } (kotlinx-coroutines-jdk8).
  • Выделение памяти не на каждый вызов. Если suspend-функция ни разу не приостановилась, потому что все вложенные вызовы сразу вернули значение, например при попадании в кэш, объект континуации всё равно создаётся, но живёт до конца вызова и умирает в молодом поколении. Escape analysis такие объекты обычно не устраняет, поскольку они передаются в другой метод, и поэтому «дешёвая suspend-функция в цикле на миллион итераций» оставляет миллион объектов в allocation profile.

16.2 suspendCoroutine и suspendCancellableCoroutine для callback-API

Мост к callback-API нужен, чтобы вызвать из корутины старый асинхронный клиент, который сообщает о результате через обратный вызов, и получить результат как обычное возвращаемое значение suspend-функции. Это самая практичная часть низкоуровневого API, потому что почти в каждом банковском сервисе есть legacy-клиент с обратными вызовами (SDK процессинга, драйвер очереди, асинхронный HTTP на Netty) или ListenableFuture. Строится такой мост одной функцией, и в примере ниже она оборачивает платёжный шлюз, у которого есть и обратный вызов, и отмена запроса:

// Legacy Java API:
// interface PaymentCallback { void onSuccess(Receipt r); void onError(Throwable t); }
// void charge(Request req, PaymentCallback cb);
// boolean cancel(String requestId);

suspend fun PaymentGateway.chargeAwait(req: Request): Receipt =
    suspendCancellableCoroutine { cont ->
        charge(req, object : PaymentCallback {
            override fun onSuccess(r: Receipt) { cont.resume(r) }
            override fun onError(t: Throwable) { cont.resumeWithException(t) }
        })
        cont.invokeOnCancellation { cancel(req.id) }   // отмена корутины отменяет и запрос
    }

Выбор между двумя функциями принципиален, и таблица ниже показывает, чем они различаются:

suspendCoroutine suspendCancellableCoroutine
Реагирует на отмену корутины нет да
invokeOnCancellation нет есть
Что будет при job.cancel() корутина повиснет до обратного вызова немедленный CancellationException
Двойной resume IllegalStateException IllegalStateException

Правило: по умолчанию берите suspendCancellableCoroutine. suspendCoroutine оставляет корутину неотменяемой, так что withTimeout вокруг такого вызова истечёт, а корутина продолжит висеть, пока обратный вызов не придёт, или вообще никогда. Это классический источник ситуации «таймаут сработал, а поток или соединение так и не освободились».

Чтобы мост работал корректно, он должен соблюдать три правила:

  1. resume вызывается ровно один раз. Кривые SDK вызывают onError после onSuccess, и тогда вы получите IllegalStateException: Already resumed. Защититься можно проверкой cont.isActive вместе с атомарным флагом или вызовом resumeWith через CancellableContinuation.tryResume(value, null)?.let { cont.completeResume(it) }.
  2. invokeOnCancellation должен быть быстрым и не бросать исключений. Его вызывают из произвольного потока, того, который выполняет отмену, и без корутинного контекста, а исключение из него уйдёт в CoroutineExceptionHandler.
  3. Ресурсы, полученные после отмены, надо закрыть. Если обратный вызов пришёл уже после отмены, resume ничего не сделает, а объект вроде соединения или стрима утечёт. Для этого случая есть перегрузка cont.resume(value) { cause, resource, ctx -> resource.close() }.

Многие мосты писать руками не нужно, потому что они уже есть в библиотеках: CompletableFuture.await() и CompletionStage.await() (kotlinx-coroutines-jdk8), ListenableFuture.await() (kotlinx-coroutines-guava), Mono.awaitSingle()/Flux.asFlow() (kotlinx-coroutines-reactor), Publisher.awaitFirstOrNull() (kotlinx-coroutines-reactive) и Call.await() в Retrofit. Свой мост стоит писать только для действительно чужого SDK.

16.3 Диспетчеры: стоимость переключения и limitedParallelism

Переключение диспетчера кажется бесплатным, потому что в коде это одна строка withContext, но у него есть цена, и в цикле она складывается в заметные цифры. На деле withContext(dispatcher) не «переключает поток», а ставит задачу в очередь другого диспетчера и приостанавливает текущую корутину, и стоимость этого складывается из четырёх частей:

  • выделения памяти DispatchedCoroutine;
  • CAS в очереди планировщика;
  • (в худшем случае) пробуждения спящего worker-потока через LockSupport.unpark, то есть системного вызова и работы планировщика ОС;
  • потери локальности кеша, потому что продолжение выполняется на другом ядре, и все горячие данные для него чужие.

Первые два пункта стоят сотни наносекунд, а третий уже микросекунды. Поэтому withContext в цикле по элементам считается антипаттерном, и его выносят за пределы цикла.

Здесь есть важная оптимизация, о которой стоит знать. Dispatchers.Default и Dispatchers.IO работают как два «вида» над одним CoroutineScheduler, и если текущий поток уже принадлежит этому планировщику, а лимит позволяет, переход Default → IO и обратно выполняется без передачи задачи в очередь, меняется только учёт слота. Поэтому withContext(Dispatchers.IO) { ... } из корутины на Default обходится заметно дешевле, чем withContext(myExecutor.asCoroutineDispatcher()).

Вторая деталь касается withContext с тем же диспетчером, например withContext(Dispatchers.IO) внутри корутины, которая уже работает на IO. Поток он не переключает, но всё равно создаёт новый Job и новый контекст, то есть остаётся точкой отмены и стоит выделения памяти, так что писать его «на всякий случай» не надо.

limitedParallelism(n) служит механизмом изоляции ресурсов, и применять его стоит системно. Идея в том, чтобы у каждого внешнего ресурса был свой бюджет параллелизма, а очередь стояла перед ресурсом, а не была размазана по общему IO. В конфигурации ниже заведены три таких бюджета: под базу данных, под внешний процессинг и под файловый экспорт.

@Configuration
class DispatcherConfig {
    // Бюджет под БД равен размеру пула Hikari, и очередь корутин совпадает с очередью за соединением
    @Bean fun dbDispatcher(hikari: HikariDataSource): CoroutineDispatcher =
        Dispatchers.IO.limitedParallelism(hikari.maximumPoolSize, name = "db")

    // Внешний процессинг: не больше 20 одновременных запросов, чтобы не выбить их rate limit
    @Bean fun processingDispatcher(): CoroutineDispatcher =
        Dispatchers.IO.limitedParallelism(20, name = "processing")

    // Файловый экспорт отдельно, чтобы тяжёлая выгрузка не мешала платежам
    @Bean fun exportDispatcher(): CoroutineDispatcher =
        Dispatchers.IO.limitedParallelism(4, name = "export")
}

Именованный вариант limitedParallelism(n, name) появился для того, чтобы виды различались в дампах и в toString(), потому что без имени в thread dump все они выглядят одинаково. Ключевое свойство стоит повторить ещё раз: виды над Dispatchers.IO не ограничены базовым лимитом 64, поэтому сумма бюджетов может превысить 64, и так задумано (by design) (Dispatchers.IO). С Dispatchers.Default всё наоборот: вид над ним ограничен числом ядер, потому что там лимит физический.

⚠️ Грабли. limitedParallelism нужно вызывать один раз и хранить результат. Если написать withContext(Dispatchers.IO.limitedParallelism(10)) внутри метода, на каждый вызов будет создаваться новый вид со своим лимитом 10, то есть никакого ограничения не будет вообще, зато появится выделение памяти. На ревью такое встречается регулярно.

16.4 Режимы CoroutineStart

CoroutineStart определяет, когда и где корутина, созданная через launch или async, начнёт выполнять своё тело. У параметра start четыре значения, и разница между ними видна только под нагрузкой, поэтому таблицу ниже стоит читать вместе с колонкой «Когда нужно», где сказано, какую проблему решает каждое значение:

Значение Поведение Когда нужно
DEFAULT Задача ставится в очередь диспетчера, выполнение начнётся, когда дойдёт очередь; отмена до старта — корутина не выполнится вообще по умолчанию
LAZY Не стартует, пока не вызовут start(), join() или await() построить граф задач заранее, запустить выборочно
ATOMIC Как DEFAULT, но отмена до первой точки приостановки не работает — тело гарантированно начнёт выполняться когда в начале тела есть обязательный acquire/try с парным finally
UNDISPATCHED Тело начинает выполняться немедленно в текущем потоке до первой приостановки, дальше — по диспетчеру нужно синхронно захватить состояние/контекст до того, как что-то изменится

UNDISPATCHED остаётся единственным способом гарантировать, что launch { } успел что-то сделать до того, как продолжился вызывающий код, например зарегистрировал подписчика перед публикацией события. Он же часто оказывается причиной вопроса «а почему мой код выполняется на HTTP-потоке».

ATOMIC в продакшене нужен редко, но он показателен, потому что закрывает дыру «корутину отменили между launch и первой строкой тела, а ресурс уже выдан». Если вы пишете launch { val lease = acquire(); try { ... } finally { release(lease) } }, при DEFAULT возможен сценарий, в котором тело не начнётся и acquire не произойдёт, и это нормально. Но если acquire произошёл до launch, отмена до старта потеряет release. Поэтому правильнее захватывать ресурс внутри тела, а cleanup выполнять через withContext(NonCancellable) в finally.

16.5 Job и SupervisorJob

Каждый Job занимает узел в дереве корутин, и от того, в каком он состоянии и как реагирует на ошибки детей, зависит всё поведение structured concurrency. Состояния Job и переходы между ними показаны на схеме ниже; обратите внимание на состояние Completing между завершением тела и завершением всей корутины:

                  cancel()/ошибка ребёнка
   New ──start()──► Active ───────────────► Cancelling ──► Cancelled
                     │                          ▲
                     │ тело завершилось         │
                     ▼                          │
                 Completing ───────────────────-┘
                     │ все дети завершились
                     ▼
                 Completed

Упускают обычно как раз то, что Completing означает «моё тело закончилось, но дети ещё работают». Родитель в этом состоянии не принимает новых детей, и launch в завершающемся scope бросит исключение, но существующих детей он ждёт. Отсюда поведение coroutineScope { launch { delay(10_000) } }, при котором блок «вернулся», а корутина висит ещё 10 секунд.

Job() и SupervisorJob() различаются ровно одним: тем, как узел обрабатывает ошибку ребёнка. Таблица показывает это различие и заодно то, в чём они совпадают:

Job() SupervisorJob()
Ребёнок упал отменяет себя и всех siblings, ошибка идёт вверх ничего не делает, ошибка идёт в CoroutineExceptionHandler ребёнка
Родителя отменили отменяет всех детей отменяет всех детей (одинаково!)
Ребёнок отменён (CancellationException) ничего, siblings живут то же

Главным источником заблуждений служит вторая строка: supervisor не делает детей независимыми от отмены сверху, он делает независимыми только их ошибки.

Есть ещё одна деталь, которая ломает людям картину мира. SupervisorJob(), переданный как элемент контекста в launch(SupervisorJob()), не делает эту корутину supervisor-ом, а превращает её Job в отдельный корень, отвязанный от структурной иерархии: родитель перестаёт её ждать, и отмена родителя её не затронет. Это утечка в чистом виде, оформленная как «я просто хотел, чтобы ошибка не валила остальных». Правильно в этом случае писать supervisorScope { } или держать CoroutineScope(SupervisorJob()) полем компонента, как в примере:

// ❌ Корутина отвязана от родителя: её не ждут, не отменяют, а ошибки теряются
scope.launch(SupervisorJob()) { longRunningWork() }

// ✅ Независимость ошибок внутри одного уровня
supervisorScope {
    launch { workA() }
    launch { workB() }
}

16.6 Механизм структурированной отмены

Структурированная отмена означает, что вызов cancel() на одном узле дерева распространяется на всё поддерево под ним, и на интервью часто просят объяснить, что физически происходит при job.cancel() и кто кого отменяет. Ответ состоит из шести шагов, и каждый из них объясняет одну из ловушек, разобранных выше:

  1. cancel(cause) переводит Job в состояние Cancelling и записывает причину, которой по умолчанию становится CancellationException, если явная причина не задана.
  2. Job обходит список детей (ChildHandle) и вызывает cancel на каждом, рекурсивно вниз по дереву. Отмена идёт сверху вниз, синхронно, в потоке того, кто её вызвал.
  3. Каждая корутина, которая в этот момент приостановлена на suspend-точке, получает resumeWithException(CancellationException), то есть возобновляется исключением прямо в точке приостановки. delay, await, receive, emit и Mutex.lock отменяемы, потому что внутри у них CancellableContinuation.
  4. Корутина, которая в этот момент выполняется, а не стоит на приостановке, ничего не замечает. Об отмене она узнает на следующей suspend-точке, потому что каждая из них перед приостановкой проверяет isActive, а если suspend-точек больше нет, не узнает никогда.
  5. CancellationException разворачивает стек и выполняет finally-блоки, но любой suspend-вызов в finally немедленно бросит CancellationException, потому что Job уже находится в Cancelling. Спасение здесь только одно, и это withContext(NonCancellable) { }.
  6. Когда все дети завершились, Job переходит в Cancelled, и родитель, который ждал в join() или coroutineScope, продолжает работу.

Из этой последовательности вытекают все практические правила работы с отменой.

CancellationException сообщает об отмене корутины, а не о сбое. Логировать её как ошибку нельзя, потому что вы зашумите логи при каждом закрытии соединения клиентом; превращать её в HTTP 500 тоже нельзя, а главное, её нельзя глотать. Проглоченная отмена означает, что корутина продолжит работу вне дерева: сделает второе списание, отправит уведомление после того, как клиент отвалился, или займёт соединение, которое уже вернули в пул. Ниже показана классическая ошибка с универсальным catch и два способа её исправить:

// ❌ Классика: универсальный catch съедает отмену
suspend fun charge(cmd: Charge): Result = try {
    gateway.charge(cmd)
} catch (e: Exception) {           // CancellationException : IllegalStateException : Exception
    log.error("charge failed", e)
    Result.Failed
}

// ✅ Вариант 1: отдельная ветка (порядок важен — CancellationException первым)
suspend fun charge(cmd: Charge): Result = try {
    gateway.charge(cmd)
} catch (e: CancellationException) {
    throw e
} catch (e: Exception) {
    log.error("charge failed", e)
    Result.Failed
}

// ✅ Вариант 2: проверка активности после catch
suspend fun charge2(cmd: Charge): Result {
    return try { gateway.charge(cmd) } catch (e: Exception) {
        currentCoroutineContext().ensureActive()   // бросит, если нас отменили
        log.error("charge failed", e); Result.Failed
    }
}

Второй вариант лучше тем, что ловит и случай, когда корутину отменили, но упавший код бросил не CancellationException, а собственное исключение; так бывает с HTTP-клиентами, которые при закрытии соединения бросают IOException.

runCatching содержит тот же баг, только невидимый. Внутри runCatching { } реализован как try { Result.success(block()) } catch (e: Throwable) { Result.failure(e) } и ловит Throwable, то есть и CancellationException, и OutOfMemoryError. Поэтому в корутинном коде его использование по умолчанию ошибочно, а если стиль вам нравится, заведите собственный вариант, который пропускает отмену:

inline fun <T> coRunCatching(block: () -> T): Result<T> = try {
    Result.success(block())
} catch (e: CancellationException) {
    throw e
} catch (e: Throwable) {
    Result.failure(e)
}

withTimeout против withTimeoutOrNull. Обе функции ставят таймер в диспетчере и при его срабатывании отменяют внутренний scope исключением TimeoutCancellationException, а различаются тем, что видит вызывающий код:

withTimeout withTimeoutOrNull
При таймауте бросает TimeoutCancellationException возвращает null
Тип исключения подкласс CancellationException —
Опасность если не поймать рядом, выше по стеку это выглядит как обычная отмена null легко перепутать с «данных нет»
Внутри блока обычные finally работают, suspend в них — только под NonCancellable то же

В банковском коде практичнее всего сразу превращать таймаут в доменную ошибку, как в примере с запросом котировки:

suspend fun quote(req: Req): Quote = try {
    withTimeout(800.milliseconds) { pricing.quote(req) }
} catch (e: TimeoutCancellationException) {
    throw PricingUnavailable(req.id, cause = e)     // уже не CancellationException
}

Отдельная ловушка в том, что withTimeout не прерывает блокирующий код. Вызов withTimeout(1.seconds) { withContext(Dispatchers.IO) { jdbc.query(...) } } завершится по таймауту только тогда, когда JDBC вернёт управление сам. Поэтому для JDBC ставьте queryTimeout/statement_timeout на стороне драйвера и БД (глава 18), а корутинный таймаут здесь бесполезен.

16.7 CoroutineExceptionHandler, утечки и GlobalScope

CoroutineExceptionHandler служит последней инстанцией для исключений, которые никто не обработал, и по смыслу аналогичен Thread.UncaughtExceptionHandler. Он не спасает от ошибки и не продолжает работу корутины, а только сообщает о ней, и помнить о нём нужно четыре вещи, которые определяют, дойдёт ли до него исключение вообще:

  • вызывается он только для корневых корутин, то есть для детей supervisorScope, для корутин в scope с SupervisorJob и для корутин без родителя;
  • обработчик, установленный на дочернем launch внутри coroutineScope, игнорируется, потому что ребёнок делегирует ошибку родителю;
  • для async он не вызывается никогда, поскольку исключение лежит в Deferred;
  • если обработчика нет, исключение уходит в Thread.currentThread().uncaughtExceptionHandler, а на JVM по умолчанию просто печатается в stderr. В контейнере с JSON-логами это строка вне формата, которую не найдёт ни одно оповещение.

Для Spring-сервиса минимальная настройка выглядит так: один scope на приложение с SupervisorJob, обработчиком, который пишет ошибку в лог и увеличивает счётчик метрики, и отменой при остановке контекста.

@Configuration
class CoroutineScopeConfig {
    private val log = LoggerFactory.getLogger(javaClass)

    @Bean(destroyMethod = "cancel")          // Spring вызовет cancel() при остановке контекста
    fun applicationScope(): CoroutineScope {
        val handler = CoroutineExceptionHandler { ctx, e ->
            log.error("Unhandled coroutine failure in {}", ctx[CoroutineName]?.name ?: "unnamed", e)
            Metrics.counter("coroutine.unhandled").increment()
        }
        return CoroutineScope(SupervisorJob() + Dispatchers.Default + handler + CoroutineName("app"))
    }
}

GlobalScope считается антипаттерном, и причины у этого вполне конкретные. Это CoroutineScope с пустым контекстом, в котором нет ни Job-родителя, ни обработчика, ни имени. Поэтому корутину в нём не отменяет ничто, кроме её собственного Job, который обычно никто не сохраняет, и она переживает запрос, переживает @PreDestroy и переживает закрытие Spring-контекста, а её исключения уходят в stderr. В тестах с несколькими контекстами (@DirtiesContext, @SpringBootTest с разными профилями) такие корутины накапливаются и держат ссылки на устаревшие бины, что даёт классическую утечку памяти в тестовом прогоне. Начиная с Kotlin 1.6 GlobalScope помечен @DelicateCoroutinesApi, и компилятор требует @OptIn; это единственное, что стоит оставить, чтобы GlobalScope бросался в глаза на ревью.

Легитимный случай у него, строго говоря, один: фоновая задача уровня всего приложения, которая обязана жить, пока жив процесс, и жизненным циклом которой вы управляете сознательно. Но в Spring-приложении для этого есть бин со scope, поэтому формулировка «легитимных случаев нет» здесь практически точна.

Чтобы корутины не утекали, достаточно проверить шесть пунктов:

  1. В коде нет GlobalScope, и это проверяется grep-ом в CI.
  2. Каждый долгоживущий CoroutineScope объявлен бином с destroyMethod = "cancel" или с @PreDestroy.
  3. Каждый launch в scope с SupervisorJob работает с CoroutineExceptionHandler.
  4. У каждого async есть гарантированный await() внутри coroutineScope/supervisorScope, а не «где-нибудь потом».
  5. Все CoroutineName заданы, потому что иначе дампы невозможно читать.
  6. В тестах используется runTest, который сам падает, если остались незавершённые корутины.

17. Flow: операторы, hot-потоки, тестирование

Раздел 8 дал модель Flow, а этот раздел посвящён рабочим подробностям, которые нужны, когда Flow используют в продакшене: какие операторы есть, сколько стоит каждый, как выбрать стратегию backpressure, как настроить горячие потоки, как обернуть обратный вызов и как обрабатывать ошибки. Цена здесь важна потому, что часть операторов работает как простой вложенный коллектор, а часть незаметно заводит канал и отдельную корутину. В конце раздела показано, как тестировать Flow с помощью Turbine.

17.1 Операторы Flow и их стоимость

Операторы Flow различаются не только тем, что они делают, но и тем, сохраняют ли порядок, дают ли параллелизм и во что обходятся. Таблица ниже собирает рабочий набор с этими тремя характеристиками; на колонку «Цена» стоит смотреть в первую очередь, потому что именно в ней видно, где появляется канал:

Оператор Что делает Порядок сохраняется Параллелизм Цена
map 1→1, suspend-лямбда да нет ноль (вложенный коллектор)
transform 1→N, можно emit сколько угодно да нет ноль
filter/onEach фильтр / side effect да нет ноль
flatMapConcat 1→Flow, подпотоки последовательно да нет по объекту на подпоток

У flatMapMerge по умолчанию concurrency = DEFAULT_CONCURRENCY, то есть 16, и это значение настраивается свойством kotlinx.coroutines.flow.defaultConcurrency. Это ровно тот оператор, который нужен для задачи «обогатить 10 000 транзакций, вызывая внешний сервис, но не более чем 20 запросами одновременно»:

suspend fun enrichAll(txs: Flow<Tx>): Flow<EnrichedTx> =
    txs.flatMapMerge(concurrency = 20) { tx ->
        flow { emit(enrichmentClient.enrich(tx)) }
    }

flatMapLatest подходит для случаев, когда важен только последний элемент, например для поисковой подсказки или пересчёта котировки при изменении суммы. Каждый новый элемент отменяет корутину предыдущего подпотока, так что внешний вызов действительно прерывается, если клиент поддерживает отмену.

Тем, кто пришёл из Reactor, удобнее всего сопоставить операторы напрямую; подробно Reactor разобран в главе 11 (11-reactive.md), а таблица ниже показывает соответствия и места, где они неточны:

17.2 Модели backpressure во Flow

Backpressure отвечает на вопрос, что делать, если потребитель медленнее производителя, и Flow даёт на него три разных ответа: buffer, conflate и collectLatest. Пример ниже прогоняет один и тот же поток котировок со скоростью 1000 элементов в секунду через медленный рендер всеми способами, включая вариант без всякой стратегии:

val prices: Flow<Price> = quoteStream()          // 1000 элементов/с

// 1. Ничего: производитель ждёт потребителя — 10 элементов/с сквозной throughput
prices.collect { slowRender(it) }

// 2. buffer: конвейер, всплески сглаживаются, при переполнении производитель ждёт
prices.buffer(100).collect { slowRender(it) }

// 3. conflate: потребителю важно только последнее значение — промежуточные выбрасываются
prices.conflate().collect { slowRender(it) }

// 4. collectLatest: начатая обработка отменяется при новом значении
prices.collectLatest { slowRender(it) }

В терминах бизнеса выбор выглядит так. buffer означает «нужны все элементы, и я разрешаю отставать»; conflate означает «нужно текущее состояние», как для котировок, баланса на дашборде или health; collectLatest означает «нужно текущее состояние, а старая работа бессмысленна», как для перерасчёта или рендера. Для платёжных событий правильный ответ почти всегда buffer с ограниченной ёмкостью и сигнализацией при заполнении, потому что терять события нельзя.

Второй параметр buffer называется onBufferOverflow и принимает значения SUSPEND (по умолчанию), DROP_OLDEST и DROP_LATEST. Вызов buffer(0, BufferOverflow.SUSPEND) вырождается в отсутствие буфера, но с отдельной корутиной под upstream, то есть с конвейером.

17.3 SharedFlow и StateFlow: параметры и выбор

У горячих потоков несколько параметров, и от их сочетания зависит, будет ли SharedFlow шиной событий, кэшем последнего значения или источником утечки памяти. Сначала посмотрим, как объявляется MutableSharedFlow для платёжных событий и какие три параметра у него есть, затем сравним его со StateFlow и разберём, как превратить холодный поток в горячий:

val events = MutableSharedFlow<PaymentEvent>(
    replay = 0,                                   // сколько последних значений получит новый подписчик
    extraBufferCapacity = 64,                     // буфер сверх replay
    onBufferOverflow = BufferOverflow.SUSPEND,    // что делать при переполнении
)

Механика у него такая: есть общий буфер размера replay + extraBufferCapacity, и emit при SUSPEND приостанавливается, пока самый медленный подписчик не освободит место. tryEmit работает без suspend и возвращает false, если места нет, а при DROP_OLDEST/DROP_LATEST всегда возвращает true. Чем SharedFlow отличается от StateFlow, показывает таблица:

Свойство SharedFlow StateFlow
Значение по умолчанию нет обязательно
replay настраивается (0..N) всегда 1
Дедупликация нет да, по equals
Конфляция только через onBufferOverflow всегда
Синхронное чтение нет .value
emit может приостановиться да нет (всегда конфлейтит)
Все ли значения дойдут да (при достаточном буфере) нет, только последнее
Типичное применение шина событий, уведомления конфигурация, фича-флаги, состояние

Из практики вытекают три правила:

  1. replay > 0 означает утечку памяти по значению. MutableSharedFlow(replay = 1000) вечно держит тысячу последних объектов, поэтому для событийной шины ставят replay = 0.
  2. SUSPEND в сочетании с зависшим подписчиком останавливает весь производитель. Медленный подписчик тормозит и всех остальных, и сам emit. Если подписчики независимы и события можно терять, берут DROP_OLDEST, а если терять нельзя, то это задача уже не для SharedFlow, а для Kafka (глава 29).
  3. StateFlow не эмитит равное значение. Если ваш тип объявлен как data class с полем метки времени, дедупликация не сработает, и так же будет с обычным классом без equals, где сравнение идёт по ссылке. Оба случая приносят сюрпризы, будь то «почему подписчик не получил обновление» или «почему он получил лишнее».

Превращают cold в hot операторы shareIn/stateIn, и в примере ниже так устроен кэш курсов валют, который раз в 30 секунд обновляется из внешнего клиента:

@Service
class RateCache(scope: CoroutineScope, client: RateClient) {
    val rates: StateFlow<Rates> = flow {
        while (true) { emit(client.fetch()); delay(30.seconds) }
    }.stateIn(scope, SharingStarted.Eagerly, Rates.EMPTY)
}

Когда запускать upstream, решает SharingStarted. При Eagerly upstream стартует сразу и больше не останавливается, при Lazily стартует с первым подписчиком и дальше тоже не останавливается, а WhileSubscribed(stopTimeoutMillis, replayExpirationMillis) стартует с первым подписчиком и останавливается через timeout после ухода последнего. Серверному кэшу, который должен быть готов к первому запросу, подходит Eagerly, а потоку, привязанному к активным клиентам вроде SSE-подписок, подходит WhileSubscribed(5000).

17.4 callbackFlow и channelFlow

Обычный flow { } разрешает emit только из своей собственной корутины, и этого мало, когда источником служит обратный вызов или несколько корутин сразу. Для таких случаев нужен channelFlow/callbackFlow, внутри которого доступен send, вызываемый откуда угодно, а под капотом работает канал. В примере ниже так превращается в Flow потребитель Kafka:

fun KafkaConsumer<String, String>.asFlow(topic: String): Flow<ConsumerRecord<String, String>> =
    callbackFlow {
        val listener = object : RebalanceListener { /* ... */ }
        subscribe(listOf(topic), listener)
        val job = launch(Dispatchers.IO) {
            while (isActive) {
                poll(Duration.ofMillis(100)).forEach { trySend(it) }
            }
        }
        awaitClose {                    // обязателен: вызывается при отмене коллектора
            job.cancel()
            unsubscribe()
            close()
        }
    }

Правил для этих строителей потоков четыре:

  • awaitClose { } в callbackFlow обязателен, и без него строитель бросит IllegalStateException при завершении, потому что библиотека настаивает на том, чтобы вы отписались от источника.
  • channelFlow устроен так же, но awaitClose не требует, и применять его стоит, когда источником служат ваши же корутины, а не внешний обратный вызов.
  • trySend не приостанавливается и возвращает результат, и при Channel.BUFFERED (по умолчанию, 64) переполнение вернёт failure, так что, если результат не проверить, элемент потеряется молча. Для гарантий доставки нужен send из корутины.
  • Платить приходится каналом и как минимум одной дополнительной корутиной, поэтому channelFlow заметно дороже flow, и там, где хватает обычного строителя, использовать его не стоит.

17.5 Исключения в Flow: catch, retryWhen, onCompletion

Ошибки во Flow обрабатываются операторами, а не блоками try/catch, и у каждого из этих операторов своя зона ответственности: retryWhen решает, пересоздать ли поток, catch подставляет запасную ветку, а onCompletion срабатывает при любом завершении. Пример ниже собирает все три оператора в одном потоке платежей:

fun payments(): Flow<Payment> = source()
    .retryWhen { cause, attempt ->
        val retriable = cause is IOException && attempt < 3
        if (retriable) delay(100L * (attempt + 1)) // линейный backoff
        retriable                                   // true = пересоздать upstream
    }
    .catch { e ->
        log.error("payment stream failed", e)
        emit(Payment.SENTINEL)                      // catch может эмитить — это «fallback-ветка»
    }
    .onCompletion { cause ->
        if (cause == null) log.info("stream finished") else log.warn("stream ended: {}", cause.message)
    }

Важно здесь следующее:

  • retryWhen получает cause и номер попытки и пересоздаёт подписку на upstream, то есть flow { } выполнится заново со всеми побочными эффектами. Для потребления из очереди это означает повторную подписку, а для HTTP-стрима повторный запрос.
  • catch ловит только upstream и может вызывать emit, и это единственный легальный способ подставить fallback.
  • onCompletion получает cause, который равен null при нормальном завершении, CancellationException при отмене и исключению при ошибке. Он играет роль finally для flow и видит отмену, что удобно для метрик.
  • catch не ловит CancellationException, потому что библиотека специально её пропускает, так что здесь, в отличие от try/catch, за вас уже подумали.

Порядок операторов имеет значение: .catch { }.map { } поймает ошибки только того, что стоит до catch, а ошибка в map пролетит мимо. Поэтому идиома «обработать всё» такая: логика в onEach, затем catch, затем пустой collect().

17.6 Тестирование Flow: Turbine

Turbine — это маленькая библиотека (app.cash.turbine:turbine) для тестирования Flow, которая даёт test { } с awaitItem()/awaitComplete()/awaitError() и падает, если в потоке остались непрочитанные элементы. Нужна она потому, что toList() работает только для конечных потоков, а для hot-потоков и для проверок вида «что пришло через 5 секунд виртуального времени» его не хватает. Ниже два теста: первый проверяет конфляцию StateFlow, второй проверяет, что retryWhen делает ровно три попытки.

@Test
fun `conflates rapid updates`() = runTest {
    val state = MutableStateFlow(0)
    state.test {
        assertEquals(0, awaitItem())        // initial
        state.value = 1
        state.value = 2
        assertEquals(2, awaitItem())        // 1 «съеден» конфляцией — это ожидаемое поведение
        cancelAndIgnoreRemainingEvents()
    }
}

@Test
fun `retries three times then fails`() = runTest {
    var attempts = 0
    val f = flow<Int> { attempts++; throw IOException("boom") }
        .retryWhen { _, a -> a < 2 }
    f.test {
        assertIs<IOException>(awaitError())
        assertEquals(3, attempts)
    }
}

Turbine вместо toList() стоит брать по трём причинам. Во-первых, hot-потоки бесконечны, и toList() на них просто зависнет. Во-вторых, awaitItem() встраивается в виртуальное время runTest, так что можно проверить, что «после advanceTimeBy(30.seconds) пришёл элемент». В-третьих, Turbine падает при «лишних» элементах и незакрытых подписках, и это находит утечки, которые toList() игнорирует.

18.1 Плагины all-open и no-arg в байткоде

Проверить работу плагинов проще всего через javap, и это стоит уметь делать руками: вопрос «а что именно делает плагин» встречается на собеседованиях, а в проекте с него начинается диагностика «почему прокси не создался». Вот как выглядит сервис, скомпилированный без плагинов:

$ javap -p build/classes/kotlin/main/com/acme/TransferService.class
public final class com.acme.TransferService {          // ← ACC_FINAL
  public final com.acme.Receipt transfer(...);         // ← методы тоже final
}

CGLIB не может создать у такого класса подкласс, и вы получаете BeanCreationException: Cannot subclass final class. Если @Transactional стоит на методе final-класса, Spring в лучшем случае бросит исключение, а в худшем, когда прокси создан на интерфейсе JDK, а метода в интерфейсе нет, молча не применит транзакцию. С плагином kotlin("plugin.spring") тот же класс выглядит так:

public class com.acme.TransferService {                // ACC_FINAL снят
  public com.acme.Receipt transfer(...);               // и с метода тоже
}

Плагин работает на уровне компилятора, а не рефлексии: он снимает final с классов, помеченных аннотациями из списка или мета-аннотированных ими, и с их не-private членов. Исходник при этом остаётся без open, что приятно при чтении, но мешает понять, «почему это вообще компилируется». Плагин kotlin("plugin.jpa") добавляет к @Entity конструктор без параметров:

public com.acme.Order();        // синтетический конструктор без параметров

Этот конструктор помечен как синтетический, поэтому вызвать Order() из Kotlin или Java нельзя, только рефлексией, и это ровно то, что делает Hibernate. Инициализаторы свойств он по умолчанию не выполняет, и изменить это можно через noArg { invokeInitializers = true }. Из этого следует, что var lines: MutableList<Line> = mutableListOf() после того, как объект создаст Hibernate, будет равен null, пока Hibernate не подставит свою PersistentBag, и обращение к lines у объекта, созданного не через ваш конструктор, до этой подстановки даст NPE в non-null типе.

Кроме того, kotlin-spring не покрывает ряд аннотаций, которые обычно забывают добавить в allOpen { }: jakarta.persistence.Entity, MappedSuperclass и Embeddable, которые нужны Hibernate для lazy-прокси, io.github.resilience4j.* (@Retryable, @CircuitBreaker), org.springframework.retry.annotation.Retryable и собственные аннотации с AOP-аспектами вроде @Audited и @Metered.

18.2 @ConfigurationProperties: валидация и вложенность

Конфигурация на data class удобна, но у неё есть нюансы с валидацией и вложенными классами, из-за которых кривой конфиг может пройти незамеченным, а сервис упадёт уже на первом платеже. Ниже конфигурация процессинга с валидацией полей и вложенным блоком повторных попыток:

@ConfigurationProperties("bank.processing")
@Validated
data class ProcessingProperties(
    @field:NotBlank val terminalId: String,
    @field:Positive val maxAmountMinor: Long,
    val timeout: Duration = Duration.ofSeconds(3),
    @field:Valid val retry: Retry = Retry(),
    val hosts: List<String> = emptyList(),
) {
    data class Retry(
        @field:Min(1) @field:Max(10) val attempts: Int = 3,
        val backoff: Duration = Duration.ofMillis(200),
    )
}

С таким классом связаны четыре нюанса, и каждый из них уже ломал чей-то деплой:

  1. @field: обязателен для Bean Validation на свойствах data class. Без use-site target аннотация уходит на параметр конструктора, и Hibernate Validator её не увидит. Для constructor binding Boot умеет читать и параметры, но полагаться на это не стоит, потому что поведение различается между валидацией свойств и валидацией конструктора.
  2. Ошибка валидации роняет сервис на старте, и это правильно, потому что сервис с кривым конфигом лучше не поднимется вовсе, чем упадёт на первом платеже. Проверьте только, что ваш readiness-probe этого не маскирует (глава 46).
  3. Вложенные классы со значением по умолчанию (val retry: Retry = Retry()) требуют @field:Valid, иначе их внутренние ограничения не проверятся.
  4. Неизменяемость здесь реальная. data class с val означает, что @RefreshScope или hot-reload из Spring Cloud Config не поменяют объект «на месте», и для этого нужен новый бин. Если конфигурация должна меняться во время выполнения, держите её в StateFlow (раздел 17.3), а @ConfigurationProperties используйте как стартовое значение.

18.3 Обработка ошибок в корутинах: @ControllerAdvice, MDC, трассировка

Привычные механизмы Spring для обработки ошибок и логирования работают и с suspend-контроллерами, но с двумя оговорками, связанными с отменой и с тем, что корутина меняет потоки. @ControllerAdvice с @ExceptionHandler работает для suspend-контроллеров без изменений: исключение из корутины пробрасывается в Mono, который возвращает CoroutinesUtils, а дальше его подхватывает обычный реактивный pipeline обработки ошибок. Сам обработчик тоже может быть suspend, как в примере, где недоступность сервиса котировок превращается в ответ 503:

@RestControllerAdvice
class ApiExceptionHandler {
    @ExceptionHandler(PricingUnavailable::class)
    suspend fun handlePricing(e: PricingUnavailable): ResponseEntity<ApiError> {
        metrics.increment("pricing.unavailable")
        return ResponseEntity.status(503).body(ApiError("PRICING_UNAVAILABLE", e.requestId))
    }
}

Ловушек здесь две:

  • CancellationException до обработчика не доходит, и так и должно быть, потому что клиент отвалился и отвечать некому. Но если вы сами бросили TimeoutCancellationException из withTimeout и не превратили его в доменную ошибку (раздел 16.6), он выглядит как отмена, и вместо 504 клиент получит оборванное соединение без записи в логе. Поэтому конвертируйте таймауты прямо рядом с withTimeout.
  • MDC не переживает приостановку. ThreadLocal, на котором построен MDC в Logback, привязан к потоку, а корутина потоки меняет. Решений два: MDCContext из kotlinx-coroutines-slf4j, то есть элемент контекста, который восстанавливает MDC при каждом resume, или переход на Micrometer context propagation (ContextRegistry, Hooks.enableAutomaticContextPropagation(); в Spring Boot это spring.reactor.context-propagation=AUTO, см. главы 11 и 50). MDCContext нужно явно добавлять в контекст, через withContext(MDCContext()) { } или при создании scope, как в примере ниже:
suspend fun handle(cmd: Command) = withContext(MDCContext(mapOf("traceId" to cmd.traceId))) {
    log.info("processing")     // traceId будет в логе и после каждой приостановки
    step1(); step2()
}

18.4 Kotlin и Spring AOT / GraalVM native

GraalVM native image заранее компилирует приложение и требует знать всю рефлексию на этапе сборки, а Kotlin-сервис пользуется рефлексией через kotlin-reflect и синтетические методы. Поэтому в native image ломаются вещи, которые на обычной JVM работают незаметно, и ниже перечислено, что именно ломается из-за Kotlin:

  • kotlin-reflect. Spring использует его для конструкторной инъекции, значений по умолчанию и nullability, а Jackson для десериализации. В native image это рефлексия по @kotlin.Metadata, и для каждого класса нужны reachability metadata. Часть подсказок Spring AOT генерирует сам, но для своих DTO, которые десериализуются динамически (полиморфизм, Map<String, Any>), придётся писать RuntimeHintsRegistrar.
  • Аргументы со значениями по умолчанию. Синтетические $default-методы при constructor binding вызываются рефлексией и тоже требуют подсказок.
  • Корутины. Сами по себе они работают, потому что state machine компилируются в обычные классы без всякой рефлексии. Однако DebugProbes и stack trace recovery рефлексию используют, поэтому в native их отключают (-Dkotlinx.coroutines.stacktrace.recovery=false).
  • kotlinx.serialization вместо Jackson убирает всю эту категорию проблем, потому что сериализаторы генерирует компилятор и рефлексии нет (раздел 12.2). Для native-сервиса это весомый аргумент.
  • Время сборки. Kotlin-модуль даёт больше классов (раздел 14.4), а native-image компилирует их все, поэтому сборка идёт дольше, чем у эквивалента на Java, и счёт здесь идёт на минуты, а не на секунды.

18.5 JPA: val/var, copy() и коллекции

Этот подраздел продолжает раздел 11 и собирает конкретику, которая всплывает на ревью Kotlin-сущностей: что на самом деле означает val в сущности, почему copy() опасен, как обращаться с коллекциями и чем можно заменить JPA, если её грабли в конкретном сервисе перевешивают возможности.

val в сущности остаётся иллюзией. Hibernate пишет в поля рефлексией, не обращая внимания на отсутствие сеттера, поэтому val ему не мешает, но обманывает читателя кода. Хуже обстоит дело со smart cast: компилятор разрешает его для val-свойства именно потому, что считает свойство неизменным, и после проверки на null позволяет обращаться к нему как к ненулевому без повторной проверки. Если Hibernate поменял поле рефлексией между проверкой и использованием, например при refresh(), это допущение нарушается, и код, который выглядит защищённым проверкой, может упасть с NullPointerException. Отсюда практическое правило: в сущностях всё объявляется как var, кроме тех полей, которые задаются в конструкторе и действительно неизменны (например, val createdAt), да и там честнее var.

copy() на managed-сущности оказывается ловушкой, и выглядит она так:

// ❌ если Order — data class (чего делать не надо, но встречается)
val updated = order.copy(status = OrderStatus.PAID)
repo.save(updated)

Здесь copy() создаёт новый detached-объект с тем же id и с тем же значением @Version. save() для объекта с непустым id вызывает merge(), Hibernate загружает текущее состояние и сравнивает версии, и если между вашим чтением и этим merge кто-то обновил строку, вы получите OptimisticLockException там, где ожидали обычное обновление. Вдобавок все lazy-связи в копии остались непроинициализированными прокси, привязанными к старой сессии, и обращение к ним даст LazyInitializationException. Для managed-сущности правильный способ только один: написать order.status = OrderStatus.PAID и дать dirty checking сделать UPDATE.

Коллекции. При загрузке Hibernate подменяет поле коллекции своей реализацией (PersistentBag, PersistentSet), и из этого вытекают три правила:

  • тип свойства должен быть только MutableList/MutableSet, потому что kotlin.collections.List не даст Hibernate работать корректно, а в вашем коде даст UnsupportedOperationException при add;
  • инициализация в объявлении (= mutableListOf()) нужна объектам, которые создаёт ваш конструктор, а для объектов, созданных Hibernate, сработает подмена (но помните про invokeInitializers, раздел 18.1);
  • никогда не заменяйте коллекцию целиком (order.lines = newList) на managed-сущности с orphanRemoval, потому что Hibernate потеряет свою обёртку и бросит A collection with cascade="all-delete-orphan" was no longer referenced. Правильно писать order.lines.clear(); order.lines.addAll(newList).

Альтернативы JPA в Kotlin-проекте. Если грабли JPA перевешивают её возможности, есть пять альтернатив, и таблица ниже сопоставляет их с JPA по тому, что каждая даёт и чем за это приходится платить:

Подход Что даёт Чем платите
JPA/Hibernate + kotlin-jpa Экосистема Spring Data, кэш 2-го уровня, dirty checking Все грабли раздела 11; сущности не идиоматичны для Kotlin
Spring Data JDBC Агрегаты, никаких прокси и lazy; data class можно как модель Нет ленивых связей, нет dirty checking — всегда полный UPDATE

Смешивать два подхода в одном проекте нормально, а вот смешивать их в одной транзакции можно только с пониманием того, что JPA не увидит изменений, сделанных мимо неё, и потребуется flush()/clear() (глава 12).

19. Функциональные идиомы и производительность

Kotlin поощряет функциональный стиль, и в нём легко написать код, который выглядит изящно, но хуже читается, хуже диагностируется или неожиданно выделяет объекты. Этот раздел честно разбирает, где функциональные идиомы окупаются, а где проигрывают обычному if: цепочки scope functions, Result и runCatching против sealed-иерархий ошибок, модификаторы inline-функций, реальное поведение value class и порядки цифр, во что обходятся типичные конструкции.

19.1 Scope functions и читаемость кода

Правило из раздела 4.2 гласит «одна scope function на выражение», и его стоит подкрепить примером, потому что нарушают его все, и выглядит нарушение обычно как «функциональный» код, который трудно отлаживать. Ниже одна и та же функция поиска курса написана дважды, цепочкой ?.let и с ранними возвратами:

// ❌ Четыре вложенных ?.let — «функционально», нечитаемо, недиагностируемо
fun resolve(id: String): Rate? =
    repo.findCurrency(id)?.let { cur ->
        rates.find(cur)?.let { rate ->
            rate.takeIf { it.isFresh() }?.let { fresh ->
                adjust(fresh)?.let { adjusted -> adjusted }
            }
        }
    }

// ✅ Ранний возврат: видно, какая именно проверка не прошла, и легко добавить лог/метрику
fun resolve2(id: String): Rate? {
    val cur = repo.findCurrency(id) ?: return null.also { log.debug("no currency for {}", id) }
    val rate = rates.find(cur) ?: return null
    if (!rate.isFresh()) return null
    return adjust(rate)
}

Второй вариант на две строки длиннее, зато лучше по всем остальным параметрам: каждую причину неуспеха можно отделить, на неё можно поставить точку останова и добавить метрику, а трассировка стека получается осмысленной. Цепочка ?.let скрывает, почему результат оказался null, а в банковском коде это «почему» и составляет суть инцидента.

Второе правило гласит, что ?.let для side effect на деле подменяет собой обычный if. Выражение order?.let { audit.log(it) } читается как «если заказ не null, залогировать», и лучше так и написать.

19.2 Result, runCatching и sealed-иерархии ошибок

У Kotlin есть два способа вернуть ошибку без исключения: встроенный Result и собственная sealed-иерархия, и для доменных ошибок они совсем не равноценны. kotlin.Result — это value class над Any?, в котором ошибка обёрнута в Failure. Язык накладывает на него ограничения: объявить Result<T> возвращаемым типом обычной функции без @OptIn нельзя (исторически это было запрещено, сейчас разрешено, но остаётся плохой практикой), а использовать его как тип поля без упаковки нельзя. Главная же проблема в семантике, потому что Result не различает ошибки и сообщает только, что «что-то упало с Throwable». Вызывающему приходится писать when (e) { is X -> ...; is Y -> ... }, то есть делать ровно то, от чего пытались уйти.

runCatching уже разобран в 16.6: он ловит Throwable, включая CancellationException и OutOfMemoryError. Поэтому в корутинном коде его не применяют, а в обычном берут только там, где действительно «любая ошибка одинакова», например при разборе необязательного поля или для best-effort метрики.

Идиоматичной альтернативой для доменных ошибок служит sealed-иерархия, которая перечисляет все исходы операции вместе с данными, нужными для ответа клиенту. Так выглядит результат перевода между счетами:

sealed interface TransferResult {
    data class Ok(val receipt: Receipt) : TransferResult
    data class InsufficientFunds(val available: Money, val required: Money) : TransferResult
    data class LimitExceeded(val limit: Money, val period: Period) : TransferResult
    data class AccountBlocked(val reason: BlockReason) : TransferResult
    data object GatewayUnavailable : TransferResult
}

По сравнению с исключениями это даёт четыре вещи: (1) типизированный контракт, при котором по сигнатуре видно, чем может закончиться операция; (2) exhaustive when, при котором новая ветка ломает компиляцию всех обработчиков; (3) ошибку, которая несёт данные (available, required), нужные для ответа клиенту; (4) отсутствие затрат на заполнение стека.

Исключения всё-таки лучше для технических сбоев вроде отказа сети, БД или таймаута, которые должны «пролететь» через десять кадров стека до общего обработчика. Смешивать оба подхода нормально, и граница проходит так: ожидаемые бизнес-исходы описывают sealed-типами, а неожиданные технические сбои бросают исключениями. Признаком того, что граница проведена неправильно, служит when по sealed-иерархии с веткой is UnknownError и throw внутри.

arrow-kt (Either<E, A>, Raise-DSL, Option, оптики) даёт полноценный функциональный слой. Стоит ли его брать, зависит от команды. Если команда целиком согласна на такой стиль и готова учить новичков Raise-контексту, то да, потому что он даёт композицию ошибок без вложенных when. В обычной банковской команде на Spring скорее нет, потому что sealed-типы и исключения покрывают 95 % задач, а arrow добавляет зависимость, собственный стиль и барьер входа. Отдельно от остального иногда берут Either для валидации с накоплением ошибок (zipOrAccumulate), потому что здесь стандартной библиотеке действительно нечего предложить.

19.3 inline, crossinline, noinline и reified

Раздел 4.3 объяснил, что делает inline, а здесь собрано, когда объект лямбды на самом деле создаётся и когда нет, потому что именно от этого зависит, окупается ли модификатор. Таблица ниже перечисляет типовые ситуации, а после неё разобраны crossinline, noinline и границы reified:

Ситуация Выделение памяти
Лямбда в inline fun нет
Лямбда, не захватывающая ничего ({ it * 2 }) синглтон, создаётся один раз
Лямбда, захватывающая val из окружения объект на каждый вызов
Лямбда с noinline в inline fun объект
Лямбда, переданная в не-inline функцию объект (через invokedynamic с 2.0)
Ссылка на метод ::foo объект (или синглтон, если без receiver)

crossinline нужен, когда inline-лямбду вызывают не напрямую, а из другого объекта, например внутри Runnable или в другом потоке. Non-local return из неё в таком случае невозможен, и компилятор требует пометки. Типичный пример даёт обёртка вокруг executor:

inline fun <T> withRetry(times: Int, crossinline block: () -> T): T { /* ... */ }

noinline решает обратную задачу: конкретную лямбду нужно сохранить в поле или передать дальше как значение, а значит, встраивать её нельзя.

У reified тоже есть границы, и знать их нужно, чтобы не ждать от него того, чего он не умеет:

  • работает он только в inline fun;
  • внутри доступны T::class, T::class.java, is T, as T и object : TypeReference<T>() {};
  • для вложенных generic-параметров он не работает: reified T в List<T> после стирания даст List<*> на том уровне, где тип уже не reified;
  • reified-функцию нельзя вызвать из Java, поэтому для Java-потребителей дублируйте её перегрузкой с Class<T>;
  • создать экземпляр T() напрямую нельзя, только через рефлексию T::class.java.getDeclaredConstructor().newInstance();
  • каждый вызов встраивает тело, поэтому большие reified-функции раздувают байткод вызывающих.

19.4 value class и упаковка

Value class экономит выделение памяти только в части позиций, и чтобы понимать, окупается ли он в конкретном коде, нужно знать, где компилятор всё-таки его боксит. Таблица ниже сводит эти правила (Inline value classes); обратите внимание, что nullable-поле и элемент коллекции боксятся всегда:

Позиция Боксится?
Параметр/возврат функции нет (имя манглируется)
Локальная переменная нет
Поле класса типа UserId нет
Поле типа UserId? да
Элемент List<UserId>, ключ Map<UserId, _> да

В банковском домене value class применяют прежде всего для идентификаторов и денег, и пример ниже показывает и то, где он защищает, и то, где нет:

@JvmInline value class AccountId(val raw: Long)
@JvmInline value class Minor(val units: Long) {           // сумма в копейках
    init { require(units >= 0) { "negative amount" } }
    operator fun plus(o: Minor) = Minor(units + o.units)
    fun toBigDecimal(): BigDecimal = BigDecimal.valueOf(units, 2)
}

fun transfer(from: AccountId, to: AccountId, amount: Minor) { /* ... */ }
// transfer(to, from, amount) — теперь тоже ошибка компиляции? Нет: оба AccountId.
// Защита от перестановки однотипных параметров — только именованные аргументы.

Здесь нужна честная оговорка, и её стоит проговаривать вслух: value class защищает от перепутывания разных типов (AccountId vs CardId), но не от перестановки двух аргументов одного типа. От этого спасают только именованные аргументы в вызовах (transfer(from = a, to = b, amount = m)) и соответствующее правило в code style.

19.5 Стоимость идиом в цифрах

Ниже собраны конструкции Kotlin, стоимость которых обычно спрашивают на интервью или обсуждают на ревью, и для каждой указан порядок цены и то, когда о ней стоит беспокоиться. Большинство из них заметны только на горячем пути, и точные цифры для своего кода всё равно даст только замер:

  • Intrinsics.checkNotNullParameter обходится в одну проверку ссылки плюс потенциальный throw-блок, и JIT устраняет её на горячем пути, как только убедится, что null не приходит. Отключать её (-Xno-param-assertions) не стоит, потому что выигрыш неизмерим, а потеря диагностики большая.
  • by lazy по умолчанию работает в режиме SYNCHRONIZED, то есть через double-checked locking с volatile-полем, и чтение уже инициализированного значения стоит volatile read плюс виртуальный вызов getValue. На пути в миллионы операций в секунду это заметно, и там стоит брать lazy(LazyThreadSafetyMode.PUBLICATION), который обходится без блокировки, но может посчитать значение несколько раз, или NONE, если инициализация гарантированно однопоточная, например в конструкторе бина.
  • Строковые шаблоны вида "order $id status $status" на JVM 9+ компилируются в invokedynamic через StringConcatFactory, так же как в Java. И ловушка у них та же: шаблон в аргументе логгера (log.debug("order $id")) вычисляется всегда, даже если debug выключен. Поэтому пишите log.debug("order {}", id) или пользуйтесь Kotlin-логгером с лямбдой (log.debug { "order $id" } из kotlin-logging).
  • data class и copy. copy со значениями по умолчанию вызывается через copy$default с битовой маской и создаёт новый объект со всеми полями. Поэтому в горячем цикле «обновить одно поле у большого data class» означает полную копию, и для класса из 20 полей на миллионе итераций разница видна в allocation rate.
  • sequence против коллекций. На коллекции из 10–100 элементов обычные операторы быстрее, потому что они inline и не выделяют лямбды, а sequence создаёт по объекту-обёртке на оператор и лямбды не встраивает. На 10⁵–10⁶ элементов с ранним выходом (first, take(k), any) sequence выигрывает в разы или на порядки, так как обрабатывает k элементов вместо N. При полном проходе без раннего выхода разница остаётся в пределах десятков процентов и зависит от числа операторов, ведь каждый оператор в eager-варианте означает ещё один полный проход и ещё один ArrayList на N элементов. Правило большого пальца такое: если коллекция > 10⁴ элементов, или цепочка > 3 операторов, или есть ранний выход, переходите на asSequence().
  • Коллекции Kotlin поверх java.util не добавляют никаких накладных расходов, потому что это те же самые классы. Расходы появляются от map/filter, которые создают промежуточные списки, и от упаковки, ведь под List<Int> на деле лежит List<Integer>.
  • K2 (с Kotlin 2.0) сменил фронтенд компилятора, дав единое представление для всех платформ и более быстрый и строгий вывод типов. Для кода это означало, что часть программ, которые компилировались в K1 «по недосмотру», перестала компилироваться (smart cast через геттеры, некоторые случаи вывода типов), улучшилась диагностика и стали доступны новые возможности языка (context parameters стабильны в 2.4.0). На байткод K2 почти не влияет, потому что это фронтенд. С версии 2.4.0 -language-version=1.9 (K1) объявлен устаревшим (What's new in Kotlin 2.4.0).

20. Тестирование: подробности

Раздел 13 познакомил с MockK, runTest и Kotest, а здесь разобраны подробности, от которых зависит, будут ли тесты надёжными: какой вариант заглушки выбрать, как управлять виртуальным временем, почему тесты с корутинами нестабильны и как совместить Kotest с JUnit и Testcontainers. Почти все проблемы в этой области проявляются одинаково, тестами, которые проходят не потому, что код верен, а потому, что заглушка вернула 0 или корутина не успела стартовать. Ниже по порядку разобраны варианты заглушек MockK, виртуальное время и причины нестабильности, а затем сравнение Kotest с JUnit 5 и интеграция с Testcontainers.

20.1 MockK: mockk, spyk и relaxed

Варианты заглушки в MockK различаются тем, что происходит при вызове, который тест не записал, и от этого выбора зависит, поймает ли тест забытое взаимодействие или молча вернёт 0. Таблица ниже сопоставляет пять вариантов, а после неё собраны приёмы для suspend-функций, статики и object:

Вариант Поведение незаписанного вызова Когда применять
mockk<T>() MockKException: no answer found по умолчанию: тест явно описывает все взаимодействия
mockk<T>(relaxed = true) возвращает значение по умолчанию (0, "", пустая коллекция, relaxed-заглушка) заглушки, до которых тесту нет дела
mockk<T>(relaxUnitFun = true) Unit-функции молчат, остальные строги лучший компромисс для сервисов с void-методами
spyk(realObject) вызывает реальную реализацию частичная подмена одного метода у реального объекта
spyk<T>() заглушка с реальными реализациями интерфейса по умолчанию редко

Правило здесь простое: relaxed = true на весь проект даёт тесты, которые проходят только потому, что заглушка вернула 0, поэтому берите relaxUnitFun.

Для корутин и Kotlin-специфичных конструкций у MockK есть свой набор приёмов, и пример ниже собирает основные из них на платёжном шлюзе:

// suspend-функции
coEvery { gateway.charge(any()) } returns Receipt("r-1")
coEvery { gateway.charge(match { it.amount > Minor(100_000) }) } throws LimitExceeded()
coVerify(exactly = 1) { gateway.charge(any()) }
coVerifyOrder { gateway.reserve(any()); gateway.commit(any()) }

// захват аргумента
val slot = slot<ChargeRequest>()
coEvery { gateway.charge(capture(slot)) } returns Receipt("r-1")
service.pay(cmd)
assertEquals(cmd.orderId, slot.captured.orderId)

// захват всех вызовов
val all = mutableListOf<ChargeRequest>()
coEvery { gateway.charge(capture(all)) } returns Receipt("r-1")

// ответ, зависящий от аргумента
coEvery { rates.find(any()) } answers { Rate(firstArg<String>(), BigDecimal.ONE) }

// последовательные ответы: первый вызов падает, второй проходит (тест повторной попытки)
coEvery { gateway.charge(any()) } throws IOException("timeout") andThen Receipt("r-1")

// статика и расширения
mockkStatic(Instant::class)
every { Instant.now() } returns Instant.parse("2026-01-01T00:00:00Z")
mockkStatic("com.acme.MoneyExtKt")          // top-level и extension-функции файла MoneyExt.kt

// object и companion
mockkObject(FeatureFlags)
every { FeatureFlags.isEnabled("new-limits") } returns true

unmockkAll() в @AfterEach обязателен, если в тестах использовались mockkStatic/mockkObject/mockkConstructor, потому что они меняют глобальное состояние JVM и перетекают между тестами. Симптом узнаётся сразу: тест проходит в одиночку и падает в наборе.

Платить за MockK приходится тем, что создание заглушки заметно дороже, чем в Mockito, из-за инструментации ByteBuddy и чтения @kotlin.Metadata, и в наборе из тысяч тестов это складывается в секунды на прогон. Лечится это тем, что не подменяют моком то, что можно построить: data class строится быстрее, чем создаётся мок.

20.2 runTest, виртуальное время и нестабильные тесты

Виртуальное время позволяет проверить логику с задержками точно по шагам, но только если тест управляет часами явно, а тестируемый код не уходит на реальные диспетчеры. Пример ниже проверяет, что повторная попытка платежа происходит ровно через секунду, не раньше и не позже:

@Test
fun `retries with backoff`() = runTest {
    coEvery { gateway.charge(any()) } throws IOException() andThen Receipt("ok")
    val service = PaymentService(gateway, retryDelay = 1.seconds)

    val job = launch { service.pay(cmd) }
    advanceTimeBy(999.milliseconds); runCurrent()
    coVerify(exactly = 1) { gateway.charge(any()) }      // второй попытки ещё нет
    advanceTimeBy(2.milliseconds); runCurrent()
    coVerify(exactly = 2) { gateway.charge(any()) }
    job.join()
}

Для управления временем в runTest есть несколько инструментов: advanceTimeBy(d) продвигает виртуальные часы, runCurrent() выполняет всё, что запланировано на текущий момент, advanceUntilIdle() выполняет задачи, пока они не кончатся, testScheduler.currentTime возвращает текущее виртуальное время, backgroundScope служит scope для корутин, которые не должны завершиться, например подписок на hot-flow, а TestScope.testScheduler передают в собственный StandardTestDispatcher.

Тесты с корутинами бывают нестабильны по трём причинам:

  1. Захардкоженный диспетчер. withContext(Dispatchers.IO) внутри тестируемого кода уводит выполнение с тестового планировщика, так что виртуальное время перестаёт действовать, delay становится реальным, а порядок выполнения недетерминированным. Лечится это внедрением диспетчера (class Service(private val io: CoroutineDispatcher = Dispatchers.IO)). Можно ещё вызвать на весь тестовый набор Dispatchers.setMain(StandardTestDispatcher()), но это работает только для Dispatchers.Main, которого на бэкенде нет.
  2. Гонка между launch и проверкой. С StandardTestDispatcher дочерняя корутина не стартует до runCurrent()/advanceUntilIdle()/join(), поэтому тест, который сразу после launch делает coVerify, увидит ноль вызовов, а «иногда» будет проходить, если между ними случилась хоть какая-то приостановка. Лечится это явными runCurrent()/advanceUntilIdle().
  3. Реальное время в утверждениях. Проверка assertTrue(elapsed < 100) через System.currentTimeMillis() начинает то проходить, то падать на загруженном CI, поэтому в виртуальном времени используйте testScheduler.currentTime.

Кроме того, runTest падает с UncompletedCoroutinesError, если по завершении тела в scope теста остались незавершённые корутины, и это полезная возможность, потому что она ловит утечки. Если корутина должна жить весь тест, как подписка, её место в backgroundScope.

Так вы получаете shouldBe и Arb, не меняя инфраструктуру. В банковском контексте property-based тест выглядит так, на примере проверки того, что сумма в копейках без потерь переводится в BigDecimal и обратно:

@Test
fun `minor units roundtrip`() = runTest {
    checkAll(Arb.long(0L..1_000_000_000L)) { units ->
        Minor(units).toBigDecimal().movePointRight(2).toLong() shouldBe units
    }
}

Testcontainers с Kotlin работает так же, как в Java, но с двумя деталями, которые удобно знать заранее. Во-первых, контейнер объявляют в companion object с @Container и @JvmStatic, потому что без @JvmStatic JUnit не увидит статическое поле. Во-вторых, @DynamicPropertySource тоже требует @JvmStatic, как в тесте главной книги ниже:

@SpringBootTest
@Testcontainers
class LedgerIntegrationTest {
    companion object {
        @Container @JvmStatic
        val pg = PostgreSQLContainer("postgres:17-alpine")

        @DynamicPropertySource @JvmStatic
        fun props(r: DynamicPropertyRegistry) {
            r.add("spring.datasource.url", pg::getJdbcUrl)
            r.add("spring.datasource.username", pg::getUsername)
            r.add("spring.datasource.password", pg::getPassword)
        }
    }

    @Test fun `posts entry`() = runBlocking { /* реальная БД — виртуальное время не нужно */ }
}

В интеграционных тестах с реальной БД используйте runBlocking, а не runTest, потому что виртуальное время там только мешает, а runTest будет ругаться на «медленные» операции при таймауте 60 с.

21.1 NPE из Java-клиента через platform type

Первый инцидент показывает, как platform type из сгенерированного Java-клиента превращается в NPE в Kotlin-коде, который выглядит безопасным. Он интересен тем, что стек указывает не туда, где появился null, а лечение оказывается не в месте падения, а на границе с Java-клиентом.

Симптом. Раз в несколько часов в логе появляется NullPointerException в EnrichmentService.enrich, в строке с city.length, хотя код написан на Kotlin и city объявлен как String. На стейдже ошибка не воспроизводится.

Диагностика. Стек указывает на Kotlin-функцию, в которой нет ни одного явного !!, поэтому следующим шагом смотрим, откуда приходит значение. city берётся из geoClient.resolve(address).city, а клиент написан на Java, сгенерирован из OpenAPI и не содержит nullability-аннотаций, так что в Kotlin поле имеет тип String!. Декомпиляция байткода (javap -c) показывает Intrinsics.checkNotNullExpressionValue, но совсем не там, где её ждали: проверка стоит в точке присваивания в другой функции, а enrich получает уже non-null тип и никаких проверок не содержит. Запрос в логи geo-сервиса объясняет остальное: для адресов в сельской местности сервис штатно возвращает "city": null.

Корневая причина. Platform type приняли за non-null. Компилятор Kotlin не мог знать nullability этого поля, а код писали в предположении «раз String, значит, не null».

Лечение. На границе с клиентом поставили тонкий адаптер, в котором типы объявлены честно:

@Component
class GeoAdapter(private val client: GeoClient) {
    fun resolve(address: String): GeoInfo? {
        val raw = client.resolve(address) ?: return null
        return GeoInfo(
            city = raw.city,                 // тип объявлен как String? в GeoInfo — честно
            region = raw.region ?: UNKNOWN_REGION,
            countryCode = raw.countryCode ?: return null,   // без страны запись бессмысленна
        )
    }
}

Как не допустить. (1) Ввести правило, по которому ни один тип из Java-клиента не уходит дальше адаптера. (2) Включить в OpenAPI-генераторе генерацию JSpecify/JetBrains-аннотаций по required-списку схемы. (3) Добавить в сборку флаг -Xjsr305=strict. (4) Написать контрактный тест, который подаёт в адаптер ответ со всеми полями null.

21.2 data class-сущность потеряла строку в HashSet

Второй инцидент про то, как равенство по значению у data class ломает JPA-сущность, и про то, что эффектов оказалось два: один виден сразу по данным в БД, а второй, более тонкий, связан с изменением hashCode после присвоения id и обнаружился уже после первого исправления.

Симптом. Заказ сохраняется с тремя позициями, а в БД попадают только две. Воспроизводится это только для заказов, в которых две позиции совпадают и по товару, и по количеству.

Диагностика. @OneToMany объявлен как MutableSet<OrderLine>, а OrderLine объявлен как data class. Две позиции с одинаковыми полями (id = null до сохранения, один и тот же товар и одно и то же количество) равны по сгенерированному equals, и Set схлопнул их в одну. Позже нашли и второй, более тонкий эффект: код, который клал сущность в HashSet до persist, а искал её после, не находил её, потому что после присвоения id изменился hashCode, а объект остался в старом бакете.

Корневая причина. У объекта с identity-семантикой и изменяющимся id были equals/hashCode по значению.

Лечение. OrderLine перевели в обычный класс, где equals определён как other is OrderLine && id != null && id == other.id, а hashCode возвращает константу. Коллекцию позиций перевели на MutableList, потому что порядок строк важен для печатной формы, а уникальности по значению нет и быть не должно.

Как не допустить. В code style ввели правило, запрещающее @Entity + data class, и проверяют его правилом detekt или простым тестом, который через рефлексию обходит все @Entity и падает, если класс объявлен как data:

@Test
fun `no data class entities`() {
    val entities = Reflections("com.acme").getTypesAnnotatedWith(Entity::class.java)
    val offenders = entities.filter { it.kotlin.isData }
    assertTrue(offenders.isEmpty()) { "data class entities: $offenders" }
}

21.3 runCatching перехватил отмену, и корутина не остановилась

Третий инцидент показывает, как runCatching превращает таймаут в повторное списание. Он особенно неприятен в платёжном сервисе, потому что клиент уже получил ответ о неудаче, а корутина, которая должна была остановиться, продолжила работу и отправила платёж в шлюз ещё раз, так что деньги клиента списались дважды.

Симптом. После того как на вызов внешнего процессинга поставили таймаут, в логах появились «двойные» списания: платёж уходил в шлюз повторно через 30 секунд после того, как клиент получил ответ «таймаут».

Диагностика. На стейдже включили DebugProbes и воспроизвели ситуацию: после withTimeout корутина, которая должна была умереть, оставалась в дампе в состоянии RUNNING. В коде нашёлся цикл повторных попыток, внутри которого стоял runCatching { gateway.charge(req) }. TimeoutCancellationException, будучи подклассом CancellationException, ловился runCatching и превращался в Result.failure, после чего цикл делал delay, который сразу же бросал отмену. И здесь обнаружилась вторая ошибка: delay тоже стоял внутри runCatching. В результате отмена гасилась на каждой итерации, цикл проходил все три попытки и отправлял платёж повторно.

Корневая причина. runCatching ловит Throwable, в том числе CancellationException, которая в корутинах служит управляющим сигналом, а не ошибкой.

Лечение. runCatching заменили собственным coRunCatching (раздел 16.6) и добавили currentCoroutineContext().ensureActive() в начало каждой итерации цикла повторных попыток. Кроме того, сам таймаут теперь превращается в доменное исключение сразу за withTimeout.

Как не допустить. Завести правило detekt, запрещающее runCatching в файлах с suspend, и пункт в чеклисте code review, по которому любой catch (e: Exception) в suspend-функции обязан либо иметь ветку для CancellationException, либо вызывать ensureActive(). Закрепить это тестом: runTest { val job = launch { retryingCall() }; advanceTimeBy(...); job.cancel(); advanceUntilIdle(); coVerify(exactly = 1) { gateway.charge(any()) } }.

21.4 Утечка корутины в GlobalScope после запроса

Четвёртый инцидент про утечку памяти из-за GlobalScope, которая копилась днями и проявилась только через OOM. Корутины в нём никто не отменял, потому что у них не было родителя, а число одновременных отправок уведомлений ничем не ограничивалось, так что при недоступности внешнего сервиса их становилось всё больше.

Симптом. Куча медленно растёт на всех подах, и через 3–4 дня работы они падают с OOM. GC-логи показывают, что старое поколение растёт монотонно, а full GC освобождает всё меньше памяти.

Диагностика. Heap dump и jmap -histo показали десятки тысяч экземпляров StandaloneCoroutine и, что важнее, столько же NotificationContext, каждый со ссылкой на объект запроса и на ByteArray с телом. Поиск по коду нашёл в контроллере GlobalScope.launch { notifier.send(ctx) }, написанный с намерением «отправить уведомление, не задерживая ответ». Клиент уведомлений при недоступности внешнего сервиса повторял отправку с экспоненциальным backoff до часа, так что корутины копились, никто их не отменял, а привязки к жизненному циклу запроса у них не было.

Корневая причина. GlobalScope запускает корутины без родителя, и их не отменяет ни завершение запроса, ни остановка контекста. Вдобавок число одновременных отправок ничем не ограничивалось.

Лечение. (1) Завели бин applicationScope с SupervisorJob и destroyMethod = "cancel" (раздел 16.7). (2) Под диспетчер уведомлений выделили limitedParallelism(20). (3) Добавили внутреннюю очередь фиксированного размера Channel(capacity = 1000, onBufferOverflow = DROP_OLDEST) с метрикой отброшенных сообщений. (4) Ввели общий таймаут на отправку в 30 секунд.

Как не допустить. Запретить GlobalScope в CI (grep -r "GlobalScope" src/main && exit 1); найти его тривиально, потому что он всё равно требует @OptIn(DelicateCoroutinesApi::class). И ввести правило: «fire-and-forget» в веб-приложении означает либо очередь (Kafka/outbox, главы 29 и 31), либо именованный scope с бюджетом и метриками, но никогда не «просто launch».

21.5 Dispatchers.IO исчерпан блокирующим вызовом

Пятый инцидент показывает в действии лимит 64 у Dispatchers.IO, о котором шла речь в разделе 7.2: сервис деградирует, хотя все метрики пулов и базы данных остаются зелёными, и найти причину помогают только thread dump и простая арифметика пропускной способности, после которой узкое место становится очевидным.

Симптом. При нагрузке выше ~150 rps p99 вырос со 120 мс до 8 с. При этом CPU занят на 20 %, пул Hikari на треть, а pg_stat_activity показывает 10 активных запросов из 40 возможных, так что все дашборды зелёные, кроме латентности.

Диагностика. Thread dump показал 64 потока DefaultDispatcher-worker-*, и все они стояли в socketRead0 внутри драйвера внешнего сервиса скоринга. Дальше всё решила арифметика: скоринг отвечает за 400 мс, 64 потока дают 160 операций в секунду, и пропускная способность упёрлась ровно в лимит Dispatchers.IO. Остальные корутины стояли в очереди диспетчера, которую не видно ни в одной метрике, потому что ни Hikari, ни БД, ни HTTP-пул о ней не знают.

Корневая причина. Блокирующий HTTP-клиент (старый Apache HttpClient) вызывался через withContext(Dispatchers.IO), и лимит 64 стал узким местом для всего сервиса, включая эндпоинты, которым скоринг вообще не нужен.

Лечение. (1) Для скоринга выделили отдельный диспетчер Dispatchers.IO.limitedParallelism(32, "scoring"), и теперь исчерпание его бюджета не затрагивает остальные операции. (2) Общий блокирующий диспетчер перевели на виртуальные потоки через Executors.newVirtualThreadPerTaskExecutor().asCoroutineDispatcher(). (3) Добавили таймер «время ожидания входа в блок withContext», который служит прямой метрикой очереди диспетчера. (4) В долгосрочном плане клиент заменяют на WebClient с awaitBody().

Как не допустить. Ввести правило, по которому каждый внешний ресурс получает именованный диспетчер с явным бюджетом, равным его пулу соединений или меньшим. Включить BlockHound в тестовом профиле, чтобы блокирующий вызов на Dispatchers.Default падал сразу, и завести оповещение на «время ожидания диспетчера > 50 мс».

21.6 @Transactional на suspend не откатил транзакцию

Шестой инцидент про транзакцию JPA, размазанную по двум потокам и двум соединениям, из-за чего списание осталось в БД без зачисления. Он коварен тем, что в интеграционных тестах всё работало, а сломалось только в проде, где корутина после приостановки действительно сменила поток.

Симптом. При ошибке во второй половине бизнес-операции первая половина оставалась в БД: списание было, а зачисления не было. В интеграционных тестах при этом всё откатывалось корректно.

Диагностика. Метод был объявлен как @Transactional suspend fun transfer(...), и внутри него два вызова репозиториев JPA шли через withContext(Dispatchers.IO). В логах Hibernate видно два разных соединения для двух операций, и причина ясна из механики: TransactionSynchronizationManager держит соединение в ThreadLocal, а withContext переносит выполнение на другой поток пула, так что второй репозиторий открывает собственную транзакцию. Первая транзакция при ошибке во второй не откатывается, потому что она уже зафиксирована. В тестах всё работало потому, что runBlocking выполнял всё на одном потоке, и соединение «случайно» оказывалось тем же.

Корневая причина. JPA-транзакция привязана к потоку, а suspend эту привязку ломает, и документация Spring поддержки такого сочетания не обещает (раздел 10.4).

Лечение. Транзакцию целиком поместили внутрь одного withContext на выделенном диспетчере БД:

@Service
class TransferService(
    private val tx: TransactionTemplate,
    private val accounts: AccountRepository,
    @Qualifier("dbDispatcher") private val db: CoroutineDispatcher,
) {
    // Транзакция целиком внутри одного withContext — один поток, одно соединение
    suspend fun transfer(cmd: TransferCommand): Receipt = withContext(db) {
        tx.execute {
            val from = accounts.findByIdOrNull(cmd.from) ?: error("no account ${cmd.from}")
            val to = accounts.findByIdOrNull(cmd.to) ?: error("no account ${cmd.to}")
            from.debit(cmd.amount)
            to.credit(cmd.amount)
            Receipt(cmd.id)
        }!!
    }
}

Критично, чтобы внутри tx.execute { } не было ни одного suspend-вызова, потому что любая приостановка там снова разорвёт привязку к потоку.

Как не допустить. (1) Написать архитектурный тест, который проверяет, что ни одна suspend-функция не помечена @Transactional, если в проекте нет реактивного TransactionManager. (2) Ввести правило, что транзакционные методы не бывают suspend, и отмечать их суффиксом Blocking или выносить в отдельный слой репозиториев, который вызывается только из withContext(db). (3) Добавить интеграционный тест на откат, который выполняется не через runBlocking в одном потоке, а через реальный HTTP-вызов к поднятому приложению.

22. Грабли и антипаттерны

Ниже собраны двадцать восемь граблей, на которые команды наступают в Kotlin-сервисах чаще всего; большинство из них уже разобрано в главе, а здесь они сведены в один список для быстрой проверки кода и для подготовки к интервью. Каждый пункт построен по одной схеме: как проблема проявляется, почему она возникает и чем её лечат, так что по симптому из лога или дампа можно сразу найти причину. Первые пункты касаются null-safety, корутин и Spring, середина посвящена JPA, Jackson и тестам, а последние пункты относятся к Flow, интеропу и производительности.

  1. NPE из platform type в неожиданном месте. Проявляется это как NullPointerException: ... must not be null в строке присваивания или вызова Kotlin-функции, хотя «Kotlin же null-safe». Причина в том, что значение из Java-API без аннотаций объявлено или выведено как non-null. Лечится явными типами на Java-границах, флагом -Xjsr305=strict и JSpecify @NullMarked в своих Java-модулях.
  2. runBlocking внутри suspend-кода или реактивного кода. Под нагрузкой сервис виснет, и thread dump показывает, что все DefaultDispatcher-worker или reactor-http-nio стоят в BlockingCoroutine.joinBlocking. Причина в том, что поток диспетчера блокируется ожиданием корутины, которой нужен этот же пул. Лечится это тем, что runBlocking оставляют только на границе с блокирующим миром, а внутри используют withContext.
  3. Очередь на Dispatchers.IO при 64 потоках. Латентность растёт, хотя пул соединений недогружен, а CPU низкий. Причина в том, что одновременных блокирующих операций больше 64. Лечится это limitedParallelism под размер пула соединений или VT-диспетчером, а длину очереди можно измерить через DebugProbes.
  4. @Transactional на suspend fun с JPA. Данные пишутся без транзакции, вылетает TransactionRequiredException или коммит уходит на другом соединении. Причина в том, что ThreadLocal-транзакция теряется при смене потока. Лечится через withContext(db) { transactionTemplate.execute { } } или переходом на R2DBC.
  5. data class в роли @Entity. Появляются LazyInitializationException из hashCode/toString, элементы теряются в HashSet, а на двунаправленных связях случается StackOverflowError. Лечится обычным классом с equals по id, константным hashCode и toString без связей.
  6. GlobalScope.launch в Spring-бине. Тесты с несколькими контекстами держат потоки и утекают, graceful shutdown не дожидается фоновых задач, а исключения теряются. Лечится полем бина CoroutineScope(SupervisorJob() + handler) с cancel() в @PreDestroy.
  7. async без await(). Ошибка исчезает без следа, и в логах ничего нет. Причина в том, что исключение лежит в Deferred, await() никто не вызвал, а в supervisor-scope родитель не отменяется. Лечится тем, что для fire-and-forget берут launch с CoroutineExceptionHandler, а async используют только вместе с await().
  8. Проглоченная CancellationException. После job.cancel() или таймаута корутина продолжает работать, и появляются вызовы «после отмены» и дублирование операций. Причина в catch (e: Exception) или runCatching без переброса исключения. Лечится строкой if (e is CancellationException) throw e или вызовом ensureActive() после catch.
  9. flow { withContext(IO) { emit() } }. Поток падает с IllegalStateException: Flow invariant is violated. Лечится через flowOn(Dispatchers.IO) или channelFlow.
  10. Final-класс без all-open. @Cacheable/@Transactional молча не работают, или сервис падает с BeanCreationException: Cannot subclass final class. Лечится плагином kotlin-spring и явными аннотациями в allOpen { } для нестандартных случаев (@Retryable, @Entity).
  11. ?.let { } ?: fallback() с nullable-результатом лямбды. Fallback вызывается даже тогда, когда объект не null. Лечится переходом на if/else.
  12. lateinit вместо конструкторной инъекции в проде. Появляется UninitializedPropertyAccessException в init {} или из-за порядка @PostConstruct, а тесты начинают требовать Spring-контекст. Лечится первичным конструктором.
  13. is-префикс в DTO с Jackson. Поле isActive сериализуется как active и не читается обратно. Лечится аннотацией @JsonProperty("isActive") или переименованием поля.
  14. Non-null Int/Long, который из null в JSON превратился в 0. Сумма платежа оказывается равной 0 вместо ошибки валидации. Лечится включением FAIL_ON_NULL_FOR_PRIMITIVES в ObjectMapper или типом Long? с явной валидацией.
  15. Dispatchers.IO, захардкоженный в сервисе. runTest не пропускает delay, и тесты идут секундами. Лечится тем, что CoroutineDispatcher внедряют через конструктор.
  16. Extension-функция, затенённая членом или не полиморфная. После апгрейда библиотеки поведение меняется без изменения кода, потому что в ней появился одноимённый member. Лечится тем, что чужие типы не расширяют именами, которые могут появиться в их API, и unit-тестом на границе.
  17. Мутация Kotlin-List из Java. «Неизменяемый» объект вдруг изменился, потому что под List лежит ArrayList. Лечится через toList() или Collections.unmodifiableList на границе либо через kotlinx.collections.immutable.
  18. synchronized или ReentrantLock через suspend-точку. Возникает IllegalMonitorStateException или взаимоблокировка. Лечится переходом на kotlinx.coroutines.sync.Mutex/Semaphore.
  19. limitedParallelism, вызванный внутри метода. Лимит не работает, а в дампе сотни потоков. Причина в том, что каждый вызов создаёт новый вид диспетчера со своим счётчиком. Лечится тем, что вид создают один раз как бин или поле.
  20. launch(SupervisorJob()) вместо supervisorScope. Корутина не отменяется при shutdown, родитель её не ждёт, а исключения уходят в stderr. Причина в том, что переданный Job отвязывает корутину от дерева. Лечится через supervisorScope { } или scope-бин.
  21. suspendCoroutine вместо suspendCancellableCoroutine. withTimeout истёк, а операция висит и держит соединение, потому что мост к обратному вызову не реагирует на отмену. Лечится через suspendCancellableCoroutine с invokeOnCancellation.
  22. MutableSharedFlow(replay = N) в роли «кэша». Куча растёт, а объекты событий живут вечно, потому что буфер replay навсегда удерживает N последних значений. Лечится значением replay = 0 для шины и StateFlow для состояния.
  23. StateFlow не эмитит обновление. Подписчик не получает новое значение, потому что конфляция вместе с дедупликацией по equals отбрасывает значение, равное старому. Лечится тем, что в значение включают версию или метку времени, либо переходом на SharedFlow.
  24. Java мутировал Kotlin-List. «Неизменяемая» коллекция в агрегате изменилась, или в чужом Java-коде вылетел UnsupportedOperationException. Лечится через List.copyOf/unmodifiableList на границе, а во входящие Java-методы стоит передавать ArrayList(...).
  25. Checked-исключение из Kotlin не ловится в Java. Java-код не компилируется с catch (IOException e), поэтому разработчик ловит Exception или не ловит ничего, и ошибка пролетает мимо обработчика. Лечится аннотацией @Throws(IOException::class) на публичных Kotlin-методах, которые вызываются из Java.
  26. Забытый @field: на валидации @ConfigurationProperties или DTO. Некорректный конфиг проходит, и @NotBlank не срабатывает, потому что аннотация ушла на параметр конструктора. Лечится use-site target @field: и тестом на некорректный конфиг.
  27. Строковый шаблон в аргументе логгера. Форматирование заметно нагружает CPU даже при выключенном debug, потому что log.debug("x=$x") вычисляется всегда. Лечится записью log.debug("x={}", x) или логгером с лямбдой.
  28. copy() managed-сущности. На ровном месте появляются OptimisticLockException или LazyInitializationException, потому что копия detached, у неё тот же id и версия, а прокси привязаны к старой сессии. Лечится тем, что поля меняют на самом managed-объекте, и тогда dirty checking сделает UPDATE.

23. Диагностика

Этот раздел собирает инструменты и порядок действий для типовых проблем Kotlin-сервиса: зависших корутин, блокировок на диспетчере, невидимой очереди Dispatchers.IO, пустых трассировок стека, несозданных прокси и медленной компиляции. Сначала по каждой проблеме сказано, каким инструментом её видно и на что смотреть, а в конце даны три пошаговых чеклиста для ситуаций, с которыми дежурный сталкивается чаще всего: сервис тормозит при низком CPU, корутина не останавливается после отмены, транзакция не откатилась. Завершает раздел заметка о том, как читать падения runTest.

Зависшие и утекшие корутины. Чтобы их увидеть, подключают kotlinx-coroutines-debug и включают пробы флагом -Dkotlinx.coroutines.debug (или через DebugProbes.install() в тесте). Вызов DebugProbes.dumpCoroutines(System.out) печатает дамп, где для каждой корутины видны её состояние (SUSPENDED/RUNNING), точка приостановки и дерево Job. В проде для этого используют агент -javaagent:kotlinx-coroutines-core-jvm.jar (⚠️ доступность агента в 1.10 отдельно не перепроверял) или endpoint, который вызывает DebugProbes.dumpCoroutinesInfo(). Имена тоже помогают: CoroutineName("order-enricher") вместе с -Dkotlinx.coroutines.debug добавляют @coroutine#N к имени потока в thread dump, и тогда jstack/jcmd Thread.print показывает, какая корутина сейчас держит поток.

Блокировки на диспетчере. В тестах их ловит BlockHound: после BlockHound.install(CoroutinesBlockHoundIntegration()) блокирующий вызов бросает BlockingOperationError с указанием точки, где он произошёл. В проде снимают thread dump (jcmd <pid> Thread.print) и фильтруют его по DefaultDispatcher-worker: если все потоки стоят в socketRead0/Object.wait/park внутри JDBC, причина найдена. JFR (jcmd <pid> JFR.start) даёт то же самое через события jdk.ThreadPark/jdk.JavaMonitorWait по потокам диспетчера.

Очередь Dispatchers.IO. Прямой метрики для неё нет, поэтому измеряют косвенно: Micrometer-таймером вокруг withContext(Dispatchers.IO), где время от вызова до первой строки внутри блока и есть ожидание в очереди, и Executors-метриками, если вы используете собственный пул через asCoroutineDispatcher() с ExecutorServiceMetrics.

Stack trace recovery. Если стеки исключений из корутин выглядят «пустыми», то есть состоят из одной строки resumeWith, значит, recovery выключен (-Dkotlinx.coroutines.stacktrace.recovery=false) или у исключения нет конструктора (String). В тестах и на стейджинге recovery стоит включить, а в проде решать взвешенно, помня о стоимости копирования исключений.

Прокси и final. Сообщение BeanCreationException: ... Cannot subclass final class означает, что не подключён all-open. Проверить байткод можно командой javap -p -v build/classes/kotlin/main/com/acme/Service.class | grep -E "flags|ACC_FINAL", и класс, скомпилированный с плагином, не должен быть ACC_FINAL. Для no-arg при подключённом kotlin-jpa команда javap -p покажет public com.acme.Order(), то есть синтетический конструктор.

Байткод корутин и лямбд. javap -p -c на *Kt.class и *$1.class показывает, сколько получилось классов state machine, где стоят Intrinsics.checkNotNull* и заинлайнены ли лямбды (в дескрипторах не должно быть Function0/Function1). Плагин IDE «Show Kotlin Bytecode → Decompile» делает то же самое интерактивно, а для value class там видны mangled имена вида find-<hash>.

Компиляция. ./gradlew build --scan или --profile показывают время compileKotlin в сравнении с compileJava, а настраивают его через kotlin.daemon.jvmargs и org.gradle.configuration-cache. -Xreport-perf у kotlinc выводит время по фазам компиляции, а -Wextra (2.1+) включает дополнительные проверки, в том числе на избыточные !! и небезопасные вызовы.

Nullability на границах. Здесь помогают флаги -Xjsr305=strict и -Xtype-enhancement-improvements-strict-mode, а предупреждение компилятора Type mismatch: inferred type is String! but String was expected служит сигналом того, что в коде platform type.

Чеклист «сервис тормозит, CPU низкий».

  1. Снять jcmd <pid> Thread.print > td.txt и посмотреть, сколько там потоков DefaultDispatcher-worker-* и в каком они состоянии. Если все стоят в socketRead0/park внутри клиента или драйвера, значит, исчерпан Dispatchers.IO.
  2. Посчитать их через grep -c "DefaultDispatcher-worker" td.txt: если их ровно 64 (или max(64, cores)), это лимит, а не совпадение.
  3. Проверить метрики пулов (Hikari hikaricp.connections.active, HTTP-клиент), и если они недогружены, узкое место находится выше, в очереди диспетчера.
  4. Замерить время входа в блок таймером вокруг withContext(dispatcher), который фиксирует момент до вызова и момент первой строки внутри; рост этого времени означает очередь диспетчера.
  5. Разнести ресурсы по именованным limitedParallelism и повторить замер.
  6. Для окончательного диагноза вызвать DebugProbes.dumpCoroutines() и сравнить, сколько корутин находится в состоянии CREATED (в очереди), а сколько в RUNNING.

Чеклист «корутина не останавливается после отмены».

  1. Проверить, есть ли в теле вообще suspend-точки, потому что цикл без них не отменяется никогда, и в него нужно добавить ensureActive()/yield().
  2. Выполнить grep -rn "runCatching\|catch (e: Exception)\|catch (e: Throwable)" src/main по файлам с suspend и искать проглоченную CancellationException.
  3. Проверить, не блокирующий ли это вызов: withContext(IO) { jdbc.query() } не прерывается, и здесь нужен таймаут на уровне драйвера или БД.
  4. Проверить, не запущена ли корутина через GlobalScope или launch(Job()), ведь тогда она может просто находиться вне дерева.
  5. Вызвать DebugProbes.dumpCoroutines() после cancel(): если корутина осталась в дампе, её точка приостановки покажет, где она застряла.
  6. Закрепить исправление тестом runTest { val j = launch { subject() }; advanceUntilIdle(); j.cancelAndJoin(); coVerify(exactly = 1) { ... } }.

Чеклист «транзакция не откатилась».

  1. Посмотреть в логе Hibernate или через spring.jpa.show-sql, одно ли соединение используется на всю операцию или несколько, а для этого включить logging.level.org.springframework.transaction=DEBUG и найти границы транзакции.
  2. Проверить, не объявлен ли метод одновременно suspend и @Transactional, потому что с JPA это несовместимо (раздел 10.4).
  3. Проверить, нет ли suspend-вызова внутри tx.execute { }, ведь любая приостановка рвёт привязку к потоку.
  4. Проверить self-invocation, то есть вызов this.method() внутри бина, при котором прокси обходится, а также @Transactional на private- или final-методе, который тоже не работает.
  5. Выполнить javap -p Service.class | grep final и убедиться, что не забыт kotlin("plugin.spring").

Тесты с корутинами. Падение runTest с UncompletedCoroutinesError означает, что корутина утекла из scope теста, и обычно это launch во внедрённом scope, который забыли отменить. Сообщение TimeoutCancellationException after 60 s указывает либо на реальный delay на не-тестовом диспетчере, либо на взаимоблокировку.

24. Вопросы на интервью

Ниже двадцать шесть вопросов, которые по Kotlin на бэкенде задают чаще всего, и к каждому дана готовая формулировка ответа. Ответы рассчитаны на то, чтобы произнести их вслух за сорок–семьдесят секунд, и построены по одной схеме: сначала механизм, затем следствие из него и в конце практический вывод или граница применимости. Первые двадцать два вопроса проверяют понимание корутин, null-safety, классов, Spring и JPA, следующие три построены как ловушки, в которых правдоподобный ответ оказывается неверным, а последний вопрос поведенческий и разобран по схеме STAR. Заучивать формулировки дословно не нужно: полезнее увидеть в них структуру хорошего ответа, в котором механизм объясняется, а не пересказывается.

  1. Что происходит с suspend fun при компиляции? Компилятор выполняет CPS-трансформацию: он добавляет к функции параметр Continuation<T> и меняет возвращаемый тип на Any?. Тело при этом превращается в state machine, то есть в один класс с полем label и полями для тех локальных переменных, которые живут через точку приостановки. Когда функция действительно приостанавливается, она возвращает маркер COROUTINE_SUSPENDED, а продолжение потом вызывается через continuation.resumeWith, и when(label) прыгает в нужное состояние. Поэтому состояние корутины живёт в куче как обычный объект, а не на стеке потока, и миллион приостановленных корутин стоит десятки мегабайт, а не гигабайты.

  2. Чем coroutineScope отличается от supervisorScope? Общее у них то, что оба ждут всех своих детей и оба отменяют детей, когда отменяют родителя. Различаются они тем, как распространяется ошибка ребёнка. В coroutineScope она отменяет siblings и пробрасывается из scope, то есть работает принцип fail-fast. В supervisorScope siblings продолжают работать, а исключение ребёнка либо обрабатывает он сам, либо для launch оно уходит в CoroutineExceptionHandler, а для async остаётся лежать в Deferred до вызова await(). Поэтому первый берут, когда нужно «собрать всё или ничего», а второй, когда нужно «собрать то, что получилось».

  3. Почему async не бросает исключение сразу, и в чём здесь ловушка? async сохраняет исключение в Deferred и бросает его при await(), и именно поэтому await() можно обернуть в try/catch. Ловушка в том, что в обычном, не supervisor, scope упавший async всё равно немедленно отменяет родителя, и try/catch вокруг await() не спасает, потому что упал не await, а весь scope. Если нужно пережить ошибку одного async, нужен supervisorScope. Вторая ловушка обратная: если в supervisor-scope у async нет await(), исключение теряется навсегда.

  4. Что за лимит 64 у Dispatchers.IO, и почему он опасен на бэкенде? Dispatchers.IO работает как вид общего пула CoroutineScheduler с лимитом параллелизма max(64, cores). Если сервис делает 200 одновременных JDBC-вызовов через withContext(IO), то 64 из них работают, а 136 стоят в очереди диспетчера, которую не видят ни пул соединений, ни БД, так что латентность растёт, а метрики остаются зелёными. Лечить это можно тремя способами: выделить Dispatchers.IO.limitedParallelism(n) под размер пула соединений, пользуясь тем, что виды не ограничены базовым лимитом, поднять kotlinx.coroutines.io.parallelism или перейти на newVirtualThreadPerTaskExecutor().asCoroutineDispatcher().

  5. Как работает отмена корутины, и что происходит с блокирующим кодом внутри неё? Отмена в корутинах кооперативная: cancel() переводит Job в состояние Cancelling, а код узнаёт об этом только в suspend-точках библиотеки, таких как delay, yield, withContext и emit, которые проверяют isActive и бросают CancellationException. Поэтому цикл без suspend-вызовов не отменится, и в него нужно добавить ensureActive() или yield(). Блокирующий вызов внутри withContext(IO) тоже не отменится, пока не вернёт управление, а runInterruptible помогает только коду, который уважает Thread.interrupt(), потому что транслирует отмену именно в него. Cleanup в уже отменённой корутине можно выполнить только через withContext(NonCancellable).

  6. Почему runCatching в корутинах считается граблями? Он ловит CancellationException, и отменённая корутина продолжает выполнение так, как будто отмены не было: уходит в fallback, затем в следующую операцию и так до конца тела. Отсюда правило: в любом catch (e: Exception) внутри корутин нужно перебрасывать CancellationException или вызывать ensureActive() после catch. То же самое относится к retry-обёрткам и к try/catch внутри цикла.

  7. Как Flow обходится без request(n) и всё-таки даёт backpressure? emit объявлен как suspend-функция и не возвращается, пока downstream не обработал элемент, а по умолчанию производитель и потребитель работают в одной корутине, так что производитель физически не может опередить потребителя. Буферизацию вводят явно: buffer(n) запускает upstream в отдельной корутине с каналом между ними, conflate() оставляет только последнее значение, а collectLatest отменяет обработку, как только приходит новый элемент. flowOn под капотом делает то же самое, что buffer, только запускает upstream на другом диспетчере.

  8. Почему data class нельзя делать JPA-сущностью? Потому что equals/hashCode по всем полям ломают контракт, который нужен сущности. До persist у неё id = null, после него уже нет, и объект в HashSet «теряется». Кроме того, hashCode и toString инициализируют lazy-связи, что вне сессии даёт LazyInitializationException, и рекурсивно обходят двунаправленные связи вплоть до StackOverflowError. Наконец, copy() создаёт detached-объект с тем же id, и его merge может дать OptimisticLockException. Сущность определяется идентичностью, а не значением, поэтому ей нужен обычный класс с equals по id и константным hashCode.

  9. Зачем нужны плагины kotlin-spring и kotlin-jpa? Классы Kotlin по умолчанию final, а Spring оборачивает бины в прокси CGLIB-подклассами для @Transactional, @Cacheable и @Configuration, и final-класс подклассить нельзя. kotlin-spring подключает all-open, и тот открывает классы с @Component, @Transactional, @Async, @Cacheable, @SpringBootTest и классы, мета-аннотированные ими. kotlin-jpa подключает no-arg, и тот генерирует для @Entity/@Embeddable/@MappedSuperclass синтетический конструктор без параметров, доступный только рефлексией, то есть как раз для Hibernate. А чтобы Hibernate мог строить lazy-прокси, сущности нужно ещё открыть через allOpen { annotation("jakarta.persistence.Entity") }.

  10. Работает ли @Transactional на suspend fun? Работает только с реактивным TransactionManager, то есть с R2DBC или reactive Mongo: начиная со Spring 6.1 фреймворк оборачивает suspend-метод в mono {} и применяет TransactionalOperator. С JPA и JDBC он не работает, потому что транзакция привязана к потоку через ThreadLocal, а корутина после приостановки продолжается на другом потоке. Поэтому решение такое: не делать метод suspend, а вызывать его целиком в withContext(db) { transactionTemplate.execute { } } на одном потоке, лучше на VT-диспетчере, либо переходить на R2DBC.

  11. Корутины или virtual threads: что и когда выбирать? Виртуальные потоки решают проблему «блокирующий код держит поток» без изменения кода, и для Java-проекта на Spring MVC это выбор по умолчанию. Корутины дают то, чего у VT нет или что появилось там позже: structured concurrency и отмену как first-class концепцию в стабильном API, Flow с backpressure и дешёвую приостановку без копирования стека. При этом от блокирующих вызовов корутины не спасают и требуют suspend в сигнатурах. Поэтому в Kotlin-проекте на WebFlux я беру корутины, на MVC с Java 21 беру VT для обработки запросов и корутины для оркестрации, а Dispatchers.IO заменяю VT-диспетчером.

  12. Что такое platform type, и где кончается null-safety? Тип, пришедший из Java без nullability-аннотаций, компилятор видит как T!, то есть «T или T?», и позволяет присвоить его в non-null переменную, вставляя runtime-проверку в точке присваивания. Null-safety действует только там, где объект создан Kotlin-кодом, а всё, что создаёт рефлексия, будь то Hibernate, Jackson без Kotlin-модуля или Mockito, может положить null в non-null поле. Kotlin понимает JSpecify, которым размечен Spring 7, JSR-305 с флагом -Xjsr305=strict и JetBrains-аннотации, поэтому Java-границы нужно размечать.

  13. Во что компилируется value class, и когда он всё-таки боксится? Он компилируется в само значение: параметр типа UserId(val v: Long) становится long, и выделений памяти нет. Упаковка происходит тогда, когда нужен ссылочный тип, то есть в generic-позиции (List<UserId>), в nullable-типе (UserId?), в интерфейсном типе и в Any. Имена функций с value class в параметрах манглируются (find-<hash>), чтобы find(UserId) и find(OrderId) не конфликтовали, и поэтому из Java такой метод не вызвать без @JvmName.

  14. Иммутабелен ли Kotlin List? Нет, он read-only только на уровне типов: это интерфейс без мутирующих методов, но в байткоде он остаётся java.util.List, и под listOf() лежит Arrays$ArrayList, а под map {} лежит ArrayList. Поэтому Java-код или приведение as MutableList могут его мутировать. Настоящую неизменяемость дают List.copyOf/Collections.unmodifiableList на границе или библиотека kotlinx.collections.immutable.

  15. Что делает runBlocking, и где его нельзя вызывать? Он блокирует текущий поток до завершения корутины и крутит внутри собственный event loop. Уместен он в main, в тестах без виртуального времени и на границе с блокирующим Java-кодом. Вызывать его нельзя внутри suspend-функции, внутри WebFlux-обработчика или на Netty event loop и внутри корутины на Dispatchers.Default, потому что он блокирует поток диспетчера, и если ожидаемой корутине нужен тот же поток или пул, получается взаимоблокировка, которая проявляется только под нагрузкой.

  16. Как тестировать код с delay, и почему Dispatchers.IO в сервисе этому мешает? runTest из kotlinx-coroutines-test выполняет тело на StandardTestDispatcher с виртуальным временем, так что delay(1.hours) проходит мгновенно, а время можно двигать через advanceUntilIdle()/advanceTimeBy(). Но виртуальное время работает только для диспетчеров с TestCoroutineScheduler, и захардкоженный withContext(Dispatchers.IO) { delay(5.seconds) } займёт реальные 5 секунд. Поэтому диспетчер внедряют через конструктор со значением по умолчанию Dispatchers.IO и подменяют в тестах.

  17. Полиморфны ли extension-функции? Нет, потому что они компилируются в статические методы, у которых receiver стоит первым параметром, и разрешаются по объявленному типу ещё на этапе компиляции. Если объявить fun Payment.channel() и fun CardPayment.channel(), то для val p: Payment = CardPayment() вызовется версия для Payment. Кроме того, член класса всегда побеждает extension с той же сигнатурой, поэтому при апгрейде библиотеки поведение может измениться, хотя ваш код не менялся.

  18. Что такое exception transparency у Flow? Это правило, по которому catch {} обрабатывает только исключения из upstream, а исключение, брошенное в collect {}, пролетает мимо него. Внутри flow {} нельзя ловить исключение из emit и продолжать эмитить, и библиотека такие попытки детектирует. Поэтому идиома выглядит так: логика в onEach, затем catch, а collect() пустой. Для повторов служат retry/retryWhen, которые пересоздают подписку, а роль finally играет onCompletion.

  19. Java-код вызывает ваш Kotlin-метод, который бросает IOException. Что увидит Java-разработчик? Он не увидит ничего, потому что Kotlin не пишет в байткод атрибут Exceptions, и для javac метод «не бросает checked-исключений», так что catch (IOException e) вокруг него не скомпилируется с ошибкой «exception is never thrown». Разработчик поймает Exception целиком или не поймает ничего, и ошибка пролетит мимо обработки. Лечится это аннотацией @Throws(IOException::class) на Kotlin-методе. В обратную сторону ситуация симметрична: Kotlin не заставляет обрабатывать checked-исключения Java, поэтому Files.readString() без try/catch скомпилируется и бросит исключение уже во время выполнения.

  20. Что происходит по шагам при job.cancel()? Job переходит в состояние Cancelling и рекурсивно вызывает cancel на всех детях, сверху вниз и синхронно. Корутины, приостановленные на suspend-точке, возобновляются исключением CancellationException прямо в этой точке, а те, что в этот момент выполняются, узнают об отмене на следующей suspend-точке, если же её нет, то не узнают никогда. Исключение разворачивает стек и выполняет finally, где любой suspend-вызов сразу бросит отмену, поэтому cleanup делают в withContext(NonCancellable). Когда все дети завершились, Job становится Cancelled, и родитель, который ждал в join(), продолжает работу.

  21. Чем suspendCoroutine отличается от suspendCancellableCoroutine, и что выбрать? suspendCancellableCoroutine даёт CancellableContinuation, поэтому корутина реагирует на отмену, а через invokeOnCancellation можно отменить и нижележащую операцию. suspendCoroutine отмену игнорирует, и withTimeout вокруг такого моста истечёт, а операция продолжит висеть и держать ресурс. Поэтому выбирать всегда стоит suspendCancellableCoroutine, кроме случаев, когда отменить нижележащую операцию физически нельзя. И тот и другой вариант требуют ровно одного resume, а повторный вызов даст IllegalStateException.

  22. Как выбрать между SharedFlow и StateFlow? StateFlow ведёт себя как SharedFlow с replay = 1, который всегда конфлейтит, дедуплицирует значения по equals и даёт синхронный .value, то есть он моделирует состояние, и промежуточные значения в нём теряются. SharedFlow моделирует события: у него настраиваются replay, extraBufferCapacity и onBufferOverflow, и при SUSPEND каждое событие получат все подписчики ценой того, что медленный подписчик тормозит emit. Поэтому для состояния вроде конфига, фича-флагов или текущего курса берут StateFlow, а для шины событий внутри процесса SharedFlow с replay = 0. Kafka ни тот ни другой не заменяет, потому что у них нет персистентности и доставки после рестарта.

  23. Вопрос-ловушка: защищает ли supervisorScope детей от отмены родителя? Нет, не защищает. Supervisor меняет ровно одно: ошибка ребёнка не отменяет siblings и не поднимается вверх. Отмена сверху вниз работает одинаково и в Job, и в SupervisorJob, так что при cancel() родителя отменяются все дети. Заблуждение подкрепляется тем, что launch(SupervisorJob()) действительно «отвязывает» корутину, но это не supervision, а выход из структурной иерархии, то есть утечка: родитель такую корутину не ждёт, и shutdown её не остановит.

  24. Вопрос-ловушка: в проекте один и тот же data class используется и как DTO, и как JPA-сущность. Что сломается первым? В роли DTO не сломается ничего, потому что это его законное применение. В роли сущности первым сломается hashCode: он считается по всем полям первичного конструктора, а значит, трогает lazy-связи, что вне сессии даёт LazyInitializationException, и меняется после присвоения id при persist, из-за чего объект «теряется» в HashSet. Следом toString() рекурсивно обойдёт двунаправленную связь и даст StackOverflowError, а copy() создаст detached-объект с тем же id и версией, чей merge может неожиданно бросить OptimisticLockException.

  25. Вопрос-ловушка: через сколько вернётся управление из withTimeout(1.seconds) { withContext(Dispatchers.IO) { jdbcTemplate.query(sql) } }? Через столько, сколько выполняется запрос, а вовсе не через секунду. Отмена кооперативная и доставляется в suspend-точках, а поток, который сидит в блокирующем socketRead, не проходит ни одной suspend-точки, поэтому таймаут сработает только тогда, когда JDBC вернёт управление сам. Настоящие таймауты для JDBC ставят на уровне драйвера (queryTimeout, socketTimeout) и БД (statement_timeout), как разобрано в главе 18, а runInterruptible { } помогает лишь коду, который уважает Thread.interrupt().

  26. Поведенческий вопрос (STAR): расскажите об инциденте, в котором виноват был Kotlin или корутины. Situation: у платёжного сервиса на Kotlin/WebFlux p99 вырос со 120 мс до 8 секунд при 150 rps, хотя CPU был загружен на 20 %, а пул БД занят на треть. Task: нужно было найти узкое место, которого не видно ни в одной метрике, и убрать его, не переписывая сервис. Action: мы сняли thread dump и увидели ровно 64 потока диспетчера, заблокированных в HTTP-клиенте скоринга, а затем посчитали пропускную способность (64 / 0.4 с ≈ 160 rps) и получили совпадение с точкой деградации. После этого мы выделили для скоринга именованный Dispatchers.IO.limitedParallelism(32), перевели общий блокирующий диспетчер на виртуальные потоки и добавили метрику времени ожидания входа в withContext. Result: p99 вернулся к 150 мс, деградация скоринга перестала задевать остальные эндпоинты, а новая метрика теперь ловит такие ситуации за минуты. Главный вывод команды состоял в том, что невидимая очередь опаснее видимой, и у каждого внешнего ресурса должен быть собственный бюджет параллелизма.

25. Попробовать руками

Ниже четырнадцать упражнений, каждое из которых воспроизводит на собственной машине один из механизмов главы, от state machine в байткоде до транзакции, размазанной по двум соединениям. Все они устроены одинаково: сначала вы пишете минимальный код и видите проблему своими глазами, а затем вносите исправление из соответствующего раздела и убеждаетесь, что поведение изменилось. Делать их стоит по порядку, потому что первые упражнения про корутины готовят почву для последних, про Spring и JPA.

  1. Увидеть state machine. Напишите suspend fun с двумя delay, скомпилируйте её и выполните javap -p -c на *Kt.class и *$1.class. Вы увидите параметр Continuation, возвращаемый тип Object, поле label, tableswitch по нему и сравнение с IntrinsicsKt.getCOROUTINE_SUSPENDED(). Затем уберите второй delay и напишите suspend fun a() = b(), и класса state machine не окажется, потому что сработает tail call.

  2. Лимит 64. Выполните runBlocking { (1..200).map { async(Dispatchers.IO) { Thread.sleep(1000); Thread.currentThread().name } }.awaitAll() } и засеките время: получится около 4 секунд (200/64 с округлением вверх), а не 1. Если заменить диспетчер на Dispatchers.IO.limitedParallelism(200) или на VT-диспетчер, время сократится примерно до 1 секунды. Распечатайте distinct() имён потоков, и в первом случае их окажется не больше 64.

  3. async отменяет родителя. Запустите coroutineScope { val a = async { delay(100); throw IllegalStateException() }; val b = async { delay(1000); "ok" }; try { a.await() } catch (e: Exception) { println("caught") }; b.await() }. «caught» напечатается, но b.await() бросит CancellationException/IllegalStateException, потому что scope к этому моменту уже отменён. Замените coroutineScope на supervisorScope, и b вернёт «ok».

  4. Проглоченная отмена. Выполните val job = launch { repeat(5) { runCatching { delay(100) }; println("step $it") } }; delay(150); job.cancel(), и вы увидите все 5 строк «step», причём последние напечатаются мгновенно: runCatching съел CancellationException, а delay в отменённой корутине бросает её сразу. Добавьте .onFailure { if (it is CancellationException) throw it }, и цикл остановится после первого шага.

  5. data class в JPA. Объявите @Entity data class Order(@Id @GeneratedValue var id: Long? = null, var status: String) со связью @OneToMany(LAZY) lines, сохраните заказ, закройте сессию и вызовите order.hashCode(), и вы получите LazyInitializationException. Затем положите сущность в HashSet<Order> до persist, сохраните её и проверьте set.contains(order), который вернёт false.

  6. Final и прокси. Уберите kotlin("plugin.spring") из проекта, где есть @Service с @Transactional, и при старте получите BeanCreationException: Cannot subclass final class. Верните плагин и выполните javap -v Service.class | grep flags, чтобы убедиться, что ACC_FINAL пропал.

  7. Flow invariant. Выполните flow { withContext(Dispatchers.IO) { emit(1) } }.collect() и получите IllegalStateException: Flow invariant is violated. Замените это на .flowOn(Dispatchers.IO) и добавьте println(Thread.currentThread().name) в строитель и в collect: потоки окажутся разными, а downstream останется на вызывающем потоке.

  8. Виртуальное время. Тест @Test fun t() = runTest { val t = testScheduler.currentTime; delay(1.hours); println(testScheduler.currentTime - t) } мгновенно напечатает 3600000. Оберните delay в withContext(Dispatchers.Default), и тест начнёт ждать по-настоящему; для наглядности поставьте delay(3.seconds).

  9. Platform type в generic. Напишите Java-класс с методом Map<String,String> headers(), который возвращает map со значением null. Если из Kotlin вызвать headers()["k"].length, код скомпилируется и упадёт с NPE без имени переменной в сообщении. Объявите val h: Map<String, String?> = client.headers(), и компилятор потребует ?.. После этого добавьте на пакет Java-класса @NullMarked (JSpecify) и посмотрите, как меняется диагностика.

  10. Checked-исключение через границу. Объявите в Kotlin fun read(p: Path): String = Files.readString(p), а в Java попробуйте обернуть вызов в try { } catch (IOException e) { }, и вы увидите ошибку компиляции «exception is never thrown». Добавьте @Throws(IOException::class) и пересоберите проект, после чего Java-код скомпилируется. Разницу видно в javap -v, где появится атрибут Exceptions.

  11. Spilled-переменные в state machine. Напишите suspend-функцию с пятью локальными переменными разных типов (String, Long, BigDecimal, List, Int), которые живут через два delay. javap -p на сгенерированном классе-континуации покажет поля L$0..L$3, J$0 и I$0. Уберите использование трёх переменных после первого delay, и число полей сократится, потому что компилятор спиллит только то, что действительно живёт через приостановку.

  12. limitedParallelism внутри метода. Сделайте сервис, в котором withContext(Dispatchers.IO.limitedParallelism(4)) { Thread.sleep(500) } вызывается 100 раз параллельно, и засеките время. Получится ~0.5–1 с, а не 12.5 с, то есть лимит не сработал, потому что каждый вызов создаёт собственный вид. Вынесите limitedParallelism(4) в поле, и время вырастет до ~12.5 с, а в thread dump будет видно 4 занятых потока.

  13. Turbine и StateFlow. Напишите тест с MutableStateFlow(0), подпишитесь через test { }, быстро присвойте 1, 2, 3 и убедитесь, что awaitItem() вернёт 0 и 3, потому что промежуточные значения конфлейтнулись. Замените поток на MutableSharedFlow(extraBufferCapacity = 8), и придут все три значения.

  14. @Transactional + suspend. Сделайте @Transactional suspend fun с двумя вызовами JPA-репозитория через withContext(Dispatchers.IO), включите logging.level.org.hibernate.resource.jdbc=DEBUG и посмотрите, что соединений два. Бросьте исключение после первого сохранения, и первая запись останется в БД. Перепишите код на withContext(db) { tx.execute { } }, и соединение станет одно, а откат заработает.
