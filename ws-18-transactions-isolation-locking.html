Мастерская к главе 18. Транзакции, изоляция и блокировки

Мастерская6 разделов14 способов← к главе

Здесь собрана практика к разделам главы 18: к каждому разделу два-три способа увидеть описанное своими глазами. Способы идут от простого к сложному. Первый обходится консолью базы. Второй — программа на Java в одном файле, которую IntelliJ IDEA запускает без проекта. Третий — маленькое приложение на Spring Boot, то есть то, с чем вы работаете каждый день. Делать все способы не обязательно, но второй и третий показывают одно и то же явление с разных сторон: из чистого JDBC видно, что делает база, а из Spring видно, что из этого доходит до вашего кода.

Все результаты ниже получены запуском на PostgreSQL 16.15, JDK 21.0.10, драйвере org.postgresql:postgresql:42.7.8 и Spring Boot 4.1.1. Числа времени зависят от машины, а вот «потеряно 700 списаний» и «откат вернул деньги» от машины не зависят.

Подготовка стенда

Понадобится Docker. Поднимите базу той же версии, на которой проверялись примеры:

Bash
docker run -d --name ws-pg -e POSTGRES_PASSWORD=dev -p 5432:5432 postgres:16
docker exec -it ws-pg psql -U postgres

Вторая команда открывает psql внутри контейнера. Для упражнений «в двух окнах» откройте её в двух вкладках терминала: каждая вкладка будет отдельной сессией и отдельной транзакцией. Если удобнее IntelliJ IDEA, подключитесь к localhost:5432 (пользователь postgres, пароль dev) в окне Database и откройте две консоли. Только переключите в каждой консоли режим транзакций с Auto на Manual, иначе IDEA будет фиксировать каждую команду сама.

Программы на Java из этой мастерской написаны так, что им нужен только драйвер. В IntelliJ IDEA создайте пустой проект, добавьте библиотеку org.postgresql:postgresql:42.7.8 (File → Project Structure → Libraries → From Maven) и запускайте файлы как обычные классы с main. Из терминала то же самое делается без проекта, потому что JDK 11 и новее запускает исходник напрямую:

Bash
java -cp postgresql-42.7.8.jar Transfer.java

Адрес базы и пароль программы берут из -Dws.url и -Dws.pass, а по умолчанию подключаются к jdbc:postgresql://localhost:5432/postgres с паролем dev.

18.1 Свойства ACID

← Вернуться к разделу 18.1 в главе

Раздел главы объяснял, что атомарность в PostgreSQL почти ничего не стоит по времени, но стоит места, что одна ошибка ломает всю транзакцию и что долговечность измеряется задержкой COMMIT. Ниже три способа это потрогать: в консоли, из JDBC и из Spring, где атомарность чаще всего ломают незаметно.

Способ 1. Консоль psql: откат, мёртвые версии и цена fsync

Выполните в одном окне psql по порядку:

SQL
CREATE TABLE ws_payments(id bigserial PRIMARY KEY, amount numeric(19,2) NOT NULL);

BEGIN;
INSERT INTO ws_payments(amount) SELECT 100 FROM generate_series(1, 100000);
SELECT count(*) FROM ws_payments;                          -- 100000: своя транзакция видит свои строки
ROLLBACK;

SELECT count(*) FROM ws_payments;                          -- 0
SELECT pg_size_pretty(pg_relation_size('ws_payments'));   -- 4328 kB: место осталось занятым
SELECT n_live_tup, n_dead_tup FROM pg_stat_user_tables WHERE relname = 'ws_payments';  -- 0 | 100000
VACUUM ws_payments;
SELECT pg_size_pretty(pg_relation_size('ws_payments'));   -- 0 bytes

Что должно получиться: после ROLLBACK строк ноль, а файл таблицы весит те же 4328 kB, и статистика показывает 100 000 мёртвых версий. Откат не стёр ни одной строки, он только пометил транзакцию как прерванную. Место вернул VACUUM, причём в этом примере он даже укоротил файл до нуля, потому что все страницы оказались пустыми и стояли в конце. Если n_dead_tup показывает 0, подождите секунду и повторите запрос: статистика доходит до представления с небольшой задержкой.

Теперь ошибка посреди транзакции:

SQL
BEGIN;
INSERT INTO ws_payments(amount) VALUES (10);
SELECT 1/0;                                               -- ERROR: division by zero
INSERT INTO ws_payments(amount) VALUES (20);              -- ERROR: current transaction is aborted…
COMMIT;                                                   -- psql напишет ROLLBACK, а не COMMIT
SELECT count(*) FROM ws_payments;                         -- 0

Что должно получиться: после первой ошибки база отказывается выполнять что-либо в этой транзакции (код 25P02), а COMMIT молча превращается в откат. Первая вставка, которая прошла успешно, тоже пропала. Именно так атомарность выглядит со стороны клиента: успешный оператор внутри неуспешной транзакции ничего не значит.

Цену долговечности покажет pgbench, он есть в образе postgres:16. Выйдите из psql и выполните в терминале:

Bash
docker exec ws-pg sh -c 'echo "INSERT INTO ws_payments(amount) VALUES (1);" > /tmp/ins.sql
for m in on off; do echo "synchronous_commit=$m"
  PGOPTIONS="-c synchronous_commit=$m" pgbench -U postgres -n -c 1 -t 3000 -f /tmp/ins.sql postgres | grep -E "latency average|tps"
done'

На стенде получилось 0,520 мс на коммит с synchronous_commit=on и 0,114 мс с off, то есть разница в 4,5 раза: столько стоит ожидание fsync журнала на каждом коммите. На ноутбуке с хорошим NVMe разница будет другой, но знак не изменится. Сделайте для себя вывод, который важен на интервью: off не ломает атомарность и согласованность, он лишь разрешает потерять последние подтверждённые коммиты при падении сервера.

Способ 2. Программа на JDBC: перевод с автокоммитом и в транзакции

Перевод между счетами состоит из двух UPDATE. Программа выполняет его трижды: с включённым автокоммитом, в транзакции и в транзакции, где сумма больше остатка и срабатывает CHECK. Получатель с номером 99 не существует, поэтому вторая половина перевода не находит строку.

Java
import java.math.BigDecimal;
import java.sql.*;

public class Transfer {
    static final String URL = System.getProperty("ws.url", "jdbc:postgresql://localhost:5432/postgres");

    public static void main(String[] args) throws Exception {
        try (Connection c = DriverManager.getConnection(URL, "postgres", System.getProperty("ws.pass", "dev"))) {
            reset(c);
            System.out.println("Было:                " + balances(c));
            try { transfer(c, 1, 99, new BigDecimal("30.00"), true); }
            catch (SQLException e) { System.out.println("Ошибка: " + e.getMessage()); }
            System.out.println("Автокоммит, после:   " + balances(c) + "  ← 30 списано и никуда не пришло");

            reset(c);
            try { transfer(c, 1, 99, new BigDecimal("30.00"), false); }
            catch (SQLException e) { System.out.println("Ошибка: " + e.getMessage()); }
            System.out.println("Транзакция, после:   " + balances(c) + "  ← откат вернул деньги");

            reset(c);
            try { transfer(c, 1, 2, new BigDecimal("500.00"), false); }
            catch (SQLException e) { System.out.println("Ошибка: " + e.getSQLState() + " " + e.getMessage().lines().findFirst().orElse("")); }
            System.out.println("CHECK, после:        " + balances(c));
        }
    }

    static void transfer(Connection c, long from, long to, BigDecimal amount, boolean autoCommit) throws SQLException {
        c.setAutoCommit(autoCommit);
        try (PreparedStatement debit = c.prepareStatement("UPDATE ws_accounts SET balance = balance - ? WHERE id = ?");
             PreparedStatement credit = c.prepareStatement("UPDATE ws_accounts SET balance = balance + ? WHERE id = ?")) {
            debit.setBigDecimal(1, amount); debit.setLong(2, from); debit.executeUpdate();
            credit.setBigDecimal(1, amount); credit.setLong(2, to);
            if (credit.executeUpdate() != 1) throw new SQLException("счёт получателя " + to + " не найден");
            if (!autoCommit) c.commit();
        } catch (SQLException e) {
            if (!autoCommit) c.rollback();
            throw e;
        } finally {
            c.setAutoCommit(true);
        }
    }

    static void reset(Connection c) throws SQLException {
        try (Statement s = c.createStatement()) {
            s.execute("DROP TABLE IF EXISTS ws_accounts");
            s.execute("CREATE TABLE ws_accounts (id bigint PRIMARY KEY, balance numeric(19,2) NOT NULL CHECK (balance >= 0))");
            s.execute("INSERT INTO ws_accounts VALUES (1, 100.00), (2, 100.00)");
        }
    }

    static String balances(Connection c) throws SQLException {
        StringBuilder sb = new StringBuilder();
        try (ResultSet rs = c.createStatement().executeQuery("SELECT id, balance FROM ws_accounts ORDER BY id")) {
            while (rs.next()) sb.append("#").append(rs.getLong(1)).append("=").append(rs.getBigDecimal(2)).append(' ');
        }
        return sb.toString().trim();
    }
}

Что должно получиться:

Было:                #1=100.00 #2=100.00
Ошибка: счёт получателя 99 не найден
Автокоммит, после:   #1=70.00 #2=100.00  ← 30 списано и никуда не пришло
Ошибка: счёт получателя 99 не найден
Транзакция, после:   #1=100.00 #2=100.00  ← откат вернул деньги
Ошибка: 23514 ERROR: new row for relation "ws_accounts" violates check constraint "ws_accounts_balance_check"
CHECK, после:        #1=100.00 #2=100.00

Первая строка после ошибки показывает, во что превращается перевод, если два UPDATE не объединены в транзакцию: деньги исчезли. Обратите внимание, что база при этом ни в чём не виновата, каждый оператор отдельно выполнился правильно. Третий прогон показывает букву C: ограничение CHECK — это согласованность, которую обеспечивает сама база, и нарушившая его транзакция откатывается целиком.

Попробуйте сами: уберите c.rollback() из catch во втором прогоне и посмотрите, что изменится. Подсказка: без отката соединение возвращается с открытой прерванной транзакцией, и следующий reset упадёт с 25P02. В пуле соединений такое соединение отравляет следующий запрос другого потока.

Способ 3. Spring Boot: @Transactional не откатывает проверяемое исключение

В Spring атомарность чаще всего ломается не в базе, а в правилах отката. По умолчанию @Transactional откатывает транзакцию на RuntimeException и Error, а на проверяемом исключении фиксирует её. Если проверка лимита выброшена после списания, списание сохранится.

Создайте проект на start.spring.io (Spring Boot 4.1.1, Java 21, зависимости JDBC API и PostgreSQL Driver) или возьмите такой pom.xml:

XML
<parent>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-parent</artifactId>
    <version>4.1.1</version>
</parent>
<groupId>dev.team</groupId>
<artifactId>ws-tx</artifactId>
<version>1.0</version>
<properties>
    <java.version>21</java.version>
</properties>
<dependencies>
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-jdbc</artifactId>
    </dependency>
    <dependency>
        <groupId>org.postgresql</groupId>
        <artifactId>postgresql</artifactId>
        <scope>runtime</scope>
    </dependency>
</dependencies>

src/main/resources/application.properties:

properties
spring.datasource.url=jdbc:postgresql://localhost:5432/postgres
spring.datasource.username=postgres
spring.datasource.password=dev
spring.main.banner-mode=off
logging.level.root=warn

И один класс приложения:

Java
package dev.team.ws;

import java.math.BigDecimal;
import org.springframework.boot.CommandLineRunner;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.context.annotation.Bean;
import org.springframework.jdbc.core.simple.JdbcClient;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@SpringBootApplication
public class WsTxApplication {

    public static void main(String[] args) {
        SpringApplication.run(WsTxApplication.class, args);
    }

    /** Проверяемое исключение: Spring по умолчанию НЕ откатывает транзакцию из-за него. */
    static class LimitExceededException extends Exception {
        LimitExceededException(String msg) { super(msg); }
    }

    @Service
    static class TransferService {
        private final JdbcClient jdbc;
        TransferService(JdbcClient jdbc) { this.jdbc = jdbc; }

        @Transactional
        public void transfer(long from, long to, BigDecimal amount) throws LimitExceededException {
            debit(from, amount);
            checkDailyLimit(from, amount);           // бросает проверяемое исключение уже после списания
            credit(to, amount);
        }

        @Transactional(rollbackFor = Exception.class)
        public void transferSafe(long from, long to, BigDecimal amount) throws LimitExceededException {
            debit(from, amount);
            checkDailyLimit(from, amount);
            credit(to, amount);
        }

        private void debit(long id, BigDecimal amount) {
            jdbc.sql("UPDATE ws_accounts SET balance = balance - :a WHERE id = :id").param("a", amount).param("id", id).update();
        }
        private void credit(long id, BigDecimal amount) {
            jdbc.sql("UPDATE ws_accounts SET balance = balance + :a WHERE id = :id").param("a", amount).param("id", id).update();
        }
        private void checkDailyLimit(long id, BigDecimal amount) throws LimitExceededException {
            if (amount.compareTo(new BigDecimal("50.00")) > 0)
                throw new LimitExceededException("суточный лимит 50.00 превышен: " + amount);
        }
    }

    @Bean
    CommandLineRunner demo(TransferService svc, JdbcClient jdbc) {
        return args -> {
            Runnable reset = () -> {
                jdbc.sql("DROP TABLE IF EXISTS ws_accounts").update();
                jdbc.sql("CREATE TABLE ws_accounts (id bigint PRIMARY KEY, balance numeric(19,2) NOT NULL CHECK (balance >= 0))").update();
                jdbc.sql("INSERT INTO ws_accounts VALUES (1, 100.00), (2, 100.00)").update();
            };
            var balances = (java.util.function.Supplier<String>) () ->
                    jdbc.sql("SELECT string_agg('#' || id || '=' || balance, ' ' ORDER BY id) FROM ws_accounts").query(String.class).single();

            reset.run();
            try { svc.transfer(1, 2, new BigDecimal("80.00")); } catch (LimitExceededException e) { System.out.println("Ошибка: " + e.getMessage()); }
            System.out.println("@Transactional:                  " + balances.get());

            reset.run();
            try { svc.transferSafe(1, 2, new BigDecimal("80.00")); } catch (LimitExceededException e) { System.out.println("Ошибка: " + e.getMessage()); }
            System.out.println("@Transactional(rollbackFor=...): " + balances.get());
        };
    }
}

Что должно получиться:

Ошибка: суточный лимит 50.00 превышен: 80.00
@Transactional:                  #1=20.00 #2=100.00
Ошибка: суточный лимит 50.00 превышен: 80.00
@Transactional(rollbackFor=...): #1=100.00 #2=100.00

Восемьдесят рублей списались и никуда не пришли, хотя метод помечен @Transactional и база работает правильно. Spring зафиксировал транзакцию, потому что LimitExceededException проверяемое. Во втором методе rollbackFor = Exception.class меняет правило, и списание откатывается. На проектах это правило обычно задают один раз: либо все бизнес-исключения наследуют RuntimeException, либо в команде договариваются писать rollbackFor. На Kotlin эта ловушка ещё незаметнее: компилятор не требует объявлять исключения, и class LimitExceededException(msg: String) : Exception(msg) выглядит безобидно, но Spring смотрит на тип во время выполнения, видит наследника Exception, а не RuntimeException, и фиксирует транзакцию. Тот же сервис на Kotlin 2.3.21 (классы и методы открыты через open, потому что без плагина kotlin-spring прокси не перехватит вызов) дал тот же результат:

Ошибка: суточный лимит 50.00 превышен: 80.00
Kotlin, @Transactional:                  #1=20.00 #2=100.00
Ошибка: суточный лимит 50.00 превышен: 80.00
Kotlin, @Transactional(rollbackFor=...): #1=100.00 #2=100.00

В Kotlin атрибут записывается массивом: @Transactional(rollbackFor = [Exception::class]).

Попробуйте сами: перенесите вызов checkDailyLimit перед debit и убедитесь, что теперь оба варианта оставляют баланс нетронутым. Это вторая защита, и она надёжнее первой: сначала проверить, потом писать.

Способ 1. Два окна psql: одно и то же чтение на READ COMMITTED и REPEATABLE READ

Создайте таблицу из главы:

SQL
CREATE TABLE accounts (
    id      bigint PRIMARY KEY,
    owner   text   NOT NULL,
    balance numeric(19,2) NOT NULL
);
INSERT INTO accounts VALUES (1, 'alice', 100.00), (2, 'alice', 100.00);

Дальше команды чередуются между окнами A и B. Окно B работает в режиме автокоммита, то есть каждая его команда сразу фиксируется.

SQL
-- A
BEGIN ISOLATION LEVEL READ COMMITTED;
SELECT balance FROM accounts WHERE id = 1;                  -- 100.00
SELECT count(*) FROM accounts WHERE owner = 'alice';        -- 2

-- B
UPDATE accounts SET balance = 20 WHERE id = 1;
INSERT INTO accounts VALUES (3, 'alice', 50);

-- A
SELECT balance FROM accounts WHERE id = 1;                  -- 20.00: неповторяющееся чтение
SELECT count(*) FROM accounts WHERE owner = 'alice';        -- 3: фантом
UPDATE accounts SET balance = balance - 10 WHERE id = 1;    -- проходит
ROLLBACK;

Верните данные (UPDATE accounts SET balance = 100 WHERE id = 1; DELETE FROM accounts WHERE id > 2;) и повторите то же самое, начав транзакцию в A с BEGIN ISOLATION LEVEL REPEATABLE READ;.

Что должно получиться: на REPEATABLE READ оба повторных чтения возвращают 100.00 и 2, потому что транзакция A работает со снимком, сделанным при первом запросе. А последний UPDATE завершится ошибкой 40001 could not serialize access due to concurrent update: строку, которую A видит в снимке, B уже изменила, и PostgreSQL не позволяет A писать поверх версии, которой A не видела. Так на практике выглядит граница между уровнями: на первом уровне вы читаете свежие данные и спокойно пишете, на втором читаете стабильные данные и должны быть готовы повторить транзакцию.

Попробуйте сами: в варианте с REPEATABLE READ поставьте SELECT now(); первой командой после BEGIN, а команды B выполните до неё. Снимок берётся первым запросом, а не командой BEGIN, поэтому A увидит 20.00 сразу.

Способ 2. Программа на JDBC: потерянное обновление на восьми потоках

Восемь потоков списывают со счёта по 1 рублю, каждый по 100 раз, итого ожидаем 10 000 − 800 = 9 200. Программа повторяет опыт четырьмя способами: «прочитать, вычесть в Java, записать», атомарный UPDATE, SELECT ... FOR UPDATE и REPEATABLE READ с повтором транзакции при 40001.

Java
import java.sql.*;
import java.util.concurrent.*;
import java.util.concurrent.atomic.AtomicInteger;

public class LostUpdate {
    static final String URL = System.getProperty("ws.url", "jdbc:postgresql://localhost:5432/postgres");
    static final String PASS = System.getProperty("ws.pass", "dev");
    static final int THREADS = 8, PER_THREAD = 100, START = 10_000;

    interface Debit { void run(Connection c) throws SQLException; }

    public static void main(String[] args) throws Exception {
        run("1. прочитать, вычесть в Java, записать", c -> {
            long b = readBalance(c, "");
            update(c, "UPDATE ws_wallet SET balance = ? WHERE id = 1", b - 1);
        }, Connection.TRANSACTION_READ_COMMITTED);
        run("2. атомарный UPDATE balance = balance - 1", c ->
            update(c, "UPDATE ws_wallet SET balance = balance - 1 WHERE id = 1", null),
            Connection.TRANSACTION_READ_COMMITTED);
        run("3. SELECT ... FOR UPDATE", c -> {
            long b = readBalance(c, " FOR UPDATE");
            update(c, "UPDATE ws_wallet SET balance = ? WHERE id = 1", b - 1);
        }, Connection.TRANSACTION_READ_COMMITTED);
        run("4. REPEATABLE READ + повтор при 40001", c -> {
            long b = readBalance(c, "");
            update(c, "UPDATE ws_wallet SET balance = ? WHERE id = 1", b - 1);
        }, Connection.TRANSACTION_REPEATABLE_READ);
    }

    static void run(String name, Debit debit, int isolation) throws Exception {
        try (Connection c = DriverManager.getConnection(URL, "postgres", PASS); Statement s = c.createStatement()) {
            s.execute("DROP TABLE IF EXISTS ws_wallet");
            s.execute("CREATE TABLE ws_wallet (id int PRIMARY KEY, balance bigint NOT NULL)");
            s.execute("INSERT INTO ws_wallet VALUES (1, " + START + ")");
        }
        AtomicInteger retries = new AtomicInteger();
        ExecutorService pool = Executors.newFixedThreadPool(THREADS);
        long t0 = System.nanoTime();
        for (int t = 0; t < THREADS; t++) pool.submit(() -> {
            try (Connection c = DriverManager.getConnection(URL, "postgres", PASS)) {
                c.setAutoCommit(false);
                c.setTransactionIsolation(isolation);
                for (int i = 0; i < PER_THREAD; i++) {
                    while (true) {
                        try { debit.run(c); c.commit(); break; }
                        catch (SQLException e) {
                            c.rollback();
                            if ("40001".equals(e.getSQLState())) { retries.incrementAndGet(); continue; }
                            throw e;
                        }
                    }
                }
            }
            return null;
        });
        pool.shutdown();
        pool.awaitTermination(2, TimeUnit.MINUTES);
        long ms = (System.nanoTime() - t0) / 1_000_000;
        try (Connection c = DriverManager.getConnection(URL, "postgres", PASS)) {
            long end = readBalance(c, "");
            long expected = START - THREADS * PER_THREAD;
            System.out.printf("%-44s остаток %d, ожидали %d, потеряно списаний: %d, повторов: %d, %d мс%n",
                    name, end, expected, end - expected, retries.get(), ms);
        }
    }

    static long readBalance(Connection c, String suffix) throws SQLException {
        try (ResultSet rs = c.createStatement().executeQuery("SELECT balance FROM ws_wallet WHERE id = 1" + suffix)) {
            rs.next();
            return rs.getLong(1);
        }
    }

    static void update(Connection c, String sql, Long value) throws SQLException {
        try (PreparedStatement ps = c.prepareStatement(sql)) {
            if (value != null) ps.setLong(1, value);
            ps.executeUpdate();
        }
    }
}

На стенде два прогона дали одно и то же:

1. прочитать, вычесть в Java, записать       остаток 9900, ожидали 9200, потеряно списаний: 700, повторов: 0, 1480 мс
2. атомарный UPDATE balance = balance - 1    остаток 9200, ожидали 9200, потеряно списаний: 0, повторов: 0, 1527 мс
3. SELECT ... FOR UPDATE                     остаток 9200, ожидали 9200, потеряно списаний: 0, повторов: 0, 2512 мс
4. REPEATABLE READ + повтор при 40001        остаток 9200, ожидали 9200, потеряно списаний: 0, повторов: 2800, 4305 мс

Из 800 списаний наивный вариант потерял 700, и база при этом не выдала ни одной ошибки. Три исправления дают правильный остаток, но по-разному. Атомарный UPDATE оказался самым быстрым, потому что чтение и запись сливаются в один оператор, а ожидание блокировки строки длится одну команду. FOR UPDATE медленнее в полтора раза: строка заблокирована от чтения до коммита, и потоки выстраиваются в очередь. REPEATABLE READ дал правильный итог ценой 2 800 повторов на 800 полезных списаний, и на горячей строке это самый дорогой способ. Из этого следует практическое правило: если операцию можно записать одним UPDATE ... SET x = x - ? с условием в WHERE, так и делайте, а уровень изоляции поднимайте там, где читаете много строк и решаете по ним.

Попробуйте сами: в варианте 1 поставьте Connection.TRANSACTION_REPEATABLE_READ вместо READ_COMMITTED и ничего больше не меняйте. Потерь станет ноль, а повторов столько же, сколько в варианте 4: эти два кода отличаются только уровнем изоляции. Затем уменьшите THREADS до 1 и убедитесь, что наивный вариант перестал терять. Ошибка, которая проявляется только под нагрузкой, на интервью называется «работает на моей машине», и этот опыт хорошо её объясняет.

Раздел главы объяснял, что имя уровня изоляции ничего не гарантирует само по себе: snapshot isolation не помещается в иерархию ANSI, и в разных СУБД за одним именем стоит разное поведение. Способ 1. Два окна psql: перекос записи на REPEATABLE READ и на SERIALIZABLE

Правило банка такое: клиент может уйти в минус по отдельному счёту, но сумма по всем его счетам не уходит ниже нуля. У Алисы два счёта по 100, и две операции одновременно списывают по 150, каждая со своего счёта.

SQL
DROP TABLE IF EXISTS accounts;
CREATE TABLE accounts (id bigint PRIMARY KEY, owner text NOT NULL, balance numeric(19,2) NOT NULL);
INSERT INTO accounts VALUES (1, 'alice', 100.00), (2, 'alice', 100.00);
SQL
-- A
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT sum(balance) FROM accounts WHERE owner = 'alice';   -- 200.00: хватает, 200 − 150 ≥ 0

-- B
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT sum(balance) FROM accounts WHERE owner = 'alice';   -- 200.00: тоже хватает

-- A
UPDATE accounts SET balance = balance - 150 WHERE id = 1;
-- B
UPDATE accounts SET balance = balance - 150 WHERE id = 2;

-- A
COMMIT;
-- B
COMMIT;

SELECT sum(balance) FROM accounts;                          -- -100.00

Что должно получиться: обе транзакции зафиксировались, и сумма по клиенту стала −100. Ни одна строка не изменялась двумя транзакциями сразу, поэтому snapshot isolation конфликта не видит: каждая транзакция приняла верное решение по своему снимку, а вместе они нарушили правило.

Верните данные и повторите всё с BEGIN ISOLATION LEVEL SERIALIZABLE; в обоих окнах. Теперь первый COMMIT пройдёт, а второй завершится ошибкой:

ERROR:  could not serialize access due to read/write dependencies among transactions

Код ошибки 40001, итог 50.00: прошло только одно списание. Сериализуемый уровень PostgreSQL заметил, что каждая транзакция читала строки, которые меняла другая, и что никакой последовательный порядок не даёт такого результата.

Попробуйте сами: в варианте с SERIALIZABLE поменяйте порядок COMMIT, сначала зафиксируйте B. Ошибку получит A. Какой из двух транзакций откатиться, решает порядок фиксации, а не порядок начала, и код должен быть готов к откату любой из них.

Способ 2. Spring Boot: перекос записи в сервисе и то, каким исключением приходит 40001

Тот же опыт из Java показывает, что именно получит ваш код. Проект тот же, что в 18.1 (Spring Boot 4.1.1, JDBC API, PostgreSQL Driver), а класс положите в отдельный пакет, например dev.team.ws.skew, чтобы при запуске не срабатывал раннер из 18.1. Защёлка CountDownLatch заставляет обе транзакции прочитать сумму до того, как кто-то из них спишет деньги. Без неё гонку пришлось бы ловить случайно.

Java
package dev.team.ws.skew;

import java.math.BigDecimal;
import java.util.concurrent.CountDownLatch;
import java.util.concurrent.CompletableFuture;
import org.springframework.boot.CommandLineRunner;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.context.annotation.Bean;
import org.springframework.dao.ConcurrencyFailureException;
import org.springframework.jdbc.core.simple.JdbcClient;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Isolation;
import org.springframework.transaction.annotation.Transactional;

@SpringBootApplication
public class SkewApplication {

    public static void main(String[] args) {
        SpringApplication.run(SkewApplication.class, args);
    }

    @Service
    static class OverdraftService {
        private final JdbcClient jdbc;
        OverdraftService(JdbcClient jdbc) { this.jdbc = jdbc; }

        /** Правило клиента: сумма по всем его счетам не уходит в минус. */
        void withdraw(long accountId, BigDecimal amount, CountDownLatch bothRead) throws InterruptedException {
            BigDecimal total = jdbc.sql("SELECT sum(balance) FROM accounts WHERE owner = 'alice'").query(BigDecimal.class).single();
            bothRead.countDown();
            bothRead.await();                       // обе транзакции прочитали сумму до того, как кто-то списал
            if (total.subtract(amount).signum() < 0) throw new IllegalStateException("не хватает средств");
            jdbc.sql("UPDATE accounts SET balance = balance - :a WHERE id = :id").param("a", amount).param("id", accountId).update();
        }

        @Transactional(isolation = Isolation.REPEATABLE_READ)
        public void withdrawRepeatableRead(long id, BigDecimal a, CountDownLatch l) throws InterruptedException { withdraw(id, a, l); }

        @Transactional(isolation = Isolation.SERIALIZABLE)
        public void withdrawSerializable(long id, BigDecimal a, CountDownLatch l) throws InterruptedException { withdraw(id, a, l); }
    }

    /** Повтор снаружи транзакции: каждая попытка — новая транзакция с новым снимком. */
    @Service
    static class OverdraftFacade {
        private final OverdraftService svc;
        OverdraftFacade(OverdraftService svc) { this.svc = svc; }

        public void withdraw(long id, BigDecimal amount, CountDownLatch l) throws InterruptedException {
            for (int attempt = 1; ; attempt++) {
                try { svc.withdrawSerializable(id, amount, l); return; }
                catch (ConcurrencyFailureException e) {
                    if (attempt == 3) throw e;
                    System.out.println("  счёт " + id + ": 40001, попытка " + attempt + " откатилась, повторяю");
                }
            }
        }
    }

    interface Call { void run(long id, BigDecimal a, CountDownLatch l) throws Exception; }

    @Bean
    CommandLineRunner skew(OverdraftService svc, OverdraftFacade facade, JdbcClient jdbc) {
        return args -> {
            for (String level : new String[]{"REPEATABLE_READ", "SERIALIZABLE", "SERIALIZABLE + повтор"}) {
                jdbc.sql("DROP TABLE IF EXISTS accounts").update();
                jdbc.sql("CREATE TABLE accounts (id bigint PRIMARY KEY, owner text NOT NULL, balance numeric(19,2) NOT NULL)").update();
                jdbc.sql("INSERT INTO accounts VALUES (1, 'alice', 100.00), (2, 'alice', 100.00)").update();
                Call call = switch (level) { case "SERIALIZABLE" -> svc::withdrawSerializable; case "REPEATABLE_READ" -> svc::withdrawRepeatableRead; default -> facade::withdraw; };
                CountDownLatch latch = new CountDownLatch(2);
                var f1 = CompletableFuture.runAsync(() -> run(call, 1, latch));
                var f2 = CompletableFuture.runAsync(() -> run(call, 2, latch));
                CompletableFuture.allOf(f1, f2).join();
                System.out.println(level + ": сумма по клиенту после двух списаний по 150 = "
                        + jdbc.sql("SELECT sum(balance) FROM accounts").query(BigDecimal.class).single());
            }
        };
    }

    static void run(Call call, long id, CountDownLatch latch) {
        try {
            call.run(id, new BigDecimal("150.00"), latch);
            System.out.println("  счёт " + id + ": списано");
        } catch (Exception e) {
            Throwable root = e; while (root.getCause() != null) root = root.getCause();
            System.out.println("  счёт " + id + ": " + e.getClass().getName()
                    + "\n      иерархия: " + hierarchy(e.getClass())
                    + "\n      причина: " + root.getClass().getSimpleName() + " " + root.getMessage().lines().findFirst().orElse(""));
        }
    }

    static String hierarchy(Class<?> c) {
        StringBuilder sb = new StringBuilder(c.getSimpleName());
        for (Class<?> p = c.getSuperclass(); p != null && p != Object.class; p = p.getSuperclass()) sb.append(" → ").append(p.getSimpleName());
        return sb.toString();
    }
}

Второй неочевиден: ошибку сериализации Spring 7 переводит в CannotAcquireLockException, наследника PessimisticLockingFailureException, хотя никакой пессимистичной блокировки в коде нет. Поэтому ловить нужно общего предка, ConcurrencyFailureException (или TransientDataAccessException), а не конкретный класс: на другой СУБД или в другой версии Spring перевод может отличаться. Третий урок показывает фасад. Повтор работает только снаружи транзакции: вторая попытка начинается с новым снимком, видит уже списанные 150, и правило отказывает честно, «не хватает средств». Повтор внутри того же @Transactional-метода ничего бы не дал, потому что прерванную транзакцию PostgreSQL не продолжает (код 25P02, раздел 11 главы).

Попробуйте сами: замените в OverdraftFacade вызов svc.withdrawSerializable на svc.withdrawRepeatableRead. Повторов не будет вовсе, обе операции пройдут, и сумма снова станет −100. Повтор спасает только тогда, когда база умеет заметить конфликт.

18.4 Уровни изоляции в PostgreSQL

← Вернуться к разделу 18.4 в главе

Раздел главы разбирал, когда каждый уровень берёт снимок и что происходит при встрече с чужим изменением. Три коротких опыта в консоли закрывают три утверждения главы, которые чаще всего пересказывают неточно: READ UNCOMMITTED в PostgreSQL ничем не отличается от READ COMMITTED, снимок REPEATABLE READ берётся первым запросом, а не командой BEGIN, и READ COMMITTED может молча пропустить строку.

Способ 1. Консоль psql: READ UNCOMMITTED, который не читает чужого

SQL
-- A
BEGIN;
UPDATE accounts SET balance = 1000000 WHERE id = 1;          -- не фиксируем

-- B
BEGIN ISOLATION LEVEL READ UNCOMMITTED;
SHOW transaction_isolation;                                   -- read uncommitted
SELECT balance FROM accounts WHERE id = 1;                    -- 100.00, а не 1000000
ROLLBACK;

-- A
ROLLBACK;

Что должно получиться: база честно приняла уровень read uncommitted, но грязного чтения нет. В многоверсионном хранении для этого пришлось бы специально ломать проверку видимости, поэтому PostgreSQL этот уровень просто приравнивает к READ COMMITTED.

Теперь момент, когда берётся снимок:

SQL
-- A
BEGIN ISOLATION LEVEL REPEATABLE READ;

-- B
UPDATE accounts SET balance = 20 WHERE id = 1;                -- после BEGIN в A, но до её первого запроса

-- A
SELECT balance FROM accounts WHERE id = 1;                    -- 20.00: изменение B видно

-- B
UPDATE accounts SET balance = 30 WHERE id = 1;

-- A
SELECT balance FROM accounts WHERE id = 1;                    -- снова 20.00: снимок уже взят
ROLLBACK;

Что должно получиться: первое чтение видит 20, второе тоже 20. Снимок появился в момент первого запроса, всё, что зафиксировано до него, в снимок попало, а всё, что после, уже нет. На практике это значит, что «открыл транзакцию, сходил в другой сервис, потом прочитал» читает не то состояние, которое было при BEGIN.

Способ 2. Консоль psql: EvalPlanQual и строка, пропущенная без ошибки

Это упражнение 9 из раздела 19 главы, здесь с пояснением, на что смотреть. Пусть на счёте 1 снова 100.

SQL
-- A
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;    -- баланс станет 0, не фиксируем

-- B (READ COMMITTED, автокоммит)
UPDATE accounts SET balance = balance - 10 WHERE id = 1 AND balance >= 100;
-- B висит: строку держит A

-- A
COMMIT;

-- B сразу отвечает:
-- UPDATE 0

Что должно получиться: B ждала, а после фиксации A ответила UPDATE 0, без ошибки. На уровне READ COMMITTED PostgreSQL после ожидания перечитывает свежую версию строки и заново проверяет условие WHERE (механизм EvalPlanQual, раздел 4.6 главы). Баланс стал 0, условие balance >= 100 больше не выполняется, и строка тихо выпала из обновления. Для кода это значит: проверяйте число обновлённых строк. Метод, который игнорирует результат executeUpdate() или JdbcClient.update(), примет «списание не состоялось» за «списано».

Попробуйте сами: выполните то же самое, начав B с BEGIN ISOLATION LEVEL REPEATABLE READ; и закончив COMMIT;. Вместо UPDATE 0 придёт 40001 could not serialize access due to concurrent update: на этом уровне база не перечитывает строку, а сообщает о конфликте, и решение о повторе переходит к приложению.

Способ 3. Spring Boot: повтор снаружи транзакции на SERIALIZABLE

Программа из способа 2 раздела 18.3 уже содержит третий прогон, «SERIALIZABLE + повтор», и он относится как раз к этому разделу. Сериализуемый уровень PostgreSQL (SSI, раздел 4.4 главы) не блокирует транзакции, а откатывает одну из них, поэтому без повтора на нём нельзя писать прикладной код. В выводе видно, что первая попытка второго списания откатилась с 40001, вторая попытка прошла по новому снимку и отказала по правилу, итоговая сумма 50.00.

Попробуйте сами: уберите защёлку CountDownLatch (вызовы countDown и await) и запустите программу несколько раз. Чаще всего повторов не будет вовсе, потому что транзакции успевают выполниться по очереди. Ошибка сериализации проявляется только при настоящем перекрытии транзакций, поэтому на стенде её приходится вызывать нарочно, а в проде она приходит под нагрузкой.

18.6 Табличные блокировки в PostgreSQL

← Вернуться к разделу 18.6 в главе

Главная мысль раздела главы: короткий ALTER TABLE, вставший в очередь за долгим SELECT, останавливает таблицу для всех, и лечится это lock_timeout перед каждой миграцией. Консоль показывает очередь изнутри, а программа измеряет, сколько из-за неё ждёт обычный запрос API.

Способ 1. Три окна psql: миграция, аналитика и запрос API

SQL
-- A: аналитический запрос, который держит транзакцию открытой
BEGIN;
SELECT count(*) FROM accounts;                                -- ACCESS SHARE до конца транзакции

-- B: миграция
ALTER TABLE accounts ADD COLUMN note text;                    -- висит: нужен ACCESS EXCLUSIVE

-- C: обычный запрос приложения
SELECT balance FROM accounts WHERE id = 1;                    -- тоже висит, хотя с A не конфликтует

Пока всё висит, откройте четвёртое окно и посмотрите, кто кого ждёт:

SQL
SELECT pid, pg_blocking_pids(pid) AS blocked_by, wait_event_type, left(query, 50) AS query
FROM pg_stat_activity
WHERE wait_event_type = 'Lock';

Что должно получиться: две строки. Миграция ждёт сессию A (жёсткая блокировка, hard block). Запрос C ждёт уже не A, а саму миграцию: C стоит в очереди за B (мягкая блокировка, soft block). Зафиксируйте A (COMMIT;), и сразу пройдут обе.

Теперь повторите опыт, но в окне B перед ALTER выполните SET lock_timeout = '2s';. Через две секунды миграция упадёт с 55P03 canceling statement due to lock timeout, покинет очередь, и запрос C сразу получит ответ. Миграция не выполнилась, но таблица жива, и её можно повторить ночью.

Попробуйте сами: выполните в B BEGIN; SET lock_timeout = '2s'; ROLLBACK; и затем ALTER TABLE ... без нового SET. Миграция снова повиснет без ограничения: SET внутри транзакции откатывается вместе с ней. На этом в мастерской споткнулся и автор: скрипт проверки ставил таймаут внутри транзакции, первый же ROLLBACK его отменил, и следующий запрос ждал две минуты. Поэтому таймаут для миграций задают либо в начале каждой транзакции через SET LOCAL, либо на уровне соединения, когда транзакции ещё нет.

Способ 2. Программа на JDBC: сколько ждёт запрос API

Программа повторяет ту же сцену в коде: аналитика держит ACCESS SHARE три секунды, миграция встаёт в очередь, а через 300 мс приходит запрос по одному счёту. Затем всё повторяется с lock_timeout = 500ms у миграции.

Java
import java.sql.*;
import java.util.concurrent.*;

public class DdlQueue {
    static final String URL = System.getProperty("ws.url", "jdbc:postgresql://localhost:5432/postgres");
    static final String PASS = System.getProperty("ws.pass", "dev");

    public static void main(String[] args) throws Exception {
        try (Connection c = conn(); Statement s = c.createStatement()) {
            s.execute("DROP TABLE IF EXISTS ws_accounts");
            s.execute("CREATE TABLE ws_accounts (id bigint PRIMARY KEY, balance numeric(19,2) NOT NULL)");
            s.execute("INSERT INTO ws_accounts SELECT g, 100 FROM generate_series(1, 1000) g");
        }
        run(null);
        run("500ms");
    }

    static void run(String lockTimeout) throws Exception {
        System.out.println("--- миграция " + (lockTimeout == null ? "без lock_timeout" : "с lock_timeout = " + lockTimeout));
        ExecutorService pool = Executors.newCachedThreadPool();
        Connection analyst = conn();
        analyst.setAutoCommit(false);
        analyst.createStatement().executeQuery("SELECT count(*) FROM ws_accounts").close();   // держит ACCESS SHARE до конца транзакции

        Future<String> migration = pool.submit(() -> {
            try (Connection c = conn(); Statement s = c.createStatement()) {
                if (lockTimeout != null) s.execute("SET lock_timeout = '" + lockTimeout + "'");
                long t0 = System.nanoTime();
                try {
                    s.execute("ALTER TABLE ws_accounts ADD COLUMN IF NOT EXISTS note text");
                    return "ALTER выполнен через " + ms(t0) + " мс";
                } catch (SQLException e) {
                    return "ALTER упал через " + ms(t0) + " мс: " + e.getSQLState() + " " + e.getMessage().lines().findFirst().orElse("");
                }
            }
        });
        Thread.sleep(300);                                   // миграция уже стоит в очереди

        Future<String> api = pool.submit(() -> {
            try (Connection c = conn(); Statement s = c.createStatement()) {
                long t0 = System.nanoTime();
                s.executeQuery("SELECT balance FROM ws_accounts WHERE id = 42").close();
                return "SELECT по id = 42 ответил через " + ms(t0) + " мс";
            }
        });
        Thread.sleep(3000);                                  // аналитика работает ещё три секунды
        try (Connection c = conn(); ResultSet rs = c.createStatement().executeQuery(
                "SELECT pid, pg_blocking_pids(pid) AS blocked_by, left(query, 50) AS q FROM pg_stat_activity " +
                "WHERE wait_event_type = 'Lock' ORDER BY pid")) {
            while (rs.next()) System.out.println("  ждёт блокировку: pid " + rs.getInt(1) + " ← " + rs.getString(2) + "  " + rs.getString(3));
        }
        analyst.commit();
        analyst.close();
        System.out.println("  " + migration.get());
        System.out.println("  " + api.get());
        pool.shutdown();
        try (Connection c = conn(); Statement s = c.createStatement()) { s.execute("ALTER TABLE ws_accounts DROP COLUMN IF EXISTS note"); }
    }

    static Connection conn() throws SQLException { return DriverManager.getConnection(URL, "postgres", PASS); }
    static long ms(long t0) { return (System.nanoTime() - t0) / 1_000_000; }
}

На стенде получилось:

--- миграция без lock_timeout
  ждёт блокировку: pid 323959 ← {323958}  ALTER TABLE ws_accounts ADD COLUMN IF NOT EXISTS n
  ждёт блокировку: pid 323960 ← {323959}  SELECT balance FROM ws_accounts WHERE id = 42
  ALTER выполнен через 3337 мс
  SELECT по id = 42 ответил через 3020 мс
--- миграция с lock_timeout = 500ms
  ALTER упал через 504 мс: 55P03 ERROR: canceling statement due to lock timeout
  SELECT по id = 42 ответил через 191 мс

Цепочка ожиданий видна в первых двух строках: миграция ждёт аналитику, а запрос по ключу ждёт миграцию. Запрос, который обычно выполняется за миллисекунду, ждал три секунды и ждал бы тридцать минут, если бы аналитика работала тридцать минут. С таймаутом он ждал 191 мс: столько оставалось до момента, когда миграция сдалась (500 мс минус 300 мс, на которые запрос пришёл позже). Номера процессов у вас будут другими.

Попробуйте сами: запустите внутри run не один запрос API, а двадцать в цикле через pool.submit, и выставьте пулу соединений приложения предел в десять. Так устроен типичный инцидент: соединения пула кончаются, пока все они стоят в очереди за миграцией, и сервис перестаёт отвечать даже на запросы к другим таблицам.

18.7 Строчные блокировки

← Вернуться к разделу 18.7 в главе

Раздел главы объяснял четыре режима строчных блокировок, NOWAIT, SKIP LOCKED и очередь задач на таблице. Консоль показывает, что именно блокирует вставка платежа в строке клиента, а программа на трёх воркерах сравнивает три способа разбирать очередь и считает дубли.

Способ 1. Два окна psql: что запрещает вставка дочерней строки

SQL
CREATE TABLE ws_client  (id bigint PRIMARY KEY, name text, risk text);
CREATE TABLE ws_payment (id bigserial PRIMARY KEY, client_id bigint REFERENCES ws_client(id), amount numeric);
INSERT INTO ws_client VALUES (1, 'Иванов', 'low');

-- A: платёж клиента, транзакция открыта
BEGIN;
INSERT INTO ws_payment(client_id, amount) VALUES (1, 500);

-- B: каждую команду выполняйте в своей транзакции с таймаутом
BEGIN; SET LOCAL lock_timeout = '500ms';
UPDATE ws_client SET risk = 'high' WHERE id = 1;                       -- проходит
ROLLBACK;

BEGIN; SET LOCAL lock_timeout = '500ms';
UPDATE ws_client SET id = 2 WHERE id = 1;                              -- 55P03: смена ключа ждёт A
ROLLBACK;

BEGIN;
SELECT * FROM ws_client WHERE id = 1 FOR UPDATE NOWAIT;                -- 55P03 could not obtain lock on row
ROLLBACK;

BEGIN;
SELECT * FROM ws_client WHERE id = 1 FOR NO KEY UPDATE NOWAIT;         -- проходит
ROLLBACK;

Что должно получиться: проверка внешнего ключа при вставке платежа поставила на строку клиента FOR KEY SHARE. Он запрещает удалять клиента и менять его ключ, но не мешает обычным изменениям других полей: UPDATE поля risk берёт FOR NO KEY UPDATE, и эти режимы совместимы. А явный FOR UPDATE конфликтует с FOR KEY SHARE, поэтому привычка писать SELECT ... FOR UPDATE для «заблокировать клиента на время операции» на самом деле блокирует и все вставки платежей этого клиента. Если нужно лишь не дать изменить строку параллельно, хватит FOR NO KEY UPDATE.

Попробуйте сами: пока транзакция A открыта, выполните в A SELECT locktype, mode FROM pg_locks WHERE pid = pg_backend_pid() AND relation = 'ws_client'::regclass;. Вы увидите только табличный RowShareLock. Строчная блокировка в pg_locks не видна, потому что хранится в заголовке самой строки (раздел 7.2 главы); посмотреть её можно расширением pgrowlocks.

Способ 2. Программа на JDBC: три воркера разбирают очередь платежей

Триста задач, три воркера, каждый берёт пачку по десять, «отправляет платёж» (2 мс на задачу), записывает отправку в журнал ws_done и помечает задачи выполненными. Опыт повторяется тремя способами выборки: без блокировки, с FOR UPDATE и с FOR UPDATE SKIP LOCKED. Журнал отправок показывает главное: сколько платежей ушло дважды.

Java
import java.sql.*;
import java.util.*;
import java.util.concurrent.*;

public class TaskQueue {
    static final String URL = System.getProperty("ws.url", "jdbc:postgresql://localhost:5432/postgres");
    static final String PASS = System.getProperty("ws.pass", "dev");
    static final int TASKS = 300, WORKERS = 3, BATCH = 10;

    public static void main(String[] args) throws Exception {
        run("1. SELECT без блокировки, потом UPDATE", "");
        run("2. SELECT ... FOR UPDATE", " FOR UPDATE");
        run("3. SELECT ... FOR UPDATE SKIP LOCKED", " FOR UPDATE SKIP LOCKED");
    }

    static void run(String name, String lockClause) throws Exception {
        try (Connection c = conn(); Statement s = c.createStatement()) {
            s.execute("DROP TABLE IF EXISTS ws_task");
            s.execute("CREATE TABLE ws_task (id bigserial PRIMARY KEY, status text NOT NULL DEFAULT 'NEW', worker text)");
            s.execute("INSERT INTO ws_task(status) SELECT 'NEW' FROM generate_series(1, " + TASKS + ")");
            s.execute("DROP TABLE IF EXISTS ws_done");
            s.execute("CREATE TABLE ws_done (task_id bigint, worker text)");   // журнал «отправленных платежей»
        }
        ExecutorService pool = Executors.newFixedThreadPool(WORKERS);
        long t0 = System.nanoTime();
        List<Future<Integer>> results = new ArrayList<>();
        for (int w = 1; w <= WORKERS; w++) {
            String worker = "воркер-" + w;
            results.add(pool.submit(() -> {
                int processed = 0;
                try (Connection c = conn()) {
                    c.setAutoCommit(false);
                    while (true) {
                        List<Long> ids = new ArrayList<>();
                        try (ResultSet rs = c.createStatement().executeQuery(
                                "SELECT id FROM ws_task WHERE status = 'NEW' ORDER BY id LIMIT " + BATCH + lockClause)) {
                            while (rs.next()) ids.add(rs.getLong(1));
                        }
                        if (ids.isEmpty()) { c.commit(); break; }
                        for (long id : ids) {
                            Thread.sleep(2);                                    // «отправка платежа во внешнюю систему»
                            try (PreparedStatement ins = c.prepareStatement("INSERT INTO ws_done VALUES (?, ?)")) {
                                ins.setLong(1, id); ins.setString(2, worker); ins.executeUpdate();
                            }
                        }
                        try (PreparedStatement up = c.prepareStatement("UPDATE ws_task SET status = 'DONE', worker = ? WHERE id = ANY (?)")) {
                            up.setString(1, worker); up.setArray(2, c.createArrayOf("bigint", ids.toArray())); up.executeUpdate();
                        }
                        c.commit();
                        processed += ids.size();
                    }
                }
                return processed;
            }));
        }
        StringBuilder per = new StringBuilder();
        for (Future<Integer> f : results) per.append(f.get()).append(' ');
        pool.shutdown();
        long ms = (System.nanoTime() - t0) / 1_000_000;
        try (Connection c = conn(); ResultSet rs = c.createStatement().executeQuery(
                "SELECT count(*), count(DISTINCT task_id), (SELECT count(*) FROM ws_task WHERE status <> 'DONE') FROM ws_done")) {
            rs.next();
            System.out.printf("%-40s отправлено %d, уникальных задач %d, дублей %d, не сделано %d; по воркерам: %s| %d мс%n",
                    name, rs.getInt(1), rs.getInt(2), rs.getInt(1) - rs.getInt(2), rs.getInt(3), per, ms);
        }
    }

    static Connection conn() throws SQLException { return DriverManager.getConnection(URL, "postgres", PASS); }
}

Два прогона на стенде:

1. SELECT без блокировки, потом UPDATE   отправлено 900, уникальных задач 300, дублей 600, не сделано 0; по воркерам: 300 300 300 | 1466 мс
2. SELECT ... FOR UPDATE                 отправлено 300, уникальных задач 300, дублей 0, не сделано 0; по воркерам: 0 150 150 | 1420 мс
3. SELECT ... FOR UPDATE SKIP LOCKED     отправлено 300, уникальных задач 300, дублей 0, не сделано 0; по воркерам: 100 100 100 | 509 мс

1. SELECT без блокировки, потом UPDATE   отправлено 900, уникальных задач 300, дублей 600, не сделано 0; по воркерам: 300 300 300 | 1454 мс
2. SELECT ... FOR UPDATE                 отправлено 300, уникальных задач 300, дублей 0, не сделано 0; по воркерам: 150 150 0 | 1409 мс
3. SELECT ... FOR UPDATE SKIP LOCKED     отправлено 300, уникальных задач 300, дублей 0, не сделано 0; по воркерам: 100 100 100 | 509 мс

Наивный вариант отправил каждый платёж трижды: все три воркера читали одни и те же десять строк, и никто никому не мешал. Это 600 лишних переводов на 300 задач, и все задачи при этом честно помечены выполненными. FOR UPDATE убрал дубли, но превратил три воркера в один: пока воркер держит пачку, остальные ждут те же строки, а один воркер в каждом прогоне вообще не получил работы (после ожидания он перечитывает строки, видит DONE и выпадает из выборки). Время то же, что у наивного варианта, то есть параллельность пропала. SKIP LOCKED раздал задачи поровну, по 100, без дублей и втрое быстрее: каждый воркер пропускает чужие строки и сразу берёт следующие свободные.

Попробуйте сами: сделайте так, чтобы каждая десятая пачка один раз падала после «отправки», а саму отправку пишите через второе соединение с автокоммитом, как настоящий вызов внешней системы. В цикле воркера откройте Connection ext = conn() рядом с c, вставляйте в ws_done через ext, а сразу после выборки добавьте:

Java
if (ids.get(0) % 100 == 1 && !failed.contains(ids.get(0))) {   // каждая десятая пачка падает один раз
    failed.add(ids.get(0));
    for (long id : ids) { /* «отправить платёж» через ext, как в основном цикле */ }
    c.rollback();
    continue;
}

где failed — общий для воркеров ConcurrentHashMap.newKeySet(). На стенде вышло так:

3. SELECT ... FOR UPDATE SKIP LOCKED     отправлено 330, уникальных задач 300, дублей 30, не сделано 0; по воркерам: 100 100 100 | 605 мс

Откат вернул задачи трёх упавших пачек в очередь, их подобрали и выполнили, и ни одна задача не потерялась. А тридцать «отправок» из упавших пачек остались: внешнюю систему откат базы не касается. Отсюда правило настоящих очередей: у каждой задачи есть ключ идемпотентности, и получатель отбрасывает повтор с тем же ключом. Внешние вызовы внутри транзакции разобраны в разделе 13 главы.
