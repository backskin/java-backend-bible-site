Приложение закрывает один конкретный пробел. Вакансии на стыке Java и ИИ почти всегда пишут «Python будет плюсом» или «знание Python», и на интервью спрашивают не синтаксис, а понимание: чем Python отличается от Java по устройству, где он на самом деле нужен рядом с бэкендом и что вы с ним уже делали. Книга в целом про Java и Kotlin, поэтому здесь не учебник языка, а карта перехода: что в Python устроено иначе, какие ловушки подстерегают человека с опытом Java, как организовать окружение, как вызвать модель, как написать оценку качества на pytest и как поднять тонкий сервис вокруг модели.

Все примеры запущены на Python 3.14.3 под Windows, модель и эмбеддинги работают на Ollama в кластере kind (см. главу 78), выводы приведены как получены. Это те же qwen2.5:1.5b и bge-m3, что и в главе 78, поэтому числа можно сопоставлять.

F1. Место Python рядом с Java-бэкендом

Python в связке с бэкендом занимает три места, и интервьюер обычно проверяет, что вы их различаете.

Первое место: подготовка и исследование. Нарезка документов, подбор порога близости, прогон оценки качества на сотне примеров, разведка новой модели и обработка выгрузок. Здесь важны скорость написания и готовые библиотеки, а производительность и поддерживаемость на годы вперёд не нужны. Скрипт на сорок строк, который вы запустили пять раз и выбросили, пишется на Python быстрее, чем проект на Java.

Второе место: сам инструментарий вокруг моделей. Большая часть библиотек для обучения, дообучения и запуска моделей, а также оценочные и экспериментальные инструменты появляются сначала на Python. Если вам нужно что-то выжать из модели за пределами HTTP-вызова, вы с большой вероятностью будете читать Python-код.

Третье место: небольшие сервисы-обёртки. Вокруг модели или конвейера поднимают тонкий HTTP-сервис, который отдаёт результат Java-системе по REST. Такой сервис живёт отдельным процессом, а граница с Java проходит по контракту (OpenAPI), что даёт возможность заменить любую из сторон.

Где Python не нужен: ядро бизнес-логики, транзакционные операции с деньгами, высоконагруженные синхронные сервисы. Там остаётся Java с её типами, зрелыми профилировщиками и предсказуемой моделью потоков. Честный ответ на вопрос «почему не написать всё на Python» звучит так: можно, но проверка типов в Python происходит снаружи (анализатором), поток исполнения упирается в блокировку интерпретатора (раздел F7), а для денег и отказоустойчивости вам нужны гарантии, которые в Java дают компилятор и модель памяти.

❓ Спрашивают на интервью. Когда бы вы выбрали Python, а когда Java для сервиса вокруг LLM? Python берут, когда сервис тонкий, живёт недолго или опирается на библиотеку, существующую только на Python, и когда команде нужна скорость эксперимента. Java берут, когда сервис станет частью основного контура: транзакции, нагрузка, строгий контракт, уже настроенные мониторинг, безопасность и сборка. Хороший ответ называет границу: общаются по HTTP с описанным контрактом, а не переписывают одну сторону под другую.

F2. Синтаксис за вечер: соответствия Java ↔ Python

Таблица для быстрого перехода. В левой колонке то, что вы пишете на Java каждый день.

Ниже сокращённый вариант запущенного примера. Для каждой идиомы в комментарии записан эквивалент на Java.

Python
from dataclasses import dataclass
from decimal import Decimal

@dataclass(frozen=True)                       # record Payment(String id, long amountMinor, String currency)
class Payment:
    id: str
    amount_minor: int
    currency: str = "RUB"

    def fee_minor(self) -> int:               # self — это явный this
        return round(self.amount_minor * 0.015)

payments = [Payment("p-1", 150_000), Payment("p-2", 20_000, "USD"), Payment("p-3", 5_000)]

# stream().filter(...).map(...).toList()
rub_amounts = [p.amount_minor for p in payments if p.currency == "RUB"]

# groupingBy(Payment::currency, summingLong(Payment::amountMinor))
by_currency: dict[str, int] = {}
for p in payments:
    by_currency[p.currency] = by_currency.get(p.currency, 0) + p.amount_minor

first, *rest = payments                       # распаковка; в Java аналога нет
maybe = next((p for p in payments if p.currency == "EUR"), None)   # Optional.empty()
print("float:", 0.1 + 0.2, "| Decimal:", Decimal("0.1") + Decimal("0.2"))
print("7 / 2 =", 7 / 2, "| 7 // 2 =", 7 // 2, "| -7 // 2 =", -7 // 2, "| -7 % 2 =", -7 % 2)

Вывод запуска:

по валютам: {'RUB': 155000, 'USD': 20000}
p-1: 150000 коп., комиссия 2250 коп.
p-2: 20000 коп., комиссия 300 коп.
p-3: 5000 коп., комиссия 75 коп.
первый: p-1 остальные: ['p-2', 'p-3'] последние два: ['p-2', 'p-3']
платёж в евро найден: False
ошибка разбора: invalid literal for int() with base 10: '12,5'
float: 0.1 + 0.2 = 0.30000000000000004 | Decimal: 0.3
7 / 2 = 3.5 | 7 // 2 = 3 | -7 // 2 = -4 | -7 % 2 = 1
срез: Пла | длина: 6 | в верхнем регистре: ПЛАТЁЖ
по убыванию суммы: ['p-1', 'p-2', 'p-3']
генератор: [0, 1, 4, 9, 16]

Два результата, о которые спотыкается человек из Java. Первый: / всегда возвращает float, а целочисленное деление записывается //. Второй: // округляет вниз, а не к нулю: -7 // 2 это -4, а не -3, и остаток -7 % 2 это 1; в Java -7 / 2 даёт -3, а -7 % 2 даёт -1. Расхождение важно, когда вы переписываете расчёт сумм или календарную арифметику.

🎲 Неочевидно. Одна и та же сумма в float и в Decimal расходится уже на втором знаке цепочки операций. Запуск показал классический результат: 0.1 + 0.2 равно 0.30000000000000004, а сумма Decimal("0.1") + Decimal("0.2") равна 0.3. Но ловушка в другом: Decimal(0.1) (число, а не строка) даст длинный «хвост», потому что число 0.1 уже было неточным до передачи. Деньги всегда создают из строки или из целого числа минимальных единиц. Тот же приём работает и в Java: new BigDecimal("0.1"), а не new BigDecimal(0.1).1

❓ Спрашивают на интервью. Чем is отличается от == в Python и почему is для строк и чисел опасен? == сравнивает значения (вызывает __eq__), is сравнивает тождество объектов, то есть ссылки. Интерпретатор кэширует малые целые и может повторно использовать одинаковые строки, поэтому is для них иногда даёт True, а иногда нет, и результат зависит от версии и от способа создания значения. is применяют только для сравнения с None, True и False.2

F3. Ловушки Python для человека из Java

Каждая из семи воспроизведена запуском. Это те места, где опыт Java подсказывает неверный ответ.

Python
# 1. Изменяемое значение по умолчанию создаётся один раз, при определении функции
def add_item(item, bucket=[]):
    bucket.append(item)
    return bucket
print(add_item("a"), add_item("b"))

# 2. Замыкания в цикле захватывают переменную, а не её значение
functions = [lambda: i for i in range(3)]
print([f() for f in functions])
functions = [lambda i=i: i for i in range(3)]      # привязка значения через аргумент по умолчанию
print([f() for f in functions])

# 3. is и малые числа
print(int("1000") is int("1000"), int("100") is int("100"))

# 4. Ложные значения
print([bool(v) for v in ([], "", 0, None, [0], "0")])

# 7. Подсказка типа не проверяется при выполнении
def double(value: int) -> int:
    return value * 2
print(double("ab"))

Вывод:

1. изменяемый аргумент по умолчанию: ['a', 'b'] ['a', 'b'] (во втором вызове уже два элемента)
2. замыкания в цикле: [2, 2, 2] (ожидали [0, 1, 2])
   с привязкой значения: [0, 1, 2]
3. int('1000') is int('1000'): False | ==: True | для 100: True (малые числа кэшируются, большие нет)
   списки: равны True | один и тот же объект False
4. ложные значения: [False, False, False, False, True, True]
5. два вычисления подряд: 0.26 с; в двух потоках: 0.26 с (выигрыша нет; для процессора нужны процессы или другая версия интерпретатора)
6. 2 ** 100 = 1267650600228229401496703205376 (в Java long переполнился бы)
7. double('ab') = abab (подсказка int не помешала; проверяет только анализатор вроде mypy)

Разбор по порядку. Первая ловушка: список по умолчанию создаётся один раз при определении функции, поэтому второй вызов видит элемент из первого. В Java такого нет, потому что значение по умолчанию там не бывает. Правильный приём: bucket=None и if bucket is None: bucket = [] внутри. Вторая: лямбды в цикле читают переменную i в момент вызова, когда цикл уже закончился и i == 2; поэтому и получилось [2, 2, 2]. В Java этой ловушки нет, потому что захватываемые переменные должны быть эффективно финальными. Третья: на int("1000") дважды получились разные объекты, а на int("100") один и тот же; это деталь реализации, и полагаться на неё нельзя. Четвёртая: пустые коллекции, 0, пустая строка и None считаются ложными, а список [0] и строка "0" нет; поэтому if items: читается как «список не пуст», а вот if value: для числа скрывает ноль как «нет значения». Шестая: целые не переполняются, поэтому код, который в Java ловил бы переполнение, в Python без ошибки продолжит с огромным числом. Седьмая: подсказки типов нужны анализатору и читателю, а не интерпретатору; double("ab") вернул "abab".3

Пятая ловушка главная для тех, кто пишет сервисы, и разобрана в разделе F7.

🎲 Неочевидно. Тест с общим изменяемым значением по умолчанию проходит поодиночке и падает в наборе. Функция с bucket=[] из примера выше накапливает состояние между вызовами, а значит и между тестами одного процесса. Каждый тест по отдельности даёт верный результат, а весь набор в другом порядке падает. В Java такого поведения у метода не бывает, поэтому причину ищут долго. Линтеры (например, правило B006 у flake8-bugbear и ruff) ловят это заранее: ⚠️ не проверено запуском в этой книге.3

❓ Спрашивают на интервью. Что напечатает цикл, который создаёт лямбды с i и вызывает их после цикла? Все значения будут одинаковыми и равными последнему i, потому что замыкание ссылается на переменную, а не на значение. Это вопрос на понимание областей видимости; чинится привязкой значения (lambda i=i: i) или functools.partial.

F4. Окружение: venv, pip и зависимости, если вы привыкли к Maven

В Maven зависимости лежат в локальном репозитории ~/.m2 и общие для всех проектов, версии зафиксированы в pom.xml, транзитивные разрешаются по правилам «ближайшее определение выигрывает». В Python по умолчанию всё ставится в одно общее окружение интерпретатора, и два проекта, которым нужны разные версии одной библиотеки, конфликтуют. Поэтому каждому проекту создают собственное виртуальное окружение (venv), своего рода личный ~/.m2 рядом с проектом.

Bash
python -m venv .venv                                  # создать окружение в каталоге .venv
./.venv/Scripts/python -m pip install requests pytest   # Windows; на Linux и macOS: .venv/bin/python
./.venv/Scripts/python -m pip freeze                  # зафиксировать версии

Результат запуска (фрагмент pip freeze):

Установка двух пакетов принесла ещё восемь транзитивных. Список pip freeze — это аналог зафиксированного дерева зависимостей: его сохраняют в requirements.txt и воспроизводят командой pip install -r requirements.txt. Для проектов с несколькими слоями зависимостей используют pyproject.toml и инструменты вроде uv, poetry или pip-tools; в запуске для этой книги они не использовались: ⚠️ не проверено.4

Практические отличия от Maven, которые стоит знать на собеседовании:

  • Версии без фиксации плавают. pip install requests поставит текущую версию, а через месяц на другой машине поставит другую. Эквивалент «воспроизводимой сборки» достигается только фиксацией (freeze, lock-файл).
  • Нет единого механизма dependencyManagement/BOM. Согласованность набора версий обеспечивает ваш lock-файл.
  • Запускать надо интерпретатор из окружения (.venv/Scripts/python) или активировать окружение, иначе пакеты не найдутся. Частая причина «у меня работает, а в контейнере нет» — запуск не тем интерпретатором.
  • Сборка образа: pip install выполняют на этапе сборки Docker-образа, а в итоговый образ кладут окружение целиком, так же как кладут fat jar.

F5. Вызов модели без библиотек: чат, эмбеддинги, косинус

Запускаемый пример на стандартной библиотеке: только urllib, json и math. Он показывает, что клиент к модели — это обычный HTTP-вызов, и ничего магического в нём нет. Ollama в запуске слушает порт 11434 (через kubectl port-forward).

Python
import json, math, time, urllib.request

BASE = "http://localhost:11434"
MODEL = "qwen2.5:1.5b"
EMBED_MODEL = "bge-m3"

def post(path: str, body: dict, timeout: float = 120) -> dict:
    request = urllib.request.Request(BASE + path, data=json.dumps(body).encode("utf-8"),
                                     headers={"Content-Type": "application/json"})
    with urllib.request.urlopen(request, timeout=timeout) as response:
        return json.load(response)

def chat(prompt: str, temperature: float = 0.0, num_predict: int = 40) -> dict:
    return post("/api/chat", {"model": MODEL, "stream": False,
                              "options": {"temperature": temperature, "num_predict": num_predict},
                              "messages": [{"role": "user", "content": prompt}]})

def embed(text: str) -> list[float]:
    return post("/api/embed", {"model": EMBED_MODEL, "input": text})["embeddings"][0]

def cosine(a: list[float], b: list[float]) -> float:
    dot = sum(x * y for x, y in zip(a, b))
    return dot / (math.sqrt(sum(x * x for x in a)) * math.sqrt(sum(y * y for y in b)))

❓ Спрашивают на интервью. Как посчитать близость двух эмбеддингов и почему обычно берут косинус, а не расстояние? Косинус измеряет угол между векторами и не зависит от их длины: важно направление, то есть смысловая близость. Для нормализованных векторов косинус равен скалярному произведению, и именно его считает векторная база (в pgvector это оператор <=>, расстояние 1 − косинус).5

F6. Оценка качества на pytest: параметризованный тест и порог

Оценка (eval) модели — это тот же тестовый набор, где ожидаемый результат получен от человека, а проверка статистическая. В Python для этого достаточно pytest. Параметризованный тест — аналог @ParameterizedTest JUnit 5 с @MethodSource.

Python
import pytest, requests

BASE = "http://localhost:11434"
MODEL = "qwen2.5:1.5b"
LABELS = ["перевод", "кредит", "карта", "другое"]

CASES = [
    ("Не дошёл перевод по номеру телефона", "перевод"),
    ("Хочу рефинансировать ипотеку", "кредит"),
    ("Карту заблокировали после покупки за границей", "карта"),
    ("Какая сегодня погода?", "другое"),
    ("Отправил деньги не тому человеку", "перевод"),
    ("Нужен график платежей по кредиту", "кредит"),
]

def classify(text: str) -> str:
    prompt = ("Классифицируй обращение клиента банка. Ответь одним словом из списка: " + ", ".join(LABELS)
              + f".\nОбращение: {text}\nКласс:")
    r = requests.post(BASE + "/api/chat", json={"model": MODEL, "stream": False,
                      "options": {"temperature": 0, "num_predict": 8},
                      "messages": [{"role": "user", "content": prompt}]}, timeout=120)
    r.raise_for_status()
    answer = r.json()["message"]["content"].strip().lower()
    return next((label for label in LABELS if label in answer), "?")

@pytest.mark.parametrize("text,expected", CASES)
def test_case(text, expected):
    assert classify(text) == expected

def test_accuracy_gate():
    hits = sum(classify(t) == e for t, e in CASES)
    accuracy = hits / len(CASES)
    print(f"\naccuracy = {hits}/{len(CASES)} = {accuracy:.2f}")
    assert accuracy >= 0.6

Результат поучителен сразу двумя вещами. Модель на 1,5 миллиарда параметров ошиблась на фразе про блокировку карты и назвала её «другое». Поштучный тест на этом падает, а суммарный порог (accuracy >= 0.6, фактически 0,83) проходит. Это и есть разница между двумя видами проверок: поштучная фиксирует регрессию на конкретном примере (хорошо для регрессионного набора, который вы расширяете после каждого инцидента), а порог принимает или отклоняет модель целиком (хорошо для выбора между моделями и для ворот в CI). Смешивать их нельзя: если поштучные тесты красные «ожидаемо», сборка перестаёт быть сигналом. Поэтому в практике разделяют регрессионный набор (должен быть зелёным всегда) и оценочный набор (проверяется порогом и сравнивается между версиями).

Что отличается от привычного JUnit: assert — обычный оператор, pytest сам разбирает выражение и печатает значения; тестовая оснастка (fixtures в pytest) подключается по имени аргумента, без аннотаций и расширений; идентификаторы параметризованных тестов строятся из данных (здесь они в юникоде, и в выводе консоли превращались в К...).

В запуске такого не случилось, но малая модель может ответить фразой «Это обращение о карте». В примере поиск ведётся подстрокой, поэтому «карте» не найдётся по метке «карта»: сравнение по подстроке чувствительно к склонению. Для боевого кода просят у модели структурный вывод (JSON-схема, глава 78, раздел о структурном выводе) и проверяют значение по перечислению, а не ищут слова в свободном тексте.

F7. Параллелизм: GIL, потоки, asyncio и почему здесь это важно для вызовов модели

В Python 3.14.3, который использовался в запусках, обычная сборка работает с глобальной блокировкой интерпретатора (GIL): sys._is_gil_enabled() вернул True. Блокировка не даёт двум потокам одновременно исполнять байт-код Python, поэтому потоки не ускоряют вычисления, нагружающие процессор. Запуск ловушки 5: два вычисления подряд заняли 0,26 с, те же два в двух потоках тоже 0,26 с. В Java два потока на двух ядрах дали бы почти двукратный выигрыш.

Блокировка отпускается на операциях ввода-вывода, поэтому потоки работают для сетевых вызовов. Здесь встречается вторая ловушка, на этот раз общая для Java и Python: ускоряет ли параллельный вызов клиента, если узкое место на сервере. Запуск шести запросов к модели:

Python
def sequential() -> float:
    t0 = time.perf_counter()
    for p in PROMPTS: one(p)
    return time.perf_counter() - t0

def with_threads(workers: int) -> float:
    t0 = time.perf_counter()
    with ThreadPoolExecutor(max_workers=workers) as pool:
        list(pool.map(one, PROMPTS))
    return time.perf_counter() - t0

async def with_asyncio() -> float:
    t0 = time.perf_counter()
    await asyncio.gather(*(asyncio.to_thread(one, p) for p in PROMPTS))
    return time.perf_counter() - t0
последовательно: 1.20 с
пул из 3 потоков: 1.10 с
пул из 6 потоков: 1.10 с
asyncio.gather + to_thread: 1.11 с

Ускорения почти нет: 1,20 против 1,10. Причина не в Python. Ollama в этой установке обрабатывает запросы к одной модели по очереди на процессоре, и клиентский параллелизм упирается в сервер. Это тот же вывод, что в главе 78 про ограничение параллелизма: сначала измерьте пропускную способность сервера, а потом решайте, сколько потоков на клиенте, иначе вы только увеличите очередь и задержку каждого запроса. У платного API-провайдера картина противоположная: там сервер принимает много запросов параллельно, и пул потоков или asyncio дают почти линейный выигрыш до лимита квоты.

Сопоставление с Java:

Задача Java Python
Много ожидающих сетевых вызовов виртуальные потоки (Java 21), StructuredTaskScope asyncio или ThreadPoolExecutor
Нагрузка на процессор в нескольких потоках обычные потоки, ускорение есть multiprocessing (процессы), потоки не помогают при GIL
Состояние между потоками synchronized, java.util.concurrent те же проблемы; плюс GIL не делает составные операции атомарными

Свободная от GIL сборка (free-threaded) существует и документирована, но она отдельная, а не включена по умолчанию: ⚠️ в этой книге она не запускалась, проверьте по странице документации, какая сборка у вас.7

🎲 Неочевидно. Асинхронный код блокируется одним синхронным вызовом. В asyncio нельзя вызывать блокирующую функцию (requests.post, чтение файла, тяжёлое вычисление) прямо из корутины: она остановит весь цикл событий, и все остальные запросы сервиса встанут. Поэтому блокирующий вызов отдают в поток (asyncio.to_thread, как в примере) или берут асинхронный клиент (в разделе F8 используется httpx.AsyncClient). Тот же класс ошибки в Java встречается с виртуальными потоками, когда вызов «закрепляет» поток-носитель.

❓ Спрашивают на интервью. Что такое GIL и когда он мешает? Это блокировка в основной реализации Python (CPython), разрешающая исполнять байт-код только одному потоку в момент времени. Она не мешает вводу-выводу (при ожидании сети блокировка отпускается), но делает бессмысленными потоки для вычислений на процессоре; тогда берут процессы или вычисления в нативных библиотеках, которые отпускают блокировку.7

F8. Тонкий сервис вокруг модели: FastAPI и контракт

Типичный сервис-обёртка: принять JSON, проверить, вызвать модель, вернуть типизированный ответ. На Python для этого используют FastAPI и pydantic: модель данных описывается классом, валидация и OpenAPI-схема получаются автоматически. Сервис в запуске поднимался командой uvicorn service:app --port 8092, версии из окружения: fastapi 0.156.2, uvicorn 0.54.0, pydantic 2.14.1, httpx 0.28.1.

Python
import httpx
from fastapi import FastAPI
from pydantic import BaseModel, Field

BASE = "http://localhost:11434"
app = FastAPI(title="support-classifier")

class Ticket(BaseModel):
    text: str = Field(min_length=3, max_length=2000)

class Verdict(BaseModel):
    label: str
    raw: str

@app.post("/classify", response_model=Verdict)
async def classify(ticket: Ticket) -> Verdict:
    prompt = ("Классифицируй обращение клиента банка. Ответь одним словом: перевод, кредит, карта или другое.\n"
              f"Обращение: {ticket.text}\nКласс:")
    async with httpx.AsyncClient(timeout=60) as client:
        r = await client.post(BASE + "/api/chat", json={"model": "qwen2.5:1.5b", "stream": False,
                              "options": {"temperature": 0, "num_predict": 8},
                              "messages": [{"role": "user", "content": prompt}]})
    raw = r.json()["message"]["content"].strip()
    label = next((l for l in ("перевод", "кредит", "карта", "другое") if l in raw.lower()), "другое")
    return Verdict(label=label, raw=raw)

Для Java-разработчика это аналог @Valid с Bean Validation и springdoc-openapi, только без настройки и аннотаций на параметрах.

Но вторая строка вывода выявила то, что нельзя пропустить: вопрос про футбол модель классифицировала как «перевод», хотя метка «другое» существует. Малая модель с коротким ответом (num_predict 8) не умеет отказываться, а вывод "перевод" внешне нормален и никаких ошибок не вызывает. Если поверх такого ответа принимают решение (например, направляют обращение в очередь переводов), ошибка тихая. Защита та же, что в главе 79: оценка на размеченном наборе, порог уверенности, возможность ответа «не знаю» и ручная проверка выборки.

Сравнение с Spring: тот же сервис на Spring Boot — это контроллер, record для запроса с @Size, WebClient или RestClient для вызова модели и springdoc для схемы; по объёму кода они сопоставимы, а по эксплуатации Java-вариант вписывается в уже настроенный у вас контур (метрики Micrometer, трассировка, безопасность). Поэтому на собеседовании корректный ответ звучит «Python-сервис для эксперимента и вспомогательных задач, Java для того, что становится частью основного контура».

🎲 Неочевидно. Корректный с виду ответ модели с неверной меткой не вызывает ни одной ошибки. В запуске футбольный вопрос получил метку перевод, код ответил 200 OK, и в логах сервиса ничего подозрительного. Единственный способ заметить дефект — оценка на данных, для которых вы знаете правильный ответ. Поэтому в сервис добавляют метрику распределения меток: внезапный перекос в сторону одной метки — признак деградации раньше, чем придёт жалоба.

❓ Спрашивают на интервью. Как сделать контракт сервиса на Python проверяемым для Java-потребителя? Описать вход и выход классами pydantic: FastAPI публикует /openapi.json, по нему Java-сторона генерирует клиент или проверяет контрактными тестами (глава 81, раздел 11). Версию схемы держат в репозитории рядом с кодом и сравнивают при сборке, чтобы несовместимое изменение ломало сборку, а не прод.8

F9. Python на собеседовании Java-разработчика

Короткая версия ответа, которую можно проговорить за минуту. «Основной язык у меня Java и Kotlin, Python использую точечно: скрипты для разведки и оценки, небольшие сервисы вокруг моделей. Я понимаю, чем он отличается по устройству: GIL и потому процессы для вычислений, изменяемые значения по умолчанию, динамическая типизация с подсказками, виртуальные окружения вместо общего репозитория зависимостей. В запусках я вызывал модель по HTTP без библиотек, писал оценку на pytest с порогом точности и поднимал FastAPI-обёртку с контрактом. Если задача идёт в основной контур, оставляю её на Java и общаюсь с Python-частью по описанному HTTP-контракту».

Чего не говорить. Не утверждайте, что «Python медленный и поэтому не годится»: тяжёлые вычисления в нём выполняют нативные библиотеки, а накладные расходы интерпретатора на фоне ожидания модели не заметны. Не утверждайте и обратного, что «потоки в Python работают как в Java». И не называйте опыт, которого не было: проще честно сказать, что писали скрипты и тонкие сервисы, чем попасть на вопрос про asyncio или упаковку, не имея за спиной практики.
